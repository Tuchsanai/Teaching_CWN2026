# skill-optimizer — วัด → หาสาเหตุ → แก้ → วัดซ้ำ → ประตูรับ

`O=<โฟลเดอร์ของ SKILL.md นี้>/scripts/skillopt.py` · Python 3.8+ stdlib · รันโจทย์ผ่านคำสั่ง `yoloN` ตามกติกาของ base skill `yolo` (ต้องล็อกอินแล้ว ห้ามล็อกอินแทนผู้ใช้)

| ต้องการ | คำสั่ง | ใช้โทเคน |
|---|---|---|
| วัดขนาดและต้นทุนบริบทของสกิล | `python3 $O lint <โฟลเดอร์สกิล>` | ไม่ใช้ |
| รันสกิลกับชุดโจทย์ | `python3 $O run <suite> --skill <โฟลเดอร์สกิล> --label v0 --reps 2 --accounts yolo2,yolo3` | **ใช้** |
| รันแบบไม่มีสกิล (เส้นฐาน) | `python3 $O run <suite> --skill none --label noskill` | **ใช้** |
| ดูข้อที่พลาด + path ของร่องรอย | `python3 $O failures <suite> --label v0 --split train` | ไม่ใช้ |
| ตารางเทียบรุ่น + `results.json` | `python3 $O report <suite> --labels v0,v1` | ไม่ใช้ |
| ความแกว่งของรุ่นเดียวกัน (A/A) | `python3 $O null <suite> --label v0` | ไม่ใช้ |
| รับหรือไม่รับรุ่นใหม่ | `python3 $O gate <suite> --base v0 --cand v1` (exit 0 = รับ) · เลือกตัวชี้วัดต้นทุน: `--cost-metric cost_usd` (ค่าเริ่มต้น) `tool_calls` `context_tokens` | ไม่ใช้ |
| ตรวจซ้ำหลังแก้ตัวตรวจ | `python3 $O grade <suite> --label v0` | ไม่ใช้ |

`<suite>` = โฟลเดอร์ที่มี `suite.json` (พรอมต์ + โจทย์ที่แบ่ง `train` / `val`) และตัวตรวจ `grade.py` · รูปแบบไฟล์: [references/suite.md](references/suite.md)
ผลของแต่ละรอบ: `<suite>/runs/<label>/<โจทย์>-r<รอบ>/` มี `sandbox/` (ผลงาน) `transcript.jsonl` (ร่องรอย) `metrics.json` `grade.json`

## ขั้นตอน (ทำตามลำดับ ห้ามข้าม)

1. **เส้นฐาน** `lint` สกิลเดิม แล้ว `run` ด้วย `--label v0 --reps 2` (ทุกโจทย์ ทั้ง train และ val) · ถ้าผู้ใช้อยากรู้ว่าสกิลคุ้มไหม ให้ `run --skill none` ด้วย
2. **ความแกว่ง** `null --label v0` จดค่า "ความแกว่งของค่าเฉลี่ย" ไว้ ส่วนต่างที่น้อยกว่านี้ถือว่าไม่ต่าง
3. **หาสาเหตุ** `failures --label v0 --split train` แล้วเปิด `transcript.jsonl` และไฟล์ใน `sandbox/` ของรอบที่พลาด **เฉพาะชุด train** · ห้ามเปิดผลรายข้อของชุด val ระหว่างแก้
4. **จดสมุดปัญหา** เขียน `ISSUES.md` ข้างสกิล: ปัญหา · พบกี่รอบจากกี่รอบ · สาเหตุ · ทางแก้ที่ลอง · ผล (รูปแบบ: [references/issues.md](references/issues.md)) ปัญหาที่พบรอบเดียวยังไม่ต้องแก้
5. **แก้ไม่เกิน 3 จุดต่อรุ่น** คัดลอกสกิลเป็นโฟลเดอร์ใหม่ (`v1`) แล้วแก้ตามลำดับความคุ้มนี้ · ก่อนแก้ ถ้าข้อตรวจใดดูผิดปกติ ให้เปิดผลงานใน `sandbox/` ดูว่าเป็นความผิดของสกิลหรือของตัวตรวจ (ตัวตรวจผิด → แก้ตัวตรวจ แล้ว `grade` ซ้ำทุกรุ่น)
   - ให้สคริปต์ตรวจและเตือนเอง (ข้อความเตือนบอกวิธีแก้) ดีกว่าเพิ่มกติกาให้ AI จำ
   - กติกาที่ระบุคำสั่ง ไฟล์ หรือค่าที่ตรวจได้ ดีกว่าคำแนะนำกว้าง ๆ
   - ลบหรือรวมกติกาที่ซ้ำหรือไม่เคยมีผล สกิลต้องไม่ยาวขึ้นโดยไม่มีเหตุผล
   - ห้ามใส่คำตอบหรือชื่อเฉพาะของโจทย์ชุด train ลงในสกิล
6. **วัดซ้ำ** `run --label v1` ด้วย `--reps` `--model` `--effort` เดียวกับ v0 ทุกค่า
7. **ประตูรับ** `gate --base v0 --cand v1` · REJECT → ใช้รุ่นเดิมต่อ จดผลลงสมุดปัญหา แล้วลองทางแก้อื่น (ห้ามแก้ตัวตรวจหรือโจทย์เพื่อให้ผ่าน)
8. **รายงาน** `report --labels v0,v1` แล้วสรุปให้ผู้ใช้: ตารางเทียบ · จุดที่แก้ · ผลประตู · ปัญหาที่ยังเปิดอยู่

## ประตูรับตัดสินอย่างไร

- ชุด train และชุด val ต้องไม่ลดลงเกินเกณฑ์ (เกณฑ์ = ค่าที่มากกว่าระหว่าง `--eps` 2 จุด กับความแกว่งของค่าเฉลี่ยของรุ่นฐาน)
- คะแนนรวมต้องดีขึ้นมากกว่าเกณฑ์ **หรือ** คะแนนเท่าเดิมแต่ต้นทุนลดลงอย่างน้อย 10%
- ต้นทุนวัดได้ 3 แบบ: `cost_usd` ราคาตามรายการ · `tool_calls` จำนวนคำสั่งต่อรอบ · `context_tokens` โทเคนขาเข้าทั้งหมดที่โมเดลต้องอ่าน · **ต้องเลือกและบอกผู้ใช้ก่อนวัดรุ่นใหม่** ห้ามเปลี่ยนหลังเห็นผล
- คะแนนชุด train ขึ้นแต่ชุด val ลง = สกิลจำโจทย์ (overfit) → ไม่รับ

## ข้อห้าม

- ห้ามแก้สกิลต้นฉบับหรือ base skills โดยตรง ทุกรุ่นเป็นโฟลเดอร์ใหม่ (`v1` `v2` …)
- ห้ามเปลี่ยนรุ่นโมเดล effort จำนวนรอบ หรือโจทย์ ระหว่างรุ่นที่จะเทียบกัน
- `run` ใช้โทเคนของบัญชีจริง: บอกจำนวนรอบที่จะรัน (โจทย์ × `--reps`) และถามผู้ใช้ก่อนถ้าเกิน 40 รอบ
- ห้ามอ่านหรือแสดง `.credentials.json` `.claude.json` `auth.json`
- ตัวเลขในรายงานต้องมาจาก `report` / `gate` เท่านั้น ห้ามประมาณ
- เวลา (วินาที) ขึ้นกับภาระของเครื่องและจำนวนรอบที่รันพร้อมกัน ใช้เทียบได้เฉพาะรุ่นที่รันด้วย `--par` เท่ากันและไม่มีงานอื่นรันอยู่
