# หัวหน้าทีมที่สลับตัวได้ (`team.py lead`)

ปัญหา: ถ้าแผนอยู่ในบริบทแชตของหัวหน้า เมื่อโควตาหัวหน้าหมดหรือหยุดกะทันหัน แผนและงานที่ค้างหายไปด้วย
ทางแก้: สถานะอยู่ในไฟล์ ผู้ควบคุมเป็นสคริปต์ หัวหน้าเป็นแค่ "รอบ" สั้น ๆ ที่เปลี่ยนตัวได้ทุกเมื่อ

```bash
python3 team.py lead --goal "คำนวณ 7*6 ด้วยลูกทีม cyolo แล้วนำผลไปบวก 100 ด้วยลูกทีม yolo" \
   --leader yolo1 --succession yolo2,cyolo1 --lead-difficulty 1 \
   [--lead-token-budget 60000] [--quota-threshold 80] [--forbid yolo3] \
   [--max-episodes 8] [--episode-timeout 1200] [--heartbeat-timeout 900]
```

## ส่วนประกอบ

| ส่วน | หน้าที่ |
|---|---|
| ผู้ควบคุม (`lead`) | สคริปต์ ไม่ใช้โทเค็น วนรอบ: เขียน `handoff.md` สด → เรียกหัวหน้า 1 รอบ → ตรวจผล/โควตา/งบ → ตัดสินใจสลับ |
| `state.json` | เป้าหมาย งานทุกชิ้น สถานะ บัญชี หัวหน้าปัจจุบัน `lead.history` `lead.checkpoints` heartbeat |
| `handoff.md` | สำหรับคนรับไม้: ตารางงานสด, บันทึก checkpoint (ทำแล้ว / ต่อไป / การตัดสินใจ), ประวัติการสลับ |
| ลูกทีม | `team.py dispatch` เปิด scheduler เป็น process แยก (`start_new_session`) หัวหน้าตายแล้วยังรันต่อ ผลลง `out/` |

## คำสั่งของหัวหน้า (`T = python3 team.py --run <id>`)

| คำสั่ง | ผล |
|---|---|
| `T add <id> --account <…> --prompt "…" [--depends a,b] [--expect int] [--difficulty 1-6]` | เพิ่มงาน (id ซ้ำ = ไม่เพิ่ม) |
| `T dispatch` | เริ่ม scheduler เบื้องหลังถ้ายังไม่รัน แล้วจบทันที |
| `T wait [ids…] [--timeout 900]` | รอจนงานจบ แสดงค่า/ไฟล์ผล (อัปเดต heartbeat ทุก 20 s) |
| `T checkpoint --done "…" --next "…" [--decision "…"]` | เขียนจุดพักงานลง state + handoff.md |
| `T finish --answer "…"` | จบงาน |
| `T status` | ตารางทีม |

ทุกรอบหัวหน้าทำ: อ่าน handoff → (ยังไม่มีงาน) add ทั้งหมด → dispatch → checkpoint → จบรอบ / (มีงานแล้ว) dispatch → wait → finish หรือ add เพิ่ม + checkpoint

## การสลับ

| ชนิด | เมื่อไร | ผล |
|---|---|---|
| เชิงรุก | หลังจบรอบ: โทเค็นที่หัวหน้าคนนี้ใช้ใน run ≥ `--lead-token-budget` หรือโควตา ≥ `--quota-threshold` | ส่งไม้ให้ผู้สืบทอดตอนที่ checkpoint ยังเขียนทัน |
| เชิงรับ | รอบล้ม (โควตาหมด, rate limit, ล็อกอินหมดอายุ), timeout, heartbeat ไม่อัปเดต, ถูกฆ่า | ย้อนไป checkpoint ล่าสุด (บันทึกใน state) + ตารางงานสด แล้วเริ่มหัวหน้าคนใหม่ |

- ผู้สืบทอด: ตาม `--succession` ที่พร้อม หรืออัตโนมัติ = บัญชีพร้อม ฝั่งเดียวกันก่อน แล้วโควตาเหลือมาก โทเค็นหัวหน้าใช้น้อย · ไม่เลือกบัญชีใน `--forbid` และบัญชีที่เคยล้มเป็นหัวหน้าใน run นี้ · หัวหน้าเป็น Codex ได้
- ทุกการสลับบันทึกใน `state.json` (`lead.history`, `events`), `board.md`, ledger (`event: lead_switch`) และสรุปท้ายคำสั่ง
- งานที่หัวหน้าเก่า add ไว้แล้วอยู่ใน state.json ไม่หาย งานที่ dispatch แล้วรันต่อ หัวหน้าใหม่แค่ `wait`

## ทดสอบโดยไม่เผาโควตาจริง

| จำลอง | วิธี |
|---|---|
| โควตาหัวหน้าหมด | `MA_SIMULATE_LIMIT=yolo1:2` → การเรียก yolo1 ครั้งที่ 2 เป็นต้นไปล้มแบบ limit ทันที (0 tokens) |
| หัวหน้าตายกลางรอบ | `MA_SIMULATE_CRASH=lead_after_dispatch` → ผู้ควบคุมฆ่าหัวหน้ารอบแรก (ทั้ง process group) ทันทีที่เห็นว่าสั่ง dispatch แล้ว — ถ้าหัวหน้าเรียก checkpoint ต่อในคำสั่งเดียวกันอาจทันบันทึกก่อน |

ผลทดสอบจริง (2026-11-08, หัวหน้า haiku/low): เชิงรุก yolo2 → yolo1 (งบ 1 token) จบ 142 ใน 19 s · เชิงรับ yolo1 ถูกฆ่าหลัง dispatch → cyolo1 (หัวหน้า Codex) และ → yolo2 (เลือกอัตโนมัติ) จบ 142 ทั้งคู่ งาน a, b ที่หัวหน้าเก่าสั่งรันจบหลังหัวหน้าตายและไม่ถูกเพิ่มซ้ำ
| ส่งไม้เชิงรุก | `--lead-token-budget 1` → หลังรอบแรกสลับทันที |
