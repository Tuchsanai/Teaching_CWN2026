# สเปกสกิลควบคุมระบบหลายบัญชี (yolo · cyolo · agent-team)

> สเปกนี้รวบรวมจากการทดลองจริงกับ container `multi-account` (Claude Code 2.1.319 · codex-cli 0.167.0) สกิลสร้างจากศูนย์ ไม่มีสกิลชุดเก่าให้อ้างอิง ข้อเท็จจริงทุกข้อต้องตรวจกับ `--help` และการเรียกจริงของเวอร์ชันที่ใช้อยู่ก่อนเขียนลงสกิล

## เป้าหมาย

สร้างโฟลเดอร์ `./skills` ที่มี 3 สกิล ทำงานร่วมกัน และติดตั้งลง container ได้ด้วยการคัดลอกโฟลเดอร์

| สกิล | รู้เรื่องอะไร |
|---|---|
| `yolo` | Claude Code ทุกบัญชี (`yolo1`…`yoloN`): เรียกแบบไม่โต้ตอบให้ถูกวิธี เลือกรุ่นและ effort ตรวจล็อกอินจริง โควตา และสถิติต่อครั้ง |
| `cyolo` | Codex CLI ทุกบัญชี (`cyolo1`…`cyoloN`): เรียกแบบไม่โต้ตอบ เลือกรุ่นและ effort จาก `models_cache.json` สร้างภาพ ตรวจล็อกอิน โควตา และสถิติต่อครั้ง |
| `agent-team` | ให้หลายบัญชีทำงานร่วมกันแบบ multi-agent ทั้งภายใน CLI เดียวกันและข้าม CLI: ส่งต่องาน ส่งข้อมูล แชร์ความรู้ และสรุปสถิติทั้งทีม |

- แต่ละสกิลเป็นโฟลเดอร์ `SKILL.md` + `scripts/` (+ `references/` เมื่อเนื้อหายาว) สคริปต์เป็น Python 3.8+ ไลบรารีมาตรฐานเท่านั้น
- `SKILL.md` สั้นและตรงประเด็น: เปิดด้วยตาราง "ต้องการ → คำสั่ง" รายละเอียดยาวย้ายไป `references/` (เปิดทีละชั้น)
- `description` เขียนทั้งไทยและอังกฤษ ระบุว่าใช้เมื่อใด (เช่น "เรียก yolo2", "ให้ cyolo ตรวจ", "แบ่งงานหลายบัญชี", "ส่งต่องานระหว่าง agent", "สถิติโทเค็นแต่ละบัญชี")
- `./skills` มี**แค่ 3 โฟลเดอร์สกิล** ไม่มีสคริปต์ติดตั้งหรือไฟล์อื่น ผู้ใช้ติดตั้งด้วยการคัดลอกโฟลเดอร์อย่างเดียว

## ผู้ใช้สกิล 2 ฝั่ง

1. **ใน container:** `yoloN` / `cyoloN` อ่านสกิลจาก `shared/skills` อัตโนมัติ
2. **Claude Code app บน host:** เข้าถึงผ่าน `docker exec <container> ...` เท่านั้น ทุก `SKILL.md` ต้องมีหัวข้อ "เรียกจาก host" บอกรูปแบบ `docker exec -i multi-account python3 <path สคริปต์ใน container> ...` และวิธีให้ host อ่านสกิลก่อนเริ่ม (`docker exec multi-account cat <path>/SKILL.md`)

## ข้อเท็จจริงจากการทดลอง (ตรวจว่ายังจริงกับเวอร์ชันนี้)

### ทั่วไป

- BASE=/root/ai-accounts · บัญชี Claude อยู่ที่ `$BASE/.Claude/yoloN` (`CLAUDE_CONFIG_DIR`) · บัญชี Codex อยู่ที่ `$BASE/.Codex/cyoloN` (`CODEX_HOME`)
- `$BASE` เป็น volume `ai-accounts` จึงคงอยู่แม้ลบ container สกิลที่วางใน `$BASE/.Claude/shared/skills` และ `$BASE/.Codex/shared/skills` จึงคงอยู่ด้วย
- Claude: `$BASE/.Claude/yoloN/skills` อาจเป็น symlink ไปทั้งโฟลเดอร์ `../shared/skills` (volume ที่สร้างก่อนหน้า) หรือเป็นโฟลเดอร์จริงที่มี symlink รายสกิล (volume ใหม่) ทั้งสองแบบ wrapper `yoloN` เชื่อมสกิลใหม่ให้เองทุกครั้งที่เรียก
- Codex: `$BASE/.Codex/cyoloN/skills` เป็นโฟลเดอร์จริง มี symlink รายสกิลไปยัง shared และ Codex เขียน `skills/.system` เอง wrapper `cyoloN` สร้าง symlink ของสกิลใหม่ให้ทุกครั้งที่เรียก (`link_shared_skills`) ห้าม symlink ทั้งโฟลเดอร์
- ทุกบัญชีทำงานเป็น root คนเดียวกัน การแยกบัญชีเป็นระดับโฟลเดอร์

### Claude Code (`yoloN`)

- เรียกงานเดียว: `yoloN -p "<prompt>" --model <alias> --effort <level> --output-format json --no-session-persistence --strict-mcp-config < /dev/null`
- ต้องปิด stdin (`< /dev/null`) และต้องมี `-p` เสมอ · prompt ต้องอยู่ก่อน flag ที่รับหลายค่า (`--allowedTools`, `--add-dir`, `--mcp-config` ฯลฯ) ไม่เช่นนั้น flag จะกลืน prompt
- **exit code 0 ไม่ได้แปลว่าสำเร็จ** ต้องดู `is_error` และ `result`
- **`auth status` บอก `loggedIn: true` แต่เรียกจริงอาจล้ม** ด้วย `Failed to authenticate: OAuth session expired and could not be refreshed` (ตอบกลับใน ~50 ms, tokens = 0) การตรวจความพร้อมต้องเรียกจริงด้วยงานสั้นที่สุด (`haiku`/`low`, "ตอบ OK") แล้วรายงานแยก "ล็อกอินแล้วแต่หมดอายุ"
- JSON ที่ได้: `result`, `is_error`, `duration_ms`, `total_cost_usd` (ราคาตามรายการ ไม่ใช่ยอดจ่ายจริง), `num_turns`, `session_id`, `usage.{input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens}`, `modelUsage.<รุ่นจริง>`
- รุ่น (alias): `opus`, `sonnet`, `haiku`, `fable` · effort: `low` `medium` `high` `xhigh` `max`
- ผลแบบมีโครงสร้าง: `--json-schema '<schema>'` แล้วอ่าน `structured_output`
- บัญชีเดียวรันหลายตัวพร้อมกันได้เมื่อใส่ `--no-session-persistence` ทุกครั้ง โควตาใช้ร่วมกันทั้งบัญชี
- โควตา: `yoloN -p "/usage"` เป็นคำสั่งในตัว (ไม่เรียกโมเดล) ให้บรรทัด `Current session` / `Current week (…)` ตรวจจริงว่ายังเป็นแบบนี้ ถ้าเวอร์ชันนี้ไม่ให้ข้อมูล ให้รายงานว่าไม่มีข้อมูล ห้ามเดา
- ห้ามอ่านหรือส่งต่อ `.credentials.json` และ `.claude.json` ห้ามแสดงอีเมลหรือ orgId

### Codex CLI (`cyoloN`)

- เรียกงานเดียว: `cyoloN exec --skip-git-repo-check --ephemeral -m <model> -c model_reasoning_effort=<level> --json -o <ไฟล์คำตอบ> "<prompt>" < /dev/null`
- คำตอบอยู่ในไฟล์ `-o` · stdout เป็น JSONL: `thread.started`, `turn.started`, `item.completed`, `turn.completed.usage.{input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens}` หรือ `turn.failed.error.message` เมื่อล้ม
- `--ephemeral` เร็วกว่า ~3.5 เท่า แต่ไม่เขียน `sessions/` ข้อมูลโควตาจึงไม่อัปเดต
- โควตาอ่านจาก rollout ล่าสุดที่ไม่ใช่ ephemeral: `$CODEX_HOME/sessions/YYYY/MM/DD/*.jsonl` event `token_count` → `payload.rate_limits.{primary, secondary}.{used_percent, window_minutes, resets_at}` ต้องรายงานเวลาของข้อมูลเสมอ
- สถานะล็อกอินอ่านจากข้อความของ `cyoloN login status` (`Logged in using ChatGPT` / `Not logged in`) ไม่ใช่ exit code · บัญชีที่ไม่ได้ล็อกอินอาจตอบ 401 แล้ว retry แต่ exit 0
- รุ่นและ effort ที่รองรับอ่านจาก `$CODEX_HOME/models_cache.json` (`slug`, `supported_reasoning_levels[].effort`, `default_reasoning_level`) ระดับที่รุ่นไม่รองรับ (เช่น `ultra` บางรุ่น) ให้ลดเป็นระดับสูงสุดที่รองรับและบันทึกว่าลดจากอะไร
- สร้างภาพทำได้ฝั่ง Codex เท่านั้น: สั่ง "สร้างภาพ (image generation) ... บันทึกเป็น PNG ที่ <absolute path>" ใช้ effort `low` (effort สูงไม่ทำให้ภาพดีขึ้น) ตรวจว่าไฟล์ขึ้นต้นด้วย PNG signature
- ห้ามอ่านหรือส่งต่อ `auth.json`

### ความยาก → รุ่นและ effort (ใช้ร่วมกันทั้งสามสกิล)

| difficulty | ลักษณะงาน | Claude | Codex |
|---|---|---|---|
| 1 | ดึงข้อมูล จัดรูปแบบ ตรวจความพร้อม · สร้างภาพ | `haiku` / `low` | `low` |
| 2 | สรุป ถาม-ตอบ แก้โค้ดจุดเดียว | `sonnet` / `medium` | `medium` |
| 3 | แก้โค้ดหลายไฟล์ debug วิเคราะห์ | `opus` / `high` | `high` |
| 4 | reasoning ซับซ้อน อัลกอริทึม | `opus` / `xhigh` | `xhigh` |
| 5 | ต้องถูกแน่นอน | `opus` / `max` | `max` |
| 6 | งานใหญ่ที่ควรแตกงานย่อยเอง | `opus` / `max` | `ultra` (ถ้ารองรับ) |

## agent-team: การทำงานร่วมกันหลายบัญชี

### พื้นที่ทำงานร่วม (run directory)

ทุกงานทีมมีโฟลเดอร์ `/workspace/.agent-team/<run_id>/` (อยู่ใน `./workspace` ที่ map ออกมาบน host)

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `graph.json` | งานทั้งหมดและความสัมพันธ์ |
| `board.md` | กระดานความรู้กลาง ทุก agent อ่านก่อนเริ่ม และเพิ่มข้อค้นพบแบบต่อท้าย (ระบุผู้เขียนและเวลา) |
| `msgs/<จาก>__<ถึง>.md` | ข้อความส่งต่องานระหว่าง agent |
| `out/<node>.md` | ผลลัพธ์ของแต่ละงาน |
| `ledger.jsonl` | สถิติทุกครั้งที่เรียก |
| `state.json` | สถานะของทั้ง run: งานแต่ละชิ้น หัวหน้าคนปัจจุบัน ประวัติการสลับ |
| `handoff.md` | จุดพักงานสำหรับหัวหน้าคนถัดไป |

### รูปแบบการทำงานร่วมกันที่ต้องรองรับ

| รูปแบบ | ความหมาย |
|---|---|
| relay (ส่งต่อ 1→1) | A → B → C ผลของงานก่อนเป็น input ของงานถัดไป |
| fan-out / fan-in | แจกงานให้หลายบัญชีพร้อมกัน แล้วให้ agent หนึ่งรวมผล |
| graph (DAG) | งานมี `depends_on` กี่ตัวก็ได้ งานที่พร้อมรันได้พร้อมกัน |
| review loop | ผู้ทำ ↔ ผู้ตรวจ วนจนผู้ตรวจตอบ `APPROVED` หรือครบ `max_rounds` |
| board | แชร์ความรู้ผ่าน `board.md` ให้ agent ที่มาทีหลังใช้ข้อค้นพบของ agent ก่อนหน้า |

### รูปแบบขั้นสูงที่ต้องรองรับเพิ่ม

| รูปแบบ | ความหมาย |
|---|---|
| debate / ตรวจไขว้ | Claude และ Codex ตอบโจทย์เดียวกันแยกกัน แล้ว agent ผู้ตัดสินเทียบและสรุปคำตอบที่ถูก พร้อมเหตุผล |
| best-of-N + judge | หลายบัญชีทำงานเดียวกัน ผู้ตัดสินให้คะแนนตามเกณฑ์ที่กำหนดแล้วเลือกผลที่ดีที่สุด |
| router | เลือกฝั่งและรุ่นให้อัตโนมัติตามชนิดงานและความยาก (ภาพ → cyolo · ตรวจโค้ด → Codex · เอกสารยาว → Claude) เมื่อ `account` เป็น `any` |
| กระจายโหลดตามโควตา + failover | ส่งงานไปบัญชีที่โควตาเหลือมากที่สุด งานที่ล้มเพราะโควตาหมดหรือล็อกอินหมดอายุ ย้ายไปบัญชีอื่นฝั่งเดียวกันพร้อมบันทึก (ยกเว้นงานที่ผู้ใช้ระบุบัญชีเอง) |
| จุดอนุมัติโดยคน (human gate) | งานที่มี `"approve": true` หยุดรอจนมีไฟล์อนุมัติใน run directory ก่อนรันต่อ |

### การบริหารโทเค็นของลูกทีม

หัวหน้าทีมต้องบริหารโควตาของลูกทีมทุกคน ไม่ใช่แค่ของตัวเอง ตัวจัดคิวใน `team.py` ทำงานเหล่านี้ให้อัตโนมัติ และหัวหน้าทีมดูภาพรวมได้ด้วยคำสั่งเดียว

1. **ก่อนสั่งงาน:** อ่านโควตาล่าสุดของทุกบัญชี (Claude: `Current session` / `Current week` · Codex: `rate_limits`) และยอดโทเค็นที่ใช้ใน run นี้จาก ledger แล้วจัดอันดับว่าใครเหลือมาก
2. **จัดงานให้คุ้ม:** งานง่ายใช้รุ่นและ effort ต่ำตามตารางความยาก กระจายงานให้บัญชีที่เหลือโควตามากก่อน ไม่ให้บัญชีใดรับงานหนักซ้อนจนหมดก่อนคนอื่น
3. **สลับเชิงรุก:** บัญชีที่โควตาเกินเกณฑ์ (ค่าเริ่มต้น session ≥ 80%) หรือเกินงบโทเค็นต่อบัญชี (`--worker-token-budget`) จะ**ไม่ได้รับงานใหม่** งานที่กำลังรันปล่อยให้จบ งานในคิวที่จัดให้บัญชีนั้นย้ายไปบัญชีอื่น
4. **สลับเชิงรับ:** ลูกทีมที่ล้มเพราะโควตาหมด, rate limit หรือล็อกอินหมดอายุ ให้ย้ายงานไปบัญชีอื่นฝั่งเดียวกันก่อน (ไม่มีจึงข้ามฝั่งถ้างานไม่ผูกกับ CLI) งานยาวให้ลูกทีมเขียนความคืบหน้าลง `msgs/` ระหว่างทาง ผู้รับงานต่อจึงไม่ต้องเริ่มจากศูนย์
5. **ไม่สลับเงียบ:** งานที่ผู้ใช้ระบุบัญชีเองไม่ย้ายอัตโนมัติ ให้หยุดและรายงาน ทุกการย้ายงานบันทึกใน `state.json`, `board.md` และ ledger (`event: worker_switch`)
6. **ภาพรวมสำหรับหัวหน้า:** `team.py status` แสดงตาราง บัญชี | บทบาท | งานที่รัน | งานในคิว | tokens ที่ใช้ใน run | โควตาล่าสุด (พร้อมเวลาของข้อมูล) | สถานะ (พร้อม / ใกล้หมด / หยุดรับงาน / ใช้ไม่ได้)

### การสลับหัวหน้าทีม (leader handoff)

ปัญหา: ถ้าแผนงานอยู่ในบริบทแชตของหัวหน้าทีม เมื่อโทเค็นหรือโควตาของบัญชีหัวหน้าหมด หรือหัวหน้าหยุดกะทันหัน แผนและงานที่ค้างจะหายไปด้วย

หลักการออกแบบ:

1. **สถานะอยู่ในไฟล์ ไม่อยู่ในหัวหัวหน้า:** `state.json` (เป้าหมาย งานทั้งหมด สถานะแต่ละงาน หัวหน้าคนปัจจุบัน ประวัติการสลับ) และ `handoff.md` (สรุปสำหรับคนรับไม้: ทำอะไรไปแล้ว อะไรกำลังรัน ขั้นต่อไป การตัดสินใจสำคัญ) อยู่ใน run directory
2. **ผู้ควบคุม (supervisor) เป็นสคริปต์ ไม่ใช้โทเค็น:** `team.py lead` รันหัวหน้าทีมเป็นรอบสั้น ๆ (episode) ทุกรอบหัวหน้าอ่าน `handoff.md` + `state.json` ทำงานหนึ่งช่วง แล้วต้องเขียน checkpoint ก่อนจบรอบ ผู้ควบคุมจึงไม่มีวันหมดโควตาและรู้สถานะเสมอ
3. **ลูกทีมไม่ผูกกับหัวหน้า:** หัวหน้าสั่งงานผ่าน `team.py` ซึ่งรันลูกทีมเป็น process แยกและเขียนผลลง `out/` หัวหน้าเปลี่ยนตัวแล้วงานที่สั่งไปยังรันต่อและผลไม่หาย
4. **สลับเชิงรุก (ก่อนหมด):** ระหว่างรอบ ผู้ควบคุมตรวจโควตาและยอดโทเค็นที่หัวหน้าใช้ไป ถ้าเกินเกณฑ์ (ค่าเริ่มต้น โควตา session ≥ 80% หรือเกินงบโทเค็นต่อหัวหน้าที่กำหนด) ให้ส่งไม้ต่อทันทีตั้งแต่ยังเหลือพอเขียน checkpoint
5. **สลับเชิงรับ (หยุดกะทันหัน):** ถ้ารอบของหัวหน้าล้ม (โควตาหมด, rate limit, ล็อกอินหมดอายุ, timeout หรือ heartbeat ไม่อัปเดต) ผู้ควบคุมย้อนไป checkpoint ล่าสุดแล้วเริ่มหัวหน้าคนใหม่
6. **เลือกผู้สืบทอด:** จากรายชื่อสืบทอด (`--succession`) หรืออัตโนมัติ: บัญชีที่ตรวจแล้วพร้อม โควตาเหลือมากสุด ฝั่งเดียวกันก่อนแล้วจึงข้ามฝั่ง (หัวหน้าเป็น Codex ได้ เพราะสกิลอยู่ทั้งสองฝั่ง) ไม่เลือกบัญชีที่ผู้ใช้ห้าม
7. **บันทึกทุกการสลับ:** เหตุผล เวลา จากใคร ไปใคร ลงใน `state.json`, `board.md` และ ledger (`event: lead_switch`) และแจ้งในสรุปสุดท้าย
8. **ทดสอบได้โดยไม่เผาโควตาจริง:** มีตัวจำลอง เช่น `MA_SIMULATE_LIMIT=yolo1` ทำให้การเรียกบัญชีนั้นล้มเหมือนโควตาหมด และ `--lead-token-budget` ตั้งงบต่ำเพื่อทดสอบการสลับเชิงรุก
9. **ตรวจงบระหว่างรอบ ไม่ใช่แค่หลังจบรอบ:** หัวหน้าที่ทำงานทั้งหมดจบในรอบเดียวต้องยังถูกตรวจงบได้ (เช่น ตรวจหลังทุกคำสั่ง `dispatch` / `checkpoint` ของหัวหน้า หรือจำกัดงานต่อรอบ) งบลูกทีมก็ตรวจทันทีที่งานแต่ละชิ้นจบ
10. **สาธิตได้ในคำสั่งเดียว กับงานของผู้ใช้เอง:** ตัวจำลองมีเป็น flag ของ `lead` ด้วย (เช่น `--simulate-crash <บัญชี>` / `--simulate-limit <บัญชี>`) และ `SKILL.md` มีคำสั่งสาธิตพร้อมใช้ที่ทำให้เกิดครบทั้ง สลับหัวหน้าเชิงรับ, สลับเชิงรุก และย้ายงานลูกทีม ในรันเดียว ใช้ได้ทั้งกับงานตัวอย่างและกับ `--goal` ของผู้ใช้ (เช่น `--demo` เปิดตัวจำลองทั้งชุดแล้วใส่ `--goal` ของตัวเองได้) ผู้ใช้ไม่ต้องอ่านโค้ดเพื่อหาว่าต้องตั้งงบเท่าไร `lead` รันแบบ foreground พิมพ์ความคืบหน้าทีละบรรทัด และจบด้วยตาราง ประวัติการสลับหัวหน้า (จาก ไป ชนิด เหตุผล) · การย้ายงานลูกทีม · ผลของแต่ละงาน · สถิติแยกตามบัญชี

### การส่งข้อมูลระหว่าง agent

- ค่าสั้นแทรกใน prompt ด้วย `{{node}}` · ข้อมูลยาวส่งเป็น path ด้วย `{{file:node}}` แล้วสั่งให้ผู้รับอ่านไฟล์เอง ห้ามยัดข้อความยาวลง prompt
- สั่งรูปแบบคำตอบที่งานถัดไปต้องใช้ (ค่าล้วนหรือ JSON) และตรวจก่อนส่งต่อ
- งานใดล้ม งานที่ขึ้นกับงานนั้นหยุดและรายงาน ห้าม retry งานที่เสียโทเคนอัตโนมัติ
- ห้าม `eval` หรือรันผลลัพธ์เป็นคำสั่ง shell

### การเลือกบัญชีและการรันพร้อมกัน

- `account` ระบุได้เป็นบัญชีเจาะจง (`yolo2`), ฝั่ง (`yolo`/`cyolo`), หรือ `any`
- ตรวจความพร้อมด้วยการเรียกจริงก่อนเริ่ม ข้ามบัญชีที่ใช้ไม่ได้พร้อมแจ้ง **ห้ามสลับบัญชีที่ผู้ใช้ระบุเองโดยไม่แจ้ง**
- **ไม่แตะบัญชีที่ไม่ได้รับอนุญาต:** ถ้าทุกงานในกราฟระบุบัญชีเจาะจง ให้ตรวจและเรียกเฉพาะบัญชีในกราฟ และมีตัวเลือกจำกัดรายชื่อบัญชี (เช่น `--workers yolo1,yolo2,cyolo1`) ที่มีผลทั้งการตรวจความพร้อม โควตา และการแจกงาน ผู้ใช้ที่สั่ง "ใช้ได้เฉพาะ 3 บัญชีนี้" ต้องใช้ `run` ได้โดยไม่มีการเรียกบัญชีอื่นเลย
- จำกัดจำนวนพร้อมกันต่อบัญชี (ค่าเริ่มต้น 3) และรวม (ค่าเริ่มต้น 8) มี timeout ต่องาน

### ใช้งานให้จบในไม่กี่คำสั่ง (ผู้ใช้หลักคือ Claude Code app บน host)

- `SKILL.md` ของ `agent-team` มีตัวอย่างกราฟพร้อมดัดแปลงของงานทีมที่พบบ่อย อย่างน้อย "ทำขนานหลายบัญชี → อีกบัญชีตรวจ → แก้และทดสอบ" งานทั่วไปทำได้โดยไม่ต้องเปิด `references/`
- `run` จบด้วยตารางสรุปของ run นั้น (งาน | บัญชี | รุ่น/effort | เวลา | input tokens | output tokens | สถานะ) และโควตาของบัญชีที่ใช้พร้อมเวลาของข้อมูล คำขอ "สรุปตาราง + โควตา" จึงจบในคำสั่งเดียว (มี `--json` ให้โปรแกรมอ่าน)
- รันต่อจาก run เดิมได้ (เช่น `run --resume <run_id>`): งานที่สำเร็จแล้วไม่รันซ้ำ รันเฉพาะงานที่ล้มหรือถูกบล็อก และแก้ `prompt` / `expect` ของงานนั้นก่อนรันใหม่ได้
- ผลที่ผิดรูปแบบ (`expect`) ไม่ทิ้ง: เก็บคำตอบไว้ใน `out/` และบอกชัดว่าไม่ผ่านเพราะอะไร
- งานที่เขียนไฟล์: กำหนดโฟลเดอร์ทำงาน (`cwd`) ต่องานได้ และ prompt ที่ส่งให้ agent บอก path แบบ absolute
- ทุกตัวอย่างในหัวข้อ "เรียกจาก host" รันได้ทั้ง PowerShell และ Git Bash บน Windows โดยไม่ต้องแก้
- ส่งกราฟจาก host แบบไม่ใช้ heredoc: เขียนไฟล์ JSON บน host (เช่นด้วยเครื่องมือ Write) แล้วส่งเข้า stdin ของ `docker exec -i … run -` (คำสั่ง heredoc ที่มี JSON ถูกตัวตรวจสิทธิ์ของ Claude Code app บล็อก)
- exit code: คำสั่งที่ทำงานสำเร็จคืน 0 แม้ผลจะบอกว่าบางบัญชีไม่พร้อม (`check`, `quota`, `status`, `stats`) · `status` / `stats` ที่ยังไม่มี run พิมพ์ข้อความบอก ไม่ใช่ Traceback · คืนค่าไม่ใช่ 0 เฉพาะเมื่อคำสั่งล้มจริงหรือมีงานล้ม
- `SKILL.md` ของ `agent-team` ยาวไม่เกินประมาณ 10 KB เรียงตามความถี่ที่ใช้: ตาราง "ต้องการ → คำสั่ง", กราฟตัวอย่าง, คำสั่งสาธิตหัวหน้าทีม, เรียกจาก host · รายละเอียดอื่นอยู่ใน `references/`

## ทดสอบใน container (PASS/FAIL ตามจริง)

- คัดลอกโฟลเดอร์แล้วเปิดแต่ละบัญชีหนึ่งครั้ง ทุกบัญชีมองเห็นสกิลทั้ง 3
- ตรวจความพร้อมทุกบัญชีด้วยการเรียกจริง แยก "พร้อม / ล็อกอินแล้วแต่หมดอายุ / ไม่ได้ล็อกอิน"
- เรียกงานเดียวฝั่ง Claude และ Codex ได้ผลถูก และมีแถวใน ledger ครบฟิลด์
- relay ข้าม CLI 3 ทอด `7*6` → `+100` → `*3` ได้ `42 → 142 → 426` ตรวจทุกทอดด้วยการคำนวณอิสระ
- fan-out 3 บัญชี + fan-in รวมผล
- graph ที่ส่งข้อมูลยาวผ่าน `{{file:node}}`
- review loop จบด้วย `APPROVED` ภายใน `max_rounds`
- board: งานที่สองใช้ข้อเท็จจริงที่งานแรกเขียนไว้ใน `board.md`
- สรุปสถิติแล้วผลรวมตรงกับ ledger
- debate (Claude vs Codex + ผู้ตัดสิน) และ best-of-N ได้ผลพร้อมเหตุผลของผู้ตัดสิน
- router เลือกฝั่งถูกตามชนิดงาน และ failover ย้ายงานเมื่อจำลองบัญชีหนึ่งล้ม (`MA_SIMULATE_LIMIT`)
- human gate หยุดรอจนมีไฟล์อนุมัติ แล้วรันต่อ
- บริหารโทเค็นลูกทีม: ตั้งงบโทเค็นของลูกทีมคนหนึ่งต่ำ แล้วงานถัดไปถูกย้ายไปบัญชีอื่นโดยงานที่รันอยู่จบตามปกติ และ `team.py status` แสดงสถานะ "หยุดรับงาน"
- สลับหัวหน้าเชิงรุก: ตั้งงบโทเค็นหัวหน้าต่ำ แล้วหัวหน้าคนใหม่ทำงานต่อจาก `handoff.md` จนจบ
- สลับหัวหน้าเชิงรับ: จำลองหัวหน้าล้มกลางคัน งานของลูกทีมที่สั่งไปแล้วไม่หาย และหัวหน้าคนใหม่ทำงานต่อจนจบ
- สาธิตครบในคำสั่งเดียว: รันคำสั่งสาธิตใน `SKILL.md` ครั้งเดียวแล้วเกิดครบทั้ง 3 เหตุการณ์ (เชิงรับ, เชิงรุก, ย้ายงานลูกทีม) ผลงานถูกต้อง และจบด้วยตารางสรุป ทั้งกับงานตัวอย่างและกับ `--goal` ใหม่ที่แบ่งงานให้ลูกทีมหลายชิ้นแล้วรวมเป็นไฟล์เดียว
- เรียกสคริปต์จาก host ผ่าน `docker exec` ได้ โดยใช้คำสั่งตามตัวอย่างใน `SKILL.md` ทุกบรรทัด (ทดสอบจาก Git Bash บน host)
- `run` จบด้วยตารางสรุปและโควตา และ `--resume` รันเฉพาะงานที่ล้ม: ตั้ง `expect` ให้งานหนึ่งไม่ผ่าน แก้แล้ว resume งานที่สำเร็จแล้วไม่มีแถวใหม่ใน ledger
- ทดสอบแบบผู้ใช้จริง: ให้ agent ใหม่ที่ไม่เคยเห็นสกิล (เช่น `yolo2` รุ่น `sonnet` ผ่าน `--output-format stream-json` เพื่อนับคำสั่ง) อ่านเฉพาะ `SKILL.md` แล้วทำงานโจทย์ใหม่ที่ไม่มีในตัวอย่าง อย่างน้อย 3 แบบ: (ก) ทำขนาน → ตรวจ → แก้และทดสอบ แล้วสรุปตาราง + โควตา (ข) สาธิตสลับหัวหน้าและย้ายงานลูกทีมกับเป้าหมายใหม่ (ค) งานผสม fan-out + debate + สร้างภาพในกราฟเดียว นับจำนวนคำสั่งและคำสั่งที่ล้ม แล้วปรับสกิลจนไม่มีคำสั่งล้มที่เกิดจากสกิล และไม่ต้องเปิดโค้ดของสกิล
- สร้างภาพเล็ก 1 ภาพผ่าน cyolo แล้วตรวจว่าเป็น PNG จริง
- กราฟที่ทุกงานระบุบัญชีเจาะจง: ledger ของ run มีแถวของบัญชีในกราฟเท่านั้น ไม่มีการเรียกบัญชีอื่น
