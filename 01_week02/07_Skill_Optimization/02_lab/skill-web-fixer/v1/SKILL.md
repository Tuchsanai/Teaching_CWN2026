# web-fixer — ตรวจตามแผน → แก้ → พิสูจน์

**ใช้ข้อมูลจากแหล่งเดียว:** TEST-PLAN.md §5 (ผลที่คาดหวัง) + §7 (ข้อมูลทดสอบ) · โค้ดกับข้อมูล seed อาจผิดได้ · ส่วน "เฉลยบั๊ก" ในแผน (ถ้ามี) ไม่ใช่บั๊กรอบนี้ ห้ามใช้
บั๊กแบบนี้มองไม่เห็นจากภายนอก (build ผ่าน ไม่มี error หน้าตาปกติ) และไม่รู้ว่ามีกี่ตัว · **รายงาน TC ได้เมื่อครบ 3 ข้อเท่านั้น:** (1) เทสต์ล้มกับเว็บเดิมเพราะค่าไม่ตรงกับแผน (2) ชี้บรรทัดโค้ดที่ผิดได้และแก้แล้ว (3) เทสต์ตัวเดิมผ่านหลังแก้

## กฎ
- ห้ามแก้ TEST-PLAN.md · e2e/playwright.config.js · e2e/global-setup.js · tools/ · ห้ามรัน npm install หรือ npx playwright install
- 1 test ต่อ 1 TC และชื่อต้องขึ้นต้นด้วยรหัส เช่น `test('TC-CART-01 ใส่ 2 ชิ้น', ...)`
- ทำเฟส A (หาบั๊ก) กับเว็บเดิมให้เสร็จก่อนแตะโค้ด · ในเฟส B (แก้) ห้ามแก้เทสต์ของบั๊กอีก ถ้าจำเป็นต้องแก้ ต้องพิสูจน์ใหม่ว่ายังล้มกับเว็บเดิม: `mv petshop .fixed && cp -a .orig/petshop petshop && tools/start-web.sh && tools/run-e2e.sh -g "TC-…"; rm -rf petshop && mv .fixed petshop && tools/start-web.sh`
- รันทุกคำสั่งจากโฟลเดอร์งาน (โฟลเดอร์ที่มี petshop/ tools/ e2e/)

## เฟส A — หาบั๊ก (เว็บเดิม)
1. เตรียม (คำสั่งเดียว): `mkdir -p .orig && cp -a petshop .orig/ && md5sum TEST-PLAN.md > .orig/plan.md5 && mkdir -p evidence && tools/start-web.sh`
2. สำรวจโค้ด: อ่าน TEST-PLAN.md ทั้งไฟล์ · `ls -R petshop/app petshop/lib petshop/components` · `grep -rn "data-testid\|aria-label" petshop/components petshop/app | cut -c1-170` · อ่านไฟล์ข้อมูลสินค้าใน lib/ (slug ราคา ขนาด สต็อก) และ route ใน app/api
3. เขียน `e2e/sweep.spec.js` ให้ครบทั้ง 40 TC:
   - assert ค่าตรงตัวตามแผน (`toHaveText('฿428')` `toHaveCount(14)` `expect(res.status()).toBe(401)`) ห้ามคำนวณค่าที่คาดหวังจากหน้าเว็บหรือจากโค้ด
   - **ผลที่คาดหวังที่มีหลายอย่าง** (มี "และ" หรือ ",") ต้องเกิด**พร้อมกันในสถานการณ์เดียว**: ป้อนข้อมูลที่ทำให้ทุกผลเกิดในครั้งเดียว (เช่น ผิด 2 ช่องพร้อมกัน) แล้ว assert ครบทุกผลก่อนกรอกใหม่หรือเปลี่ยนหน้า · ห้ามแยกเป็นหลายสถานการณ์ที่ผิดทีละอย่าง
   - ตรวจ**ทุกวลี**ในผลที่คาดหวัง: "ทันที" = ตรวจก่อน reload · "รีโหลดแล้วยังอยู่" = ตรวจหลัง reload · ตรวจทั้งตัวเลขบนหัวเว็บ (badge) และเนื้อหาในหน้า · error ต้องขึ้นที่ช่องที่ระบุและต้องไม่ไปหน้าถัดไป · ข้อความ error ที่แผนเขียนไว้ต้องตรงทุกตัวอักษร
   - locator: ใช้ getByTestId / getByRole ตามที่เห็นในโค้ด · ใช้ `await expect(...)` ที่รอให้เองอัตโนมัติ ห้ามใช้ waitForTimeout และห้ามอ่าน innerText ก่อนหน้าโหลดเสร็จ
   - ข้อมูลของแต่ละเทสต์ต้องไม่ปนกัน: `test.beforeEach(async ({ request }) => { await request.post('/api/test/reset'); })` · สมัครด้วยอีเมลใหม่ `u${Date.now()}@t.test` ทุกครั้ง · บัญชีที่มีอยู่แล้ว demo@pawpantry.test / Paw12345
   - เทสต์ API ใช้ fixture `request` · เทสต์มือถือใช้ `test.use({ viewport: { width: 390, height: 844 } })` ใน describe
   - หลักฐาน: `const shot = async (page, tc) => { if (process.env.EVIDENCE) await page.screenshot({ path: require('path').join(__dirname, '..', 'evidence', tc + '.png'), fullPage: true }); };` ทุกเทสต์ต้องเรียก `await shot(page, 'TC-…')` ตอนที่หน้าจอแสดงผลที่จะตรวจ และเรียกก่อน assert หลัก (เทสต์ API ให้ใช้ `page.setContent` แสดง URL + status + body ตัวใหญ่ แล้วค่อย shot)
4. ตรวจความครบก่อนรัน: `python3 skills/web-fixer/scripts/plan-check.py` → แก้ทุกบรรทัดที่ขึ้น ✗ จนขึ้น "ครบ ✅" · แล้วรัน: `tools/run-e2e.sh --reporter=line 2>&1 | tail -150`
5. คัดแยกทุกข้อที่ล้ม (ห้ามข้ามข้อไหน):
   - หา element ไม่เจอ / timeout / strict mode / เลือกสินค้าหรือขนาดผิด → **เทสต์ผิด** ให้แก้เทสต์
   - element ครบแต่ค่าไม่ตรงแผน → เปิดโค้ดที่คำนวณหรือตรวจค่านั้น ถ้าโค้ดขัดกับ §5/§7 → **บั๊ก** จด `TC · ไฟล์:บรรทัด · ค่าที่ได้ vs ที่คาดหวัง` · ถ้าโค้ดถูกแต่เทสต์เข้าใจแผนผิด → แก้เทสต์
   - รันซ้ำเฉพาะข้อที่แก้ `tools/run-e2e.sh --reporter=line -g "TC-AAA-01|TC-BBB-02"` จนทุกข้อที่ยังล้มเป็นบั๊กจริงที่มีบรรทัดโค้ดยืนยัน
6. ไล่อ่านโค้ดหาบั๊กที่ sweep อาจจับไม่ได้: อ่านโค้ดส่วนเงิน ฟอร์ม/สมาชิก ตะกร้า/รายการโปรด/สต็อก ค้นหา/แนะนำ และ API แล้วเทียบกับ §5/§7 จุดที่ต้องดู: ค่าคงที่และค่าขอบ (฿999 ฿50 ฿120 10% ≥฿500 รหัสผ่าน 8 ตัว+ตัวเลข), `>` กับ `>=`, off-by-one, ใช้ฟิลด์หรือตัวแปรผิดตัว, state ที่อัปเดตเฉพาะหลัง reload, กรองหรือเรียงผิด, status code · ถ้าสงสัยจุดไหน ให้เพิ่ม assert ตามที่แผนเขียนไว้ตรง ๆ ในเทสต์ของ TC นั้นเพื่อให้มันล้ม ถ้าทำให้ล้มไม่ได้ = ไม่ใช่บั๊ก ไม่ต้องแก้ ไม่ต้องรายงาน
7. เก็บหลักฐานกับเว็บเดิม: `EVIDENCE=1 tools/run-e2e.sh --reporter=line -g "<TC บั๊กทั้งหมดคั่นด้วย |>"; ls -l evidence` ทุกไฟล์ต้องใหญ่กว่า 5 KB และต้องเห็นอาการในภาพ

## เฟส B — แก้และพิสูจน์
8. แก้ที่ต้นเหตุ แก้ให้น้อยที่สุดและใช้สไตล์เดียวกับโค้ดเดิม ไม่ refactor ไม่เปลี่ยน testid หรือข้อความอื่น · `grep -rn <ชื่อฟังก์ชัน/ค่าคงที่> petshop/lib petshop/components petshop/app` เพื่อหาจุดที่ใช้ซ้ำ (ฝั่ง client กับ server/API ต้องตรงกัน)
9. `tools/start-web.sh` (ถ้าขึ้น BUILD FAILED → อ่าน error แล้วแก้ type) จากนั้น `tools/run-e2e.sh --reporter=line 2>&1 | tail -80` → sweep ต้องผ่านครบ 40 ข้อ (ข้อที่เคยผ่านต้องยังผ่าน = ไม่ทำของเดิมพัง) · ถ้าบั๊กข้อไหนยังล้ม ให้กลับไปข้อ 8
10. จัดของส่ง: คัดลอกเทสต์ของ TC ที่เป็นบั๊ก**ตามตัวอักษรเดิม** (พร้อม beforeEach และ shot) ไปไว้ใน `e2e/bugs.spec.js` แล้ว `rm e2e/sweep.spec.js` · `tools/run-e2e.sh --reporter=line` ต้องผ่านหมด 2 รอบติดกัน
11. เขียน `BUGS-FOUND.md` 1 แถวต่อ 1 ต้นเหตุ (ถ้าต้นเหตุเดียวทำให้หลาย TC ล้ม ให้ใส่ทุกรหัสในช่องแรกโดยคั่นด้วย ", "):
```
| TC | อาการ | คาดหวัง | ไฟล์ที่แก้ |
|---|---|---|---|
| TC-AAA-01 | <สิ่งที่เห็นจริง พร้อมตัวเลข> | <ผลที่คาดหวังจาก §5> | petshop/lib/xxx.ts |
```
   ช่องแรกใส่ได้เฉพาะ TC ที่ผ่านเกณฑ์ 3 ข้อด้านบน ห้ามใส่ TC ที่ไม่ได้ล้มหรือแค่ "น่าสงสัย"
12. ตรวจก่อนปิดงาน: `diff -rq .orig/petshop petshop -x .next -x node_modules` (ไฟล์ที่ต่างต้องตรงกับคอลัมน์ไฟล์ที่แก้) · `md5sum -c .orig/plan.md5` · `ls -l evidence` (ต้องครบทุก TC ในตาราง) · `tools/stop-web.sh`
