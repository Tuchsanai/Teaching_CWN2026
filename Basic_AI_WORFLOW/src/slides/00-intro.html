รอบWorkflowนักศึกษาจะเห็นว่า
1Loopทำ → ตรวจ → แก้ วนจนผ่านเกณฑ์
2Graphแตกงานเป็นส่วน ทำขนานกัน แล้วรวมกลับ
3Dynamicวางแผนก่อน ทำไปเจออะไรใหม่ก็ปรับแผนได้
กติกาสำคัญ: ทุกการทดลองต้องโชว์ระหว่างทางด้วย (log ว่า AI คิด/แก้/ปรับอะไรบ้าง) ไม่ใช่โชว์แค่ผลสุดท้าย เพราะความต่างของ Workflow อยู่ที่กระบวนการ ไม่ใช่ที่คำตอบ

เปรียบเทียบ 3 ชั้น: วิธีคิด → วิธีเขียน Prompt → ผลลัพธ์

Learning Path

ง่าย → ปานกลาง → ยาก → เปรียบเทียบ

เป้าหมายการเรียนรู้ 7 ข้อ

เข้าใจแนวคิด

  1. อธิบายและออกแบบ Loop
    Generate → Evaluate → Improve
  2. อธิบาย Graph: Node, Edge, State, Dependency
  3. ออกแบบ Graph: Sequential, Fan-out/Fan-in, Conditional
  4. บอกความต่างของ Static Graph กับ Dynamic Workflow
  5. ออกแบบ Planner–Executor–Evaluator

ลงมือทำ

  1. เขียน Prompt ควบคุมแต่ละ Workflow แล้วรันจริงบน Codex / Claude Code รวมถึงลองใช้ skill cyolo และ yolo
  2. เปรียบเทียบโจทย์เดียวกันทั้ง 3 Workflow แล้วสรุปว่าสถานการณ์แบบไหนควรใช้ Workflow แบบใด

โจทย์แนวงานความยากที่ฝังไว้Workflow ที่เห็นจุดเด่นชัด

ทุกโจทย์: วิเคราะห์ Requirement → สร้างโครงสร้างระบบ → สร้างผลลัพธ์ที่ตรวจสอบและเปรียบเทียบได้ และรันครบทั้ง 3 Workflow

โจทย์ที่ 1 — ระบบจองห้องประชุม

สร้างเว็บไซต์สำหรับระบบจองห้องประชุม
ระบบต้องสามารถ: แสดงห้องประชุม, ดูเวลาว่าง, จองห้อง, ยกเลิกการจอง, แสดงสถานะการจอง
Output: Web UI Mock-up ที่เปิดและทดลองใช้งานได้
เหมาะกับ Loop

เกณฑ์ตรวจ

  • ครบ 5 feature
  • Playwright เปิดและคลิกทดสอบได้จริง
  • Navigation ไปถึงทุก feature ≤ 2 คลิก

Output ที่ต้องส่ง

Markdown ไฟล์เดียว (diagram เป็น Mermaid): Actor/Stakeholder · FR-xx/NFR · BR-xx · Use Case · ERD · Sequence “ยื่นเบิก → อนุมัติ → จ่ายเงิน” · State · Traceability Matrix · Open Issues

เกณฑ์ตรวจ

  • ทุกประโยค trace ไป FR/BR ≥ 1 รายการ
  • 5,000 vs 10,000 → Open Issue ไม่ตัดสินเอง
  • ไม่แต่งวงเงินค่าที่พัก
  • Entity/Attribute ใน Sequence และ State ตรงกับ ERD
  • State ตอบได้ว่า “ค้างอยู่ที่ใคร”
  • Mermaid ทุกบล็อก render ได้

งานรอบแรก:
1. As-Is Process (Mermaid flowchart)
2. Data Quality Findings (ปัญหา / แถว / ผลกระทบ)
3. To-Be Process และ Data Model
4. Data Mapping + แผน Migration (รวมวิธีจับคู่ตัวตนคนไข้)
5. Gap Analysis + Roll-out Plan
6. Plan Version Log
เกณฑ์ตรวจ
  1. พบปัญหาข้อมูลอย่างน้อย 5 ประเภท
  2. ระบุวันที่กำกวมและตีความโดยอ้างหลักฐาน
  3. มีกลยุทธ์จับคู่ตัวตนคนไข้ (normalize เบอร์/ชื่อ) พร้อมกรณีให้คนยืนยัน
  4. Plan Version Log บันทึก v1 → v2 พร้อมเหตุผล
  5. Impact Analysis ของ Change Request ระบุ artifact ที่กระทบ และ reuse ส่วนที่ไม่กระทบ

กดขยายภาพเพื่ออ่านรายละเอียด

  1. เตรียม prompt.md: Template + โจทย์ใน ช่อง REQUIREMENT + RUN HARNESS
  2. รันด้วย Codex CLI (cyolo1, gpt-6-astra, effort high) หรือ Claude Code (yolo1, fable)
  3. AI เขียน output.* + trace.md ในโฟลเดอร์
  4. ถอด events.md จาก log.jsonl ด้วยสคริปต์ (ห้ามแต่ง) + screenshot ด้วย Playwright
  5. ประกอบลงสไลด์: Prompt → Process → Output
โจทย์ 3 มีเฟส 2: ส่ง Change Request ผ่าน resume thread เดิม หลังได้ Plan v1

คำสั่งรันซ้ำ (generic)

cd experiments/<task>/<workflow>
# Codex CLI (เฟส 1)
cyolo1 exec --json -m gpt-6-astra -c model_reasoning_effort="high" -o response.md "$(cat prompt.md)" > log.jsonl
# Codex CLI (เฟส 2 ของโจทย์ 3 — resume thread เดิม; thread_id จากบรรทัด thread.started ใน log.jsonl)
cyolo1 exec --json -m gpt-6-astra -c model_reasoning_effort="high" -o response-phase2.md resume <thread_id> "$(cat prompt-phase2.md)" > log-phase2.jsonl
# Claude Code (ชุดเสริม)
yolo1 -p --model fable --effort high --strict-mcp-config --output-format stream-json --verbose "$(cat prompt.md)" > log.jsonl
# ถอดร่องรอย + screenshot (กลับรากโปรเจกต์ก่อน)
cd ../../..
python3 tools/events_from_log.py experiments/<task>/<workflow>
python3 tools/shoot.py experiments/<task>/<workflow>
