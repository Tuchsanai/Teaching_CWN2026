1.4 ผลลัพธ์จากการทดลอง Loop: โจทย์ 1 → 2 → 3

หลังทำแล็บในข้อ 1.3 ให้อ่านผลตามลำดับเดียวกับโจทย์: จองห้องประชุม → เบิกค่าใช้จ่าย → ย้ายระบบคลินิก แต่ละข้อจัดเหมือนกัน คือ ผลงานที่ได้ → วงจรสร้างและตรวจ → หลักฐาน → ไฟล์สำหรับเปิดดู

ผลด้านล่างสร้างใหม่วันที่ 17 กันยายน 2026 จาก loop-template.md และพารามิเตอร์ของทั้งสามโจทย์ใน labs/prompts/loop/ โดย Codex ในบทสนทนาเดียวกันสลับบทบาท GENERATOR และ CRITIC แล้วใช้เครื่องมือบน Remote ตรวจจริง ไม่ใช่ผลจากโมเดลสองตัวที่แยกอิสระกัน และไม่ได้นำผลจากโฟลเดอร์ทดลองเดิมมาใช้แทนผลใหม่

แต่ละกรณีเก็บ prompt-used.md ซึ่งแทนพารามิเตอร์แล้ว, ผลงาน, trace.md, ผลตรวจ verification.json และภาพจากผลงานรอบนี้ไว้ด้วยกัน ผลตรวจมีทั้งการอ่านความหมายโดย CRITIC และการทดสอบด้วยเครื่องมือ ระบุวิธีตรวจแยกไว้ในแต่ละข้อ

ลำดับ ผลงานรอบใหม่ สิ่งที่เกิดขึ้นใน Loop ผลตาม C1–C3
1. จองห้องประชุม เว็บ Mock-up ที่จองและยกเลิกได้ สร้างแล้วทดสอบการคลิกจริง จบ Iteration 1 ผ่านครบ
2. เบิกค่าใช้จ่าย เอกสารข้อกำหนด แบบจำลอง และ Mockup สามส่วน Iteration 1 พบ Sequence render ไม่ผ่าน; แก้และตรวจซ้ำใน Iteration 2 ผ่านครบหลังแก้
3. ย้ายระบบคลินิก แผนย้ายระบบเฟสแรกและฉบับหลัง Change Request Iteration 1 ผ่านเฟสแรก; เมื่อรับข้อมูลใหม่ C1 ไม่ผ่าน จึงแก้และตรวจใน Iteration 2 ผ่านครบหลังเพิ่มข้อกำหนดใหม่

โจทย์ 1 — เว็บจองห้องประชุม

ผลงานที่ได้

เว็บหน้าเดียวมีห้องตัวอย่างสามห้อง ปุ่มดูเวลาว่างตามวันที่ ฟอร์มจอง และตารางสถานะพร้อมปุ่มยกเลิก ผู้เรียนทดลองครบทั้งห้าฟีเจอร์ได้ ข้อมูลเป็นข้อมูลจำลองในหน่วยความจำ รีเฟรชแล้วกลับสู่ข้อมูลตั้งต้น

วงจรสร้างและตรวจ

Iteration GENERATOR CRITIC และการตัดสินใจ
1 เชื่อมข้อกำหนดกับหน้าจอและสร้างเว็บครบห้าฟีเจอร์ C1–C3 ผ่านจากการตรวจและ Python Playwright จึงหยุด

หลักฐานตามเกณฑ์

เกณฑ์ ผล หลักฐานที่ตรวจได้
C1 ฟีเจอร์ครบ PASS แสดงห้อง ดูเวลาว่าง สร้างการจอง ยกเลิก และเห็นสถานะเปลี่ยน
C2 เปิดและทดลองจริง PASS Python Playwright เปิด headless Chromium แล้วคลิกครบห้าฟีเจอร์; ไม่พบ console/page error; ตรวจเพิ่มว่าป้องกันเวลาซ้อนและคืนเวลาว่างหลังยกเลิก
C3 เข้าถึงภายในสองคลิก PASS รายการห้อง 0 คลิก; ดูเวลาว่าง 1; ฟอร์มจอง 0; ยกเลิกรายการตัวอย่าง 1; ตารางสถานะ 0

จำนวนคลิกใน C3 หมายถึง การเข้าถึงฟีเจอร์จากหน้าแรก ไม่ใช่จำนวนคลิกรวมทุกช่องระหว่างกรอกข้อมูล การส่งฟอร์มหลังกรอกใช้ปุ่มยืนยันอีกหนึ่งคลิก

เปิดเว็บที่ทดลองได้ · อ่าน Trace · ดูผลทดสอบจริง · ดู Prompt ที่ใช้

สิ่งที่เรียนรู้: Loop หยุดได้ตั้งแต่รอบแรกเมื่อมีหลักฐานว่าผ่านครบ ไม่จำเป็นต้องสร้างรอบแก้ไขให้ครบจำนวนสูงสุด

โจทย์ 2 — ข้อกำหนดและ Mockup ระบบเบิกค่าใช้จ่าย

ผลงานที่ได้

ส่งเอกสารข้อกำหนดพร้อม Actor/Stakeholder, FR, NFR, BR, Use Case, ERD, Sequence, State, Traceability, Pain Point → หน้าจอ และ Open Issues ร่วมกับ Mockup สามส่วน ได้แก่ ยื่นเบิก → ติดตามใบเบิก → ตรวจและอนุมัติ

เอกสารแยกข้อความสัมภาษณ์เป็น S01–S10 ตามหน่วยความหมาย ย้อนกลับได้ครบทุกบรรทัด เก็บข้อขัดแย้ง 5,000/10,000 ไว้ทั้งสองฝั่ง และไม่สร้างตัวเลขวงเงินที่พัก ข้อเสนอที่ไม่มีในสัมภาษณ์ระบุว่าต้องยืนยัน

วงจรสร้างและตรวจ

Iteration สิ่งที่สร้างหรือแก้ ผลตรวจและการตัดสินใจ
1 สร้างเอกสารและ Mockup ใหม่ C1, C2 ผ่าน; C3 ไม่ผ่าน เพราะ Sequence มี semicolon ในข้อความที่ renderer ตีความเป็นตัวแบ่งคำสั่ง
2 เปลี่ยนตัวคั่นข้อความใน Sequence โดยคงข้อกำหนดเดิม ตรวจ renderer และความสอดคล้องซ้ำ C1–C3 ผ่าน จึงหยุด

เก็บ เอกสารก่อนแก้ และ ข้อผิดพลาดจาก renderer รอบแรก ไว้ให้เห็นว่าเกิดการตรวจพบและแก้จริง

หลักฐานตามเกณฑ์

เกณฑ์ ผลสุดท้าย หลักฐานที่ตรวจได้
C1 เอกสารและ Mockup ครบ PASS อ่านหัวข้อและแบบจำลองครบ; Chromium แสดง Mockup ทั้งสามส่วน
C2 ครบต้นทางและไม่แต่งนโยบาย PASS CRITIC อ่านเทียบสัมภาษณ์กับ S01–S10 และตารางย้อนกลับ; สคริปต์ตรวจว่าทุกรหัสเชื่อม FR/BR; เก็บตัวเลขและข้อขัดแย้งเดิม
C3 แบบจำลองและหน้าจอสอดคล้อง PASS Mermaid ทั้ง 4 บล็อก render จริง; ชื่อฟิลด์ที่อ้างตรง ERD; ทุกสถานะมีเจ้าของ; อ่านเทียบสถานะและนโยบายกับ Mockup พร้อมตรวจภาพ ไม่มี console/page error

แบบจำลองระบบจากผลรอบนี้

Use Case ใช้ Mermaid flowchart แสดง actor และงาน ไม่ใช่ UML use-case syntax โดยตรง

Mockup เรียงตามงานของผู้ใช้

  1. ยื่นเบิก — รูปใบเสร็จจำลอง ประเภทค่าใช้จ่าย ข้อมูลลูกค้า และเงื่อนไขวันยื่น

  1. ติดตามใบเบิก — สถานะ ผู้รับผิดชอบ และขั้นตอนถัดไป

  1. ตรวจและอนุมัติ — คำเตือนใบเสร็จอาจซ้ำและนโยบายที่ยังต้องยืนยัน

ปุ่มและช่องข้อมูลเป็นภาพจำลองตามขอบเขตโจทย์ ไม่ได้ทดสอบการอนุมัติ จ่ายเงิน หรืออัปโหลดจริง การ render ผ่านเป็นหลักฐานด้านรูปแบบ ส่วนความหมายและความสอดคล้องตรวจอ่านเพิ่มเติมใน Trace

เปิดเอกสารพร้อมแผนภาพ · อ่าน Markdown · เปิด Mockup · อ่าน Trace · ดูผลตรวจจริง · ดู Prompt ที่ใช้

สิ่งที่เรียนรู้: ผลงานดูครบยังไม่เท่ากับผ่านทุกเกณฑ์ รอบนี้ C3 ทำให้ Loop กลับไปแก้ข้อผิดพลาดที่ตรวจได้ โดยไม่เปลี่ยนข้อกำหนดหรือแต่งนโยบายให้ข้อขัดแย้งหายไป

โจทย์ 3 — แผนย้ายระบบคลินิกและการแก้หลังรับข้อมูลใหม่

ผลงานที่ได้ในเฟสแรก

เอกสารมี As-Is, Data Quality Findings, To-Be และ Data Model, Data Mapping/Migration, Gap/Roll-out และ Plan v1 ระบุปัญหาเก้าประเภทพร้อมแถว R1–R5 และผลกระทบ แยกวันที่หรือการจับคู่ที่เป็นเพียง candidate ออกจากข้อมูลที่ยืนยันแล้ว

ตัวอย่างที่เห็นจากการตรวจจริง: วันที่ R5 ตีความได้เป็น 9 มีนาคม 2026 หรือ 3 กันยายน 2026 แต่ Python ตรวจแล้วเป็นวันจันทร์และวันพฤหัสบดีตามลำดับ ทั้งคู่ไม่ตรงกับหมายเหตุวันพุธ จึงยังเลือกวันแทนเจ้าของข้อมูลไม่ได้ ส่วนเบอร์ของ R1/R2/R5 ปรับรูปแล้วตรงกัน แต่ยังไม่ใช่หลักฐานเพียงพอให้รวมบุคคลโดยอัตโนมัติ

ทำต่อเมื่อได้รับ Change Request

หลังเก็บฉบับเฟสแรก จึงส่งข้อกำหนดใหม่จากข้อ 1.6 เรื่องความยินยอมและการจองเองผ่าน LINE OA ให้ CRITIC ตรวจงานเดิมก่อน พบว่า C1 ยังขาดทั้งสองเรื่อง จากนั้นเพิ่มกระบวนการและแบบจำลอง พร้อมบันทึก Plan v1 → v2, Impact และ Reuse ในผลงานเดิม โดยเก็บฉบับก่อนเปลี่ยนไว้เปรียบเทียบ

Iteration / ช่วง สิ่งที่เกิดขึ้น ผลตรวจและการตัดสินใจ
1 / เฟสแรก สร้างแผนจากโจทย์เดิม ตรวจข้อมูลและ render แผนภาพ 3 บล็อก C1–C3 ผ่าน จบเฟสแรกและเก็บ baseline
2 / ก่อนแก้ตามข้อมูลใหม่ CRITIC ตรวจ baseline โดยเพิ่มสองข้อใหม่เข้า C1 C1 FAIL เพราะยังไม่มีความยินยอมและ LINE OA; C2, C3 เดิมยังผ่าน
2 / หลังแก้ เพิ่ม To-Be, Data Model, Mapping, Gap/Roll-out และ Plan v2; ตรวจแผนภาพรวม 5 บล็อก C1–C3 ผ่าน จบเฟสสอง

หลักฐานตามเกณฑ์

เกณฑ์ ผลสุดท้าย หลักฐานที่ตรวจได้
C1 ผลงานครบรวมข้อกำหนดใหม่ PASS เอกสารครบหัวข้อเฟสแรกและเพิ่ม ConsentRecord, LineIdentity, BookingRequest, กระบวนการจองเอง และ Impact/Reuse
C2 คุณภาพข้อมูลและความกำกวม PASS CRITIC อ่านเทียบ raw กับ findings เก้าประเภทและทะเบียนความกำกวม; Python ตรวจวันของ candidate dates
C3 จับคู่ตัวตนและแผนภาพ PASS มี normalization ชื่อ/เบอร์และกรณีคนยืนยันครบ R1–R5; Mermaid ฉบับสุดท้ายทั้ง 5 บล็อก render จริง

ภาพแผนหลังรับข้อมูลใหม่

เอกสารนี้เป็นแผนออกแบบ ไม่มีการย้ายข้อมูลคนไข้หรือเชื่อม LINE จริง และไม่ได้รับรองความครบตามกฎหมาย ประเด็นนโยบาย ตัวตน และข้อมูลกำกวมยังระบุผู้ที่ต้องยืนยันไว้

อ่านผลงานเฟสแรก · ดูผลตรวจเฟสแรก · เปิดผลงานสุดท้ายพร้อมแผนภาพ · อ่าน Markdown สุดท้าย · อ่าน Trace ทั้งสองเฟส · ดูผลตรวจสุดท้าย · ดู Prompt แรก · ดู Change Request ที่ใช้

สิ่งที่เรียนรู้: เมื่อโจทย์เพิ่ม ผลที่เคยผ่านอาจกลับมาไม่ผ่านได้ Loop จึงตรวจงานปัจจุบันกับเกณฑ์ใหม่ก่อนแก้ จำนวน Iteration บอกวงจรสร้าง/ตรวจ ส่วน Plan Version บอกการเปลี่ยนเนื้อหาแผน ต้องอ่านแยกกัน

อ่านผลทั้งสามข้อแล้วควรอธิบายอะไรได้

  1. ข้อหนึ่งแสดงการหยุดเมื่อผ่านครบพร้อมหลักฐานการคลิกจริง
  2. ข้อสองแสดงการตรวจพบข้อผิดพลาด แล้วแก้เฉพาะส่วนที่ไม่ผ่านและตรวจซ้ำ
  3. ข้อสามแสดงการรับโจทย์เพิ่ม ตรวจผลเดิมใหม่ และแยกสิ่งที่แก้กับสิ่งที่ใช้ต่อ

ทั้งสามข้อใช้เกณฑ์ C1–C3 จาก Prompt ของตนเอง ไม่ได้นำคะแนนตัวตรวจของการทดลองเดิมมาแทนผลรอบนี้
