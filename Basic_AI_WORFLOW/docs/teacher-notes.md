# บันทึกผู้สอน: โจทย์ย้ายระบบนัดหมายคลินิก

เอกสารนี้เป็นเฉลยสำหรับผู้สอน ใช้หลังนักศึกษาวิเคราะห์ CSV และอ่านผลทดลองแล้ว อ้างอิงสเปก §5 และผล `output.md` ฉบับหลัง Change Request ของแต่ละ workflow ผลที่ส่งมอบเป็นเอกสารออกแบบและแผน Migration ยังไม่ใช่ผลย้ายข้อมูลหรือทดสอบ LINE OA จริง

## ปัญหาที่ซ่อนไว้ — คัดจากสเปกตัวเต็ม

ข้อความต่อไปนี้คัดตรงจาก สเปกหัวข้อ 5 โดยคงข้อผิดพลาดเรื่องวันที่ของต้นฉบับไว้เพื่อให้ตรวจสอบย้อนกลับได้:

> **ปัญหาที่ซ่อนไว้ (ไม่บอกนักศึกษา — ใส่ในเฉลยของผู้สอนเท่านั้น):** รูปแบบวันที่ปน (dd/mm, ISO, พ.ศ. ย่อ) · จองซ้ำ · คนไข้เดียวกันแต่ชื่อ/เบอร์เขียนต่างกันข้ามสาขา (ไม่มี Patient ID) · หมอบีถูกจองชนเวลา · หมอคนเดียวหลายสาขา · เบอร์โทรขาด · แถว `09/03/2026` กำกวม (หมายเหตุ "วันพุธ" คือหลักฐานว่าเป็น 9 ก.ย. 2026 เพราะ 9 มี.ค. 2026 เป็นวันจันทร์)

## เหตุผลเรื่องวันพุธและข้อผิดพลาดในเฉลยต้นฉบับ

เจตนาของโจทย์คือให้ใช้หมายเหตุเป็นหลักฐานประกอบการตีความวันที่ แทนการเลือก locale แล้วแปลงทุกแถวทันที แต่ข้อสรุปในสเปกที่เลือก **9 ก.ย. 2026** ไม่ได้ตามมาจากค่าดิบ `09/03/2026`:

| การอ่าน | วันที่ | วันในสัปดาห์ | ข้อสรุป |
|---|---|---|---|
| DD/MM/YYYY | 2026-03-09 | วันจันทร์ | ไม่ตรงหมายเหตุวันพุธ |
| MM/DD/YYYY | 2026-09-03 | วันพฤหัสบดี | ไม่ตรงหมายเหตุวันพุธเช่นกัน |
| วันที่ที่เฉลยต้นฉบับเสนอ | 2026-09-09 | วันพุธ | ไม่ใช่ผลการสลับวัน/เดือนของค่าดิบ ต้องเปลี่ยนข้อมูลจึงจะได้ค่านี้ |

ตรวจซ้ำแบบออฟไลน์ได้จากรากโปรเจกต์:

```bash
python3 - <<'PY'
from datetime import date
for value in ('2026-03-09', '2026-09-03', '2026-09-09'):
    print(value, date.fromisoformat(value).strftime('%A'))
PY
```

ดังนั้นคำตอบที่มีหลักฐานรองรับคือ **flag ความกำกวมและความขัดแย้ง เก็บค่าดิบกับ candidate แล้วให้ผู้รับผิดชอบยืนยันวันนัดและตารางหมอ** ห้ามแก้วันที่ให้ตรงวันพุธเอง หมายเหตุอาจเป็นเวรประจำและมีข้อยกเว้น จึงยังไม่พิสูจน์ว่าวันนัดผิด ผลทดลองทั้งสาม workflow ระบุข้อขัดแย้งนี้จริง: [Loop](../experiments/3_clinic_migration/loop/output.md) บรรทัด 56, [Graph](../experiments/3_clinic_migration/graph/output.md) หัวข้อ “ข้อสรุปแถวกำกวม — N1b”, และ [Dynamic](../experiments/3_clinic_migration/dynamic/output.md) บรรทัด 207, 214

เกณฑ์ `M2_ambiguous_date_flagged` ตรวจเพียงว่าบรรทัดที่มีวันที่เป้าหมายมี marker ตามที่กำหนด การได้ PASS จึงไม่รับรองว่าข้อสรุปวันที่ถูกต้อง ผู้สอนควรให้คะแนนการชี้ข้อขัดแย้งนี้ ไม่ลงโทษคำตอบที่ไม่ยอมเลือกวันที่ตามเฉลยที่ผิด

## แต่ละ workflow พบอะไรจริง

เลขแถว R1–R5 หมายถึงแถวข้อมูล CSV ไม่นับ header “พบ” ในตารางหมายถึงเอกสารชี้ปัญหาหรือความเสี่ยงพร้อมหลักฐาน ไม่ได้หมายถึงพิสูจน์ตัวตนหรือนัดชนแล้วทุกกรณี

| ประเด็นจากสเปก | Loop | Graph | Dynamic |
|---|---|---|---|
| รูปแบบวันที่ปนและปี พ.ศ. ย่อ | พบ: Findings ข้อ 1–2; แยกวันเดือนกับศักราช และรอยืนยัน R3 | พบ: Findings แถวรูปแบบวันที่และปีสองหลัก | พบ: Findings แถวรูปแบบวันที่ผสมและปีสองหลัก |
| จองซ้ำ | พบ: ข้อ 7 ระบุ R1/R2 เป็นคู่ต้องสงสัย ยืนยันวันและเหตุการณ์ก่อนรวม | พบ: แถว “นัดซ้ำ”; ไม่เลือกแถวล่าสุดเอง | พบ: แถว “นัดที่อาจซ้ำ”; เก็บ lineage ทั้งสองแถว |
| ชื่อ/เบอร์ต่างกันข้ามสาขา และไม่มี Patient ID | พบ: ข้อ 4, 6, 9; เบอร์ตรงกันไม่พิสูจน์คนเดียวกัน | พบ: แถวเบอร์ ชื่อ และกุญแจถาวร; แยก patient matching จาก appointment dedup | พบ: แถวเบอร์ คนไข้ข้ามภาษา และไม่มีรหัส; เบอร์ร่วม/ชื่อถอดเสียงไม่พอให้รวมแฟ้ม |
| หมอบีถูกจองชนเวลา | พบความเสี่ยง: ข้อ 8 ชี้ R3/R4 ต้องยืนยันวันที่และแพทย์ก่อน | พบความเสี่ยง: แถว “เสี่ยงชนคิวหมอ”; ยังไม่ยืนยัน double booking | พบความเสี่ยง: แถว “หมอเริ่มนัดพร้อมกันในสาขาเดียว”; รอยืนยันวันและ doctor ID |
| หมอคนเดียวหลายสาขา | พบ: ข้อ 8–9 ต้องยืนยัน master หมอ เวลาเดินทาง และตารางเวร | พบ: แถว “หมอหลายสาขาและเงื่อนไขในข้อความ” | พบ: แถวไม่ทราบเวลาสิ้นสุดและ free text; ใช้ master/crosswalk ตรวจข้ามสาขา |
| เบอร์โทรขาด | พบ: ข้อ 5 ระบุ R3 และไม่มี LINE user ID ให้ผูกตัวตน | พบ: แถว “ขาดช่องทางติดต่อแบบมีโครงสร้าง” | พบ: แถว “ไม่มีช่องทางติดต่อที่ใช้ได้จาก CSV” |
| วันที่กำกวมและหมายเหตุวันพุธ | พบ: ข้อ 1, 3 ไม่เลือกวันที่ให้ R5 | พบ: Findings และ N1b ชี้ว่าทั้งสองการอ่านไม่ตรงวันพุธ | พบ: Findings และผลปฏิทิน; นำไปสู่งานทะเบียนตัดสิน/กักกัน |

การจับคู่ตัวตนมีหลักฐานต่อใน Loop §2.4, Graph หัวข้อ “Patient matching และ appointment dedup เป็นคนละกระบวนการ” และ Dynamic §3.8 ทั้งสามแยก normalization ออกจากการยืนยันมนุษย์ ผู้สอนควรให้เปรียบเทียบความเสี่ยงของการรวมคนผิดกับการคงแฟ้มซ้ำไว้ชั่วคราว

## การรับมือ Change Request: PDPA และ LINE OA

ข้อกำหนดใหม่คือเก็บความยินยอมของคนไข้ตาม PDPA และให้คนไข้จองเองผ่าน LINE OA ตารางนี้สรุปสิ่งที่เอกสารทดลองเสนอ ไม่ใช่การรับรองการปฏิบัติตามกฎหมายหรือผลเชื่อมต่อบริการจริง

| Workflow | วิธีเปลี่ยนงานและหลักฐาน | ผลกระทบและสิ่งที่ใช้ต่อ |
|---|---|---|
| Loop | Iteration 2 ตรวจผลงานเดิมด้วยเกณฑ์ใหม่: C1 FAIL; Iteration 3 เพิ่ม §2.8 และออก v1.1 มีวงจร consent พร้อม purpose/notice/evidence/withdrawal, การผูกตัวตน, LINE OA self-booking จนได้เลขนัด และ mapping/migration/roll-out/acceptance ส่วนเพิ่ม | คง Findings, identity rules, Mapping/Migration และ diagram เดิมตามรายงานตรวจ แล้วเพิ่ม flow ใหม่ แก้ย่อหน้า To-Be/Gap เรื่อง LINE ที่ขัดกับข้อกำหนดใหม่ การเปลี่ยนรุ่นใช้ v1.0 → v1.1 จึงไม่ผ่าน M4 ที่ต้องมี v2; ไม่พบคำ Impact จึงไม่ผ่าน M5 แม้มีคำอธิบายขอบเขตแก้ไข |

## คำแนะนำการอภิปรายในห้อง

1. ให้แต่ละกลุ่มอ่าน CSV ก่อนเปิดเฉลย แยก “เห็นจากข้อมูล” “อนุมาน” และ “ต้องถามเจ้าของข้อมูล” แล้วเปิดตาราง Findings ของทั้งสาม workflow เปรียบเทียบหลักฐานและผลกระทบ
2. ให้คำนวณวันในสัปดาห์ด้วยตนเอง แล้วอภิปรายว่าเมื่อสเปกกับข้อมูลไม่สอดคล้อง ควรเก็บข้อมูลและแจ้งประเด็นอย่างไร การเปลี่ยนค่าจนตรงคำใบ้ทำให้สูญเสียหลักฐานอะไร
3. ถามว่าเบอร์เดียวกันเพียงพอให้รวม Patient ID หรือไม่ และการยืนยันคนเดียวกันต่างจากการยืนยันว่านัดเดียวกันอย่างไร ให้เสนอข้อมูลที่ต้องขอเพิ่มสำหรับ R3 และ R5
4. ปล่อย Change Request หลังอ่านผลเฟสแรก แล้วให้ทำนายส่วนที่จะต้องแก้ก่อนเปิด response-phase2.md เปรียบเทียบการแก้เฉพาะเกณฑ์ที่ตก การรัน node ตาม dependency และการเพิ่มงานพร้อมแก้ dependency
5. ใช้ Graph เป็นตัวอย่างถามว่า “รันซ้ำแล้วเนื้อหาเดิม” มีต้นทุนต่างจาก “ใช้ผลเดิมโดยไม่รันซ้ำ” อย่างไร อ้างจำนวนรอบ โทเคน และเวลาจริงในผลตรวจ ห้ามสรุปว่ารอบหนึ่ง iteration, node และ plan version เป็นหน่วยงานเท่ากัน
6. ให้ท้าทาย checker: ตารางห้าแถวอาจเป็นปัญหาเดียวซ้ำกัน, marker Impact อาจไม่มีการวิเคราะห์จริง, และเอกสารที่ใช้คำไทยอาจตกเกณฑ์คำอังกฤษ ให้แยกผลตามกฎตรวจจากการประเมินเชิงความหมายโดยผู้สอน
7. ปิดกิจกรรมด้วยเกณฑ์รับก่อนใช้งานจริงที่นักศึกษาเสนอเอง: การยืนยันเจ้าของข้อมูล การทดสอบ consent/withdrawal และสิทธิ์ตัวตน การทดสอบ OA และคิวซ้ำ และเงื่อนไข rollback โดยชี้ว่ารายการทดสอบในเอกสารยังไม่ใช่ผลทดสอบที่ได้รัน
