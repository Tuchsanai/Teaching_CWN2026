# Scenarios ครัวและหน้าร้าน — fixture v3

**Fixture สมมติที่สร้างใหม่ ไม่ใช่ scenarios ต้นฉบับ และห้ามส่งกลับเป็นต้นฉบับ.**
สถานะทุกกรณี: **NOT_RUN**; ช่องผลจริง/หลักฐานยังไม่มีข้อมูล. baseline JSON มีเพียง pointer ไปยังสามไฟล์ที่ไม่พบ จึงไม่ทราบรหัส scenario เดิม; รหัส CHG- ในไฟล์นี้เป็นรหัสใหม่ของการทดลอง ไม่ใช่การเปลี่ยนชื่อรหัสเดิม.

UI เป้าหมาย `../ui-mockup-v3.html`; FR authority `../fr-nfr-v3.md`; Flow `../flow-v3.md`. JSON manifest resolve paths จาก directory ที่เก็บ JSON. ทุก expected ต่อไปนี้คือเกณฑ์ตรวจภายหลัง ไม่ใช่ผลที่สังเกตแล้ว.

เริ่มแต่ละกรณีด้วย browser context ใหม่ เปิด UI แล้วกด `btn-reset`; ข้อมูลจำลองเวลา 2026-01-01T12:00:00+07:00, ช่วง 11:30–13:30, N=3, X=10, คิวว่าง. หนึ่ง context ใช้แท็บเดียวแชร์ state ระหว่างบทบาท; ไม่ reload กลางกรณี. บทบาทลูกค้าไม่ล็อกอิน; พนักงาน/ผู้จัดการเลือก role แล้วเลือก `staff-user`, กรอก `staff-pin` เป็น 0000 และกด `btn-login` ทุกครั้งที่สลับเข้าใหม่. บัญชี demokitchen/demofront/demomanager เป็น placeholder สาธารณะทั้งหมด.

Helper “ส่งหนึ่งใบ”: ลูกค้าเลือก `table-select=01`, `btn-open-menu`, `menu-item-m01`, `btn-add-item`, `btn-submit-order` (ถ้าเปิดโต๊ะอยู่แล้วไม่ต้องเปิดซ้ำ). หนึ่งใบเพิ่มเลข `order-id` หนึ่งและล้าง `cart-count`; หลายจานต้องกดเพิ่มหลายครั้งก่อน submit เดียว. สลับโต๊ะแล้วต้องกด `btn-open-menu` จึงเปลี่ยน active session. ในตัวตรวจใช้ `[data-testid="ชื่อ"]`; scope ใบครัว/หน้าร้านด้วย `data-order-id` และรายการด้วย `item-resolution[data-item-id]` ไม่ใช้ locator ของรายการซ้ำทั่วหน้า.

ผู้ทดลองเก็บ case ID, context/รอบ, seed/ค่าตั้ง, sim-clock, steps, expected เทียบ actual, screenshot ก่อน/หลังและ trace/console error. แยกผล smoke ใน mock กับ AC ระบบจริงและจำนวนตัวอย่างตาม FR. ห้ามนับภาพหลายภาพแทนรอบหรือใช้เวลาจำลองเป็นเวลา LAN. ใน pre-run นี้ไม่มีการรัน browser หรือ UI tests.

## CHG-K01 — คิวและสถานะสองปลายทาง (US-05/10/11)

ส่ง m01 สามใบในเวลาเดียวกันไม่ขยับ clock; ใบครัวใน `kitchen-queue` ต้องเรียง received_at แล้วเลขออเดอร์ monotonic. ครัวกด `btn-status-next` ของใบที่เลือกหนึ่งครั้งเป็นกำลังทำ อีกครั้งเป็นเสร็จแล้ว. สลับลูกค้าและหน้าร้านโดยไม่ reload; ID เดียวกันแสดงสถานะอาหารใหม่. ตรวจข้อความสถานะอาหารใน `front-order` ไม่ใช้ `front-payment-status` แทน. สถานะเงินยังไม่จ่าย. ที่ใบที่สาม capacity เต็มแต่ใบที่สี่ยังส่งได้และเลขยังต่อเนื่อง.

AC จริง US-05 ครัว→ลูกค้าไม่รีเฟรช ≤5 วินาที ≥18/20, US-11 หนึ่งแตะ→หน้าร้าน ≤5 วินาที ≥18/20, US-10 ส่ง→ครัว ≤3 วินาที ≥18/20; ชุดยิง 30 ใบจากสองมือถือพร้อมกัน ลำดับตรง 30/30 ซ้ำ 3 รอบห้ามสลับคู่. Context เดียวไม่พิสูจน์ concurrency หรือ LAN.

## CHG-K02 — แมปวัตถุดิบหมด/กลับมามี (US-06/12/13/20)

ใช้ CHG-C03 ตรวจทั้งจาน/เฉพาะตัวเลือก/ตะกร้าค้าง. เพิ่มชุดวัตถุดิบจำลองห้าชนิด rice, chicken, pork, egg, milk: reset ใหม่แต่ละชนิด, อ่าน mapping ในหน้าผู้จัดการก่อนกด, ครัวกดหมดหนึ่งครั้งแล้วเทียบเมนู/ตัวเลือกทั้งหมดที่เกี่ยวและไม่เกี่ยว. กดกลับมามีแล้วชุดที่เปิดคืนต้องตรงชุดที่ปิดและไม่เปิดรายการที่ยังติดวัตถุดิบอื่นหมด. คง US-20 อ้าง US-14 ตามต้นฉบับ; ความสัมพันธ์ US-12/13 เป็นข้อเสนอใน fixture ไม่ใช่การแก้รหัส AC.

บันทึกผล 5 ชนิดแยกกัน; AC เวลายังคงตาม FR ไม่ใช้ clock จำลองยืนยันเวลาจริง.

## CHG-K03 — ห้ากรณีแจ้งทำไม่ได้และจัดการรายการ (US-09/14)

แต่ละแถว context ใหม่; สร้างสองรายการ 60+55=115. เมื่อครัวกด `btn-item-unavailable` ของจาน 60 ต้อง pending; เก็บจุดเริ่มครัวและจุดเห็น alert ลูกค้า. หลังลูกค้ากดทางเลือก เก็บจุดเริ่มลูกค้าและจุดเห็นรายการใหม่/นำออกที่ครัวแยกจากกัน. Fixture ปรับยอดเทียบ `resolution-order-total` กับ `front-adjusted-total` ของ ID เดียวกัน; `front-total` คง 115.

| กรณี | เตรียม/ทางเลือก | Expected fixture |
|---|---|---|
| 1 | ยังไม่จ่าย คืนจาน 60 | adjusted=55; ครัวไม่แสดงจานที่คืนในรายการต้องทำ |
| 2 | ยังไม่จ่าย เปลี่ยนจาน 60 เป็น m02 | preview ก่อนยืนยัน, adjusted=110; ครัวแสดง m02 แทน |
| 3 | หน้าร้านรับเงินสดแล้ว ลูกค้าคืนจาน 60 | adjusted=55; จ่ายแล้วและ payment-log เดิมคง; มีข้อความยังไม่ยืนยันคืนเงินจริง |
| 4 | ยืนยันสลิปแล้ว เปลี่ยนจาน 60 เป็น m02 | adjusted=110; คงจ่ายแล้ว/log และข้อค้างส่วนต่าง |
| 5 | สร้างออเดอร์ถัดไปก่อนแจ้งใบแรก แล้วคืนจาน 60 ของใบแรก | alert และทางเลือกอ้างใบแรกถูกต้อง; ใบถัดไปไม่ถูกแก้; ใบแรก adjusted=55 |

เพิ่มเติมใน context ใหม่: ไม่มี replacement selection แล้วกดเปลี่ยนต้อง pending; เลือก replacement แล้วครัวปิดวัตถุดิบก่อนยืนยันต้องปฏิเสธตาม stock; กดทำไม่ได้ของหลายจานและคืนจนหมดไม่ปิดโต๊ะ/เปลี่ยนเงินอัตโนมัติ; หลัง return ไม่มีปุ่มคืนซ้ำ. กรณี duplicate handler ภายใน/concurrency ยังไม่มีหลักฐานและไม่ใช้การหายของปุ่มพิสูจน์ระบบจริง. จำนวนออเดอร์ยืนยัน/confirmed_at ไม่เปลี่ยนจากการคืน/เปลี่ยนตาม fixture.

AC ต้อง 5/5 การแจ้ง US-09 และ 5/5 การอัปเดตครัว US-14 ภายใน 10 วินาทีบน LAN แยกกัน. ทั้งสิบการวัดยัง NOT_RUN/ระบบจริง NOT_TESTED.

## CHG-K04 — ยอด/การยืนยันเงิน/อัตลักษณ์ใบ (US-08/15)

ตาม CHG-C05 ตรวจทุก payment event ของ ID เดียวกัน. ลูกค้าเลือก cash ยังไม่จ่าย; หน้าร้านรับเงินจริงใน fixture แล้วจ่ายแล้ว. ครัวที่ล็อกอิน demokitchen ต้องไม่มีสิทธิ์ยืนยันเงิน. เลือก PromptPay แล้วค้างจ่ายจน demofront ยืนยัน; เก็บ payment-log ผู้ใช้/เวลา/order ID. Dine-in แสดงโต๊ะ, takeaway แสดง T-001 เป็นต้น. หลังคืน/เปลี่ยนเทียบยอด adjusted แยก snapshot และไม่แก้ log เดิม. จำนวนตัวอย่างจริงและสัดส่วนคง FR-08/15.

## CHG-K05 — ปิดโต๊ะ/แยก session (US-16)

เปิดโต๊ะ 01 ส่งใบหนึ่ง จด session ID. หน้าร้านเลือก `front-table-select=01`, `btn-close-table`; ลูกค้ายังเปิด session เดิมต้องสั่งต่อไม่ได้. เลือกโต๊ะ 01 แล้ว `btn-open-menu` อีกครั้ง: session ID ใหม่, ไม่มีรายการเก่า, สถานะว่าง/ยังไม่จ่าย; ใบเก่ายังอยู่ในประวัติหน้าร้าน. สลับบทบาทไม่ล้างออเดอร์และไม่ลด count ความจุ. ทำกับโต๊ะ seed ที่มี; AC จริง 5 โต๊ะ 5/5 ยังต้องชุดข้อมูลภายนอกเพราะ snapshot มีสามโต๊ะ.

## CHG-K06 — ออฟไลน์/การติดตั้ง (US-26)

เกณฑ์จริงคงติดตั้ง Ubuntu เครื่องเดียวด้วยสคริปต์เดียว ≤30 นาทีจากเริ่มจนมือถือเปิดเมนูได้, เก็บข้อมูลในร้าน, ถอดอินเทอร์เน็ตภายนอกแล้วสั่ง/เปลี่ยนสถานะ/ปิดโต๊ะครบ 20 ใบ โดย LAN ยังทำงานและ PromptPay ยืนยันด้วยตา. HTML เดียวไม่ใช่ระบบ/สคริปต์ติดตั้ง; กรณีนี้ **NOT_TESTED** รอระบบและหลักฐานภายนอก. การเปิด HTML แบบ offline ไม่ใช่ผลผ่าน US-26.
