# Scenarios ผู้จัดการและ US-21 — fixture v3

**Fixture สมมติที่สร้างใหม่ ไม่ใช่ scenarios ต้นฉบับ และห้ามส่งกลับเป็นต้นฉบับ.**
สถานะทุกกรณี: **NOT_RUN**; ช่องผลจริง/หลักฐานยังไม่มีข้อมูล. baseline JSON มีเพียง pointer ไปยังสามไฟล์ที่ไม่พบ จึงไม่ทราบรหัส scenario เดิม; รหัส CHG- ในไฟล์นี้เป็นรหัสใหม่ของการทดลอง ไม่ใช่การเปลี่ยนชื่อรหัสเดิม.

UI เป้าหมาย `../ui-mockup-v3.html`; FR authority `../fr-nfr-v3.md`; Flow `../flow-v3.md`. JSON manifest resolve paths จาก directory ที่เก็บ JSON. ทุก expected ต่อไปนี้คือเกณฑ์ตรวจภายหลัง ไม่ใช่ผลที่สังเกตแล้ว.

เริ่มแต่ละกรณีด้วย browser context ใหม่ เปิด UI แล้วกด `btn-reset`; ข้อมูลจำลองเวลา 2026-01-01T12:00:00+07:00, ช่วง 11:30–13:30, N=3, X=10, คิวว่าง. หนึ่ง context ใช้แท็บเดียวแชร์ state ระหว่างบทบาท; ไม่ reload กลางกรณี. บทบาทลูกค้าไม่ล็อกอิน; พนักงาน/ผู้จัดการเลือก role แล้วเลือก `staff-user`, กรอก `staff-pin` เป็น 0000 และกด `btn-login` ทุกครั้งที่สลับเข้าใหม่. บัญชี demokitchen/demofront/demomanager เป็น placeholder สาธารณะทั้งหมด.

Helper “ส่งหนึ่งใบ”: ลูกค้าเลือก `table-select=01`, `btn-open-menu`, `menu-item-m01`, `btn-add-item`, `btn-submit-order` (ถ้าเปิดโต๊ะอยู่แล้วไม่ต้องเปิดซ้ำ). หนึ่งใบเพิ่มเลข `order-id` หนึ่งและล้าง `cart-count`; หลายจานต้องกดเพิ่มหลายครั้งก่อน submit เดียว. สลับโต๊ะแล้วต้องกด `btn-open-menu` จึงเปลี่ยน active session. ในตัวตรวจใช้ `[data-testid="ชื่อ"]`; scope ใบครัว/หน้าร้านด้วย `data-order-id` และรายการด้วย `item-resolution[data-item-id]` ไม่ใช้ locator ของรายการซ้ำทั่วหน้า.

ผู้ทดลองเก็บ case ID, context/รอบ, seed/ค่าตั้ง, sim-clock, steps, expected เทียบ actual, screenshot ก่อน/หลังและ trace/console error. แยกผล smoke ใน mock กับ AC ระบบจริงและจำนวนตัวอย่างตาม FR. ห้ามนับภาพหลายภาพแทนรอบหรือใช้เวลาจำลองเป็นเวลา LAN. ใน pre-run นี้ไม่มีการรัน browser หรือ UI tests.

## CHG-21 — N=3 ต้องตรวจผ่าน 3 จาก 3 รอบ (เกณฑ์ ไม่ใช่ผลรัน)

Trace: US-21 → FR-21 → MRG-34/35 → C-V2-01/02/03 → SCR-17/SCR-03 → `capacity-limit`, `capacity-window`, `capacity-message`, `btn-submit-order`.

N=3 มาจากข้อเปลี่ยนสมมติ; ต้นฉบับคง N=5. 15 นาที, นาที 00/15/30/45, ข้อความก่อนยืนยัน และจำนวน 3/3 คงเดิม. X=10 และเขตเวลา +07:00 เป็น fixture. แต่ละรอบต้องเป็น context ใหม่ มี reset และข้อมูลออเดอร์ใหม่ ห้ามใช้ภาพสามภาพของรอบเดียว. ทั้งสามรอบทำขั้น A–G ครบ:

A. เปิดผู้จัดการ `role-manager` → demomanager/0000 → `nav-capacity`. ตรวจค่าเริ่ม N=3, start=11:30, end=13:30, X=10 และ count=0. กรอกค่าทั้งสี่เดิม กด `btn-save-capacity`, ตรวจข้อความผลบันทึก. ขยับเวลาให้ตรงรอบด้วยปุ่มเดิมและบันทึก `sim-clock`/`capacity-window`.
B. ลูกค้าโต๊ะ 01 ส่งสำเร็จสองใบ ใบแรกให้มี m01 สองจานใน submit เดียวเพื่อยืนยันว่าจำนวนจานไม่นับเป็นออเดอร์. ก่อน submit และหลังใบที่ 1/2 ต้องไม่พบ `capacity-message`. ตรวจ count=2 ผ่านหน้าผู้จัดการแล้วกลับลูกค้า; การเปิดหน้า/สลับบทบาทไม่เพิ่ม count.
C. เพิ่ม m02 ลงตะกร้าเป็นใบที่จะสาม ยังไม่กดยืนยัน. count=2 และ `capacity-message` ยังไม่ปรากฏแม้ตะกร้าไม่ว่าง; `btn-submit-order` กดได้. เก็บหลักฐานจุดนี้เพื่อจับการนับตะกร้าหรือ prospective count ผิด.
D. ส่งใบที่ 3 สำเร็จ จด `order-id=3`, `cart-count=0`. ตรวจ manager `capacity-window` count=3 โดยเวลายังเป็นหน้าต่างเดิม. ไม่ reset ระหว่างขั้น.
E. ลูกค้าใหม่จำลองโดยเลือกโต๊ะ 02 และ `btn-open-menu` ให้เป็น session ใหม่ที่ยังไม่มีออเดอร์; เพิ่ม m01 ในตะกร้า. **ก่อนกดใบที่ 4** ต้องเห็น `capacity-message` หนึ่งจุดเป็น “ครัวเต็ม รอประมาณ 10 นาที” พร้อมป้าย “X เป็นค่าจำลอง ยังไม่ยืนยันสูตร”. ตรวจข้อความอยู่ก่อน `btn-submit-order` ใน DOM และมองเห็นบนหน้าจอ ปุ่ม enabled. Snapshot ก่อนกดต้องแสดง order ล่าสุดของ session ใหม่ยังว่าง พร้อมยืนยันว่า message ไม่รอให้ลูกค้าใหม่นี้ส่งก่อน.
F. กด submit ตะกร้าถูกต้อง: ต้องส่งใบที่ 4 ได้ ไม่ถูกปฏิเสธด้วยเหตุเต็ม, ครัว/หน้าร้านมี order ID 4, manager count=4. กลับลูกค้าใหม่โต๊ะ 03 เปิดเมนู/เพิ่มอาหารแต่ยังไม่ส่ง: คำเตือนยังแสดงที่ count>N และปุ่ม enabled. ทดสอบไม่ใช่เงื่อนไข count==N อย่างเดียว.
G. เก็บ actual/หลักฐานแยกรอบ ได้แก่ clock, window, count 0/2/3/4, order ID, received_at ในใบครัว (confirmed_at ไม่เปิดโดย selector โดยตรง), ข้อความก่อนยืนยัน, ปุ่มก่อน/หลัง และผลส่งใบ 4. หากสคริปต์ไม่มีช่องอ่าน confirmed_at ห้ามรายงานว่าตรวจ field นี้แล้ว; เวลาในใบครัวเป็น received_at ไม่ใช่หลักฐาน log เซิร์ฟเวอร์.

| รหัสรอบ | เวลาและการเตรียมหลัง context ใหม่/reset | Expected window +07:00 | ผลจริง |
|---|---|---|---|
| CHG-21-R1 | 12:00 seed; ทำ A–G | [12:00,12:15) | NOT_RUN |
| CHG-21-R2 | seed แล้ว +10 นาทีและ +5 นาที; ทำ A–G | [12:15,12:30) | NOT_RUN |
| CHG-21-R3 | seed แล้ว +10 นาทีสามครั้ง; ทำ A–G | [12:30,12:45) | NOT_RUN |

จำนวนรอบที่ผ่าน: **ไม่มีข้อมูล**; ต้องครบ 3/3 ของรอบที่รันจริง จึงรายงานผ่านชุด fixture นี้ได้. ยังไม่เท่ากับผลระบบจริงหรือการปิดข้อค้างธุรกิจ.

## CHG-21-B01 — ทุกขอบหน้าต่าง 00/15/30/45

แต่ละแถว context ใหม่/reset แล้วตั้งเวลาเริ่มด้วยปุ่ม +10/+5/+1 นาทีเดิม จากนั้นส่งสามใบที่เวลา “ก่อน” โดยไม่ขยับระหว่างส่ง; count=3 และเห็นเต็ม. กด +1 นาทีครั้งเดียวตรงขอบ: count=0 ในหน้าต่างใหม่, ไม่แสดงเต็ม, ใบเก่ายังอยู่ครัว; ยืนยันใบใหม่ได้และ count=1. ตรวจ full date/time ใน `capacity-window` ไม่ใช้แค่เลขนาที.

| ก่อน | หลัง +1 นาที | นาทีขอบที่ตรวจ |
|---|---|---|
| 12:14 | 12:15 | 15 |
| 12:29 | 12:30 | 30 |
| 12:44 | 12:45 | 45 |
| 12:59 | 13:00 | 00 |

[เริ่ม,สิ้นสุด) เป็นสมมติฐาน fixture เดิม. **12:14:59→12:15:00 และขอบหนึ่งวินาทีอื่นยัง NOT_TESTED** เพราะ UI ไม่มีปุ่มขยับวินาที; ไม่เพิ่ม test hook หรืออ้างว่าตรวจแล้ว.

## CHG-21-B02 — ช่วงตั้งค่าและขอบเริ่ม/สิ้นสุด

Context ใหม่ ตั้งช่วง 12:05–12:10, N=3, X=10 (ช่วงนี้เป็น fixture boundary เท่านั้น ไม่แก้ค่า default). ส่งสามใบเวลา 12:00: count=3 แต่นอกช่วงจึงไม่แสดงเต็ม. +5 นาทีถึง 12:05: อยู่ในช่วงและ count=3 เดิมจึงแสดงก่อนยืนยัน; +1 สี่ครั้งถึง 12:09 ยังคงแสดง; +1 ถึง 12:10 ไม่แสดงเมื่อสิ้นสุดแบบ exclusive แม้ window/count เดิม. ไม่ให้การเปลี่ยนเวลาแสดงผลนี้เปลี่ยนช่วงรับกลับบ้านหรือช่วง ETA. รีเซ็ตแล้ว start/end ต้องกลับ 11:30–13:30.

## CHG-21-B03 — นับออเดอร์ ไม่ใช่จาน/ตะกร้า/สถานะ

Context ใหม่: เพิ่มสี่จานแต่ยังไม่ submit → count=0. ส่งครั้งเดียว → count=1; ส่งกลับบ้านหนึ่งใบ → count=2; ส่งหน้าร้านอีกใบ → count=3. ตรวจทุกขั้นผ่าน manager แล้วกลับลูกค้า; เปิดเมนูซ้ำ/สลับบทบาทไม่เพิ่มจำนวน. ครัวกดสถานะเสร็จแล้วไม่ลบ confirmed order จาก count ใน fixture. ปิดโต๊ะ/เปิด session ใหม่ไม่ลดยอดนับ. เมนูหมดแล้ว submit ถูกปฏิเสธตามกฎเดิมไม่เพิ่ม count; คำเตือนความจุและ stock rejection เป็นคนละเหตุ.

## CHG-21-B04 — คืน/เปลี่ยนยังไม่ลดจำนวนยืนยัน

เตรียมสามใบให้เต็ม; ใบแรก 115 บาทตาม CHG-K03. ครัวแจ้งทำไม่ได้แล้วลูกค้าคืนจาน 60 หรือ (context ใหม่) เปลี่ยนเป็น m02; manager count ยังคง 3, คำเตือนยังอยู่, order ID เดิมและ snapshot ยังคง. ยอดปรับ 55/110 แยกจาก snapshot115; payment/status ไม่เปลี่ยนเพราะ capacity. นโยบายนับนี้เป็น fixture เดิม รอ Q-V2-CAPACITY ไม่ประกาศเป็นนโยบายจริง.

## CHG-21-B05 — ตั้งค่า/reset/X และไม่เปลี่ยน ETA

Context ใหม่ ส่งสองใบ (count=2). ผู้จัดการตั้ง N=2, X=7 แล้ว save: ลูกค้าเห็น “ครัวเต็ม รอประมาณ 7 นาที” พร้อมป้ายจำลองก่อนยืนยัน; count ยัง 2. เปลี่ยน N=4 แล้ว save: ไม่แสดงเต็ม. เปลี่ยนกลับ N=3, X=10 แล้วส่งอีกใบ: แสดงเต็ม. ไม่ล็อก N=3 ตายตัวเพราะเปลี่ยนเฉพาะค่าทดสอบ. ETA ยัง “ยังประมาณไม่ได้”; pickup ยังช่วง 15 นาทีเริ่ม ≥20 นาที; PromptPay ไม่เปลี่ยน. กด reset: N=3, X=10, ช่วง11:30–13:30, clock12:00, count=0, ออกจากระบบ.

ตรวจ input N=0/ว่าง/ทศนิยม, X<0, start≥end แล้ว save: แสดงข้อจำกัด fixture และไม่เปลี่ยนค่าที่บันทึก. ไม่ถือ validation นี้เป็น AC ใหม่.

## CHG-21-B06 — สิทธิ์เข้าหน้าความจุ

Context ใหม่แยก anonymous/demokitchen/demofront/demomanager. ลูกค้า/ครัว/หน้าร้านเปิด `#/manager/capacity` ต้องเห็นปฏิเสธและไม่มี capacity-settings; เลือก role-manager ด้วยบัญชีครัว/หน้าร้านก็เข้าไม่ได้. ผู้จัดการเข้าได้ทั้งเมนูและ direct URL. สลับออกจากผู้จัดการแล้วกลับเข้าต้อง login ใหม่. นี่คือสิทธิ์ fixture เดิม; ไม่ใช้เป็นหลักฐาน security ฝั่ง server.

## CHG-M01 — จัดการเมนู/ราคา/รูป/ตัวเลือก (US-19)

1. สร้างออเดอร์เดิม 5 ใบที่ m01+ไข่ 60 บาทต่อใบ เก็บทุก order ID (แม้ capacity เต็มก็ยังส่งได้).
2. ผู้จัดการ `nav-menu-admin`, เลือก m01, แก้ราคาแล้ว `btn-save-menu`; ออเดอร์เดิม 5 ใบต้องคงยอด snapshot 60 ทุกใบ. ออเดอร์ใหม่ใช้ราคาที่บันทึก. สังเกตข้อมูลในหน้าลูกค้าโดยไม่ reload ทั้ง HTML เพราะจะ reset fixture; เกณฑ์ refresh ระบบจริงยังต้องตรวจแยก.
3. `admin-menu-select=new`, กรอกชื่อ/ราคาและตัวเลือกผ่านฟอร์ม บันทึกแล้วมี `menu-item-m09`; ทดสอบตัวเลือก 0 และ 10 รายการ รวมพยายามเพิ่มรายการที่ 11 (ข้อจำกัดตาม AC). รูปใช้ไฟล์จำลอง jpg/png ≤2 MB และเกินขนาด/ชนิดอื่นด้วย `admin-menu-image`, บันทึกผลจริง; นิยาม 2 MB ที่ยังค้างให้ระบุฐาน byte ของ fixture. ไม่อ้างทดสอบหากไม่มีไฟล์ตัวอย่าง.
4. ลบเมนูที่มีแมป: ต้องเตือน; ยกเลิก dialog แล้วเมนู/แมปยังอยู่; ยืนยันแล้วลบทั้งเมนูและแมป. ยอดใบเก่ายังคงเดิม.

AC ระบบจริงแสดงเมนู/ตัวเลือกใหม่เมื่อรีเฟรช ≤1 นาที, snapshot 5/5 และกฎไฟล์/0–10/ลบแมปคงเดิม. UI N=3 ไม่แก้ handler จัดการเมนู.

## CHG-M02 — หน้าแมปแยกจากจัดการเมนู (US-20/12/13)

ผู้จัดการ `nav-mapping`: ไม่มีฟอร์มเพิ่มเมนู/ราคา, `mapping-menu` มีเฉพาะเมนูที่มีอยู่, ตัวเลือกตรงเมนู. เลือกห้าเมนูที่สร้างแล้ว ตั้งแมปทั้งจาน/เฉพาะตัวเลือกผ่าน `mapping-scope`, `mapping-option`, `mapping-ingredient`, `btn-save-mapping`. ตรวจ readback และผลหมด/กลับมามีผ่านครัว/ลูกค้าให้ครบ 5 เมนู. เมนูที่ยังไม่สร้างต้องไม่อยู่ในตัวเลือก. คงรหัสอ้าง US-14/ข้อค้าง Q-20 ไม่แก้เอง; AC 5/5 และแสดงเมื่อรีเฟรช ≤1 นาทีคงเดิม.

## CHG-M03 — บัญชี/PIN/ล็อก/URL (US-25)

ทดสอบชื่อผู้ใช้ขอบ 3/20 ตัว และ PIN ตัวเลข 4/6 หลัก รวมค่าหลุดขอบ/อักขระผิดผ่าน `nav-accounts` และ `btn-save-account`. สร้างบัญชีครัวจำลอง ktest01/0000 เพิ่มหนึ่งบัญชีเพื่อร่วม demokitchen และ demofront เป็นสามบัญชี. เข้าผิด PIN 5 ครั้งติดแล้วใส่ PIN ถูกก่อนครบ5นาทีต้องถูกล็อก; +5นาทีแล้วถูกต้องเข้าได้. แต่ละบัญชีครัว/หน้าร้าน 3 บัญชี × direct URL `#/manager/menu`, `#/manager/reports` ต้องปฏิเสธครบ6/6และไม่แสดง section ป้องกัน. บัญชีผู้จัดการเข้าหน้าที่อนุญาตได้; ไม่มีอีเมล. ตรวจไม่สืบทอดสิทธิ์หลังเปลี่ยนบทบาท.

## CHG-M04 — Reset/regression รวม

ตั้งค่าความจุ/เมนู/แมป/บัญชี/PromptPay, สร้างออเดอร์และคืนรายการ แล้ว reset: ทุกข้อมูลกลับ seed, บัญชีเพิ่มและ events/adjustments หาย, clock12:00, count0/N3/X10. หลัง reset ทำ CHG-C01 และ CHG-K01 ใหม่เพื่อตรวจการสั่ง/คิว/สถานะพื้นฐาน. ทั้งหมดรอผู้ทดลองรันด้วยสคริปต์ร่วมภายนอก.
