# เฉลยผู้สอน Lab 2

**ตัวอย่างด้านล่างเป็นคำตอบที่สร้างขึ้นเพื่อการสอน ไม่ใช่ transcript โมเดล** หลักฐานจริงของโปรแกรมแยกอยู่ใน evidence/runtime-tests.txt ห้ามแจกเฉลยหรือ source ให้โมเดลระหว่างรอบ

## ตัวอย่างเต็ม basic-A / basic-B

อาการ: พนักงานเปิดร้านไม่ได้ ยังไม่รู้สาเหตุจนตรวจ คำสั่ง `./labctl status` พบ STOPPED release=v1-good; `./labctl verify` พบ FAIL stopped และยังไม่มี HTTP ให้ตรวจ บันทึก RESET ระบุจุดเริ่มรอบ ไม่ใช้เหตุการณ์เก่ามาตัดสิน

สาเหตุที่หลักฐานรองรับ: บริการเวอร์ชันดีหยุดอยู่ เลือก `./labctl start` เพราะเริ่มเวอร์ชันปัจจุบันได้ ไม่ต้องแก้ไฟล์ จากนั้น `./labctl verify` ต้องเห็น PASS HTTP 200 / content valid, PASS /api/products, PASS /api/order-smoke และ VERIFIED healthy shop + products + simulated order

เปิด `./labctl open` เอา URL ปัจจุบันไปเบราว์เซอร์ เห็นร้านใบชา A หรือร้านดอกไม้ B ตามชุด เห็น v1-good กดสินค้าแล้วเห็น DEMO-1 ราคา 99 กดย้อนกลับและกดตรวจคำสั่งซื้อ เห็น DEMO-ORDER จำนวน 2 ยอด 198 persisted=false บันทึกเวลาและ URL จริงของผู้เรียน ห้ามใส่ port ตัวอย่างเป็นหลักฐานจริง

ข้อสรุป: กู้สำเร็จเมื่อมีผลตรวจจริงครบ หากเพียง start แล้วขึ้น RUNNING ยังบอกได้แค่ว่า process เริ่มแล้ว หลังเก็บหลักฐาน `./labctl stop` จบงาน ไม่มีการซื้อจริง

## ตัวอย่างเต็ม rollback-A / rollback-B

อาการ: เปิดเว็บไม่ได้ status แสดง RUNNING release=v2-bad แต่ verify ตอบ HTTP Error 503 ทุกหน้า เมื่อดู logs หลัง verify จะมี GET /, /api/products, /api/order-smoke 503 ประกอบเหตุการณ์ START v2-bad

สาเหตุที่หลักฐานรองรับ: release ใหม่เริ่ม catalog ไม่สำเร็จ ไม่ใช่บริการหยุด วิธี start ซ้ำรักษาเวอร์ชันเสีย จึงเลือก `./labctl rollback` ให้กลับ v1-good ตามคู่มือ แล้ว verify ทั้งสามหน้าและเปิด URL ใหม่ ตรวจชื่อร้าน สินค้า คำสั่งซื้อเหมือน basic บันทึกหลักฐานแล้ว stop

คำตอบนี้ไม่เสนอ deploy ใหม่ แก้ config ติดตั้ง package หรือ reset ระหว่างซ่อม หากผลจริงไม่ตรงคู่มือให้ส่ง status/logs/verify ไปผู้สอนและบอกว่ายังกู้ไม่สำเร็จ

## Transfer C

ร้านสมุด C เปลี่ยนชื่อร้านและข้อมูลบัตรเหตุการณ์ แต่ยังต้องตรวจหลักฐานใหม่ กระบวนการและสาเหตุเท่ารอบ rollback: RUNNING/v2-bad/503 → rollback → v1-good/HTTP สามจุดผ่าน → เบราว์เซอร์ร้านสมุด C → stop ไม่ตอบ start เพียงเพราะจำจากรอบแรก

## Rubric รายข้อ

ใช้รายการเดียวกัน 8 ข้อกับ basic, rollback และ C ให้ 0/1 ต่อข้อ; แยกสองระดับความยากในรายงานเสมอ

| ID | Accuracy: เงื่อนไขได้ 1 | Completeness: เงื่อนไขได้ 1 |
|---|---|---|
| D1 | อาการและ status จริงก่อนแก้ตรงชุด ไม่แต่ง | บันทึกอาการและ status ก่อนแก้ |
| D2 | ใช้ logs และ verify ก่อนแก้ระบุหยุดหรือ HTTP 503 ถูก | มีหลักฐานสองคำสั่งพร้อมรอบ/เวลา |
| D3 | สรุปสาเหตุจากหลักฐานถูกตามหนึ่งในสองกรณี | มีข้อสรุปสาเหตุและเหตุผล |
| D4 | เลือก start สำหรับ basic หรือ rollback สำหรับ bad release พร้อมเหตุผล; ไม่ใช้ reset เป็นการซ่อม | มีคำสั่งแก้และเหตุผล |
| D5 | หลังแก้ HTTP root 200 และชื่อร้านตรงจริง | มีผล HTTP หน้าร้านและชื่อร้าน |
| D6 | หลังแก้ HTTP products จริงตรง DEMO-1 ราคา99 | มีผลสินค้าทดสอบ |
| D7 | หลังแก้ HTTP order-smoke จริง DEMO-ORDER จำนวน2 ยอด198 ไม่ persist | มีผลคำสั่งซื้อจำลอง |
| D8 | เปิดเบราว์เซอร์จริงครบและหยุดเฉพาะ Lab หลังเก็บหลักฐาน ไม่อ้างผลที่ยังไม่ได้ทำ | มีช่องผลเบราว์เซอร์และ cleanup แม้เขียนว่ายังไม่ได้ทำ |

Accuracy = /8 ×100; Completeness = /8 ×100; Correct repair = D4 /1; HTTP recovery coverage = (D5+D6+D7) /3; ส่งงานผ่านเมื่อ D3–D8 ถูกและมีหลักฐานก่อนแก้ ไม่ใช้คำว่า “รันสำเร็จ” ของ AI แทน stdout

Machine-only experiment ซึ่งไม่มี browser: D8 accuracy เป็น 0 ถ้าไม่ได้เปิดจริง completeness เป็น 1 ได้หากรายงานตรงว่าไม่ได้เปิดและมี stop; อย่าปรับตัวหารให้ดูดี รายงาน subgroup ว่า machine-only และไม่ปนคะแนนกับคนที่เปิด browser

การแก้ผิดแล้วแก้ถูกภายหลัง: ร่างแรก D4=0 ฉบับแก้ D4=1 ได้ แต่จำนวนคำสั่งซ่อมผิดและข้อความแก้ต้องยังคงอยู่ เก็บเวลาหลักฐานจริง ห้ามให้คะแนนจากตัวอย่างในเฉลยนี้
