# คุยกับ AI ให้เป็นงานที่ตรวจได้

## จากงานใกล้ตัวสู่สาม Lab

เวลาขอให้เพื่อนช่วยตอบลูกค้า เราไม่ได้ส่งแค่ “ตอบให้หน่อย” แต่บอกว่าลูกค้าซื้ออะไร กติกาคืนของคืออะไร และเรื่องไหนต้องถามหัวหน้า AI ก็ต้องได้ข้อมูลเหล่านี้ และคำตอบที่ฟังมั่นใจอาจยังไม่มีหลักฐาน

Prompt คือข้อความที่เราสั่งในรอบนั้น เช่น “แยกเรื่องที่ตกลงแล้วกับเรื่องที่ยังขัดกัน พร้อมบอกแหล่งที่มา” Prompt ที่ดีประกอบด้วยงาน ข้อมูล ขั้นตอน ขอบเขต และผลลัพธ์ที่ต้องการ คำสั่งยาวไม่ได้แปลว่าดีเสมอไป แต่ต้องครบสิ่งที่มีผลต่อการตัดสินใจ

Skill เปรียบเหมือนคู่มือทำงานประจำที่ AI เรียกใช้ซ้ำได้ ในชุดนี้เป็นโฟลเดอร์ที่มี SKILL.md เขียนคำแนะนำภาษาธรรมชาติ พร้อมเอกสารอ้างอิงและแบบผลลัพธ์ ชื่อและคำอธิบายช่วยให้เครื่องมือค้นพบคู่มือ เนื้อหาบอกวิธีทำงาน เราจะให้ AI สร้างไฟล์เหล่านี้จากการสนทนา ผู้เรียนไม่ต้องแก้ส่วนหัวหรือไฟล์ระบบเอง

ตัวอย่าง: ถ้าสั่งตอบลูกค้าทุกวัน แบบ Prompt ต้องส่งคำแนะนำครบทุกครั้ง; แบบ Skill เรียกคู่มือเดิมแล้วส่งคำร้องและนโยบายชุดใหม่ได้ ทั้งสองแบบยังต้องอ่านข้อมูลปัจจุบันและให้คนตรวจ **Skill ไม่ใช่การฝึกโมเดลใหม่** และไม่ได้เพิ่มอำนาจคืนเงินหรือทำให้ข้อเท็จจริงถูกเอง

## อะไรอยู่ในคู่มือที่ดี

1. วัตถุประสงค์: งานเสร็จแล้วช่วยใครอย่างไร
2. เงื่อนไขใช้และขอบเขต: ใช้เมื่อไร งานใดต้องส่งคน
3. ข้อมูลที่ต้องมี: ข้อความ ออเดอร์ นโยบาย วันที่
4. ขั้นตอน: อ่าน เทียบ จัดลำดับ ร่าง ตรวจ
5. การจัดการข้อมูลขาดและข้อยกเว้น: ถามอะไร ใครตัดสิน
6. รูปแบบผลลัพธ์: ตารางและร่างที่คนตรวจง่าย
7. เกณฑ์ตรวจรับ: หลักฐานใดแสดงว่างานครบ
8. ข้อจำกัดและวิธีใช้ซ้ำ: เปลี่ยนข้อมูลใหม่ ตรวจฉบับนโยบาย ไม่ยกคำตอบเก่ามาใช้

## ประโยชน์และข้อจำกัด

| ประเด็น | Skill อาจช่วยอย่างไร | สิ่งที่ยังต้องตรวจ |
|---|---|---|
| ทำตามขั้นตอน | ลดโอกาสลืมขั้นตรวจหลักฐาน | คำแนะนำครบจริงหรือไม่ |
| ความสม่ำเสมอ | ใช้แบบคำตอบเดียวกัน | ตารางดูดีแต่เหตุผลผิดได้ |
| ใช้ซ้ำ | เปลี่ยนข้อมูลโดยไม่เขียนคู่มือใหม่ | กติกาเก่ายังใช้ได้หรือไม่ |
| ต้นทุน | อาจลดเวลาสั่งในงานถัดไป | ต้องนับเวลาสร้างและดูแลแยก |
| งานใหม่ | เป็นจุดเริ่มต้นได้ | คู่มือร้านค้าไม่ใช่คู่มือทุกอุตสาหกรรม |

ในการทดลองนี้เนื้อหาคำแนะนำของสองแบบเหมือนกัน จึงวัดผลของวิธีส่งและใช้ซ้ำภายใต้เงื่อนไขนี้ ไม่ได้พิสูจน์ว่า Prompt ทั่วไปที่สั้นกว่าจะสู้ Skill ไม่ได้ และไม่รับประกันว่า Skill จะชนะ

## คำศัพท์ที่ใช้

| คำ | ภาษาง่าย ๆ | ตัวอย่างในคาบ |
|---|---|---|
| AI Agent | AI ที่อ่านไฟล์และใช้เครื่องมือทำงานได้ | อ่านข้อมูลร้านแล้วจัดตาราง |
| LLM | โมเดลภาษาที่สร้างและตีความข้อความ | ร่างคำตอบร้องเรียน |
| CLI / Terminal | หน้าต่างพิมพ์คำสั่งให้คอมพิวเตอร์ | วาง ./labctl status |
| Session | การสนทนาหนึ่งชุดที่มีประวัติร่วม | เปิดใหม่เพื่อไม่เห็นคำตอบรอบเก่า |
| System Analysis | ทำความเข้าใจงานและข้อตกลงก่อนสร้างระบบ | พบว่าฝ่ายขายกับคลังพูดไม่ตรงกัน |
| Requirement | สิ่งที่ระบบต้องทำ | ให้ตรวจยอดก่อนยืนยัน |
| UAT / ตรวจรับ | คนลองสถานการณ์เทียบกับข้อตกลง | จ่ายแล้วกดยกเลิก ควรเกิดอะไร |
| DevOps | งานร่วมกันเพื่อส่งมอบและดูแลบริการ | คาบนี้ฝึกเพียงสังเกต ตรวจ และกู้ |
| Service / process | โปรแกรมที่เปิดรอให้บริการ | เว็บร้านค้าต้องกำลังทำงาน |
| Log | บันทึกเหตุการณ์จากระบบ | เริ่มบริการหรือเกิด 503 เมื่อไร |
| HTTP 200 / 503 | รหัสตอบจากเว็บ: ส่งหน้าได้ / บริการไม่พร้อม | ต้องอ่านเนื้อหาต่อแม้ได้ 200 |
| Port / loopback | ช่องรับเว็บ / ที่อยู่ในเครื่องตนเอง | 127.0.0.1 และเลขช่องที่ Lab เลือก |
| Rollback | กลับไปใช้เวอร์ชันก่อนหน้า | จาก v2-bad กลับ v1-good |
| Smoke test | ทดสอบงานสำคัญสั้น ๆ | อ่านสินค้าและคำสั่งซื้อจำลอง |
| API / endpoint | ในคาบนี้คือหน้าทดสอบสำเร็จรูป | กดลิงก์สินค้าหรือคำสั่งซื้อ ไม่ต้องเชื่อมระบบ |
| Native discovery | เครื่องมือพบ Skill ในตำแหน่งที่รองรับ | เห็นชื่อในรายการแล้วเรียกด้วย $ |
| Frontmatter | ส่วนหัวชื่อและคำอธิบายของไฟล์ | AI เขียนให้ ผู้เรียนอ่านความหมาย |
| Escalation | ส่งต่อคนที่มีอำนาจหรือความชำนาญ | ผู้จัดการตัดสินข้อยกเว้น |

ลองก่อนเริ่ม: เมื่อเอกสารใหม่ขัดกับเอกสารเก่า ควรถาม “ใครอนุมัติและแทนข้อไหน” ก่อนเลือกฉบับใหม่ และเมื่อ AI บอกว่าซ่อมเสร็จ ให้ขอหลักฐานที่ผู้ใช้ทำงานได้จริง
