# Student Prompt — เลือก AI Agent ให้เหมาะกับงาน

ไฟล์นี้ใช้คู่กับ `readme.original.md` เพื่อให้นักศึกษาเห็นว่า **ระบบเลือก Agent อย่างไร**
ก่อนนำผลการเลือกไปสร้าง Multi-Account AI CLI

> วิธีใช้: คัดลอกส่วน “Prompt สำหรับทดลอง” ส่งให้ AI agent แล้วแทนค่าข้อมูลในวงเล็บเหลี่ยม
> ห้ามใส่ API key, password หรือข้อมูลลับของลูกค้า

## ขั้นตอนการเลือก

### ขั้นที่ 1 — จำแนกประเภทงาน

เลือกประเภทที่ใกล้ที่สุด:

| รหัส | ประเภทงาน | ตัวอย่าง |
|---|---|---|
| `FRONTEND` | Frontend / WebDev | สร้างหน้าเว็บ, React, HTML/CSS, prototype |
| `ARCHITECTURE` | วิเคราะห์และออกแบบระบบ | ออกแบบ architecture, วิเคราะห์ trade-off, review design |
| `BATCH` | งานปริมาณมาก | อ่านไฟล์จำนวนมาก, แปลงข้อมูล, สร้างผลลัพธ์ซ้ำ ๆ |
| `CLIENT_CODE` | แก้โค้ดลูกค้า | แก้ bug, refactor, test ใน repository ลูกค้า |
| `GENERAL` | งานทั่วไป | สรุปเอกสาร, เขียนข้อความ, งานที่ไม่เข้ากลุ่มด้านบน |

### ขั้นที่ 2 — ประเมินข้อจำกัด

ให้คะแนนแต่ละข้อเป็น ต่ำ / กลาง / สูง:

- ความเสี่ยงหากผลลัพธ์ผิด
- ปริมาณงานหรือจำนวนไฟล์
- ความสำคัญของความเร็ว
- ความเข้มงวดของงบประมาณ
- ความลับของข้อมูล
- ความจำเป็นต้องใช้ context ยาว

### ขั้นที่ 3 — อ่านข้อมูลปัจจุบัน

เปิด LMArena ในหมวดที่ตรงกับงาน แล้วบันทึก:

- วันที่ของข้อมูล
- โมเดลที่นำมาเปรียบเทียบ
- คะแนนและช่วงอันดับ/ช่วงความเชื่อมั่น
- จำนวนโหวต
- ราคา input/output
- context length
- สถานะ preliminary ถ้ามี

ห้ามสรุปว่าโมเดลหนึ่ง “ดีที่สุดเสมอ” จาก snapshot เพียงครั้งเดียว

### ขั้นที่ 4 — ใช้ Routing Policy ของชั้นเรียน

| งาน | Primary Agent | Verification Agent | เหตุผลหลัก |
|---|---|---|---|
| `FRONTEND` | Qwen Code | ผู้ใช้ตรวจ UI; เพิ่ม Codex เมื่อความเสี่ยงสูง | ตัวอย่าง WebDev แสดงทางเลือกที่คะแนนแข่งขันได้และต้นทุนต่ำกว่า |
| `ARCHITECTURE` | Claude Code | Codex CLI | ให้ตัวหนึ่งวิเคราะห์และอีกตัวตรวจข้อสมมติ/โค้ด |
| `BATCH` | Qwen Code | Codex CLI สุ่มตรวจ | ลดต้นทุนงานปริมาณมาก และเพิ่ม quality control |
| `CLIENT_CODE` | Codex CLI บัญชีลูกค้า | ตาม policy ลูกค้า | รักษาขอบเขต credential และ audit trail |
| `GENERAL` | Agent ที่คุ้มที่สุดตามข้อมูลล่าสุด | เพิ่ม Agent ที่สองเมื่อความเสี่ยงสูง | ไม่บังคับยี่ห้อเมื่อหลักฐานไม่เพียงพอ |

Policy นี้เป็น **ตัวอย่างเพื่อการสอน** ผู้เรียนต้องปรับเมื่อข้อมูล ราคา หรือข้อกำหนดเปลี่ยน

### ขั้นที่ 5 — เลือก Account

เลือกบัญชีหลังเลือก Agent:

1. งานส่วนตัว → personal account
2. งานทีม → team account
3. งานลูกค้า → account ของลูกค้านั้นเท่านั้น
4. ถ้าโควตาไม่พอ → เลือกบัญชีอื่นได้เฉพาะเมื่อสิทธิ์และข้อมูลอนุญาต
5. ห้ามย้ายข้อมูลลูกค้าไปบัญชีส่วนตัวเพื่อหลบโควตา

ชื่อ wrapper ตัวอย่าง:

- Claude Code: `yolo1` ถึง `yolo5`
- Codex CLI: `cyolo1` ถึง `cyolo5`
- Qwen Code: `qyolo1` ถึง `qyolo3`

### ขั้นที่ 6 — กำหนดวิธีตรวจผล

- ความเสี่ยงต่ำ: ผู้ใช้ตรวจผลลัพธ์โดยตรง
- ความเสี่ยงกลาง: ใช้ Agent ที่สองตรวจเฉพาะจุดสำคัญ
- ความเสี่ยงสูง: ใช้ Agent ที่สองตรวจทั้งหมด และต้องมี human approval
- งานปริมาณมาก: สุ่มตรวจตามสัดส่วนที่ระบุ พร้อมบันทึก error rate

### ขั้นที่ 7 — สร้าง Routing Card

AI agent ต้องตอบในรูปแบบนี้:

```text
ประเภทงาน:
Primary Agent:
Verification Agent:
Account/Wrapper:
หลักฐานที่ใช้:
เหตุผลด้านคุณภาพ:
เหตุผลด้านราคา/โควตา:
ข้อจำกัดหรือความไม่แน่นอน:
วิธีทดสอบใน container/sandbox/VM:
Human approval ที่ต้องมี:
ผลลัพธ์: ROUTE / NEED_MORE_DATA / REJECT
```

## Prompt สำหรับทดลอง

```text
คุณเป็น AI Agent Router สำหรับชั้นเรียน Multi-Account AI CLI

ให้วิเคราะห์งานด้านล่างตามขั้นที่ 1–7 ในไฟล์ agent-routing-prompt.md และต้องทำตามข้อ 3, 4,
9, 10 และ 11 ของ readme.original.md

ข้อมูลงาน:
- ชื่องาน: [ใส่ชื่องาน]
- รายละเอียด: [อธิบายงานโดยไม่ใส่ข้อมูลลับ]
- ระบบปฏิบัติการ: [Ubuntu หรือ Windows]
- จำนวนไฟล์/ปริมาณงาน: [ระบุ]
- ระดับความเสี่ยง: [ต่ำ/กลาง/สูง]
- งบประมาณ: [ต่ำ/กลาง/สูง]
- ต้องการผลลัพธ์ภายใน: [ระบุเวลา]
- ประเภทข้อมูล: [ส่วนตัว/ทีม/ลูกค้า/สาธารณะ]
- บัญชีที่ได้รับอนุญาต: [ระบุชื่อเชิงบทบาท ห้ามใส่ credential]

กฎ:
1. จำแนกงานเป็น FRONTEND, ARCHITECTURE, BATCH, CLIENT_CODE หรือ GENERAL
2. เลือก Primary Agent และ Verification Agent จากหลักฐาน ไม่เลือกเพราะชื่อแบรนด์
3. ถ้ามีข้อมูล LMArena ปัจจุบัน ให้บันทึกวันที่ คะแนน ช่วงอันดับ ราคา และจำนวนโหวต
4. ถ้าไม่มีข้อมูลปัจจุบัน ให้ตอบ NEED_MORE_DATA และบอกข้อมูลที่ต้องตรวจเพิ่ม
5. งานลูกค้าต้องใช้บัญชีลูกค้า ห้าม route ไปบัญชีส่วนตัว
6. งานความเสี่ยงสูงต้องมี Agent ที่สองและ human approval
7. ห้ามใช้ credential จริงในการทดสอบ ให้เสนอ container/sandbox/VM และ fake credential
8. ตอบเป็น Routing Card ตามรูปแบบที่กำหนด และสรุป workflow เป็นลำดับ 1 → 2 → 3
```

## แบบฝึกหัด

หรือระดับความเสี่ยง การเลือก Agent จะเปลี่ยนหรือไม่:

1. สร้างหน้า Landing Page
2. รีวิว architecture ระบบชำระเงิน
3. แปลงไฟล์ log 10,000 ไฟล์
4. แก้ bug ใน repository ลูกค้า
