# ข้อตกลง fixture เพิ่มสำหรับ UI v2

นี่เป็นสมมติฐานเพื่อให้ชุดทดสอบทำซ้ำได้ ไม่ใช่ AC ร้านและยังไม่ยืนยันจาก UI ที่รันจริง
ต้องอ่านสัญญา ../../004_LAB_Conditional_Graph_UI_Mockup/input/ui-contract.md ก่อน
LAB 005 เสนอ selector ใหม่บางตัว แต่ไม่ได้ตรึงค่าตั้งทุกตัวไว้
ตรวจ HTML v2 ที่เลือกในขั้น 6.0 และบันทึก mapping ใน work/input-check.md ก่อนรัน
ถ้า UI ใช้ชื่ออื่น ให้คัดลอก JSON เป็น work/ui-scenarios-v2.json แล้วเปลี่ยนเฉพาะ selector ที่ตรวจพบจริง
ถ้าฟีเจอร์ไม่ถูกสร้าง ให้คง fail/ข้อค้าง ไม่สร้างผลผ่านหรือเปลี่ยนเป็น skip เพื่อซ่อนปัญหา

| data-testid เพิ่ม | ความหมายใน fixture |
|---|---|
| btn-item-unavailable | ปุ่มทำไม่ได้ในใบครัว; ชุดทดสอบสร้างใบเดียวจึงไม่กำกวม |
| item-resolution | ข้อความแจ้งลูกค้าว่าทำไม่ได้ ต้องมีคำว่า วัตถุดิบหมด |
| btn-return-item | ลูกค้าคืนรายการที่ทำไม่ได้ ยอดของรายการนั้นลดออก |
| capacity-message | ข้อความ ครัวเต็ม รอประมาณ ... นาที แสดงก่อนยืนยันเมื่อถึง N |
| capacity-limit | input number ตั้ง N จำลองในหน้าผู้จัดการ |
| rush-start | input time เริ่มช่วงเร่งด่วน |
| rush-end | input time สิ้นสุดช่วงเร่งด่วน |
| btn-save-capacity | บันทึก N และช่วงเวลาใน UI จำลอง |

fixture เริ่มด้วย btn-reset, โต๊ะ 01, เวลาจำลอง 12:00 ตามสัญญาเดิม
ทดสอบครัวเต็มตั้งช่วง 11:30–13:30 และ N=5 เอง ไม่เดาค่า default ของ UI
ส่ง 5 ออเดอร์ในเวลาจำลองเดียว แล้วเตรียมใบที่ 6; ต้องเห็นข้อความก่อนกดยืนยัน
ไม่ทดสอบว่าห้ามส่งใบที่ 6 เพราะต้นฉบับไม่ได้บังคับปฏิเสธอัตโนมัติ
กรณีทำไม่ได้ใช้จาน m01 ราคา 50 เพียงจานเดียว คืนแล้ว cart ไม่ใช่ยอดบิล
ชุดนี้ตรวจยอดบิลหลังคืนด้วย payment-summary-total ซึ่งเป็น selector เพิ่ม:

| data-testid เพิ่ม | ความหมายใน fixture |
|---|---|
| payment-summary-total | ยอดบิล session ล่าสุดฝั่งลูกค้า รูปแบบเลขตามด้วย บาท; หนึ่งจานคืนครบเป็น 0 บาท |

สถานะรายการ “รอลูกค้าตัดสินใจ” แสดงใน kitchen-queue แยกจากสถานะออเดอร์
การคืนรายการลดบิลจำลองไม่ยืนยันว่าได้คืนเงินจริง
fixture หลายรายการใช้ demokitchen/demofront/demomanager และ PIN 0000 ตามสัญญาเดิม
ชื่อเหล่านี้เป็นข้อมูลทดสอบสาธารณะ ไม่ใช่ชื่อบัญชีจริง
