ร่างนี้ใช้เฉพาะ input.md และ manual.md เป็น **ร้านจำลอง ใช้ข้อมูลฝึก ไม่มีการชำระเงินจริง** ผู้ใช้เป็นผู้เลือกและรันคำสั่งเอง ยังไม่มีหลักฐานหลังทำ จึงยังสรุปว่ากู้คืนสำเร็จไม่ได้ ทั้งสองรอบเป็นคนละเหตุการณ์ ไม่ใช่ขั้นตอนต่อกัน

“บริการ” คือโปรแกรมที่รับคำขอจากหน้าเว็บ; “รุ่น” คือชุดพฤติกรรมของโปรแกรม; “logs” คือบันทึกเหตุการณ์; “rollback” คือกลับไปใช้รุ่นก่อนที่ตรวจแล้วว่าดี

**หลักฐานก่อนกู้ — สิ่งที่สังเกตจริง**

| ID | สิ่งที่เห็น | ความหมาย |
|---|---|---|
| A-S1 | `STOPPED version=v1` | รอบ basic บริการหยุดอยู่ที่รุ่น v1 |
| A-S2 | Browser แจ้ง `ERR_CONNECTION_REFUSED` | เปิดหน้าร้านที่ URL ที่บันทึกไว้ไม่ได้ สอดคล้องกับบริการหยุด |
| A-S3 | logs มี `SERVICE_STOPPED` และ `SERVICE_NOT_STARTED` | ระบุว่าบริการยังไม่ได้เริ่มทำงาน |
| A-U1 | `RUNNING version=v2 bookings=0` | รอบ advanced บริการทำงานที่ v2 แต่จำนวนรายการเป็นศูนย์ไม่ได้บอกสาเหตุด้วยตัวเอง |
| A-U2 | Browser จองไม่สำเร็จ พร้อม `UPDATE_V2_BOOKING_BROKEN` | มีหลักฐานว่าการจองผ่านหน้าเว็บเสียใน v2 |
| A-U3 | logs มี `UPDATE_APPLIED` และ `BOOKING_ERROR` ด้วยสาเหตุเดียวกัน | เชื่อมปัญหาการจองกับรุ่นอัปเดต v2 |

**สาเหตุ ข้อสันนิษฐาน และสิ่งที่ต้องตรวจเพิ่ม**

- **basic: สาเหตุหลักคือบริการยังไม่ได้เริ่มทำงาน — มั่นใจสูง** จาก A-S1–A-S3 จึงเข้าเงื่อนไขใช้ `start` ตามคู่มือ ข้อสันนิษฐานคือเมื่อเริ่มบริการแล้วจะจองได้ แต่ยังต้องพิสูจน์ด้วย `check` และ browser; หลักฐานชุดนี้ยังไม่มีผลจองสำเร็จ
- **advanced: สาเหตุหลักคือรุ่นอัปเดต v2 ทำให้จองไม่ได้ — มั่นใจสูง** จาก A-U1–A-U3 บริการยังทำงาน จึงไม่เข้าเงื่อนไขใช้ `start` แก้ปัญหานี้
- **ต้องตรวจเพิ่มก่อนเปลี่ยนรุ่น:** A-U1–A-U3 ยังไม่ยืนยันว่ามี v1 ที่ตรวจแล้วว่าดี ข้อที่ต้องถามผู้สอนคือ “มี v1 พร้อมให้ย้อนกลับและมีหลักฐานว่าจองสำเร็จหรือไม่?” ตามเงื่อนไข `rollback` ใน manual.md ระหว่างยังไม่ยืนยัน ให้เก็บ `status`/`logs` และหยุดก่อนเปลี่ยนรุ่น ตารางด้านล่างจึงระบุ `rollback` เป็นทางเลือกที่มีเงื่อนไขเท่านั้น
- ภาพสถานะอาจต่างจากตอนผู้เรียนลงมือ ต้องตรวจ `status` ปัจจุบันอีกครั้งทั้งสองรอบ หากไม่ตรง A-S1 หรือ A-U1 ให้ขอ `logs` ปัจจุบันและหยุดเพื่อประเมินใหม่ การเปิดหน้าได้หรือได้ HTTP 200 เพียงอย่างเดียวไม่ยืนยันว่าจองสำเร็จ

**คำแนะนำสำหรับผู้ใช้ — ทำแยกทีละรอบจากโฟลเดอร์ Week2 ตามคู่มือ**

| คำสั่งตามลำดับ | เมื่อใด | เหตุผล | ผลคาดหวัง |
|---|---|---|---|
| 1. `./shop preflight` | ก่อนเริ่มแต่ละรอบ | ตรวจความพร้อมของ Python และพอร์ต ซึ่งเป็นจุดรับการเชื่อมต่อ | `PREFLIGHT OK` และ URL; ถ้าขัดข้องให้หยุดแจ้งผู้สอน |
| 2. `./shop status` | ก่อนเลือกคำสั่งกู้ | ยืนยันสถานะและจดรุ่นก่อนทำ | basic: `STOPPED version=v1`; advanced: `RUNNING version=v2` |
| 3. `./shop logs` | สถานะต่างจากภาพเดิม หรือ advanced ยังขาดการยืนยัน v1 ที่ดี | เก็บเหตุการณ์ปัจจุบันให้ผู้สอนตรวจ | บันทึกเวลา รุ่น และเหตุขัดข้อง; ยังไม่เปลี่ยนแปลง |
| 4ก. `./shop start` | **basic เท่านั้น:** ยังหยุดที่ v1 และควรใช้รุ่นปัจจุบัน ตาม A-S1–A-S3 | เริ่มบริการที่หยุดอยู่ | `STARTED version=v1` |
| 4ข. `./shop rollback` | **advanced เท่านั้น:** ยังเป็น v2 จองเสียตาม A-U1–A-U3 และยืนยันแล้วว่ามี v1 ที่ดี | กลับจากรุ่นที่จองเสียไปยังรุ่นที่ตรวจแล้ว | `ROLLED BACK version=v1` |
| 5. `./shop status` | หลังทำ 4ก **หรือ** 4ข เพียงอย่างเดียว | ตรวจบริการและรุ่นหลังทำ | `RUNNING version=v1` |
| 6. `./shop check` | หลังสถานะถูกต้อง | ตรวจหน้าเว็บและการจองผ่านช่องรับคำขอของบริการ | `CHECK PASS booking=… version=v1`; จดเลขที่ได้จริง |
| 7. `./shop open` | หลัง check ผ่าน | รับ URL ไปเปิดใน browser | URL สำหรับเปิดหน้าร้าน |
| 8. `./shop logs` | หากกู้หรือตรวจขั้นใดไม่ผ่าน รวมถึง browser | เก็บหลักฐานส่งผู้สอน | เหตุการณ์พร้อมเวลา รุ่น และข้อผิดพลาด; หยุดการทดลองแก้ต่อ |

หลังขั้น 7 ให้ผู้ใช้เปิด URL ที่คำสั่งพิมพ์ แล้วกด **จองสินค้า** ด้วยข้อมูลฝึก ต้องเห็นเลขจองจริงและรุ่น v1 บันทึกเลขจาก browser แยกจากเลขที่ `check` สร้าง หากไม่สำเร็จให้ทำขั้น 8 และแจ้งผู้สอน ห้ามลองเปลี่ยนหลายอย่างหรือ reset เพื่อให้ผลดูผ่าน
