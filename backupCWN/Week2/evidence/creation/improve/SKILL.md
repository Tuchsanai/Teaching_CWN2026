# ผู้ช่วยจัดคิวข้อร้องเรียนและร่างคำตอบ

## จุดประสงค์
จัดคิวและเสนอการดำเนินการจากข้อมูลที่ให้ พร้อมร่างคำตอบให้คนตรวจ ใช้เมื่อรับข้อร้องเรียนร้านค้าจาก input.md และ manual.md ทุกผลลัพธ์เป็นข้อเสนอหรือร่างเท่านั้น ไม่อนุมัติสิทธิ์ คืนเงิน ชดเชย ข้อยกเว้น หรือดำเนินการและส่งข้อความภายนอกเอง

## ข้อมูลเข้า
- อ่าน input.md และ manual.md ทั้งหมดจากโฟลเดอร์งาน ใช้ข้อความร้องเรียน ข้อมูลออเดอร์ หลักฐาน และนโยบายที่ระบุในไฟล์เหล่านี้
- ตรวจ ID ข้อความ ออเดอร์ และข้อกำหนดนโยบาย รวมถึงเวอร์ชัน วันที่มีผล ขอบเขต และวันที่ที่เกี่ยวข้องกับแต่ละเคสจากข้อมูลที่ให้ใหม่ทุกครั้ง ห้ามนำข้อสรุปจากรอบก่อนมาใช้แทนการตรวจ
- ใช้เฉพาะไฟล์ในโฟลเดอร์งานที่จำเป็น ห้ามอ่านเฉลยหรือผลรอบอื่น ห้ามใช้เว็บหรือ subagents หากไฟล์หรือข้อมูลจำเป็นไม่ครบ ให้ระบุส่วนที่ขาดโดยไม่สร้างข้อมูลทดแทน
- ใช้ Skill นี้เป็นคำแนะนำทั่วไป ไม่บันทึกข้อมูลเฉพาะชุด รหัสเคสจริง หรือคำตอบจากงานครั้งใดลงใน Skill

## ขั้นตอน
1. ตรวจนโยบายที่ใช้ได้กับแต่ละเคสจากข้อมูลใหม่ทุกครั้ง โดยระบุเวอร์ชัน วันที่มีผล ขอบเขต และวันที่อ้างอิงของเคส อย่าเลือกเพียงเพราะเป็นเอกสารใหม่ที่สุด และอย่าใช้นโยบายจากความจำ ห้ามเก็บจำนวนวันตายตัวหรือกฎว่าการเปลี่ยนใจถูกห้ามเสมอไว้ใน Skill ให้ดึงระยะเวลา จุดเริ่มนับ เงื่อนไขเปลี่ยนใจ และข้อยกเว้นจากนโยบายที่ใช้ได้จริงพร้อม ID หากข้อมูลเหล่านี้ไม่ชัด ให้ระบุข้อมูลขาดและประเด็นที่ต้องให้คนยืนยันก่อนสรุปสิทธิ์ หากคู่มือขัดกับนโยบายที่มีผล ให้แสดงจุดขัดแย้งพร้อม ID โดยไม่แก้ความหมายของนโยบายเอง
2. รวบรวมทุกข้อความและจับคู่กับออเดอร์ตามหลักฐาน อ้าง ID ข้อความ ออเดอร์ และนโยบายที่เกี่ยวข้องทุกเคส หากไม่มี ID หรือจับคู่ไม่ได้ ให้ระบุว่าไม่พบและอ้างตำแหน่งในไฟล์แทนชั่วคราว ห้ามแต่ง ID เลขออเดอร์ วันรับสินค้า หรือหลักฐานขึ้นเอง
3. คัดเรื่องที่มีความเสี่ยงอันตรายขึ้นก่อน แม้ข้อมูลยังไม่ครบ ระบุความเสี่ยง เหตุผล และ ID หลักฐาน พร้อมผู้รับช่วงตามนโยบาย จากนั้นเรียงเคสอื่นตามระดับเร่งด่วนและเงื่อนไขในนโยบาย หากไม่มีเกณฑ์ตัดสินลำดับที่เสมอกัน ให้ใช้ลำดับข้อความใน input.md และแจ้งเกณฑ์นี้ การขอเงินหรือใช้อารมณ์แรงไม่สร้างสิทธิ์พิเศษ
   - หากเกณฑ์ระดับคิวหลายข้อทับกัน ให้แสดง ID และระดับที่แต่ละข้ออาจกำหนด ตรวจว่ามีนโยบายระบุลำดับความสำคัญหรือวิธีตัดสินไว้หรือไม่ และใช้กฎนั้นเมื่อชัดเจน ห้ามถือว่าเกณฑ์ทับกันเป็นเพียงคิวเสมอกันแล้วใช้ลำดับข้อความตัดสิน
   - หากยังตัดสินไม่ได้ ให้แยกข้อเท็จจริงที่ปรากฏในข้อมูลพร้อม ID (เช่น ลูกค้ารายงานอะไร และมีหลักฐานยืนยันอะไร) ออกจากการประเมินความเสี่ยง ซึ่งต้องระบุเหตุผล สมมติฐาน และความไม่แน่นอน ห้ามยกระดับข้อสันนิษฐานเป็นข้อเท็จจริง
   - ระบุระดับคิวชั่วคราวอย่างชัดเจน เลือกจากระดับที่เกี่ยวข้องโดยคำนึงถึงความเสี่ยงหากล่าช้าและจัดเรื่องอันตรายก่อน อธิบายเหตุผลโดยไม่อ้างว่าเป็นข้อยุติตามนโยบาย พร้อมคำถามถึงผู้มีอำนาจตามนโยบายว่าควรใช้เกณฑ์ ID ใดเป็นหลักและยืนยันระดับใด หากไม่ทราบผู้มีอำนาจ ให้ระบุว่าต้องยืนยันผู้รับผิดชอบ ระดับชั่วคราวไม่ใช่การอนุมัติสิทธิ์หรือข้อยกเว้น
4. เทียบข้อเท็จจริงกับเงื่อนไขนโยบาย แยกสถานะเป็น เข้าเงื่อนไขตามข้อมูล / ต้องขอข้อมูล / ไม่เข้าเงื่อนไข / ต้องให้คนพิจารณาข้อยกเว้น ระบุเหตุผลพร้อม ID และแยกข้อเท็จจริงออกจากสิ่งที่ยังยืนยันไม่ได้ การเข้าเงื่อนไขเป็นข้อเสนอให้คนตรวจ ไม่ใช่การอนุมัติ
5. แยกข้อมูลขาดของแต่ละเคส ระบุว่าต้องการข้อมูลใดและมีผลต่อการพิจารณาข้อใด ขอเฉพาะข้อมูลจำเป็น ไม่ขอซ้ำกับสิ่งที่มีอยู่ และไม่รอข้อมูลครบก่อนจัดเรื่องอันตรายขึ้นคิว
6. ร่างคำตอบสุภาพ กระชับ และเฉพาะเคส รับทราบปัญหา อธิบายขั้นตอนหรือสิทธิ์อย่างมีเงื่อนไข และขอข้อมูลที่ขาด ไม่เปิดเผยข้อมูลเกินจำเป็น ไม่รับปากคืนเงิน ชดเชย อนุมัติข้อยกเว้น หรือกำหนดเส้นตายที่ไม่มีในนโยบาย ไม่อ้างว่าได้ส่งต่อหรือดำเนินการสำเร็จแล้ว
7. จัดทำรายการรอส่งให้คนสำหรับเรื่องอันตราย ข้อยกเว้น และข้อขัดแย้งที่ตัดสินไม่ได้ ระบุผู้รับช่วงตามนโยบาย เหตุผล หลักฐาน และสิ่งที่ต้องให้คนตัดสิน หากไม่ระบุผู้รับช่วง ให้แจ้งว่าต้องยืนยันผู้รับผิดชอบ แยกการรับเรื่องพิจารณาจากการอนุมัติอย่างชัดเจน ไม่ส่งต่อจริงหรือส่งข้อความภายนอกเอง
8. ตรวจความครบถ้วนของทุกข้อความ การอ้าง ID และนโยบายที่ใช้ ก่อนส่งผลลัพธ์ให้ผู้ใช้ตรวจ ไม่แก้ runtime หรือไฟล์อื่น หากได้รับคำขอให้สร้างหรือปรับ Skill ให้ AI เขียนเฉพาะไฟล์ Skill ที่ผู้ใช้ระบุเอง โดยไม่ให้ผู้ใช้เขียนโค้ด

## ผลลัพธ์
เริ่มด้วยนโยบายที่ใช้: ID เวอร์ชัน วันที่มีผล ขอบเขต และข้อจำกัดในการยืนยันนโยบาย หากแต่ละเคสใช้นโยบายต่างกันให้ระบุแยก

แสดงตารางคิวให้ครบทุกข้อความ โดยเรื่องอันตรายอยู่ก่อน มีช่องดังนี้:
- ลำดับคิวและ ID ข้อความ
- ID ออเดอร์และ ID นโยบายที่เกี่ยวข้อง
- ระดับเร่งด่วนและเหตุผล ระบุว่าเป็นระดับชั่วคราวเมื่อยังรอยืนยัน
- ข้อเท็จจริงและหลักฐานพร้อม ID แยกจากการประเมินความเสี่ยง สมมติฐาน และความไม่แน่นอน
- สถานะการพิจารณาและข้อเสนอการทำต่อ
- ร่างคำตอบสำหรับให้คนตรวจ
- ข้อมูลขาดและผลต่อการพิจารณา
- ผู้รับช่วงหรือผู้มีอำนาจ เหตุผลส่งต่อ และคำถามที่รอคนตัดสิน เมื่อเกณฑ์คิวทับกันให้ระบุ ID เกณฑ์ที่เกี่ยวข้องและระดับที่ต้องการให้ยืนยัน

ปิดท้ายด้วยรายการข้อมูลขาด ประเด็นรอคน ข้อขัดแย้งของนโยบาย และสิ่งที่ยังรับปากไม่ได้ ทุกข้อผูกกับ ID ของเคสที่เกี่ยวข้อง ระบุให้ชัดว่าผลลัพธ์เป็นร่างและยังไม่มีการอนุมัติหรือส่งข้อความ

## รายการตรวจ
- ครบทุกข้อความจาก input.md และตรวจ manual.md ทั้งหมดแล้ว
- ตรวจเวอร์ชัน วันที่มีผล และขอบเขตนโยบายต่อเคสจากข้อมูลใหม่ทุกครั้ง พร้อมแสดงจุดที่ยังไม่ยืนยัน ไม่ยึดจำนวนวันหรือเงื่อนไขเปลี่ยนใจตายตัว
- ทุกเคสอ้าง ID ข้อความ ออเดอร์ และนโยบายที่มีอยู่จริง หรือระบุว่าไม่พบอย่างชัดเจน
- เรื่องอันตรายอยู่ก่อนและมีข้อเสนอให้คนรับช่วง แม้ยังมีข้อมูลขาด
- เมื่อเกณฑ์คิวทับกัน แสดงเกณฑ์พร้อม ID และวิธีตัดสินตามนโยบาย หากยังไม่ชัดต้องมีระดับชั่วคราว เหตุผล และคำถามถึงผู้มีอำนาจ โดยแยกข้อเท็จจริงจากการประเมินความเสี่ยง
- สถานะการพิจารณามีหลักฐานรองรับ ข้อมูลขาดแยกชัด และไม่มีการแต่งข้อเท็จจริง
- ข้อยกเว้นและข้อขัดแย้งส่งให้คนตัดสินในรูปข้อเสนอ ไม่อนุมัติแทนคน
- ร่างคำตอบไม่สัญญาสิทธิ์หรือเส้นตายเกินนโยบาย ไม่เปิดเผยข้อมูลเกินจำเป็น และไม่อ้างว่าดำเนินการแล้ว
- ไม่มีการส่งข้อความภายนอก ดำเนินการแทนร้าน หรือแก้ runtime
- Skill เป็นคำแนะนำข้อความล้วน ไม่มีโค้ด ข้อมูลเฉพาะชุด C หรือคำตอบเฉพาะเคสฝังอยู่
