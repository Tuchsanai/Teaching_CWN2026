**หลักฐานก่อนกู้คืน**

สองรอบเป็นคนละเหตุการณ์ ต้องวินิจฉัยและกู้แยกกัน ข้อมูลที่ให้ยังไม่มีผลหลังทำ

| ID | สิ่งที่เห็นจริง | ความหมาย |
|---|---|---|
| A-S1 | `STOPPED version=v1` | บริการหรือโปรแกรมรับคำขอจากเว็บหยุดอยู่ รุ่นปัจจุบันคือ v1 |
| A-S2 | Browser แจ้ง `ERR_CONNECTION_REFUSED` | เข้าเว็บร้านไม่ได้ สอดคล้องกับบริการหยุด |
| A-S3 | บันทึกเหตุการณ์มี `SERVICE_STOPPED` และ `SERVICE_NOT_STARTED` | ระบุว่าบริการยังไม่ได้เริ่มทำงาน |
| A-U1 | `RUNNING version=v2 bookings=0` | บริการทำงานอยู่บน v2 แต่จำนวนจองศูนย์อย่างเดียวไม่บอกสาเหตุ |
| A-U2 | Browser จองไม่สำเร็จ พร้อม `UPDATE_V2_BOOKING_BROKEN` | การจองบน v2 ใช้งานไม่ได้ |
| A-U3 | มี `UPDATE_APPLIED` และ `BOOKING_ERROR` ระบุสาเหตุเดียวกัน | เชื่อมปัญหาการจองกับรุ่นอัปเดต v2 |

**สาเหตุ ข้อสันนิษฐาน และสิ่งที่ต้องถาม**

- **รอบ basic: บริการยังไม่ได้เริ่มทำงาน — ความมั่นใจสูง** จาก A-S1–A-S3 จึงเลือก `start` ซึ่งเป็นการเปิดบริการรุ่นปัจจุบัน
- **รอบ advanced: รุ่นอัปเดต v2 ทำให้จองสินค้าไม่ได้ — ความมั่นใจสูง** จาก A-U1–A-U3 จึงเข้าเงื่อนไขพิจารณา `rollback` หรือกลับไปรุ่นก่อนที่ตรวจแล้วว่าดี การใช้ `start` ไม่แก้ปัญหา v2 ตามคู่มือ
- **ข้อสันนิษฐานที่ยังยืนยันไม่ได้:** v1 พร้อมให้ย้อนกลับและผ่านการจองแล้ว เพราะ A-U1–A-U3 ไม่มีผลทดสอบ v1 ก่อนอัปเดต ส่วน A-S1 เป็นอีกเหตุการณ์และแสดงเพียง v1 ที่หยุดอยู่
- **สิ่งที่ต้องถามผู้สอนก่อน rollback:** มี v1 ที่ตรวจแล้วว่าจองได้และพร้อมย้อนกลับหรือไม่ พร้อมขอหลักฐานผลตรวจหรือเลขจองของ v1 หากยังยืนยันไม่ได้ ให้เก็บ `status`/`logs` และหยุดก่อนเปลี่ยนรุ่น
- **สิ่งที่ต้องตรวจเพิ่มก่อนลงมือทั้งสองรอบ:** สถานะและบันทึกเหตุการณ์ปัจจุบันยังตรงกับ A-S1–A-S3 หรือ A-U1–A-U3 หรือไม่ เพราะข้อมูลที่ให้เป็นภาพสถานะ ณ เวลาที่บันทึก

ไม่มีผู้เรียนโต้ตอบในรอบนี้ จึงระบุคำถามและเงื่อนไขไว้ให้คนทำตรวจต่อ โดยไม่สมมติคำตอบแทน

**คำแนะนำให้คนทำตามคู่มือ**

ทำในโฟลเดอร์ Week2 ของรอบที่เกี่ยวข้อง เลือกคำสั่งกู้เพียงคำสั่งเดียวตามสาเหตุ

| ลำดับ / คำสั่ง | เมื่อใด | เหตุผล | ผลคาดหวัง |
|---|---|---|---|
| 1. `./shop preflight` | ก่อนเริ่มแต่ละรอบ | ตรวจ Python และพอร์ตหรือช่องทางเชื่อมต่อ | `PREFLIGHT OK` พร้อม URL; หากขัดข้องให้หยุดแจ้งผู้สอน |
| 2. `./shop status` แล้ว `./shop logs` | ก่อนกู้ | ยืนยันรุ่นและสาเหตุปัจจุบัน | basic ตรงกับ A-S1/A-S3; advanced ตรงกับ A-U1/A-U3 หากต่างให้หยุดประเมินใหม่ |
| 3ก. `./shop start` | เฉพาะ basic ที่ยัง `STOPPED version=v1` | เริ่มบริการที่ยังไม่ได้เปิด | `STARTED version=v1` |
| 3ข. `./shop rollback` | เฉพาะ advanced ที่ยังมีปัญหา v2 และยืนยันว่ามี v1 ที่ดีแล้ว | กลับไปรุ่นที่จองได้ | `ROLLED BACK version=v1` |
| 4. `./shop status` | หลังคำสั่งกู้ที่เลือก | ตรวจว่าบริการทำงานและเป็นรุ่นใด | `RUNNING version=v1` |
| 5. `./shop check` | หลังตรวจสถานะ | ทดสอบหน้าเว็บและการจองผ่านช่องทางรับคำขอจริง | `CHECK PASS booking=... version=v1` จดเลขจริง |
| 6. `./shop open` | หลัง check ผ่าน | รับ URL สำหรับเปิด browser | URL ของร้านฝึก |

หลังข้อ 6 ให้คนทำเปิด URL ใน browser แล้วกด **จองสินค้า** ด้วยข้อมูลฝึก ต้องเห็นเลขจองจริงและรุ่น **v1** บันทึกเลขจองจาก browser แยกจากเลขที่ `check` สร้าง การเปิดหน้าเว็บได้หรือได้ HTTP 200 ยังไม่ยืนยันว่าจองสำเร็จ

หากตรวจหรือจองไม่ผ่าน ให้เก็บ `./shop logs` หยุดการลองแก้ และแจ้งผู้สอนพร้อมผลคำสั่งและข้อผิดพลาด ห้ามใช้ `reset` ระหว่างกู้เพื่อทำให้ผลดูผ่าน

**ช่องรอหลักฐานหลังทำ**

| รายการบันทึก | basic | advanced |
|---|---|---|
| คำสั่งที่คนทำจริงและผลตอบกลับ | รอกรอก | รอกรอก |
| รุ่นก่อน → หลัง | v1 ตาม A-S1 → รอตรวจ | v2 ตาม A-U1 → รอตรวจ |
| หลักฐาน v1 ที่ดีก่อน rollback | ไม่เกี่ยวกับคำสั่ง start | รอผู้สอนยืนยัน |
| ผล `status` หลังทำ | รอกรอก | รอกรอก |
| ผล `check` / เลขจองจริง | รอกรอก | รอกรอก |
| ผล browser / เลขจองจริง / รุ่น | รอกรอก | รอกรอก |
| สถานะ: รอทดสอบ / ผ่าน / ไม่ผ่าน | **รอทดสอบ** | **รอทดสอบ** |
