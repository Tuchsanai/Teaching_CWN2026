ข้อค้นพบที่ใช้สอนได้

Lab1 และ Lab2 ครบ 12 เกณฑ์ทั้ง P/S ใน A/B; Lab1 ฝั่ง Skill มีคำว่า “ขอ取消ออเดอร์” ปนในสองร่าง แม้คะแนนความครบถ้วนเต็ม จึงต้องตรวจภาษาเพิ่มก่อนใช้ ไม่แก้ไฟล์ raw เพื่อทำให้ผลสวย Lab3 ตามรูบริกเดิม P=10/12 และ S=11/12 ทั้ง A/B แต่ข้อคิวทับกัน: แก้วร้าวอาจเป็นความเสี่ยง P1 และข้อความของเสียที่ข้อมูลขาดอาจจัด P2 เบื้องต้นได้ จึงมี sensitivity แบบ post-hoc (วิเคราะห์เพิ่มเติมหลังเห็นผล) ที่รับเหตุผลดังกล่าวอย่างเท่าเทียม ซึ่งทั้งสองฝ่ายได้ 12/12 ความต่างหนึ่งคะแนนไม่ใช่หลักฐานว่า Skill เหนือกว่าโดยทั่วไป Lab2 ทุกเงื่อนไขเลือก start/rollback ตรงเหตุและขอหลักฐาน known-good v1 ก่อนลงมือเมื่อ snapshot ไม่ให้ผลนั้น ถือเป็นการขอข้อมูลที่เหมาะสม AI ไม่ได้รันบริการจริง; ภาพและเลขจองที่ผ่านเป็นการทดสอบ runtime อัตโนมัติแยกต่างหาก ดู snapshot ต้นทาง runtime และผลล่าสุดใน browser/

ต้นทุนที่แยกไว้

จำนวนคำขอทดลอง/สาธิตที่มี raw logs ครบใน experiments และ creation: 22; input 997,119, cached input 829,312, output 44,430, reasoning output 3,712; input + output 1,041,549 โทเคนตาม CLI cached input เป็นส่วนหนึ่งของ input และ reasoning เป็นรายละเอียดของ output ไม่บวกซ้ำ ไม่คำนวณราคา subscription จากราคา API ค่า input ของ CLI สะสมตามการทำงานหลาย tool turns และอาจมี cached context; S-confirmed มีต้นทุนเปิดอ่านเพื่อพิสูจน์ gate เพิ่ม ไม่ถือว่าเป็นต้นทุน Skill โดยธรรมชาติทั้งหมด ต้นทุนเตรียม input-only directory วัดจริงแยกใน launcher-prepare-checks.json เป็นเวลาสคริปต์ ไม่ใช่เวลาติดตั้งเครื่องทั้งห้อง เวลาคนติดตั้ง/ออกแบบ Skill/เขียนคำขอ/ตรวจร่างไม่ได้วัด ไม่ประมาณเป็นศูนย์

การสาธิตสร้าง/ปรับ/ทำ C ใหม่ใช้ launcher จริง อยู่หลังการทดลองหลัก แยกเป็นต้นทุนสร้างและบำรุงรักษา ตัวอย่าง flawed v1 ของการ hard-code วันเป็นตัวอย่างผู้สอนแต่งที่ติดป้าย ไม่อ้างว่าเป็นความผิดที่โมเดลทำจริง ผล C หลังปรับเป็น assisted transfer เพราะผู้สร้าง Skill มีข้อมูล C อยู่แล้ว

ข้อจำกัดและเงื่อนไขปรับปรุง

นี่คือ technical pilot ไม่ใช่การศึกษากับผู้เรียนจริง มีหนึ่ง sample ต่อเงื่อนไข/ชุด การสลับลำดับ P-A/S-B/S-A/P-B ใช้ในการออกแบบและรอบเริ่มต้น แต่การยืนยัน native เพิ่มทำให้ลำดับผล main ของ Lab1/3 ไม่สมดุลเต็มที่ ไม่วิเคราะห์นัยสำคัญ ไม่อ้างลดเวลาคนหรือจำนวนการแก้ที่ไม่ได้วัด ผู้จัดทำ AI worker เป็นผู้ประเมินเอง ไม่ blind; รูบริกคิว Lab3 มีส่วนทับกัน; ความยาวคำตอบ คำขอ native gate เครือข่าย และ cache ต่างกัน; input directories เป็นการแยกบริบท ไม่ใช่ OS sandbox ตรวจ trace ว่าอ่านเฉพาะข้อมูล/คู่มือ/Skill ที่ให้ ดู package audit การศึกษาต่อควรล็อกกติกาคิวที่ชัดก่อนเริ่ม เก็บ rubric/hash ก่อนดูผล ทำซ้ำหลายกลุ่มกับข้อมูลใหม่ ให้คนตรวจแบบไม่เห็น P/S และนับเวลา/คำใบ้/การแก้จริง แยกเวลาสร้างและปรับ Skill แล้วค่อยตัดสินความคุ้มจากการใช้ซ้ำ
