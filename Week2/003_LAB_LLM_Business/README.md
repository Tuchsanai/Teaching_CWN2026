## เริ่มทำ: คัดลอก → วาง → ตรวจผล

**เตรียมก่อนจับเวลา:** ผู้สอนจัดเครื่องและบัญชีตามคู่มือกลาง เปิด Terminal (หน้าต่างรับคำสั่ง) ที่โฟลเดอร์ **Week2**; ไฟล์คู่มือสองไฟล์นี้มีเนื้อหาและข้อมูลครบ ส่วนคำสั่ง `./learn` และ `./shop` ใช้เครื่องมือกลางที่ผู้สอนเตรียมให้

ใน HTML ให้กดปุ่ม **คัดลอกข้อความ** ใต้กรอบ แล้ววางลงในตำแหน่งที่ระบุ ใน Markdown ให้คัดลอกเฉพาะข้อความในกรอบ ไม่คัดลอกเครื่องหมายกรอบ ไม่ต้องพิมพ์หรือแก้โค้ด

### ขั้นที่ 1 — เลือกชุดและวิธีตามที่ผู้สอนกำหนด

เลือก **เพียงหนึ่งกรอบ** แล้ววางใน Terminal กด Enter; P คือ Prompt ที่ให้ขั้นตอนครบ ส่วน S คือเรียก Skill ที่เตรียมไว้ อย่าทำทุกชุดต่อกันโดยไม่จบรอบ

**ชุด A / Prompt**

```bash
./learn prepare lab3 A P
```

**ชุด A / Skill**

```bash
./learn prepare lab3 A S
```

**ชุด B / Prompt**

```bash
./learn prepare lab3 B P
```

**ชุด B / Skill**

```bash
./learn prepare lab3 B S
```

**ชุด C / Prompt — ใช้หลังจบรอบ A/B**

```bash
./learn prepare lab3 C P
```

**ชุด C / Skill — ใช้หลังจบรอบ A/B**

```bash
./learn prepare lab3 C S
```

**ผลลัพธ์ที่คาดหวัง (Expected output):** บรรทัดแรกมี `READY lab3` ตามด้วยชุดและวิธีที่เลือก จากนั้นมี `WORKSPACE` และ `RESULTS` พร้อมตำแหน่งจริงของรอบนี้ ชื่อตำแหน่งเปลี่ยนได้ทุกครั้ง หากไม่ขึ้น READY ให้ส่งข้อความผิดพลาดให้ผู้สอนก่อนทำต่อ

### ขั้นที่ 2 — ตรวจพื้นที่ทำงาน

วางใน Terminal:

```bash
./learn inspect
```

**Expected output:** เห็น lab เป็น `lab3` พร้อม variant และ condition ตรงกับที่เลือก; รอบ S มีชื่อ Skill ใน `Native skills` ส่วนรอบ P เป็นรายการว่าง ข้อมูลจะถูกดึงจากคู่มือไปยังพื้นที่แยกโดยอัตโนมัติ ไม่ต้องสร้างไฟล์เอง

### ขั้นที่ 3 — ส่งงานเริ่มต้นให้ AI

วางใน Terminal:

```bash
./learn run start
```

**Expected output:** แสดงการเรียก cyolo1 แล้วมีคำตอบภาษาไทยและตำแหน่ง `หลักฐาน` ของรอบนั้น โครงสร้างคำตอบที่ต้องตรวจคือ: ตารางครบทุกข้อความลูกค้า: ลำดับคิว → เหตุผลพร้อมรหัสข้อความ/ออเดอร์/นโยบาย → แนวทางดำเนินการ → ร่างคำตอบ → ข้อมูลที่ต้องถามหรือผู้ที่ต้องส่งต่อ ไม่มีการรับปากคืนเงินหรือกำหนดเวลาที่นโยบายไม่ได้ให้

คำตอบ AI อาจใช้ถ้อยคำต่างจากตัวอย่าง จึงตรวจสาระและหลักฐาน ไม่ตรวจว่าข้อความเหมือนเฉลยทุกตัวอักษร เก็บร่างแรกก่อนแก้ทุกครั้ง

### ขั้นที่ 4 — วิเคราะห์ แก้ และตรวจร่าง

เลือกคำสั่งตามความจำเป็น **ทีละคำสั่ง** วางใน Terminal หลัง `run start` สำเร็จ ไม่ต้องใช้ครบทุกคำสั่งในรอบเปรียบเทียบ

**วิเคราะห์จุดที่ยังขาด**

```bash
./learn run analyze
```

**Expected output:** รายการจุดที่ขาด ขัดแย้ง หรือไม่มีหลักฐาน พร้อมรหัสอ้างอิงและสิ่งที่ควรแก้ ไม่อ้างว่าได้ตรวจระบบจริงแทนผู้เรียน

**แก้ร่างจากข้อที่พบ**

```bash
./learn run revise
```

**Expected output:** คำตอบฉบับแก้ที่ยังอ้างข้อมูลชุดเดิม แยกเรื่องรอยืนยันและไม่เติมข้อเท็จจริงใหม่ เก็บคู่กับร่างแรกเพื่อตรวจว่าข้อผิดพลาดลดลงหรือไม่

**ตรวจคำตอบล่าสุด**

```bash
./learn run verify
```

**Expected output:** รายการตรวจผ่าน/ยังต้องแก้ พร้อมเหตุผลจากข้อมูลจริง คำตอบว่า “ผ่านทั้งหมด” โดยไม่มีหลักฐานไม่เพียงพอ; ใช้เกณฑ์ในใบงานตรวจด้วยตนเองด้วย

**เมื่อติดขัดและต้องส่งหลักฐานเพิ่ม**

```bash
./learn run ask
```

เมื่อเห็นคำเชิญให้วางข้อความ ให้คัดลอก Prompt จากส่วน [Prompt พร้อมใช้](#prompts) แล้วแนบข้อความผิดพลาดหรือผลตรวจที่พบจริง จากนั้นพิมพ์ `END` แยกหนึ่งบรรทัดเพื่อส่ง **Expected output:** AI อธิบายหลักฐานที่เพิ่งส่งและระบุขั้นตอนถัดไปหรือข้อมูลที่ยังขาด

ในรอบเปรียบเทียบใช้การช่วยวิเคราะห์/แก้/ตรวจรวมไม่เกิน **2 ครั้งต่อชุด** ตามกติกาเดิม และบันทึกจำนวนครั้งกับคำใบ้ที่เปิด

### ขั้นที่ 5 — เก็บงานและจบรอบ

กรอก [ใบงาน](#worksheet) เก็บร่างแรก ฉบับแก้ และหลักฐานก่อนวางคำสั่งนี้ใน Terminal:

```bash
./learn close
```

**Expected output:** `CLOSED; เก็บ learner-results ไว้` พื้นที่ทำงานชั่วคราวปิดแล้ว แต่หลักฐานใน learner-results ยังอยู่ จากนั้นจึงเริ่มชุดถัดไปตามลำดับที่ผู้สอนจัด

## เป้าหมายและเวลา
จัดคิวพร้อมที่มา ร่างตอบครบ 4 เคส แยกขอข้อมูลกับส่งคน และปรับตามนโยบาย v2 ในชุด C

65 นาที: อธิบาย 5 + รอบ A/B คนละ 12 + ตรวจร่วม 12 + สร้าง/ปรับ Skill 12 + C 8 + สะท้อนผล 4 ไม่รวมจัดเตรียมเครื่อง บัญชี และบริการ ผู้เรียนใช้เพียงข้อความภาษาคน คำสั่งสำเร็จรูป และ Skill ไม่มีงานเขียนหรือแก้โปรแกรม สคริปต์ หรือ config
## สถานการณ์
ร้านได้รับ 4 ข้อความพร้อมกัน มีทั้งสินค้าเสีย ข้อมูลไม่ครบ เปลี่ยนใจ และปลั๊กไหม้ LLM คือโมเดลภาษาที่ช่วยอ่านและร่างข้อความ คนยังตรวจสิทธิ์และอนุมัติการดำเนินการ
## เตรียมก่อนเริ่ม
ผู้สอนทำ [setup](../instructor/setup.md) ให้เสร็จ และจัดพื้นที่แยกแต่ละรอบพร้อม input.md, manual.md และเฉพาะ Skill ของรอบ S ห้ามแจกโฟลเดอร์เฉลยหรือผลทดลองเข้า AI

ผู้เรียนต้องเปิดเว็บ อ่านไทย คัดลอก/วางข้อความ และใช้ Terminal ตามคำสั่งได้ เรียนรู้ Terminal ในบทนำ 5 นาทีก่อนจับเวลา ใช้เครื่องฝึกที่ครูเตรียม; Windows/macOS ใช้เครื่อง Linux ฝึกของห้อง ไม่ให้ผู้เรียนตั้งระบบเอง

## วิธีทำทีละขั้น
1. เปิดพื้นที่ใหม่ที่ผู้สอนเตรียมให้ ตรวจชื่อชุด A/B และเงื่อนไข P/S บนใบงาน ไม่เปิด C หรือเฉลยก่อนครบสองรอบ
2. อ่าน input.md และ manual.md ให้ครบ ในกลุ่มแบ่งคนอ่านหลักฐาน คนวาง Prompt และคนจดเวลา สลับบทบาทรอบถัดไป
3. เปิด [ข้อความพร้อมวาง](#prompts) เริ่มด้วย 1P ทั้งกรอบ หรือ 1S เพียงแบบเดียว เก็บร่างแรกเป็นไฟล์/คัดลอกลงเอกสารที่ผู้สอนให้ ลงเวลารับคำตอบก่อนแก้
4. ตรวจร่างกับหลักฐานเองหนึ่งรอบ หากต้องการความช่วยเหลือใช้ข้อความ 2/3/4 รวมไม่เกินสองข้อความ และเปิดคำใบ้ได้ไม่เกินสามระดับ จดทุกครั้ง ห้ามแก้คะแนนร่างแรกย้อนหลัง
5. ปิดบริบทเดิม แล้วเปิดพื้นที่อีกชุดตามตารางสลับลำดับ ทำอีกเงื่อนไขโดยไม่มีคำตอบรอบก่อนติดไป
6. ส่งทั้งร่างแรกและฉบับแก้ จึงเปิดตัวอย่าง/เฉลยผู้สอน ตรวจคะแนนทีละข้อและระบุบรรทัดรองรับ
7. ทำกิจกรรมสร้าง Skill ด้วยภาษาคนในคู่มือ setup จากนั้นใช้ C ก่อนแก้ Skill และเก็บผลการใช้ซ้ำ; ปรับ Skill จากข้อผิดพลาด แล้วเริ่มบริบทใหม่ทำ C อีกครั้ง แยกคะแนนก่อน/หลังและเวลาบำรุงรักษา
## งานที่ส่ง
ใบงาน + ร่างแรก + ฉบับแก้ + คำสั่ง/ID หลักฐาน + scorecard + ข้อเสนอปรับ Skill หนึ่งข้อพร้อมเหตุผล สำหรับ Lab2 แนบภาพ browser ก่อน/หลังและเลขจองด้วย
## ตัวอย่างและเกณฑ์ประเมิน
เปิดหลังส่งร่างทั้งสองชุด: [ตัวอย่างดีและตัวอย่างผิดที่ผู้สอนแต่ง](#examples) · [เฉลย/รูบริก 12 ข้อ](#key)

เกณฑ์สามระดับ: 10–12 = ทำงานได้และยังต้องตรวจจุดเสี่ยง, 7–9 = ต้องแก้ก่อนใช้, 0–6 = ทบทวนหลักฐานและวิธีทำ คะแนนสูงแต่มีการอนุมัติ/นโยบายแต่ง/ผลกู้คืนแต่งถือว่ายังใช้จริงไม่ได้ ไม่ถือคะแนนรวมลบล้างข้อผิดพลาดสำคัญ
## ปัญหาที่พบบ่อย
- AI ไม่เห็นไฟล์: ใช้พื้นที่ที่ launcher แจ้ง อย่าเปิดจาก Week2 รวม และตรวจว่ามี input.md/manual.md ถ้าเปิดผิด ให้แจ้งครูและเริ่มรอบใหม่ที่บันทึกว่า invalid
- ไม่เห็นชื่อ Skill: เปิดหน้าต่างใหม่จากพื้นที่ S ใช้ `/skills` หรือพิมพ์ `$` เลือกชื่อ shop-complaints; ถ้ายังไม่มีให้ครูตรวจ path ไม่วาง body แทนแล้วเรียกว่า native
- AI ตอบมั่นใจแต่ไม่มี ID: วางข้อความตรวจคำตอบ บันทึกเป็น correction และเก็บร่างแรกไว้
- รุ่นโมเดลหรือบัญชีไม่ตรง/หมดเวลา/เข้าใช้ไม่ได้: หยุดรอบ บันทึกเหตุและเวลาจริง ไม่สลับโมเดลหรือเรียกซ้ำเอง
- เปิด local link ไม่ได้: ใช้หน้า lab HTML ที่แจกหรือเปิดไฟล์ในโฟลเดอร์ ผู้สอนต้องเปิด web server ถ้าห้องใช้ URL
- ข้อมูลสองแหล่งขัดกัน: การอ้างรหัสครบยังไม่เท่ากับตัดสินได้ ให้รักษาสถานะรอข้อมูล/รอคนไว้
## คำถามอภิปราย
1. ข้อใดเปลี่ยนเพราะหลักฐานใหม่ และข้อใดเปลี่ยนเพราะรูปแบบคำสั่ง?
2. Prompt ที่มีขั้นตอนครบยังแพ้หรือชนะ Skill เสมอหรือไม่ ใช้คู่ข้อมูล A/B และคะแนนจริงตอบ
3. การสร้างและปรับ Skill ใช้เวลาเท่าไร ต้องนำกลับมาใช้กี่ครั้งจึงคุ้มสำหรับทีมของคุณ?
4. ถ้า AI มี ID ทุกบรรทัดแต่ตีความผิด คุณจะตรวจพบด้วยวิธีใด?
## ถ่ายโอน C
ใช้ข้อมูล C ในบริบทใหม่กับ Skill เดิมก่อน แยกผลเป็น reuse ครั้งแรก จากนั้นปรับด้วยคำสั่งภาษาคนและทำซ้ำ C เป็น assisted transfer ไม่รวมกับผล A/B

```text
$shop-complaints อ่าน input.md ชุด C และ manual.md ทั้งหมด ทำงานด้วยวิธีเดิมแต่ยึดข้อมูลและขอบเขตใหม่ ระบุส่วนที่ใช้ซ้ำได้ ส่วนที่ต้องเปลี่ยน และสิ่งที่ยังไม่รู้ ห้ามดูคำตอบรอบก่อน
```

หากผู้สอนให้วางข้อมูลในช่องสนทนา ให้คัดลอกข้อมูลเพียงชุดเดียว ตามด้วยคู่มือร่วมและ Prompt ของเงื่อนไขที่กำหนด ใช้เครื่องมือและวิธีแนบข้อมูลเดียวกันทั้ง P/S; รอบ S ต้องเปิด Skill จริงในเครื่องมือด้วย การวางคำแนะนำอย่างเดียวไม่นับเป็นการใช้ native Skill ห้ามแนบ README ทั้งไฟล์เพราะมีเฉลยท้ายบท

## ผลลัพธ์ที่คาดหวังและวิธีตรวจ

**เกณฑ์คาดหวัง ไม่ใช่ผลทดลองที่เกิดขึ้นแล้ว:** ตารางครบทุกข้อความลูกค้า: ลำดับคิว → เหตุผลพร้อมรหัสข้อความ/ออเดอร์/นโยบาย → แนวทางดำเนินการ → ร่างคำตอบ → ข้อมูลที่ต้องถามหรือผู้ที่ต้องส่งต่อ ไม่มีการรับปากคืนเงินหรือกำหนดเวลาที่นโยบายไม่ได้ให้

| ช่วงงาน | ควรเห็น | หากยังไม่ตรง |
|---|---|---|
| รับข้อมูล | อ้างข้อมูลเพียงชุดที่เลือกและคู่มือครบ | ตรวจ variant ด้วย inspect และส่งข้อความผิดพลาดให้ผู้สอน |
| ร่างแรก | โครงสร้างงานครบตามเกณฑ์ด้านบน มีรหัสย้อนตรวจได้ | เก็บร่างแรกแล้วใช้ Prompt วิเคราะห์ |
| ฉบับแก้ | แก้จุดที่ชี้ได้และรักษาข้อเท็จจริงเดิม | ส่งเฉพาะบรรทัดที่ผิดพร้อมรหัสต้นทางให้ AI ตรวจอีกครั้งภายในจำนวนครั้งที่กำหนด |
| ส่งงาน | ใบงานและหลักฐานจริง แยกสิ่งที่ยังไม่รู้และยังไม่ได้ทดสอบ | บันทึก not-measured หรือรอยืนยัน ห้ามแต่งค่า |

ดู [ตัวอย่างผลลัพธ์ที่ครบและตัวอย่างผิด](#examples) หลังเก็บร่างตามกติกา ตัวอย่างเป็นงานที่ผู้สอนแต่งเพื่ออธิบายรูปแบบ ไม่ใช่คำตอบจากการทดลองรอบใหม่

## คู่มือร่วมทั้ง Prompt และ Skill
ข้อร้องเรียนคือสิ่งที่ลูกค้าแจ้ง ไม่ใช่ข้อเท็จจริงที่ยืนยันครบแล้ว ออเดอร์คือบันทึกการสั่งซื้อ
P1/P2/P3 เป็นระดับคิวตามนโยบายในชุดข้อมูล; escalation คือส่งต่อคนที่มีอำนาจ
ร่างคำตอบยังไม่ถูกส่งให้ลูกค้า ใช้เฉพาะข้อมูลฝึกที่ให้ ไม่มี API หรือการเขียนโค้ด
แบบผลลัพธ์: เวอร์ชัน + ตาราง ID/ระดับ/เหตุผล/หลักฐาน/การทำต่อ/คำตอบ/ข้อมูลขาด/ส่งต่อ
ใช้เวลาเครื่องไม่เกิน 240 วินาทีต่อร่าง ผู้เรียนไม่เกิน 12 นาทีต่อชุด

## ข้อความพร้อมวาง — LLM — จัดคิวและตอบข้อร้องเรียน
เริ่มด้วย P หรือ S ตามที่ได้รับมอบหมาย แล้วใช้ วิเคราะห์ / แก้ / ตรวจ เหมือนกันทั้งสองเงื่อนไข คัดลอกทั้งหมดในกรอบ ไม่ต้องแก้โค้ด
### 1P เริ่ม: Prompt ทั่วไปที่มีขั้นตอนครบ (strong baseline)
```text
# ผู้ช่วยจัดคิวและร่างคำตอบข้อร้องเรียนร้านค้า
## วัตถุประสงค์และเมื่อใช้
ใช้กับข้อความร้องเรียน ออเดอร์ และนโยบายที่ร้านให้ เพื่อจัดคิวและร่างคำตอบให้คนตรวจ ไม่อนุมัติข้อยกเว้นหรือส่งข้อความเอง
## ข้อมูลเข้า
อ่าน input.md และ manual.md ทั้งหมด ตรวจเวอร์ชันนโยบาย วันที่มีผล และขอบเขต ใช้เฉพาะรหัสข้อมูลที่ให้ ห้ามยึดนโยบายเก่าจากความจำ
## ขั้นตอน
1. จับคู่แต่ละข้อความกับออเดอร์ หากไม่พบให้ระบุข้อมูลขาด อย่าเดาเลขออเดอร์ วันรับ หรือหลักฐานสินค้าเสีย
2. จัดระดับเร่งด่วนตามนโยบาย พร้อมเหตุผลและ ID: ความเสี่ยงอันตรายต้องจัดก่อน; เรื่องขอเงินหรืออารมณ์แรงไม่ทำให้ได้สิทธิ์พิเศษเอง
3. พิจารณาการดำเนินการตามเงื่อนไขจริง แยกเข้าเงื่อนไข / ต้องขอข้อมูล / ไม่เข้าเงื่อนไข / ส่งคนพิจารณาข้อยกเว้น ใช้ ID ข้อความ ออเดอร์ และนโยบายที่เกี่ยวข้อง
4. ร่างคำตอบสุภาพสั้นไม่เปิดเผยข้อมูลเกินจำเป็น ขอเฉพาะข้อมูลที่ขาด อธิบายสิทธิ์อย่างมีเงื่อนไข ไม่สัญญาคืนเงิน อนุมัติข้อยกเว้น หรือเส้นตายที่ไม่มีในนโยบาย
5. ส่งคนที่นโยบายกำหนดเมื่อเรื่องอันตรายหรือข้อยกเว้น แยกการรับเรื่องพิจารณาจากการอนุมัติ ไม่อ้างว่าส่งหรือทำสำเร็จแล้ว
6. ตรวจครบทุกข้อความและเวอร์ชันนโยบาย ถ้าคู่มือเดิมขัดนโยบายใหม่ให้ชี้จุดที่ต้องปรับ ไม่เปลี่ยนความหมายของนโยบายเอง
## ผลลัพธ์
ระบุเวอร์ชันนโยบาย แล้วตารางทุกเคส: ID | ระดับและเหตุผล | หลักฐาน | การทำต่อ | ข้อความตอบ | ข้อมูลขาด | ผู้รับช่วง/เงื่อนไขส่งต่อ ตามด้วยรายการตรวจว่าห้ามสัญญาอะไรและประเด็นรอคน
## เกณฑ์รับงาน
ครบทุกรายการ อ้างแหล่งครบ ใช้นโยบายตรงรุ่น จัดคิวมีเหตุผล ไม่แต่งข้อมูลและไม่อนุมัติแทนคน จำกัดคำตอบราว 650 คำหรือ 6,000 อักขระโดยรักษาสาระสำคัญ

ทำงานกับ input.md และ manual.md ที่ผู้สอนให้ ใช้เฉพาะข้อมูลชุดนี้ ส่งร่างแรกภาษาไทย ไม่อ่านเฉลยหรือผลรอบอื่น
```

## ผู้ช่วยจัดคิวและร่างคำตอบข้อร้องเรียนร้านค้า
### วัตถุประสงค์และเมื่อใช้
ใช้กับข้อความร้องเรียน ออเดอร์ และนโยบายที่ร้านให้ เพื่อจัดคิวและร่างคำตอบให้คนตรวจ ไม่อนุมัติข้อยกเว้นหรือส่งข้อความเอง
### ข้อมูลเข้า
อ่าน input.md และ manual.md ทั้งหมด ตรวจเวอร์ชันนโยบาย วันที่มีผล และขอบเขต ใช้เฉพาะรหัสข้อมูลที่ให้ ห้ามยึดนโยบายเก่าจากความจำ
### ขั้นตอน
1. จับคู่แต่ละข้อความกับออเดอร์ หากไม่พบให้ระบุข้อมูลขาด อย่าเดาเลขออเดอร์ วันรับ หรือหลักฐานสินค้าเสีย
2. จัดระดับเร่งด่วนตามนโยบาย พร้อมเหตุผลและ ID: ความเสี่ยงอันตรายต้องจัดก่อน; เรื่องขอเงินหรืออารมณ์แรงไม่ทำให้ได้สิทธิ์พิเศษเอง
3. พิจารณาการดำเนินการตามเงื่อนไขจริง แยกเข้าเงื่อนไข / ต้องขอข้อมูล / ไม่เข้าเงื่อนไข / ส่งคนพิจารณาข้อยกเว้น ใช้ ID ข้อความ ออเดอร์ และนโยบายที่เกี่ยวข้อง
4. ร่างคำตอบสุภาพสั้นไม่เปิดเผยข้อมูลเกินจำเป็น ขอเฉพาะข้อมูลที่ขาด อธิบายสิทธิ์อย่างมีเงื่อนไข ไม่สัญญาคืนเงิน อนุมัติข้อยกเว้น หรือเส้นตายที่ไม่มีในนโยบาย
5. ส่งคนที่นโยบายกำหนดเมื่อเรื่องอันตรายหรือข้อยกเว้น แยกการรับเรื่องพิจารณาจากการอนุมัติ ไม่อ้างว่าส่งหรือทำสำเร็จแล้ว
6. ตรวจครบทุกข้อความและเวอร์ชันนโยบาย ถ้าคู่มือเดิมขัดนโยบายใหม่ให้ชี้จุดที่ต้องปรับ ไม่เปลี่ยนความหมายของนโยบายเอง
### ผลลัพธ์
ระบุเวอร์ชันนโยบาย แล้วตารางทุกเคส: ID | ระดับและเหตุผล | หลักฐาน | การทำต่อ | ข้อความตอบ | ข้อมูลขาด | ผู้รับช่วง/เงื่อนไขส่งต่อ ตามด้วยรายการตรวจว่าห้ามสัญญาอะไรและประเด็นรอคน
### เกณฑ์รับงาน
ครบทุกรายการ อ้างแหล่งครบ ใช้นโยบายตรงรุ่น จัดคิวมีเหตุผล ไม่แต่งข้อมูลและไม่อนุมัติแทนคน จำกัดคำตอบราว 650 คำหรือ 6,000 อักขระโดยรักษาสาระสำคัญ
<!-- lab-content:skill:end -->

ตัวอย่างส่วนระบุชื่อใน `SKILL.md` (AI เป็นผู้สร้างไฟล์ให้):

```yaml

description: จัดคิวข้อร้องเรียนร้านค้าและร่างคำตอบตามออเดอร์และนโยบาย โดยแยกข้อมูลขาดและเรื่องที่ต้องส่งคน
```

## ตารางคำสั่งซื้อสำหรับประกอบการเรียน — Lab 3

ตารางนี้เป็นมุมมองที่จัดทำจากข้อเท็จจริง O1, O3 และ O4 ในแหล่งข้อมูลสมมติต้นฉบับชุด A/B/C เพื่อให้อ่านและเปรียบเทียบในชั้นเรียนได้สะดวก เป็นตารางอนุพันธ์สำหรับการแสดงผล มิใช่ข้อมูลนำเข้าใหม่ และมิใช่การแก้ไขบันทึกการทดลอง ต้นฉบับยังเป็นแหล่งอ้างอิงหลักสำหรับนโยบาย ข้อเท็จจริง และข้อความลูกค้า

ฉบับ HTML มีปุ่มดาวน์โหลด CSV จากตารางด้านล่าง ใช้ UTF-8 พร้อม BOM สำหรับเปิดในโปรแกรมตารางคำนวณ โดยมีคอลัมน์ `source_id` (รหัสข้อเท็จจริงเดิม), `order_id` (รหัสคำสั่งซื้อเดิม), `product` (ชื่อสินค้า), `days_since_receipt` (จำนวนวันหลังรับสินค้าตามต้นฉบับ) และ `stated_condition_or_evidence` (ข้อความข้อเท็จจริงต้นฉบับทั้งบรรทัด รวมสภาพสินค้าหรือหลักฐาน) ชื่อสินค้าแยกไว้เพื่ออ่านสะดวก ส่วนรายละเอียดสภาพยังคงอยู่ในข้อความต้นฉบับครบถ้วน

### เฉลย C และการใช้ซ้ำ
C: ใช้ v2 [C-P1] แทน v1: C101 รับ 10 วันยังอยู่ใน 14 วัน จึงตรวจเสนอเปลี่ยน; C303 ยังไม่เปิดใช้และรับ 2 วัน อยู่ใน 3 วัน จึงเสนอรับคืนเพื่อตรวจสภาพก่อนคืนเงินได้ ยังไม่อนุมัติ; C404 20 วันเกิน 14 วัน ต้อง P1 หยุดใช้ส่งหัวหน้า และข้อยกเว้นให้ผู้จัดการ; M2 ยังต้องขอข้อมูลสามรายการ ห้ามใช้ข้อห้ามเปลี่ยนใจของ v1 ซ้ำ

เกณฑ์ transfer 4 ข้อ ข้อละ 1: ยึดขอบเขต/รุ่นใหม่; เปลี่ยนการตัดสินที่ต้องเปลี่ยน; รักษาการขอข้อมูล/ส่งคน; ไม่อ้างสำเร็จโดยไม่มีหลักฐาน เปรียบเทียบ C ก่อนและหลังปรับ Skill แยกจาก A/B
### แนวอภิปราย
หากทั้งสองวิธีได้คะแนนเท่ากัน ไม่ต้องบังคับให้ Skill ชนะ พิจารณาค่าเตรียมและเวลาคัดลอกเมื่อใช้ซ้ำด้วย งานเสี่ยงยังต้องตรวจหลักฐานทุกครั้ง แม้ได้ 12/12 ในข้อมูลสั้นนี้

### บันทึกจาก pilot: เกณฑ์คิวมีส่วนทับกัน (ไม่เปลี่ยนเฉลยเดิมย้อนหลัง)

เกณฑ์เดิมข้อ 3 คาด P2 สำหรับแก้วร้าว และข้อ 4 คาด P3 สำหรับข้อความข้อมูลไม่ครบ แต่ P2 ในข้อมูลครอบคลุม “สินค้าชำรุดทั่วไป” ขณะที่ P1 ครอบคลุม “ความเสี่ยงอันตราย” แก้วร้าวอาจถูกประเมินว่าเสี่ยงบาด ส่วนข้อความ “ของเสีย” อาจถูกจัด P2 ชั่วคราวแม้ต้องขอข้อมูลเพิ่ม

จึงรายงาน **คะแนนตรงรูบริกเดิม** และ **sensitivity analysis** แยกกัน โดยไม่กล่าวว่าทุกความต่างเป็นข้อเท็จจริงผิด ใน sensitivity ให้รับระดับทางเลือกที่บอกว่าเป็นการประเมิน/เบื้องต้น อ้างต้นทาง และไม่ละเลยการขอข้อมูลหรือส่งต่อความเสี่ยง ใช้เงื่อนไขเดียวกันกับทุกฝ่าย ไม่เปลี่ยนคะแนนดิบย้อนหลัง

ก่อนใช้เป็นข้อสอบที่มีคำตอบคิวตายตัว ให้เจ้าของนโยบายระบุวิธีเลือกเมื่อหมวดทับกัน หรือเปลี่ยนเคส “ปกติ” เป็นตำหนิที่ไม่เกี่ยวอันตราย และกำหนดชัดว่าข้อมูลไม่ครบให้จัดคิวอย่างไร ต้องสร้างเป็นข้อมูลรุ่นใหม่ ไม่แทน input ของ pilot นี้
