แผนเปรียบเทียบอย่างเป็นธรรม

วันที่จัดทำอ้างจาก UTC ใน evidence/build และ metadata ของแต่ละ run ข้อมูล A/B/C ของ Lab1/3 เป็นข้อมูลฝึกสมมติใหม่ ส่วน Lab2 A/B เป็น snapshot ก่อนกู้จากบริการจริงในแพ็กเกจ ไม่ใช้ผลทดลอง Week1 เป็นผลใหม่

คำถามวิจัยสำหรับห้องเรียน

เมื่อใช้คำแนะนำกระบวนการเดียวกัน Skill ช่วยรักษาความครบถ้วนและลดภาระการใช้ซ้ำหรือไม่? ไม่ตั้งสมมติฐานว่าต้องชนะ Prompt เสมอ ความต่างรอบเดียวอาจเกิดจากความสุ่ม ความยาวคำตอบ ลำดับเรียนรู้ และเครือข่าย

เงื่อนไข

P = Prompt ทั่วไปที่มีขั้นตอนครบ (strong baseline) มีเนื้อหาคำสั่งตรงส่วน Skill ใน README ของแต่ละ Lab และ body ใน SKILL.md; S = ใช้ชื่อ native Skill ผ่าน $shop-... จาก .agents/skills พร้อมข้อมูลและคู่มือเดียวกัน ไม่เอา Prompt สั้นที่ขาดขั้นมาแข่ง

คงที่: cyolo1 / gpt-6-astra / high, input+manual ต่อชุด, อุปกรณ์, รายการคำสั่ง, tools, คำใบ้, รูบริก, งบเวลาและจำนวนความช่วยเหลือ ตั้ง fresh context ทุก trial ไม่ใช้ resume ไม่มีเฉลย ร่างเดิม หรือผลคนอื่นในโฟลเดอร์ AI

ใช้ temporary input-only project แยกนอก Week2 แล้วตรวจ trace ของการอ่าน การแยกโฟลเดอร์นี้ไม่ใช่ OS sandbox; wrapper cyolo1 มี bypass จึงจำกัดคำสั่งและตรวจ trace ไม่กล่าวอ้างว่าป้องกันการอ่านไฟล์อื่นได้ทางระบบ การทดลองไม่มี credential reads/copies

Lab1 A/B: 8 แหล่ง สี่หมวด สามข้อขัดแย้ง และข้อมูลขาดเท่ากัน เปลี่ยนชื่อ/เปอร์เซ็นต์/จำนวนวัน; Lab3 A/B: 10 แหล่ง สี่เคสประเภทเดียวกัน เปลี่ยนชื่อออเดอร์และวันรับซึ่งยังอยู่ในเกณฑ์; Lab2 A/B: อย่างละสองเหตุการณ์ basic=บริการหยุด และ advanced=v2 จองเสีย เปรียบเทียบภายในชนิดสาเหตุเดียวกัน ห้ามเทียบ start ของฝ่ายหนึ่งกับ rollback ของอีกฝ่าย

เครื่อง: 1 คำตอบแรกต่อ trial, deadline 240 วินาที, คำตอบเป้าหมายราว 650 คำ/6,000 อักขระ (ไม่ใช่ hard token cap), ไม่มีการโต้ตอบกับผู้เรียนใน pilot ไม่มี forced seed และไม่รับประกันเวลาหรือโทเคนเท่ากัน

ผู้เรียน: Lab1/3 รอบละ 12 นาที; Lab2 30 นาทีต่อชุดที่มีสองเหตุการณ์; ให้ความช่วยเหลือผ่านข้อความวิเคราะห์/แก้/ตรวจรวมไม่เกิน 2 ครั้ง และคำใบ้ไม่เกิน 3 ระดับเหมือนกัน ต้องนับและเก็บร่างก่อนช่วย ข้อมูล C ใช้หลังรอบหลัก

การวัด

  • คะแนน completeness 12 รายการตามเฉลย เก็บ vector 0/1 และหลักฐาน ไม่ใช้ค้น keyword ตัดสินคุณภาพ
  • accuracy = ข้ออ้างที่รองรับ / ข้ออ้างทั้งหมด เมื่อมีผู้ตรวจนับจริง มิฉะนั้น not-measured
  • เวลา latency เครื่อง และเวลาผู้เรียนแยกกัน; การแก้/คำใบ้ของมนุษย์ not-measured ใน technical pilot ไม่ใช้ 0 อ้างว่าคนไม่ต้องแก้
  • Lab1: ข้อขัดแย้งที่พบจาก 3, สิ่งที่ขาด, การเดา precedence; Lab2: สาเหตุตรง, คำสั่งอนุญาต, browser transaction จริง; Lab3: ครบเคส, คิว, policy version, ข้อยกเว้นที่ไม่อนุมัติเอง
  • ต้นทุน setup/สร้าง Skill/ปรับ Skill แยกจากเวลาภารกิจ และต้นทุนตรวจ native เพิ่มแยกจาก trial หลัก
  • เก็บผลร่างแรกและผลประเมินของร่างนั้น ไม่เรียกคะแนนประเมินว่าเป็นฉบับที่แก้แล้ว ถ้าไม่มี assisted rerun ให้ช่องฉบับแก้เป็น not-measured

เหตุล้มเหลวและข้อจำกัด

เก็บ timeout/error/ไม่ยืนยัน native เป็นแถวที่ตรวจสอบได้ ห้ามลบทิ้งหรือเรียกซ้ำโดยไม่เปิดเผย JSONL บางรุ่นไม่บันทึกการโหลด body ของ $skill อัตโนมัติ จึงต้องมี explicit file-read confirmation ที่ path native ก่อนนับผ่าน gate การยืนยันด้วยคำพูด AI อย่างเดียวไม่พอ

การทดลองนี้เป็น technical pilot ของผู้จัดทำ ไม่ใช่งานวิจัยกับนักเรียนจริง จำนวนตัวอย่างน้อย ผู้จัดทำแพ็กเกจ (AI worker) ตรวจเองและไม่ blind ยังไม่มีผู้ประเมินมนุษย์อิสระ ไม่ประมาณนัยสำคัญหรือความเหนือกว่าสากล เสนอให้ห้องเรียนทำซ้ำหลายกลุ่ม สลับลำดับ ปกปิดเงื่อนไขจากผู้ตรวจ และทดสอบ C ก่อนปรับคู่มือ
