2. **🆕 เกินบทเรียน ① การจองชนกัน:** เขียน test ที่เปิด **2 browser context พร้อมกัน** จองห้องเดียวกันเวลาเดียวกัน (ยิงพร้อมกันจริง ไม่ใช่ทีละคน) วนอย่างน้อย 50 รอบ ต้องได้ผู้ชนะ 1 คนทุกรอบ · ถ้าเว็บที่ AI สร้างพัง ให้บันทึกบั๊ก **แล้วสั่งแก้ที่ต้นเหตุ** (ระดับ DB constraint / transaction ไม่ใช่เช็กใน UI) และพิสูจน์ว่า test ผ่านหลังแก้
3. **🆕 เกินบทเรียน ② กฎเงินแบบ property-based:** เขียนฟังก์ชัน **oracle อิสระ** คำนวณราคาจาก [D]+[R] เท่านั้น (ห้าม import โค้ดของเว็บ) แล้วใช้ `fast-check` สุ่มการจอง ≥ 1,000 แบบ (ห้อง × เวลาเริ่ม × ความยาว × ระดับสมาชิก × คูปอง) เทียบกับราคาที่ API ของเว็บตอบ · ข้อที่ไม่ตรงต้องย่อ (shrink) เป็นตัวอย่างเล็กสุดและจัดเข้า triage

## ข้อ 2 · skill `interview-to-testplan`: ใช้ได้กับร้านที่ไม่เคยเห็น (20%)

### ที่มา
ส่วน 02 สร้าง skill `test-from-plan` แล้วสอนให้ "เรียนรู้" จากเว็บเดียว (petshop) แต่ **ไม่เคยพิสูจน์ว่า skill ไม่ได้จำคำตอบของเว็บนั้น** และการวัดว่า skill ดีขึ้นจริงยังเป็นการดูด้วยตา ไม่ใช่ตัวเลข

### สิ่งที่ต้องทำ
1. เก็บวิธีทำงานบท 04 ช่วง **ฟังร้าน → TEST-PLAN** (LAB 1–4 และ 7–10) เป็น skill เดียวตาม 6 ขั้นของหัวข้อ 16 · ใช้ **ข้อ 1 + สบายใจ สปา** เป็นชุดฝึก
2. **งานที่ต้องคำนวณให้เป็นสคริปต์ ห้ามให้ AI นับเอง** (หลักหัวข้อ 9 "งานซ้ำให้โค้ด งานคิดให้ AI") อย่างน้อย 3 ตัว:
   - `trace_check` — US/BR ไหนไม่มี TC รองรับ
   - `boundary_gen` — สร้างค่าขอบ 3 ค่าจาก BR ที่มีตัวเลข
   - `oracle_lint` — TC ไหนมีแค่ [A]/[O] หรือมีคำว่า "แสดงถูกต้อง" · สัดส่วน [O-ยังไม่ยืนยัน]
3. **ชุด eval ของ skill:** อย่างน้อย 6 เคส ใช้ `claude plugin eval` (แบบ LAB 6) เทียบ **มี skill vs ไม่มี skill** รันเคสละ ≥ 3 รอบ รายงานค่าเฉลี่ยและความแกว่ง ใช้สคริปต์ข้อ 2 เป็นตัวให้คะแนน (ไม่ใช้ AI ตัดสินอย่างเดียว)
4. **วงจรเรียนรู้แบบมีหลักฐาน:** v1 → vN ทุกเวอร์ชันมีบรรทัดใน `CHANGELOG.md` ว่า "เคสไหนพลาด → แก้อะไร → คะแนน eval ก่อน/หลัง" ห้ามแก้ที่ไม่มีเคสพลาดรองรับ
5. **วันส่ง ผู้สอนแจกบันทึกสัมภาษณ์ร้านที่ 3 (hold-out)** ทีมรัน skill **ครั้งเดียว ห้ามแก้ skill** แล้วส่งผล · ถ้า skill ยังพูดถึง "สปา" หรือ "โต๊ะ" ในร้านที่ไม่เกี่ยว = จำคำตอบ (overfit)
6. แพ็กเป็น plugin ที่มีหัวไฟล์ตามมาตรฐานโนวาเทค (`owner`, `layer`, `version`, `uses/next/follows`) เตรียมใช้ในข้อ 3

| ซ่อน URL | ประกอบ URL จากชิ้นส่วนตอนรัน · ใช้ตัวอักษรหน้าตาเหมือน (homoglyph) · encode สั้นกว่าเกณฑ์ BLOB |
| คำสั่งที่ไม่มีคำต้องห้าม | prompt injection ภาษาไทยแบบสุภาพที่ไม่ตรงคำใน `COMMENT_CMD` · ซ่อนใน `references/` ที่โหลดตอนหลัง (ชั้น 3 ของ progressive disclosure) |
| ส่งออกผ่าน AI ไม่ใช่สคริปต์ | ให้ SKILL.md สั่ง AI ใส่ข้อมูลลงลิงก์รูป markdown หรือ "รายงาน" ที่ส่งไปที่อื่น |
| แย่งงาน (trigger hijacking) | `description` ที่ทำให้ skill ถูกเรียกแทน `core:customer-data-policy` หรือ `bug-report` |
| ซัพพลายเชน | dependency ที่โหลดตอนรัน · plugin ชื่อซ้ำ/คล้ายของภายใน |

แต่ละ PR ต้องมี: เป้าหมาย (ขโมยอะไร/ทำอะไร) · หลักฐานว่า CI เขียว · หลักฐานว่า **Claude ที่โต๊ะผู้ใช้ทำตามจริง** เมื่อติดตั้ง (ส่งไป server ปลอมของตัวเอง) · และ **ส่ง PR ให้ทีมอื่นลองจับ** (ผู้สอนจับคู่)

### ส่วน C · Blue Team (12)
1. แก้ CI ให้จับ PR ของ **ทีมตัวเองและทีมคู่** ทั้งหมด โดย **ไม่บล็อก PR ดีที่มีอยู่** (PR A ของ LAB 6 และ skill ข้อ 2 ต้องยังผ่าน) — รายงาน false positive / false negative บนชุด PR ทั้งหมด
2. ทำชุด regression: เก็บ PR อันตรายทุกตัวเป็น fixture ใน `tests/security/` ให้ CI รันทุกครั้ง
3. ปิดช่องโหว่เชิงกระบวนการจาก LAB 5: approve เก่าหมดอายุเมื่อมี commit ใหม่ · CODEOWNER ≥ 2 คนต่อแผนก (หรือกลไกทดแทนถ้า Gitea ทำไม่ได้ — อธิบายเหตุผล)
4. เขียน `THREAT-MODEL.md`: ผู้โจมตีมีสิทธิ์อะไร (เขียน PR ได้ / เป็น CODEOWNER / เข้าถึงเครื่องผู้รีวิว) · ด่านไหนกันอะไร · **อะไรที่ CI ไม่มีทางกันได้ด้วย regex** และต้องพึ่งด่าน eval หรือคน — ห้ามอ้างว่า "กันได้หมด"

### ส่ง
export ของ Gitea (PR ทั้งหมด + Actions log) · `redteam/` (PR + หลักฐาน) · CI ที่แก้แล้ว + `tests/security/` · `THREAT-MODEL.md` · ตารางผลการจับ PR ของทีมคู่

### เกณฑ์ (30)
| คะแนน | วัดอะไร |
|---|---|
| 6 | ส่วน A ครบวงจร PR → CI → eval → approve → release → update ถึงโต๊ะ |
| 12 | แต่ละ PR อันตรายที่ **ผ่าน CI เดิมและได้ผลจริงที่โต๊ะ** = 3 คะแนน (สูงสุด 4 ตัว) · +โบนัส 2 ถ้าทีมคู่จับไม่ได้ |
| 8 | CI ใหม่จับได้ทั้งของตัวเองและทีมคู่ · false positive = 0 บน PR ดี · มี regression |
| 4 | THREAT-MODEL ซื่อตรงเรื่องขีดจำกัด + ปิดช่องโหว่กระบวนการ 2 ข้อ |

## ข้อ 4 · ⭐ คลัง skill 150+ ตัว: หาเจอ วัดได้ เปลี่ยนแปลงได้ไม่พัง (25%)

### ที่มา
LAB 7 วัด `skill-finder` กับคลังแค่ **23 skill** ได้ hit@1 80% บนคำค้นใหม่ และพบว่า (1) คำค้นปนอังกฤษหาไม่เจอ (2) การเติม "สรุปจากเนื้อหา" ไม่ช่วยในคลังเล็ก แต่งานวิจัยบอกว่าช่วยในคลังใหญ่ — **บทเรียนสรุปว่า "ต้องวัดกับคลังของตัวเองเสมอ" แต่ยังไม่ได้วัดตอนคลังโต** (ทฤษฎีหัวข้อ 24.3–24.4, 25)
อีกเรื่องที่ LAB ยังไม่แตะ: เมื่อต้อง **รื้อ skill ที่คนอื่นพึ่งอยู่** จะทำยังไงไม่ให้บริษัทพัง

### ส่วน A · ขยายบริษัท (5)
- เพิ่มแผนก Legal, Marketing, Support, Procurement, Security (หรือแผนกที่ทีมเลือก) จนคลังมี **≥ 150 skill** ที่ **ทำงานได้จริงอย่างน้อย 30 ตัว** ที่เหลือเป็น skill ที่มีหัวไฟล์และขั้นตอนสมจริง
- ต้องมี **คู่ skill ที่ชื่อ/หน้าที่ใกล้กันโดยตั้งใจ** อย่างน้อย 10 คู่ (เช่น `contract-review` ของ Legal กับ `proposal-review` ของ Sales) เพื่อให้การค้นยาก
- ทุกตัวต้องผ่าน CI ของข้อ 3

### ส่วน B · วัดการค้นแบบไม่โกงตัวเอง (12)
1. **ชุดคำค้นจากคนจริง:** ทุกคนในห้องเขียนคำสั่งแบบพนักงาน 10 ข้อ (ไทย อังกฤษ และปน) ผู้สอนรวมเป็นชุดกลาง · **ทีมได้ใช้เฉพาะคำค้นของทีมอื่น** เป็นชุดทดสอบ (กันการเขียนคำค้นให้ตรงกับ description ของตัวเอง แบบ "เคยเห็น 98%" ใน LAB 7)
2. เทียบอย่างน้อย 3 วิธี: BM25 trigram (baseline ของ LAB 7) · embedding/hybrid · LLM rerank top-k · รายงาน **hit@1, hit@5, MRR, latency, ค่าใช้จ่ายต่อ 1,000 คำค้น** ที่ 23 / 75 / 150 skill (ดูว่าเส้นโค้งตัดกันตรงไหน)
3. ตอบด้วยข้อมูล: **"สรุปจากเนื้อหา" เริ่มช่วยที่คลังขนาดเท่าไร** (หรือไม่ช่วยเลย) และคำค้นปนอังกฤษแก้ได้ด้วยอะไร
4. **ตัวตรวจ description ชนกัน:** สคริปต์ใน CI ที่เตือนเมื่อ skill ใหม่มี description ใกล้กับ skill เดิมเกินเกณฑ์ (ต่อยอดจาก PR D ใน LAB 6 ที่ Claude ไม่ยอมสร้าง `report`) — ต้องจับคู่ที่ตั้งใจใส่ในส่วน A ได้

### ส่วน C · เปลี่ยนแปลงโดยไม่พัง (8)
สถานการณ์: ฝ่าย Legal สั่ง **แยก `sales:sales-proposal` เป็น `proposal-bank` กับ `proposal-gov`** เพราะลูกค้าภาครัฐมีกฎข้อมูลต่างจากธนาคาร
1. ใช้กราฟ (`uses/next/follows`) หาทุก skill และทุกโต๊ะที่กระทบ **ก่อน** ลงมือ แล้วเทียบกับที่กระทบจริงหลังทำ
2. ออกแบบการเลิกใช้ (deprecation): `sales-proposal` กลายเป็น skill นำทางชั่วคราวที่ชี้ไปตัวใหม่ · เลขเวอร์ชันแบบ semver (ตัวไหน major ตัวไหน minor และเพราะอะไร) · วันหมดอายุ
3. CI ต้องบล็อกถ้ามีเส้น `uses/next` ชี้ไป skill ที่ถูกลบ · พิสูจน์ด้วย PR ที่ตั้งใจทำผิด
4. รันดีล deal-001 และ deal-002 ซ้ำหลังเปลี่ยน ต้องยังได้ภาคผนวก PDPA ครบเหมือนผล LAB 5

### ส่ง
คลังที่ขยายแล้ว · `search-eval/` (ชุดคำค้น สคริปต์ ผลทุกขนาดคลัง) · `SEARCH-REPORT.md` พร้อมกราฟ · `MIGRATION.md` (กราฟก่อน/หลัง แผนเลิกใช้ ผลรันดีลซ้ำ)
