# ทบทวนความเสี่ยงทางเทคนิค (tech-risk-review)

ทำแบบ CTO: ดูว่างานนี้ **จะพังตรงไหน โดยเฉพาะตรงที่เราเคยพังมาแล้ว** และทีมรับไหวหรือไม่ ไม่ต้องออกแบบระบบหรือคิดราคาเอง
ผลลัพธ์คือไฟล์เดียว `work/<YYYY-MM-DD>-tech-risk-review-<ชื่องาน>.md` ตาม `references/report-template.md`

## 1 · แยกโหมด
- **รับงานใหม่** (มี TOR / proposal / ดีล) → ตอบคำถาม "เสี่ยงตรงไหน" และ "ทีมรับไหวไหม"
- **ขึ้นระบบ** (มี release / ผล test / แผน deploy) → ตอบคำถาม "ปล่อยได้ไหม"
ถ้าไม่ชัดว่าเป็นโหมดไหน ให้ถามผู้ใช้ 1 คำถาม

## 2 · หาข้อมูล
1. อ่านเอกสารของงานนั้นให้ครบ (TOR, release notes, test log, ผลการทดลองโมเดล)
2. ถ้าเครื่องนี้มี `company-kit/` ให้อ่านไฟล์ที่ตรงกับเรื่องนั้นจริง (incident, runbook, arch-standards, monthly-kpi, ml-queue-forecast, qa log) เพราะข้อมูลใน `references/` เป็นภาพ ณ พ.ย. 2026 และอาจล้าสมัยแล้ว
3. ถ้าไม่มี company-kit ให้ใช้ `references/` แทน แล้ว **เขียนในรายงานว่าใช้ข้อมูลอ้างอิง ณ วันที่เท่าไร**

## 3 · ให้คะแนนรายด้าน
ไล่ทุกด้านใน `references/risk-checklist.md` และให้ระดับ 🔴 สูง / 🟠 กลาง / 🟡 ต่ำ / 🟢 ไม่มีประเด็น
- ทุกระดับต้องมี **หลักฐาน** (ไฟล์ + ข้อเท็จจริง) ห้ามให้ระดับจากความรู้สึก
- เทียบกับ `references/lessons-learned.md` ทุกครั้ง: ถ้างานนี้มีรูปแบบเดียวกับที่เคยพัง ให้ขึ้นระดับอย่างน้อย 🟠 และระบุว่าซ้ำกับเหตุการณ์ไหน
- เกณฑ์ภายใน (alert, หน้าต่าง deploy, มาตรฐานสถาปัตยกรรม, ราคาคร่าว ๆ) ดูได้ใน `references/company-standards.md`

## 4 · ตัดสิน
| คำตัดสิน | เมื่อไหร่ |
|---|---|
| **GO** | ไม่มีด้านไหนเป็น 🔴 และมี 🟠 ไม่เกิน 2 ด้าน และทุกด้านมีเจ้าของรับผิดชอบ |
| **GO with conditions** | มี 🔴 ที่ปิดได้ด้วยเงื่อนไขที่ทำทันก่อนจุดตัดสินใจ (วันยื่นข้อเสนอ / วัน deploy) |
| **NO-GO / เลื่อน** | มี 🔴 ที่ปิดไม่ทันก่อนจุดตัดสินใจ — โหมดขึ้นระบบ: E2E ของ flow หลักล้ม, ไม่มีแผน rollback, ไม่มี backup หรือ cert เหลือน้อยกว่า 21 วัน |

เงื่อนไขแต่ละข้อต้องมี **เจ้าของ (user)** และ **กำหนดเวลา** ให้แบ่งเป็น "ก่อนจุดตัดสินใจ" กับ "ระหว่างทำงาน"

## 5 · เขียนรายงาน
- ใช้ `references/report-template.md` และให้คำตอบสั้นอยู่บนสุด อ่าน 30 วินาทีแล้วต้องรู้ว่าควรทำอะไร
- เรื่องร้ายแรงที่เจอระหว่างทางแต่อยู่นอกขอบเขตงาน (เช่น cert ของลูกค้าอื่นใกล้หมด) ให้ใส่ในหัวข้อ "เรื่องด่วนนอกงาน" ห้ามละไว้
- ตัวเลขเงินเป็นแค่ประมาณการ ให้ส่งต่อ `fin-joy` (pricing-calc) ส่วนการอนุมัติดีลเป็นงานของ `md-somchai` (deal-approval)

## กติกา
- ทำตาม skill `core:customer-data-policy`: ห้ามคัดลอกเบอร์มือถือ เลขบัตร หรือเลขบัญชีจาก TOR หรือ log ลงรายงาน
- ไม่ระบุตัวคนที่ทำพลาดในอดีต ให้พูดถึงระบบ (blameless) แต่ระบุเจ้าของงานข้างหน้าได้
- ห้ามแก้เอกสารต้นทางหรือโค้ด skill นี้อ่านและประเมินอย่างเดียว
