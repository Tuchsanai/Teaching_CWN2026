# กติกาขึ้นระบบจริงของโนวาเทค (สรุปสำหรับ skill)

> สรุปจาก `company-kit/deploy-runbook.md` (ปรับปรุงล่าสุด 2026-10-01, ผู้ดูแล `ops-art`) และบทเรียนจาก incident 2026-09, coding-rules ข้อ 7, arch-standards และ customer-data-policy
> ถ้า runbook ฉบับจริงเปลี่ยน ต้องอัปเดตไฟล์นี้และขึ้น version ของ skill

## 0. บทบาทและช่วงเวลา

- ทุกรอบต้องมี 3 บทบาท และคนเดียวถือได้ไม่เกิน 2 บทบาท
  - **Deploy lead** กด deploy และตัดสิน rollback
  - **Verifier** ทำ smoke test ต้องเป็น QA หรือ dev ที่ **ไม่ได้เขียนฟีเจอร์นั้น**
  - **Comms** คุยกับลูกค้าและอัปเดตช่อง `#deploy`
- ช่วงเวลาที่ทำได้: **อังคาร–พฤหัส 21:00–23:00**
- ห้าม deploy ในวันต่อไปนี้ (ยกเว้น hotfix Sev 1):
  - วันศุกร์
  - วันก่อนวันหยุดยาว
  - **ลูกค้าธนาคาร: วันที่ 25 ถึงสิ้นเดือน** (ช่วงเงินเดือนออก)

## 1. เตรียมล่วงหน้า (T−3 ถึง T−1)

1. release notes ต้องเสร็จ และมีรายการ ticket, migration, feature flag และความเสี่ยง
2. ต้องผ่าน UAT และลูกค้าเซ็นรับเป็นลายลักษณ์อักษร (อีเมลก็ได้) · **ไม่มีลายลักษณ์อักษร = ไม่ deploy**
3. แจ้งลูกค้าล่วงหน้า **อย่างน้อย 3 วันทำการ** (ตามสัญญา SLA) ด้วยแม่แบบ `NOTICE-maintenance`
   - ระบุวัน เวลา ผลกระทบ (มี downtime ไหม กี่นาที) และช่องทางติดต่อ
   - ใช้ **เบอร์ on-call กลาง** เท่านั้น ห้ามใส่เบอร์มือถือส่วนตัว
4. dry-run migration ทุกตัวบน staging ที่ใช้สำเนาโครงสร้างและขนาดข้อมูลใกล้ production (ข้อมูลปิดบังแล้ว) และจดเวลา · ถ้าเกิน 5 นาที หรือ lock ตารางใหญ่ ต้องแยกรอบหรือทำแบบ online
5. migration ต้องย้อนกลับได้ หรือเป็นแบบ **expand** (เพิ่มอย่างเดียว)
   - ต้องเปลี่ยนผ่าน `prisma migrate` เท่านั้น ห้ามแก้ DB ด้วยมือ
   - ถ้าจะลบหรือเปลี่ยนชื่อคอลัมน์ ต้องแบ่งเป็น 2 รอบปล่อย (expand → contract)
6. ฟีเจอร์ใหม่ที่เสี่ยงต้องอยู่หลัง **feature flag** ปิดไว้ก่อน แล้วค่อยเปิดหลัง deploy ผ่าน
7. cert TLS ของ **ทุกโดเมนที่เกี่ยวข้อง** (รวม subdomain ของ API, proxy และ webhook) ต้องเหลือ **มากกว่า 21 วัน** — ดูบทเรียนด้านล่าง
8. จองคน on-call ไว้ **2 ชั่วโมงหลัง deploy** และ **เช้าวันถัดไป 08:00–10:00**
- เพิ่มเติม: ระบบของลูกค้าธนาคารต้อง deploy บน cloud region ประเทศไทยเท่านั้น

## 2. วัน deploy ก่อนกด (T−30 นาที)

1. เปิด bridge call และโพสต์เริ่มใน `#deploy` (เวอร์ชัน, ลิงก์ release notes, ชื่อคนใน 3 บทบาท)
2. ดู dashboard: error rate, latency, queue · ถ้าระบบป่วยอยู่แล้ว ให้ **เลื่อน**
3. **backup DB** แบบ snapshot ทันทีก่อน deploy → เช็กว่าสถานะเป็น `available` → จดชื่อ snapshot ลงช่อง
4. จด **image tag เวอร์ชันปัจจุบัน** ไว้ใช้ rollback
5. ปิด cron/batch ที่เขียนข้อมูลชนกับ migration (เช่น batch ข้อมูลหรือพยากรณ์ที่รันตอนกลางคืน)

## 3. Deploy

1. เปิดหน้า maintenance ถ้ามี downtime ตามที่แจ้งลูกค้าไว้
2. รัน `prisma migrate deploy` แล้วดูเวลาเทียบกับตอน dry-run · ถ้านานเกิน 2 เท่า ให้หยุดคิดก่อน
3. deploy image แบบ rolling ทีละ instance จน `/readyz` ผ่านทุกตัว
4. ปิดหน้า maintenance

## 4. Smoke test (Verifier ทำให้เสร็จภายใน 15 นาที)

1. login, logout และ refresh token
2. flow หลักของระบบ 1 รอบเต็ม เช่น จองคิว → ยกเลิก หรือ สั่งซื้อ → จ่ายด้วยบัตรทดสอบ
3. webhook ภายนอกเข้ามาได้ (ดูว่า log มี event ใหม่)
4. คิวงานไม่ค้าง, error rate < 1%, latency p95 ไม่แย่กว่าก่อน deploy เกิน 20%
5. เปิด feature flag ทีละตัว แล้วทำข้อ 2 ซ้ำหลังเปิดแต่ละตัว
- ต้องใช้ user ทดสอบหรือข้อมูลสังเคราะห์เท่านั้น ห้ามใช้บัญชีของลูกค้าจริง

## 5. Rollback

**ต้อง rollback ทันทีถ้า** เจออย่างใดอย่างหนึ่ง:
- smoke test ข้อไหนไม่ผ่าน และแก้ไม่ได้ใน 15 นาที
- error rate > 5% ต่อเนื่อง 5 นาที
- **ข้อมูลผิดแม้แค่รายการเดียว** (เช่น ยอดเงินเพี้ยน)

ทำตามลำดับ:
1. ปิด feature flag ที่เพิ่งเปิด (เร็วที่สุด ให้ลองวิธีนี้ก่อน)
2. deploy image tag เดิมที่จดไว้
3. ถ้า migration ทำให้โค้ดเก่าใช้ไม่ได้ → restore snapshot · **deploy lead และหัวหน้าทีม dev ต้องตกลงร่วมกันก่อน** เพราะข้อมูลหลังเวลา snapshot จะหาย
4. Comms แจ้งลูกค้า **ภายใน 30 นาที** ว่าย้อนกลับแล้ว และผลกระทบคืออะไร

## 6. หลัง deploy

1. Comms แจ้งลูกค้าว่าเสร็จแล้ว พร้อมสิ่งที่เปลี่ยน เขียนเป็นภาษาผู้ใช้ ไม่ใช้เลข ticket
2. เปิด cron/batch ที่ปิดไว้ในหมวด 2 ข้อ 5 คืน
3. on-call เฝ้าระบบ 2 ชั่วโมงหลัง deploy และเช้าวันถัดไป · ถ้าเกิดเหตุ ต้องเขียน postmortem ภายใน 3 วันทำการ
4. ปิด ticket, tag release ใน git และอัปเดต CHANGELOG

## บทเรียนจากเหตุจริง (ใช้ประกอบการตัดสิน)

- **Incident 2026-09 (ShopDee payment ล่ม 47 นาที):** cert ของ subdomain `api.pay` ถูก upload มือ (ลูกค้าซื้อ OV cert เอง) จึงไม่ auto-renew และหมดอายุ
  - uptime check ยิงแค่หน้า `www` ไม่มี alert เรื่องวันหมดอายุ cert · reminder อยู่ในปฏิทินส่วนตัวของคนที่ลาออกไปแล้ว
  - webhook ของ gateway ผ่านโดเมนเดียวกัน จึงพังตามไปด้วย และต้อง reconcile ทีหลัง
  - → ต้องเช็ก cert **ทุก subdomain** โดยเฉพาะตัวที่ upload มือ · หลังเหตุนี้พบ cert ที่ upload มือ 4 ตัว ให้เช็กจากรายการกลาง ไม่ใช่จากความจำของใคร
- **เขตเวลา:** ถ้า runner หรือ server ใช้ UTC แต่เครื่อง dev ใช้ Asia/Bangkok บั๊กเรื่องเวลาอาจหลุดจาก dev ไปได้ · ระบบที่มีช่วงเวลา (นัดหมาย, slot, ตัดรอบ) ต้อง smoke test ช่วงท้ายวันด้วย
- **Payment:** webhook ต้องมี idempotency (`event_id` UNIQUE) เพื่อให้ gateway retry ได้โดยไม่ทำรายการซ้ำ · สถานะ order ไปได้ทางเดียว `pending → paid → refunded`
