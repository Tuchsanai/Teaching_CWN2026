# บริบทโปรเจกต์พยากรณ์คิวสาขา (สรุปจาก company-kit ณ 3 พ.ย. 2026)

> ต้นทาง: `company-kit/deal-001/tor-bank-queue.md` (TOR ข้อ 3.3), `company-kit/ml-queue-forecast/notes.md` + `experiment-results.csv`, `company-kit/onboarding-notes.md` · ข้อมูลสมมติ

## เกณฑ์จาก TOR ธนาคารนครหลวงพัฒนา (deal-001, ข้อ 3.3)
- พยากรณ์ **จำนวนลูกค้าต่อสาขาต่อชั่วโมง ล่วงหน้า 7 วัน** อัปเดตทุกคืน (โครงการมี 120 สาขา)
- **MAPE ภาพรวมไม่เกิน 20%** ทดสอบกับ **ข้อมูล 3 เดือนล่าสุด**
- ต้องคำนึงถึงวันหยุดนักขัตฤกษ์, วันเงินเดือนออก, วันหยุดยาว
- ธนาคารจะส่งข้อมูลบัตรคิวย้อนหลัง 24 เดือน (ไม่ระบุตัวตน) หลังเซ็นสัญญา
- ต้องติดตามความแม่นยำหลังใช้งานจริงได้ และถอยกลับไปรุ่นเดิมได้

## ข้อมูลต้นแบบตอนนี้
- บัตรคิวรายชั่วโมงจากแอปนัดหมาย **ธนาคารออมทรัพย์เกษตรไทย** (40 สาขานำร่อง, ไม่ระบุตัวตน, ใช้ได้ตามสัญญา MA) — ยังไม่ใช่ข้อมูลนครหลวงฯ
- target ช่วง 08:30–15:30 · เฉลี่ยประมาณ 15 คน/ชม. สาขาใหญ่พีค 60+
- qdata-v3 = 40 สาขา · **qdata-v4** = เพิ่มตารางวันหยุด, ลบแถวซ้ำจากตู้คิว ~1.2%, ตัดสาขา 017/033 (ปิดปรับปรุง ส.ค.–ก.ย.) → 38 สาขา
- split ที่ใช้: train 2025-09-01..2026-06-30 · test 2026-07-01..2026-09-30

## ปัญหาที่รู้แล้ว (ต้องมี metric แยก)
- **พยากรณ์ต่ำกว่าจริงช่วง 11:00–13:00 ประมาณ −20 ถึง −30%** ในสาขาย่านออฟฟิศ → อันตรายกว่าพยากรณ์เกิน
- สาขาเปิดใหม่ (< 8 สัปดาห์) ไม่มี lag → fallback ค่าเฉลี่ยสาขาขนาดเดียวกัน
- ยังไม่มี monitoring ของข้อมูลที่เข้าทุกคืน · ยังไม่มี run ไหนลง MLflow
- งานวันแรกของคนใหม่ทีม ML (onboarding) = "รันการทดลอง r03 ซ้ำให้ได้ผลเดิม"

## ข้อเสนอที่ส่งต่อให้ model-release (ยังไม่ตัดสิน)
- ปล่อย r03 แทน v1 ที่เกษตรไทยก่อน แล้วใช้เป็นจุดเริ่มต้นของนครหลวงฯ
- เกณฑ์ rollback ที่เสนอ: MAPE รายสัปดาห์ > 22% สองสัปดาห์ติดกัน หรือ under-forecast ช่วงเที่ยงเกิน 30% · shadow mode 1–2 สัปดาห์
