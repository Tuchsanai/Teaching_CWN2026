# เขียน PRD (prd-writer)

ผลลัพธ์: `work/<YYYY-MM>-feature-priority-<product>.md` (ถ้าถูกถามเรื่องลำดับ) + `work/prd-<product>-<feature>.md`
ความรู้บริษัทที่ต้องใช้สรุปไว้ใน `references/` แล้ว — ใช้ได้แม้เครื่องไม่มี `company-kit/` (ถ้ามี ให้เทียบตัวเลขกับต้นฉบับที่ใหม่กว่า)

## ขั้นตอน

1. **หา input** — feedback/ticket/ตัวเลขที่ผู้ใช้ให้ ถ้าไม่ให้ ลองหา `company-kit/product/novaqueue-feedback-*.md` และโน้ตใน `notes/` · ไม่มีข้อมูลเลย → ถาม อย่าแต่งตัวเลข
2. **จัดกลุ่ม + ให้คะแนน** ตาม `references/prioritization.md` (รวม feedback ที่เป็นปัญหาเดียวกัน, ตรวจ "ประตู" 🚫/🏦 ก่อนคิดคะแนน) → เขียนไฟล์ลำดับ ถ้าผู้ใช้สั่งแค่ PRD ฟีเจอร์เดียว ให้ใส่ตารางหลักฐานใน PRD แทน
3. **เขียน PRD** ตาม `references/prd-template.md` ให้ครบ 5 ข้อบังคับใน `references/prd-rules.md`
   - ทุกตัวเลขบอกที่มา, ตัวเลขที่คำนวณเองแสดงสูตร (เช่น 238,100 × ฿0.35)
   - เป้าตัวชี้วัดที่ยังไม่มีข้อมูลรองรับ เขียนว่า "ข้อเสนอ" และใส่ในคำถามเปิด
   - AC เขียนแบบ Given/When/Then มีเลข `AC-xx.y` และค่าที่วัดได้ (เวลา, จำนวน, ขนาด) — QA ต้องเขียน test ได้โดยไม่ต้องถามกลับ
   - NFR ให้สอดคล้อง `references/novaqueue-facts.md` หัวข้อสถาปัตยกรรม (คิว, ชื่อ event, region ไทย)
4. **ตรวจ PDPA ก่อนบันทึก** (`references/prd-rules.md` ข้อ PDPA) — ค้นในไฟล์ว่าไม่มีชื่อ/เบอร์/เลขบัญชีของลูกค้าปลายทาง เช่น `grep -nE "0[689][0-9]-?[0-9]{3}-?[0-9]{4}|คุณ[ก-๙]+" work/prd-*.md` · อ้าง ticket ด้วยรหัส feedback (F-xx) แทน
5. **ตรวจเลข** — รวมจำนวนครั้ง/เปอร์เซ็นต์/เงินซ้ำอีกรอบ
6. **สรุปให้ผู้ใช้**: ไฟล์ที่ได้, ลำดับที่เสนอ, คำถามเปิดที่ต้องตัดสินเอง และใครทำต่อ (`next`)

## กติกาที่ห้ามข้าม

- ฟีเจอร์ใหม่ทำบน **v2 เท่านั้น** · ลูกค้า v1 ขอ → เสนอย้ายตามข้อเสนอมาตรฐาน
- feedback ที่ขัดหลักความเป็นธรรมของธนาคาร (เช่น VIP ข้ามคิว) → ใส่ "ไม่ทำ" + รอ MD (`md-somchai`) ห้ามรับเอง
- ราคา/ต้นทุนบริการภายนอก (เช่น LINE OA) ใส่จาก price list ได้ แต่ทำเครื่องหมาย ⚠️ ให้ `fin-joy` ยืนยันก่อนใช้ขาย
- ข้อความยินยอม/การเก็บข้อมูลส่วนบุคคลใหม่ → ส่ง `plat-may` (`customer-data-policy`) รีวิว
- ไม่ส่ง PRD ออกนอกบริษัทเอง และไม่ commit เว้นแต่ผู้ใช้สั่ง
