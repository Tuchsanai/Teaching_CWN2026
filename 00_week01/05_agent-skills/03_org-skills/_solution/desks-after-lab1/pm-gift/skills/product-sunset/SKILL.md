# แผนเลิกให้บริการ (product-sunset)

เปลี่ยน "รายชื่อลูกค้าที่ยังใช้ของเก่า" เป็น **แผนปิดบริการที่ผ่านนโยบายทุกข้อ** + **ร่างประกาศถึงลูกค้า**
กติกาทั้งหมดสรุปไว้ใน `references/` แล้ว ใช้ได้แม้เครื่องนั้นไม่มี `company-kit`

## ข้อห้าม (เช็กก่อนทำทุกครั้ง)

1. แผนและประกาศเป็น **ร่าง** จนกว่า MD อนุมัติ ห้ามส่ง ห้ามบอกวันปิดกับลูกค้ารายใดก่อนอนุมัติ
2. ห้ามเขียนว่า "ลบข้อมูลแล้ว" จนกว่า DevOps (`ops-art`) ยืนยันว่าลบครบทั้ง backup และ log
3. ห้ามใส่เบอร์มือถือส่วนตัว เลขบัตร เลขบัญชี หรือชื่อลูกค้าปลายทางในเอกสาร (ดู `references/pdpa-for-sunset.md`)
4. ห้ามแต่งตัวเลขที่ไม่มีในข้อมูล (เช่น ราคาเวอร์ชันใหม่) ให้เขียนว่า "ต้องขอจาก ..." แทน

## ขั้นตอน

### 1 · หาข้อมูลลูกค้า
- หาไฟล์ลูกค้าของเวอร์ชันที่จะปิด เช่น `company-kit/product/<product>-<version>-customers.csv` และไฟล์ overview ของผลิตภัณฑ์ ถ้าไม่เจอให้ถามผู้ใช้
- คอลัมน์ที่ต้องมี: ชื่อลูกค้า, ประเภท (bank/government/hospital/...), วันหมด MA, ค่า MA ต่อปี, การใช้งาน 30 วัน, สนใจเวอร์ชันใหม่, หมายเหตุ ขาดคอลัมน์ไหนให้จดเป็นช่องว่างที่ต้องถาม
- ถ้าคำถามคือ "ลูกค้ายังใช้ v1 อยู่กี่ราย" → ตอบจำนวนราย + ใช้งานจริงกี่ราย (มีคิว/ธุรกรรมใน 30 วัน) + สาขาใช้จริง/ทั้งหมด แล้วหยุดถ้าผู้ใช้ไม่ได้ขอแผน

### 2 · คำนวณตัวเลขตัดสิน (ดูสูตรใน `references/sunset-rules.md`)
- ค่า MA ที่จะหายรวม และมีลูกค้าธนาคาร/สถาบันการเงินไหม → ต้องให้ MD อนุมัติหรือไม่
- **วันปิดที่แนะนำ** = วันหมด MA ช้าที่สุดของลูกค้าที่ยังไม่ยืนยันย้าย (ไม่ต้องขอหนังสือยินยอม) และต้อง ≥ วันประกาศ + 180 วัน
- วันประกาศ = วันอนุมัติที่คาด + เวลาเตรียมประมาณ 1–2 สัปดาห์
- วันเปิดส่งออกข้อมูล (≤ วันปิด − 90 วัน), วันสุดท้ายค่าย้ายฟรี (วันประกาศ + 90 วัน), วันลบข้อมูลเสร็จ (วันปิด + 30 วัน)
- นับวันทีละเดือนให้ถูก แล้วเขียนจำนวนวันจริงในตารางตรวจ
- **หาลูกค้าที่ MA หมดก่อนวันปิด** → เป็นเรื่องที่ต้องตัดสินใจเสมอ (ต่อ MA ตามสัดส่วน / ดูแลฟรี / ขอหนังสือยินยอมปิดก่อน) คิดเงินตามสัดส่วนให้ด้วย

### 3 · เขียนแผนภายใน → `work/<product>-<version>-sunset-plan.md`
ใช้โครงจาก `references/plan-template.md` (สรุป → เหตุผล → ตารางลูกค้า → ตรวจกับนโยบาย → ไทม์ไลน์ → เรื่องให้ MD ตัดสิน → PDPA → รายได้ → งานต่อ)
- ทุกแถวในตารางตรวจกับนโยบายต้องมี ✅/⚠️ และเหตุผล
- ความเสี่ยงรายลูกค้าที่ต้องจับเสมอ: ธนาคาร (DPA), ราชการ (จัดซื้อใหม่ใช้เวลานาน อาจไม่ทันหน้าต่างค่าย้ายฟรี), ข้อมูลอ่อนไหว (สุขภาพ ฯลฯ), ติดต่อไม่ได้ (ส่งหนังสือลงทะเบียนตอบรับ), ใช้งานน้อยจนอาจไม่ต่อ
- ในเรื่องที่ขอให้ MD ตัดสิน ให้มีทางเลือก + ข้อเสนอของ PM ทุกข้อ

### 4 · ร่างประกาศถึงลูกค้า → `work/<product>-<version>-eol-notice-draft.md`
ใช้ `references/notice-template.md` (น้ำเสียงและรูปแบบตามแบรนด์) ทำฉบับเดียวมีย่อหน้า `[เฉพาะ ...]` สำหรับลูกค้าที่มีเงื่อนไขพิเศษ ใส่หมายเหตุหัวไฟล์ว่าห้ามส่งก่อนอนุมัติ

### 5 · ตรวจก่อนส่งงาน
- [ ] วันปิด − วันประกาศ ≥ 180 วัน · ส่งออกข้อมูลเปิด ≥ 90 วันก่อนปิด · ลบข้อมูลภายใน 30 วันหลังปิด
- [ ] ไม่มีลูกค้าที่ยังไม่ย้ายถูกปิดก่อน MA หมด (หรือมีทางเลือกให้ MD แล้ว)
- [ ] ระบุชัดว่าต้องให้ MD อนุมัติหรือไม่ และเพราะเกณฑ์ข้อไหน
- [ ] ไม่มีข้อมูลส่วนบุคคลต้องห้าม ไม่มีตัวเลขที่แต่งเอง ข้อเสนอในประกาศไม่เกินข้อเสนอมาตรฐาน
- [ ] สรุปให้ผู้ใช้: ไฟล์ที่ได้ ตัวเลขสำคัญ และเรื่องที่ต้องตัดสินใจ
