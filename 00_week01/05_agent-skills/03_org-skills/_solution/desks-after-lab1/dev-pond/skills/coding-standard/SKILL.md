# coding-standard — รีวิวโค้ดตามกติกาทีม 10 ข้อ

ทำเรื่องเดียว: เอาโค้ดเทียบกับ `references/coding-rules.md` แล้วให้คะแนน + บอกวิธีแก้แบบที่ทีมใช้
(ไม่ขึ้นโปรเจกต์ใหม่ → `project-scaffold` · ไม่เขียนแผนทดสอบ → `test-from-plan`)

## ขั้นตอน

1. **หาขอบเขต** — PR/diff/ไฟล์ที่ผู้ใช้ให้มา ถ้าไม่ระบุ ใช้ `git diff` ของ branch ปัจจุบัน · ดู `.gitignore`, `.env*`, `prisma/migrations/`, `__tests__/`, `tests/e2e/` ด้วยเสมอ (ข้อ 5–7 ตัดสินจากไฟล์ที่ "ไม่มี" ได้)
2. **อ่าน `references/coding-rules.md`** แล้วไล่ทีละข้อ 1→10 · ข้อละ 1 คะแนน ผ่าน/ไม่ผ่านเท่านั้น (ไม่มีครึ่งคะแนน) · ทุก ❌ ต้องชี้ `ไฟล์:บรรทัด`
3. **เช็กจุดเสี่ยงที่ทีมเคยเจ็บ** ใน `references/known-incidents.md` (token หลุดกลางจ่ายเงิน, webhook ซ้ำ) — ถ้าโค้ดแตะ auth/payment ต้องเช็กทุกบรรทัดในนั้น
4. **ข้อมูลส่วนบุคคลใน log/response** — เลขบัตร ปชช., เบอร์มือถือเต็ม, เลขบัญชี, token, รหัสผ่าน = ❌ ข้อ 8 (ถ้ามี skill `customer-data-policy` ให้ใช้วิธี mask ตามนั้น)
5. **เขียนผล** ตาม `references/review-format.md`: กล่องคะแนน → ตารางรายจุดเรียงตามความเสี่ยง (security/เงิน ก่อน สไตล์ทีหลัง) → ข้อความตอบ PR สั้น ๆ ที่ copy ได้
6. ถ้าผู้ใช้ขอ "เขียนให้ตรงสไตล์ทีม" → แก้โค้ดตามตารางเลย แล้วรีวิวซ้ำจนได้ ≥ 8 พร้อมบอกข้อที่ยังทำไม่ได้เอง (เช่น หมุน secret ที่หลุด, รัน migrate)

## กติกาการตัดสิน

- ≥ 8 = ✅ merge ได้ · < 8 = ❌ ห้าม merge — ไม่ปัดขึ้น ไม่ "ผ่านแบบมีเงื่อนไข"
- secret หลุดใน commit/PR = แนะนำ **หมุน secret** เสมอ แม้ลบออกแล้ว
- PR ฟีเจอร์ที่ไม่มี test เลย: ให้คะแนนได้ แต่ระบุว่า "ไม่รีวิวต่อจนกว่าจะมี test" (ข้อ 6)
- ไม่แน่ใจว่าผ่านไหม (เช่น coverage ไม่มีรายงาน) → ใส่ ❓ แทน ✅/❌ แล้วบอกว่าต้องดูอะไรเพิ่ม และไม่นับคะแนนข้อนั้น
- ต่อท้ายผลด้วย: ถ้า merge ได้ → ส่งต่อ QA (`test-from-plan`)
