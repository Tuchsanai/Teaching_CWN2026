# การตัดสินใจที่ใช้เป็นค่าเริ่มต้น (จากรอบแรก deal-001 นครหลวงพัฒนา, 3 พ.ย. 2026)

บอกผู้ใช้ในสรุปทุกครั้งว่าใช้ข้อไหน · ผู้ใช้สั่งต่างได้

1. **SPEC + TEST-PLAN แยก 2 ไฟล์** — TEST-PLAN ส่งให้ QA ตรงได้โดยไม่ต้องตัด
2. **requirement ที่ TOR ไม่เขียน ใส่ใน SPEC ระดับ S พร้อม Q-NN** แทนที่จะรอคำตอบ — เพราะต้องยื่นข้อเสนอก่อนได้คำตอบ · ทุกค่าที่เดาต้องมีป้ายสมมติฐาน
3. **ใส่ค่าตัวเลขเริ่มต้นเอง** เมื่อ TOR ไม่บอก (เช่น จองล่วงหน้า 14 วัน, OTP 5 นาที, ล็อก 15 นาทีหลังผิด 5 ครั้ง, RPO 15 นาที/RTO 4 ชม.) เพื่อให้ test มีตัวเลขตรวจได้ — แก้ตามคำตอบลูกค้า
4. **ผู้ประสานงานลูกค้า: ใส่ชื่อ + อีเมลบริษัท ไม่ใส่เบอร์มือถือ** แม้ TOR จะมีเบอร์ (policy ข้อ 2)
5. **สถาปัตยกรรมแค่เบื้องต้น** (service/โมดูล + Mermaid 1 ภาพ + เหตุผลแยก service) — รายละเอียด C4 ให้ `arch-template`
6. **URL ของ TEST-PLAN เป็น placeholder** `https://<project>-uat.example` เพราะระบบยังไม่มี · QA ต้องแก้ก่อนรัน
7. **requirement ที่ทดสอบผ่านเว็บไม่ได้** (pen test ภายนอก, pilot, รายงาน MA, code review) ไม่ฝืนเขียนเป็น test case → ใส่หัวข้อ "ตรวจด้วยวิธีอื่น"
8. รอบแรก `check-spec.mjs` พบ requirement ไม่มี test 20 ข้อ → เพิ่ม test 5 ข้อ + ย้าย 12 ข้อเข้าหัวข้อตรวจด้วยวิธีอื่น + เติมรหัสอ้างอิงใน test เดิม 3 ข้อ → **รันสคริปต์ก่อนส่งเสมอ**
9. เกณฑ์ผ่านเขียน "อัตราผ่านรวม ≥ 95%" ก่อน "P1 ผ่านทั้งหมด" — รอบแรกเขียน "P1 ผ่าน 100%" ก่อน แล้ว parse-plan ของ QA อ่านเป็นเกณฑ์ 100%
