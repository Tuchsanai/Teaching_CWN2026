## คำตอบสั้น

**รับได้ แต่มีเงื่อนไข (GO with conditions)** — ทีมทำได้ทางเทคนิค เพราะ stack, booking, LINE และคิวงานเป็นสิ่งที่ทีมเคยทำแล้ว แต่มี **3 เรื่องที่ถ้าไม่จัดการจะพังซ้ำแบบที่เคยพัง**

## รายละเอียดและหลักฐาน

### 1. คน / ความจุทีม 🔴
- ทีมตาม JD NVT-JOB-2026-021: Dev 4 + QA 1 + DevOps 1 + ML 1 (หัวหน้า `dev-pond`) — **1 ใน 4 Dev ยังเป็นตำแหน่งว่าง** และต้องเริ่มงานไม่เกิน 4 ม.ค. 2027 ซึ่งเหลือประมาณ 8 สัปดาห์ รวมช่วงปีใหม่ด้วย
- `monthly-kpi.csv` ต.ค.: ตำแหน่งว่าง 6 (เพิ่ม Senior Full-stack + **ML Engineer**), โปรเจกต์ on-time 7/10, gross margin 27.1% (เป้า 30%) เพราะ DentDee เกินแผน 18 man-day → **การประเมิน effort ของเราเพี้ยนมาแล้ว**
- ML: โมเดลพยากรณ์ทำโดย "ต้า" ซึ่งเป็น DS สัญญาจ้าง ตอนนี้อยู่ใน notebook บนเครื่องเขาคนเดียว ถ้าเขาไม่อยู่ ความรู้ก็หายไปด้วย (แบบเดียวกับ reminder ต่อ cert ที่หายไปพร้อมบัญชีของ dev ที่ลาออก)
- **คำถามเรื่องความจุ: ทีมรับงานนี้ไหวไหม** → ไหว **ถ้า** ได้ Senior ภายในกำหนด และปลดคน 7 คนนี้จากโปรเจกต์อื่นได้จริง ถ้าไม่ได้ Senior ภายใน 4 ม.ค. ต้องให้ `dev-pond` ถือ booking engine เอง แล้วงาน review ของทั้งทีมจะช้าลง

### 2. ML พยากรณ์ 🔴
- ผลที่มีเป็นข้อมูลของ **เกษตรไทย 38–40 สาขา** ไม่ใช่นครหลวงฯ 120 สาขา ข้อมูลจริง 24 เดือนจะได้ **หลังเซ็นสัญญา**
- r03 MAPE 15.2% (ผ่านเกณฑ์ ≤20%) แต่ **เปลี่ยนข้อมูลเป็น qdata-v4 พร้อมกับเพิ่ม feature** (ตัดซ้ำ 1.2%, ตัด 2 สาขาที่ปิดปรับปรุง) จึงยังบอกไม่ได้ว่าดีขึ้นเพราะ feature หรือเพราะข้อมูลสะอาดขึ้น — r02 ซึ่งเป็นรุ่นที่ผ่านเกณฑ์แบบเฉียด ๆ (19.8%) ก็ยังไม่ได้รันบน v4
- ไม่ได้ fix seed, ไม่ได้จดผล tune รายตัว, ยังไม่ลง MLflow
- พยากรณ์ **ต่ำกว่าจริง 20–30% ช่วง 11:00–13:00** ในสาขาย่านออฟฟิศ ซึ่งทำให้สาขาจัดคนไม่พอ (เสียหายกว่าพยากรณ์เกิน)
- TOR ข้อ 3.3 บังคับให้ "ติดตามความแม่นยำ + ถอยกลับรุ่นเดิมได้" แต่ตอนนี้ **ยังไม่มีทั้งสองอย่าง**
- สาขาเปิดใหม่ (< 8 สัปดาห์) ยังไม่มี lag → ต้องใช้ fallback
- ✅ จุดแข็ง: มี baseline (r01) ให้ถอยกลับได้ และมีข้อมูลต้นแบบที่ใกล้เคียงงานจริง

### 3. Core banking Customer Lookup API (REST + mTLS) 🟠
- ตามมาตรฐานต้องแยกเป็น `core-connector` service (arch-standards ข้อ 2.4) แยกเครือข่าย
- **client cert ของ mTLS มักออกโดยธนาคาร → ต่ออายุอัตโนมัติไม่ได้ ต้อง upload ด้วยมือ** ซึ่งเป็นรูปแบบเดียวกับ cert `api.pay` ของ ShopDee ที่หมดอายุแล้วไม่มี alert จนระบบล่ม 47 นาที
- ⚠️ เรื่องเดียวกันยังค้างอยู่: cert มือของ BaanRai หมดอายุ **2026-11-02** และในเธรดยังไม่มีใครยืนยันว่าต่อแล้ว (ดู "เรื่องด่วนนอกดีล")
- ระบบจองคิวขึ้นกับ API ของธนาคาร ถ้า API ช้าหรือล่ม ลูกค้าเดิมจะยืนยันตัวตนไม่ได้ → ต้องมี timeout, circuit breaker และ fallback ให้จองแบบ walk-in หรือ guest

### 4. Booking engine 🟠
- **บั๊กที่เปิดอยู่** (CI #1873, repo `kaset-appointment-web` release/2026.11): runner ตั้ง TZ=UTC ทำให้จองช่วง 15:00 เวลาไทยถูกตีความเป็น 22:00 → ระบบตอบ 409 "เต็ม" ทั้งที่หน้าจอบอกว่ายังว่าง เกิดหลัง commit "move slot time handling to date-fns-tz" ส่วนเครื่องที่ตั้ง TZ Bangkok จองผ่านปกติ → **บั๊กแบบนี้หลุดผ่านการทดสอบบนเครื่อง dev ได้**
- 120 สาขา × ช่วง 15 นาที × 5 ประเภทบริการ และพีควันที่ 25–5 → ต้องใช้ slot lock ด้วย Redis (TTL), ทำ load test ที่ระดับพีค และกันจองซ้ำ
- walk-in จากตู้ Q-Matic กับคิวที่จองไว้ต้องอยู่ในคิวเดียวกัน → มีเรื่องลำดับคิวและ race condition

### 5. ความปลอดภัย / compliance 🟠
- ข้อกำหนด: TLS 1.2+, AES-256 at rest, **เลขบัตรประชาชนห้ามเก็บเป็นข้อความธรรมดา** (เก็บ hash ไว้ค้นหา + เข้ารหัสระดับคอลัมน์), audit log 2 ปี, NDA ทุกคน, ปฏิบัติตามกติกา ธปท. และ PDPA
- **pen test โดยผู้ทดสอบที่ธนาคารกำหนด ก่อนเปิดใช้จริง** → เราคุมคิวผู้ทดสอบเองไม่ได้ และถ้าเจอปัญหาต้องเผื่อเวลาแก้ด้วย จึงต้องล็อกวันไว้ราวเดือน 4
- log ต้อง redact เลขบัตรและเบอร์โทร (coding-rules ข้อ 8)
- ✅ ทีมมีแบบแผน token 15 นาที + rotate และ audit module อยู่แล้ว (project-scaffold-notes)

### 6. Integration อื่น 🟡
- **LINE OA / LIFF**: ทีมเคยส่ง LINE ผ่าน BullMQ แล้ว แต่ LIFF + การยืนยันตัวตน (บัตร + วันเกิด + OTP) ใน LIFF ยังเป็นเรื่องใหม่
- **Q-Matic รุ่นเดิม (REST)**: ยังไม่เห็นเอกสาร API และ sandbox → เสี่ยงที่สุดในกลุ่มนี้ เพราะเป็นของบุคคลที่สามที่เราควบคุมไม่ได้
- **Entra ID SSO**: เป็นมาตรฐาน OIDC ความเสี่ยงต่ำ แต่ต้องได้สิทธิ์ลงทะเบียน app จาก IT ธนาคาร (มักใช้เวลานาน)

### 7. Timeline / หน้าต่าง deploy 🟠
- ถ้าเซ็น 4 ม.ค. 2027 → เดือน 5 = 4 พ.ค.–3 มิ.ย. (นำร่อง 10 สาขา), เดือน 6 = 4 มิ.ค.–3 ก.ค. (ขยายครบ 120 สาขา)
- deploy-runbook: **ห้าม deploy วันที่ 25–สิ้นเดือนสำหรับลูกค้าธนาคาร** และห้ามวันศุกร์หรือก่อนวันหยุดยาว → แต่ละเดือนเหลือหน้าต่าง deploy ราววันที่ 2–24 และวันอังคาร–พฤหัสเท่านั้น
- เมษายน (เดือน 4) มีสงกรานต์ ถ้า pen test ตกช่วงนั้นเวลาแก้จะหายไป
- ML: ข้อมูลเข้าเดือน 1 → เทรนเดือน 2–3 → shadow mode เดือน 4 → นำร่องเดือน 5 **แผนนี้ไม่มีเวลาเผื่อเลย**

### 8. Ops / SLA หลังขึ้นระบบ 🟠
- SLA uptime 99.5% (หยุดได้ประมาณ 3.6 ชม./เดือน) และ Sev1 ต้องตอบใน 30 นาที → ต้องมี on-call 24×7 (สอดคล้องกับ MA-PREM)
- incident ก.ย.: **ลูกค้ารู้ก่อนเรา 9 นาที** เพราะ uptime check ยิงไปแค่หน้าแรก → งานนี้ต้องมี synthetic check ที่จองคิวทดสอบทุก 5 นาที และ alert cert < 21 วันครบทุกโดเมนรวม core-connector
- DevOps มี 2 คน (`ops-art`, `ops-fon`) ดูแล 10 โปรเจกต์ที่ทำอยู่
