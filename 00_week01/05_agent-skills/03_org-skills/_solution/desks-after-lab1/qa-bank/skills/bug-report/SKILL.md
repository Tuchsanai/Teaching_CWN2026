# เขียนรายงานบั๊ก (bug-report)

เป้าหมายเดียว: **Dev อ่านรายงานนี้อย่างเดียวแล้วทำซ้ำบั๊กได้** · หนึ่งรายงาน = หนึ่งบั๊ก (หลาย test ล้มด้วยสาเหตุเดียวกัน = รายงานเดียว, อาการต่างกัน = แยกใบ)

## ขั้นตอน

1. **รวบรวมข้อมูลดิบ** — log ของ test ที่ล้ม, trace/network, server log (requestId), โน้ตทดสอบมือ, ข้อมูล release/deadline · ถ้าไม่มีอะไรเลยให้ถามผู้ใช้ก่อน อย่าเดา
2. **ดึงข้อเท็จจริงให้ครบ** ก่อนเขียน
   - repo · branch · commit · environment · URL · browser · **timezone** (ของ runner/เครื่อง/server ถ้าเกี่ยว)
   - ค่าที่ใช้จริงทุกขั้น: user ทดสอบ, สาขา/รหัส, วันที่, เวลา, ปุ่ม/ช่องที่กด (เอาจากโค้ด test ทีละบรรทัด)
   - expected vs received จาก assertion + HTTP status/body ที่เกี่ยว
   - เคสที่ **ผ่าน** เทียบกับเคสที่ **ล้ม** (ช่วงเวลา, สาขา, เครื่อง, env) → ใช้ใน "ไม่เกิดเมื่อ"
3. **ตัดสินว่าเว็บผิดหรือ test ผิด** — ถ้า test ผิด (selector เปลี่ยน, ข้อมูลทดสอบหมด) ไม่ต้องเขียนบั๊ก แจ้งผู้ใช้แทน ห้ามแก้ test ให้ผ่านเฉย ๆ
4. **เขียนตามแม่แบบ** ใน [references/bug-template.md](references/bug-template.md) ครบทุกหัวข้อ เรียงตามแม่แบบ
   - ชื่อ `[BUG] <สิ่งที่พัง> เมื่อ <เงื่อนไข>` ≤ 80 ตัวอักษร
   - Severity ใช้ตารางเกณฑ์ในแม่แบบ · Priority ดูจาก deadline release
   - ขั้นตอนเป็นเลขข้อ ใส่ค่าจริง + คำสั่งรัน test อัตโนมัติถ้ามี
   - ถ้าเกี่ยวกับเวลา ให้เขียนค่าที่ควรเป็นทั้งเวลาท้องถิ่นและ UTC (เช่น 15:00 ไทย = 08:00Z)
   - "ข้อสังเกตของ QA" = ข้อเท็จจริงที่ชี้ทาง (ความต่างผ่าน/ไม่ผ่าน, commit น่าสงสัย) **ไม่ฟันธงต้นเหตุ** และบอกสิ่งที่ยังไม่ได้เก็บ
5. **ตรวจข้อมูลส่วนบุคคล** ตาม [references/data-policy.md](references/data-policy.md) — ทั้งข้อความ request/response/log และภาพที่แนบ
6. **บันทึก** ที่ `work/BUG-<YYYY-MM-DD>-<slug>.md` (วันที่ = วันที่พบ) แล้วรายงานผู้ใช้สั้น ๆ: ชื่อบั๊ก, Sev/P, จุดที่ตัดสินเอง/ข้อมูลที่ขาด

## เช็กลิสต์ก่อนส่ง
- [ ] คนที่ไม่เคยเห็น test นี้ทำตามขั้นตอนแล้วเจอบั๊กได้ (ไม่มีคำว่า "เลือกสาขาใดก็ได้" / "ประมาณ")
- [ ] มีทั้งผลที่คาดและผลจริง เป็นข้อความ/สถานะที่ตรวจได้
- [ ] มีความถี่ x/y และเงื่อนไขที่ "ไม่เกิด"
- [ ] หลักฐานมี path + requestId
- [ ] ไม่มีเลขบัตร/เบอร์มือถือ/เลขบัญชี/ชื่อลูกค้าปลายทาง
