# บริบทโมเดลพยากรณ์คิวสาขา (ตัวที่ปล่อยบ่อยที่สุด)

> สรุปจาก `company-kit/ml-queue-forecast/` (notes ของ DS + experiment-results.csv) และ TOR deal-001 · ณ 3 พ.ย. 2026 · ถ้ามีรอบทดลองใหม่ ให้ยึดข้อมูลใน MLflow แทน

## งาน
- target = จำนวนลูกค้าต่อสาขาต่อชั่วโมง 08:30–15:30 · เฉลี่ย ~15 คน/ชม. สาขาใหญ่พีค 60+
- ข้อมูล: บัตรคิวรายชั่วโมง ธนาคาร**ออมทรัพย์เกษตรไทย** 40 สาขานำร่อง ไม่ระบุตัวตน ใช้ได้ตามสัญญา MA · ข้อมูลใหม่เข้าทุกคืน
- ผู้ใช้: ผู้จัดการสาขาดูผ่าน dashboard เพื่อจัดคน
- เกณฑ์ลูกค้าถัดไป **นครหลวงพัฒนา** (TOR deal-001 ข้อ 3.3): พยากรณ์ล่วงหน้า 7 วัน อัปเดตทุกคืน · **MAPE ≤ 20% ภาพรวม ทดสอบกับข้อมูล 3 เดือนล่าสุด** · SLA uptime ≥ 99.5%
- สถาปัตยกรรม: โมเดล Python แยกเป็น `forecast-service` (มาตรฐาน arch ของบริษัท)

## ปัญหาที่รู้แล้ว (ต้องมีในทุก release plan)
1. พยากรณ์ต่ำกว่าจริง 11:00–13:00 ราว −20 ถึง −30% ในสาขาย่านออฟฟิศ (อันตรายกว่าพยากรณ์เกิน)
2. สาขาเปิดใหม่ < 8 สัปดาห์ไม่มี lag → fallback ค่าเฉลี่ยสาขาขนาดเดียวกัน
3. สาขาที่ปิดแล้วเปิดใหม่ (017, 033) lag ช่วงปิดเป็นศูนย์/ว่าง → ต้องใช้ fallback แบบสาขาใหม่จนมีข้อมูลหลังเปิด ≥ 8 สัปดาห์ (ยังไม่ได้ทดสอบ)
4. ยังไม่มี monitoring drift เลย
5. วันเงินเดือนออก = 25 และวันทำการสุดท้ายของเดือน · ช่วงที่ผู้จัดการสาขาบ่นมากที่สุด
