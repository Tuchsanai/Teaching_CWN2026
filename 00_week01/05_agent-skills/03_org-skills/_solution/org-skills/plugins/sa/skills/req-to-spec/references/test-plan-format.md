# รูปแบบ TEST-PLAN.md (ให้ `test-from-plan` ของ QA อ่านได้)

`test-from-plan` (owner `qa-mint`) อ่านแผนด้วยสคริปต์ `parse-plan.mjs` — ต้องเขียนให้ตรงกติกานี้ ไม่งั้นสคริปต์ QA อ่านผิด

## หัวข้อที่ต้องมี (ระดับ `##`)
1. `## ระบบที่ทดสอบ` — **URL แรกในไฟล์ = baseURL** (ยังไม่มีระบบ ใส่ placeholder เช่น `https://<project>-uat.example` และเขียนว่าใส่จริงเมื่อขึ้น uat) · `GET /healthz` · reset ข้อมูลแบบ `POST /api/test/reset` · ระบบภายนอกใช้ stub/sandbox อะไร
2. `## ระดับ (Priority)` — P1 ต้องผ่านทั้งหมด, P2, P3
3. `## ข้อมูลทดสอบ` — synthetic เท่านั้น ตัวเลขบัตร/เบอร์แสดงแบบปิดบัง (ค่าจริงอยู่ใน fixture ของ uat)
4. `## Test cases` — ตารางเดียว คอลัมน์ตามลำดับนี้:
   `| # | ID | โมดูล | สิ่งที่ทดสอบ | ระดับ | ผลที่คาดหวัง | อ้างอิง |`
   - ID `TC-<MOD>-NN` (ใช้ MOD เดียวกับ FR) · ระดับ `P1`/`P2`/`P3` เท่านั้น
   - "อ้างอิง" = รหัส FR/NFR เขียนย่อได้ `FR-BKG-05, 06` (= 05 และ 06)
   - "ผลที่คาดหวัง" ต้องตรวจได้จากภายนอก (หน้าจอ/HTTP status/ข้อความ/ไฟล์) มีตัวเลขชัด
   - test ที่ใช้ค่าจากสมมติฐาน ใส่ *(สมมติฐาน Q-NN)* ในช่อง "สิ่งที่ทดสอบ"
5. `## Requirement ที่ตรวจด้วยวิธีอื่น (ไม่ใช่ test case)` — `| Requirement | วิธีตรวจ | ใครตรวจ |` สำหรับข้อที่ทดสอบผ่านหน้าเว็บไม่ได้ (pen test ภายนอก, code review, pilot, รายงาน MA)
6. `## เกณฑ์ผ่าน (Exit criteria)` — **บรรทัดแรกต้องขึ้นด้วยอัตราผ่านรวม** เช่น `อัตราผ่านรวม ≥ 95% · P1 ผ่านทั้งหมด · ...`
   (parse-plan ใช้ `%` ตัวแรกในหัวข้อนี้เป็นอัตราผ่าน — ถ้าเขียน "P1 ผ่าน 100%" ก่อน จะได้เกณฑ์ 100% ผิด · คำว่า "P1 ผ่านทั้งหมด" ทำให้สคริปต์รู้ว่า P1 ต้องผ่านครบ)
7. `## ไม่อยู่ในแผนนี้`

## ห้ามใช้ชื่อหัวข้อที่มีคำว่า เฉลย / ผู้สอน / solution / answer / bug mode
parse-plan ข้ามหัวข้อพวกนี้ทั้งหัวข้อ (กติกา black-box ของ QA)

## ตรวจ
- `node <SKILL_DIR>/scripts/check-spec.mjs <โฟลเดอร์>` — ครอบคลุม requirement, รหัสซ้ำ, คอลัมน์, ข้อมูลส่วนบุคคล
- ถ้าเครื่องมี skill `test-from-plan`: `node <test-from-plan>/scripts/parse-plan.mjs --plan <TEST-PLAN.md> --out <scratch>/plan.json` ต้องได้ URL, จำนวน test ตรง และ "เกณฑ์ผ่าน" ตามที่ตั้งใจ
