# เขียน postmortem (postmortem)

เปลี่ยน log ดิบของเหตุขัดข้อง 1 ครั้ง ให้เป็นเอกสารที่ทีมใช้แก้ระบบได้จริง และลูกค้าอ่านแล้วมั่นใจ
**หัวใจคือไม่โทษคน:** ถามว่า "ทำไมระบบปล่อยให้เกิด" ไม่ใช่ "ใครทำ"

## Input
- log/แชต/ticket ของเหตุ (ไฟล์ที่ผู้ใช้ชี้ หรือวางมา) — ถ้าไม่บอก ให้ถามว่าเหตุไหน อย่าเดา
- ถ้ามีโน้ตใน `notes/` ของโต๊ะ ให้อ่านด้วย

## ขั้นตอน
1. **อ่านกติกา** `references/company-rules.md` (Sev/SLA, มาตรฐาน alert, เหตุที่เคยเกิด) + skill `customer-data-policy` (core) และ skill `brand-guide` (core) สำหรับฉบับลูกค้า
2. **เรียงไทม์ไลน์** จาก log ทั้งหมด (แชตมักไม่เรียง) แล้วปักหมุด 6 จุด: เริ่มเหตุ · ตรวจพบ (ใคร/อะไรเจอ: เราหรือลูกค้า) · ตอบรับ · รู้ต้นเหตุ · บรรเทา · ยืนยันปกติ + ข้อมูลถูกต้องครบ — คำนวณนาทีจากจุดเริ่ม
   - ถ้าเวลาเริ่มในแหล่งต่าง ๆ ไม่ตรงกัน (เช่น ของพังจริง vs เวลาที่ log นับ) ให้ใช้ตัวเลขที่ทีมใช้ทางการ แล้ว **ใส่อีกค่าไว้ด้วย** ห้ามเลือกเงียบ
3. **วัดผลกระทบ** เป็นตัวเลข: นาที, จำนวนรายการ/ผู้ใช้, เงิน, สายเข้า, SLA ผ่าน/ไม่ผ่าน, ส่วนที่ *ไม่* กระทบ
4. **หาต้นเหตุ** ด้วย "ทำไม" ทีละชั้นจนถึงระดับกระบวนการ (ดู `references/root-cause-guide.md`) แยก ต้นเหตุหลัก / ปัจจัยเสริม / ทำไมไม่รู้ตัวก่อน
5. **เขียนสิ่งที่ได้ผลดี และสิ่งที่ต้องดีขึ้น** — ถ้าในห้องมีการถามหาคนผิด ให้เปลี่ยนเป็นคำถามเชิงระบบ
6. **Action items** ทุกข้อมี: ประเภท (แก้ทันที / ตรวจพบก่อน / ตรวจพบเร็ว / ตัดต้นเหตุ / ไม่ผูกกับคน / ลดผลกระทบ), เจ้าของเป็นบทบาท, กำหนดเป็นวันที่ (ค.ศ.), สถานะ
   - **ไล่ TODO ที่ค้างใน log ทุกข้อ** เทียบกับวันนี้ ถ้าเลยกำหนดหรือใกล้แล้ว → ขึ้นเป็น A1 และพูดในสรุปบรรทัดแรก ๆ
7. **เขียน 2 ไฟล์** ใน `work/` จาก `references/template-internal.md` และ `references/template-customer.md`
   - `work/postmortem-<YYYY-MM-DD>-<ระบบ>.md` — ภายใน
   - `work/incident-report-<ลูกค้า>-<YYYY-MM-DD>-customer.md` — ถึงลูกค้า
8. **ตรวจก่อนส่ง** (checklist ด้านล่าง) แล้วสรุปให้ผู้ใช้: ต้นเหตุ 1 บรรทัด, A1, จุดที่ตัดสินใจเอง

## Checklist ก่อนส่ง
- [ ] ไม่มีชื่อคนผูกกับความผิด (ใช้บทบาท: Dev, DevOps, Sales, on-call)
- [ ] ฉบับลูกค้า: ไม่มีชื่อลูกค้าอื่น, ไม่มีเบอร์มือถือ/เลขบัตร/เลขบัญชี/ชื่อลูกค้าปลายทาง, ไม่มีรายละเอียดภายใน (ปฏิทินส่วนตัว, ใครลาออก), ไม่มีอีโมจิ, ไม่สัญญาว่า "จะไม่เกิดอีก 100%"
- [ ] ทุกตัวเลขมีที่มาใน log · ตัวเลขที่ไม่ตรงกันระบุทั้งสองค่า
- [ ] action item ทุกข้อมีเจ้าของ + วันที่ · TODO ค้างใน log ถูกหยิบมาครบ
- [ ] เขียน postmortem ภายใน 3 วันทำการหลังเหตุ (ถ้าเลยแล้ว ให้บอกผู้ใช้)

## สิ่งที่ต้องถามผู้ใช้ (อย่าตัดสินแทน)
- เลขที่เอกสาร (ถ้ายังไม่มีลำดับ ใช้ `NVT-PM-<ปี>-<ลำดับ>` และติดคำว่า "ร่าง")
- ชื่อคนเป็นเจ้าของ action item (skill ใส่เป็นบทบาทไว้ก่อน)
- ตัวเลือกที่ต้องให้ลูกค้าตัดสิน — skill เขียนเป็นตัวเลือกพร้อมคำแนะนำ ไม่ตัดสินแทนลูกค้า
