# กติกาเฉพาะประเภทเอกสาร

> รวบรวมจากไฟล์กลางของบริษัท (company-kit) และจากสรุป PDPA ที่แต่ละแผนกเคยคัดลอกไว้ใน skill ของตัวเอง (ยุบรวมมาไว้ที่นี่ที่เดียว 2026-11-03) · ทุกข้อ **เพิ่ม** จาก policy-summary.md ไม่ได้แทนที่

| ประเภท | ไปไหน | กติกาเพิ่ม | ที่มา |
|---|---|---|---|
| **ใบแจ้งหนี้** | ภายนอก | ผู้ติดต่อลูกค้า = ชื่อ + ตำแหน่ง + อีเมลบริษัท **เท่านั้น** (ห้ามเบอร์มือถือ) · ห้ามชื่อ/ข้อมูลลูกค้าปลายทาง · ห้ามรายละเอียดเคสภายในของลูกค้า (ใช้รหัสเคส/ticket) · เลขผู้เสียภาษีนิติบุคคล + บัญชีรับเงินของบริษัท (ธ.สยามรุ่งเรือง 714-2-08835-1) แสดงได้ · ระวังหมายเหตุที่ระบบ auto-fill ดึงมาจาก call center | invoicing-rules v2026.2 ข้อ 4–5 |
| **อีเมลติดตามลูกค้า / proposal / สไลด์** | ภายนอก | ข้อมูลติดต่อจากบันทึกประชุมหรือ TOR **ห้ามคัดลอกเบอร์มือถือ** ลงไป ใช้อีเมลบริษัท · อ้างผลงานลูกค้าเก่าได้แค่ชื่อองค์กร + ตัวเลขผลลัพธ์ ไม่มีข้อมูลลูกค้าปลายทาง | customer-data-policy ข้อ 2 |
| **บันทึกประชุม** | ภายใน | ไม่ผิดข้อห้ามข้อ 2 (ไม่ได้ส่งออก) แต่เบอร์มือถือควรย้ายไป CRM แล้วลบจากโน้ต = 🟡 · ถ้าจะ **ส่งต่อให้ลูกค้า/คนนอก** ให้ตรวจแบบภายนอกทั้งฉบับ (รวมส่วน "ความรู้สึกหลังประชุม (ภายใน)" ที่ต้องตัดทิ้งด้วย) | customer-data-policy ข้อ 2 |
| **TOR จากลูกค้า** | ภายใน (ไดรฟ์ฝ่ายขาย) | เก็บได้ตามที่ลูกค้าส่งมา 5 ปีหลังจบสัญญา · ห้ามคัดลอกเบอร์มือถือผู้ติดต่อใน TOR ไปใส่ proposal/spec | customer-data-policy ข้อ 2, 5 |
| **รายงานบั๊ก / ticket** | ภายใน | ใช้ user ทดสอบ synthetic เท่านั้น (เช่น `qa-user-07`) ห้ามข้อมูลลูกค้าจริง · ห้ามเลขพาสปอร์ต/สัญญาสินเชื่อ/CIF ด้วย · screenshot/video ต้องเบลอและเขียนในรายงานว่าเบลอแล้ว · เจอข้อมูลจริงใน log → mask ในรายงาน + แจ้ง DevOps redact ที่ logger (เขียนใน "ข้อสังเกตของ QA") | qa/bug-template.md, bug-report |
| **log / โค้ด** | ภายใน | ห้าม log รหัสผ่าน, token, เลขบัตรประชาชน, เบอร์โทรเต็ม (ใช้ redact ของ pino) · เลขบัตรประชาชน/เบอร์ในฐานข้อมูลเข้ารหัสระดับคอลัมน์หรือ hash · เจอใน log ให้แจ้ง DevOps | coding-rules ข้อ 8, arch-standards |
| **ประกาศปิดปรับปรุง (NOTICE-maintenance)** | ภายนอก | ห้ามเบอร์มือถือส่วนตัวของใคร ใช้เบอร์ on-call กลาง | deploy-runbook 1.3 |
| **postmortem / รายงาน incident** | ภายใน/ผู้บริหาร (บางครั้งส่งลูกค้า) | log ที่ยกมาต้องไม่มีข้อมูลลูกค้าปลายทาง ถ้าส่งลูกค้าให้ตรวจแบบภายนอก · ฉบับลูกค้า **ห้ามมีชื่อลูกค้ารายอื่น** และรายละเอียดภายในเรื่องพนักงาน · เบอร์ติดต่อใช้ on-call กลาง · ถ้าเหตุมีข้อมูลรั่ว ต้องเขียนในสรุปและแจ้ง `plat-may` | customer-data-policy ข้อ 4, postmortem |
| **สรุปดีล / ข้อมูลโครงการที่มีข้อมูลสุขภาพ** | ภายใน | ระบบที่เก็บข้อมูลสุขภาพ = ข้อมูลอ่อนไหว ม.26 ต้องให้ `plat-may` ดู | DS-2026-034 |
| **ข้อมูลทดสอบ / dataset ML** | ภายใน | synthetic หรือ **ไม่ระบุตัวตน** และมีสิทธิ์ใช้ตามสัญญา (เช่น MA) · ห้ามคัดลอกข้อมูลจริงลงเครื่องตัวเอง ใช้ bucket ของทีม · feature ห้ามดึงข้อมูลส่วนบุคคล (CIF, ระดับลูกค้ารายคน) ถ้าไม่จำเป็น ข้อมูลอ่อนไหวห้ามใช้ · สำเนาข้อมูลลูกค้าปลายทางลบภายใน 90 วันหลังส่งมอบ — ระบุ `data_version` ให้ตามลบได้ | customer-data-policy ข้อ 4–5, mlflow-experiment |
| **รายงานทดลอง ML / ทะเบียน run / release notes โมเดล** | ภายใน (release notes บางครั้งส่งลูกค้า) | อ้างอิงแค่ระดับสาขา-ชั่วโมง / ตัวเลขรวม ไม่ใช่ระดับคน (รวมแถวตัวอย่างที่ทำนายผิด) · ใช้ข้อมูลลูกค้า A เป็นต้นแบบให้ลูกค้า B: ส่ง B ได้แค่วิธีการ/metric รวม **ห้ามส่งข้อมูลดิบของ A** | mlflow-experiment, model-release |
| **proposal (เนื้อหาโซลูชัน)** | ภายนอก | เขียนให้ชัดว่าเลขบัตรประชาชนไม่เก็บแบบข้อความธรรมดา, ข้อมูลเทรนเป็นข้อมูลไม่ระบุตัวตน, ลบสำเนาข้อมูลลูกค้าปลายทางภายใน 90 วันหลังส่งมอบ · ลูกค้าธนาคาร/สถาบันการเงิน **ต้องมี "ภาคผนวก PDPA" 3 ข้อ** ใช้ข้อความจาก `references/bank-pdpa-annex.md` ตรงตัว (เกณฑ์ของ MD, ถ้อยคำดูแลโดย `plat-may`) · ไม่ใช่ธนาคารแต่มีข้อมูลอ่อนไหว ม.26 → ส่ง `plat-may` ดูก่อนส่ง | sales-proposal, deal-approval ข้อ 5 (deal-rules v2026.3) |
| **ชุดต้อนรับพนักงานใหม่** | ภายใน HR | ห้ามเลขบัตรประชาชน เบอร์มือถือ อีเมลส่วนตัว เลขบัญชีของพนักงานใหม่ในไฟล์ — เก็บใน HR system เท่านั้น | onboarding-pack |
| **JD / ประกาศรับสมัคร** | ภายนอก | ใช้ข้อห้ามข้อ 3 ของ policy-summary ตามปกติ (ห้ามเบอร์มือถือส่วนตัว ใช้อีเมล/เบอร์สำนักงาน) | customer-data-policy ข้อ 2 |
