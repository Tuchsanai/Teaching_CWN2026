# deal-approval — ตัดสินดีลจากกำไรและความเสี่ยง

ทำเรื่องเดียว: อ่านสรุปดีล 1 ใบ → ตรวจ 7 ข้อตามลำดับ → เขียน `approval.md` ไม่คิดราคาใหม่เอง (นั่นคือ `pricing-calc`) และไม่แก้ proposal (นั่นคือ `sales-proposal`)

ความรู้ที่ต้องใช้ (ไม่ต้องเปิด company-kit):
- `references/approval-rules.md` — ดีลไหนต้องผ่าน MD, เกณฑ์ 7 ข้อ, กฎภาคผนวก PDPA ลูกค้าธนาคาร, ผล 3 แบบ
- skill `pricing-rules` (core) — price-list + กฎ margin/ส่วนลด/buffer/VAT (สคริปต์อ่าน price-list ของ core เอง)
- skill `customer-data-policy` (core) — ข้อมูลที่ห้ามอยู่ในเอกสาร (ข้อ 7)
- `references/approval-template.md` — รูปแบบ `approval.md`

## ขั้นตอน

1. **อ่านสรุปดีล** ดึง: ลูกค้า + ประเภท (ธนาคาร/สถาบันการเงินหรือไม่, มีข้อมูลอ่อนไหวไหม), รายการ man-day/บริการ, ส่วนลด, ระยะเวลา, ทีม, UAT, งวดเงิน, เครดิตเทอม, ค่าปรับ, ใครถือกี่โปรเจกต์
2. **ลูกค้าธนาคาร/สถาบันการเงิน → เช็กภาคผนวก PDPA ก่อนอย่างอื่น** ต้องมี 3 ข้อพอดี (DPA, data residency ไทย, แจ้งเหตุ 72 ชม.) ไม่มีหรือไม่ครบ → ❌ ตีกลับ Sales ทันที ไม่ต้องตรวจข้ออื่น
3. **ตรวจตัวเลขซ้ำด้วยสคริปต์** — อย่าเชื่อ margin ในสรุปดีลเฉย ๆ
   - เขียน `deal-input.json` (รูปแบบอยู่หัวไฟล์สคริปต์) แล้วรัน `python scripts/deal_check.py deal-input.json`
   - ได้: ราคา/ต้นทุน/margin ตรงกับสรุปไหม, % ส่วนลด, % ใช้กำลังคน, และ **margin ถ้าเติม buffer 10%** (ตั้ง `buffer_included: false` เมื่อสรุปดีลไม่ได้บอกว่ารวม buffer แล้ว)
   - ของนอก price-list ใส่ใน `external` (ต้นทุนจริง + ≥ 20%)
4. **ตรวจ 7 ข้อตามตารางใน `approval-rules.md`** ให้ผลแต่ละข้อ ✅ / ❌ / 🟡 / — พร้อมตัวเลขจริง
   - กับดักที่เจอบ่อย: margin ดูผ่านเพราะไม่มี buffer หรือตัด QA · ใช้กำลัง < 85% แต่ UAT สั้น · งวดสุดท้ายใหญ่ซ่อนอยู่ "หลัง go-live N วัน" · ค่าปรับ "ไม่มีเพดาน" = unlimited liability
5. **ตัดสินผล**
   - margin (หลังส่วนลด + buffer) < 15% → ❌ (ปฏิเสธ ห้ามขอยกเว้น)
   - ข้อ 1–5 ข้อใดไม่ผ่าน → ❌ ตีกลับ ระบุเลขข้อ, ส่งให้ใคร, ต้องแก้อะไร
   - ไม่ผ่านแค่ข้อ 6 (ทีม) หรือ margin 15–25% ที่มีเหตุผลเชิงกลยุทธ์ที่ตรวจสอบได้ → 🟡 อนุมัติแบบมีเงื่อนไข
   - ผ่านทั้งหมด → ✅
6. **เขียน `approval.md`** ตาม `references/approval-template.md` เก็บไว้ใน `work/<รหัสดีล>/` พร้อม `deal-input.json` · เหตุผล ≤ 5 บรรทัด · ตอบผู้ใช้สั้น ๆ: ผล + margin + 2–3 เหตุผลหลัก

## หลักที่ MD ใช้
- "เหตุผลเชิงกลยุทธ์" (ลูกค้าใหม่, reference, ได้งานต่อ) ใช้ได้เฉพาะช่วง margin 15–25% และต้องมีหลักฐาน (LOI/MOU/อีเมลลูกค้า) — คำพูดเซลส์อย่างเดียวไม่พอ
- เส้นตายของเซลส์ไม่ใช่เหตุผลให้อนุมัติ
- เวลาตีกลับ ให้ทางออกด้วย (แบ่งเฟส, ปรับงวด, เปลี่ยนคน) ไม่ใช่แค่ "ไม่ผ่าน"
- ไม่คัดลอกเบอร์มือถือ/เลขบัตร/ชื่อลูกค้าปลายทางลง approval.md (ถ้าสงสัยเรื่องข้อมูลส่วนบุคคล ใช้ `customer-data-policy`)
