# ด่านก่อนปล่อยโมเดล (release gates) — ต้องผ่านทุกด่านก่อน Go

> สรุปจากประสบการณ์ปล่อยโมเดลของทีม ML/MLOps โนวาเทค + `ml-queue-forecast/notes.md` · ใช้กับโมเดลทุกตัวที่ผลไปถึงผู้ใช้ปลายทาง

| ด่าน | คำถาม | ผ่านเมื่อ | ถ้าไม่ผ่าน |
|---|---|---|---|
| G1 เทียบแฟร์ | โมเดลใหม่กับตัวที่ใช้อยู่ (และ baseline) ทดสอบบน **data version เดียวกัน · ชุดสาขา/กลุ่มเดียวกัน · ช่วง test เดียวกัน** ไหม | มีผลทุกตัวบน data version ล่าสุด ใน MLflow | ส่งกลับ `mlflow-experiment` ให้รันซ้ำ — ห้ามอ้างตัวเลขข้าม data version |
| G2 ทำซ้ำได้ | fix seed, มี git commit, data version, model artifact ลง MLflow Model Registry (ไม่ใช่ drive / notebook บนเครื่องใคร) | คนอื่นรันซ้ำได้ metric หลักต่างไม่เกิน ±0.3 จุด | No-go |
| G3 ผ่านเกณฑ์สัญญา | metric หลักผ่านเกณฑ์ใน TOR/สัญญาของลูกค้า | ผ่านพร้อม margin (แนะนำ ≥ 2 จุด) | ถ้าผ่านแบบเฉียด ให้เขียนความเสี่ยงชัดใน release notes |
| G4 กลุ่มย่อย | แยก error ตามกลุ่มที่ผู้ใช้เจ็บที่สุด (เช่น ช่วงเงินเดือนออก, สัปดาห์วันหยุด, ช่วงเวลา, ประเภทสาขา) + ดู **ทิศทาง** error (ต่ำกว่าจริง vs สูงกว่าจริง ไม่เท่ากัน) | ไม่มีกลุ่มไหนแย่กว่าตัวเดิม | ระบุเป็น known issue + เกณฑ์เฝ้า หรือ No-go ถ้าแย่กว่าตัวเดิม |
| G5 ข้อมูลขอบ | หน่วยที่ถูกตัดออกจากชุดเทรน/test, หน่วยใหม่ไม่มีประวัติ, หน่วยที่ปิดไปแล้วกลับมา — โมเดลทำอะไรกับมัน | มี fallback ที่เขียนไว้และทดสอบแล้ว | No-go จนกว่าจะมี fallback |
| G6 ทางถอย | ตัวเดิมยังรันคู่ขนานได้ไหม, สลับกลับด้วย flag ได้ภายในกี่นาที, ใครกด | สลับได้ ≤ 15 นาทีโดยไม่ deploy | No-go |
| G7 เฝ้าดู | มี job คิด metric รายวัน/สัปดาห์จากข้อมูลจริงที่เข้าทุกคืน + แจ้งเตือนตาม `rollback-criteria.md` | สคริปต์ `check_rollback.py` (หรือเทียบเท่า) รันอัตโนมัติ | No-go |
| G8 shadow | รัน shadow (คำนวณจริง แต่ผู้ใช้ไม่เห็น) ครอบช่วงเสี่ยงอย่างน้อย 1 รอบ (เช่น ต้องครอบวันเงินเดือนออก) | ผลเกณฑ์ rollback = OK หรือ WATCH ที่อธิบายได้ | ยืด shadow / No-go |
| G9 ข้อมูลส่วนบุคคล | ข้อมูลเทรน/รายงานไม่ระบุตัวตน, release notes ไม่มีข้อมูลลูกค้าปลายทาง | ตาม `customer-data-policy` (core) | แก้ก่อนส่งออก |
| G10 ขั้นตอน deploy | ลูกค้าเซ็นรับ, แจ้งล่วงหน้า, 3 บทบาท, ช่วงเวลาที่อนุญาต | ตาม `deploy-rules.md` | เลื่อนวัน |

## หลักคิด

- **เปลี่ยนสองอย่างพร้อมกัน = ไม่รู้ว่าอะไรทำให้ดีขึ้น** (เช่น feature ใหม่ + data version ใหม่) → G1 สำคัญที่สุด
- error ที่ทำให้ผู้ใช้ "จัดคนไม่พอ" อันตรายกว่า error ที่ทำให้ "จัดคนเกิน" → เกณฑ์ต้องดู bias ไม่ใช่แค่ MAPE
- ผล Go/No-go ต้องเขียนเหตุผลทุกด่าน ไม่ใช่แค่ ✅
