# Checklist ขึ้นระบบจริง (deploy-checklist)

งานนี้คือ **เตรียมขึ้น production 1 รอบ** โดยไม่ลืมขั้นตอนไหน (backup, migration, rollback, แจ้งลูกค้า)
ผลลัพธ์คือไฟล์ markdown 1 ไฟล์ที่คนในห้อง deploy ติ๊กตามได้ และมีคำตัดสินอยู่บรรทัดบนสุด
skill นี้ไม่ได้กด deploy เอง หน้าที่ของมันคือเตรียม checklist และบอกว่ามีอะไรขวางอยู่

`SKILL_DIR` = โฟลเดอร์ของ skill นี้ · กติกาทั้งหมดอยู่ใน `references/deploy-rules.md` ซึ่งสรุปมาจาก runbook ของบริษัท ใช้ได้แม้ในเครื่องที่ไม่มี company-kit

## ขั้นตอน

1. **เก็บข้อมูลของ release นี้** จากที่ผู้ใช้ให้มา หรือจากไฟล์ในโปรเจกต์ (release notes, log ของ CI/test, อีเมล UAT, โน้ตทีม)
   - ระบบ / ลูกค้า / **เป็นลูกค้าธนาคารหรือไม่** / วันเวลา deploy / เวอร์ชัน (branch, commit)
   - migration: มีกี่ตัว ย้อนกลับได้ไหม เป็นแบบ expand ไหม แปลงข้อมูลเดิมด้วยไหม
   - feature flag, cron/batch ที่เขียนข้อมูล, webhook ภายนอก, โดเมนและ cert ที่เกี่ยวข้อง
   - ผลทดสอบล่าสุด (ถ้ามีรายงานจาก `test-from-plan` / `bug-report` ให้ใช้คำตัดสินของรายงานนั้น)
   - ข้อมูลไหนหาไม่เจอ **ห้ามเดา** ให้ทิ้งช่อง `____` ไว้ และถือว่าเป็น blocker หรือคำถามที่ต้องตอบ
2. **เช็กวันที่** ด้วยสคริปต์ (ใช้ Python 3.8+ ไม่ต้องลงอะไรเพิ่ม):
   ```
   python SKILL_DIR/scripts/deploy_window.py <YYYY-MM-DD> [--bank] [--today <วันนี้>] [--holiday <วันหยุด> ...] [--hotfix-sev1]
   ```
   สคริปต์จะบอกว่าวันนี้ผ่านกติกาไหม วันสุดท้ายที่ต้องส่งประกาศแจ้งลูกค้า ช่วงที่ต้องมี on-call และวันสำรอง · exit code 1 = ไม่ผ่าน
   สคริปต์ไม่รู้วันหยุดราชการไทย ต้องใส่ผ่าน `--holiday` เอง
3. **อ่าน `references/deploy-rules.md`** แล้วไล่เทียบทีละข้อ (หมวด 0–6) กับข้อมูลจากข้อ 1
4. **เขียน checklist** ตามโครงใน `references/checklist-template.md` และ **ปรับให้เข้ากับ release นี้** ห้ามคัด runbook มาทั้งดุ้น
   - smoke test ต้องเป็น flow จริงของระบบนี้ และต้องมี regression ของบั๊กที่แก้ในรอบนี้
   - เงื่อนไข "ข้อมูลผิด" ในหมวด rollback ต้องเขียนให้ชัดว่าในระบบนี้หมายถึงอะไร (เช่น ยอดเงิน เวลานัด หรือแต้ม)
   - ถ้ามี migration ที่แปลงข้อมูลเดิม ต้องมีขั้นเก็บข้อมูลที่เกิดหลัง snapshot ไว้ก่อน restore
   - ระบุชื่อคนในแต่ละบทบาท · Verifier ห้ามเป็นคนที่เขียนฟีเจอร์นั้น
5. **ตัดสิน GO / NO-GO** ใส่ไว้บนสุดของไฟล์ พร้อมตาราง blocker (เรื่อง ที่มา คนรับผิดชอบ และกำหนดเสร็จ) และวันสำรองจากสคริปต์
   - ถ้าเจอข้อใดข้อหนึ่งต่อไปนี้ให้ตัดสิน NO-GO: test ยังล้ม / ไม่มีลายลักษณ์อักษรว่าเซ็นรับ UAT / แจ้งลูกค้าไม่ทัน / ไม่มี release notes / cert เหลือ ≤ 21 วัน / migration ยังไม่ได้ dry-run
6. **ร่างประกาศแจ้งลูกค้า** (`NOTICE-maintenance`) ใส่ท้ายไฟล์ และทำตาม `customer-data-policy`:
   ใช้เบอร์ on-call กลางเท่านั้น ห้ามมีเบอร์มือถือส่วนตัว ห้ามมีชื่อหรือเลขของลูกค้าปลายทาง และเขียนเป็นภาษาผู้ใช้ ไม่ใช้เลข ticket
7. **บันทึกไฟล์** ไว้ที่ `work/<YYYY-MM-DD>-<ระบบ>-<เวอร์ชัน>/deploy-checklist.md` แล้วตอบผู้ใช้สั้น ๆ: คำตัดสิน, blocker, งานที่ต้องทำ "พรุ่งนี้", และวันสำรอง

## ถ้าผู้ใช้ถามแค่ "แผน rollback ถ้าพัง"

ให้ตอบเฉพาะหมวด 5 ที่ปรับให้เข้ากับระบบนี้แล้ว: เกณฑ์ที่ต้อง rollback, ลำดับ flag → image เดิม → restore snapshot (ต้องมี 2 คนตกลงร่วมกัน) และการแจ้งลูกค้าภายใน 30 นาที
ถ้ายังไม่รู้ว่า migration ย้อนกลับได้ไหม ต้องถามก่อน เพราะคำตอบนี้เปลี่ยนแผนทั้งหมด

## หลังจบ

ถ้า rollback หรือมีผลกระทบกับลูกค้า → ส่งต่อให้ skill `postmortem` (ฝน, `ops-fon`) ภายใน 3 วันทำการ
