# สิ่งที่ลูกค้ามักลืมเขียนใน TOR แต่จะถามทีหลัง (checklist ของ sa-ton)

ไล่ทุกหมวด · ข้อที่ TOR ไม่ได้พูด → requirement ระดับ S (ที่มา `GAP`) + คำถาม Q-NN พร้อมสมมติฐาน
🔴 = มักกระทบราคา/ขอบเขต ต้องถามก่อนยื่นราคา

## 1. ผู้ใช้และการเข้าระบบ
- กลุ่มผู้ใช้ที่ TOR ไม่ได้นับ: คนที่ **ยังไม่เป็นลูกค้า** (เช่น มาเปิดบัญชี แต่ TOR บังคับยืนยันตัวตนด้วยระบบหลัก) 🔴, คนจองแทนผู้อื่น (ลูกจองให้พ่อแม่)
- บทบาท/สิทธิ์: ใครเห็นข้อมูลของใคร (สาขา / ภาค / ทั้งประเทศ), role มาจากไหน (AD/Entra group มีให้จริงไหม)
- ล็อกบัญชี, rate limit OTP, ข้อความ error ที่ไม่บอกว่าข้อมูลไหนผิด (กัน enumeration)
- consent / privacy notice ตอนเข้าใช้ครั้งแรก (PDPA) และเก็บเวอร์ชันข้อความ

## 2. กติกาธุรกิจที่ "ทุกคนรู้" ยกเว้นในเอกสาร
- จองล่วงหน้าได้กี่วัน / ปิดรับก่อนกี่นาที / จำกัดจำนวนต่อคน
- มาสาย / ไม่มา (no-show) นิยามอย่างไร มีบทลงโทษไหม
- ลำดับความสำคัญเมื่อมีหลายช่องทางปนกัน (จอง vs walk-in, VIP) 🔴 — ลูกค้าจะถามแน่ตอน UAT
- ลดความจุหลังมีคนจองแล้ว / ปิดสาขากะทันหัน → แจ้งใคร ทำอะไรกับรายการเดิม
- วันหยุด/เวลาทำการ ใครเป็นคนดูแลข้อมูล
- ตัวเลข KPI ในวัตถุประสงค์ (เช่น "ลดเวลารอ 30%") **วัดอย่างไร ฐานเท่าไร** 🔴 — ถ้าไม่ตกลงก่อน จะเถียงกันตอนรับมอบ

## 3. การแจ้งเตือน
- ช่องทางของผู้ใช้แต่ละกลุ่ม (คนที่ไม่มี LINE?) · fallback เมื่อส่งไม่สำเร็จ / ผู้ใช้บล็อก
- **ใครจ่ายค่า SMS / ข้อความ** และใช้ gateway ของใคร 🔴
- ข้อความยืนยันทันทีหลังทำรายการ (TOR มักเขียนแต่ "แจ้งเตือนก่อนนัด")

## 4. การเชื่อมต่อระบบ
- มี sandbox ไหม ได้เมื่อไร (ช้า = ไทม์ไลน์เลื่อน) · เอกสาร API รุ่นที่ใช้จริง · rate limit
- ระบบปลายทางล่ม → ผู้ใช้เห็นอะไร ระบบทำงานต่อได้แค่ไหน
- อุปกรณ์เดิมที่สาขา (ตู้คิว, จอ) อยู่ในเครือข่ายที่ออก cloud ได้ไหม 🔴
- webhook: ตรวจลายเซ็น + idempotent (รับซ้ำได้)
- ใบรับรอง mTLS ใครต่ออายุ — ต้องมี alert ก่อนหมด (บทเรียน incident 2026-09)

## 5. ข้อมูลและรายงาน
- ข้อมูลตั้งต้น (master สาขา, ภาค, ประเภทบริการ) ใครส่ง รูปแบบไหน
- ข้อมูลย้อนหลังที่จะได้ "หลังเซ็นสัญญา" → เสี่ยงเวลา + คุณภาพ (สาขาปิด/ย้าย/เปิดใหม่, แถวซ้ำ)
- ส่งออก Excel ต้องไม่มีข้อมูลระบุตัวบุคคล · ความสดของตัวเลข dashboard
- ระยะเวลาเก็บข้อมูลส่วนบุคคล แล้ว anonymize เมื่อไร · ลบสำเนาข้อมูลลูกค้าภายใน 90 วันหลังส่งมอบ (นโยบายบริษัท)

## 6. ML / พยากรณ์ (ถ้ามี)
- เกณฑ์ความแม่นยำวัดบนข้อมูลชุดไหน (hold-out ตามเวลา) และรายงานแยกช่วงที่ยาก (วันเงินเดือนออก, สัปดาห์วันหยุด, ช่วงเที่ยง)
- **พยากรณ์ต่ำกว่าจริงอันตรายกว่าพยากรณ์เกิน** (จัดคนไม่พอ) — เกณฑ์แยก
- หน่วยที่ข้อมูลไม่พอ (สาขาใหม่ < 8 สัปดาห์) ใช้ fallback อะไร
- เกณฑ์ถอยกลับรุ่นเดิม + ใครอนุมัติ · shadow mode ก่อนให้ผู้ใช้เห็น · บันทึก dataset/seed ทุกรุ่น

## 7. ความปลอดภัย / compliance
- pen test: ใครจ่าย กี่รอบ รวม retest ไหม ใช้เวลากี่สัปดาห์ 🔴 — จองรอบให้มีเวลาแก้ก่อน go-live
- มาตรฐานที่อ้าง (ธปท. IT risk, PCI DSS, PDPA) → แตกเป็นข้อที่ทดสอบได้
- audit log: เก็บกี่ปี ใครค้นได้ แก้ไม่ได้ (append-only)
- ข้อมูลอ่อนไหว (เลขบัตรประชาชน, เลขบัตรเครดิต) เก็บแบบ hash/token เท่านั้น ห้ามอยู่ใน log/Excel/error

## 8. NFR ที่ TOR มักไม่มีตัวเลข
- ปริมาณใช้งานช่วงพีค (คำขอ/วินาที, ผู้ใช้/วัน) 🟡 → ต้องใช้ตั้ง load test
- uptime วัด 24×7 หรือเวลาทำการ, นิยาม Sev 1–4, ค่าปรับ 🔴
- DR: RPO / RTO, backup เก็บกี่วัน
- อุปกรณ์/เบราว์เซอร์ที่ผู้ใช้ใช้จริง, ผู้สูงอายุ (ตัวใหญ่, ≤ 4 ขั้น), ภาษาที่สอง

## 9. ส่งมอบและโครงการ
- UAT กี่สัปดาห์ (ถ้าไม่เขียน เสนอ ≥ 3 สัปดาห์) · ใครเป็นผู้รับมอบ
- นำร่อง: เลือกหน่วยนำร่องให้มีความหลากหลาย · ขยายเป็นระลอก
- อบรมผู้ใช้กี่คน รูปแบบไหน · คู่มือกี่ชุด
- งบ "รวม hosting + MA ปีแรก" → แยกต้นทุนรายปีให้ชัด
- out of scope ที่ต้องเขียนในสัญญา (อุปกรณ์เดิม, ค่าข้อความ, แอป native)
