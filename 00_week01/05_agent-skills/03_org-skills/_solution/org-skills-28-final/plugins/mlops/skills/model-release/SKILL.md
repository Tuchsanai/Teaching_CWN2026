# model-release — ปล่อยโมเดลรุ่นใหม่พร้อมเกณฑ์ถอยกลับ

ทำเรื่องเดียว: ตัดสินว่าโมเดลรุ่นใหม่ **พร้อมปล่อยไหม ปล่อยเมื่อไหร่ ถอยเมื่อไหร่** แล้วเขียนเป็น release plan
(ทดลอง/เทียบรอบ → `mlflow-experiment` · คืน deploy จริง → `deploy-checklist` · ถอยแล้วเขียนสรุปเหตุ → `postmortem`)

`SKILL_DIR` = โฟลเดอร์ของ skill นี้ · ความรู้ที่ต้องใช้อยู่ใน `references/` ครบ ไม่ต้องมี company-kit ในเครื่อง

| ไฟล์ | ใช้ตอน |
|---|---|
| `references/release-gates.md` | ด่าน G1–G10 ที่ต้องตรวจ |
| `references/rollback-criteria.md` | เกณฑ์ R1–R5 ค่าเริ่มต้น + วิธีถอย + ใครตัดสิน |
| `references/deploy-rules.md` | ช่วงเวลาห้าม deploy, แจ้งลูกค้า 3 วันทำการ, 3 บทบาท |
| `references/data-policy.md` | ข้อมูลลูกค้าใน release notes / รายงาน |
| `references/queue-forecast.md` | บริบทโมเดลพยากรณ์คิว (r01–r03, ปัญหาที่รู้แล้ว, เกณฑ์ TOR) |
| `templates/release-plan.md` | โครงไฟล์ผลลัพธ์ |
| `scripts/check_rollback.py` | ตรวจเกณฑ์ rollback จาก CSV พยากรณ์เทียบของจริง (stdlib ล้วน) |

## ขั้นตอน

1. **หาของที่จะปล่อย** — ถามหรือหาเอง: รุ่นใหม่ (run id), รุ่นที่ใช้อยู่ใน production, ลูกค้า, data version, ผลทดลอง (MLflow / CSV ผลทดลอง / notes ของ DS) · ถ้าเป็นโมเดลพยากรณ์คิว อ่าน `references/queue-forecast.md` ก่อน
2. **ตรวจด่าน G1–G10** ตาม `references/release-gates.md` ทีละด่าน — ทุกด่านให้สถานะ ✅ / ⚠️ / ❌ พร้อมหลักฐาน ห้ามติ๊กผ่านโดยไม่มีหลักฐาน
   - G1 ต้องเช็กทุกครั้ง: เทียบ data version + จำนวนหน่วย (สาขา) + ช่วง test ของทุก run ที่เอามาเทียบ ถ้าไม่ตรงให้เขียนว่า "เทียบไม่แฟร์" ข้างตัวเลข
   - G4 ดูทั้งขนาดและ **ทิศทาง** error ในกลุ่มที่ผู้ใช้เจ็บ (ต่ำกว่าจริง = จัดคนไม่พอ)
   - G5 หาหน่วยที่ถูกตัดออกจากข้อมูล แล้วถามว่าตอนนี้ระบบจริงยังต้องพยากรณ์ให้หน่วยนั้นไหม
3. **สรุปสถานะ**: GO / GO แบบมีเงื่อนไข (ระบุเงื่อนไขและเส้นตาย) / NO-GO
4. **วางแผนเวลา** ตาม `references/deploy-rules.md`: ตรวจด่านค้าง → แจ้งลูกค้า (≥ 3 วันทำการ) → shadow (ต้องครอบช่วงเสี่ยง เช่น 25–สิ้นเดือน) → ประชุม Go/No-go → สลับจริงในช่วงที่อนุญาต → เฝ้าดู 4 สัปดาห์ · ใช้วันจริงในปฏิทิน (เช็กวันในสัปดาห์และวันหยุดราชการ)
5. **ตั้งเกณฑ์ rollback** จาก `references/rollback-criteria.md` — ใช้ค่าเริ่มต้น ถ้าปรับให้เขียนเหตุผล · ระบุ flag, ตัวเดิมรันคู่ขนาน, ใครกด
6. **ถ้ามีไฟล์ผลพยากรณ์เทียบของจริง** (ช่วง shadow หรือหลังขึ้นจริง) รัน
   `python "$SKILL_DIR/scripts/check_rollback.py" <file.csv>` แล้วแปะตารางผลลงแผน (exit 2 = แนะนำถอย)
7. **เขียนไฟล์** ตาม `templates/release-plan.md` ที่ `work/<YYYY-MM-DD>-release-<model>-<run>.md` (หรือที่ผู้ใช้บอก) · ข้อความแจ้งลูกค้าใช้ภาษาผู้ใช้ ไม่มีข้อมูลส่วนบุคคล (`references/data-policy.md`)
8. **ตอบผู้ใช้สั้น ๆ**: สถานะ Go/No-go, ด่านที่ค้าง (ใคร/ภายในเมื่อไหร่), วันสลับจริง, เกณฑ์ถอยหลัก, เรื่องที่ต้องให้คนตัดสิน

## กติกา

- **ไม่ตัดสินแทนคน** ในเรื่อง: ค่าเกณฑ์ที่ต่างจากค่าเริ่มต้น, วันสลับจริงที่ใกล้วันหยุดยาว, ยอมรับ known issue — ให้ใส่ในหัวข้อ "เรื่องที่ต้องให้คนตัดสิน"
- ตัวเลขทุกตัวในแผนต้องอ้างที่มาได้ (run id / ไฟล์) · ห้ามแต่งผลทดลองที่ยังไม่ได้รัน ให้เขียนว่า "รอรัน"
- ไม่มีทางถอยที่ทดสอบแล้ว = NO-GO เสมอ
