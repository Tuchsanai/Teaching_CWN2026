สถานะ: ร่างแรก รอทีมยืนยันหัวข้อ 1 | อัปเดตล่าสุด: 2026-11-06

ตอนเขียนแผน โฟลเดอร์โปรเจกต์ยังว่างและยังไม่มี requirement เป็นลายลักษณ์อักษร
ทุกอย่างในหัวข้อ 1 จึงเป็น **สมมติฐาน** ไม่ใช่ข้อกำหนด

## 2. สถาปัตยกรรมและ stack ที่แนะนำ

**ใช้ modular monolith**: deploy เป็นแอปเดียว (แยก process `api` กับ `worker`) แต่แบ่งโมดูลชัดเจน
ทีมเล็กยังไม่คุ้มกับต้นทุนของ microservices และถ้าขอบเขตโมดูลดี ค่อยแยกทีหลังได้

| ส่วน | เลือก | เหตุผล |
|---|---|---|
| ภาษา / framework | TypeScript + NestJS | ระบบโมดูลตรงกับโครงที่ต้องการ และมีตัวช่วยด้าน auth/validation |
| ฐานข้อมูล | PostgreSQL | ข้อมูลเงินต้องใช้ transaction และ unique constraint |
| ORM / migration | Prisma | migration ตรงไปตรงมา ใช้ raw SQL ได้เมื่อต้อง lock แถว |
| งานเบื้องหลัง | pg-boss (คิวบน Postgres) | ไม่ต้องเพิ่ม infrastructure ในช่วงแรก |
| ฟอร์มจ่ายเงิน | Hosted checkout ของผู้ให้บริการ | ข้อมูลบัตรไม่ผ่านเซิร์ฟเวอร์เรา ขอบเขต PCI เล็กลงมาก |

ยังไม่ใส่ Redis, Kafka, Kubernetes ไว้ก่อน จะเพิ่มเมื่อมีตัวเลขยืนยันว่าจำเป็น

## 4. โมดูลและขอบเขตหน้าที่

| โมดูล | รับผิดชอบ | ไม่รับผิดชอบ |
|---|---|---|
| `auth` | สมัคร, login, ออก/หมุน/เพิกถอน token, ยืนยันอีเมล, reset password | ข้อมูลโปรไฟล์ |
| `users` | ข้อมูลผู้ใช้, ลบบัญชีตาม PDPA | รหัสผ่านและ token |
| `membership` | แพ็กเกจ, สถานะ subscription, ตอบคำถาม "คนนี้ใช้ฟีเจอร์นี้ได้ไหม" | การคุยกับผู้ให้บริการชำระเงิน |
| `payments` | checkout, webhook, คืนเงิน, กระทบยอด | การตัดสินสิทธิ์สมาชิก |
| `notifications` | ส่งอีเมลจาก event | กฎธุรกิจ |
| `audit` | บันทึกแบบเพิ่มอย่างเดียว ว่าใครทำอะไรเมื่อไร | log สำหรับ debug |

### กติกาการเชื่อมโมดูล

- โมดูลเรียกกันผ่าน service ที่ export เท่านั้น ห้าม query ตารางของโมดูลอื่น บังคับด้วย lint rule
- `payments` ไม่แก้สถานะสมาชิกเอง แต่ส่ง event เช่น `payment.succeeded` ผ่าน outbox ให้ `membership` ไปอัปเดต
- ชื่อ SDK ของผู้ให้บริการปรากฏได้เฉพาะใน `payments/adapters/` เท่านั้น

### ตารางหลัก

| โมดูล | ตาราง | constraint ที่สำคัญ |
|---|---|---|
| `users` | `users` | unique อีเมล (ไม่สนตัวพิมพ์) |
| `auth` | `refresh_tokens`, `one_time_tokens` | unique `token_hash` |
| `membership` | `plans`, `subscriptions` | partial unique: หนึ่งคนมี subscription ที่ใช้งานอยู่ได้หนึ่งรายการต่อแพ็กเกจ |
| `payments` | `payments`, `refunds`, `webhook_events` | unique `(provider, provider_event_id)` และ `(user_id, idempotency_key)` |
| `shared` | `outbox` | - |
| `audit` | `audit_logs` | ไม่อนุญาต update/delete |

เงินเก็บเป็น **จำนวนเต็มหน่วยย่อย** (สตางค์) คู่กับรหัสสกุลเงินเสมอ ห้ามใช้ float

## 5. การจัดการ token

### ชนิดของ token

| | Access token | Refresh token | Token ใช้ครั้งเดียว (ยืนยันอีเมล/reset) |
|---|---|---|---|
| รูปแบบ | JWT เซ็นด้วย ES256 | สุ่ม 256 บิต (opaque) | สุ่ม 256 บิต (opaque) |
| อายุ | 15 นาที | 30 วัน (ไม่ใช้งาน 14 วันหมดอายุ) | อีเมล 24 ชม. / reset 30 นาที |
| เก็บฝั่งเซิร์ฟเวอร์ | ไม่เก็บ | เก็บเฉพาะ SHA-256 | เก็บเฉพาะ SHA-256 |
| เก็บฝั่งเว็บ | ในหน่วยความจำ ห้ามใส่ localStorage | Cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` | อยู่ในลิงก์อีเมล |

### กติกา

1. **ตรวจ JWT ให้ครบ**: ล็อก algorithm ฝั่งเซิร์ฟเวอร์ ตรวจ `iss`, `aud`, `exp` และเลือก public key จาก `kid`
2. **Claims เท่าที่จำเป็น**: `sub`, `iss`, `aud`, `iat`, `exp`, `jti` เท่านั้น ห้ามใส่ข้อมูลส่วนตัว
3. **สถานะสมาชิกไม่อยู่ใน JWT**: ตรวจจาก `membership` ทุกครั้ง เพื่อให้จ่ายเงินหรือยกเลิกแล้วมีผลทันที
4. **รหัสผ่าน**: แฮชด้วย Argon2id

### Refresh token rotation

ทุกครั้งที่ refresh จะออก token ใหม่และทำให้ตัวเก่าใช้ไม่ได้ โดย token ที่สืบกันมาอยู่ใน `family_id` เดียวกัน

```text
ส่ง refresh token เข้ามา → ค้นจาก hash แล้ว lock แถว (SELECT ... FOR UPDATE)
  ├─ ไม่พบ / หมดอายุ / family ถูกเพิกถอน → 401
  ├─ ยังไม่เคยใช้                         → ออกตัวใหม่ในธุรกรรมเดียวกัน
  ├─ เพิ่งถูกใช้ภายใน 10 วินาที            → ออกตัวใหม่ใน family เดิม (กรณีเปิดหลายแท็บพร้อมกัน)
  └─ เคยใช้ไปนานกว่านั้น                  → ถือว่าถูกขโมย: เพิกถอนทั้ง family + บันทึก audit + แจ้งเตือนผู้ใช้
```

ฝั่งเว็บต้องทำให้มีคำขอ refresh ทีละคำขอด้วย เพื่อลดการเข้าช่วงผ่อนผันโดยไม่จำเป็น

### การเพิกถอนและการดูแล key

| เหตุการณ์ | สิ่งที่ต้องทำ |
|---|---|
| Logout | เพิกถอน family ของอุปกรณ์นั้น |
| เปลี่ยน/reset รหัสผ่าน | เพิกถอนทุก family ของผู้ใช้ และแจ้งทางอีเมล |
| ระงับบัญชี | เพิกถอนทุก family และเช็กสถานะบัญชีตอน refresh |
| หมุน signing key | เปิดใช้ key ใหม่ และคง public key เก่าไว้อย่างน้อยเท่าอายุ access token (15 นาที) |

**ข้อจำกัดที่ยอมรับ**: access token ที่ออกไปแล้วจะใช้ได้จนหมดอายุ สูงสุด 15 นาทีหลังเพิกถอน
สำหรับงานเสี่ยงสูง เช่น เปลี่ยนอีเมลหรือขอคืนเงิน ให้ถามรหัสผ่านซ้ำ

### การป้องกันอื่น ๆ

- CSRF: ใช้ `SameSite=Strict` ร่วมกับตรวจ `Origin` บน endpoint ที่อ่าน cookie
- Rate limit: จำกัด login, refresh, reset ทั้งตาม IP และตามบัญชี
- กันการเดาว่าอีเมลมีในระบบ: login และ forgot password ตอบเหมือนกันทุกกรณี และใช้เวลาใกล้เคียงกัน
- Log: ห้ามมี token, รหัสผ่าน หรือ header `Authorization` / `Cookie`
- Secret: เก็บใน secret manager ไม่ commit ลง repo

ถ้ามีแอปมือถือ ให้ส่ง refresh token ผ่าน body และเก็บใน Keychain/Keystore โดยใช้กติกา rotation เดิม

## 6. Flow การชำระเงิน

### หลักการ

1. **Webhook คือความจริง** หน้า redirect กลับจาก checkout ใช้แสดงผลเท่านั้น ห้ามให้สิทธิ์จากตรงนั้น
2. **ราคามาจากเซิร์ฟเวอร์** ไคลเอนต์ส่งแค่ `plan_id` และเก็บ snapshot ราคาไว้ในแถว `payment`
3. **ทุกอย่างทำซ้ำได้โดยไม่เกิดผลซ้ำ** ทั้ง API, webhook, และ event ระหว่างโมดูล
4. **ห้ามถือ DB transaction ค้างไว้ระหว่างเรียก API ภายนอก**

### Flow หลัก

```text
1. POST /api/v1/checkout (plan_id + header Idempotency-Key)
2. สร้าง payment สถานะ created แล้ว commit
3. เรียกผู้ให้บริการ โดยส่ง idempotency key ที่สร้างจาก payment.id
4. บันทึก provider reference, เปลี่ยนเป็น pending แล้วคืน URL ของ checkout
5. ผู้ใช้จ่ายเงินบนหน้าของผู้ให้บริการ
6. Webhook เข้ามา: ตรวจลายเซ็นจาก raw body → INSERT webhook_events (ซ้ำก็ตอบ 200) → เข้าคิว → ตอบ 2xx
7. Worker: เทียบยอดเงินและสกุลเงินกับ payment → เปลี่ยนสถานะ + เขียน outbox ในธุรกรรมเดียวกัน
8. membership รับ payment.succeeded → เปิดหรือต่ออายุ subscription (รับซ้ำได้โดยไม่ต่ออายุซ้ำ)
9. หน้าเว็บ poll สถานะจากเซิร์ฟเวอร์ และแสดง "กำลังตรวจสอบ" จนกว่าจะได้ผล
```

### State machine

```text
payment:      created → pending → succeeded → partially_refunded → refunded
                          ├──────→ failed
                          └──────→ expired

subscription: pending → active ⇄ past_due → expired
                        active → cancel_at_period_end → expired
```

การเปลี่ยนสถานะที่ไม่อยู่ในแผนภาพให้ปฏิเสธและบันทึก log ซึ่งช่วยรับมือ webhook ที่มาผิดลำดับ
ถ้าไม่แน่ใจสถานะจริง ให้ถามจาก API ของผู้ให้บริการ

### เมื่อเกิดเรื่องผิดปกติ

| สถานการณ์ | วิธีรับมือ |
|---|---|
| เรียกผู้ให้บริการแล้ว timeout | **ห้ามสรุปว่าล้มเหลว** คงสถานะ pending แล้วให้ job ตรวจซ้ำ เพราะเงินอาจตัดไปแล้ว |
| แอปล่มหลังขั้น 3 ก่อนขั้น 4 | Job กระทบยอดหยิบ payment ที่ค้าง `created` ไปตรวจ |
| Webhook หาย | Job ทุก 5-10 นาทีถามสถานะ payment ที่ค้าง `pending` |
| Webhook ซ้ำ | unique constraint กันไว้ ตอบ 200 |
| ยอดเงินไม่ตรง | ไม่ให้สิทธิ์ ทำเครื่องหมายให้คนตรวจ และแจ้งเตือนทีม |
| ผู้ใช้กดจ่ายซ้ำ | `Idempotency-Key` และ partial unique index ของ subscription |
| ต่ออายุไม่สำเร็จ | เข้า `past_due` มีช่วงผ่อนผัน (ค่าเริ่มต้น 7 วัน) แจ้งเตือนผู้ใช้ เลยกำหนดจึง `expired` |

นอกจากนี้ มี job รายวันเทียบรายการในระบบกับรายงานของผู้ให้บริการ ส่วนต่างต้องแจ้งเตือนคนดูแล

## 7. การจัดการ error

### รูปแบบ response

ใช้ RFC 9457 (`application/problem+json`) และมี `code` ที่คงที่ให้ไคลเอนต์ใช้ตัดสินใจ

```json
{
  "type": "https://docs.example.com/errors/payment-declined",
  "title": "Payment declined",
  "status": 402,
  "code": "PAYMENT_DECLINED",
  "detail": "ธนาคารปฏิเสธรายการ กรุณาลองบัตรอื่น",
  "request_id": "01J..."
}
```

ไคลเอนต์ต้องใช้ `code` ไม่ใช่ข้อความ เพราะข้อความเปลี่ยนหรือแปลภาษาได้

### ประเภทของ error

| ประเภท | HTTP | ตัวอย่าง `code` | Log | Alert |
|---|---|---|---|---|
| ข้อมูลไม่ถูกต้อง | 400 / 422 | `VALIDATION_FAILED` | info | ไม่ |
| ยังไม่ยืนยันตัวตน | 401 | `TOKEN_EXPIRED`, `INVALID_CREDENTIALS` | info | ไม่ |
| ไม่มีสิทธิ์ | 403 | `MEMBERSHIP_REQUIRED` | info | ไม่ |
| ไม่พบ | 404 | `NOT_FOUND` (รวมกรณีเป็นของคนอื่น) | info | ไม่ |
| สถานะขัดแย้ง | 409 | `ALREADY_SUBSCRIBED`, `IDEMPOTENCY_KEY_REUSED` | info | ไม่ |
| ธนาคารปฏิเสธ | 402 | `PAYMENT_DECLINED` | info | เมื่ออัตราสูงผิดปกติ |
| เรียกถี่เกิน | 429 | `RATE_LIMITED` | warn | เมื่อสูงผิดปกติ |
| ผู้ให้บริการมีปัญหา | 502 / 503 | `PAYMENT_PROVIDER_UNAVAILABLE` | error | ใช่ |
| บั๊กของเรา | 500 | `INTERNAL_ERROR` (ไม่เผยรายละเอียด) | error + stack | ใช่ |

### กติกาในโค้ด

- ชั้น domain โยน error ที่มีความหมายทางธุรกิจ และไม่รู้จัก HTTP มีตัวแปลงเป็น response จุดเดียวใน `shared/errors`
- `adapters/` แปลง error ของผู้ให้บริการเป็น error ของเราเสมอ แยกให้ได้ว่า "ถูกปฏิเสธ", "ลองใหม่ได้" หรือ "ไม่รู้ผล"
- ห้าม `catch` แล้วเงียบ ถ้าจัดการไม่ได้ให้ปล่อยขึ้นไปพร้อม context

### Retry และ timeout

- เรียกภายนอกต้องมี timeout เสมอ (ค่าเริ่มต้น 10 วินาที) แล้วปรับตามเอกสารผู้ให้บริการ
- retry เฉพาะ error ชั่วคราว ด้วย exponential backoff + jitter และต้องส่ง idempotency key ทุกครั้ง
- งานใน worker ที่ล้มเหลวเกินจำนวนครั้งเข้า dead-letter queue พร้อม alert และมี runbook วิธีนำกลับมารันใหม่

### Webhook

| สถานการณ์ | ตอบกลับ |
|---|---|
| ลายเซ็นผิด | 400 และบันทึก warn |
| ประเภท event ที่ไม่สนใจ | 200 |
| รับเข้าคิวสำเร็จ หรือเป็น event ซ้ำ | 200 |
| บันทึกลง database ไม่ได้ | 500 เพื่อให้ผู้ให้บริการส่งซ้ำ |

### Observability

- ทุก request และงานใน worker มี `request_id` / `correlation_id` ไหลต่อจาก API ไปถึง outbox
- ใช้ structured log (JSON) และห้ามมีข้อมูลส่วนตัวหรือข้อมูลบัตร
- ตัวชี้วัดที่ต้อง alert: อัตรา 5xx, อัตราจ่ายสำเร็จตก, webhook ค้าง, outbox ค้าง, dead-letter มีงานเข้า

## 8. การทดสอบ

### ระดับของเทสต์

| ระดับ | ทดสอบอะไร | เครื่องมือ | รันเมื่อ |
|---|---|---|---|
| Unit | state machine, คำนวณรอบบิล, กฎการหมุน token | Vitest | ทุก PR |
| Integration | API + Postgres จริง, constraint, การ lock | Testcontainers + Supertest | ทุก PR |
| Webhook | payload จริงจาก sandbox ที่เก็บเป็น fixture + ลายเซ็นทดสอบ | Fixture | ทุก PR |
| Contract | adapter กับ sandbox จริงของผู้ให้บริการ | Sandbox | รายคืน (ไม่ขวาง PR) |
| E2E | สมัคร → จ่ายเงิน → ใช้ฟีเจอร์ได้ → ยกเลิก | Playwright | ก่อน deploy |

**อย่า mock ฐานข้อมูลในเทสต์เรื่องเงิน** เพราะความถูกต้องขึ้นกับ transaction และ unique constraint จริง
ให้ mock ที่ขอบเขต `PaymentProvider` ด้วย fake adapter แทน

### กรณีที่ต้องมีก่อนขึ้นจริง

**Token และการยืนยันตัวตน**

- [ ] JWT หมดอายุ, ลายเซ็นผิด, `alg: none`, `aud` ผิด ถูกปฏิเสธ
- [ ] ใช้ refresh token ซ้ำนอกช่วงผ่อนผันแล้ว family ถูกเพิกถอนทั้งหมด
- [ ] refresh พร้อมกันหลายคำขอแล้วไม่ทำให้ผู้ใช้หลุดจากระบบ
- [ ] reset รหัสผ่านแล้ว session เดิมใช้ไม่ได้ และลิงก์ใช้ซ้ำไม่ได้
- [ ] ผู้ใช้ A เข้าถึงข้อมูลหรือ payment ของผู้ใช้ B ไม่ได้
- [ ] rate limit ของ login ทำงาน และ response ไม่บอกว่าอีเมลมีในระบบหรือไม่

**การชำระเงิน**

- [ ] webhook เดิมส่งมาพร้อมกัน 10 ครั้ง ต่ออายุสมาชิกเพียงครั้งเดียว
- [ ] webhook มาผิดลำดับ (`failed` หลัง `succeeded`) สถานะไม่ถอยหลัง
- [ ] webhook ลายเซ็นผิดถูกปฏิเสธ และไม่มีการเปลี่ยนแปลงข้อมูล
- [ ] ยอดเงินใน webhook ไม่ตรงกับ payment แล้วไม่ให้สิทธิ์
- [ ] ส่ง `Idempotency-Key` เดิมซ้ำแล้วได้ผลเดิม ส่ง key เดิมแต่ข้อมูลต่างได้ 409
- [ ] ผู้ให้บริการ timeout แล้ว payment ยังไม่ถูกตีว่าล้มเหลว และ job กระทบยอดแก้สถานะได้
- [ ] worker ล่มกลางงาน รันใหม่แล้วข้อมูลถูกต้องและไม่เกิดผลซ้ำ
- [ ] redirect กลับมาโดยไม่มี webhook ยังไม่ได้สิทธิ์
- [ ] คืนเงินเต็มจำนวนและบางส่วน สิทธิ์สมาชิกเปลี่ยนตามนโยบาย
- [ ] สมาชิกเปลี่ยนเป็น `past_due` และ `expired` ตามเวลา (ใช้นาฬิกาจำลองในเทสต์)

### CI และเกณฑ์ merge

ทุก PR ต้องผ่าน lint, typecheck, unit, integration, ตรวจ migration, secret scan และ dependency audit

- Coverage: `payments/domain` และ `auth` ตั้งเป้า branch coverage อย่างน้อย 90% ส่วนอื่นไม่บังคับตัวเลข
- โค้ดใน `auth` และ `payments` ต้องมีผู้รีวิวอย่างน้อยหนึ่งคนที่ไม่ใช่ผู้เขียน
- ก่อนขึ้นจริง ทดลองกู้ backup และทดสอบ flow จ่ายเงินจริงยอดน้อยบน production พร้อมคืนเงิน

## 9. ลำดับงาน

ยังไม่ประมาณเวลาจนกว่าจะได้คำตอบหัวข้อ 1 ทำตามลำดับนี้ โดยแต่ละเฟสต้องผ่านเกณฑ์ก่อนไปต่อ

| เฟส | งาน | เกณฑ์เสร็จ |
|---|---|---|
| 0. ฐาน | repo, CI, Docker Compose, config, logging, error format, health check | clone แล้วรันได้ด้วยคำสั่งเดียว และ CI ผ่าน |
| 1. สมาชิก | `users`, `auth`, token rotation, ยืนยันอีเมล, reset password | ผ่านเช็กลิสต์ token ทั้งหมด |
| 2. แพ็กเกจ | `plans`, `subscriptions`, การตรวจสิทธิ์, outbox, audit | เปลี่ยนสิทธิ์ด้วย event จำลองได้ครบทุกสถานะ |
| 3. จ่ายเงิน | adapter, checkout, webhook, คืนเงิน | E2E บน sandbox ผ่าน |
| 4. กันพลาด | job กระทบยอด, dead-letter, ต่ออายุ, runbook, alert | ผ่านเช็กลิสต์การชำระเงินทั้งหมด |
| 5. ขึ้นจริง | security review, ทดสอบโหลด, ทดลองกู้ backup, ทดสอบจ่ายจริง | ทีมอนุมัติ go-live |

เริ่มเฟส 1 และ 2 ได้ก่อนเลือกผู้ให้บริการ เพราะ `payments` แยกออกมาอยู่หลัง event
แต่เฟส 3 ต้องรู้คำตอบข้อ 2-4 ของหัวข้อ 1 ก่อน

## 10. ความเสี่ยงหลัก

| ความเสี่ยง | ผลกระทบ | การป้องกัน |
|---|---|---|
| ตัดเงินแล้วไม่ได้สิทธิ์ หรือได้สิทธิ์โดยไม่จ่าย | เสียเงินและความเชื่อถือ | webhook + job กระทบยอด + การเทียบรายวัน |
| ตัดเงินซ้ำ | ต้องคืนเงินและเสียชื่อเสียง | idempotency ทุกชั้น |
| Token รั่ว | บัญชีถูกยึด | อายุสั้น, rotation, ตรวจการใช้ซ้ำ |
| ผู้ให้บริการล่ม | รับเงินไม่ได้ชั่วคราว | แจ้งผู้ใช้ชัดเจน และไม่ตัดสิทธิ์สมาชิกเดิม |
| ข้อมูลส่วนตัวรั่วผ่าน log | ผิด PDPA | กรองข้อมูลใน logger พร้อมเทสต์ |
| Requirement เรื่องภาษี/คืนเงินมาช้า | ต้องแก้ schema | ถามตั้งแต่วันแรก (หัวข้อ 1 ข้อ 7) |
