## คนใหม่ ไม่มีแพ็ก · 92 วินาที · 2 คำสั่ง

เขียนแผนไว้ที่ `work/plan.md` แล้วครับ ยังไม่มีโค้ด

**ข้อควรรู้ก่อน:** โฟลเดอร์โปรเจกต์ยังว่างอยู่และยังไม่ได้เป็น git repo จึงยังไม่มี stack หรือข้อกำหนดเดิมให้ยึด ผมเลยตั้งสมมติฐานไว้ในหัวข้อ 0 ของแผน ได้แก่ TypeScript/Node, PostgreSQL, Redis และให้ผู้ให้บริการชำระเงินเป็น adapter ที่เปลี่ยนเจ้าได้ หัวข้อนี้ต้องให้ทีมยืนยันก่อนเริ่มเขียนโค้ด

**สิ่งที่มีในแผน**
1. **โครงโฟลเดอร์:** แบ่งตาม `src/modules/*` แต่ละโมดูลมี routes, service และ repository ส่วน `shared/` เก็บของที่ใช้ร่วมกัน เช่น error, logger, db
2. **โมดูล:** users, auth, plans, subscriptions, payments (มี `FakeProvider` ไว้ใช้ตอน dev/test), webhooks, audit
3. **Token:**
   - access token เป็น JWT อายุสั้น 10–15 นาที เก็บในหน่วยความจำฝั่ง client
   - refresh token เป็นค่าสุ่มที่อ่านความหมายไม่ได้ เก็บใน cookie แบบ HttpOnly ส่วน DB เก็บแค่ค่า hash
   - ออก refresh token ใหม่ทุกครั้งที่ใช้ ถ้ามีคนเอาตัวเก่ามาใช้ซ้ำ ระบบจะยกเลิกทั้งชุดและบังคับ login ใหม่
   - เปลี่ยนรหัสผ่านหรือ logout ทุกเครื่องแล้ว token เก่าใช้ไม่ได้ทันที
   - วางขั้นตอนหมุน key ที่ใช้ลงชื่อ token ไว้แล้ว
4. **Error:**
   - ทุก error ตอบรูปแบบเดียวกันตามมาตรฐาน RFC 9457 มี `code` คงที่ให้ client ใช้ และมี `requestId` ไว้ตามหาใน log
   - เรียก payment provider แล้ว timeout จะยังไม่ตัดสินว่าล้มเหลว แต่ตั้งเป็น `pending` แล้วรอ webhook หรือ job ตรวจยอดมายืนยัน
5. **การทดสอบ:** มี unit, integration (ใช้ DB จริงใน container), ทดสอบ webhook ด้วยข้อมูลตัวอย่างจริงจาก provider, e2e, ทดสอบกับ sandbox ของ provider และตรวจด้าน security พร้อมรายการเคสที่ต้องมี เช่น กดจ่ายซ้ำต้องตัดเงินแค่ครั้งเดียว, webhook ส่งซ้ำ, refresh token ที่ถูกใช้ซ้ำ

ท้ายแผนมีลำดับงานราว 6 สัปดาห์ และ checklist สำหรับวันแรก

**สิ่งที่ควรทำวันนี้:** ส่งคำถามในหัวข้อ 0 ให้หัวหน้า โดยเฉพาะ 3 เรื่องนี้ เพราะกระทบโครงสร้างระบบมากที่สุด
- ใช้ payment provider เจ้าไหน
- มีระบบ subscription จริงไหม
- มี mobile app ไหม

ถ้าทีมมี stack มาตรฐานหรือ template โปรเจกต์อยู่แล้ว บอกผมได้เลยครับ จะปรับแผนให้ตรงกัน

## คนใหม่ มีแพ็ก core + dev · 101 วินาที · 5 คำสั่ง

ผมเขียนแผนไว้ที่ `work/plan.md` แล้ว ยังไม่ได้เขียนโค้ดตามที่ขอ แผนนี้อิงจาก skill `dev:project-scaffold` ซึ่งเป็นมาตรฐานของทีมสำหรับระบบแบบนี้ มีสรุปบั๊กจากโปรเจกต์เก่าที่ทีมเคยเจอด้วย

**แผนมี 7 ส่วน:**
1. **คำถามที่ต้องถามก่อนเริ่ม:** ในโฟลเดอร์ยังไม่มี spec ผมจึงเดาชื่อลูกค้า ราคาแพ็กเกจ วิธี login (มี OTP ไหม) ช่องทางแจ้งเตือน และเวอร์ชันข้อความยินยอม PDPA เองไม่ได้ ต้องถามลูกค้าหรือหัวหน้าก่อน
2. **โครงโฟลเดอร์:** เป็นแอป Next.js ตัวเดียว แยกโค้ดเป็นโมดูลภายในตัว แต่ละโมดูลมีไฟล์ชุดเดียวกันหมด (`index`, `service`, `repository`, `schema`, `errors`, `__tests__`) และโมดูลอื่นเรียกใช้ได้ผ่าน `index.ts` เท่านั้น
3. **5 โมดูล:** auth, member, payment, notification, audit แต่ละโมดูลมีตารางของตัวเอง แผนแยกให้เห็นว่าอะไรมีใน template แล้ว และอะไรต้องทำเพิ่ม (OTP, reset password, คืนเงิน, ผู้ให้บริการส่งข้อความจริง)
4. **การจัดการ token:** กันบั๊กที่ token หมดอายุระหว่างผู้ใช้อยู่หน้าจ่ายเงิน
   - access token อายุ 15 นาที
   - refresh token เปลี่ยนตัวใหม่ทุกครั้งที่ใช้ ถ้ามีคนเอาตัวเก่ามาใช้ซ้ำ ระบบยกเลิกทั้งชุด
   - ฝั่ง browser ต่ออายุ token ก่อนพาไปหน้าจ่ายเงินทุกครั้ง แล้วหยุดตัวจับเวลาก่อนเปลี่ยนหน้า
   - หน้ากลับจากการจ่ายเงินอ่านผลจากเลข order ไม่ต้องรอให้ login อยู่
   - webhook ที่ gateway ส่งมาซ้ำจะถูกประมวลผลแค่ครั้งเดียว และต้องตรวจลายเซ็นก่อนทุกครั้ง
5. **การจัดการ error:** error ทุกตัวเป็น class ของทีม (`AppError`) ห้าม catch แล้วเงียบ API ตอบรูปแบบเดียวกันหมด ข้อมูลที่รับเข้ามาตรวจด้วย Zod log เป็น JSON และปิดบังข้อมูลอ่อนไหว
6. **การทดสอบ:** unit test ของ `service.ts` ต้องครอบคลุมอย่างน้อย 80% ของบรรทัด แผนระบุเคสหลักของแต่ละโมดูลไว้ ส่วน E2E ข้อที่สำคัญที่สุดคือ `checkout.spec.ts` ตั้ง token ให้หมดใน 5 วินาที แล้วต้องยังเห็นหน้า "ชำระเงินสำเร็จ" โดยไม่เด้งไป login
7. **ขั้นตอนลงมือและ checklist ก่อนส่งทีม**

ได้คำตอบส่วนที่ 1 เมื่อไร บอกผมได้เลย ผมจะเริ่มสร้างโครงตามแผน ทั้งเขียน config, รันตัวสร้างโครง, ตรวจตามมาตรฐาน และรันเทสต์
