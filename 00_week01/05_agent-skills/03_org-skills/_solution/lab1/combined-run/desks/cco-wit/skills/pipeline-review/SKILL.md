# pipeline-review

ทบทวน pipeline ทั้งก้อนในภาพเดียว (เหมือนประชุมทบทวนเช้าวันจันทร์) แล้วออกคำตัดสินที่ทีมทำต่อได้ทันที
skill นี้ทำเรื่องเดียว: **จัดลำดับและตัดสินดีล** — ไม่คิดราคาเอง (`pricing-calc`), ไม่อนุมัติแทน MD (`deal-approval`), ไม่เขียน spec (`req-to-spec`)

## ข้อมูลเข้า

หาในโฟลเดอร์ที่ผู้ใช้ชี้ หรือ `company-kit/` ของบริษัท ถ้าไม่มีให้ถามผู้ใช้ — ทำต่อด้วยสิ่งที่มีและบอกว่าขาดอะไร

| ข้อมูล | ไฟล์ที่มักใช้ | ใช้ทำอะไร |
|---|---|---|
| KPI รายเดือน | `monthly-kpi.csv` | pipeline, win rate, gross margin เทียบเป้า, คนว่าง |
| สรุปดีลที่คิดราคาแล้ว | `deal-summaries/DS-*.md` | ราคา, GM, ส่วนลด, timeline, เงื่อนไขจ่าย, ค่าปรับ |
| TOR ที่ยังไม่คิดราคา | `deal-*/tor-*.md` | วงเงิน, กำหนดยื่น, ขอบเขต, ข้อกำหนดความปลอดภัย |
| ผลิตภัณฑ์ | `product/` (NovaQueue overview, feedback, v1 customers, lifecycle policy) | ดีลไหนใช้ของที่มีได้, ลูกค้า MA ที่กำลังหมด |

เกณฑ์และความรู้บริษัทที่ต้องใช้อยู่ใน `references/` — อ่านก่อนเริ่มเสมอ
- `references/decision-rules.md` — เกณฑ์ margin / ส่วนลด / timeline / สัญญา และตารางตัดสิน 4 ทาง
- `references/company-context.md` — เป้า KPI, ผลิตภัณฑ์ NovaQueue, นโยบาย sunset, ใครรับงานต่อ
- `references/output-template.md` — โครงรายงานที่ต้องได้

## ขั้นตอน

1. **อ่าน KPI ก่อนดูดีล** — เทียบ 2 เดือนล่าสุดกับเป้า เขียนประโยคเดียวว่าเดือนนี้ "ต้องเร่งปิดดีล" หรือ "ต้องเลือกดีล" (GM ต่ำกว่าเป้า / win rate ต่ำ / คนไม่พอ → เลือกดีล ห้ามซื้อยอดด้วยการลดราคา)
2. **ทำรายการดีลทั้งหมด** ทั้งดีลที่คิดราคาแล้วและ TOR ที่ยังไม่คิด + โอกาสจากผลิตภัณฑ์ (ลูกค้า MA ที่ใกล้หมด, ลูกค้าที่จะย้ายเวอร์ชัน) · บวกมูลค่าเทียบกับ pipeline ใน KPI — ถ้าไม่ครบ ให้บอกส่วนต่างและขอรายการจากหัวหน้าทีมขาย · แยก "วงเงิน TOR" (เพดาน) ออกจาก "ราคาเสนอ"
3. **ตรวจแต่ละดีลตาม `decision-rules.md`** ครบ 6 มุม: ตัวเงิน (GM, ส่วนลด), timeline + buffer + UAT, สัญญา (ค่าปรับ, งวดจ่าย, เครดิต), ข้อมูลส่วนบุคคล/อ่อนไหว (DPA, PCI, PDPA), กำลังคน (tech lead, ตำแหน่งที่ว่าง, ช่วงเวลาชนกัน), ความเข้ากับผลิตภัณฑ์
4. **ตัดสิน 1 ใน 4** — เร่ง / ส่งต่อ / ประคอง / ตีกลับ (เร่ง + ส่งต่อพร้อมกันได้) ทุกคำตัดสินต้องมี: เหตุผลเป็นตัวเลข, ทำอะไรต่อ, ใคร, ภายในวันไหน · ตีกลับ = ตีกลับ "ร่าง" ไม่ใช่ทิ้งลูกค้า ต้องบอกว่าร่างใหม่ต้องเปลี่ยนอะไรบ้างจึงจะผ่าน
5. **ไล่ความเชื่อมโยงข้ามดีล** — ลูกค้าคนเดียวกันอยู่ทั้งในดีลและในรายชื่อลูกค้าผลิตภัณฑ์ไหม, ดีลไหนแย่งทีม/ช่วงเวลาเดียวกัน, TOR ไหนขอฟีเจอร์ที่ลูกค้าเดิมขออยู่แล้ว
6. **ดีลไหนเสี่ยงหลุด** — ตารางสั้น: ดีล / เสี่ยงอะไร / ป้องกันอย่างไร (รวมลูกค้า MA ที่ใช้งานลดลง)
7. **ทีมขายกับทีม product ต้องคุยเรื่องอะไร** — 3–5 วาระ เรียงตามผลต่อรายได้ · ใส่สิ่งที่เซลส์ "ห้ามรับปาก" (ฟีเจอร์ที่ยังไม่มีวัน, วันปิดเวอร์ชันเก่าที่ยังไม่อนุมัติ, ฟีเจอร์ที่ขัดกฎ regulator)
8. **เขียนรายงานตาม `output-template.md`** เก็บที่ `work/pipeline-review-YYYY-MM-DD.md` (หรือที่ผู้ใช้กำหนด) แล้วตอบในแชตเป็นตารางสรุป 1 ตาราง + 3 บรรทัดสิ่งที่ต้องทำวันนี้

## กติกา

- **ห้ามคัดลอกข้อมูลส่วนบุคคล** (ชื่อ/เบอร์/อีเมลผู้ประสานงานลูกค้า, ข้อมูลลูกค้าปลายทางใน ticket) ลงรายงาน — อ้างเป็นบทบาทหรือเลข ticket แทน (ตาม `customer-data-policy`)
- ไม่แต่งตัวเลข: ถ้ายังไม่มีการคิดราคา เขียน "ยังไม่คิดราคา" และส่งต่อให้คนคิด
- ไม่อนุมัติแทน MD — ดีลที่เข้าเกณฑ์ MD ให้เขียนว่า "ส่งเข้า `deal-approval`" หรือ "ตีกลับก่อนเข้า MD"
- ระบุวันที่จริงทุกกำหนด (คิดจากวันนี้) และบอกข้อจำกัดของข้อมูลไว้ท้ายรายงานเสมอ
