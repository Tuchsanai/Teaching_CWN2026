# เขียนแบบไม่โทษคน

หลัก: ทุกคนตัดสินใจดีที่สุดจากข้อมูลที่มีตอนนั้น ถ้าคนพลาดได้ แปลว่า **ระบบปล่อยให้พลาดได้** — postmortem แก้ระบบ ไม่ได้ตัดสินคน

## เปลี่ยนชื่อเป็นบทบาท

| ใน log | ในเอกสาร |
|---|---|
| ชื่อคนที่ดู log / แก้ระบบ | On-call DevOps |
| ชื่อ dev ที่ทดสอบ / reconcile | Dev |
| ชื่อเซลส์ที่รับเรื่องลูกค้า | Sales |
| คนที่คุยกับลูกค้าระหว่างเหตุ | Comms |
| "dev ที่ลาออกไป" / "คนที่ upload cert" | "พนักงานคนหนึ่ง" หรือไม่กล่าวถึงเลย ให้พูดถึงกระบวนการแทน |

## ประโยคที่ควรเลี่ยง → เขียนแทน

| เลี่ยง | เขียนแทน |
|---|---|
| X ลืมต่อ cert | cert ใบนี้ต่ออายุด้วยมือ และไม่มีระบบเตือนวันหมดอายุ |
| X upload cert ผิดวิธี | ตอนนั้นกระบวนการรองรับ cert ของลูกค้าด้วยการ upload มือเท่านั้น ไม่มีขั้นลงทะเบียน |
| ไม่มีใครดู alert | alert ไม่ครอบคลุม flow จ่ายเงิน จึงไม่มีสัญญาณให้ดู |
| ควรจะรู้อยู่แล้ว | ข้อมูลนี้ไม่ได้อยู่ในที่ที่ทีมเข้าถึงได้ |
| human error | ระบุว่ากระบวนการ/เครื่องมือขาดอะไร (ตรวจซ้ำ, alert, ทะเบียน, automation) |

## คำถามที่มีคนถามในห้อง แล้วต้องเปลี่ยนทิศ

- "ใครเป็นคน upload cert ตอนนั้น?" → "ทำไมกระบวนการ upload มือถึงไม่มีขั้นลงทะเบียนวันหมดอายุ?"
- "ทำไมไม่มีใครต่อ?" → "การเตือนต่ออายุผูกกับอะไร และทำไมมันหายได้โดยไม่มีใครรู้?"

## action item ที่ดี vs ไม่ดี

- ไม่ดี: "ระวังให้มากขึ้น", "ตักเตือนผู้เกี่ยวข้อง", "อบรมคนที่ทำพลาด"
- ดี: เปลี่ยนระบบหรือกระบวนการ ตรวจสอบได้ว่าเสร็จ มีเจ้าของเป็นทีม เช่น "alert เมื่อ cert เหลือ < 21 วันทุกโดเมน ส่งเข้าช่องทีม"
