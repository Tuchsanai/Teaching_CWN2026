# postmortem — สรุปเหตุขัดข้องแบบไม่โทษคน

เปลี่ยน log ดิบของ incident ให้เป็น postmortem 1 ฉบับที่ตอบได้ว่า: เกิดอะไร กระทบแค่ไหน **ระบบ**พลาดตรงไหน และจะไม่ให้เกิดซ้ำได้อย่างไร

## ขั้นตอน

1. **อ่านข้อมูลดิบทั้งหมด** (log แชต, ticket, โน้ต) — ถ้าผู้ใช้ไม่ให้มา ให้ถามหา อย่าแต่งเหตุการณ์เอง
2. **เรียง timeline** เป็นตาราง เวลา | เกิดอะไร | หมายเหตุ เริ่มจากเหตุตั้งต้น (เช่น config ปีก่อน) ไม่ใช่แค่ตอนล่ม ระบุจุด เริ่มเหตุ / รู้เหตุ / กลับมาใช้ได้ / ปิดผลกระทบข้อมูล แล้วคำนวณ time to detect / diagnose / mitigate / resolve เอง (ตรวจเลขให้ตรงกับ log)
3. **วัดผลกระทบ** เป็นตัวเลข: นาทีที่ใช้ไม่ได้, รายการเสีย/ค้าง, เงิน, สายเข้า, SLA ผ่านหรือไม่ และใครรู้ก่อน (เราหรือลูกค้า)
4. **หาต้นเหตุ** — แยก trigger ออกจาก root cause ถาม "ทำไม" อย่างน้อย 5 ชั้นจนถึงระดับกระบวนการ/ระบบ เขียนต้นเหตุสรุป 1–2 ประโยค แล้วแยก "ปัจจัยร่วม"
5. **ไปได้ดี / ไปได้ไม่ดี / โชคช่วย** — "โชคช่วย" คือความเสี่ยงที่รอดมาได้ ต้องเขียนเสมอ
6. **Action items** — ทุกข้อผูกกับต้นเหตุหรือปัจจัยร่วม มีลำดับ P1–P3, เจ้าของเป็นทีม/บทบาท, กำหนด, สถานะ ถ้าไม่รู้สถานะให้เขียนว่า "ยังไม่ยืนยัน" ห้ามเดา
7. **คำถามที่ยังเปิด** — TODO ที่ไม่มีใครตอบใน log ให้ยกขึ้นมาบนสุดของ action items ถ้าเลยกำหนดแล้ว
8. **ตรวจก่อนส่ง** ตาม checklist ด้านล่าง แล้วบันทึกไฟล์ `postmortem-<YYYY-MM-DD>-<ลูกค้า>-<ระบบ>.md`

## กติกาไม่โทษคน (สำคัญที่สุด)

- อ้างถึงคนด้วย **บทบาท** (On-call DevOps, Dev, Sales, Comms) ไม่ใช้ชื่อ — แม้ log จะมีชื่อ
- ห้ามตอบคำถาม "ใครเป็นคนทำ" — เปลี่ยนเป็น "กระบวนการไหนปล่อยให้ทำแบบนั้นได้"
- คำต้องห้ามและวิธีเขียนแทน ดู [references/blameless-writing.md](references/blameless-writing.md)

## Checklist ก่อนส่ง

- [ ] ไม่มีชื่อคนในเนื้อหา (ยกเว้นผู้เขียน/ผู้รีวิวในหัวเอกสาร)
- [ ] ตัวเลขใน timeline, ผลกระทบ และ TL;DR ตรงกัน
- [ ] action item ทุกข้อชี้กลับไปที่ต้นเหตุได้ และมีเจ้าของเป็นทีม
- [ ] ไม่มีข้อมูลส่วนบุคคลตามนโยบายข้อมูลลูกค้า (ถ้าจะส่งให้ลูกค้า ใช้ skill `customer-data-policy` ตรวจซ้ำ)
- [ ] ระบุ Sev และเทียบ SLA ตามเกณฑ์บริษัท
