# รีวิวโค้ดตามมาตรฐานทีม (coding-standard)

เรื่องเดียว: **ตรวจโค้ดเทียบ coding-rules 10 ข้อ แล้วให้คะแนน** — ไม่ขึ้นโครงโปรเจกต์ (นั่นคือ `project-scaffold`) ไม่ทดสอบเว็บ (นั่นคือ `test-from-plan`)
ความรู้ที่ต้องใช้อยู่ใน `references/` ครบ ไม่ต้องเข้าถึง company-kit:
- `references/coding-rules.md` — กติกา 10 ข้อ + สิ่งที่ต้องมองหา (สรุปจาก `company-kit/coding-rules.md` v2026.2)
- `references/known-bugs.md` — บั๊กจริงที่ทำให้เกิดกติกาบางข้อ (token ShopDee 2025, webhook ซ้ำ BaanRai 2026) + โครงโฟลเดอร์มาตรฐาน + ตัวแปร `.env.example`
- `references/review-template.md` — รูปแบบผลรีวิวที่ต้องส่ง

## ขั้นตอน

1. **หาของที่จะรีวิว** — diff / PR / ไฟล์ / โฟลเดอร์ที่ผู้ใช้ชี้ (ถ้าเป็น repo git: `git diff <base>...HEAD`) อ่าน description ของ PR ด้วย (มักบอก coverage และสิ่งที่ "จะทำ PR หน้า")
   - ไม่มีโค้ดให้รีวิว → ถามผู้ใช้ก่อน อย่าเดาโค้ด
2. **อ่าน `references/coding-rules.md`** แล้วไล่ทีละข้อ 1→10 กับ **ทุกไฟล์ที่ PR แตะ** (ไม่หักคะแนนจากโค้ดเก่าที่ PR ไม่ได้แตะ — ถ้าเห็นให้จดเป็น "นอก PR")
   - ทุกข้อต้องมีหลักฐาน `ไฟล์:บรรทัด/จุด` ทั้งตอน ✅ และ ❌ ห้ามให้ผ่านเพราะ "ไม่เห็นปัญหา" โดยไม่ได้ดูจริง
   - ข้อที่ PR ไม่เกี่ยวเลย (เช่นไม่มี migration) = ✅ พร้อมเขียน "ไม่เกี่ยวกับ PR นี้"
   - ข้อใดผิดแม้จุดเดียว = ❌ ทั้งข้อ (ไม่มีครึ่งคะแนน) · จุดเดียวผิดสองข้อ (เช่น env ไม่ผ่าน Zod = ข้อ 3 และ 5) หักทั้งสองข้อ
   - วัด coverage ไม่ได้ → ใช้ตัวเลขจาก CI/description และระบุที่มา ถ้าไม่มีเลยให้เขียน "ยืนยันไม่ได้" และขอ report
3. **เทียบกับบั๊กจริงใน `references/known-bugs.md`** — ถ้าโค้ดแตะ auth / token / payment / webhook ต้องเช็กทุกจุดในนั้น และอ้างชื่อเหตุการณ์ในคอมเมนต์ (คนแก้จะเข้าใจว่าทำไมสำคัญ)
4. **สรุปคะแนน** `coding-rules: x/10` → ≥ 8 = ✅ merge ได้ · < 8 = ❌ request changes
   - ข้อ 5 / 9 / 10 (ความลับ, token, webhook เงิน) ที่ ❌ ให้อยู่บนสุดของรายการ "ต้องแก้" เสมอ แม้คะแนนรวมจะ ≥ 8
5. **เขียนผลตาม `references/review-template.md`** — กล่องคะแนน, ตารางรายข้อ, ต้องแก้ (บอกวิธีแก้ที่ทำได้จริง ไม่ใช่แค่ "ผิด"), คำชม, คอมเมนต์สั้นพร้อมโพสต์
   - บันทึกเป็นไฟล์ `review-<PR>.md` ในโฟลเดอร์ที่ผู้ใช้ทำงาน (ถ้าไม่บอก) และแสดงกล่องคะแนนในแชต

## โหมด "เขียนให้ตรงสไตล์ทีม"
ผู้ใช้ขอให้แก้/เขียนโค้ด → เขียนตาม 10 ข้อตั้งแต่แรก แล้วรันขั้น 2–4 กับโค้ดที่ตัวเองเขียนก่อนส่ง ต้องได้ 10/10 (หรือบอกข้อที่ยังทำไม่ได้พร้อมเหตุผล)

## ห้าม
- ห้ามแก้โค้ดของ PR เองระหว่างรีวิว เว้นแต่ผู้ใช้สั่ง
- ห้ามคัดลอกค่า secret / ข้อมูลส่วนตัวที่เจอในโค้ดลงผลรีวิว — อ้างแค่ตำแหน่ง (`service.ts: fallback secret`)
- ห้ามเพิ่มกติกาที่ไม่มีใน 10 ข้อแล้วนับเป็นคะแนน — ข้อเสนออื่นใส่หัวข้อ "แนะนำ" ได้แต่ไม่หักคะแนน
