# Checklist ขึ้นระบบจริง (deploy-checklist)

ย่อ runbook ฉบับยาวให้เป็น checklist ของ **รอบปล่อยงานรอบเดียว** ที่ติ๊กได้จริง และไม่ทิ้งขั้นสำคัญ
ความรู้ของบริษัทที่ต้องใช้สรุปไว้แล้วใน `references/` — ไม่ต้องมี company-kit ในเครื่อง

## อินพุต

- ชื่อรอบ/เวอร์ชัน (เช่น `2026.11`) — ถ้าไม่บอก ให้ถาม
- ถ้ามี: release notes, ระบบ/ลูกค้า, migration, feature flag, downtime, ชื่อคน 3 บทบาท
- ข้อมูลที่ไม่มี **ห้ามเดา** ให้ใส่ `[ ___ ]` และยกไปไว้ในหัวข้อ "จุดที่ต้องตัดสินใจ"

## ขั้นตอน

1. อ่าน `references/runbook-essentials.md` (ขั้นตอน 6 หมวด + เกณฑ์ตัวเลข) และ `references/lessons-and-data-rules.md` (บทเรียน incident + กติกาประกาศลูกค้า)
2. **คำนวณวัน deploy** จากวันนี้:
   - นับ 3 วันทำการถัดจากวันส่งประกาศลูกค้า → วันถัดไปที่เป็นอังคาร–พฤหัส คือวันเร็วสุด
   - ตัดวันศุกร์, ก่อนวันหยุดยาว, และวันที่ 25–สิ้นเดือนถ้าเป็นลูกค้าธนาคาร
   - เขียนเหตุผลการเลือกวันสั้น ๆ + วันสำรอง
   - ผู้ใช้บอก "คืนนี้" แต่ประกาศลูกค้ายังไม่ออกครบ 3 วันทำการ → **เตือนว่าผิด SLA** (ยกเว้น hotfix Sev 1)
3. เขียน checklist ตาม `assets/checklist-template.md` — คงลำดับ 6 หมวดและตัวเลขเกณฑ์ไว้ครบ เติมค่าที่รู้ ที่ไม่รู้ใส่ `[ ___ ]`
4. หมวด rollback ต้องมี: เกณฑ์ตัดสิน 3 ข้อ · ลำดับ flag → image เดิม → restore snapshot (ต้อง deploy lead + หัวหน้าทีม dev ตกลงร่วมกัน) → แจ้งลูกค้าใน 30 นาที
   - ผู้ใช้ขอแค่ "แผน rollback" → ทำเฉพาะหมวด 2.3–2.4 (สิ่งที่ต้องจดไว้) + หมวด 5
5. ตรวจตัวเองก่อนส่ง:
   - [ ] ครบ 4 เรื่องที่ห้ามลืม: **backup snapshot · migration dry-run/ย้อนกลับได้ · rollback · แจ้งลูกค้า (ก่อน/ระหว่างถอย/หลังเสร็จ)**
   - [ ] มีเช็ก TLS cert > 21 วัน รวมโดเมนย่อย api/webhook/payment
   - [ ] ประกาศลูกค้าไม่มีเบอร์มือถือส่วนตัว (ใช้เบอร์ on-call กลาง)
   - [ ] 3 บทบาท คนเดียวถือไม่เกิน 2
6. บันทึกไฟล์ที่ `work/deploy-checklist-<รอบ>.md` (หรือที่ผู้ใช้กำหนด) แล้วสรุป: วันที่เสนอ + เหตุผล, จุดที่ต้องตัดสินใจ, ความเสี่ยงที่เห็น

## ส่งต่อ

- ก่อนหน้า: ผลทดสอบ `test-from-plan` (ปล่อยได้ไหม) และ `tech-risk-review` ของ CTO ถ้ามี — ถ้าคำตัดสินคือ "ไม่ควรปล่อย" ให้แจ้งก่อนทำ checklist
- ถัดไป: ถ้าเกิดเหตุหลัง deploy → `postmortem` ภายใน 3 วันทำการ
- เนื้อหาที่ส่งลูกค้า → ใช้กติกา `customer-data-policy` (สรุปใน references)
