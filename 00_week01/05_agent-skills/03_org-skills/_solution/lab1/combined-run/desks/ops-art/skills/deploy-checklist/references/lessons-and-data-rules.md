# บทเรียน incident + กติกาข้อมูลลูกค้าที่เกี่ยวกับการ deploy

## บทเรียนจาก incident 2026-09-18 (payment ล่ม 47 นาที)
สรุปจาก `company-kit/incident-2026-09.md`

- ต้นเหตุ: TLS cert ของโดเมนย่อย payment proxy (`api.pay...`) ที่ **upload มือ** (OV cert ที่ลูกค้าซื้อเอง) หมดอายุ — ตัวอื่น auto-renew หมด
- ไม่มี alert เพราะ uptime check ยิงแค่หน้า www และไม่มี alert วันหมดอายุ cert · ลูกค้ารู้ก่อนเรา 9 นาที
- webhook ก็ผ่านโดเมนเดียวกัน → มี order ตัดเงินแล้วแต่สถานะไม่อัปเดต ต้อง reconcile (idempotency ช่วยกันซ้ำ)
- reminder ต่อ cert อยู่ในปฏิทินส่วนตัวของคนที่ลาออก → หายไปด้วย

**ใช้ใน checklist:**
- เช็ก cert > 21 วัน **ทุกโดเมนที่เกี่ยวข้อง รวมโดเมนย่อย api / webhook / payment** ไม่ใช่แค่ www
- ไล่ดูรายการ cert ที่ upload มือ (ตอน incident มี 4 ตัว) ว่าตัวไหนใกล้หมด · รายการ cert ควรอยู่ในไฟล์กลาง ไม่ใช่ปฏิทินคน
- smoke test ต้องรวม webhook และ flow จ่ายเงิน (ถ้าระบบมี)

## กติกาประกาศ/อีเมลถึงลูกค้า
สรุปจาก `company-kit/customer-data-policy.md` v1.4 (ผู้ดูแล `plat-may`, skill `customer-data-policy`)

- ห้ามใส่ **เบอร์มือถือส่วนตัว** ของใครก็ตามในเอกสารที่ส่งออก (ทั้งคนของเราและพนักงานลูกค้า) → ใช้เบอร์ on-call กลาง / อีเมลบริษัท
- ห้ามเลขบัตรประชาชน, เลขบัญชี/เลขบัตร, ชื่อลูกค้าปลายทาง (ใช้รหัสเคสแทน) — ถ้าต้องอ้างจริงให้ mask เช่น `081-XXX-4567`, `4111 XXXX XXXX 1234` · ไม่จำเป็น → ตัดทิ้ง
- screenshot dashboard/log ที่แนบให้ลูกค้าต้องเบลอข้อมูลข้างต้น
- staging ที่ใช้ dry-run ต้องเป็นข้อมูลปิดบัง/สังเคราะห์ ห้ามคัดลอก DB จริงมาเครื่องตัวเอง
- สงสัยข้อมูลรั่ว (ส่งผิดคน) → แจ้ง `plat-may` ภายใน 1 ชั่วโมง

## หัวข้อที่ประกาศ maintenance ต้องมี (แม่แบบ `NOTICE-maintenance`)
วัน · เวลา · ผลกระทบ (มี downtime ไหม กี่นาที) · ช่องทางติดต่อ (เบอร์ on-call กลาง)
> ตัวแม่แบบฉบับเต็มไม่อยู่ใน company-kit — ถ้าไม่มีในมือ ให้ร่างตาม 4 หัวข้อนี้
