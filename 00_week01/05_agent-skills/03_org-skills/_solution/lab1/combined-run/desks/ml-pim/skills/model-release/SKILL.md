# model-release — แผนปล่อยโมเดลพร้อมเกณฑ์ถอยกลับ

ผลลัพธ์: ไฟล์ Markdown 1 ไฟล์ `work/<model>-<run>-release-plan.md` ตามโครงใน `references/release-plan-template.md`

## ขั้นตอน

1. **หาข้อมูลเข้า** — ผลการทดลอง (csv/MLflow), โน้ตของคนเทรน, โมเดลที่รันอยู่ใน production ตอนนี้, เกณฑ์ความแม่นยำของลูกค้า/TOR
   ถ้าเป็นโมเดลพยากรณ์คิวของโนวาเทค ดูสรุปใน `references/queue-forecast-context.md` ก่อน แล้วค่อยเปิดไฟล์ต้นทางถ้ามีในเครื่อง
2. **อ่านตารางผลแบบจับผิด** — ก่อนเชื่อว่ารอบใหม่ดีกว่า เช็กว่าแต่ละรอบใช้ data version / จำนวนหน่วย (สาขา) / test period เดียวกันไหม, fix seed ไหม, artifact อยู่ที่ไหน ทำซ้ำได้ไหม ถ้าไม่เท่ากันให้ตั้งเป็น gate "เทียบแบบแฟร์" (ใช้ skill `mlflow-experiment` ถ้ามี)
3. **ตั้ง gate ก่อน shadow** — อย่างน้อย: เทียบแฟร์, ลงทะเบียน artifact ให้ทำซ้ำได้, มี monitoring รายวันที่คำนวณทั้งโมเดลใหม่และโมเดลเดิมคู่กัน, backtest แยก segment ที่เป็นจุดอ่อนที่รู้แล้ว
4. **วางไทม์ไลน์** shadow → go/no-go → go-live → hypercare ตาม `references/deploy-rules.md` (วัน/เวลาห้าม deploy, แจ้งลูกค้า ≥ 3 วันทำการ, UAT sign-off) ให้ shadow ครอบคลุมช่วงที่โมเดลใหม่อ้างว่าดีขึ้น (เช่น payday) เปิดปฏิทินจริงเช็กวันในสัปดาห์และวันหยุดเสมอ
5. **เขียนเกณฑ์** ตาม `references/rollback-criteria.md`: เกณฑ์ผ่าน shadow + rollback 3 ระดับ (A ทันที / B ความแม่นยำ / C เฝ้าระวัง) ทุกข้อต้องมีตัวเลข ช่วงเวลา ใครตัดสิน และ **เทียบกับโมเดลเดิมที่รันคู่** เสมอ
6. **วิธีถอยกลับ** — ให้โมเดลเดิมรันคู่ต่อช่วง hypercare แล้วถอยด้วย flag/config ก่อน ค่อย image tag เดิม restore DB เป็นทางสุดท้าย
7. **ขอบเขต + ความเสี่ยงที่เหลือ + ใครต้องยืนยันอะไร** แล้วปิดท้ายด้วยรายการ "จุดที่ต้องตัดสินใจ" ให้ผู้ใช้

## กติกา

- ห้ามแต่งตัวเลขที่ไม่มีในข้อมูล ถ้าขาด (เช่น bias ของโมเดลเดิมใน segment) ให้ตั้งเป็นงานใน gate
- ห้ามถอยกลับเพราะข้อมูลเข้าเสีย — แยกปัญหาข้อมูลออกจากปัญหาโมเดล
- ไม่ใส่ข้อมูลส่วนบุคคล (เบอร์มือถือ ชื่อลูกค้าปลายทาง) ลงแผน ใช้ช่องทาง on-call กลาง
- Verifier ต้องไม่ใช่คนที่เทรนโมเดลนั้น
- แผนเป็น "ร่าง" จนกว่าหัวหน้าทีม ML อนุมัติ
