# กติกา deploy ที่เกี่ยวกับการปล่อยโมเดล (สรุปจาก company-kit/deploy-runbook.md)

> ต้นทาง: runbook ทีม DevOps ผู้ดูแล `ops-art` ปรับปรุง 2026-10-01 · สรุป ณ 2026-11-04 · ถ้าต้นทางใหม่กว่านี้ให้ยึดต้นทาง

## บทบาท (คนเดียวห้ามถือเกิน 2)
- **Deploy lead** กดปุ่ม ตัดสินใจ rollback · **Verifier** ทำ smoke test (ต้องไม่ใช่คนทำงานนั้นเอง) · **Comms** คุยลูกค้า + อัปเดตช่อง `#deploy`

## ช่วงเวลา
- ปกติ อังคาร–พฤหัส 21:00–23:00
- ห้าม: วันศุกร์ · ก่อนวันหยุดยาว · **วันที่ 25–สิ้นเดือน สำหรับลูกค้าธนาคาร** (เงินเดือนออก) — ยกเว้น hotfix Sev 1

## ก่อน deploy (T−3 ถึง T−1 วัน)
- Release notes (ticket, migration, flag, ความเสี่ยง)
- UAT + ลูกค้าเซ็นรับเป็นลายลักษณ์อักษร (อีเมลได้) — ไม่มี = ไม่ deploy
- แจ้งลูกค้า ≥ 3 วันทำการ แม่แบบ `NOTICE-maintenance` ใช้เบอร์ on-call กลาง ห้ามเบอร์มือถือส่วนตัว
- Migration dry-run บน staging ขนาดใกล้จริง, ต้องย้อนกลับได้หรือเป็น expand-only, > 5 นาทีต้องแยกรอบ
- ของเสี่ยงอยู่หลัง feature flag ปิดไว้ก่อน
- จอง on-call 2 ชม. หลัง deploy + เช้าวันถัดไป 08:00–10:00

## T−30 นาที
- โพสต์ `#deploy` (เวอร์ชัน, release notes, 3 บทบาท) · ระบบป่วยอยู่ → เลื่อน
- snapshot DB + เช็ก `available` + จดชื่อ · จด image tag ปัจจุบัน
- ปิด cron/batch ที่ชนกับ migration (ระบุตัวอย่าง: **batch พยากรณ์รอบคืน**) แล้วเปิดคืนหลังเสร็จ

## Smoke test (ภายใน 15 นาที)
- flow หลัก 1 รอบ · error rate < 1% · latency p95 ไม่แย่กว่าเดิม > 20% · เปิด flag ทีละตัวแล้วทดสอบซ้ำ

## Rollback ของ runbook
- ทันทีถ้า: smoke test ไม่ผ่านและแก้ไม่ได้ใน 15 นาที · error rate > 5% นาน 5 นาที · ข้อมูลผิดแม้รายการเดียว
- ลำดับ: ปิด flag → deploy image tag เดิม → restore snapshot (deploy lead + หัวหน้าทีม dev ต้องตกลงร่วม) → แจ้งลูกค้าภายใน 30 นาที

## หลัง deploy
- แจ้งลูกค้าเป็นภาษาผู้ใช้ · เปิด batch คืน · on-call · เกิดเหตุ → postmortem ภายใน 3 วันทำการ · tag release + CHANGELOG

## สิ่งที่ runbook ไม่ได้พูดถึง (ต้องเติมเองในแผนโมเดล)
- shadow mode, เกณฑ์ความแม่นยำ, การรันโมเดลเดิมคู่, rollback ที่เกิดหลายวัน/สัปดาห์หลัง deploy → ดู `rollback-criteria.md`
