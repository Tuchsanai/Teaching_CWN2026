## 1. สรุปสั้น (TL;DR)

- r03 ดีกว่า v1 ที่ใช้อยู่มาก: MAPE ภาพรวม 31.5 → 15.2 · วันเงินเดือนออก 44.2 → 17.4 · สัปดาห์มีวันหยุด 52.8 → 19.6 (ตรงจุดที่ผู้จัดการสาขาบ่น)
- **แต่ยังปล่อยทันทีไม่ได้** มี gate ที่ต้องปิดก่อน 4 ข้อ: (G1) เทียบแบบแฟร์บนข้อมูลชุดเดียวกัน (G2) ลง MLflow ให้ทำซ้ำได้ (G3) มี monitoring รายวัน (G4) เช็กจุดอ่อนช่วงเที่ยงกับสาขาใหม่
- แผน: ปิด gate → **shadow 3 สัปดาห์ (11–30 พ.ย. ครอบคลุมช่วงเงินเดือนออก 25–30 พ.ย.)** → go/no-go 30 พ.ย. → **go-live อังคาร 1 ธ.ค. 2026 21:00** → เฝ้าดู 4 สัปดาห์ โดยเก็บ v1 รันคู่ไว้เพื่อถอยกลับได้ในไม่กี่นาที
- ถอยกลับ = สลับ dashboard กลับไปใช้ v1 (เปลี่ยน config/flag ไม่ต้อง restore ฐานข้อมูล)

**ข้อควรระวังในการอ่านตาราง**
1. r03 ใช้ข้อมูลคนละชุดกับ r01/r02 (v4: ลบแถวซ้ำ ~1.2%, ตัดสาขา 017/033 ที่ปิดปรับปรุง ส.ค.–ก.ย., เพิ่มตารางวันหยุด) — สาขาที่ปิดปรับปรุงอยู่ใน test period ของ r01/r02 จึงอาจทำให้ error ของสองรอบนั้นสูงเกินจริง → **ยังสรุปไม่ได้ว่าดีขึ้นเพราะ feature หรือเพราะข้อมูลสะอาดขึ้น**
2. ไม่ได้ fix seed, ผลการ tune `num_leaves` ไม่ได้จด, โมเดลอยู่ใน notebook บนเครื่องต้า + `model_r03.txt` ใน drive → ยังไม่มีหลักฐานว่าทำซ้ำได้
3. ช่วง 11:00–13:00 สาขาย่านออฟฟิศพยากรณ์ **ต่ำกว่าจริง −20 ถึง −30%** (อันตรายกว่าพยากรณ์เกิน เพราะสาขาจัดคนไม่พอ)
4. สาขาเปิดใหม่ < 8 สัปดาห์ไม่มี lag → fallback ค่าเฉลี่ยสาขาขนาดเดียวกัน
5. ยังไม่มี monitoring ใด ๆ แม้ข้อมูลใหม่เข้าทุกคืน

## 5. เกณฑ์ (ทั้งก่อนและหลัง go-live)

นิยาม: MAPE คิดบนชั่วโมงที่สาขาเปิด 08:30–15:30 ของ 38 สาขา · bias = (Σพยากรณ์ − Σจริง) / Σจริง (ติดลบ = พยากรณ์ต่ำ) · "สาขาออฟฟิศ" = รายชื่อที่ตกลงใน G4 · ทุกตัวคำนวณจาก job G3 หลังข้อมูลจริงเข้าทุกคืน

### 5.1 เกณฑ์ผ่าน shadow → go-live (ต้องครบทุกข้อ)

| # | เกณฑ์ |
|---|---|
| S1 | MAPE รายสัปดาห์ของ r03 ≤ 20% ทุกสัปดาห์ของ shadow และดีกว่า v1 ในสัปดาห์เดียวกันทุกสัปดาห์ |
| S2 | MAPE ช่วง payday 25–30 พ.ย. ของ r03 ≤ 22% และดีกว่า v1 ในช่วงเดียวกัน |
| S3 | bias ช่วง 11:00–13:00 สาขาออฟฟิศ ไม่แย่กว่า −30% (เฉลี่ยรายสัปดาห์) และไม่แย่กว่า v1 |
| S4 | batch คืนของ r03 สำเร็จทุกคืน ไม่มีค่าพยากรณ์ติดลบ/ว่าง/NaN |

**ระดับ A — ถอยกลับทันที (deploy lead คืน go-live / on-call หลังจากนั้น ตัดสินได้เลย ไม่ต้องรอประชุม)**

| # | เหตุ |
|---|---|
| R-A1 | batch r03 ล้ม หรือพยากรณ์วันถัดไปไม่ครบทุกสาขาภายใน 06:00 (ก่อนสาขาจัดคน) และแก้ไม่ได้ใน 30 นาที |
| R-A2 | ค่าพยากรณ์ผิดรูปแม้ 1 รายการ: ติดลบ, ว่าง, NaN, หรือ > 3 เท่าของค่าสูงสุดในอดีตของสาขา-ชั่วโมงนั้น (เทียบ runbook "ข้อมูลผิดแม้รายการเดียว") |
| R-A3 | dashboard สาขา error/โหลดไม่ขึ้นหลังสลับโมเดล (smoke test ไม่ผ่าน และแก้ไม่ได้ใน 15 นาที ตาม runbook §5) |

**ระดับ B — ถอยกลับเมื่อความแม่นยำแย่ลง (ml-pim เสนอ, ml-jay อนุมัติ ภายใน 1 วันทำการ)**

| # | เหตุ | ที่มา |
|---|---|---|
| R-B1 | MAPE รายสัปดาห์ภาพรวม > 22% **สองสัปดาห์ติด** | ข้อเสนอต้า (TOR 20% + กันชน 2 จุด) |
| R-B2 | bias ช่วง 11:00–13:00 สาขาออฟฟิศ แย่กว่า −30% ทั้งสัปดาห์ **และ** แย่กว่า v1 ในสัปดาห์เดียวกัน | ข้อเสนอต้า + เงื่อนไขเทียบ v1 (ถ้า v1 ก็พลาดเท่ากัน ถอยกลับไม่ช่วย) |
| R-B3 | MAPE รายสัปดาห์ของ r03 แย่กว่า v1 (ที่รันคู่) ในสัปดาห์เดียวกัน | โมเดลใหม่ต้องไม่แพ้ของเดิม |
| R-B4 | MAPE ช่วง payday หรือสัปดาห์มีวันหยุด > 25% และแย่กว่า v1 | จุดขายหลักของ r03 |

**ระดับ C — เฝ้าระวัง (ไม่ถอยกลับ แต่สืบสาเหตุ + บันทึก)**

- MAPE รายสัปดาห์ 20–22% (สัปดาห์เดียว) · ข้อมูลจริงขาด > 5% หรือแถวซ้ำ > 2% ในคืนใดคืนหนึ่ง (อาจเป็นปัญหาข้อมูล ไม่ใช่โมเดล — **ห้ามถอยกลับเพราะข้อมูลเสีย** ให้แก้ข้อมูลก่อน) · สาขาร้องเรียนจัดคนไม่พอ ≥ 3 สาขาในสัปดาห์เดียว · สาขาใหม่ที่ใช้ fallback MAPE > 30%

### 5.3 วิธีถอยกลับ (ลำดับตาม runbook §5 ปรับให้เข้ากับโมเดล)

1. สลับ flag/config `forecast_model` ของ dashboard จาก `r03` → `v1` (เร็วสุด เพราะ v1 ยังรันคู่อยู่และมีพยากรณ์ของวันถัดไปพร้อม)
2. ถ้า flag ใช้ไม่ได้ → deploy image tag เดิมที่จดไว้ก่อน go-live
3. ไม่ต้อง restore snapshot เว้นแต่มีการเปลี่ยน schema ที่โค้ดเก่าใช้ไม่ได้ (ถ้าต้อง restore: deploy lead + หัวหน้าทีม dev ต้องตกลงร่วมกัน)
4. Comms แจ้งผู้ประสานงานธนาคารภายใน 30 นาที: ถอยกลับแล้ว ผลกระทบคือ dashboard กลับไปใช้ตัวเลขแบบเดิม
5. ถ้าถอยกลับจากระดับ A หรือ B → เขียน postmortem ภายใน 3 วันทำการ (skill `postmortem` ของ ops-fon) และ r03 ต้องเริ่มแผนนี้ใหม่ตั้งแต่ shadow

## 6. คืน go-live (อ. 1 ธ.ค.) — ส่วนที่ต่างจาก deploy ปกติ

**บทบาท** (คนเดียวห้ามถือเกิน 2): Deploy lead = ops-art (หรือที่ DevOps มอบหมาย) · Verifier = ml-jay (ไม่ได้เป็นคนเทรน r03) · Comms = ผู้ดูแลลูกค้าเกษตรไทย · ml-pim = เจ้าของโมเดล อยู่ใน bridge call

**T−30 นาที**: โพสต์ `#deploy` (เวอร์ชัน r03 / MLflow run id / release notes / 3 บทบาท) · ดู dashboard ปกติ · snapshot DB + จดชื่อ · จด image tag ปัจจุบัน + ค่า flag `forecast_model=v1` · **พักเฉพาะ batch พยากรณ์คืนถ้าเวลาชนกับช่วง deploy** แล้วเปิดคืนหลังเสร็จ

**Deploy**: ไม่มี migration ที่คาดไว้ (ตารางผล shadow สร้างตั้งแต่ 11 พ.ย.) · สลับ flag `forecast_model=r03` · ไม่มี downtime

**Smoke test (Verifier ภายใน 15 นาที)**:
1. dashboard ของ 3 สาขาตัวอย่าง (สาขาใหญ่, สาขาออฟฟิศ, สาขาเล็ก) แสดงพยากรณ์ 7 วันจาก r03 ครบทุกชั่วโมง 08:30–15:30
2. ค่าที่แสดงตรงกับตาราง shadow ของวันเดียวกัน
3. ไม่มีค่าติดลบ/ว่าง · error rate < 1% · latency p95 ไม่แย่กว่าก่อน deploy เกิน 20%
4. สาขา 017 / 033 ยังแสดง v1 (ดูข้อ 7)

**หลัง deploy**: แจ้งลูกค้าว่าเสร็จ (ภาษาผู้ใช้: "ตัวเลขพยากรณ์วันเงินเดือนออกและวันหยุดแม่นขึ้น") · on-call 2 ชม. + เช้า 2 ธ.ค. 08:00–10:00 · tag release

## 7. ขอบเขตที่ไม่รวมในรอบนี้
