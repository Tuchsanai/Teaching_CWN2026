# TOR → spec + แผนทดสอบ (req-to-spec)

ผลลัพธ์ 2 ไฟล์ในโฟลเดอร์งานของผู้ใช้ (ค่าเริ่มต้น `work/`):
- `<deal>-spec.md` — ตามโครง `references/spec-template.md`
- `<deal>-test-plan.md` — ตามโครง `references/test-plan-template.md` (ตารางอ่านได้ด้วย `test-from-plan`)

ความรู้บริษัทที่ต้องใช้ **อยู่ใน references/ แล้ว** ไม่ต้องเปิด company-kit:
- `references/novatech-standards.md` — มาตรฐานสถาปัตยกรรม v4 + นโยบายข้อมูลลูกค้า v1.4 แบบย่อ
- `references/forgotten-topics.md` — หัวข้อที่ลูกค้ามักไม่เขียนใน TOR แต่จะถามทีหลัง

## ขั้นตอน

1. **อ่าน TOR ทั้งฉบับ** จดเลขหัวข้อ วันยื่น งบ ระยะเวลา ถ้าไม่มี TOR หรือไฟล์ไม่ครบ → ถามผู้ใช้ อย่าเดา
2. **แตก requirement** ทีละหัวข้อ TOR เป็นแถวในตาราง
   - รหัส `FR-<โมดูล>-NN` / `NFR-<หมวด>-NN` (โมดูลตั้งชื่อตามโดเมนเป็นคำนามเอกพจน์ เช่น `booking`, `branch`)
   - ทุกแถวมี **เกณฑ์ยอมรับที่วัดได้** + ระดับ Must/Should/Could + ป้ายที่มา `[TOR x.y]` / `[สมมติฐาน]` / `[มาตรฐาน]`
   - ประโยคเดียวใน TOR ที่มีหลายเรื่อง → แยกแถว (เช่น "จอง/เลื่อน/ยกเลิก" = 3 แถว)
3. **ไล่ checklist `forgotten-topics.md` ทุกข้อ** — ข้อที่ TOR ไม่พูดถึง ให้ (ก) ใส่สมมติฐานที่สมเหตุสมผลในแถว requirement และ (ข) เพิ่มคำถาม `Q-NN` ในหัวข้อคำถามถึงลูกค้า โยงกลับรหัส requirement
4. **หาจุดที่ TOR ขัดกันเอง / เป็นไปไม่ได้ / วัดไม่ได้** (เช่น บังคับยืนยันตัวตนกับระบบลูกค้าเดิม แต่มีบริการสำหรับคนที่ยังไม่เป็นลูกค้า, เกณฑ์ ML ที่ไม่บอกระดับการวัด, ข้อมูลมาหลังเซ็นสัญญา) → หัวข้อความเสี่ยง + คำถาม
5. **ผูกกับมาตรฐานบริษัท** (`novatech-standards.md`) ในหัวข้อ "ขอบเขตสถาปัตยกรรม" แค่ระดับชิ้นส่วน (monolith + service ที่ต้องแยกตามเกณฑ์ + ชื่อ) — รายละเอียดแผนภาพเป็นงานของ `arch-template`
6. **เขียนแผนทดสอบ**: ทุก requirement Must มี test อย่างน้อย 1 ข้อ, P1 = Must ที่กระทบเงิน/ข้อมูลลูกค้า/ความปลอดภัย/ข้อสัญญา · รหัส test รูปแบบ `XX-NN` (เช่น `BK-01`) · มีเกณฑ์เริ่ม/ผ่าน
7. **ตรวจก่อนส่ง** (ทำจริง ไม่ใช่ข้าม)
   - ตาราง traceability: ทุกหัวข้อ TOR โยงถึง requirement, ทุก requirement Must โยงถึง test
   - `grep` หาเบอร์มือถือ/เลขบัตร/เลขบัญชีในไฟล์ผลลัพธ์ → ต้องไม่มี (ข้อมูลติดต่อใน TOR ห้ามคัดลอก, ดูกติกาข้อมูลใน `novatech-standards.md`) ถ้ามี skill `customer-data-policy` ให้ใช้ตรวจซ้ำ
   - แผนทดสอบห้ามมี URL ตัวอย่าง/ปลอม (`test-from-plan` จะหยิบ URL แรกเป็นเว็บที่ทดสอบ) ใส่ `_รอกำหนด_` แทน
8. **สรุปให้ผู้ใช้**: จำนวน requirement/test, คำถามที่ต้องได้คำตอบก่อนยื่นราคา (ข้อที่กระทบราคาหรือเกณฑ์รับงาน) และสมมติฐานที่ตัดสินเอง

## กติกา

- ห้ามแต่ง requirement ที่ TOR ไม่มีแล้วติดป้ายว่า `[TOR]` — ของที่เติมเองต้องเป็น `[สมมติฐาน]` + มี `Q-NN` เสมอ
- ตัวเลขที่ TOR ไม่ให้ (โหลด, RPO/RTO, เวลาแจ้งเตือน) ใส่ค่าเสนอได้ แต่ต้องเป็นสมมติฐาน
- เป้าหมายธุรกิจที่ระบบควบคุมไม่ได้คนเดียว (เช่น "ลดเวลารอ 30%") → เสนอเป็น KPI ติดตาม ไม่ใช่เงื่อนไขรับงาน และบอกผู้ใช้
- เอกสารเป็นภาษาไทย ศัพท์เทคนิคใช้อังกฤษได้
