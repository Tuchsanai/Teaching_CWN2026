## 1. บทสรุปผู้บริหาร

เราเสนอระบบจองคิวสาขาผ่านเว็บและ LINE OA พร้อมโมเดลพยากรณ์คิวล่วงหน้า 7 วัน สำหรับ 120 สาขา ในราคา **4,792,000 บาท (ไม่รวม VAT)** ภายในวงเงินที่ธนาคารกำหนด รวมค่าพัฒนา, hosting ปีแรก และบำรุงรักษาปีแรก

- **ปัญหา:** ลูกค้ารอคิวเฉลี่ย 38 นาที (สูงสุด 95 นาทีช่วงวันที่ 25–5 ของเดือน) และสาขาจัดพนักงานไม่ตรงกับช่วงที่คนมาก
- **สิ่งที่เสนอ:** ลูกค้าจอง/เลื่อน/ยกเลิกคิวได้เอง, walk-in เข้าคิวเดียวกันผ่านตู้เดิม, ผู้จัดการสาขาเห็นพยากรณ์รายชั่วโมงล่วงหน้า 7 วันเพื่อจัดคน
- **เป้าหมาย:** ลดเวลารอเฉลี่ยลง 30% ภายใน 6 เดือนหลังเปิดใช้ · ส่งมอบใน 6 เดือน (นำร่อง 10 สาขาเดือนที่ 5, ครบ 120 สาขาเดือนที่ 6)
- **ความเสี่ยงต่ำกว่าการสร้างใหม่ทั้งหมด:** ต่อยอดจาก booking engine ที่เราใช้งานจริงแล้วกับธนาคารและองค์กร 486 สาขา (~238,000 คิวต่อเดือน)

## 2. ความเข้าใจความต้องการ

เราสรุปความต้องการตาม TOR ดังนี้ และยืนยันว่าข้อเสนอครอบคลุมทุกข้อ (ดูตารางเทียบในข้อ 2.2)

### 2.1 ประเด็นหลักที่ธนาคารให้ความสำคัญ

- **ลูกค้า:** จองคิวได้ทั้งเว็บและ LINE OA (บัญชีทางการของธนาคารบน LINE) เลือกสาขา ประเภทบริการ และช่วงเวลา 15 นาที
- **สาขา:** เรียกคิว ย้ายช่อง บันทึกเวลาบริการจริง และปรับจำนวนช่องบริการตามผลพยากรณ์
- **ความปลอดภัยและการกำกับดูแล:** ตามแนวนโยบายความเสี่ยงด้าน IT ของ ธปท. และ PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล)
- **ความต่อเนื่องของบริการ:** uptime ≥ 99.5% และตอบรับเหตุร้ายแรง (Sev 1) ภายใน 30 นาที

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้างระบบ

- Modular monolith (Next.js + Node.js/TypeScript) แยกโมดูล booking / identity / branch / notification / kiosk / report — ดูแลง่าย ขยายสาขาได้โดยไม่ต้องเขียนใหม่
- Forecast service (Python) แยกออกมา เพราะรอบการทำงานและทรัพยากรต่างจากระบบหลัก รันเป็นงานกลางคืน เขียนผลลง PostgreSQL
- PostgreSQL (managed, HA) + Redis สำหรับล็อกช่องเวลา ป้องกันการจองซ้อน และคิวงานสำหรับการแจ้งเตือน แยกจาก request หลัก
- Hosting บน cloud ภูมิภาคประเทศไทย ขนาด Medium (4 vCPU × 3 + PostgreSQL HA + Redis) หน้าระบบมี WAF (ไฟร์วอลล์เว็บ) และป้องกัน DDoS
- Monitoring / APM (ระบบติดตามประสิทธิภาพ) และ log กลาง แจ้งเตือนทีมเมื่อระบบผิดปกติ

### 4.2 ความปลอดภัยและการปฏิบัติตามข้อกำหนด

| ข้อกำหนด TOR ข้อ 4 | การดำเนินการ |
|---|---|
| แนวนโยบาย IT risk ของ ธปท. และ PDPA | จัดทำเอกสาร data flow, การจัดประเภทข้อมูล และบันทึกกิจกรรมการประมวลผลข้อมูลส่งธนาคาร |
| TLS 1.2 ขึ้นไป / AES-256 | เข้ารหัสทุกช่องทางและทุกฐานข้อมูล, เชื่อม core banking ด้วย mTLS |
| เลขบัตรประชาชนห้ามเก็บแบบข้อความธรรมดา | ใช้เลขบัตรเพื่อค้นข้อมูลแล้วเก็บเฉพาะค่า hash แบบมี key (HMAC) และ CIF ที่เข้ารหัส ไม่เก็บเลขบัตรในฐานข้อมูลหรือ log |
| Audit log ทุกการเข้าถึงข้อมูลลูกค้า ≥ 2 ปี | บันทึกผู้เข้าถึง เวลา และรายการ แยกเก็บแบบแก้ไขไม่ได้ 2 ปี |
| Penetration test โดยผู้ทดสอบอิสระที่ธนาคารกำหนด | เตรียมสภาพแวดล้อมทดสอบ แก้ไขช่องโหว่ทุกระดับ High ขึ้นไปก่อนเปิดใช้ และทดสอบช่องโหว่ทุกรอบปล่อยงาน |
| NDA ทุกคนที่เข้าถึงข้อมูล | ทีมทุกคนลงนาม NDA ก่อนเริ่มงาน, ใช้ข้อมูลทดสอบแบบสังเคราะห์, เข้าถึงข้อมูลจริงผ่านคำขอที่ธนาคารอนุมัติเท่านั้น |

### 4.3 การดูแลโมเดลพยากรณ์หลังใช้งานจริง

- วัด MAPE รายสัปดาห์ต่อสาขาบน dashboard และเก็บทุกรุ่นของโมเดลใน model registry
- ทดลองแบบ shadow mode (โมเดลรันคู่ แต่ยังไม่แสดงให้สาขา) 2 สัปดาห์ก่อนเปิดให้สาขาใช้ตัวเลขจริง
- เกณฑ์ถอยกลับ: ถ้า MAPE รายสัปดาห์เกิน 22% สองสัปดาห์ติด หรือพยากรณ์ต่ำกว่าจริงเกิน 30% ในช่วงพีค ระบบถอยกลับรุ่นก่อนหน้าและแจ้งทีม (ปรับเกณฑ์ร่วมกับธนาคารได้)
- สาขาเปิดใหม่ที่ยังไม่มีข้อมูลย้อนหลัง ใช้ค่าเฉลี่ยของสาขาขนาดเดียวกันจนมีข้อมูลครบ 8 สัปดาห์

- ไม่รวม: ค่าผู้ทดสอบเจาะระบบอิสระที่ธนาคารกำหนด, ค่าใช้จ่ายฝั่งระบบของธนาคาร (core banking, API Gateway, Entra ID, ตู้ Q-Matic), ค่า SMS OTP หากใช้ gateway ของธนาคาร
- ยืนราคา 90 วันนับจากวันยื่นข้อเสนอ

## 8. ระดับการให้บริการ (SLA)

ระบบพร้อมใช้งาน (uptime) **≥ 99.5% ต่อเดือน** ไม่รวมช่วงบำรุงรักษาที่แจ้งล่วงหน้า 3 วัน

| ระดับ | ตัวอย่าง | ตอบรับ | แก้ไข/แนวทางชั่วคราว |
|---|---|---|---|
| Sev 1 | จองคิวไม่ได้ทุกสาขา หรือสาขาเรียกคิวไม่ได้ทั้งระบบ | 30 นาที | 4 ชั่วโมง |
| Sev 2 | สาขาใดสาขาหนึ่งเรียกคิวไม่ได้, แจ้งเตือน LINE ไม่ส่ง, พยากรณ์ไม่อัปเดต | 2 ชั่วโมง | 1 วันทำการ |

- ช่องทางแจ้งเหตุ: ระบบ ticket + โทรศัพท์ทีมดูแลระบบ, รายงานสรุป SLA ทุกเดือน
