# ทบทวนความเสี่ยงทางเทคนิค (tech-risk-review)

ทำแบบที่ CTO ทำ: อ่านงาน → แปลงเป็นชิ้นงานตามมาตรฐาน → ไล่หาจุดที่เสี่ยง **โดยอ้างหลักฐานจริงทุกข้อ** → ให้คะแนน → ตัดสิน → บอกว่าต้องทำอะไร ใครทำ ก่อนเมื่อไร
ไม่ประเมินราคา/margin (เป็นงานสายการเงิน) และไม่ตัดสินอนุมัติดีลแทน MD

ความรู้ที่ต้องใช้อยู่ใน `references/` ของ skill นี้แล้ว (ใช้ได้แม้เครื่องนั้นไม่มี company-kit):
- `references/risk-lenses.md` — 6 มุม + คำถามที่ต้องถามทุกครั้ง + เกณฑ์คะแนน
- `references/company-standards.md` — สรุปมาตรฐานสถาปัตยกรรม, runbook ขึ้นระบบ, นโยบายข้อมูลลูกค้า, โครงทีม
- `references/known-failures.md` — จุดที่เคยพังจริง (incident, บั๊ก, การทดลอง ML) ที่ต้องเช็กว่างานใหม่จะซ้ำไหม
- `references/output-format.md` — โครงผลงานที่ต้องได้

## ขั้นตอน

1. **รับโจทย์และหาเอกสาร** — งานคืออะไร (ดีลใหม่ หรือ release ที่จะขึ้นระบบ) อ่านเอกสารที่ผู้ใช้ให้ (TOR, spec, release notes, log) ถ้ามี `company-kit/` ในเครื่องให้เปิดไฟล์ต้นฉบับที่ references อ้างถึงเพื่อเช็กว่าข้อมูลใหม่กว่าที่สรุปไว้ไหม ถ้าไม่มีโจทย์ชัดเจน ถามก่อน อย่าเดา
2. **แปลงเป็นชิ้นงาน** — ใช้ `company-standards.md` ส่วนสถาปัตยกรรม: กี่ตัวที่ต้อง deploy, อะไรต้องแยก service, ระบบภายนอกกี่ระบบ, ข้อมูลอ่อนไหวอะไรบ้าง ใส่เป็นตารางสั้น ๆ
3. **ไล่ 6 มุม** ตาม `risk-lenses.md` ทีละมุม ตอบคำถามบังคับของแต่ละมุม
4. **เทียบกับจุดที่เคยพัง** — อ่าน `known-failures.md` ทุกครั้ง ถามว่า "งานนี้มีเงื่อนไขแบบเดียวกันไหม" (เช่น cert ที่ต้องต่อมือ, timezone, โมเดลที่ยังไม่มี MLOps) ถ้าซ้ำ = โอกาสเกิดสูงอัตโนมัติ
5. **ให้คะแนน** โอกาส × ผลกระทบ (1–3) ทุกข้อต้องมีคอลัมน์ "หลักฐาน" ระบุไฟล์/บรรทัด/ตัวเลข ข้อที่ไม่มีหลักฐานให้จดเป็น "คำถาม" ไม่ใช่ความเสี่ยง
6. **ตัดสิน** ตามเกณฑ์ใน `risk-lenses.md` (มี 🔴 ที่ไม่มีทางลด = ไม่ควรรับ/ไม่ปล่อย, มี 🔴 ที่ลดได้ = แบบมีเงื่อนไข และต้องเขียนเงื่อนไขเป็นข้อ ๆ ที่ตรวจได้)
7. **ตอบ 3 คำถามของ CTO** ตรง ๆ: เสี่ยงตรงไหน / ปล่อยขึ้นระบบได้ไหม / ทีมรับไหวไหม
8. **ส่งต่อ** — ใครทำอะไร ใช้ skill ไหนของทีม (`deploy-checklist`, `postmortem`, `model-release`, `test-from-plan`, `bug-report`, `mlflow-experiment`) และส่งผลให้ `deal-approval` ของ MD ถ้าเป็นดีลใหม่
9. **เขียนรายงาน** ตาม `output-format.md` ลง `work/<งาน>-tech-risk-review.md` (หรือที่ผู้ใช้กำหนด) แล้วสรุปคำตัดสิน + เงื่อนไขในแชตไม่เกิน 10 บรรทัด

## กติกา

- **ทุกความเสี่ยงต้องมีหลักฐาน** ห้ามใส่ความเสี่ยงทั่วไปแบบ "อาจล่าช้า" โดยไม่มีตัวเลขหรือเหตุการณ์รองรับ
- ผลการทดลอง/ตัวเลขที่ **เทียบกันไม่ได้** (ข้อมูลคนละเวอร์ชัน, จำนวนตัวอย่างต่างกัน, ไม่ fix seed) ให้ชี้ออกมา อย่ายกตัวเลขที่ดีที่สุดมาเป็นหลักฐานว่าผ่าน
- แยกให้ชัด: "ข้อเท็จจริงจากเอกสาร" กับ "สิ่งที่สมมติ" — เขียนข้อสมมติในหัวข้อข้อจำกัดท้ายรายงาน
- ทำตาม `customer-data-policy` (สรุปใน `company-standards.md`): ไม่คัดลอกเบอร์มือถือ/เลขบัตร/ชื่อลูกค้าปลายทางลงรายงาน
- งานด่วนที่เจอระหว่างทาง (เช่น cert ใกล้หมด, release ที่มีบั๊กกำลังจะ deploy) ให้ขึ้นบนสุดของรายงาน แม้ไม่ใช่งานที่ถูกถาม
- ตัวเลขใน references เป็น snapshot ณ วันที่เขียนไว้ ถ้าผู้ใช้ให้ข้อมูลใหม่กว่า ใช้ของใหม่และบอกว่าต่างจากเดิมตรงไหน
