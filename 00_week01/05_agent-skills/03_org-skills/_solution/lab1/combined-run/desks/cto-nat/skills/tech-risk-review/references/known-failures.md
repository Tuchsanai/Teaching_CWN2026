# จุดที่เคยพังจริง — เช็กทุกครั้งว่างานใหม่มีเงื่อนไขแบบเดียวกันไหม

## F1 · cert ที่ต่ออายุมือหมดอายุ ไม่มีใครรู้ (incident 2026-09-18, Sev1)

- ระบบ: ShopDee payment (`api.pay` proxy ไป ThaiPay GW) ล่ม **47 นาที** ช่วงขายดีวันศุกร์ order ค้าง 214, ตัดเงินแล้วแต่ webhook ไม่เข้า 9 รายการ (รอดเพราะมี idempotency + reconcile)
- ต้นเหตุเชิงระบบ: cert OV ที่ลูกค้าซื้อเองถูกอัปโหลดมือ อายุ 1 ปี · reminder อยู่ใน Google Calendar ส่วนตัวของ dev ที่ลาออก · ไม่มี alert วันหมดอายุ cert · uptime check ยิงแค่หน้าแรก www ไม่ยิง api ย่อย · **ลูกค้ารู้ก่อนเรา 9 นาที**
- สิ่งที่แก้แล้ว: runbook ข้อ 1.7 เช็ก cert > 21 วัน, arch-standards เพิ่ม alert cert < 21 วัน
- ยังค้าง: synthetic transaction ทุก 5 นาที, ทะเบียน cert มือในไฟล์กลาง, cert มือมี 4 ตัว (ShopDee 1 + ลูกค้าอื่น 3) — **BaanRai หมด 2026-11-02 ไม่มีใครยืนยันว่าต่อแล้ว**
- **เช็กในงานใหม่:** มี cert/secret ที่ไม่ได้ auto-renew ไหม (mTLS client cert ของ core banking, OV cert ของลูกค้า) · SLA ผูกเวลาตอบรับไหม · monitoring ยิง flow สำคัญจริงหรือแค่หน้าแรก

## F2 · บั๊ก timezone ของ slot จองคิว (CI run #1873, 2026-11-02)

- ระบบ: `kaset-appointment-web` (แอปนัดหมายสาขา ธนาคารออมทรัพย์เกษตรไทย) branch `release/2026.11` commit 3b7e9f1
- อาการ: จอง 15:00/15:30 ไม่ได้ ขึ้น "ช่วงเวลานี้เต็มแล้ว" ทั้งที่หน้าจอบอก "ว่าง 3 ที่" · API ตอบ `409 BOOKING_SLOT_FULL` · server log `resolvedLocalSlot: 2026-11-06 22:00`, `capacity: 0` (ส่ง `15:00:00.000Z` = เวลา UTC แล้วไปบวก +7 เป็น 22:00 หลังสาขาปิด)
- เกิดบน CI/UAT (TZ=UTC) แต่ผ่านบนเครื่อง dev (Asia/Bangkok) · ช่วงเช้าผ่าน เพราะ +7 ยังอยู่ในเวลาเปิดสาขา
- น่าสงสัย: commit "refactor: move slot time handling to date-fns-tz" (2026-10-30)
- **ลูกค้าเกษตรไทยกำหนด deploy release นี้ 2026-11-10**
- **เช็กในงานใหม่:** จะใช้โค้ดจองคิว/slot นี้ซ้ำไหม · test รันด้วย TZ เดียวกับ server production ไหม · มี test ช่วงขอบเวลา (ใกล้ปิดสาขา, ข้ามวัน) ไหม

## F3 · ผลทดลอง ML ที่ดูดีแต่เทียบกันไม่ได้ (พยากรณ์คิว ต.ค. 2026)

ข้อมูล: บัตรคิวรายชั่วโมง ธนาคารออมทรัพย์เกษตรไทย 40 สาขานำร่อง · เฉลี่ย ~15 คน/ชม. สาขาใหญ่พีค 60+ · ทำโดย DS สัญญาจ้าง

| run | โมเดล | data | สาขา | MAPE | payday | holiday week |
|---|---|---|---|---|---|---|
| r01 | moving avg 4 สัปดาห์ (ที่รันใน prod เกษตรไทย) | qdata-v3 | 40 | 31.5 | 44.2 | 52.8 |
| r02 | LightGBM + lag/rolling | qdata-v3 | 40 | 19.8 | 27.6 | 38.9 |
| r03 | r02 + วันหยุด/payday/long weekend | **qdata-v4** | **38** | 15.2 | 17.4 | 19.6 |

- qdata-v4 = เพิ่มตารางวันหยุด + ลบแถวซ้ำ ~1.2% + **ตัด 2 สาขาที่ปิดปรับปรุง** → r02 กับ r03 เทียบกันไม่ได้ ยังไม่รู้ว่าดีขึ้นเพราะ feature หรือเพราะข้อมูลสะอาดขึ้น (ยังไม่ได้รัน r02 บน v4)
- ไม่ fix seed · ไม่ได้จดผล tune รายตัว · โมเดลอยู่ใน notebook บน laptop + ไฟล์ใน drive ยังไม่ลง MLflow · ข้อมูลเข้าทุกคืนแต่ไม่มี monitoring drift
- พยากรณ์ **ต่ำกว่าจริง 20–30% ช่วง 11:00–13:00** สาขาย่านออฟฟิศ (อันตรายกว่าพยากรณ์เกิน เพราะจัดคนไม่พอ) · สาขาใหม่ < 8 สัปดาห์ไม่มี lag ใช้ค่าเฉลี่ยสาขาขนาดเดียวกันแทน
- ข้อเสนอที่ยังไม่มีใครตัดสิน: เกณฑ์ถอยกลับ (MAPE รายสัปดาห์ > 22% สองสัปดาห์ติด? under-forecast ช่วงเที่ยง > 30%?), shadow mode 1–2 สัปดาห์
- **เช็กในงานใหม่:** ตัวเลขที่จะเอาไปผูกสัญญามาจากข้อมูลของใคร เทียบกันได้ไหม · มี MLOps (tracking, monitoring, rollback) ตามที่ลูกค้าขอไหม · คนที่รู้โมเดลเป็นสัญญาจ้างคนเดียวไหม
