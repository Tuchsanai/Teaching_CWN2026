# prd-writer

จาก feedback ดิบ → จัดลำดับ → PRD 1 ฉบับต่อ 1 ฟีเจอร์ ที่ผ่านกติกา PRD ของบริษัท
ทำเรื่องเดียว: **ตัดสินว่าทำอะไรก่อน แล้วเขียน PRD** (ไม่ทำแผนเลิกให้บริการ ไม่ทำ spec สถาปัตยกรรม ไม่เขียน test)

## ก่อนเริ่ม อ่าน references

- `references/prd-rules.md` — 5 สิ่งที่ PRD ต้องมี + กติกาข้อมูลส่วนบุคคลที่ใช้กับ PRD (บังคับ)
- `references/novaqueue-context.md` — เวอร์ชัน, วงจรชีวิต, ตัวเลขฐาน, ต้นทุน, เรื่องต้องห้าม, คนที่ต้องถาม
- `references/prd-template.md` — โครง PRD ที่ต้องใช้

ถ้ามีไฟล์ใหม่กว่าใน `company-kit/product/` ให้ใช้ตัวเลขจากไฟล์ใหม่ แต่ กติกาใน references ยังใช้จนกว่าเจ้าของจะแก้

## ขั้นตอน

1. **รวบรวมหลักฐาน** — อ่าน feedback/ตัวเลขที่ผู้ใช้ให้ คำนวณแนวโน้ม (เดือนต่อเดือน) และต้นทุนที่คำนวณได้ (เช่น จำนวน SMS × ราคา) ห้ามคัดลอกชื่อ เบอร์ เลขบัญชีของลูกค้าปลายทาง — อ้างด้วยรหัส ticket (F-xx) เท่านั้น
2. **จัดกลุ่มเป็นปัญหา** — รวม ticket ที่เป็นปัญหาเดียวกัน (ดูที่ "ลูกค้าเจออะไร" ไม่ใช่ "ลูกค้าขอวิธีแก้อะไร") รวมจำนวนครั้งที่ถูกพูดถึงต่อกลุ่ม
3. **ผ่าน gate ก่อนให้คะแนน** (ไม่ผ่าน = ไม่เข้า backlog ส่งต่อคนตัดสิน)
   - ขัดสัญญา/หลักกำกับ (เช่น VIP ข้ามคิว) → ส่ง MD
   - ขอบน v1 → ไม่รับ (v1 ดูแลอย่างเดียว)
   - เป็นข้อกำหนด security/compliance → แยก track ส่ง Tech ไม่ใช้คะแนนนับครั้ง
4. **ให้คะแนน RICE แบบย่อ** — `Reach × Impact × Confidence ÷ Effort`
   - Reach = จำนวนครั้งที่ถูกพูดถึง · Impact 3/2/1 = แก้ตัวชี้วัดหลัก (no-show, รอนาน, ต้นทุน, รายได้) หลายตัว / 1 ตัว / ความสะดวก · Confidence % · Effort คน-สัปดาห์
   - เขียนให้ชัดว่า Effort เป็นการประเมินของ PM ต้องให้ Dev lead ยืนยัน และบอกข้อจำกัดของการนับ (เสียงผู้จัดการสาขา 1 ครั้งแทนคนจำนวนมาก)
5. **ตรวจข้อสังเกตเดิม** ในไฟล์ feedback (ถ้ามี) ทีละข้อ ว่าจริง/ไม่จริง/ต้องเช็ก
6. **เขียนเอกสารจัดลำดับ** — ตารางกลุ่ม, gate, คะแนน, ฟีเจอร์ที่เลือก, สิ่งที่ต้องทำต่อ (ใครทำ)
7. **เขียน PRD ของอันดับ 1** ตาม `references/prd-template.md` — ครบ 5 หัวข้อบังคับ, เกณฑ์ตรวจรับแบบ Given/When/Then ที่มีตัวเลขวัดได้ (เวลา, จำนวนครั้ง, สถานะ) เพื่อให้ QA เขียน test ได้ทันที
8. **ตรวจก่อนส่ง** (checklist ด้านล่าง) แล้วบันทึกไฟล์ใน `work/` ของโต๊ะผู้ใช้

## ห้าม

- ห้ามใส่ตัวเลขราคา/ต้นทุนที่ยังไม่ยืนยัน (เช่น ค่า LINE OA) เป็นข้อเท็จจริง — ใส่เป็น "คำถามที่ยังเปิด" พร้อมชื่อคนยืนยัน
- ห้ามแต่งตัวเลข baseline — ถ้าไม่มีให้เขียน "ยังไม่มีข้อมูล ต้องวัดก่อนเริ่ม"
- ห้ามสัญญาวัน GA หรือฟีเจอร์กับลูกค้าในเอกสาร — GA ต้องผ่าน MD

## Checklist ก่อนส่ง

- [ ] มีหลักฐานเป็นตัวเลข/จำนวนครั้ง ทุกปัญหา
- [ ] ไม่มีชื่อ เบอร์ เลขบัตร เลขบัญชี ของลูกค้าปลายทาง (ค้นคำว่า `08`, `09`, `06`, `คุณ` ก่อนส่ง)
- [ ] ตัวชี้วัดทุกตัวมีค่าปัจจุบัน + เป้าหมาย (เป้าหมายระบุว่าเป็น "เสนอ")
- [ ] มีทั้ง "ทำ" และ "ไม่ทำในรอบนี้"
- [ ] user story ทุกข้อมีเกณฑ์ตรวจรับที่ทดสอบได้
- [ ] มีหัวข้อผลกระทบต่อเวอร์ชันอื่น (ทำบน v2 เท่านั้น)
- [ ] คำถามที่ยังเปิดมีชื่อผู้ตอบ

- สงสัยเรื่องข้อมูลส่วนบุคคล → ใช้ skill `customer-data-policy`
