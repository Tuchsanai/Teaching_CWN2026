# ข้อเสนอโครงการ: ระบบจองคิวสาขาและพยากรณ์ปริมาณคิว (Branch Queue Booking & Forecasting)

**เสนอต่อ:** ธนาคารนครหลวงพัฒนา จำกัด (มหาชน) — ฝ่ายพัฒนาช่องทางสาขา

**เลขที่เอกสาร:** NVT-PRP-2026-[รอเลขจากทะเบียนเอกสาร] · **วันที่:** 4 พฤศจิกายน 2026
**จัดทำโดย:** นิดา แก้วมณี (หัวหน้าทีมขาย) · ไอศวรรย์ บุญมา (Solution Architect)

## 1. บทสรุปผู้บริหาร

เราเสนอระบบจองคิวผ่านเว็บและ LINE OA พร้อมโมเดลพยากรณ์จำนวนลูกค้ารายสาขารายชั่วโมงล่วงหน้า 7 วัน เพื่อลดเวลารอเฉลี่ยที่สาขาลง 30% ภายใน 6 เดือนหลังเปิดใช้

ปัจจุบันลูกค้าของธนาคารรอคิวเฉลี่ย 38 นาที และสูงสุด 95 นาทีช่วงวันที่ 25–5 ของเดือน ขณะที่สาขาจัดพนักงานไม่ตรงกับช่วงที่ลูกค้ามาก ระบบที่เสนอแก้ทั้งสองด้าน: ลูกค้าเลือกเวลามาได้เอง และผู้จัดการสาขาเห็นปริมาณคิวล่วงหน้าเพื่อจัดช่องบริการได้ทัน

- ระยะเวลา 6 เดือนนับจากวันลงนามสัญญา นำร่อง 10 สาขาในเดือนที่ 5 ขยายครบ 120 สาขาในเดือนที่ 6
- มูลค่ารวม **4,800,000 บาท (ไม่รวม VAT)** ครอบคลุมค่าพัฒนา, hosting ปีแรก, license ปีแรก และ MA ปีแรก ตามขอบเขตงบประมาณข้อ 6 ของ TOR
- เชื่อมต่อ core banking, LINE OA และตู้กดบัตรคิวเดิม **ผ่าน API โดยไม่แก้ไขระบบเดิมของธนาคาร**

### สิ่งที่ขอยืนยันก่อนเริ่มงาน

1. **Customer Lookup API** — เอกสาร API, sandbox สำหรับทดสอบ, ใบรับรอง mTLS และขีดจำกัดจำนวนครั้งเรียกต่อวินาที รวมถึง **ช่องทางส่ง OTP** (TOR ระบุว่า API คืนชื่อ ระดับลูกค้า และ CIF จึงขอยืนยันว่าเบอร์สำหรับส่ง OTP มาจากระบบใด และใครเป็นผู้ส่ง OTP)
2. **ตู้ Q-Matic** — รุ่นและเวอร์ชัน API ของทั้ง 120 สาขาเหมือนกันหรือไม่ และเอกสาร API จากผู้ผลิต
3. **เวลาให้บริการของสาขา** — มีสาขาที่เปิดวันเสาร์-อาทิตย์หรือหลัง 17:00 น. (เช่น สาขาในห้างสรรพสินค้า) หรือไม่ เพราะกำหนดชั่วโมงที่ SLA ต้องครอบคลุม (หัวข้อ 8)
4. **วันส่งข้อมูลบัตรคิวย้อนหลัง 24 เดือน** — ขอรับภายในสัปดาห์ที่ 3 หลังลงนามสัญญา เพื่อให้พัฒนาและทดสอบโมเดลทันก่อน UAT
5. **การแจ้งเตือนลูกค้าที่จองผ่านเว็บแต่ไม่ใช้ LINE** — ใช้อีเมล หรือต้องการ SMS (SMS ไม่รวมในราคานี้ ดูตัวเลือกเสริมหัวข้อ 7)
6. **บัญชี LINE OA** — แพ็กเกจปัจจุบันและโควตาข้อความของบัญชีธนาคาร
7. **Penetration test** — ผู้ทดสอบที่ธนาคารกำหนด, จำนวนรอบทดสอบซ้ำหลังแก้ไข และผู้รับผิดชอบค่าใช้จ่าย
8. **อุปกรณ์ที่สาขา** — ใช้พีซี/จอเรียกคิวที่สาขามีอยู่ หรือต้องจัดหาเพิ่ม

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้าง

- **Modular monolith** (Next.js + Node.js/TypeScript) แยกโมดูล booking / branch / notification / report — ทีมเดียวดูแล deploy และแก้ปัญหาได้เร็ว
- **forecast-service** (Python) แยกเป็น service เพราะคนละ runtime และรันเป็น batch
- **core-connector** แยกเครือข่ายสำหรับเรียก Customer Lookup API ผ่าน API Gateway ของธนาคารด้วย mTLS — ระบบส่วนอื่นเข้าถึง core banking ไม่ได้โดยตรง
- **PostgreSQL** (managed, HA) เป็นฐานข้อมูลหลัก · **Redis** สำหรับ slot lock ป้องกันจองซ้อน, session และ rate limit
- **คิวงาน (BullMQ)** สำหรับส่งข้อความ LINE, sync กับ Q-Matic และงานพยากรณ์ ทุกงานส่งซ้ำได้โดยไม่เกิดผลซ้ำ งานที่ล้มเหลวครบกำหนดแจ้งเตือนทีมทันที
- Hosting บน **cloud ภูมิภาคประเทศไทยเท่านั้น** แยกสภาพแวดล้อม dev / uat / prod

### 4.2 ความปลอดภัย (ตอบ TOR ข้อ 4 ทีละข้อ)

| ข้อกำหนด TOR | มาตรการของเรา |
|---|---|
| ปฏิบัติตามแนวนโยบายความเสี่ยงด้าน IT ของ ธปท. และ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 | เก็บข้อมูลส่วนบุคคลเท่าที่จำเป็นต่อการจองคิว, ข้อมูลอยู่ใน cloud ภูมิภาคไทย, จัดทำเอกสารการประมวลผลข้อมูลและแบบประเมินผู้ให้บริการตามที่ธนาคารกำหนด, กระบวนการแจ้งเหตุข้อมูลรั่วไหลภายในเวลาที่กฎหมายกำหนด |
| เข้ารหัสขณะส่ง TLS 1.2 ขึ้นไป | TLS 1.2+ ทุกช่องทาง ปิด protocol รุ่นเก่า, mTLS กับ API Gateway ของธนาคาร, แจ้งเตือนใบรับรองที่ใกล้หมดอายุล่วงหน้า 21 วัน |
| เข้ารหัสขณะจัดเก็บ AES-256 | ฐานข้อมูล, backup และ object storage เข้ารหัส AES-256 กุญแจเก็บใน key management service ของ cloud |
| เลขบัตรประชาชนห้ามเก็บแบบข้อความธรรมดา | ใช้เลขบัตรเพื่อส่งตรวจกับ core banking เท่านั้น ในระบบเก็บเป็นค่า hash แบบมีกุญแจ (HMAC-SHA256) ไม่เก็บเลขเต็ม, ไม่บันทึกลง log |
| Audit log ทุกการเข้าถึงข้อมูลลูกค้า เก็บ ≥ 2 ปี | บันทึกผู้ใช้ เวลา การกระทำ และรายการที่เข้าถึง ทุกครั้งที่เปิดดูหรือค้นข้อมูลลูกค้า เก็บแบบแก้ไขไม่ได้ในภูมิภาคไทย 2 ปี |
| Pentest โดยผู้ทดสอบอิสระที่ธนาคารกำหนด ก่อนเปิดใช้จริง | กำหนด pentest ในเดือนที่ 4 ก่อน UAT, แก้ช่องโหว่ระดับสูงและวิกฤตทั้งหมดก่อนนำร่อง และทดสอบซ้ำ |
| NDA ทุกคนที่เข้าถึงข้อมูล | ทุกคนในทีมลงนาม NDA กับธนาคารก่อนได้รับสิทธิ์ ส่งรายชื่อผู้มีสิทธิ์ให้ธนาคารตรวจ และถอนสิทธิ์ภายในวันที่ออกจากโครงการ |
| (มาตรการเพิ่มเติม) | Web Application Firewall + ป้องกัน DDoS, สิทธิ์ตามบทบาท (ผู้บริหาร / ผู้จัดการสาขา / พนักงาน / ผู้ดูแลระบบ), rate limit และจำกัดจำนวนครั้งยืนยันตัวตนผิด, สแกนช่องโหว่ไลบรารีทุกครั้งที่ deploy |

### 4.3 การดูแลโมเดลพยากรณ์

- **ข้อมูลเทรน**: ข้อมูลบัตรคิวย้อนหลัง 24 เดือนแบบไม่ระบุตัวตนที่ธนาคารส่งให้ ใช้เฉพาะระดับสาขา-ชั่วโมง ไม่ใช้ข้อมูลรายบุคคล เก็บใน cloud ภูมิภาคไทยเท่านั้น และ **ลบสำเนาภายใน 90 วันหลังส่งมอบ**
- **เกณฑ์รับมอบ**: MAPE ภาพรวม ≤ 20% บนข้อมูล 3 เดือนล่าสุดตาม TOR พร้อมรายงานแยกช่วงวันเงินเดือนออก สัปดาห์ที่มีวันหยุด และรายช่วงเวลาของวัน
- **ก่อนให้สาขาใช้ตัวเลข**: รันคู่ขนาน (shadow mode) 2 สัปดาห์ในช่วงนำร่อง เทียบพยากรณ์กับคิวจริงก่อนแสดงให้ผู้จัดการสาขา
- **ติดตามหลังใช้งาน**: รายงานความแม่นยำรายสัปดาห์ต่อสาขา และเฝ้าระวังการพยากรณ์ต่ำกว่าจริงเป็นพิเศษ เพราะทำให้สาขาจัดคนไม่พอ
- **ถอยกลับรุ่นเดิม**: ทุกรุ่นของโมเดลลงทะเบียนพร้อมเวอร์ชันข้อมูลและผลทดสอบ ถ้าความแม่นยำต่ำกว่าเกณฑ์ที่ตกลงกับธนาคารต่อเนื่อง ระบบสลับกลับรุ่นก่อนหน้าได้ภายในรอบการรันถัดไป
- **สาขาเปิดใหม่ที่ยังไม่มีประวัติ**: ใช้ค่าอ้างอิงจากสาขาขนาดและย่านใกล้เคียงจนมีข้อมูลพอ
