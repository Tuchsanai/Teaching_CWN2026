## 5. แผน rollback

**ต้อง rollback ทันทีถ้า** เจออย่างใดอย่างหนึ่ง:
- smoke test ข้อไหนไม่ผ่าน และแก้ไม่ได้ใน 15 นาที
- error rate > 5% ต่อเนื่อง 5 นาที
- **ข้อมูลผิดแม้แค่รายการเดียว** ซึ่งในระบบนี้หมายถึง:
  - จองซ้อน (ช่องเดียวกันมีมากกว่าจำนวนช่องบริการ) หรือเวลานัดที่บันทึกไม่ตรงกับที่ลูกค้าเลือก
  - ลูกค้าเห็นหรือยกเลิกคิวของคนอื่นได้ · OTP หรือแจ้งเตือนไปผิดคน
  - ลำดับคิวจองกับ walk-in ผิดกติกาที่ตกลง (Q-06) · บัตรคิวจาก Q-Matic หาย
  - เวลารอที่ใช้วัด KPI คำนวณผิด (FR-RPT-03)
  - เลขบัตรประชาชนแบบข้อความธรรมดาโผล่ใน log, DB หรือ Excel (เป็นเหตุละเมิดด้วย → แจ้ง `plat-may` ภายใน 1 ชม. ตาม NFR-SEC-07)

ทำตามลำดับ:
1. **ปิด feature flag** ที่เพิ่งเปิด (รอบระลอก: เอาสาขาใหม่ออกจาก flag สาขาเดิมยังใช้ต่อได้) · ถ้าปัญหาเป็นที่พยากรณ์อย่างเดียว ให้สลับกลับรุ่นโมเดลเดิม (FR-FCT-07 ภายใน 15 นาที) ไม่ต้อง rollback ทั้งระบบ
2. **deploy image tag เดิม** ที่จดไว้ข้อ 2.4 (รอบนำร่องไม่มีเวอร์ชันเดิม = ปิด flag สาขานำร่องทั้งหมด แล้วให้สาขาใช้ Q-Matic แบบเดิม)
3. **restore snapshot** เฉพาะเมื่อ migration ทำให้โค้ดเก่าใช้ไม่ได้ · **Deploy lead (อาร์ต) และหัวหน้าทีม dev (มิว) ต้องตกลงร่วมกันก่อน**
   - ก่อน restore: export การจอง, การเช็กอิน และบัตรคิวที่เกิดหลังเวลา snapshot เก็บไว้ (ใน region ไทย) เพื่อใส่กลับและแจ้งลูกค้าที่จองไว้
   - รอบนำร่องที่ยังไม่มีข้อมูลจริง: restore ได้โดยไม่เสียข้อมูล
4. Comms แจ้งธนาคาร **ภายใน 30 นาที** ว่าย้อนกลับแล้ว ผลกระทบคืออะไร และสาขาต้องทำอะไร (เช่น ใช้ตู้คิวแบบเดิม)

ถ้า rollback หรือมีผลกระทบกับลูกค้า → ส่งต่อ `postmortem` (ฝน `ops-fon`) ภายใน 3 วันทำการ
