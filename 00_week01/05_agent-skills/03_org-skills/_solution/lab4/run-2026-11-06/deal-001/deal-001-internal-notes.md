## 5. ความเสี่ยง

1. **ยืนยันตัวตนอาจทำตาม TOR ไม่ได้:** TOR ข้อ 3.4 ระบุว่า API คืนแค่ชื่อ ระดับลูกค้า และ CIF แต่ข้อ 3.1 ต้องตรวจวันเกิดและส่ง OTP ถ้าได้เบอร์หรือวันเกิดไม่ได้ ต้องเปลี่ยนการออกแบบ (ถามไว้ใน proposal ข้อ 2)
2. **กำลังคน:** DS-2026-034 ระบุว่า tech lead (ปอนด์) จะถือ 3 โปรเจกต์ช่วง ม.ค.–ก.พ. 2027 รวมดีลนี้ และ `monthly-kpi.csv` ยังมีตำแหน่ง Senior Full-stack กับ ML Engineer เปิดอยู่ ถ้าทีมไม่ครบ ประโยค "ทีมชุดเดียว / ไม่ใช้ผู้รับเหมาช่วง" จาก proposal เก่าใช้ไม่ได้ จึงตัดออก
3. **ML:** ผล r03 (MAPE 15.2%) **ไม่ได้ใส่ใน proposal** เพราะเป็นผลต้นแบบบนข้อมูลของอีกธนาคาร จำนวนสาขาและรุ่นข้อมูลต่างจาก r02 (ยังไม่เคยเทียบแบบแฟร์) ยังพยากรณ์ช่วงเที่ยงต่ำกว่าจริง −20 ถึง −30% ในสาขาย่านออฟฟิศ และยังไม่มี monitoring/MLflow ส่วนสิทธิ์ใช้ข้อมูลเกษตรไทยกับดีลนี้ก็ควรตรวจก่อน
4. **เกณฑ์ MAPE ≤ 20% เป็นเกณฑ์ตรวจรับ:** ยังไม่มีผลบนข้อมูลของนครหลวงฯ เราผูกตัวเองตาม TOR โดยไม่มีหลักฐานจากข้อมูลนี้ และข้อมูลยังมาหลังเซ็นสัญญา ไม่ได้ระบุวันใน TOR
5. **เป้าลดเวลารอ 30%:** ขึ้นกับการจัดคนของสาขาด้วย ใน proposal เขียนเป็นเป้าหมาย ไม่ใช่การรับประกัน ควรระวังไม่ให้กลายเป็นเงื่อนไขสัญญาหรือค่าปรับ
6. **แผนงานตึง:** penetration test ขึ้นกับคิวของผู้ทดสอบที่ธนาคารกำหนด และการขยาย 110 สาขาใน 2 สัปดาห์ของเดือนที่ 6 เพื่อให้ hypercare จบใน 6 เดือน
7. **SLA 8x5 กับ uptime 99.5%:** ความล่มนอกเวลาทำการยังนับ uptime แต่ไม่มีคนตอบรับ จึงเสี่ยงผิด SLA รายเดือนได้ง่าย (99.5% ≈ 3.6 ชั่วโมงต่อเดือน) เป็นเหตุผลให้ทบทวนข้อตัดสินใจ 1
