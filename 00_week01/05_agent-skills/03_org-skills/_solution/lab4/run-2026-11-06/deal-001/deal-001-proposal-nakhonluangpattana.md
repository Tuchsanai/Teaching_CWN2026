**เสนอต่อ:** ธนาคารนครหลวงพัฒนา จำกัด (มหาชน) — ฝ่ายพัฒนาช่องทางสาขา

## 1. บทสรุปผู้บริหาร

เราเสนอระบบจองคิวผ่านเว็บและ LINE OA (LINE Official Account) พร้อมโมเดลพยากรณ์คิวล่วงหน้า 7 วัน สำหรับทั้ง 120 สาขา โดยมีเป้าหมายลดเวลารอเฉลี่ยลง 30% ภายใน 6 เดือนหลังเปิดใช้

ปัจจุบันลูกค้าของธนาคารรอคิวเฉลี่ย 38 นาที และสูงสุด 95 นาทีในช่วงวันที่ 25–5 ของเดือน ขณะที่สาขาจัดพนักงานไม่ตรงกับช่วงที่คนมาก เป้าหมาย 30% เทียบเท่าเวลารอเฉลี่ยประมาณ 26.6 นาที ผลลัพธ์นี้ต้องอาศัยทั้งระบบและการปรับตารางพนักงานของสาขา เราจึงเสนอให้วัดค่าตั้งต้นร่วมกันก่อนนำร่อง และรายงานผลรายสาขาใน Dashboard

- **ระยะเวลา:** 6 เดือนนับจากวันลงนามสัญญา (คาดว่า 4 มกราคม 2027) นำร่อง 10 สาขาในเดือนที่ 5 และครบ 120 สาขาภายในเดือนที่ 6
- **มูลค่า:** 4,800,000 บาท (ไม่รวม VAT) รวมค่าพัฒนา hosting ปีแรก และ MA (การบำรุงรักษา) ปีแรก อยู่ในวงเงินของ TOR

### สิ่งที่ขอยืนยันก่อนเริ่มงาน

1. **ข้อมูลจาก Customer Lookup API:** TOR ระบุว่า API คืนชื่อ ระดับลูกค้า และ CIF แต่ขั้นตอนยืนยันตัวตนต้องตรวจวันเดือนปีเกิดและส่ง OTP ไปยังเบอร์ของลูกค้า ขอยืนยันว่า API ตรวจวันเกิดและส่ง OTP หรือคืนปลายทาง OTP ได้หรือไม่ พร้อมเอกสาร API และกำหนดเปิด sandbox (สภาพแวดล้อมทดสอบ)
2. **ช่องทางและค่าใช้จ่าย OTP:** ใช้ SMS gateway ของธนาคารหรือไม่ และธนาคารเป็นผู้รับค่าข้อความหรือไม่
3. **ตู้ Q-Matic:** ขอเอกสาร REST API และยืนยันว่าทั้ง 120 สาขาใช้รุ่นและ API เดียวกัน
4. **ข้อมูลย้อนหลัง 24 เดือน:** ขอรับภายใน 2 สัปดาห์หลังลงนามสัญญา พร้อมคำอธิบายข้อมูล เพราะกระทบแผนงานพยากรณ์โดยตรง
5. **วิธีคำนวณ MAPE "ในภาพรวม":** ขอตกลงสูตร ระดับการรวมผล และการจัดการชั่วโมงที่ไม่มีลูกค้า ก่อนเริ่มทดสอบ
6. **เวลาให้บริการ:** ขอยืนยันเวลาทำการจริงของสาขา รวมสาขาที่เปิดวันหยุด เพื่อเลือกแพ็ก MA ให้ตรงกับการใช้งาน ดูหัวข้อ 8
7. **Penetration test:** ขอทราบผู้ทดสอบที่ธนาคารกำหนด ช่วงเวลา จำนวนรอบทดสอบซ้ำ และผู้รับค่าใช้จ่าย
8. **LINE OA:** ขอยืนยันผู้ถือบัญชี แพ็กเกจข้อความ และผู้รับค่าข้อความส่วนที่เกินโควตา
9. **การเริ่มนับ hosting ปีแรก:** เราเสนอให้นับ 12 เดือนจากวันเริ่มนำร่อง
10. **อุปกรณ์และเครือข่ายสาขา:** ขอยืนยันว่าธนาคารจัดเตรียมอุปกรณ์และเครือข่ายสำหรับ Branch Console
11. **การใช้ระดับลูกค้า:** ข้อเสนอนี้ใช้ระดับลูกค้าเพื่อแสดงข้อมูลแก่พนักงานเท่านั้น ไม่จัดลำดับคิวตามระดับลูกค้า หากธนาคารต้องการให้แจ้งก่อนเริ่มออกแบบ

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้าง

ระบบเป็น modular monolith (แอปเดียวที่แบ่งโมดูลชัดเจน) และแยก service เฉพาะส่วนที่จำเป็น เพื่อให้ดูแลง่ายและแยกส่วนที่มีความเสี่ยงออกจากกัน

- **แอปหลัก:** Next.js + Node.js/TypeScript โมดูล booking, branch, notification, report
- **core-connector:** แยกเครือข่ายสำหรับเชื่อม core banking ผ่าน mTLS (การยืนยันตัวตนสองฝั่งด้วยใบรับรอง)
- **forecast-service:** แยกเป็น Python สำหรับโมเดลพยากรณ์
- **ข้อมูล:** PostgreSQL แบบ managed และ HA (ทำงานต่อเนื่องเมื่อเครื่องหลักขัดข้อง) กับ Redis สำหรับ slot lock (ล็อกช่องเวลาป้องกันการจองซ้อน)
- **คิวงาน:** แจ้งเตือนและงาน batch แยกจาก request หลัก มีการส่งซ้ำและแจ้งเตือนเมื่อล้มเหลว
- **Hosting:** cloud ภูมิภาคประเทศไทยเท่านั้น มี WAF (ไฟร์วอลล์เว็บแอปพลิเคชัน) ป้องกัน DDoS และระบบ monitoring

### 4.2 ความปลอดภัย

เราตอบข้อกำหนดข้อ 4 ของ TOR ทุกข้อด้วยมาตรการต่อไปนี้

| ข้อกำหนด TOR | มาตรการ |
|---|---|
| แนวนโยบายความเสี่ยง IT ของ ธปท. | จัดทำตารางเทียบข้อกำหนดกับมาตรการของระบบร่วมกับฝ่าย IT ของธนาคารในช่วงออกแบบ แยกสภาพแวดล้อม dev, UAT, production และจำกัดสิทธิ์เข้าถึง production ผ่านการขออนุมัติ |
| พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 | จัดทำข้อตกลงประมวลผลข้อมูลกับธนาคาร เก็บเฉพาะข้อมูลที่จำเป็น ใช้ข้อมูลเทรนแบบไม่ระบุตัวตน ใช้ข้อมูลสังเคราะห์ในการทดสอบ และลบสำเนาข้อมูลลูกค้าปลายทางภายใน 90 วันหลังส่งมอบ |
| TLS 1.2 ขึ้นไป และ AES-256 | ใช้ TLS 1.2 ขึ้นไปทุกช่องทาง เข้ารหัส AES-256 ที่ฐานข้อมูลและ backup และ mTLS สำหรับการเชื่อม core banking |
| เลขบัตรประชาชนห้ามเก็บแบบข้อความธรรมดา | ไม่เก็บแบบข้อความธรรมดา ใช้ keyed hash เมื่อจำเป็นต้องค้นหา ปิดบังในหน้าจอ และไม่บันทึกลง log พร้อมจำกัดจำนวนครั้งที่พยายามยืนยันตัวตน |
| Audit log ไม่น้อยกว่า 2 ปี | บันทึกทุกการเข้าถึงข้อมูลลูกค้า (ใคร เมื่อไร ข้อมูลใด) เก็บ 2 ปีในประเทศไทย จำกัดสิทธิ์แก้ไขและตรวจค้นได้ |
| Penetration test โดยผู้ทดสอบอิสระก่อนเปิดใช้ | จัดเวลาทดสอบก่อน UAT และก่อนเปิดนำร่อง แก้ไขช่องโหว่ตามผลทดสอบและส่งทดสอบซ้ำก่อนเปิดใช้งานจริง |
| NDA ทุกคนที่เข้าถึงข้อมูล | ทุกคนที่เข้าถึงข้อมูลลงนาม NDA รายบุคคลก่อนรับสิทธิ์ และส่งรายชื่อให้ธนาคารตรวจสอบได้ |

นอกจากนี้ เราใช้ SSO ของธนาคารร่วมกับสิทธิ์ตามบทบาทสำหรับพนักงาน และมีการแจ้งเตือนล่วงหน้าเมื่อใบรับรอง TLS ใกล้หมดอายุ

### 4.3 การดูแลโมเดลพยากรณ์

เราผูกการตรวจรับโมเดลกับข้อมูลจริงของธนาคาร ตามเกณฑ์ MAPE ไม่เกิน 20% ในภาพรวมบนข้อมูล 3 เดือนล่าสุดตาม TOR

- **ข้อมูล:** ใช้ข้อมูลบัตรคิวย้อนหลัง 24 เดือนแบบไม่ระบุตัวตนที่ธนาคารส่งให้หลังลงนามสัญญา และกันข้อมูล 3 เดือนล่าสุดไว้ทดสอบเท่านั้น
- **ปัจจัยในโมเดล:** วันหยุดนักขัตฤกษ์ วันเงินเดือนออก วันหยุดยาว วันในสัปดาห์ ชั่วโมง และขนาดสาขา
- **รายงานผล:** แสดงทั้งภาพรวมและรายกลุ่ม ได้แก่ ช่วงเงินเดือนออก สัปดาห์ที่มีวันหยุด และช่วงพักเที่ยง เพราะการพยากรณ์ต่ำกว่าจริงทำให้สาขาจัดคนไม่พอ
- **ก่อนใช้จริง:** รันแบบเงาระหว่างนำร่องเพื่อเทียบค่าพยากรณ์กับจำนวนจริง ก่อนใช้ประกอบการจัดตาราง
- **หลังใช้จริง:** ติดตามความแม่นยำรายสัปดาห์ แจ้งเตือนเมื่อเกินเกณฑ์ที่ตกลงร่วมกัน และถอยกลับรุ่นเดิมจากทะเบียนรุ่นได้
- **สาขาเปิดใหม่:** ใช้ค่าอ้างอิงจากสาขาขนาดเดียวกันจนกว่าจะมีประวัติเพียงพอ

## 8. ระดับการให้บริการ (SLA)

เรารับประกัน uptime ไม่น้อยกว่า 99.5% ต่อเดือน และตอบรับ Sev 1 ภายใน 30 นาทีตาม TOR ภายในเวลาให้บริการของแพ็กที่เสนอ

| ระดับ | ตัวอย่าง | ตอบรับ | แก้ไข/แนวทางชั่วคราว |
|---|---|---|---|
| Sev 1 | จองคิวไม่ได้ทุกสาขา หรือระบบเรียกคิวใช้ไม่ได้ทั้งหมด | 30 นาที | 4 ชั่วโมง |
| Sev 2 | บางสาขาเรียกคิวไม่ได้ หรือฟังก์ชันหลักใช้ไม่ได้บางส่วน | 2 ชั่วโมง | 1 วันทำการ |
| Sev 3 | ปัญหาเล็ก หรือคำถาม | 1 วันทำการ | 5 วันทำการ |

- **ชั่วโมงที่ครอบคลุม:** แพ็ก MA Standard ให้บริการแบบ 8x5 คือวันจันทร์–ศุกร์ 8 ชั่วโมงต่อวัน ไม่รวมวันหยุด เวลาตอบรับและแก้ไขในตารางนับภายในชั่วโมงเหล่านี้ และจะระบุช่วงเวลาที่แน่นอนในสัญญา
- **นอกชั่วโมงบริการ:** ระบบ monitoring ยังทำงานตลอดเวลา แต่การตอบรับจะเริ่มในชั่วโมงบริการถัดไป หากธนาคารต้องการให้ครอบคลุม 24x7 ให้เลือก MA Premium ตามตัวเลือกเสริมในหัวข้อ 7
- **Uptime:** ≥ 99.5% ต่อเดือน ไม่รวมช่วงบำรุงรักษาที่แจ้งล่วงหน้า 3 วัน และรายงานผลทุกเดือน
- **ระยะเวลา:** รับประกันและบำรุงรักษา 1 ปีหลังขึ้นระบบ
