## 1. บทสรุปผู้บริหาร

เราเสนอระบบจองคิวผ่านเว็บและ LINE OA (บัญชีทางการของธนาคารบน LINE) พร้อมโมเดลพยากรณ์ปริมาณลูกค้ารายสาขารายชั่วโมงล่วงหน้า 7 วัน เพื่อลดเวลารอเฉลี่ยที่สาขาลง 30% ภายใน 6 เดือนหลังเปิดใช้

- **ปัญหาวันนี้:** ลูกค้ารอคิวเฉลี่ย 38 นาที และสูงสุด 95 นาทีช่วงวันที่ 25–5 ของเดือน ใน 120 สาขา ขณะที่สาขายังจัดพนักงานไม่ตรงกับช่วงที่คนมาก
- **สิ่งที่ธนาคารได้:** ลูกค้าจองช่วงเวลา 15 นาทีได้ล่วงหน้า, ลูกค้า walk-in เข้าคิวเดียวกันผ่านตู้กดบัตรคิวเดิม, ผู้จัดการสาขาเห็นผลพยากรณ์ 7 วันเพื่อปรับจำนวนช่องบริการ และผู้บริหารเห็น dashboard รายสาขา/ภาค/ทั้งประเทศ
- **วิธีลดความเสี่ยง:** เชื่อมระบบเดิมทั้งหมดผ่าน API โดยไม่แก้ระบบเดิม, นำร่อง 10 สาขาก่อนขยาย, ผ่าน penetration test (การทดสอบเจาะระบบ) ก่อนเปิดใช้จริง
- **ระยะเวลาและมูลค่า:** 6 เดือนนับจากวันลงนามสัญญา · **4,800,000 บาท (ไม่รวม VAT)** รวมค่าพัฒนา, hosting ปีแรก และ MA (บริการบำรุงรักษา) ปีแรก อยู่ในวงเงิน TOR

### สิ่งที่ขอยืนยันก่อนเริ่มงาน

1. **ชั่วโมงที่ SLA ต้องครอบคลุม** — TOR ระบุ Sev 1 ตอบรับใน 30 นาที แต่ไม่ระบุช่วงเวลา ข้อเสนอนี้ใช้บริการ 8x5 (วันทำการ) ถ้าธนาคารต้องการ 24x7 เพราะลูกค้าจองผ่าน LINE ได้ตลอดเวลา เรามีตัวเลือกเสริมในหัวข้อ 7
2. **เวลาทำการของสาขา** — สาขาที่เปิดวันเสาร์-อาทิตย์หรือในห้างสรรพสินค้ามีกี่แห่ง และเปิดกี่โมง (กระทบช่วงพยากรณ์และช่วงเวลา SLA)
3. **ช่องทาง OTP และแจ้งเตือนสำหรับผู้จองผ่านเว็บ** — ใช้ OTP/SMS gateway เดิมของธนาคารได้หรือไม่
4. **สเปก API ของระบบเดิม** — เอกสาร Customer Lookup API, ใบรับรอง mTLS สำหรับ uat/prod และเอกสาร REST API ของตู้ Q-Matic รุ่นที่ใช้ พร้อมวันที่เปิดสภาพแวดล้อมทดสอบให้เรา · เราต้องได้เอกสาร API ภายในเดือนที่ 1 (29 มกราคม 2027) และสภาพแวดล้อมทดสอบพร้อมใบรับรอง mTLS ของ uat ภายในสิ้นเดือนที่ 2 (26 กุมภาพันธ์ 2027) เพื่อเชื่อมระบบได้ตลอดเดือนที่ 3
5. **ตู้ Q-Matic สำหรับทดสอบ** — ขอตู้ Q-Matic รุ่นที่ใช้ หรือตัวจำลองสำหรับทดสอบ 1 ชุด พร้อมเอกสาร REST API ตามข้อ 4 เพื่อทดสอบการออกบัตรคิวและลำดับคิว walk-in ตั้งแต่เดือนที่ 3
6. **วันส่งข้อมูลบัตรคิวย้อนหลัง 24 เดือน** — เราต้องได้ข้อมูลภายในสัปดาห์ที่ 3 หลังลงนามสัญญา เพื่อทดสอบความแม่นยำได้ทันเดือนที่ 4
7. **ผู้ทดสอบเจาะระบบอิสระ** — ผู้ทดสอบที่ธนาคารกำหนดและช่วงเวลาทดสอบ (ข้อเสนอนี้ถือว่าธนาคารว่าจ้างผู้ทดสอบเอง เรารับผิดชอบเตรียมระบบและแก้ไขผลทดสอบ) · แผนงานนี้ขอช่วงทดสอบเจาะระบบ 1–12 เมษายน 2027 และทดสอบซ้ำ 22–23 เมษายน 2027
8. **ระยะเก็บ audit log 2 ปี** — ข้อเสนอนี้เก็บ audit log บนระบบนี้ในประเทศไทย ถ้าธนาคารต้องการส่งต่อเข้าระบบ log กลางของธนาคารด้วย ขอให้แจ้งเพื่อประเมินเพิ่ม
9. **ช่วงเวลาของ hosting ปีแรก** — ข้อเสนอนี้นับ hosting และ license 12 เดือนตั้งแต่วันลงนามสัญญา (มกราคม – ธันวาคม 2027) เพื่อใช้ทั้งช่วงพัฒนาและหลังเปิดใช้ ส่วน MA นับ 1 ปีจากวันขึ้นระบบ ถ้าธนาคารต้องการให้ hosting ครอบคลุมถึงสิ้นปี MA (มิถุนายน 2028) มีตัวเลือกเสริมในหัวข้อ 7

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้างระบบ

ระบบหลักเป็น modular monolith (ระบบเดียวที่แบ่งโมดูลชัดเจน) และแยกเป็นบริการต่างหากเฉพาะส่วนที่มีเหตุผลด้านความปลอดภัยหรือเทคโนโลยี

- **ระบบหลัก** Next.js + Node.js/TypeScript แบ่งโมดูล booking / branch / notification / report
- **ฐานข้อมูล** PostgreSQL แบบ managed เปิด HA (สำรองอัตโนมัติ) + Redis สำหรับ slot lock และ cache
- **คิวงาน** (queue) สำหรับส่งแจ้งเตือน, sync กับตู้คิว และงานพยากรณ์ทุกคืน แยกจาก request ของลูกค้า งานที่ล้มส่งซ้ำอัตโนมัติและแจ้งเตือนทีม
- **core-connector** บริการแยกเครือข่ายสำหรับเรียก Customer Lookup API ผ่าน API Gateway ของธนาคารด้วย mTLS เท่านั้น
- **forecast-service** บริการ Python แยกสำหรับโมเดลพยากรณ์
- **Hosting** cloud ภูมิภาคประเทศไทย แยกสภาพแวดล้อม dev / uat / prod, มี WAF (ไฟร์วอลล์เว็บแอปพลิเคชัน) และป้องกัน DDoS หน้าระบบ · ฐานข้อมูล ไฟล์สำรอง (backup) และ log ทั้งหมดอยู่ในประเทศไทย (ภาคผนวก ก ข้อ 2)
- **การเฝ้าระวัง** ระบบ monitoring และ log กลางในภูมิภาคประเทศไทย แจ้งเตือนเมื่อ error rate สูง ระบบตอบช้า คิวงานค้าง และใบรับรอง TLS ใกล้หมดอายุ

### 4.2 ความปลอดภัย (ตอบ TOR ข้อ 4 ทีละข้อ)

| ข้อกำหนดใน TOR | มาตรการของเรา |

### 4.3 การดูแลโมเดลพยากรณ์

โมเดลจะเปิดใช้ก็ต่อเมื่อผ่านเกณฑ์ MAPE ≤ 20% บนข้อมูล 3 เดือนล่าสุดของธนาคาร และมีทางถอยกลับที่ทดสอบแล้ว

- **การพัฒนา:** เริ่มจากโมเดลอ้างอิงแบบค่าเฉลี่ยวันและชั่วโมงเดียวกัน แล้วพัฒนาโมเดล gradient boosting ที่ใส่ปัจจัยวันหยุดนักขัตฤกษ์ วันเงินเดือนออก และวันหยุดยาว ตามข้อมูลบัตรคิวย้อนหลัง 24 เดือนของธนาคาร
- **การทดสอบ:** รายงาน MAPE ภาพรวม แยกรายสาขา รายช่วงเวลา (รวมช่วงพักเที่ยง) และช่วงวันที่ 25–5 ของเดือน เพราะการพยากรณ์ต่ำกว่าจริงทำให้สาขาจัดคนไม่พอ
- **ก่อนให้สาขาใช้:** รันคู่ขนานแบบ shadow mode (คำนวณแต่ยังไม่แสดงให้สาขา) 2 สัปดาห์ ระหว่างนำร่อง
- **หลังใช้งานจริง:** ทะเบียนรุ่นโมเดลทุกครั้งที่เปลี่ยน, รายงานความแม่นยำรายสัปดาห์บน dashboard, เกณฑ์ถอยกลับรุ่นเดิมหรือโมเดลอ้างอิงอัตโนมัติ เมื่อความแม่นยำต่ำกว่าเกณฑ์ที่ตกลงกับธนาคาร · การปรับจูนโมเดลรอบถัดไปหลังเปิดใช้ ทำภายใต้บริการ MA
- **สาขาเปิดใหม่** ที่ยังไม่มีข้อมูลย้อนหลัง ใช้ค่าของสาขาขนาดใกล้เคียงกันจนมีข้อมูลพอ

- **ถ้าต้องการ 24x7:** ตัวเลือก MA-PREM ในหัวข้อ 7 ให้เวลาตอบรับและแก้ไขข้างต้นนับตลอด 24 ชั่วโมงทุกวัน
- **uptime ≥ 99.5% ต่อเดือน** วัดตลอด 24 ชั่วโมง ไม่รวมช่วง maintenance ที่แจ้งล่วงหน้าอย่างน้อย 3 วัน (จัดนอกเวลาทำการของสาขา)
- ระบบ monitoring เฝ้าระวังตลอด 24 ชั่วโมงและแจ้งเตือนทีมอัตโนมัติ
- รายงาน SLA และ uptime ทุกเดือน, ช่องทางแจ้งปัญหาผ่านระบบ ticket และอีเมลกลางของทีมบริการ

## 9. ทำไมต้องโนวาเทค

เราเคยส่งมอบระบบให้สถาบันการเงิน 2 โครงการตามที่ TOR ข้อ 7 กำหนด และหนึ่งในนั้นเป็นระบบจองคิวสาขาแบบเดียวกับโครงการนี้

| ปี | ธนาคาร | โครงการ | ผลลัพธ์ |
|---|---|---|---|
| 2025 | ธนาคารออมทรัพย์เกษตรไทย (ฝ่ายบริหารเครือข่ายสาขา) | แอปนัดหมายสาขาผ่าน LINE OA และเว็บ | ขึ้นระบบ 40 สาขานำร่องเมื่อ 18 สิงหาคม 2025, slot lock ผ่าน load test 2,000 การจองพร้อมกัน |
| 2024 | ธนาคารสยามรุ่งเรือง (ฝ่ายสินเชื่อรายย่อย) | ระบบติดตามสถานะสินเชื่อออนไลน์ (Loan Tracking Portal) | ขึ้นระบบ 14 กุมภาพันธ์ 2025, เชื่อมระบบสินเชื่อเดิมผ่าน API โดยไม่แก้ระบบเดิม, ผ่าน penetration test ของธนาคาร |

- **ทำได้จริงแล้ว:** ทีมเคยออกแบบและส่งมอบระบบจอง LINE LIFF, slot lock และ branch console ที่ใช้งานจริงในสาขาธนาคาร
- **ไม่แตะระบบเดิม:** เชื่อม core banking และตู้ Q-Matic ผ่าน API ที่ธนาคารมีอยู่
- **ทีมชุดเดียว** ตั้งแต่ออกแบบถึง MA พร้อมรายงานความคืบหน้าทุกสัปดาห์
- **ทดสอบกับผู้ใช้จริงตั้งแต่เดือนแรก** ทั้งลูกค้าและพนักงานสาขา ไม่รอจนถึง UAT

## ภาคผนวก ก: ภาคผนวก PDPA (การคุ้มครองข้อมูลส่วนบุคคล)

ภาคผนวกนี้เป็นส่วนหนึ่งของข้อเสนอ โนวาเทคจะลงนามข้อตกลงการประมวลผลข้อมูลส่วนบุคคล (DPA) กับ ธนาคารนครหลวงพัฒนา จำกัด (มหาชน) ("ผู้ว่าจ้าง") ก่อนเริ่มประมวลผลข้อมูล ตามมาตรา 40 แห่ง พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 โดยมีสาระสำคัญอย่างน้อยดังนี้

1. **ข้อตกลงการประมวลผลข้อมูล (DPA)** — ผู้ว่าจ้างเป็นผู้ควบคุมข้อมูลส่วนบุคคล โนวาเทคเป็นผู้ประมวลผลข้อมูลส่วนบุคคล ประมวลผลตามคำสั่งของผู้ว่าจ้างเท่านั้น จัดให้มีมาตรการรักษาความมั่นคงปลอดภัยที่เหมาะสม ไม่ใช้ผู้ประมวลผลช่วงโดยไม่ได้รับความยินยอมจากผู้ว่าจ้าง และลบหรือคืนข้อมูลส่วนบุคคลเมื่อสิ้นสุดสัญญา
   - มาตรการที่ใช้ในโครงการนี้: เข้ารหัส AES-256 ขณะจัดเก็บและ TLS 1.2 ขึ้นไปขณะส่ง, เลขบัตรประชาชนเก็บเป็นค่า HMAC ไม่เก็บเลขเต็ม, audit log ทุกการเข้าถึงข้อมูลเก็บ 2 ปี (หัวข้อ 4.2)
2. **ที่เก็บข้อมูลในประเทศไทย (data residency)** — ข้อมูลส่วนบุคคลทั้งหมด รวมถึง backup และ log เก็บใน data center ในประเทศไทยเท่านั้น
   - มาตรการที่ใช้ในโครงการนี้: ทุกสภาพแวดล้อม ฐานข้อมูล ไฟล์สำรอง และ log กลาง อยู่บน cloud ภูมิภาคประเทศไทย (หัวข้อ 4.1)
3. **การแจ้งเหตุละเมิดข้อมูล (breach notification)** — โนวาเทคแจ้งผู้ว่าจ้างโดยไม่ชักช้า และไม่เกิน 24 ชั่วโมงนับจากทราบเหตุ พร้อมรายละเอียดเท่าที่ทราบ และให้ความร่วมมือเพื่อให้ผู้ว่าจ้างแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลได้ภายใน 72 ชั่วโมง
