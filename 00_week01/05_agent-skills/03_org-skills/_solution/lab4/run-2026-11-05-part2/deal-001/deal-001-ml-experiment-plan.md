## ข้อสังเกตที่ต้องระวัง

1. **ข้อมูลไม่ใช่ของลูกค้าจริง** — เกษตรไทย 38–40 สาขา, train 10 เดือน · นครหลวงฯ 120 สาขา, ข้อมูล 24 เดือน, มีสาขาเล็กและสาขาในห้างหลายแบบ ตัวเลข 15.2% จึงเป็นแค่หลักฐานว่า "วิธีนี้น่าจะไปถึง" ไม่ใช่คำสัญญา (ตรงกับ internal-notes ข้อ 3)
2. **นิยาม MAPE ยังไม่ได้ตกลงกับธนาคาร** — TOR เขียนแค่ "MAPE ภาพรวม ≤ 20%" ชั่วโมงที่คนมา 0–2 คนทำให้ MAPE พุ่ง (หรือหารศูนย์ไม่ได้) สาขาเล็ก 120 แห่งจะดึงค่าขึ้นแรงกว่าในเกษตรไทย → ต้องตกลงในเดือน 1 ว่า (ก) รวมทุกชั่วโมงหรือตัดชั่วโมงที่ actual < k (ข) เฉลี่ยแบบ branch-hour หรือถ่วงน้ำหนัก (WAPE) (ค) นับเฉพาะเวลาทำการจริงของแต่ละสาขา · P0-7 จะวัดว่านิยามต่างกันทำให้ตัวเลขต่างกันแค่ไหน
3. **วิธีประเมินยังไม่ตรงการใช้งาน** — การใช้งานจริงคือรันทุกคืนแล้วพยากรณ์ล่วงหน้า 1–7 วัน ต้องตรวจว่า lag/rolling ใน r02/r03 ใช้เฉพาะข้อมูลถึงวัน origin (กันข้อมูลรั่ว) และรายงาน MAPE แยก horizon
4. **ช่วงเที่ยงพยากรณ์ต่ำ −20 ถึง −30%** ในสาขาย่านออฟฟิศ (จากโน้ต ยังไม่มีตัวเลขจาก run) — metric รวม 15.2% ไม่สะท้อน และ proposal 4.3 สัญญาว่าจะรายงานช่วงพักเที่ยงและวันที่ 25–5 แยก
5. **holiday week มีตัวอย่างน้อย** — test ก.ค.–ก.ย. มีวันหยุดไม่กี่สัปดาห์ ส่วน "3 เดือนล่าสุด" ของธนาคารตอนส่งข้อมูล ม.ค. 2027 คือ ต.ค.–ธ.ค. 2026 ซึ่งมีปีใหม่และวันหยุดยาวหลายช่วง ยากกว่าช่วงที่เราทดสอบ
6. **การใช้โค้ด/notebook ของงานเกษตรไทยกับนครหลวงฯ** — ใช้วิธีการได้ แต่สิทธิ์ reuse โค้ดยังรอตรวจ (internal-notes D2) · pipeline ที่จะใช้ใน P1 ควรเขียนใหม่ใน repo ทีม ไม่ยก notebook ของ DS สัญญาจ้างไปตรง ๆ
