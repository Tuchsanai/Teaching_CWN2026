# ข้อเสนอโครงการ: พอร์ทัลยื่นคำร้องโต้แย้งรายการบัตรเครดิต (Card Dispute Portal)

**เสนอต่อ:** ธนาคารเอเชียไทยสากล จำกัด (มหาชน) — ฝ่ายปฏิบัติการบัตรเครดิต
**อ้างอิง TOR:** ATI-IT-2026-052
**เลขที่เอกสาร:** NVT-PRP-2026-[รอเลขจากทะเบียนเอกสาร] · **วันที่:** 4 พฤศจิกายน 2026
**จัดทำโดย:** กฤต ธนากร (ฝ่ายขาย) · ไอศวรรย์ บุญมา (Solution Architect)

## 1. บทสรุปผู้บริหาร

เราเสนอพอร์ทัลออนไลน์ที่ให้ผู้ถือบัตรยื่นคำร้องโต้แย้งรายการได้ครบในครั้งเดียว พร้อมระบบงานเจ้าหน้าที่ที่มี SLA timer (ตัวนับวันครบกำหนดตามกฎเครือข่ายบัตร) เพื่อลดเวลาเริ่มตรวจสอบจากเฉลี่ย 9 วันเหลือไม่เกิน 2 วันทำการ

ปัจจุบันธนาคารรับคำร้องประมาณ 3,500 รายการต่อเดือนผ่านแบบฟอร์มกระดาษและอีเมล และต้องโทรตามเอกสารเพราะข้อมูลไม่ครบ ระบบที่เสนอแก้ที่ต้นทาง: แบบฟอร์มถามต่อตามประเภทเหตุผล และไม่ให้ส่งคำร้องจนกว่าข้อมูลและหลักฐานที่จำเป็นครบ คำร้องจึงเข้าคิวเจ้าหน้าที่พร้อมตรวจสอบได้ทันที

- ระยะเวลา **4 เดือน** นับจากวันลงนามสัญญา รวม UAT (การทดสอบรับมอบโดยผู้ใช้ของธนาคาร) 3 สัปดาห์ ตามข้อ 5 ของ TOR
- มูลค่ารวม **2,200,000 บาท (ไม่รวม VAT)** ครอบคลุมค่าพัฒนา, hosting (ค่าระบบ cloud) ปีแรก และ MA (บริการดูแลระบบ) ปีแรก ตามข้อ 6 ของ TOR
- **ไม่เก็บเลขบัตรเต็มในระบบใหม่** ใช้ token (รหัสแทนเลขบัตร) จาก CardLink และเชื่อมต่อ CardLink, SMS gateway และ email gateway **ผ่าน API (ช่องทางเชื่อมต่อระบบ) โดยไม่แก้ไขระบบเดิมของธนาคาร**

## 2. ความเข้าใจความต้องการ

เราเข้าใจว่าเป้าหมายหลักคือให้คำร้องที่เข้ามา "ครบตั้งแต่รอบแรก" เพื่อให้ทีมรับเรื่องเลิกโทรตามเอกสาร และให้ผู้ถือบัตรติดตามสถานะได้เอง

| ข้อ TOR | ความต้องการ | สิ่งที่เราส่งมอบ |

| 2.3 | ติดตามสถานะเองโดยไม่ต้องโทร call center | หน้าติดตามสถานะ 5 ขั้น + แจ้งเตือนทาง SMS/อีเมลทุกครั้งที่สถานะเปลี่ยน |

| 3.1 | เลือกรายการจากรายการย้อนหลัง 120 วัน | ดึงรายการจาก CardLink ตาม token แสดงเลขบัตร 4 หลักท้ายเท่านั้น |
| 3.1 | เหตุผล 6 ประเภทตามมาตรฐานเครือข่ายบัตร + คำถามเพิ่มเติมตามประเภท | ชุดคำถามตามประเภท ปรับข้อความและรายการหลักฐานได้จากหน้าผู้ดูแลระบบ |
| 3.1 | แนบหลักฐาน PDF/JPG/PNG สูงสุด 5 ไฟล์ ไฟล์ละไม่เกิน 10 MB | ตรวจชนิดไฟล์จากเนื้อไฟล์จริง สแกนมัลแวร์ก่อนจัดเก็บ เก็บแบบเข้ารหัส |
| 3.1 | ติดตามสถานะ 5 ขั้น และแจ้งเตือน SMS/อีเมล | สถานะ 5 ขั้นตามที่ธนาคารกำหนด แจ้งเตือนผ่านคิวงานแยก ส่งซ้ำอัตโนมัติเมื่อส่งไม่สำเร็จ |
| 3.2 | คิวคำร้อง, มอบหมายงาน, ขอเอกสารเพิ่ม, บันทึกผล | Back-office (ระบบงานเจ้าหน้าที่) บนเบราว์เซอร์: คิว กรองตามประเภท/สถานะ/วันครบกำหนด, ขอเอกสารเพิ่มแล้วผู้ถือบัตรแนบผ่านพอร์ทัลได้ทันที |
| 3.2 | SLA timer ตามกฎเครือข่ายบัตร เตือนเมื่อเหลือ 5 วัน | นับวันครบกำหนดรายคำร้องตามตารางกฎที่ธนาคารยืนยัน เตือนในหน้าคิวและทางอีเมลเมื่อเหลือ 5 วัน |
| 3.2 | SSO ด้วย Active Directory | เข้าสู่ระบบผ่าน Active Directory ของธนาคาร (SAML หรือ OpenID Connect ตามที่ธนาคารใช้) สิทธิ์ตามบทบาท |
| 3.3 | CardLink REST API: ดึงรายการและสร้างเคส dispute | ตัวเชื่อม CardLink แยกโมดูล สร้างเคสใน CardLink เมื่อคำร้องครบ ส่งซ้ำได้โดยไม่เกิดเคสซ้ำ |
| 3.3 | SMS gateway และ email gateway ของธนาคาร | ตัวเชื่อมทั้งสองช่องทางผ่านคิวงานเดียวกัน บันทึกผลการส่งทุกข้อความ |
| 4 | PCI DSS, เข้ารหัส, audit log 2 ปี, PDPA, pentest | มาตรการตอบทีละข้อในหัวข้อ 4.2 |
| 5 | 4 เดือน รวม UAT ≥ 3 สัปดาห์ · MA 1 ปี | แผนงานหัวข้อ 6 · SLA หัวข้อ 8 |
| 6 | ไม่เกิน 2,200,000 บาท (ไม่รวม VAT) รวมพัฒนา, hosting และ MA ปีแรก | ราคาหัวข้อ 7 รวมก่อน VAT 2,200,000 บาท |

### สิ่งที่ขอยืนยันก่อนเริ่มงาน

1. **CardLink API** — เอกสาร API และ sandbox, วิธีตรวจเลขบัตร + วันเกิดแล้วออก token, ขีดจำกัดจำนวนครั้งเรียก และ **ช่วงเวลาที่ API ให้บริการ** (มีช่วงปิด batch กลางคืนหรือไม่)
2. **เบอร์มือถือสำหรับส่ง OTP** — ดึงจาก CardLink หรือระบบอื่น และ SMS gateway ของธนาคารรองรับข้อความ OTP หรือไม่
3. **กฎ SLA ของเครือข่ายบัตร** — ตารางระยะเวลาตามประเภทเหตุผลและเครือข่ายบัตรที่ธนาคารใช้ นับเป็นวันปฏิทินหรือวันทำการ
4. **สถานะ 5 ขั้น** — ชื่อและเงื่อนไขเปลี่ยนสถานะ และสถานะใดที่ต้องแจ้งเตือนผู้ถือบัตร
5. **Active Directory** — ใช้ SAML หรือ OpenID Connect (ผ่าน AD FS / Entra ID) และกลุ่มผู้ใช้ที่ใช้กำหนดบทบาท
6. **การแจ้งเตือน** — ค่า SMS และอีเมลคิดในบัญชี gateway ของธนาคาร (ไม่รวมในราคานี้) และต้องการทั้งสองช่องทางหรือช่องทางเดียว
7. **Penetration test** — ผู้ทดสอบที่ธนาคารกำหนด จำนวนรอบทดสอบซ้ำ และผู้รับผิดชอบค่าใช้จ่าย
8. **การเชื่อมเครือข่าย** — ช่องทางจาก cloud ไปยัง CardLink และ gateway ของธนาคาร (VPN / private link) และเงื่อนไขของฝ่าย IT Security
9. **ข้อมูลเดิม** — คำร้องที่ค้างอยู่ในระบบกระดาษ/อีเมลต้องย้ายเข้าระบบใหม่หรือไม่ (ราคานี้ไม่รวมการย้ายข้อมูล)

## 3. โซลูชันที่เสนอ

ระบบประกอบด้วย 2 หน้าจอหลักบนฐานข้อมูลเดียว และตัวเชื่อมระบบของธนาคาร 3 ตัว

| ส่วน | รายละเอียด |
|---|---|
| Cardholder Portal | เว็บ responsive (ใช้ได้ทั้งมือถือและคอมพิวเตอร์) เข้าสู่ระบบด้วยเลขบัตร + วันเกิด + OTP, เลือกรายการ, ตอบคำถามตามประเภท, แนบหลักฐาน, ยื่นคำร้อง — ไม่เกิน 4 ขั้นตอน |
| ติดตามสถานะ | สถานะ 5 ขั้นพร้อมวันที่, แจ้งเมื่อธนาคารขอเอกสารเพิ่ม และแนบเพิ่มได้ในหน้าเดียวกัน |
| Back-office | คิวคำร้อง, มอบหมายงาน, ขอเอกสารเพิ่ม, บันทึกผล, ประวัติการดำเนินการต่อคำร้อง, เข้าสู่ระบบด้วย Active Directory |
| SLA Timer | วันครบกำหนดรายคำร้องตามกฎเครือข่ายบัตร, เรียงคิวตามความเร่งด่วน, เตือนเมื่อเหลือ 5 วัน |
| CardLink Connector | ตรวจตัวตน/ออก token, ดึงรายการย้อนหลัง 120 วัน, สร้างเคส dispute |
| Notification | ส่ง OTP และแจ้งสถานะผ่าน SMS gateway และ email gateway ของธนาคาร |
| Admin & Report | ตั้งค่าคำถามและรายการหลักฐานตามประเภท, รายงานจำนวนคำร้อง, เวลาจากยื่นถึงเริ่มตรวจสอบ, คำร้องที่ใกล้ครบกำหนด, ส่งออก Excel |

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้าง

ระบบออกแบบให้เลขบัตรเต็มไม่ถูกเก็บที่ใดในระบบใหม่ และทุกการเชื่อมต่อระบบธนาคารผ่านจุดเดียวที่ควบคุมได้

- **Modular monolith** (Next.js + Node.js/TypeScript) แยกโมดูล portal / back-office / notification / report — ทีมเดียวดูแล deploy และแก้ปัญหาได้เร็ว
- **integration module** เป็นจุดเดียวที่เรียก CardLink และ gateway ของธนาคาร ผ่านช่องทางเครือข่ายที่ฝ่าย IT ธนาคารกำหนด
- **PostgreSQL** (managed) เป็นฐานข้อมูลหลัก · **Redis** สำหรับ session, OTP และ rate limit
- **คิวงาน (BullMQ)** สำหรับส่ง SMS/อีเมลและสร้างเคสใน CardLink ทุกงานส่งซ้ำได้โดยไม่เกิดผลซ้ำ งานที่ล้มเหลวครบกำหนดแจ้งเตือนทีมทันที
- ไฟล์หลักฐานเก็บใน object storage แบบเข้ารหัส เข้าถึงได้ผ่านระบบเท่านั้น
- Hosting บน **cloud ภูมิภาคประเทศไทยเท่านั้น** แยกสภาพแวดล้อม dev / uat / prod

### 4.2 ความปลอดภัย (ตอบ TOR ข้อ 4 ทีละข้อ)

| ข้อกำหนด TOR | มาตรการของเรา |
|---|---|
| PCI DSS: ห้ามเก็บเลขบัตรเต็มในระบบใหม่ ใช้ token จาก CardLink | เลขบัตรที่ผู้ถือบัตรกรอกส่งต่อไป CardLink ทันทีผ่านช่องทางเข้ารหัส แล้วใช้ token แทนในทุกส่วนของระบบ ไม่บันทึกเลขบัตรเต็มลงฐานข้อมูล, cache, log หรือไฟล์ใด ๆ · ตั้งค่า log ให้ตัดค่าเลขบัตรออกอัตโนมัติ และทดสอบว่าไม่พบเลขบัตรใน log ก่อน UAT · ไม่ขอรหัส CVV |
| แสดงเลขบัตร 4 หลักท้ายเท่านั้น | ทุกหน้าจอ อีเมล SMS และรายงาน แสดงเฉพาะ 4 หลักท้าย ทั้งฝั่งผู้ถือบัตรและเจ้าหน้าที่ |
| เข้ารหัสขณะส่ง | TLS 1.2 ขึ้นไปทุกช่องทาง ปิด protocol รุ่นเก่า, การเชื่อมต่อ CardLink และ gateway ผ่านช่องทางที่ธนาคารกำหนด, แจ้งเตือนใบรับรองที่ใกล้หมดอายุล่วงหน้า 21 วัน |
| เข้ารหัสขณะจัดเก็บ | ฐานข้อมูล, backup และไฟล์หลักฐานเข้ารหัส AES-256 กุญแจเก็บใน key management service ของ cloud |
| Audit log เก็บ 2 ปี | บันทึกผู้ใช้ เวลา การกระทำ และคำร้องที่เข้าถึง ทุกครั้งที่เจ้าหน้าที่เปิดดู แก้ไข หรือดาวน์โหลดหลักฐาน เก็บแบบแก้ไขไม่ได้ในภูมิภาคไทย 2 ปี |
| พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 | เก็บข้อมูลเท่าที่จำเป็นต่อการพิจารณาคำร้อง, แจ้งวัตถุประสงค์ก่อนยื่นคำร้อง, ข้อมูลอยู่ใน cloud ภูมิภาคไทย, กำหนดระยะเก็บไฟล์หลักฐานตามนโยบายของธนาคาร, กระบวนการแจ้งเหตุข้อมูลรั่วไหลภายในเวลาที่กฎหมายกำหนด, ใช้ข้อมูลทดสอบแบบสังเคราะห์ ไม่ใช้ข้อมูลผู้ถือบัตรจริง |
| Penetration test ก่อนเปิดใช้งาน | กำหนด penetration test (การทดสอบเจาะระบบ) ในเดือนที่ 3 ก่อน UAT, แก้ช่องโหว่ระดับสูงและวิกฤตทั้งหมดก่อนเปิดใช้ และทดสอบซ้ำ |
| (มาตรการเพิ่มเติม) | Web Application Firewall + ป้องกัน DDoS, จำกัดจำนวนครั้งกรอกเลขบัตร/วันเกิด/OTP ผิด และล็อกชั่วคราว, สิทธิ์ตามบทบาท (เจ้าหน้าที่ / หัวหน้าทีม / ผู้ดูแลระบบ), สแกนมัลแวร์ไฟล์แนบ, สแกนช่องโหว่ไลบรารีทุกครั้งที่ deploy, ทีมทุกคนลงนาม NDA ก่อนได้รับสิทธิ์ |

เราจะกรอกแบบสอบถามความปลอดภัยผู้ให้บริการ (vendor security questionnaire) ของธนาคาร และยื่นพร้อมข้อเสนอนี้

## 9. ทำไมต้องโนวาเทค

เราทำระบบให้ธนาคารที่เชื่อมระบบเดิมผ่าน API ผ่าน penetration test ของธนาคาร และขึ้นระบบได้จริงมาแล้ว

| ปี | ลูกค้า | งาน | ผลลัพธ์ |
|---|---|---|---|
| 2024 | ธนาคารสยามรุ่งเรือง — ฝ่ายสินเชื่อรายย่อย | ระบบติดตามสถานะสินเชื่อออนไลน์ (Loan Tracking Portal) | ขึ้นระบบ 14 กุมภาพันธ์ 2025, เชื่อมระบบสินเชื่อเดิมผ่าน API โดยไม่แก้ระบบเดิม, ผ่าน penetration test ของธนาคาร |
| 2025 | ธนาคารออมทรัพย์เกษตรไทย — ฝ่ายบริหารเครือข่ายสาขา | แอปนัดหมายสาขาผ่าน LINE OA และเว็บ | ขึ้นระบบ 40 สาขานำร่อง 18 สิงหาคม 2025, slot lock ผ่าน load test 2,000 การจองพร้อมกัน |

- **เคยทำพอร์ทัลติดตามสถานะให้ธนาคารมาแล้ว** — หน้าติดตามสถานะ การแจ้งเตือนผ่านคิวงาน และการเชื่อมระบบเดิมผ่าน API ใช้แนวทางที่ผ่านการใช้งานจริงกับระบบสินเชื่อ
- **เชื่อมระบบเดิมผ่าน API โดยไม่แก้ระบบเดิม** — ลดภาระฝ่าย IT ของธนาคาร
- **ทีมชุดเดียวตั้งแต่ออกแบบจนดูแลหลังขึ้นระบบ** ไม่ส่งต่องานระหว่างผู้รับจ้างหลายราย
- **ทดสอบกับผู้ใช้จริงตั้งแต่เดือนแรก** — ออกแบบหน้าคิวและ SLA timer ร่วมกับทีมรับเรื่องโต้แย้งรายการก่อนเริ่มพัฒนา
- **รายงานความคืบหน้าทุกสัปดาห์** พร้อมความเสี่ยงและสิ่งที่ต้องการจากธนาคาร
