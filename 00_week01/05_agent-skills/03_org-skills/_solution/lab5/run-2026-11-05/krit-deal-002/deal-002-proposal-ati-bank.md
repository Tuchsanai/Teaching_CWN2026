# ข้อเสนอโครงการ: พอร์ทัลยื่นคำร้องโต้แย้งรายการบัตรเครดิต (Card Dispute Portal)

**เสนอต่อ:** ธนาคารเอเชียไทยสากล จำกัด (มหาชน) — ฝ่ายปฏิบัติการบัตรเครดิต

## 1. บทสรุปผู้บริหาร

เราเสนอพอร์ทัลให้ผู้ถือบัตรยื่นคำร้องโต้แย้งรายการได้ครบในครั้งเดียว โดยตั้งเป้าให้ธนาคารเริ่มตรวจสอบคำร้องได้ภายใน 2 วันทำการ จากเดิมเฉลี่ย 9 วัน

ปัจจุบันธนาคารรับคำร้องประมาณ 3,500 รายการต่อเดือนผ่านแบบฟอร์มกระดาษและอีเมล คำร้องจำนวนมากข้อมูลไม่ครบ เจ้าหน้าที่ต้องโทรตามเอกสารก่อนเริ่มตรวจสอบได้

พอร์ทัลที่เสนอแก้ที่ต้นเหตุ 3 จุด:
- **ฟอร์มถามต่อตามประเภทเหตุผล** 6 ประเภทตามมาตรฐานเครือข่ายบัตร และไม่ให้ส่งคำร้องจนกว่าข้อมูลและหลักฐานที่จำเป็นจะครบ
- **หน้าจอเจ้าหน้าที่** มีคิวงาน การมอบหมาย และ SLA timer (ตัวนับเวลาตามกำหนดของเครือข่ายบัตร) แทนการนับวันใน Excel
- **ผู้ถือบัตรติดตามสถานะเองได้** 5 ขั้น พร้อมแจ้งเตือนทาง SMS และอีเมล โดยไม่ต้องโทร call center

ระบบไม่เก็บเลขบัตรเต็ม ใช้ token (รหัสแทนเลขบัตร) จากระบบ CardLink ตามแนวทาง PCI DSS และเชื่อมระบบเดิมของธนาคารผ่าน API โดยไม่แก้ระบบเดิม

**ระยะเวลา 4 เดือน** (กุมภาพันธ์ – พฤษภาคม 2027) ขึ้นระบบได้ก่อน 31 พฤษภาคม 2027 · **มูลค่ารวม 2,200,000 บาท (ไม่รวม VAT)** ครอบคลุมค่าพัฒนา hosting ปีแรก และ MA ปีแรก ตามวงเงินใน TOR

### สิ่งที่ขอยืนยันก่อนเริ่มงาน

1. **CardLink API** — เอกสาร API, วันที่เปิด sandbox (ระบบทดสอบ) ให้ทีมเรา (ต้องได้ภายในสัปดาห์ที่ 2 ของโครงการ), และ API ตรวจเลขบัตร + วันเกิด และออก token มีอยู่แล้วหรือไม่
2. **SMS และ email gateway** — เอกสาร API และช่องทางเชื่อมต่อ ค่าส่งข้อความเป็นของธนาคาร
3. **SSO** — Active Directory ของธนาคารรองรับ SAML หรือ OpenID Connect (มาตรฐานการเข้าระบบครั้งเดียว) ผ่านระบบใด
4. **Penetration test** — ธนาคารเป็นผู้ทดสอบเองหรือว่าจ้างผู้ทดสอบภายนอก ราคาของเรารวมการแก้ไขช่องโหว่และรองรับการทดสอบซ้ำ แต่ไม่รวมค่าผู้ทดสอบภายนอก
5. **WAF (ระบบกรองการโจมตีเว็บ)** — ธนาคารมี WAF ที่ใช้คุ้มครองพอร์ทัลนี้ได้หรือไม่ ถ้าไม่มี เราเสนอเป็นตัวเลือกเสริมในหัวข้อ 7
6. **ชั่วโมงให้บริการ MA** — ราคาหลักเป็น MA 8x5 ถ้าธนาคารต้องการ 24x7 มีตัวเลือกในหัวข้อ 7
7. **กฎเครือข่ายบัตร** — ธนาคารส่งรายการประเภทเหตุผล คำถามต่อ และกำหนดเวลาของแต่ละประเภทให้ภายในเดือนแรก
8. **ระยะเก็บข้อมูลคำร้องและไฟล์หลักฐาน** — ตามนโยบายของธนาคาร (audit log เก็บ 2 ปีตาม TOR)

## 3. โซลูชันที่เสนอ

ระบบมี 5 ส่วน ใช้ฐานข้อมูลเดียวกันและเชื่อมระบบเดิมของธนาคารผ่าน API ทั้งหมด

| ส่วน | รายละเอียด |
|---|---|
| Cardholder Portal (เว็บผู้ถือบัตร) | เว็บ responsive (ปรับตามขนาดจอ) ใช้ได้ทั้งมือถือและคอมพิวเตอร์ · เข้าสู่ระบบด้วยเลขบัตร + วันเกิด + OTP · เลือกรายการ 120 วัน → เลือกเหตุผล → ตอบคำถามต่อ → แนบหลักฐาน · ติดตามสถานะ 5 ขั้น |
| Officer Console (หน้าจอเจ้าหน้าที่) | คิวคำร้อง กรองตามประเภท/สถานะ/วันครบกำหนด · มอบหมายงาน · ขอเอกสารเพิ่ม · บันทึกผล · SLA timer และแจ้งเตือนเมื่อเหลือ 5 วัน |
| Admin (ผู้ดูแลระบบ) | ตั้งค่าประเภทเหตุผล คำถามต่อ กำหนดเวลา SLA ข้อความแจ้งเตือน · กำหนดสิทธิ์ตามกลุ่มใน AD · รายงานจำนวนคำร้องและเวลาเริ่มตรวจสอบเฉลี่ย |
| Integration (การเชื่อมต่อ) | CardLink: ตรวจตัวตน, รับ token, ดึงรายการ, สร้างเคส dispute · SMS/email gateway · Active Directory |
| Notification (การแจ้งเตือน) | คิวงานส่ง SMS และอีเมลแยกจากระบบหลัก ส่งซ้ำอัตโนมัติ บันทึกผลการส่งทุกครั้ง |

เราจะสาธิตต้นแบบหน้าจอเจ้าหน้าที่ (คิว + SLA timer) ให้ทีมรับเรื่องโต้แย้งรายการของธนาคารดูก่อนยื่นข้อเสนอ และทดสอบหน้าจอกับผู้ใช้จริงอีกครั้งในเดือนแรกของโครงการ

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้างระบบ

ระบบเป็น modular monolith (แอปเดียวแบ่งโมดูลชัดเจน) ดูแลง่ายและขยายได้โดยไม่ต้องเขียนใหม่

- Next.js + Node.js/TypeScript แบ่งโมดูล cardholder / officer / admin / integration / notification
- PostgreSQL (managed) เก็บคำร้อง audit log และตัวนับจำนวนครั้งขอ OTP
- คิวงานแยกสำหรับแจ้งเตือนและการส่งเคสเข้า CardLink — ถ้า gateway หรือ CardLink ช้า ผู้ถือบัตรยังยื่นคำร้องได้ตามปกติ
- ไฟล์หลักฐานเก็บใน object storage (ที่เก็บไฟล์) แบบเข้ารหัส แยกจากฐานข้อมูล
- Hosting บน cloud ภูมิภาคประเทศไทย ทุกส่วนรวม backup และ log อยู่ในประเทศไทย
- รองรับปริมาณ 3,500 คำร้องต่อเดือนตาม TOR และขยายขนาดเครื่องได้เมื่อปริมาณเพิ่ม

### 4.2 ความปลอดภัย

เราตอบข้อกำหนดความปลอดภัยใน TOR ข้อ 4 ทุกข้อด้วยมาตรการดังนี้

| ข้อกำหนดใน TOR | มาตรการ |
|---|---|
| PCI DSS: ห้ามเก็บเลขบัตรเต็ม ใช้ token จาก CardLink | เลขบัตรที่ผู้ถือบัตรกรอกตอนเข้าสู่ระบบส่งต่อไปยัง CardLink ทันทีผ่านช่องทางเข้ารหัส **ไม่บันทึกลงฐานข้อมูล log หรือ cache** ระบบเก็บเฉพาะ token · ปิดบังเลขบัตรในระดับ logger อีกชั้น |
| PCI DSS: แสดงเลขบัตร 4 หลักท้ายเท่านั้น | ทุกหน้าจอทั้งผู้ถือบัตรและเจ้าหน้าที่ แสดง 4 หลักท้ายเท่านั้น รวมถึงข้อความ SMS และอีเมล |
| เข้ารหัสข้อมูลขณะส่ง | TLS 1.2 ขึ้นไปทุกช่องทาง ทั้งฝั่งผู้ใช้และการเชื่อมต่อ CardLink / gateway |
| เข้ารหัสข้อมูลขณะจัดเก็บ | AES-256 สำหรับฐานข้อมูล ไฟล์หลักฐาน และ backup · วันเกิดใช้ตรวจตัวตนผ่าน CardLink ไม่เก็บในระบบ |
| audit log เก็บ 2 ปี | บันทึกการเข้าระบบ การเปิดดูคำร้อง การเปลี่ยนสถานะ และการเปลี่ยนสิทธิ์ ทั้งฝั่งผู้ถือบัตรและเจ้าหน้าที่ · แก้ไขหรือลบไม่ได้ · เก็บ 2 ปี |
| ปฏิบัติตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 | เก็บข้อมูลเท่าที่จำเป็นต่อคำร้อง · เจ้าหน้าที่เห็นเฉพาะคำร้องตามสิทธิ์ · ใช้ข้อมูลสังเคราะห์ในการทดสอบ ไม่คัดลอกข้อมูลจริงออกนอกระบบ · ลบสำเนาข้อมูลผู้ถือบัตรที่ใช้ระหว่างโครงการภายใน 90 วันหลังส่งมอบ · DPA, data residency และการแจ้งเหตุละเมิดข้อมูลภายใน 24 ชั่วโมง ดู **ภาคผนวก ก: ภาคผนวก PDPA** |
| ผ่าน penetration test ก่อนเปิดใช้งาน | กำหนด penetration test (การทดสอบเจาะระบบ) ในเดือนที่ 3 ก่อน UAT · แก้ไขช่องโหว่ระดับ critical และ high ทั้งหมด และรองรับการทดสอบซ้ำก่อนเปิดใช้งาน |

มาตรการเพิ่มเติม:
- เข้าสู่ระบบเจ้าหน้าที่ผ่าน SSO ของธนาคาร สิทธิ์ตามบทบาท (เจ้าหน้าที่ / หัวหน้าทีม / ผู้ดูแลระบบ)
- OTP หมดอายุใน 5 นาที จำกัดจำนวนครั้งขอและกรอกผิด ป้องกันการเดาเลขบัตร
- ไฟล์ที่อัปโหลดตรวจชนิดไฟล์จริงและสแกนมัลแวร์ก่อนเจ้าหน้าที่เปิดได้
- สแกนช่องโหว่ของโค้ดและ library ทุกรอบก่อนปล่อยงาน
- กรอกแบบ vendor security questionnaire ของธนาคารและส่งพร้อมข้อเสนอนี้

## ภาคผนวก ก: ภาคผนวก PDPA (การคุ้มครองข้อมูลส่วนบุคคล)

ภาคผนวกนี้เป็นส่วนหนึ่งของข้อเสนอ โนวาเทคจะลงนามข้อตกลงการประมวลผลข้อมูลส่วนบุคคล (DPA) กับ ธนาคารเอเชียไทยสากล จำกัด (มหาชน) ("ผู้ว่าจ้าง") ก่อนเริ่มประมวลผลข้อมูล ตามมาตรา 40 แห่ง พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 โดยมีสาระสำคัญอย่างน้อยดังนี้

1. **ข้อตกลงการประมวลผลข้อมูล (DPA)** — ผู้ว่าจ้างเป็นผู้ควบคุมข้อมูลส่วนบุคคล โนวาเทคเป็นผู้ประมวลผลข้อมูลส่วนบุคคล ประมวลผลตามคำสั่งของผู้ว่าจ้างเท่านั้น จัดให้มีมาตรการรักษาความมั่นคงปลอดภัยที่เหมาะสม ไม่ใช้ผู้ประมวลผลช่วงโดยไม่ได้รับความยินยอมจากผู้ว่าจ้าง และลบหรือคืนข้อมูลส่วนบุคคลเมื่อสิ้นสุดสัญญา
   - มาตรการทางเทคนิค: เข้ารหัส AES-256 ขณะจัดเก็บ (ฐานข้อมูล ไฟล์หลักฐาน backup) และ TLS 1.2 ขึ้นไปขณะส่ง · ไม่เก็บเลขบัตรเต็ม ใช้ token จาก CardLink · audit log แก้ไขหรือลบไม่ได้ เก็บ 2 ปี (หัวข้อ 4.2)
2. **ที่เก็บข้อมูลในประเทศไทย (data residency)** — ข้อมูลส่วนบุคคลทั้งหมด รวมถึง backup และ log เก็บใน data center ในประเทศไทยเท่านั้น
   - มาตรการทางเทคนิค: hosting บน cloud ภูมิภาคประเทศไทยทุกส่วน รวม object storage ไฟล์หลักฐาน backup และ log (หัวข้อ 4.1)
3. **การแจ้งเหตุละเมิดข้อมูล (breach notification)** — โนวาเทคแจ้งผู้ว่าจ้างโดยไม่ชักช้า และไม่เกิน 24 ชั่วโมงนับจากทราบเหตุ พร้อมรายละเอียดเท่าที่ทราบ และให้ความร่วมมือเพื่อให้ผู้ว่าจ้างแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลได้ภายใน 72 ชั่วโมง
