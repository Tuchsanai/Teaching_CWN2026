# ข้อเสนอโครงการ: พอร์ทัลยื่นคำร้องโต้แย้งรายการบัตรเครดิต (Card Dispute Portal)

**เสนอต่อ:** ธนาคารเอเชียไทยสากล จำกัด (มหาชน) — ฝ่ายปฏิบัติการบัตรเครดิต

## 1. บทสรุปผู้บริหาร

เราเสนอพัฒนาพอร์ทัลให้ผู้ถือบัตรยื่นคำร้องโต้แย้งรายการออนไลน์ได้ครบในครั้งเดียว เพื่อลดเวลาเริ่มตรวจสอบจาก 9 วันเหลือไม่เกิน 2 วันทำการ

ปัจจุบันธนาคารรับคำร้องประมาณ 3,500 รายการต่อเดือนผ่านแบบฟอร์มกระดาษและอีเมล ทำให้ต้องรอเฉลี่ย 9 วันกว่าจะเริ่มตรวจสอบ เพราะข้อมูลไม่ครบและเจ้าหน้าที่ต้องโทรตามเอกสาร

พอร์ทัลที่เสนอแก้ที่ต้นเหตุ 3 จุด:
- **ข้อมูลครบตั้งแต่ยื่น** — แบบฟอร์มถามคำถามตามประเภทเหตุผล 6 ประเภทของเครือข่ายบัตร และบังคับแนบหลักฐานที่จำเป็นก่อนส่ง
- **เคสเข้าคิวเจ้าหน้าที่ทันที** — สร้างเคส dispute ใน CardLink อัตโนมัติผ่าน API พร้อม SLA timer ตามกฎเครือข่ายบัตร
- **ผู้ถือบัตรติดตามสถานะเอง** — สถานะ 5 ขั้น พร้อมแจ้งเตือนทาง SMS และอีเมล

ระยะเวลา 4 เดือนนับจากวันลงนามสัญญา รวม UAT 3 สัปดาห์ มูลค่ารวม **2,200,000 บาท (ไม่รวม VAT)** ครอบคลุมค่าพัฒนา hosting ปีแรก และ MA (บริการดูแลรักษาระบบ) ปีแรก ตามวงเงินใน TOR

| 2.2 | เริ่มตรวจสอบภายใน 2 วันทำการ | สร้างเคสใน CardLink ทันทีที่ยื่น เข้าคิวเจ้าหน้าที่พร้อมเอกสารครบ และรายงานเวลาตั้งแต่ยื่นจนเริ่มตรวจสอบ |
| 2.3 | ติดตามสถานะได้เองโดยไม่ต้องโทร | หน้าติดตามสถานะ 5 ขั้น + แจ้งเตือน SMS/อีเมลทุกครั้งที่สถานะเปลี่ยน |
| 3.1 | เข้าสู่ระบบด้วยเลขบัตร 16 หลัก + วันเดือนปีเกิด + OTP ทาง SMS | ตรวจสอบตัวตนกับ CardLink และส่ง OTP ผ่าน SMS gateway ของธนาคาร โดยไม่เก็บเลขบัตรเต็ม (ดูหัวข้อ 4.2) |
| 3.1 | เลือกรายการย้อนหลัง 120 วัน | ดึงรายการจาก CardLink แบบทันที (real-time) แสดงเลขบัตร 4 หลักท้าย |
| 3.1 | เหตุผล 6 ประเภท + คำถามตามประเภท | ชุดคำถามตั้งค่าได้โดยเจ้าหน้าที่ ไม่ต้องแก้โค้ดเมื่อกฎเครือข่ายบัตรเปลี่ยน |
| 3.1 | แนบหลักฐาน PDF/JPG/PNG สูงสุด 5 ไฟล์ ไฟล์ละไม่เกิน 10 MB | ตรวจชนิดและขนาดไฟล์ สแกนมัลแวร์ เข้ารหัสก่อนจัดเก็บ |
| 3.1 | ติดตามสถานะ 5 ขั้น + แจ้งเตือน SMS/อีเมล | ตามข้อ 2.3 |
| 3.2 | คิวคำร้อง มอบหมายงาน ขอเอกสารเพิ่ม บันทึกผล | ระบบหลังบ้านสำหรับเจ้าหน้าที่ แยกสิทธิ์ตามบทบาท (เจ้าหน้าที่ หัวหน้างาน ผู้ดูแลระบบ) |
| 3.2 | SLA timer เตือนเมื่อเหลือ 5 วันก่อนครบกำหนด | นับเวลาตามกฎเครือข่ายบัตรรายประเภท แจ้งเตือนในคิวและทางอีเมล |
| 3.2 | SSO ด้วย Active Directory | เชื่อม AD ของธนาคารผ่าน SAML 2.0 หรือ OIDC ตามที่ธนาคารรองรับ |
| 3.3 | เชื่อม CardLink ผ่าน REST API | เชื่อมผ่าน API ที่มีอยู่ ไม่แก้ระบบเดิม |
| 3.3 | SMS gateway และ email gateway ของธนาคาร | เชื่อมผ่าน gateway ของธนาคาร ส่งผ่านคิวแยก ส่งซ้ำอัตโนมัติเมื่อล้มเหลว |
| 4 | PCI DSS, เข้ารหัส, audit log 2 ปี, PDPA, pentest | มาตรการรายข้อในหัวข้อ 4.2 และภาคผนวก PDPA |
| 5 | 4 เดือน รวม UAT ≥ 3 สัปดาห์ · MA 1 ปี | แผนงาน 4 เดือนในหัวข้อ 6 · MA 1 ปีในหัวข้อ 8 |
| 6 | ไม่เกิน 2,200,000 บาท (ไม่รวม VAT) รวมพัฒนา + hosting + MA ปีแรก | 2,200,000 บาท (ไม่รวม VAT) ตามหัวข้อ 7 |

### สิ่งที่ขอยืนยันก่อนเริ่มงาน

1. **API ของ CardLink** — มี API สำหรับตรวจสอบเลขบัตร + วันเดือนปีเกิด และคืนค่า token ของบัตรหรือไม่ รวมถึงเอกสาร API, สภาพแวดล้อมทดสอบ และอัตราการเรียกใช้สูงสุดที่รองรับ
2. **ขอบเขต PCI DSS** — ระบบใหม่ต้องรับเลขบัตรเต็มตอนเข้าสู่ระบบ (ส่งต่อให้ CardLink โดยไม่จัดเก็บ) ธนาคารกำหนดให้ hosting ต้องมีเอกสารรับรอง PCI DSS เพิ่มเติมหรือไม่
3. **เวลาให้บริการและ SLA** — พอร์ทัลต้องการทีมดูแลตอบเหตุนอกเวลาทำการหรือไม่ (ราคาที่เสนอใช้ MA แบบ 8x5 ดูหัวข้อ 8)
4. **Penetration test (การทดสอบเจาะระบบ)** — ดำเนินการโดยทีมของธนาคารหรือผู้ทดสอบภายนอกที่ธนาคารจัดหา
5. **ระยะเก็บไฟล์หลักฐาน** — ระยะเวลาเก็บไฟล์หลักฐานและข้อมูลคำร้องหลังปิดเคส (ส่วน audit log เก็บ 2 ปีตาม TOR)
6. **จุดเริ่มนับปีแรก** — hosting และ MA ปีแรกเริ่มนับตั้งแต่วันใช้งานจริง (go-live) ใช่หรือไม่
7. **เอกสารประกอบการยื่น** — TOR ไม่ได้ระบุรายการเอกสารที่ต้องยื่นและจำนวนผลงานอ้างอิงขั้นต่ำ ขอรายการจากธนาคารเพื่อยื่นให้ครบ

## 3. โซลูชันที่เสนอ

ระบบประกอบด้วย 4 ส่วน ใช้ฐานข้อมูลและมาตรการความปลอดภัยชุดเดียวกัน

| ส่วน | รายละเอียด |
|---|---|
| พอร์ทัลผู้ถือบัตร (เว็บ responsive) | เข้าสู่ระบบด้วยเลขบัตร + วันเดือนปีเกิด + OTP · เลือกรายการย้อนหลัง 120 วัน · เลือกเหตุผลและตอบคำถามตามประเภท · แนบหลักฐาน · ติดตามสถานะ 5 ขั้น · ตัวอักษรใหญ่ อ่านง่ายบนมือถือ |
| ระบบหลังบ้านเจ้าหน้าที่ | คิวคำร้องพร้อมตัวกรอง · มอบหมายงาน · ขอเอกสารเพิ่ม (ผู้ถือบัตรได้แจ้งเตือนและอัปโหลดในเคสเดิม) · บันทึกผล · SLA timer · รายงานจำนวนคำร้องและเวลาเฉลี่ยรายขั้น |
| ส่วนเชื่อมต่อ (integration) | CardLink: ตรวจสอบตัวตน ดึงรายการ สร้างและอัปเดตเคส dispute · SMS/email gateway ของธนาคาร · Active Directory สำหรับ SSO |
| ส่วนตั้งค่า | ชุดคำถามตามประเภทเหตุผล ระยะเวลา SLA รายประเภท และข้อความแจ้งเตือน แก้ได้โดยผู้ดูแลระบบของธนาคาร |

เราทดสอบหน้าจอกับผู้ใช้จริง (ผู้ถือบัตรและเจ้าหน้าที่) ตั้งแต่เดือนแรก เพื่อให้แบบฟอร์มใช้งานได้ครบในครั้งเดียวตามวัตถุประสงค์ข้อ 2.1

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้างระบบ

ระบบเป็น modular monolith (แอปเดียวแบ่งโมดูลชัดเจน ดูแลง่าย) บน cloud ภูมิภาคประเทศไทย

- **แอปพลิเคชัน:** Next.js (หน้าเว็บ) + Node.js/TypeScript (API) แยกโมดูลผู้ถือบัตร เจ้าหน้าที่ และ integration
- **ข้อมูล:** PostgreSQL แบบ managed สำหรับข้อมูลคำร้อง · object storage แบบเข้ารหัสสำหรับไฟล์หลักฐาน · Redis สำหรับ session และ OTP
- **คิวงาน (queue) แยก:** การส่ง SMS/อีเมล และการเรียก CardLink ทำผ่านคิว ส่งซ้ำอัตโนมัติเมื่อปลายทางขัดข้อง ผู้ถือบัตรไม่ต้องยื่นใหม่
- **ขนาดระบบ:** รองรับคำร้อง 3,500 รายการต่อเดือนตาม TOR โดยมีส่วนเผื่อสำหรับช่วงที่มีคำร้องสูง และขยายขนาดได้โดยไม่ต้องแก้แอป

### 4.2 ความปลอดภัย

เราตอบข้อกำหนดความปลอดภัยใน TOR ข้อ 4 ทุกข้อด้วยมาตรการด้านล่าง

| ข้อกำหนด TOR | มาตรการ |
|---|---|
| PCI DSS: ห้ามเก็บเลขบัตรเต็ม ใช้ token จาก CardLink | เลขบัตรที่ผู้ถือบัตรกรอกตอนเข้าสู่ระบบส่งต่อให้ CardLink ผ่านช่องทางเข้ารหัสเพื่อแลกเป็น token และอยู่ในหน่วยความจำระหว่างประมวลผลเท่านั้น ไม่บันทึกลงฐานข้อมูล ไฟล์ หรือ log (ตั้ง redact ที่ตัวบันทึก log และมีชุดทดสอบตรวจซ้ำทุก release) · ระบบเก็บเฉพาะ token และ 4 หลักท้าย |
| PCI DSS: แสดงเลขบัตร 4 หลักท้ายเท่านั้น | ทุกหน้าจอ อีเมล SMS และรายงาน แสดงเป็น `**** **** **** 1234` |
| เข้ารหัสขณะส่ง | TLS 1.2 ขึ้นไปทุกช่องทาง ทั้งผู้ใช้กับระบบ และระบบกับ CardLink / gateway / AD |
| เข้ารหัสขณะจัดเก็บ | AES-256 สำหรับฐานข้อมูล ไฟล์หลักฐาน และข้อมูลสำรอง · วันเดือนปีเกิดไม่จัดเก็บ (ใช้ตรวจสอบกับ CardLink เท่านั้น) |
| audit log เก็บ 2 ปี | บันทึกทุกการเข้าสู่ระบบ การเปิดดู แก้ไข และมอบหมายเคส แบบแก้ไขย้อนหลังไม่ได้ เก็บ 2 ปีในประเทศไทย |
| พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 | เก็บข้อมูลเท่าที่จำเป็นต่อการพิจารณาคำร้อง · สิทธิ์ตามบทบาทผ่าน SSO ของธนาคาร · ข้อมูลทั้งหมดรวม backup และ log อยู่ในประเทศไทย · รายละเอียดในภาคผนวก PDPA |
| ผ่าน penetration test ก่อนเปิดใช้งาน | ทดสอบความปลอดภัยภายในตามแนวทาง OWASP Top 10 ก่อนส่ง pentest · กำหนด pentest ในเดือนที่ 3 ก่อน UAT และแก้ไขช่องโหว่ระดับสูงและวิกฤตทั้งหมดก่อนเปิดใช้งาน |

มาตรการเพิ่มเติม: จำกัดจำนวนครั้งการขอ OTP และการเข้าสู่ระบบผิด เพื่อป้องกันการเดาเลขบัตร · สแกนมัลแวร์ไฟล์แนบทุกไฟล์ · หมดเวลา session อัตโนมัติ

### 4.3 การเชื่อมต่อระบบเดิม

เราเชื่อม CardLink, SMS gateway, email gateway และ Active Directory ผ่าน API ที่ธนาคารมีอยู่ ไม่แก้ไขระบบเดิม และมีชั้น integration แยก เพื่อให้เปลี่ยนแปลงฝั่ง CardLink ในอนาคตกระทบระบบน้อยที่สุด

## 6. แผนงาน

แผนงาน 4 เดือน คาดว่าเริ่ม 1 กุมภาพันธ์ 2027 และเปิดใช้งานภายในสิ้นเดือนพฤษภาคม 2027

| ช่วง | กิจกรรม | ผลลัพธ์ |
|---|---|---|
| เดือนที่ 1 (ก.พ. 2027) | ยืนยันความต้องการ ศึกษา API ของ CardLink ออกแบบหน้าจอและทดสอบกับผู้ใช้จริง จัดเตรียม cloud | เอกสารออกแบบ ต้นแบบหน้าจอที่ผ่านการทดสอบกับผู้ใช้ |
| เดือนที่ 2 (มี.ค. 2027) | พัฒนาพอร์ทัลผู้ถือบัตร ระบบหลังบ้าน เชื่อม CardLink และ SSO | ระบบที่ทดลองใช้ได้บนสภาพแวดล้อมทดสอบ |

## ภาคผนวก PDPA

1. **ข้อตกลงการประมวลผลข้อมูลส่วนบุคคล (DPA)** — โนวาเทคเป็นผู้ประมวลผลข้อมูลส่วนบุคคล และ ธนาคารเอเชียไทยสากล จำกัด (มหาชน) เป็นผู้ควบคุมข้อมูลส่วนบุคคล โนวาเทคประมวลผลข้อมูลส่วนบุคคลตามคำสั่งของ ธนาคารเอเชียไทยสากล จำกัด (มหาชน) เท่านั้น
2. **การเก็บข้อมูลในประเทศไทย (Data residency)** — ข้อมูลส่วนบุคคลทั้งหมดจัดเก็บใน data center ในประเทศไทยเท่านั้น รวมถึงข้อมูลสำรอง (backup) และ log
3. **การแจ้งเหตุละเมิดข้อมูลส่วนบุคคล (Breach notification)** — โนวาเทคจะแจ้ง ธนาคารเอเชียไทยสากล จำกัด (มหาชน) ภายใน 72 ชั่วโมง นับจากที่ทราบเหตุ
