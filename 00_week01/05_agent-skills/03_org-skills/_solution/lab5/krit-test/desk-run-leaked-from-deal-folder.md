## 1. บทสรุปผู้บริหาร

เราเสนอพอร์ทัลให้ผู้ถือบัตรยื่นคำร้องโต้แย้งรายการออนไลน์ โดยระบบจะไม่ให้ส่งคำร้องจนกว่าข้อมูลและหลักฐานตามประเภทเหตุผลจะครบ เพื่อให้ธนาคารลดเวลาเริ่มตรวจสอบจาก 9 วันเหลือไม่เกิน 2 วันทำการตามเป้าใน TOR
ปัจจุบันธนาคารมีคำร้องประมาณ 3,500 รายการต่อเดือนผ่านแบบฟอร์มกระดาษและอีเมล และจากการประชุมวันที่ 28 ตุลาคม 2026 คำร้องราว 40% ข้อมูลไม่ครบในรอบแรก ทีมรับเรื่องจึงต้องใช้เวลามากกับการโทรตามเอกสาร
พอร์ทัลนี้ให้ผู้ถือบัตรติดตามสถานะได้เอง และให้เจ้าหน้าที่ทำงานจากคิวเดียวที่มี SLA timer (ตัวนับเวลาครบกำหนดตามกฎเครือข่ายบัตร) แทนการนับวันใน Excel
ส่งมอบภายใน 4 เดือน (ก.พ. – พ.ค. 2027) · มูลค่า **2,197,000 บาท (ไม่รวม VAT)** รวมค่าพัฒนา, hosting (ค่าเครื่องและระบบบน cloud) ปีแรก และ MA (บริการบำรุงรักษา) ปีแรก ภายในวงเงินที่ธนาคารกำหนด โดยไม่ตัดขอบเขตงานใน TOR

สิ่งที่เราขอยืนยันกับธนาคารก่อนเริ่มงาน (กระทบแผนและราคา):
1. **เอกสาร API และระบบทดสอบ (sandbox) ของ CardLink** — ต้องใช้ได้ภายในเดือนที่ 1 ของโครงการ และ API มีบริการตรวจเลขบัตร + วันเกิด และออก token หรือไม่
2. **ตารางกฎเครือข่ายบัตร** — ระยะเวลาครบกำหนดของแต่ละประเภทเหตุผลและแต่ละเครือข่ายบัตรที่ธนาคารใช้ เพื่อตั้งค่า SLA timer
3. **ชื่อสถานะ 5 ขั้น** — เราเสนอ ยื่นคำร้อง → รับเรื่อง → ตรวจสอบ → รอผลจากร้านค้า/เครือข่ายบัตร → แจ้งผล
4. **ระยะเวลาเก็บไฟล์หลักฐานและขนาดไฟล์เฉลี่ยต่อคำร้อง** — ใช้กำหนดพื้นที่เก็บไฟล์ที่รวมในค่า hosting (คำร้อง 3,500 รายการ/เดือน แนบได้สูงสุด 50 MB ต่อคำร้อง)
5. **รูปแบบ SSO** — Active Directory ของธนาคารเชื่อมผ่าน SAML/ADFS หรือ Microsoft Entra ID
6. **ช่วงเวลาให้บริการที่ต้องการดูแล** — พอร์ทัลผู้ถือบัตรเปิด 24 ชั่วโมง ธนาคารต้องการให้ทีมดูแลตอบรับนอกเวลาทำการหรือไม่ (กำหนดแพ็ก MA ในหัวข้อ 8)
7. **ค่าจ้างผู้ทดสอบเจาะระบบ (penetration test)** — ธนาคารใช้ผู้ทดสอบที่ธนาคารว่าจ้างโดยตรงใช่หรือไม่
8. **ระยะเวลา hosting ปีแรก** — นับ 12 เดือนจากวันเริ่มใช้สภาพแวดล้อมทดสอบ หรือจากวันขึ้นระบบจริง

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้างระบบ
- Modular monolith (ระบบเดียวที่แบ่งโมดูลชัดเจน ดูแลง่ายและแยกออกเป็นบริการย่อยได้ภายหลัง) ด้วย Next.js + Node.js/TypeScript แยกโมดูล portal / staff / sla / notification / integration / report
- PostgreSQL (managed, HA — ฐานข้อมูลสำรองพร้อมสลับอัตโนมัติ) + Redis สำหรับ session, จำกัดจำนวนครั้งการเข้าสู่ระบบ และคิวงาน
- คิวงาน (queue) สำหรับแจ้งเตือนและการสร้างเคสใน CardLink แยกจาก request หลัก ทุกงานส่งซ้ำได้โดยไม่สร้างรายการซ้ำ
- ไฟล์หลักฐานเก็บใน object storage ภูมิภาคไทย สแกนไวรัสก่อนเจ้าหน้าที่เปิดดู
- Hosting บน cloud ภูมิภาคประเทศไทย มี WAF (Web Application Firewall — ไฟร์วอลล์กรองการโจมตีหน้าเว็บ) และป้องกัน DDoS หน้าระบบ

### 4.2 ความปลอดภัยและการปฏิบัติตามข้อกำหนด
เราตอบข้อกำหนดความปลอดภัยใน TOR ข้อ 4 ครบทุกข้อ ดังนี้

**PCI DSS**
- **ไม่เก็บเลขบัตรเต็มในระบบใหม่** — เลขบัตรที่ผู้ถือบัตรกรอกตอนเข้าสู่ระบบส่งตรงไปตรวจกับ CardLink ผ่าน TLS แล้วใช้ token ที่ CardLink ออกให้ในทุกขั้นต่อจากนั้น ไม่บันทึกลงฐานข้อมูล ไฟล์ หรือ log
- **แสดงเลขบัตรแบบ 4 หลักท้ายเท่านั้น** ทั้งหน้าผู้ถือบัตร หน้าเจ้าหน้าที่ รายงาน และไฟล์ export
- ระบบ log ตัดเลขบัตร วันเกิด และเบอร์โทรออกอัตโนมัติก่อนบันทึก
- WAF หน้าระบบตามข้อกำหนด PCI DSS สำหรับเว็บที่เปิดสู่สาธารณะ
- จำกัดจำนวนครั้งการกรอกเลขบัตร/วันเกิด/OTP ผิด และล็อกชั่วคราว เพื่อป้องกันการเดาข้อมูลบัตร
- เราจัดทำเอกสารการควบคุมตามข้อกำหนด PCI DSS ที่เกี่ยวกับระบบนี้ ให้ทีม IT Security ของธนาคารตรวจในเดือนที่ 1

**การเข้ารหัสและ audit log**
- เข้ารหัสข้อมูลขณะส่ง (TLS 1.2 ขึ้นไป) และขณะจัดเก็บ (AES-256) ทั้งฐานข้อมูล ไฟล์หลักฐาน และ backup
- Audit log ทุกการเข้าดู แก้ไข และ export คำร้องของเจ้าหน้าที่ เก็บ 2 ปี แก้ไขย้อนหลังไม่ได้
- สิทธิ์ตามบทบาทผ่าน Active Directory ของธนาคาร เจ้าหน้าที่เห็นเฉพาะคำร้องที่สิทธิ์อนุญาต

**พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562**
- เก็บข้อมูลเท่าที่จำเป็นต่อการพิจารณาคำร้อง ไม่เก็บเลขบัตรประชาชน
- จัดทำบันทึกกิจกรรมการประมวลผลข้อมูลของระบบนี้ให้ธนาคาร และลงนามข้อตกลงประมวลผลข้อมูล (DPA) ตามภาคผนวก PDPA
- ทีมงานใช้ข้อมูลทดสอบที่สร้างขึ้น (synthetic) ระหว่างพัฒนา ไม่ใช้ข้อมูลผู้ถือบัตรจริง และลบสำเนาข้อมูลของธนาคารที่ใช้ระหว่างโครงการภายใน 90 วันหลังส่งมอบ
- ทีมงานทุกคนที่เข้าถึงข้อมูลลงนาม NDA ก่อนเริ่มงาน

**Penetration test ก่อนเปิดใช้งาน**
- ทดสอบช่องโหว่ภายในทุกรอบปล่อยงาน
- penetration test โดยผู้ทดสอบของธนาคารในเดือนที่ 3 ก่อน UAT และเผื่อเวลาแก้ไขและทดสอบซ้ำก่อนเปิดใช้งาน

เราจะกรอกแบบประเมินความปลอดภัยผู้ให้บริการ (vendor security questionnaire) ของธนาคาร และส่งพร้อมข้อเสนอนี้

## 9. ทำไมต้องโนวาเทค

- **ผลงานกับธนาคาร 2 โครงการที่ใกล้เคียงที่สุด:**
  - ธนาคารสยามรุ่งเรือง — พอร์ทัลติดตามสถานะสินเชื่อสำหรับลูกค้าและเจ้าหน้าที่ เชื่อมระบบสินเชื่อ (LOS) เดิมผ่าน API โดยไม่แก้ระบบเดิม ผ่าน penetration test ของธนาคาร ขึ้นระบบ ก.พ. 2025
  - ธนาคารออมทรัพย์เกษตรไทย — แอปนัดหมายสาขาผ่าน LINE OA และเว็บ ขึ้นระบบ 40 สาขานำร่อง ส.ค. 2025 ผ่านการทดสอบโหลด 2,000 การจองพร้อมกัน
- พอร์ทัลลูกค้าธนาคารที่มีหน้าจอเจ้าหน้าที่และเชื่อมระบบเดิมผ่าน API เป็นงานที่เราส่งมอบแล้ว เราจึงวางแผนส่งมอบระบบนี้ได้ใน 4 เดือนภายในงบที่กำหนด
- ทีมชุดเดียวตั้งแต่ออกแบบจนดูแลหลังขึ้นระบบ
- ทดสอบหน้าจอกับทีมรับเรื่องโต้แย้งรายการตั้งแต่เดือนแรก ไม่รอจน UAT
- รายงานความคืบหน้าทุกสัปดาห์ เห็นปัญหาก่อนกลายเป็นความล่าช้า

## ภาคผนวก PDPA

1. **ข้อตกลงประมวลผลข้อมูล (DPA)** — โนวาเทคเป็นผู้ประมวลผลข้อมูลส่วนบุคคล ธนาคารเป็นผู้ควบคุมข้อมูลส่วนบุคคล และเราประมวลผลข้อมูลตามคำสั่งของธนาคารเท่านั้น
2. **ที่ตั้งข้อมูล (data residency)** — ข้อมูลส่วนบุคคลทั้งหมด รวมถึง backup และ log เก็บใน data center ในประเทศไทยเท่านั้น
3. **การแจ้งเหตุละเมิดข้อมูล (breach notification)** — เราแจ้งธนาคารภายใน 72 ชั่วโมงนับจากที่ทราบเหตุ
