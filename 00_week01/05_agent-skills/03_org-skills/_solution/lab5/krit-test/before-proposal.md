## 1. บทสรุปผู้บริหาร

เราเสนอพัฒนาพอร์ทัลให้ผู้ถือบัตรยื่นคำร้องโต้แย้งรายการ (dispute) ออนไลน์ได้ครบในครั้งเดียว เพื่อให้ธนาคารเริ่มตรวจสอบคำร้องได้ภายใน 2 วันทำการ จากเดิมเฉลี่ย 9 วัน

ปัจจุบันธนาคารได้รับคำร้องประมาณ 3,500 รายการต่อเดือนผ่านแบบฟอร์มกระดาษและอีเมล เวลาส่วนใหญ่หมดไปกับการโทรตามเอกสารที่ขาด ระบบที่เสนอแก้ที่ต้นเหตุ 3 จุด

1. **คำร้องครบตั้งแต่ยื่น** — ผู้ถือบัตรเลือกรายการจากข้อมูลจริงในระบบบัตร แล้วระบบถามคำถามและขอหลักฐานตามประเภทเหตุผล ส่งคำร้องไม่ได้ถ้าข้อมูลบังคับยังไม่ครบ
2. **คำร้องเข้าคิวเจ้าหน้าที่ทันที** — พร้อมตัวนับ SLA ตามกฎเครือข่ายบัตร และเตือนเมื่อเหลือ 5 วันก่อนครบกำหนด
3. **ผู้ถือบัตรติดตามสถานะเองได้** — สถานะ 5 ขั้นบนเว็บ พร้อมแจ้งเตือนทาง SMS และอีเมลทุกครั้งที่สถานะเปลี่ยน ลดสายติดตามเรื่องที่เข้า call center

ด้านความปลอดภัย ระบบออกแบบให้ **ไม่เก็บเลขบัตรเต็ม** ใช้ token จาก CardLink ตาม PCI DSS และเชื่อม CardLink ผ่าน REST API โดยไม่แก้ระบบเดิม

**ระยะเวลา 4 เดือน** (1 ก.พ. – 31 พ.ค. 2027 รวม UAT 3 สัปดาห์) · **มูลค่า 2,196,000 บาท (ไม่รวม VAT)** รวมค่าพัฒนา, hosting 12 เดือนแรก และ MA ปีแรก อยู่ในวงเงินของ TOR

### สิ่งที่ขอยืนยันก่อนเริ่มงาน

ข้อต่อไปนี้ TOR ยังไม่ระบุ และมีผลต่อการออกแบบหรือราคา เราตั้งข้อสมมติตามวงเล็บไว้ในข้อเสนอนี้

1. **การ tokenize เลขบัตรของ CardLink** — CardLink รับเลขบัตรจากหน้าเว็บโดยตรงแล้วคืน token ได้หรือไม่ (เช่น hosted field หรือ tokenization endpoint) *(ข้อสมมติ: ได้ — ระบบใหม่ไม่เคยได้รับเลขบัตรเต็ม ทำให้ขอบเขต PCI DSS ของระบบใหม่เล็กที่สุด ถ้าไม่ได้ ต้องคุยขอบเขต PCI DSS ของ hosting ใหม่ ดูหัวข้อ 4.2)*
2. **เอกสาร API ของ CardLink และ sandbox** — พร้อมให้ใช้ภายในสัปดาห์แรกของโครงการ พร้อมช่องทางเชื่อมต่อ (VPN/private link) *(ข้อสมมติ: พร้อม)*
3. **เครือข่ายบัตรที่รองรับ** (Visa, Mastercard, JCB, UnionPay ฯลฯ) และกฎ SLA/ระยะเวลาของแต่ละเครือข่าย *(ข้อสมมติ: ธนาคารให้ตารางกฎ ระบบรองรับได้หลายเครือข่าย)*
4. **เหตุผล 6 ประเภทและคำถามประจำแต่ละประเภท** ที่ฝ่ายปฏิบัติการใช้อยู่ *(ข้อสมมติ: ตามร่างในหัวข้อ 3.2 ยืนยันใน workshop สัปดาห์แรก)*
5. **กรณี "ไม่ได้ทำรายการเอง"** ต้องให้ระบบแนะนำหรือสั่งระงับบัตรด้วยหรือไม่ *(ข้อสมมติ: แสดงคำแนะนำและช่องทางติดต่อระงับบัตร ไม่สั่งระงับบัตรผ่านระบบนี้)*
6. **ผู้ดำเนินการ penetration test** *(ข้อสมมติ: ธนาคารหรือผู้ทดสอบที่ธนาคารว่าจ้าง เราแก้ไขช่องโหว่ที่พบโดยไม่มีค่าใช้จ่ายเพิ่ม)*
7. **ที่ตั้ง hosting** — ธนาคารยอมรับ cloud ภูมิภาคประเทศไทยหรือต้องติดตั้งใน data center ของธนาคาร *(ข้อสมมติ: cloud ภูมิภาคไทย ตามนโยบายการใช้ cloud ของธนาคาร)*
8. **เอกสารที่ต้องยื่นประกอบข้อเสนอ** (หนังสือรับรองบริษัท, ผลงานอ้างอิงขั้นต่ำ, หลักประกันซอง ฯลฯ) — TOR ยังไม่ระบุ เราพร้อมส่งเพิ่มเติมตามที่ธนาคารกำหนด

## 3. โซลูชันที่เสนอ

ระบบประกอบด้วย 2 หน้าจอหลักบนฐานระบบเดียวกัน และชั้นเชื่อมต่อระบบเดิม

| ส่วน | รายละเอียด |
|---|---|
| **เว็บผู้ถือบัตร** (responsive ใช้ได้ทั้งมือถือและคอมพิวเตอร์) | เข้าสู่ระบบด้วยเลขบัตร + วันเกิด + OTP · รายการย้อนหลัง 120 วัน ค้นหาด้วยวันที่/ร้านค้า/จำนวนเงิน · เลือกได้หลายรายการในคำร้องเดียวถ้าเหตุผลเดียวกัน · ฟอร์มตามประเภทเหตุผล · แนบหลักฐาน · หน้ายืนยันพร้อมเลขที่คำร้อง · ติดตามสถานะและตอบคำขอเอกสารเพิ่ม · ตัวอักษรใหญ่อ่านง่าย รองรับผู้สูงอายุ |
| **ระบบหลังบ้านเจ้าหน้าที่** | เข้าสู่ระบบด้วย SSO (AD) · คิวคำร้องกรองตามสถานะ/ประเภท/SLA · มอบหมายงานรายคนหรือตามกฎอัตโนมัติ · ขอเอกสารเพิ่ม (ระบบแจ้งผู้ถือบัตรให้) · บันทึกผลและเหตุผล · ดูประวัติคำร้อง · dashboard หัวหน้าทีม: ปริมาณงาน, อายุคำร้อง, คำร้องใกล้ครบ SLA |
| **SLA engine** | ตารางกฎตามเครือข่ายบัตร × ประเภทเหตุผล · นับวันทำการตามปฏิทินวันหยุดธนาคาร · เตือนเมื่อเหลือ 5 วัน และเมื่อเกินกำหนด |
| **ชั้นเชื่อมต่อ (integration)** | CardLink: ตรวจตัวตน, ดึงรายการ, สร้างเคส dispute · SMS/email gateway ของธนาคาร · คิวส่งซ้ำอัตโนมัติและบันทึกผลการเรียกทุกครั้ง |
| **ผู้ดูแลระบบ** | ตั้งค่าประเภทเหตุผลและคำถาม, ข้อความแจ้งเตือน, กฎ SLA, ปฏิทินวันหยุด, สิทธิ์ผู้ใช้ — โดยไม่ต้องแก้โค้ด |
| **รายงาน** | สถิติคำร้องรายวัน/เดือน, เวลาเริ่มตรวจสอบเฉลี่ย, สัดส่วนคำร้องที่ต้องขอเอกสารเพิ่ม · ส่งออก Excel/CSV |

### 3.1 สถานะ 5 ขั้น (ร่าง — ยืนยันกับฝ่ายปฏิบัติการ)

| ขั้น | สถานะที่ผู้ถือบัตรเห็น | เกิดเมื่อ |
|---|---|---|
| 1 | ได้รับคำร้องแล้ว | ยื่นคำร้องสำเร็จ |
| 2 | อยู่ระหว่างตรวจสอบ | เจ้าหน้าที่รับเรื่อง |
| 3 | ส่งเรื่องไปยังร้านค้า/เครือข่ายบัตร | สร้างเคสใน CardLink แล้ว |
| 4 | รอผลพิจารณา | รอผลจากร้านค้า/เครือข่ายบัตร |
| 5 | ดำเนินการเสร็จสิ้น (พร้อมผล) | บันทึกผลแล้ว |

คำขอเอกสารเพิ่มแสดงเป็นป้ายเตือนบนขั้นที่ค้างอยู่ พร้อมปุ่มแนบเอกสาร และนาฬิกา SLA ยังเดินต่อตามกฎเครือข่ายบัตร

### 3.2 เหตุผล 6 ประเภท (ร่าง — ยืนยันตามกฎเครือข่ายบัตรที่ธนาคารใช้)

| ประเภท | ตัวอย่างคำถามเพิ่มเติม | หลักฐานที่แนะนำ |
|---|---|---|
| ไม่ได้ทำรายการเอง / ไม่รู้จักรายการ | บัตรอยู่กับท่านหรือไม่, เคยให้ข้อมูลบัตรกับผู้อื่นหรือไม่ | — (แสดงคำแนะนำการระงับบัตร) |
| ถูกเรียกเก็บซ้ำ | เลือกรายการที่ซ้ำกัน | ใบเสร็จ (ถ้ามี) |
| ไม่ได้รับสินค้า/บริการ | วันที่คาดว่าจะได้รับ, ติดต่อร้านค้าแล้วหรือไม่ | หลักฐานการสั่งซื้อ, การติดต่อร้านค้า |
| สินค้า/บริการไม่ตรงตามที่ตกลง | ลักษณะปัญหา, ส่งคืนสินค้าแล้วหรือไม่ | ภาพสินค้า, หลักฐานการส่งคืน |
| ยกเลิก/คืนสินค้าแล้วยังไม่ได้รับเงินคืน | วันที่ยกเลิก, เลขอ้างอิงการยกเลิก | หลักฐานการยกเลิก/คืนเงิน |
| จำนวนเงินไม่ถูกต้อง | จำนวนเงินที่ถูกต้อง | ใบเสร็จ |

## 4. ภาพรวมสถาปัตยกรรม

### 4.1 โครงสร้างระบบ

ระบบเป็น modular monolith (ระบบเดียวที่แบ่งโมดูลชัดเจน ดูแลง่ายกว่าการแยกเป็นหลายบริการ) เหมาะกับปริมาณ 3,500 คำร้องต่อเดือน

```
ผู้ถือบัตร (เว็บ) ──HTTPS──► WAF ──► Web/API (Next.js + Node.js/TypeScript) ──► PostgreSQL (เข้ารหัส)
เจ้าหน้าที่ (SSO/AD) ─────────┘            │        │                         └► ที่เก็บไฟล์หลักฐาน (เข้ารหัส)
                                          │        └► งานพื้นหลัง (queue): แจ้งเตือน, ส่งซ้ำ, SLA, สแกนไฟล์
                                          └──private link/VPN──► CardLink API · SMS gateway · Email gateway
```

| ชั้น | เทคโนโลยี |
|---|---|
| หน้าเว็บและ API | Next.js + Node.js (TypeScript) |
| ฐานข้อมูล | PostgreSQL แบบ managed พร้อม backup รายวันและ point-in-time recovery |
| แคช/OTP/จำกัดอัตราการเรียก | Redis |
| งานพื้นหลัง | queue แยกจากหน้าเว็บ ทำให้ gateway ขัดข้องไม่กระทบการยื่นคำร้อง |
| สแกนมัลแวร์ไฟล์แนบ | ตัวสแกนทำงานในระบบเอง ไฟล์ไม่ออกไปนอกระบบ |
| Hosting | cloud ภูมิภาคประเทศไทย 3 environment: dev (ข้อมูลจำลอง), UAT, production · มี WAF และป้องกัน DDoS |

### 4.2 ความปลอดภัย (ตอบ TOR ข้อ 4 ทีละข้อ)

| ข้อกำหนด TOR | มาตรการ |
|---|---|

มาตรการเพิ่มเติมที่ธนาคารมักถาม

- **ป้องกันการเดารหัส/สุ่มเลขบัตร** — จำกัดจำนวนครั้งต่อเลขบัตรและต่อ IP, ล็อกชั่วคราวเมื่อใส่วันเกิดหรือ OTP ผิด 5 ครั้ง, CAPTCHA เมื่อพบพฤติกรรมผิดปกติ · ข้อความแจ้งข้อผิดพลาดไม่บอกว่าข้อมูลส่วนใดผิด
- **OTP** — ใช้ครั้งเดียว อายุ 5 นาที ผูกกับ session · session ผู้ถือบัตรหมดอายุเมื่อไม่ใช้งาน 10 นาที
- **ไฟล์แนบ** — ตรวจชนิดไฟล์จากเนื้อไฟล์ ไม่ใช่นามสกุล, สแกนมัลแวร์ก่อนให้เจ้าหน้าที่เปิด, ลบข้อมูลแฝงในรูปภาพ (EXIF)
- **WAF และป้องกัน DDoS** ด้านหน้าระบบ (PCI DSS v4.0 ข้อ 6.4.2 กำหนดให้เว็บที่เปิดสู่สาธารณะต้องมี)
- **สิทธิ์เจ้าหน้าที่** ผูกกับกลุ่มใน AD — ลาออกหรือย้ายฝ่ายใน AD แล้วสิทธิ์หมดทันที

## 8. SLA (ระดับการให้บริการช่วง MA)

- **ธนาคารเห็นความคืบหน้าทุกสัปดาห์** — รายงานรายสัปดาห์และสาธิตงานทุก 2 สัปดาห์ ปัญหาถูกยกขึ้นตั้งแต่เนิ่น ๆ
- **ความปลอดภัยออกแบบตั้งแต่วันแรก** — ระบบไม่เก็บเลขบัตรเต็ม และทดสอบความปลอดภัยทุก sprint ไม่ใช่รอจนถึง pentest
