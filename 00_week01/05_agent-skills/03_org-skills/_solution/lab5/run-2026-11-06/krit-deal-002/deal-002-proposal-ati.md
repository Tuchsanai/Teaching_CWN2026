# ข้อเสนอโครงการ: พอร์ทัลยื่นคำร้องโต้แย้งรายการบัตรเครดิต (Card Dispute Portal)

## 1. บทสรุปผู้บริหาร

เราเสนอพัฒนาพอร์ทัลให้ผู้ถือบัตรยื่นคำร้องโต้แย้งรายการออนไลน์ได้ครบในครั้งเดียว โดยออกแบบให้เริ่มตรวจสอบได้ภายใน 2 วันทำการ จากปัจจุบันเฉลี่ย 9 วัน

ปัจจุบันธนาคารรับคำร้องประมาณ 3,500 รายการ/เดือน ผ่านแบบฟอร์มกระดาษและอีเมล และต้องโทรตามเอกสารเพราะข้อมูลไม่ครบ พอร์ทัลแก้ที่ต้นทางด้วยแบบฟอร์มตามประเภทเหตุผล การดึงรายการจาก CardLink และการติดตามสถานะได้เอง เจ้าหน้าที่จึงได้รับคำร้องที่ครบตั้งแต่ต้น และ call center ไม่ต้องรับสายถามสถานะ

- **ระยะเวลา:** 4 เดือนนับจากวันลงนามสัญญา รวม UAT (การทดสอบโดยผู้ใช้ของธนาคาร) 3 สัปดาห์ และ MA (บริการบำรุงรักษา) 1 ปี
- **มูลค่า:** 2,200,000 บาท ไม่รวม VAT รวมค่าพัฒนา, hosting ปีแรก และ MA ปีแรก ตามวงเงินใน TOR ข้อ 6

| 3.3 | เชื่อม CardLink ผ่าน REST API | ดึงรายการบัญชีบัตรและสร้างเคส dispute ผ่าน API โดยไม่แก้ระบบเดิม |
| 3.3 | SMS gateway และ email gateway ของธนาคาร | เชื่อมผ่านคิวงาน และส่งซ้ำเมื่อส่งไม่สำเร็จ |
| 4 | PCI DSS, การเข้ารหัส, audit log 2 ปี, PDPA, penetration test | มาตรการรายข้อในหัวข้อ 4.2 และภาคผนวก PDPA |
| 5 | 4 เดือน รวม UAT ไม่น้อยกว่า 3 สัปดาห์, MA 1 ปี | แผนงานในหัวข้อ 6 และ SLA ในหัวข้อ 8 |
| 6 | ไม่เกิน 2,200,000 บาท ไม่รวม VAT | ราคาในหัวข้อ 7 |

**สิ่งที่ขอยืนยันก่อนเริ่มงาน**

1. **CardLink API:** มี API สำหรับตรวจเลขบัตร + วันเกิด และออก token, ดึงรายการย้อนหลัง 120 วัน และสร้างเคส dispute ครบหรือไม่ และมี sandbox ให้ทดสอบตั้งแต่เดือนแรกหรือไม่
2. **กฎธุรกิจ:** รายการเหตุผล 6 ประเภทพร้อมคำถามเพิ่มเติม, สถานะ 5 ขั้น และกำหนดเวลาตามกฎเครือข่ายบัตรแต่ละราย
3. **ไฟล์หลักฐาน:** ขนาดไฟล์เฉลี่ยต่อคำร้องและระยะเวลาเก็บ เพื่อยืนยันพื้นที่จัดเก็บ
4. **Penetration test:** ผู้ทดสอบเป็นทีมของธนาคารหรือผู้ให้บริการภายนอก เกณฑ์ผ่าน และผู้รับผิดชอบค่าใช้จ่าย
5. **ชั่วโมงบริการ:** ข้อเสนอนี้ให้บริการ MA แบบ 8x5 ธนาคารต้องการบริการนอกเวลาทำการหรือไม่ (ดูตัวเลือกเสริมในหัวข้อ 7)
6. **การเริ่มนับปีแรก:** ข้อเสนอนี้นับ hosting และ MA ปีแรกจากวันเปิดใช้งานจริง
7. **การวัดผล 2 วันทำการ:** จุดเริ่มและจุดสิ้นสุดของการนับเวลา เพราะผลลัพธ์นี้ขึ้นกับจำนวนเจ้าหน้าที่ของธนาคารด้วย
8. **เอกสารประกอบการยื่น:** TOR ไม่ได้ระบุรายการเอกสาร หากธนาคารมีแบบฟอร์มหรือจำนวนผลงานอ้างอิงขั้นต่ำ ขอให้แจ้งก่อนวันยื่น 20 พฤศจิกายน 2026

## 3. โซลูชันที่เสนอ

เราเสนอเว็บแอปพลิเคชันเดียวที่แยกการใช้งาน 2 ฝั่ง และเชื่อมระบบของธนาคารโดยไม่แก้ระบบเดิม

| ส่วน | รายละเอียด |
|---|---|
| ฝั่งผู้ถือบัตร | เว็บ responsive 4 ขั้นตอน: ยืนยันตัวตน → เลือกรายการ → ระบุเหตุผลและตอบคำถาม → แนบหลักฐานและส่ง จากนั้นติดตามสถานะได้เอง |
| ฝั่งเจ้าหน้าที่ | คิวคำร้อง, มอบหมายงาน, ขอเอกสารเพิ่ม, บันทึกผล, SLA timer และลงชื่อเข้าใช้ด้วย Active Directory |
| การเชื่อมต่อ | CardLink ผ่าน REST API, SMS gateway และ email gateway ของธนาคาร |
| การแจ้งเตือน | แจ้งผู้ถือบัตรเมื่อสถานะเปลี่ยนหรือต้องส่งเอกสารเพิ่ม และเตือนเจ้าหน้าที่เมื่อคำร้องเหลือเวลา 5 วันก่อนครบกำหนด |
| การใช้งาน | ทดสอบหน้าจอกับผู้ใช้ตั้งแต่เดือนแรกด้วยข้อมูลจำลอง โดยคำนึงถึงผู้ใช้สูงอายุและผู้ใช้บนมือถือ |

## 4. ภาพรวมสถาปัตยกรรม

ระบบเป็น modular monolith (แอปเดียวที่แบ่งโมดูลชัดเจน) บน cloud ภูมิภาคไทย เหมาะกับปริมาณ 3,500 คำร้อง/เดือน และดูแลรักษาง่าย

### 4.1 โครงสร้าง

| ชั้น | เทคโนโลยี | หน้าที่ |
|---|---|---|
| หน้าเว็บและ API | Next.js + Node.js/TypeScript บนเครื่อง 2 ชุด | หน้าจอทั้งสองฝั่งและกฎธุรกิจ |
| ฐานข้อมูล | Managed PostgreSQL | คำร้อง, สถานะ, audit log และคิวงานแจ้งเตือน |
| ด่านหน้า | WAF (ระบบกรองการโจมตีเว็บ) + DDoS protection | กรองทราฟฟิกก่อนเข้าระบบ |
| การเฝ้าระวัง | Monitoring/APM + log management | ติดตามสถานะระบบและเก็บ log |
| ระบบของธนาคาร | CardLink, SMS gateway, email gateway, Active Directory | เชื่อมต่อผ่านช่องทางของธนาคาร ไม่แก้ระบบเดิม |

### 4.2 ความปลอดภัย

ทุกข้อใน TOR ข้อ 4 มีมาตรการรองรับดังนี้

| ข้อกำหนด | มาตรการ |
|---|---|
| PCI DSS (มาตรฐานความปลอดภัยข้อมูลบัตร): ห้ามเก็บเลขบัตรเต็ม | รับเลขบัตรตอนเข้าสู่ระบบเพื่อส่งต่อให้ CardLink ผ่านช่องทางเข้ารหัส แล้วใช้ token แทนในทุกส่วน ไม่บันทึกเลขบัตรเต็มลงฐานข้อมูล, log หรือไฟล์ |
| แสดงเลขบัตร 4 หลักท้ายเท่านั้น | ทุกหน้าจอและการแจ้งเตือนแสดงเฉพาะ 4 หลักท้าย |
| ไฟล์หลักฐานที่อาจมีเลขบัตร | แจ้งผู้ถือบัตรให้ปิดเลขบัตรก่อนแนบ เข้ารหัสไฟล์ และจำกัดการเปิดไฟล์ตามบทบาท |
| เข้ารหัสขณะส่ง | TLS 1.2 ขึ้นไปทุกการเชื่อมต่อ |
| เข้ารหัสขณะจัดเก็บ | AES-256 สำหรับฐานข้อมูล ไฟล์หลักฐาน และ backup |
| Audit log เก็บ 2 ปี | บันทึกการเข้าสู่ระบบ การเปิดดู และการเปลี่ยนแปลงคำร้อง เก็บ 2 ปี แก้ไขย้อนหลังไม่ได้ และไม่มีเลขบัตรเต็ม |
| การยืนยันตัวตนและสิทธิ์ | ผู้ถือบัตรใช้ OTP จำกัดจำนวนครั้งที่ลองผิด เจ้าหน้าที่ใช้ SSO และสิทธิ์ตามบทบาท |
| พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 | เก็บเท่าที่จำเป็น ไม่เก็บวันเดือนปีเกิดหลังยืนยันตัวตน ไม่เก็บเลขบัตรประชาชนแบบข้อความธรรมดา และทำตามภาคผนวก PDPA |
| ข้อมูลทดสอบและการเข้าถึงข้อมูลจริง | ใช้ข้อมูลจำลองในการทดสอบ ไม่นำข้อมูลลูกค้าไปเทรนโมเดล การเข้าถึงข้อมูลจริงต้องมี ticket และผู้อนุมัติของธนาคาร สำเนาข้อมูลลูกค้าปลายทาง (ถ้ามี) ลบภายใน 90 วันหลังส่งมอบ |
| Penetration test (การทดสอบเจาะระบบ) ก่อนเปิดใช้งาน | ทดสอบก่อนเริ่ม UAT และแก้ไขจุดที่พบตามเกณฑ์ที่ตกลงก่อนเปิดใช้งาน |

### 4.3 การเชื่อมต่อ CardLink

เราเชื่อมต่อผ่าน API โดยไม่แก้ระบบเดิม เพื่อจำกัดผลกระทบต่อระบบบัตร CardLink ยังคงเป็นต้นทางของข้อมูลบัตรและเคส dispute ส่วนพอร์ทัลเก็บเฉพาะ token, ข้อมูลคำร้อง และไฟล์หลักฐาน

## 8. SLA

SLA (ข้อตกลงระดับบริการ) ของ MA-STD ครอบคลุมเวลา **8x5** (8 ชั่วโมงต่อวัน 5 วันทำการต่อสัปดาห์) ระยะเวลาตอบรับและแก้ไขด้านล่างจึงนับเฉพาะในเวลาบริการนี้

| ระดับ | ตอบรับ | แก้ไข |
|---|---|---|
| Sev 1 | 30 นาที | 4 ชั่วโมง |
| Sev 2 | 2 ชั่วโมง | 1 วันทำการ |
| Sev 3 | 1 วันทำการ | 5 วันทำการ |

Uptime ไม่ต่ำกว่า 99.5% ต่อเดือน ไม่รวม maintenance ที่แจ้งล่วงหน้า 3 วัน หากต้องการการตอบรับและแก้ไขตลอด 24 ชั่วโมง ให้เลือก MA-PREM (24x7) ในหัวข้อ 7

## ภาคผนวก PDPA

1. **DPA:** โนวาเทคเป็นผู้ประมวลผลข้อมูลส่วนบุคคล ลูกค้าเป็นผู้ควบคุมข้อมูลส่วนบุคคล และโนวาเทคประมวลผลตามคำสั่งของลูกค้าเท่านั้น
2. **Data residency:** ข้อมูลส่วนบุคคลทั้งหมดเก็บใน data center ในประเทศไทยเท่านั้น รวม backup และ log
3. **Breach notification:** โนวาเทคแจ้งเหตุละเมิดข้อมูลส่วนบุคคลให้ลูกค้าทราบภายใน 72 ชั่วโมงนับจากที่ทราบเหตุ
