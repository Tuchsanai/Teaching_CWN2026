### 2.1 จำลอง "คนจริง" ยังไง

พนักงาน 1 คน = **3 อย่าง** ที่ต้องตรงกัน

| ชิ้น | อยู่ที่ | มีไว้ทำไม |
|---|---|---|
| 🪪 การ์ดพนักงาน `people/<user>.md` | ชื่อ แผนก บทบาท **เรื่องที่เก่ง** งานที่ทำซ้ำทุกเดือน คำที่ชอบพิมพ์สั่ง AI ("ทำโปรให้ลูกค้าหน่อย") | ความเก่งที่ "อยู่ในหัว" ก่อนกลายเป็น skill · คำที่ชอบพิมพ์ใช้ทำชุดคำค้น LAB 7 |

## 4. ⭐ ออกแบบ SkillOps CI: เลือกแบบไหนดี

### 4.1 ตัวเลือก 3 แบบ

| | A · ตรวจแค่โครงสร้าง | **B · 3 ชั้น: เครื่อง + eval โดยผู้รีวิว + ออกเวอร์ชัน** ⭐ | C · AI ใน CI เต็มรูป |
|---|---|---|---|
| ทำอะไร | `validate` + หัวไฟล์ครบ | A + สแกนความปลอดภัย + ตรวจกราฟ + ผลกระทบ · eval รันที่เครื่องผู้รีวิวแล้วส่งผลเป็น status บังคับ · merge แล้วออกเวอร์ชันเอง | B แต่ CI รัน `claude plugin eval` และ AI รีวิว PR เอง ด้วย token ของบริษัท |
| จับ PR หัวไฟล์ไม่ครบ | ✅ | ✅ | ✅ |
| จับสคริปต์อันตราย | ❌ | ✅ | ✅ |
| จับ skill แย่งงานตัวอื่น (description กว้าง) | ❌ | ✅ (eval) | ✅ (eval) |
| ต้องเก็บ token AI ใน CI | ไม่ | **ไม่** | ต้อง |
| ความเสี่ยง | skill อันตรายหลุด | ผู้รีวิวต้องรัน eval เอง 1 คำสั่ง | **PR อันตรายถูกรันใน CI ที่มี token** → token รั่วได้ |
| ค่าใช้จ่ายต่อ PR | 0 | eval เฉพาะ plugin ที่แก้ | ทุก PR เสียค่า AI แม้ PR ขยะ |
| เหมาะกับ | ทีมเล็กเริ่มต้น | **บริษัทหลายแผนก (เคสเรา) · สอนได้ครบทุกสถานีของหัวข้อ 23** | องค์กรใหญ่ที่มี runner แยกปลอดภัย |

**แนะนำ B** และใน LAB 6 ให้เห็นด้วยตาว่าทำไมไม่เลือก C: PR อันตราย (PR C ด้านล่าง) ถ้าถูกรันใน CI ที่มี token จะเกิดอะไร (จำลองด้วย token ปลอม)

### 4.2 แบบ B ทำงานยังไง (ตรงกับ 7 สถานีของหัวข้อ 23)

```text
พนักงาน: "แก้ skill X แล้วเปิด PR"           ← สถานี 1–2 (Claude สร้าง branch, แก้, เปิด PR)
        │
        ▼  skill-pr.yml (อัตโนมัติ ไม่ใช้ AI · ~30 วินาที)
  ① validate      claude plugin validate
  ② frontmatter   name ≤ 64 · description ≤ 1,024 มี "ใช้เมื่อ" · metadata.owner/layer/version ครบ · version ต้องเพิ่ม
  ③ security      ส่งข้อมูลออกนอกบริษัท? อ่าน .env/token? ข้อความ prompt injection? ไฟล์ไบนารีแปลก?
  ④ graph         uses/next/follows ชี้ skill ที่มีจริง · ไม่วนเป็นวง
  ⑤ impact        คอมเมนต์ใน PR: "แก้ customer-data-policy กระทบ 9 skill → ต้องรัน eval: …"
        │
        ▼  ชั้นคน (บังคับด้วย branch protection)
  ⑥ eval          ผู้รีวิวสั่ง Claude: "รัน eval ของ PR นี้" → claude plugin eval (มี skill vs ไม่มี) → post-eval.mjs ส่ง status `skill-eval` ขึ้น PR
  ⑦ review        CODEOWNERS ขอรีวิวหัวหน้าแผนกเอง · ต้อง approve 1 คน · คนเขียน approve เองไม่ได้   ← สถานี 3–5
        │  merge
        ▼  skill-release.yml
  ⑧ release       tag `sales@1.3.0` + CHANGELOG + catalog.json + graph.html ใหม่                  ← สถานี 6
  ⑨ distribute    โต๊ะสั่ง `claude plugin marketplace update` (ของจริงตั้งอัปเดตอัตโนมัติ)            ← สถานี 7
```

| กติกา branch protection บน `main` | ผล |
|---|---|
| ห้าม push ตรง (แม้แต่หัวหน้า / ทีมกลาง) | ทุกการแก้ต้องเป็น PR (หัวข้อ 22.2 หลักข้อ 3) |
| status ที่ต้องผ่าน: `skill-pr` + `skill-eval` | เครื่องตรวจ + eval ต้องเขียวทั้งคู่ |
| ต้อง approve ≥ 1 จาก CODEOWNER · commit ใหม่ล้าง approve เดิม | คนตรวจเห็นเวอร์ชันสุดท้ายเสมอ |
