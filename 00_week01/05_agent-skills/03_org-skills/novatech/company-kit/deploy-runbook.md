# คู่มือขึ้นระบบจริง (Production Deploy Runbook)

> ทีม DevOps · ผู้ดูแล อาร์ต พงษ์ไพบูลย์ (`ops-art`) · ฉบับยาว (อาร์ตย่อเป็น checklist ตอนใช้จริง) · ปรับปรุง 2026-10-01

## 0. ก่อนเริ่ม: ใครทำอะไร

ทุกรอบ deploy production ต้องมี 3 บทบาท (คนเดียวห้ามถือเกิน 2): **Deploy lead** (กดปุ่ม, ตัดสินใจ rollback), **Verifier** (QA หรือ dev ที่ไม่ได้เขียนฟีเจอร์นั้น ทำ smoke test), **Comms** (คุยกับลูกค้า, อัปเดตช่อง `#deploy`)
ช่วงเวลาปกติ: อังคาร–พฤหัส 21:00–23:00 น. ห้าม deploy วันศุกร์ ก่อนวันหยุดยาว และช่วงวันที่ 25–สิ้นเดือนสำหรับลูกค้าธนาคาร (ช่วงเงินเดือนออก) ยกเว้น hotfix Sev 1

## 1. เตรียมล่วงหน้า (T−3 วัน ถึง T−1 วัน)

1.1 Release notes เสร็จ มีรายการ ticket, migration, feature flag, ความเสี่ยง
1.2 ผ่าน UAT และลูกค้าเซ็นรับ (อีเมลยืนยันก็ได้) — ไม่มีลายลักษณ์อักษร = ไม่ deploy
1.3 **แจ้งลูกค้า** ล่วงหน้าอย่างน้อย 3 วันทำการ (ตามสัญญา SLA): วัน เวลา ผลกระทบ (มี downtime ไหม กี่นาที) ช่องทางติดต่อ — ใช้แม่แบบ `NOTICE-maintenance` ห้ามใส่เบอร์มือถือส่วนตัวของใคร ใช้เบอร์ on-call กลาง
1.4 Migration ทุกตัว **dry-run บน staging ที่ใช้สำเนาโครงสร้าง+ขนาดข้อมูลใกล้ production** (ข้อมูลปิดบังแล้ว) จดเวลาที่ใช้ — ถ้าเกิน 5 นาที หรือ lock ตารางใหญ่ ต้องแยกรอบ/ทำแบบ online
1.5 Migration ต้องย้อนกลับได้ หรือเป็นแบบ expand (เพิ่มอย่างเดียว) ตาม `coding-rules.md` ข้อ 7
1.6 ฟีเจอร์ใหม่ที่เสี่ยงต้องอยู่หลัง **feature flag** ปิดไว้ก่อน เปิดหลัง deploy ผ่านแล้ว
1.7 เช็กใบรับรอง TLS ของทุกโดเมนที่เกี่ยวข้อง เหลือ > 21 วัน (บทเรียนจาก incident 2026-09)
1.8 จองคน on-call 2 ชั่วโมงหลัง deploy และเช้าวันถัดไป 08:00–10:00

## 2. วัน deploy — ก่อนกด (T−30 นาที)

2.1 เปิด bridge call + โพสต์เริ่มใน `#deploy` (เวอร์ชัน, ลิงก์ release notes, ชื่อ 3 บทบาท)
2.2 ดู dashboard: error rate, latency, queue ปกติไหม — ถ้าระบบป่วยอยู่แล้ว เลื่อน deploy
2.3 **Backup ฐานข้อมูล** แบบ snapshot ทันทีก่อน deploy + ทดสอบว่า snapshot สถานะ `available` และจดชื่อ snapshot ลงช่อง
2.4 จด image tag เวอร์ชันปัจจุบัน (ใช้ rollback)
2.5 ปิด cron/batch ที่เขียนข้อมูลชนกับ migration (เช่น batch พยากรณ์รอบคืน)

## 3. Deploy

3.1 เปิดหน้า maintenance ถ้ามี downtime ตามที่แจ้งลูกค้า
3.2 รัน migration (`prisma migrate deploy`) ดูเวลาเทียบกับตอน dry-run ถ้าเกิน 2 เท่าให้หยุดคิด
3.3 Deploy image ใหม่แบบ rolling (ทีละ instance) ดู `/readyz` ผ่านทุกตัว
3.4 ปิดหน้า maintenance

## 4. Smoke test (Verifier ทำ ภายใน 15 นาที)

4.1 login / logout / refresh token
4.2 flow หลักของระบบ 1 รอบเต็ม (เช่น จองคิว → ยกเลิก / สั่งซื้อ → จ่ายเงินด้วยบัตรทดสอบ)
4.3 webhook ภายนอกเข้ามาได้ (ดู log มี event ใหม่)
4.4 คิวงานไม่ค้าง, error rate < 1%, latency p95 ไม่แย่กว่าก่อน deploy เกิน 20%
4.5 เปิด feature flag ทีละตัว ทดสอบซ้ำข้อ 4.2 หลังเปิดแต่ละตัว

## 5. Rollback — เมื่อไหร่และอย่างไร

**ตัดสิน rollback ทันทีถ้า:** smoke test ข้อใดไม่ผ่านและแก้ไม่ได้ใน 15 นาที · error rate > 5% นาน 5 นาที · ข้อมูลผิด (เช่น ยอดเงินเพี้ยน) แม้แค่รายการเดียว
ลำดับ:
5.1 ปิด feature flag ที่เพิ่งเปิด (เร็วที่สุด ลองก่อน)
5.2 deploy image tag เดิมที่จดไว้ข้อ 2.4
5.3 ถ้า migration ทำให้ใช้กับโค้ดเก่าไม่ได้ → restore snapshot ข้อ 2.3 (**ต้องให้ deploy lead + หัวหน้าทีม dev ตกลงร่วมกัน** เพราะข้อมูลหลังจาก snapshot จะหาย)
5.4 Comms แจ้งลูกค้าภายใน 30 นาทีว่าถอยกลับแล้ว ผลกระทบคืออะไร

## 6. หลัง deploy

6.1 Comms แจ้งลูกค้าว่าเสร็จ + สิ่งที่เปลี่ยน (ภาษาผู้ใช้ ไม่ใช่ ticket)
6.2 เปิด cron/batch ที่ปิดไว้ข้อ 2.5
6.3 On-call เฝ้า 2 ชั่วโมง + เช้าวันถัดไป, ถ้าเกิดเหตุให้เขียน postmortem ภายใน 3 วันทำการ
6.4 ปิด ticket, tag release ใน git, อัปเดต CHANGELOG
