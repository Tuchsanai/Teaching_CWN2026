### C1 — บัญชีผู้ใช้และการเข้าสู่ระบบ
**สำรวจ** หน้าเข้าสู่ระบบ/สมัครสมาชิก/ออกจากระบบ และหน้าที่ต้องล็อกอิน
**ด้วย** บัญชี `demo@pawpantry.test` / `Paw12345` (ล็อกอินเท่านั้น) + บัญชีใหม่ที่สมัครเอง
**เพื่อหา** กฎความถูกต้องของอีเมล/รหัสผ่าน, ข้อความ error, การรั่วของข้อมูลบัญชี, การเข้าถึงหน้าที่ต้องล็อกอินโดยไม่ล็อกอิน

- **ความเสี่ยงที่เดา:** P2 (สำคัญแต่ไม่ใช่จุดทำเงินโดยตรง)
- **เวลา:** 40 นาที
- **สิ่งที่ต้องลอง (อย่างน้อย 5):**
  1. ล็อกอินด้วยบัญชี demo ถูกต้อง → ไปหน้าไหน, header เปลี่ยนอย่างไร
  2. รหัสผิด / อีเมลไม่มีในระบบ → ข้อความ error เหมือนกันไหม (ถ้าต่างกัน = บอกใบ้ว่ามีบัญชีนี้)
  3. ตัวพิมพ์ใหญ่-เล็กของอีเมล (`DEMO@PawPantry.test`), ช่องว่างหน้า/หลัง, รหัส `paw12345` (case ของรหัส)
  4. ช่องว่างเปล่า, อีเมลผิดรูปแบบ, รหัสยาวมาก / อักขระพิเศษ / ภาษาไทย
  5. สมัครสมาชิก: อีเมลซ้ำกับ demo, รหัสสั้น/ง่าย, ยืนยันรหัสไม่ตรง (ถ้ามีหน้าสมัคร)
  6. เปิด `/cart`, `/checkout`, `/orders`, `/account` ตรง ๆ ขณะยังไม่ล็อกอิน
  7. ออกจากระบบแล้วกด Back / refresh → ยังเห็นข้อมูลเดิมไหม
  8. ล็อกอินผิดหลายครั้งติดกัน → มีล็อกบัญชี/จำกัดจำนวนครั้งไหม (**ทำกับบัญชีที่สมัครเองเท่านั้น** ห้ามทำกับ demo)
- **ส่งต่อ:** ตะกร้าหายหลังล็อกอิน/ออก → C3 · ประวัติสั่งซื้อ → C6

### C2 — แคตตาล็อก ค้นหา และสถานะสต็อก (อ่านอย่างเดียว)
**สำรวจ** หน้าแรก หน้ารายการสินค้า หมวดหมู่ ค้นหา/กรอง/เรียง และหน้ารายละเอียดสินค้า
**ด้วย** ชื่อสินค้าใน TEST-DATA (ไก่ฟรีซดราย, สูตรลดก้อนขน), คำค้นภาษาไทย/อังกฤษ, การแก้ URL/query string
**เพื่อหา** ราคา/สต็อกที่แสดงไม่ตรงกันระหว่างหน้า, ป้ายหมด/ใกล้หมดผิด, ค้นหา/กรองพัง, หมวด "อาหารแมว" จัดผิด (กระทบเงื่อนไข NEWCAT50)

- **ความเสี่ยงที่เดา:** P2
- **เวลา:** 40 นาที
- **สิ่งที่ต้องลอง (อย่างน้อย 5):**
  1. ไก่ฟรีซดราย (สต็อก 0): มีป้าย "หมด" ไหม ปุ่มเพิ่มลงตะกร้าถูกปิดไหม ทั้งที่การ์ดและหน้ารายละเอียด
  2. สูตรลดก้อนขน (สต็อก 3): มีป้าย "ใกล้หมด"/แสดงจำนวนคงเหลือไหม เกณฑ์ "ใกล้หมด" คือเท่าไร
  3. ราคาเดียวกันทุกที่: การ์ด vs หน้ารายละเอียด (จดราคาทุกชิ้นเป็นตารางให้ C4/C5 ใช้หายอดขอบเขต ฿500/฿999)
  4. ค้นหา: คำไทยบางส่วน, สะกดผิด, ตัวพิมพ์ใหญ่-เล็ก, ค่าว่าง, อักขระพิเศษ `<script>` `%` `'`
  5. กรองตามหมวด + เรียงราคา น้อย→มาก / มาก→น้อย → ลำดับถูกไหม สินค้าหมดอยู่ตรงไหน
  6. แก้ URL ไปสินค้า id ที่ไม่มี / id ติดลบ / ตัวอักษร → หน้า 404 สวยไหม
  7. จดว่าสินค้าไหนอยู่หมวด "อาหารแมว" บ้าง (ส่งให้ C4)
- **ห้าม:** เพิ่มลงตะกร้าเพื่อทดสอบลึก (เป็นของ C3), เขียนรีวิว/ข้อมูลที่คนอื่นเห็น (ถ้าจำเป็นต้องติดป้าย `[C2]` ในข้อความ)

### C3 — ตะกร้าสินค้าและจำนวนเทียบสต็อก
**สำรวจ** ปุ่มเพิ่มลงตะกร้า, หน้าตะกร้า, ไอคอนจำนวนใน header
**ด้วย** บัญชีที่สมัครเองของ C3 (หรือ guest session) + สินค้าสต็อก 0 และ 3 + ค่าจำนวนขอบเขต
**เพื่อหา** การใส่เกินสต็อก, จำนวนติดลบ/ศูนย์/ทศนิยม, ยอดรวมคำนวณผิด, ตะกร้าไม่ sync ระหว่างแท็บ/ล็อกอิน

- **ความเสี่ยงที่เดา:** P1 (ขายของที่ไม่มี = เสียเงิน/ลูกค้าโกรธ)
- **เวลา:** 45 นาที
- **สิ่งที่ต้องลอง (อย่างน้อย 5):**
  1. สูตรลดก้อนขน: ใส่ 3 ได้ไหม, ใส่ 4 ได้ไหม (ทั้งกดปุ่ม + และพิมพ์ตัวเลขเอง), ข้อความ error ว่าอะไร
  2. ไก่ฟรีซดราย (0): พยายามใส่ตะกร้าทางอื่น — กดซ้ำเร็ว ๆ, แก้ HTML ปลดปุ่ม disabled, ย้อนหน้าเก่า
  3. จำนวน 0, -1, 1.5, 999999, ช่องว่าง, ตัวอักษร
  4. เพิ่มสินค้าเดียวกันสองครั้ง → รวมบรรทัดหรือแยก, จำนวนรวมเกินสต็อกได้ไหม
  5. ยอดรวมย่อย = ราคา × จำนวน ทุกบรรทัด, ปัดเศษ, ไอคอน header ตรงกับจำนวนจริง
  6. เปิดสองแท็บแก้ตะกร้าคนละแท็บ / refresh / ปิดเบราว์เซอร์แล้วเปิดใหม่ → ตะกร้ายังอยู่ไหม
  7. ใส่ตะกร้าแบบ guest แล้วล็อกอิน (บัญชี C3) → ตะกร้ารวม/หาย/ซ้ำ
  8. ลบสินค้าจนตะกร้าว่าง → ยังไปหน้า checkout ได้ไหม
- **ห้าม:** กดยืนยันสั่งซื้อ (ส่งต่อ C6) · ใส่คูปอง (ส่งต่อ C4)
- **หมายเหตุ:** ถ้าสต็อกที่เห็นไม่ใช่ 0/3 ให้เช็กบันทึกของ C6 ก่อนรายงานเป็นบั๊ก (อาจมีคนสั่งซื้อไปแล้ว)

### C4 — คูปองและการคำนวณราคา
**สำรวจ** ช่องใส่คูปองและสรุปยอด (ตะกร้า/checkout) — ไปจนถึงหน้าก่อนกดยืนยันสั่งซื้อ
**ด้วย** คูปองทั้ง 4 ตัว (PAW10, FREESHIP, NEWCAT50, SUMMER20) + ตะกร้าที่จัดให้ยอดอยู่ที่ขอบเขต ฿499/฿500/฿998/฿999 (ใช้ตารางราคาจาก C2)
**เพื่อหา** กฎคูปอง (ซ้อนได้ไหม, เงื่อนไขหมวด, ยอดขั้นต่ำคิดก่อน/หลังส่วนลด), การปัดเศษ, คูปองหมดอายุยังใช้ได้, ยอดไม่ถูกคำนวณใหม่เมื่อแก้ตะกร้า

- **ความเสี่ยงที่เดา:** P1 (คำนวณเงินผิดโดยตรง)
- **เวลา:** 60 นาที
- **สิ่งที่ต้องลอง (อย่างน้อย 5):**
  1. PAW10: ลด 10% จากอะไร (ค่าสินค้า หรือรวมค่าส่ง), ยอดเศษสตางค์ปัดขึ้น/ลง
  2. NEWCAT50: อาหารแมว ฿499 vs ฿500 · ตะกร้ามีอาหารแมว ฿400 + ของอื่น ฿200 (ยอดรวม ≥ 500 แต่อาหารแมว < 500) · ยอดที่ลด ฿50 แล้วต่ำกว่าเกณฑ์
  3. SUMMER20: ข้อความ error บอกว่า "หมดอายุ" ชัดเจนไหม ไม่ใช่ "ไม่พบคูปอง"
  4. รูปแบบรหัส: `paw10`, ` PAW10 ` (มีช่องว่าง), `PAW 10`, ค่าว่าง, รหัสมั่ว, ยาวมาก
  5. ใส่ 2 คูปองซ้อน (PAW10 + FREESHIP, PAW10 + NEWCAT50) / ใส่ตัวเดิมซ้ำ / เปลี่ยนคูปอง → ตัวเก่าถูกถอดจริงไหม
  6. ใส่คูปองแล้วลดจำนวนสินค้าจนไม่ผ่านเงื่อนไข → ส่วนลดถูกถอด/คำนวณใหม่ไหม
  7. FREESHIP + จัดส่งด่วน → ฟรี ฿120 ด้วยไหม · FREESHIP กับยอดที่ส่งฟรีอยู่แล้ว (≥ ฿999)
  8. PAW10 ทำให้ยอด ฿1,000 เหลือ ฿900 → ยังส่งฟรีไหม (เกณฑ์ ฿999 คิดก่อน/หลังส่วนลด)
  9. ยอดรวมสุดท้ายติดลบหรือเป็น 0 ได้ไหม
- **ห้าม:** กดยืนยันสั่งซื้อ (ถ้าต้องดูว่าคูปองถูก "ใช้ไปแล้ว" หลังสั่ง → เขียนเคสส่งให้ C6)
- **ใช้บัญชี:** ของ C4 เอง

### C5 — ค่าจัดส่งและฟอร์ม checkout (ไม่กดยืนยัน)
**สำรวจ** หน้า checkout: วิธีจัดส่ง, ฟอร์มที่อยู่/เบอร์โทร, ช่องทางชำระเงิน — **หยุดก่อนปุ่มยืนยันสั่งซื้อ**
**ด้วย** ตะกร้ายอด ฿998/฿999/฿1,000 (ไม่ใส่คูปอง), ข้อมูลที่อยู่แบบปกติ/ผิด/สุดขอบ
**เพื่อหา** ค่าส่งผิดที่ขอบเขต, ด่วนกับส่งฟรีทำงานร่วมกันผิด, ฟอร์มรับข้อมูลผิดรูปแบบ, ข้อความ error

- **ความเสี่ยงที่เดา:** P1
- **เวลา:** 45 นาที
- **สิ่งที่ต้องลอง (อย่างน้อย 5):**
  1. ยอด ฿998 → ค่าส่ง ฿50, ยอด ฿999 → ฟรี, ยอด ฿1,000 → ฟรี
  2. ยอด ≥ ฿999 + เลือกด่วน → ฿120 หรือ ฿70 (ส่วนต่าง) หรือฟรี? จดพฤติกรรมจริง
  3. สลับปกติ ↔ ด่วนหลายครั้ง → ยอดรวมอัปเดตถูกทุกครั้ง ไม่บวกซ้ำ
  4. เบอร์โทร: 9 หลัก, 10 หลัก, ขึ้นต้น +66, มีขีด, ตัวอักษร
  5. รหัสไปรษณีย์ 4/5/6 หลัก, ชื่อ/ที่อยู่ว่าง, ยาวมาก, มีอีโมจิ/ภาษาไทย/`<b>`
  6. ไปหน้า checkout ด้วยตะกร้าว่าง หรือเปิด URL checkout ตรง ๆ โดยไม่ล็อกอิน
  7. Refresh หน้า checkout กลางทาง → ข้อมูลฟอร์ม/วิธีส่งที่เลือกค้างไหม
- **ห้าม:** ใส่คูปอง (C4) · กดยืนยันสั่งซื้อ (C6)
- **ใช้บัญชี:** ของ C5 เอง

### C6 — สั่งซื้อจริง ตัดสต็อก ประวัติคำสั่งซื้อ (เจ้าของข้อมูลกลาง)
**สำรวจ** ปุ่มยืนยันสั่งซื้อ, หน้าสำเร็จ/ใบสั่งซื้อ, ประวัติคำสั่งซื้อ, ผลต่อสต็อก และ `POST /api/test/reset`
**ด้วย** บัญชี demo (เจ้าของคนเดียว), สินค้าสต็อก 3, เคสที่ C3/C4/C5 ส่งต่อมา, DevTools (Network) ดู request สั่งซื้อ
**เพื่อหา** การขายเกินสต็อก, สั่งซ้ำจากการกดซ้ำ, ยอดในใบสั่งซื้อไม่ตรงกับหน้า checkout, คูปองใช้ซ้ำได้, reset ไม่คืนค่าครบ

- **ความเสี่ยงที่เดา:** P1 (เงินจริง + สต็อกจริง + ข้อมูลที่เปลี่ยนถาวร)
- **เวลา:** 60 นาที
- **สิ่งที่ต้องลอง (อย่างน้อย 5):**
  1. สั่งสินค้าปกติ 1 ชิ้น → ยอดในใบสั่งซื้อ = ยอดที่หน้า checkout (สินค้า + ค่าส่ง − ส่วนลด) และสต็อกลดลง 1
  2. สูตรลดก้อนขน: สั่ง 3 ชิ้น → สต็อกเป็น 0, ป้ายเปลี่ยนเป็น "หมด" · แล้วลองสั่งอีก 1
  3. Race: เปิดสองแท็บ/สองบัญชี ใส่สูตรลดก้อนขน 3 ชิ้นทั้งคู่ แล้วกดยืนยันพร้อมกัน → ขายเกินไหม
  4. ดับเบิลคลิกปุ่มยืนยัน / กด Back แล้วยืนยันซ้ำ / refresh หน้าสำเร็จ → เกิดคำสั่งซื้อซ้ำไหม
  5. แก้ request สั่งซื้อใน DevTools (ราคา, จำนวนติดลบ, productId ของไก่ฟรีซดราย) → server ตรวจซ้ำไหม
  6. ใช้คูปองเดิมกับคำสั่งซื้อที่สอง (NEWCAT50/PAW10 ใช้ได้กี่ครั้ง)
  7. ประวัติคำสั่งซื้อแสดงครบ ถูกบัญชี และไม่เห็นของบัญชีอื่น (ลองเปิด `/orders/<id ของคนอื่น>`)
  8. เรียก `POST /api/test/reset` → สต็อกกลับเป็น 0/3, ตะกร้า/คำสั่งซื้อถูกล้างตามคาด
- **ลำดับทำงาน (สำคัญ):** ดูข้อ 3 กติกา — ช่วงแรกสั่งเฉพาะสินค้าที่ไม่อยู่ใน TEST-DATA, เคสที่ใช้สินค้าสต็อก 0/3 ทำช่วงหลังเท่านั้น

### C7 — API ฝั่งอ่าน ความปลอดภัยพื้นฐาน และ UX/ข้อความ (cross-cutting)
**สำรวจ** request ที่หน้าเว็บเรียก (`/api/*`), console error, การแสดงผลบนมือถือ, ข้อความ error/รูปแบบเงิน ทั้งเว็บ
**ด้วย** DevTools (Network/Console), การยิง GET API ตรง, ขนาดจอ 375px/768px/1440px, คีย์บอร์ดอย่างเดียว
**เพื่อหา** API คืนข้อมูลเกินจำเป็น (เช่น รหัสผ่าน/ข้อมูลผู้ใช้อื่น), endpoint ทดสอบที่เปิดโล่ง, XSS ที่สะท้อนในหน้า, layout พัง, ข้อความ/สกุลเงินไม่สม่ำเสมอ

- **ความเสี่ยงที่เดา:** P2
- **เวลา:** 45 นาที
- **สิ่งที่ต้องลอง (อย่างน้อย 5):**
  1. ไล่ดูทุก request ใน Network ระหว่างใช้งานปกติ → ทำแผนที่ endpoint ส่งให้ทุก charter
  2. GET API สินค้า/ผู้ใช้/ตะกร้า → มีฟิลด์ลับ (password hash, cost, ข้อมูลบัญชีอื่น) ไหม
  3. GET `/api/orders/<id>` / `/api/users/<id>` ของคนอื่นโดยไม่ล็อกอินหรือใช้บัญชีอื่น (IDOR — อ่านอย่างเดียว)
  4. ใส่ `<img src=x onerror=alert(1)>` ในช่องค้นหา (สะท้อนใน URL/หน้า) — ใช้ `console.log` แทน `alert` เพื่อไม่ให้ dialog ค้าง
  5. Console error/404 asset ในทุกหน้าหลัก
  6. หน้าจอมือถือ 375px: header, ตะกร้า, checkout ใช้งานได้ไหม; ใช้แค่คีย์บอร์ด (Tab/Enter) สั่งของได้ถึงหน้า checkout ไหม
  7. รูปแบบเงิน (`฿1,000` vs `1000 บาท` vs `฿1000.00`) และภาษาข้อความ error สม่ำเสมอทุกหน้า
  8. ตรวจว่า `/api/test/reset` ถูกเปิดให้ใครก็เรียกได้ไหม — **ตรวจด้วยการดู OPTIONS/เอกสาร/การตอบกลับของ GET เท่านั้น ห้าม POST** (ถ้าต้องยืนยันด้วย POST ให้ส่งให้ C6)
- **ห้าม:** POST/PUT/DELETE ใด ๆ ที่เปลี่ยนข้อมูล (สั่งซื้อ ตะกร้า บัญชี reset) — เขียนเคสส่งต่อเจ้าของแทน

## 3. กติกากันชนกัน (หลาย agent บนเว็บเดียว)

### 3.1 ทรัพยากรกลาง และเจ้าของ

| ทรัพยากรกลาง | เจ้าของคนเดียว | คนอื่นทำได้แค่ |
|---|---|---|
| `POST /api/test/reset` | **C6** | ห้ามเรียกเด็ดขาด (รวมถึงทางอ้อม ดู 3.3) |
| การกดยืนยันสั่งซื้อ (สร้าง order) | **C6** | ไปได้ถึงหน้า checkout แล้วหยุด |
| สต็อกสินค้า (ทุกอย่างที่ทำให้สต็อกลด) | **C6** | อ่าน/สังเกตเท่านั้น |
| การใช้คูปองจนถูกนับว่า "ใช้แล้ว" | **C6** | ใส่/ถอดคูปองในตะกร้าได้ (C4) แต่ไม่สั่งซื้อ |
| บัญชี `demo@pawpantry.test` (ตะกร้า, ประวัติ, โปรไฟล์) | **C6** | C1 ล็อกอิน/ออกได้เท่านั้น ห้ามแก้ตะกร้า/โปรไฟล์/รหัส ห้ามล็อกอินผิดซ้ำ ๆ จนบัญชีถูกล็อก |
| ข้อมูลที่ผู้ใช้อื่นเห็น (รีวิว, Q&A ถ้ามี) | **C2** | ห้ามเขียน |

### 3.2 บัญชีแยกต่อ charter
- ทุก charter (ยกเว้น C6) ใช้บัญชีของตัวเอง ตั้งชื่อ `qa-c<เลข>@pawpantry.test` (เช่น `qa-c3@pawpantry.test`) รหัส `Paw12345`
- C1 สมัครบัญชีให้ทุก charter ตอนเริ่ม (ภายใน 5 นาทีแรก) แล้วประกาศรายชื่อ — ถ้าเว็บ **ไม่มีหน้าสมัคร** ให้ C3/C4/C5 ใช้ guest session (ไม่ล็อกอิน) และขอช่วงเวลาใช้บัญชี demo จาก C6 เป็นรอบ ๆ ทีละคน
- ใช้ browser profile / context แยกกันต่อ agent (cookie ไม่ปนกัน)

### 3.3 Reset และ Playwright
- `TEST-DATA` บอกว่า **Playwright เรียก reset ให้อัตโนมัติ** → agent ที่ไม่ใช่ C6 **ห้ามรันชุดเทสต์ Playwright ที่มี fixture reset** ระหว่างช่วงสำรวจ (มันจะล้างข้อมูลของคนอื่นกลางทาง) ให้ใช้เบราว์เซอร์สำรวจด้วยมือ/MCP แทน
- C6 reset ได้แค่ 2 จังหวะ: **T0 (ก่อนทุกคนเริ่ม)** และ **ท้ายช่วง 2 (หลังทุกคนจบ)** — ประกาศเวลาก่อนทุกครั้ง ถ้าจำเป็นต้อง reset กลางทาง ต้องแจ้งทุกคนและรอให้ทุกคนตอบว่า "พร้อม"

### 3.4 ลำดับช่วงเวลา

| ช่วง | เวลา | ใครทำอะไร |
|---|---|---|
| T0 | นาที 0 | C6 reset → ประกาศ "เริ่มได้" · C1 สมัครบัญชีให้ทุกคน |
| ช่วง 1 | นาที 0–45 | C1–C5, C7 สำรวจตามขอบเขต · C6 สั่งซื้อได้เฉพาะ **สินค้าที่ไม่อยู่ใน TEST-DATA** (ไม่แตะไก่ฟรีซดราย/สูตรลดก้อนขน) และรวบรวมเคสที่ถูกส่งต่อมา |
| ช่วง 2 | นาที 45–60+ | คนอื่นหยุดเคสที่พึ่งตัวเลขสต็อก · C6 ทำเคสสต็อก 0/3, race, คูปองใช้ซ้ำ, เคสส่งต่อ |
| ปิดงาน | หลังช่วง 2 | C6 reset ครั้งสุดท้าย แล้วตรวจว่าสต็อกกลับเป็น 0/3 |

### 3.5 การบันทึกและการรายงาน
- ทุกการกระทำที่เขียนข้อมูล (C6) บันทึกลง log กลาง: `เวลา | charter | บัญชี | การกระทำ | สินค้า/จำนวน | order id`
- ถ้าเห็นข้อมูลเปลี่ยนแบบไม่คาด (สต็อกไม่ใช่ 0/3, ตะกร้ามีของแปลก) → ตรวจ log ของ C6 ก่อน แล้วจดเป็น **"สงสัยชนกัน"** ไม่ใช่บั๊ก จนกว่าจะทำซ้ำได้หลัง reset
- รายงานบั๊กทุกตัวต้องมี: เวลา, บัญชีที่ใช้, ขั้นตอน, ผลที่คาด vs ผลจริง, ภาพ/HAR, และบอกว่าเกิดหลัง reset ครั้งไหน
- เจอเรื่องนอกขอบเขต → จดว่า "ส่งต่อ C?" พร้อมขั้นตอน แล้วกลับมาทำ charter ตัวเอง
- ห้ามใช้ `alert()`/`confirm()` ในการทดสอบ XSS หรือสคริปต์ใด ๆ (dialog จะทำให้เบราว์เซอร์อัตโนมัติค้าง) ใช้ `console.log` แทน

## 4. สมมติฐานที่ต้องยืนยันหลังเปิดเว็บ
- มีหน้าสมัครสมาชิกจริงไหม (ถ้าไม่มี แผนบัญชีแยกใน 3.2 ต้องเปลี่ยน)
- ตะกร้าเก็บฝั่ง server (ผูกบัญชี) หรือ localStorage (ผูกเบราว์เซอร์) — ถ้าเป็น server การใช้บัญชีร่วมกันจะชนกันแน่นอน
- คูปองใส่ที่ตะกร้าหรือที่ checkout (กระทบเส้นแบ่ง C3/C4/C5)
- เกณฑ์ ฿999 และ ฿500 คิดจากยอดก่อนหรือหลังส่วนลด
- มี endpoint สั่งซื้อที่แก้ราคาฝั่ง client ได้หรือไม่
