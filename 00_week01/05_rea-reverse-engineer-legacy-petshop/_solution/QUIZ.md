## 2. คำอธิบายรายข้อ + คำตอบผิดที่พบบ่อย

### ข้อ 1 · RE vs re-engineering (🎓 1 · LAB 1 ส่วน I · LAB 9 ส่วนที่ 2 ข้อ 3)

- **ประเด็นที่ต้องมี:** RE (Chikofsky & Cross 1990) = วิเคราะห์ระบบเพื่อระบุส่วนประกอบ/ความสัมพันธ์ และสร้าง **ตัวแทนระดับสูงขึ้น** เป็น *examination* ไม่ใช่ *change* · re-engineering = RE เพื่อเข้าใจ **แล้ว** forward engineering เป็นรูปใหม่ → เปลี่ยนระบบ · ประโยคจำ "RE = ดู ไม่ใช่แก้ · แก้ = re-engineering ที่ต้องมี RE ก่อน"
- **จัด LAB:** LAB 1–3 = RE ล้วน (LAB 1 = redocumentation + design recovery จากการอ่านโค้ด · LAB 2–3 = RE ของที่ build/รันอยู่) · LAB 6 8 10 = แก้โค้ดจริง (re-engineering · BUG-01 ถกได้ว่าเป็น restructuring ดูด้านล่าง) · LAB 5 7 = ช่วง RE/วิเคราะห์ของวงจร re-engineering (เพิ่มเทสต์ แต่ยังไม่แตะโค้ดแอป)
- **รับได้ทั้งสองแบบถ้ามีเหตุผล:** LAB 4 (characterization) และ LAB 9 (พิสูจน์) **ไม่เปลี่ยนพฤติกรรมระบบ** → จัดเป็น "RE/ตรวจ" ก็ได้ หรือ "ส่วนหนึ่งของวงจร re-engineering" ก็ได้ — ให้เต็มถ้าอธิบายด้วยเกณฑ์ "เปลี่ยนระบบไหม"
- **BUG-01 เป็น restructuring ไหม:** restructuring = เปลี่ยนโครงสร้าง **โดยพฤติกรรมภายนอกเหมือนเดิม** · การลบกฎค่าส่งชุดซ้ำทำให้ยอดคำสั่งซื้อ ฿999 เปลี่ยน (พฤติกรรมเปลี่ยน) → ตอบ re-engineering (แก้เชิงแก้ไข) แข็งแรงกว่า · ตอบ restructuring ได้ถ้าให้เหตุผลว่า "พฤติกรรมที่ **ตั้งใจ** ของระบบ (หน้าเว็บ) ไม่เปลี่ยน แค่รวมกฎให้อยู่ที่เดียว" · CR-01 และ PR-1 = re-engineering
- **ผิดบ่อย:** "RE = แกะโค้ดเพื่อแก้" (ปนกับ re-engineering) · "LAB 2 ใช้ REA เลยเป็น re-engineering" (เครื่องมือไม่ได้กำหนดชนิดงาน)

### ข้อ 2 · static ≠ runtime (🎓 2 · 4 · LAB 2 ข้อ 6 · LAB 3)

- static analysis พิสูจน์ได้แค่ "**มีโค้ด** เรียก `/api/orders` อยู่ใน bytes ของ bundle" (authority `ast-static-analysis` · ถัง 🔵) ไม่ได้พิสูจน์ว่าโค้ดถูกรัน ไม่รู้ว่าใครกด เมื่อไร ส่งอะไร · REA เขียนเองว่า static relationships ไม่พิสูจน์การ execute
- หลักฐานที่ใช้ได้: HAR (LAB 3 `pawpantry-main.har` มี POST `/api/orders` 201) หรือ scenario ที่ขับเบราว์เซอร์ (🟢) หรือ log ฝั่ง server
- **ผิดบ่อย:** "เจอใน bundle = ใช้งานจริง" · "ไม่เจอใน HAR รอบนี้ = ไม่มีใครใช้" (runtime = เฉพาะรอบที่สังเกต)

### ข้อ 3 · หาไม่เจอ ≠ ไม่มี (🎓 4 · LAB 2 ส่วน B)

- ของจริงในบท: `components/FinderWizard.tsx` เรียก `` fetch(`/api/recommendations?${sp.toString()}`) `` เป็น template literal → static ไม่ได้ค่าคงที่ → REA ไม่ลงเป็น endpoint · ผลรันจริงของ A1: endpoint 9 ตัวใน static มี `a` `b` `c` (ชื่อย่อ minify) และไม่มี `/api/recommendations`
- คำตอบที่ถูก: "static ยังไม่พบ · coverage `partial`" + เหตุผลที่เป็นไปได้ (ค่าประกอบตอนรัน / minify / อยู่ใน chunk ที่ไม่ได้วิเคราะห์) + วิธีเก็บตาที่สอง (เปิดหน้า `/finder` แล้วบันทึก HAR · อ่าน source)
- REA เขียนใน limitations ว่า fact ที่ไม่มีต้อง "must not be read as absence" · `added`/`removed` ใน version compare ให้ได้เฉพาะเมื่ออีกฝั่ง coverage `complete`
- **ผิดบ่อย:** "ไม่มี API นี้" · "API นี้ถูกลบแล้ว" · เขียน TC แบบ "ต้องไม่มี X" จากหลักฐาน partial (กติกา [E] ข้อ 6)

### ข้อ 4 · 3 คำถามต่อหลักฐาน (🎓 4 · ทุก LAB ที่ใช้ REA)

- (1) **มาจาก bytes/การรันไหน** → `subject.digest` / SHA-256 / ชื่อไฟล์ HAR + เวลา · (2) **เห็นจริงหรืออนุมาน** → authority + state (`observed` / `inferred` / `unknown`) = ป้าย 🔵🟢🟡⚪ · (3) **ตรวจครบไหม** → coverage `complete` / `partial` / `unknown` + limitations
- ให้เต็มถ้าตอบ 3 แกนนี้ด้วยคำของตัวเอง แม้ไม่ใช้ศัพท์ REA ตรงตัว · คำตอบที่ได้แค่ "เชื่อถือได้ไหม" กว้าง ๆ = ไม่ได้คะแนน

### ข้อ 5 · SHA-256 และ path (🎓 5 · LAB 2 ข้อ 2 · LAB 9 ส่วนที่ 1)

- path เดียว hash ต่าง = bytes ต่าง → เนื้อหาเปลี่ยน ต้องเทสต์ฟีเจอร์ที่เกี่ยวซ้ำ (REA: *"A path never overrides a digest disagreement"*)
- hash เท่ากัน = bytes เดียวกันทุก byte → ตัดออกจาก regression scope ได้มั่นใจ **แต่ไม่ได้แปลว่าถูก** (บั๊กเดิมก็ hash เท่าเดิม)
- กับดักในบท: `next build` เขียนไฟล์ให้เอง (เช่น `next-env.d.ts`) → hash ต่างโดยไม่มีใครแก้ ต้องอธิบายได้ (รูบริกข้อ 17)
- **ผิดบ่อย:** "hash เท่ากัน = ผ่านการทดสอบแล้ว" · "ชื่อ chunk เหมือนกัน = ไฟล์เดียวกัน"

### ข้อ 6 · เมื่อไรไม่ต้องใช้ REA (🎓 3 · LAB 2 ส่วน C ข้อ 3)

- skill `reverse-engineer-anything` เขียนตรงตัว: *"Skip REA for ordinary source-repository architecture analysis"* → มี source ครบและเชื่อได้ การอ่าน repo ตรงกว่า ถูกกว่า (Evidence ของ REA ~400 KB–54 MB ต่อไฟล์ ล้น context)
- บทนี้ใช้ REA กับ "ของที่ส่งมอบ/รันอยู่": build ใน `out\v1` `out\v2` (LAB 2 9) · HAR (LAB 3 9) · scenario ขับเบราว์เซอร์ (LAB 3) · **source-to-bundle** = ยืนยันว่า build ที่ส่งมอบตรงกับ source ที่เราแก้ (LAB 9) — เป็นเรื่องที่อ่าน repo อย่างเดียวพิสูจน์ไม่ได้
- **ผิดบ่อย:** "REA เก่งกว่าอ่านโค้ด ใช้ทุกครั้ง" · "ใช้ REA หาบั๊ก BUG-01" (กฎเงินอยู่ฝั่ง server · client bundle ไม่เห็นตรรกะนี้ → 🎓 8 ขีดจำกัด)

### ข้อ 7 · HAR ออฟไลน์ + ความลับ (🎓 6 · 8 · LAB 3 ข้อ 2 · 5)

- `inspect-web-network-capture` อ่านไฟล์ HAR อย่างเดียว **ไม่ fetch URL ซ้ำ** (historical evidence) · ตรงข้ามกับ `capture-browser-scenario` ที่ขับเบราว์เซอร์จริงและมีผลข้างเคียงกับข้อมูล
- อันตรายใน HAR ต้นฉบับ: body ของ POST `/api/auth/login` มี **อีเมล + รหัสผ่านเป็น plain text** · header มี cookie `pp_session` · ที่อยู่/เบอร์ในคำสั่งซื้อ (PDPA) → REA ตัด cookie/authorization ให้อัตโนมัติ ส่วนรหัสผ่านใน body ต้องใส่ `--sensitive-value` เอง · ไฟล์ `.har` ต้นฉบับยังมีค่าลับ → `.gitignore` กัน `*.har` `out/` · ห้ามแนบ/ส่งต่อ/ส่งให้ AI ตัวอื่น
- **ผิดบ่อย:** "REA ตัดความลับให้หมดแล้ว ส่งไฟล์ HAR ได้" (ตัดใน **ผลของ REA** ไม่ได้แก้ไฟล์ต้นฉบับ)

### ข้อ 8 · [E] ขัด [D] (🎓 7 · LAB 4 ข้อ 4)

- [E] = เชื่อได้ว่าระบบ **ทำ** แต่ไม่ใช่ว่า **ควร** · [D] = ร้านบอกว่าควร → ขัดกัน = **ผู้ต้องสงสัยบั๊ก** ไม่ใช่ "test ผิด"
- ทำ **test คู่**: (ก) ล็อกค่าปัจจุบัน ฿150 ติด annotation `legacy-quirk` (กันการเปลี่ยนโดยไม่รู้ตัว) (ข) `test.fail()` กับค่าตาม [D] ฿120 ติด `KNOWN-ISSUE` (เขียวเพราะล้มตามคาด → พอแก้แล้วจะขึ้น "Expected to fail, but passed" = สัญญาณให้ปรับคู่) · จดใน BASELINE หัวข้อ "ผู้ต้องสงสัย" แล้วถามร้าน
- **ผิดบ่อย:** `expect(150)` เฉย ๆ (= อบบั๊กลงผลที่คาดหวัง · รูบริกข้อ 8 ได้ 0) · `expect(120)` ข้อเดียวที่แดงค้าง (suite แดงตลอด คนจะเริ่มเพิกเฉย) · แก้โค้ดทันทีใน LAB 4 (ยังไม่ได้ทำซ้ำ/ถามร้าน)

### ข้อ 9 · `unknown` ใน source-to-bundle (🎓 5 · LAB 9 ส่วนที่ 1 ข้อ 3)

- `compare-source-to-bundle` จับคู่ source กับ bundle ด้วย digest · มี 7 คลาส `unchanged · modified · removed · split · merged · duplicated · unknown` (`C:/t/rea/src/docs/javascript-application-workflows.md:163`)
- ผลรันจริงของ A1 (`_design/rea-probe/evidence/07-*`): `modified = 0` **ทุกคู่** · ไฟล์ที่แก้ (`lib/pricing.ts` ในรอบ probe) = `duplicated` ในคู่เวอร์ชันเดียวกัน และ `unknown` ในคู่ข้ามเวอร์ชัน → "ไฟล์ที่แก้แล้ว" จะโผล่เป็น unknown ไม่ใช่ modified
- อ่านให้ถูก: unknown = "REA หา digest ของ source นี้ใน bundle นั้นไม่เจอ" → สอดคล้องกับการแก้ **แต่** ต้องยืนยันด้วยตาที่สอง (SHA-256 ของ source v1↔ปัจจุบัน · คู่ v2src→v2build ต้องกลับมา unchanged/duplicated)
- ข้อควรรู้: เทียบกับ **static** bundle จะได้ unknown ทุกไฟล์ (A1: unknown 56) เพราะ client bundle ไม่มี source map ที่ map กลับ → LAB 9 ใช้ server bundle
- **ผิดบ่อย:** "unknown = ไฟล์หาย/ถูกลบ" · "ไม่มี modified = ไม่ได้แก้อะไร" · รายงานแค่คลาสที่ไม่เป็น 0 (พรอมต์ให้รายงานครบ 7 คลาส)

### ข้อ 10 · เทสต์เขียว ≠ ไม่มีบั๊ก (กับดักท้าย 🎓 · LAB 4 ข้อ 2 · LAB 5)

- เขียว = "ไม่มีข้อที่ **เขียนไว้** ล้ม" · ต้องถาม 3 อย่างกับชุดเดิม: ตรวจ **กฎอะไร** · ที่ **ค่าขอบไหน** · ตรวจ **ที่จุดไหน** (หน้าตะกร้า · ปุ่มยืนยัน · response ของ server · หน้าคำสั่งซื้อ/บัญชี)
- เครื่องมือช่วย: ตาราง "กฎ × TC × จุดที่ตรวจ" (LAB 4 ข้อ 2) · อ่านตัว test ไม่ใช่แค่ชื่อ · oracle ใหม่ [R] "เงินบนปุ่มยืนยัน = เงินที่ server บันทึก"
- **ผิดบ่อย:** "เขียว 120/120 แปลว่าพร้อม deploy" (ตรงกับประโยคใน `HANDOVER-NOTES.md` ที่ตั้งใจวางไว้) · "ต้องเพิ่ม test ให้ครบ 100% coverage" (ไม่ตอบว่าตรวจอะไรเพิ่ม)
