|---|---|
| ผลจาก LAB ก่อนหน้า (สัมภาษณ์ → User Story → FR/BR/NFR) | `REQUIREMENTS.md` ที่รากของบท มีรหัส `US-xx`, `FR-xx`, `BR-xx`, `NFR-xx` (ถ้าบทใช้ชื่ออื่นให้แก้คำในพรอมต์ให้ตรง) |
| โฟลเดอร์ที่ Claude จะสร้าง | `spa/` (เว็บ + Docker) · `e2e/` (Playwright) · `BUILD-PROMPT.md` · `TEST-PLAN.md` · `CLAUDE.md` |

## A. LAB · ให้ Claude เขียน "พรอมต์สร้างเว็บ" (BUILD-PROMPT.md)

🎯 เปลี่ยน requirement เป็นพรอมต์สร้างเว็บที่ละเอียดพอให้ AI ทำตามได้ (เราเขียนพรอมต์ด้วย AI อีกที)

💬 **คัดลอกพรอมต์นี้**

```text
อ่าน REQUIREMENTS.md และดูชื่อไฟล์รูปทั้งหมดในโฟลเดอร์ assets/ (ห้ามสร้างโค้ดเว็บในขั้นนี้)
แล้วเขียนไฟล์ BUILD-PROMPT.md 1 ไฟล์ เป็นพรอมต์ภาษาไทยที่ผมจะ copy ไปสั่ง Claude สร้างเว็บ
"สบายใจ สปา · Sabai Jai Wellness Spa" โดยพรอมต์นั้นต้องสั่งให้ครบทุกข้อนี้

1. เทคโนโลยี: Next.js (App Router, TypeScript) + PostgreSQL ใช้ไลบรารี pg เขียน SQL ตรง ๆ (ไม่ใช้ ORM)
   สร้างทุกอย่างในโฟลเดอร์ spa/ · docker compose มี 2 service เท่านั้น: web (sabai-web, พอร์ต 3000) และ db (sabai-db, postgres:16-alpine ไม่เปิดพอร์ตออก host)
2. Docker: db มี healthcheck pg_isready · web depends_on db แบบ service_healthy
   web มี healthcheck เรียก /api/health ด้วย node (ไม่ใช้ curl) · Next.js output standalone, HOSTNAME=0.0.0.0, TZ=Asia/Bangkok
   หน้าที่อ่าน DB ต้องเป็น dynamic (ห้ามต่อ DB ตอน build) · ตอนเริ่ม web ให้สร้างตารางและ seed เองถ้ายังไม่มี (ลองต่อ DB ซ้ำได้ 30 วินาที)
3. Windows-friendly: ห้ามมีไฟล์ .sh ที่ต้องรันตอนเริ่ม (ใช้ node แทน) · ใส่ .gitattributes ให้เป็น LF · ทุกคำสั่งในคู่มือใช้ได้ใน PowerShell
4. รูป: คัดลอก assets/ ไปไว้ที่ spa/public/assets/ แล้วใช้รูปจากที่นั่นทุกรูป ห้ามใช้รูปจากเน็ต ห้ามแก้ไฟล์ใน assets/
5. ดีไซน์ "ว้าว": โทนไทยร่วมสมัย (เขียวใบตอง ครีม ทอง) ฟอนต์ไทยอ่านง่าย hero ใหญ่ การ์ดมีเงา animation นุ่ม ๆ รองรับมือถือ
6. ฟีเจอร์ครบตาม REQUIREMENTS.md (AI ผิว, Quiz, Chatbot ไทย/อังกฤษ/จีน, Before/After, จองคิว, นักบำบัด+รีวิว,
   จองคู่/กลุ่ม, จองตามอารมณ์, Wallet, ระดับสมาชิก+แต้ม+วันเกิด, Gift Card, Dashboard+กราฟ, 360 Tour, สมุนไพร, เพลง, แพ็กเกจนักท่องเที่ยว)
7. "AI" ทุกตัวเป็นกฎตายตัว (rule-based) ไม่เรียก API ภายนอก: ข้อมูลเดิมต้องได้ผลเดิมทุกครั้ง
   (วิเคราะห์ผิว = คำตอบ + ค่าเฉลี่ยสีของรูปที่คำนวณในเบราว์เซอร์ ไม่อัปโหลดรูปขึ้นเซิร์ฟเวอร์)
8. เพลงเปิดด้วยปุ่มเท่านั้น สร้างเสียงด้วย Web Audio · LINE/email ของ Gift Card เป็นการจำลอง (โชว์ข้อความที่ "ส่ง")
9. ตัวเลขทุกอย่างตายตัว: ราคา ส่วนลดสมาชิกแต่ละระดับ อัตราแต้ม สิทธิวันเกิด เวลาเปิด-ปิด ความยาวคิว
10. สำหรับ test: data-testid ทุกปุ่ม ช่องกรอก ผลลัพธ์ และข้อความ error · <html data-ready="true" data-bug-mode="0|1">
    GET /api/health ตอบ { ok: true, db: true, now } · POST /api/test/reset (เปิดเมื่อ ALLOW_TEST_RESET=1) ล้างข้อมูลกลับเป็น seed
    และรับ { now } เพื่อล็อก "วันนี้" ของเว็บ · seed ผู้ใช้ตัวอย่างอย่างน้อย 3 คน (สมาชิกทั่วไป, Gold, คนที่เกิดเดือนเดียวกับ now) พร้อม wallet
11. BUG_MODE=1 (env ใน compose ค่าเริ่ม 0) ฝังบั๊ก 3 จุดที่ test ควรจับได้ และเป็นเรื่องเงินหรือคิว เช่น
    ส่วนลดสมาชิกคิดผิด, จองนักบำบัดเวลาเดียวกันซ้อนได้, จองด้วย wallet แล้วจำนวนครั้งไม่ลด (เลือกเองได้ถ้ามีที่ดีกว่า)
    เขียนเฉลยไว้ที่ spa/BUGS.md เท่านั้น ห้ามใส่ใน SPEC.md
12. เขียน spa/SPEC.md คู่กัน: ตารางหน้าเว็บ, ราคา/กฎทุกข้อโยงรหัส FR/BR, ตาราง data-testid ทุกตัว, ข้อความ error ทุกข้อความแบบคำต่อคำ, API ทุกเส้น, ผู้ใช้ seed
13. ขั้นสุดท้ายของพรอมต์: docker compose up -d --build แล้วรอจน 2 container healthy, เปิด /api/health ให้ดู, สรุปเป็นตาราง
    ถ้าขั้นไหนไม่ผ่านให้หยุดแล้วบอกสาเหตุ

ให้ BUILD-PROMPT.md สั้นที่สุดเท่าที่ยังครบ (ไม่เกิน 150 บรรทัด) แบ่งเป็นหัวข้อมีเลขขั้น
เสร็จแล้วสรุปเป็นตาราง: หัวข้อในพรอมต์ | FR/BR ที่ครอบคลุม | FR/BR ที่ยังไม่ครอบคลุม (ถ้ามี)
```

✅ **ผลที่ควรได้** ไฟล์ `BUILD-PROMPT.md` ~100–150 บรรทัด + ตารางโยง FR/BR ไม่มีช่อง "ยังไม่ครอบคลุม"

👀 **สังเกต**
- พรอมต์ที่ดีบอก **"ทำอะไร" + "ตรวจยังไงว่าเสร็จ"** (ข้อ 13) ไม่ใช่แค่รายการฟีเจอร์
- ข้อ 10–12 คือ "ของที่ tester ขอจาก dev" → ไม่มี testid / reset / เวลาล็อก = test เปราะ

## D. LAB · สร้างแผนการทดสอบ (TEST-PLAN.md)

🎯 เปลี่ยน requirement เป็น ~30 test case ที่โยงกลับไปหา FR/BR ได้ทุกข้อ

💬 **คัดลอกพรอมต์นี้**

```text
อ่าน REQUIREMENTS.md และ spa/SPEC.md (ห้ามเปิด spa/BUGS.md) แล้วเขียน TEST-PLAN.md แบบเดียวกับ tester มืออาชีพ
1. ระบบที่ทดสอบ · ขอบเขต (ทดสอบ / ไม่ทดสอบ) เป็นตาราง
2. เทคนิคที่ใช้พร้อมตัวอย่างจากเว็บนี้: happy path, negative, boundary, equivalence, state (รีโหลด/ทำซ้ำ), API
3. ระดับ P1 = เงินผิด/จองไม่ได้/จองซ้อน · P2 = ฟีเจอร์สำคัญ · P3 = สวยงาม/เกิดไม่บ่อย
4. ตาราง test case ประมาณ 30 ข้อ: ID (TC-<โมดูล>-01) | โมดูล | สิ่งที่ทดสอบ | FR/BR | ระดับ | ข้อมูลที่ใช้ | ผลที่คาดหวัง (ตัวเลข/ข้อความจริงจาก SPEC)
   โมดูล: HOME, MOOD, BOOK, THER, AI, CHAT, MEM, WAL, GIFT, DASH, EXP, MOB, API
   ต้องมี: E2E จองจนจบ 1 ข้อ, ค่าขอบของส่วนลด/แต้ม/วันเกิดอย่างน้อย 3 ข้อ, จองซ้อน 1 ข้อ, API ไม่ login ต้องได้ 401
5. ตาราง Traceability: FR/BR | TC ที่ครอบคลุม — ทุก FR/BR ต้องมีอย่างน้อย 1 TC
6. Entry criteria: 2 container healthy และ /api/health ok · Exit criteria: P1 ผ่านหมด และผ่านรวม ≥ 95%
7. ข้อมูลทดสอบ: ผู้ใช้ seed, วันเวลาที่ล็อก (now), ราคาที่ใช้
ถ้า SPEC ไม่บอกค่าที่ต้องใช้ ให้เขียนว่า "ต้องถาม" ห้ามเดา
สรุปท้ายเป็นตาราง: โมดูล | จำนวน TC | P1 | P2 | P3
```

✅ **ผลที่ควรได้** `TEST-PLAN.md` ~30 TC, ทุก FR/BR มี TC รองรับ, P1 ประมาณ 10 ข้อ

👀 **สังเกต**
- คอลัมน์ **FR/BR** ทำให้ตอบได้ว่า "ทดสอบครบทุกความต้องการหรือยัง" (traceability)
- เราไม่ให้ Claude อ่านเฉลยบั๊ก → ถ้า test จับบั๊กได้ใน LAB F แปลว่าแผนดีจริง ไม่ได้โกง

## E. LAB · เขียน + รัน Playwright test 3 เบราว์เซอร์ (2 พรอมต์)

💬 **คัดลอกพรอมต์นี้**

```text
สร้างโฟลเดอร์ e2e/ เป็นโปรเจกต์ Playwright (TypeScript) สำหรับทดสอบ http://localhost:3000 ห้ามแก้โค้ดใน spa/
(ถ้ามีโฟลเดอร์ ..\02_petshop-playwright-docker\e2e ให้ดูเป็นแบบอย่างได้ แต่ห้ามแก้ไฟล์ในนั้น)

2. playwright.config.ts: chromium/firefox/webkit, viewport 1280x800, locale th-TH, timezoneId Asia/Bangkok,
   retries 0, trace/screenshot เมื่อล้ม · GIF=1 → อัดวิดีโอทุก test + slowMo 650 เฉพาะ chromium
3. global-setup.ts: เช็ก /api/health ถ้าไม่พร้อมให้ error ภาษาไทยบอกวิธีเปิดเว็บ แล้ว POST /api/test/reset พร้อม now ที่ล็อกไว้
4. tests/fixtures.ts: open(page, path) รอ html[data-ready=true] · ล็อกนาฬิกาเบราว์เซอร์ให้ตรง now · login ผ่าน API
   · สร้างผู้ใช้ใหม่อีเมลไม่ซ้ำ · เลือกช่องเวลาจองที่ไม่ชนกันข้ามเบราว์เซอร์ (เลื่อนวันตามชื่อ project)
   · โหมด GIF: ป้ายชื่อ test มุมซ้ายล่าง + วงแดงตรงจุดคลิก + ค้างเฟรมสุดท้าย 2.5 วินาที
5. reporters/tester-report.ts เขียน test-report/TEST-REPORT.md: ข้อมูลการทดสอบ (โหมด BUG_MODE จาก data-bug-mode),
   1 สรุปผล + exit criteria, 2 ผลตามโมดูล, 3 ผลราย TC ทุกเบราว์เซอร์ + ลิงก์ GIF/MP4, 4 Defects (DEF-001…: ความรุนแรงจาก P,
   ผลที่คาดหวัง, ผลจริงแปลเป็นภาษาคน, ขั้นตอนทำซ้ำ, หลักฐาน) · แปลงวิดีโอเป็น gifs/<TC>.gif และ videos/<TC>.mp4 ด้วย ffmpeg
   ถ้า ffmpeg ไม่มีให้เตือนแต่ยังเขียนรายงานได้
6. รูปแบบ test: ชื่อขึ้นต้นด้วยรหัส TC จาก TEST-PLAN.md · tag ['@<โมดูล>', '@P1|@P2|@P3'] · annotation expected = ผลที่คาดหวัง
   · หา element ด้วย getByTestId ตาม spa/SPEC.md เท่านั้น ห้ามเดา selector · ห้ามใช้ waitForTimeout เพื่อรอผล
7. เขียน test แค่ 2 ข้อก่อน (TC-HOME-01 และ TC-API-01) รัน npx playwright test ให้ผ่าน 3 เบราว์เซอร์ แล้วรัน npm run test:gif
8. เขียน CLAUDE.md ที่รากของบท: โครงสร้างโฟลเดอร์, คำสั่งเปิดเว็บ/BUG_MODE ใน PowerShell, วิธีเขียน test ใหม่ตามข้อ 6
ถ้าขั้นไหนไม่ผ่านให้หยุดแล้วบอก สรุปเป็นตาราง: ไฟล์ | ทำหน้าที่อะไร
```

✅ **ผลที่ควรได้** 2 test × 3 เบราว์เซอร์ = **6 passed** · มี GIF + MP4 อย่างละ 1–2 ไฟล์ · มี `TEST-REPORT.md` และ `CLAUDE.md`

### E2 · เขียน test ครบตามแผน แล้วรัน

💬 **คัดลอกพรอมต์นี้**

```text
เขียน test ทุกข้อใน TEST-PLAN.md ลงใน e2e/tests/ (แยกไฟล์ตามโมดูล ใช้ fixtures เดิม) ห้ามอ่าน spa/BUGS.md
1. รัน npx playwright test (3 เบราว์เซอร์) · ถ้ามีข้อล้ม ให้ดูภาพ/trace ก่อน แล้วบอกว่าเป็น "บั๊กของเว็บ" หรือ "test เขียนผิด"
   แก้ได้เฉพาะ test ที่เขียนผิดจริง (selector/ลำดับขั้น) ห้ามเปลี่ยนผลที่คาดหวังให้ผ่าน ห้ามแก้โค้ดเว็บ
2. รันซ้ำอีก 1 รอบ ถ้าผลไม่เหมือนรอบแรก = test ไม่นิ่ง (flaky) ให้บอกข้อนั้นและสาเหตุ
3. รัน npm run test:gif แล้วเปิด GIF ของ test จองคิวจนจบ (E2E) ให้ผมดู
4. สรุปจาก e2e/test-report/TEST-REPORT.md เป็นตาราง: เบราว์เซอร์ | ผ่าน | ล้ม · และบอกว่าผ่านเกณฑ์ไหม
```

✅ **ผลที่ควรได้** ~30 test × 3 = **~90 passed** (BUG_MODE=0) · GIF/MP4 ทุกข้อที่เปิดหน้าเว็บ · รายงาน "ผ่านเกณฑ์ พร้อมปล่อยใช้งาน"

👀 **สังเกต**
- E1 ทำ "ครึ่งเดียวให้ผ่านก่อน" → เจอปัญหาเครื่องมือ (ffmpeg, เบราว์เซอร์) ตั้งแต่ต้น ไม่ต้องรอ 30 ข้อ
- รัน 2 รอบผลต้องเหมือนกัน — test ที่ผ่านบ้างล้มบ้างอันตรายกว่า test ที่ล้มตรง ๆ
