## 1. วัตถุประสงค์และสิ่งที่ต่างจากบท 02

### 1.1 วัตถุประสงค์การเรียนรู้
เมื่อจบบทนี้ ผู้เรียนจะ
1. **สำรวจเว็บแบบมีเป้าหมาย** (exploratory testing) ด้วย Claude Code + Playwright MCP แล้วสรุปเป็นแผนผังเว็บ รายการฟีเจอร์ และกฎที่พบ
2. **หากฎและความเสี่ยง** จากหน้าจอ (ฟอร์ม ราคา ขีดจำกัด ข้อความ error) แล้ว **จัดระดับ P1/P2/P3** ได้เอง
3. **เขียน TEST-PLAN.md ครบ 8 หัวข้อ** ตามหลักเดียวกับบท 02 ด้วยตัวเอง
4. **ออกแบบ test case ด้วย 6 เทคนิค** (Happy, Negative, Boundary, Partition, State, Security) และเขียนผลที่คาดหวังเป็นตัวเลข/ข้อความที่ตรวจได้
5. **รู้ที่มาของผลที่คาดหวัง (test oracle)** ทุกข้อ และรู้ว่าเมื่อไรต้อง "ถามทีม" แทนการลอกจากหน้าจอ
6. **ตรวจคุณภาพแผน** (coverage matrix ฟีเจอร์ × เทคนิค, หาจุดกำกวม) แล้วพิสูจน์ด้วยการแปลงแผนเป็น Playwright และรันกับโหมดบั๊ก

### 1.2 ต่างจากบท 02 อย่างไร

| ผลที่คาดหวังมาจาก | SPEC.md (เชื่อได้) | 3 แหล่ง ต้องชั่งน้ำหนักเอง (ดู 1.3) |
| ทักษะที่ได้ | อ่านแผน · สั่งสร้าง test · อ่านรายงาน | สำรวจ · คิด test case · เขียนแผน · ตรวจแผน |

**ทำไมต้องมีบทนี้:** งานจริงส่วนใหญ่ไม่มีสเปกครบ tester ต้องเรียนรู้ระบบจากการใช้งาน แล้วตัดสินใจเองว่าอะไร "ถูก" บทนี้ฝึกทักษะที่ AI ทำแทนไม่ได้ทั้งหมด คือ **การตัดสินว่าอะไรควรทดสอบ และผลแบบไหนถึงนับว่าถูก**

### 1.3 ปัญหาหัวใจของบท: ไม่มีสเปก แล้วรู้ได้ยังไงว่าผลไหน "ถูก"? (Test oracle)

ผลที่คาดหวังทุกข้อในแผนต้องติดป้าย **ที่มา** 1 ใน 3 แบบ

| ป้าย | ที่มา | ตัวอย่าง | เชื่อได้แค่ไหน |
|---|---|---|---|
| **[D] ข้อมูลทีม** | TEST-DATA.md | PAW10 ลด 10% · ค่าส่ง ฿50 ฟรีเมื่อครบ ฿999 | ✅ สูงสุด ทีมพัฒนายืนยันแล้ว |
| **[R] กฎทั่วไป / สามัญสำนึก** | คณิตศาสตร์ กฎหมาย/มาตรฐานที่ทุกคนรู้ ประสบการณ์ใช้เว็บขายของ | ฿799 × 10% = ฿79.9 · เบอร์มือถือไทย 10 หลักขึ้นต้น 0 · ลบรายการโปรดแล้วตัวเลขต้องลด · สินค้าหมดต้องซื้อไม่ได้ | 🟡 ดี แต่ต้องเขียนเหตุผลกำกับ |
| **[O] สังเกตจากเว็บ** | สิ่งที่เห็นบนหน้าจอตอนสำรวจ | ข้อความ error "รหัสไปรษณีย์ต้องเป็นตัวเลข 5 หลัก" · ค้น "แซลมอน" พบ 5 รายการ | 🔴 ต่ำสุด เว็บอาจผิดอยู่แล้ว |

**กับดักสำคัญ: "อบบั๊กลงในผลที่คาดหวัง" (baking the bug in)**
ถ้าลอกค่าจากหน้าจอไปเป็นผลที่คาดหวังตรง ๆ แล้วเว็บผิดอยู่แล้ว test จะ **ผ่านตลอดไป** แม้ระบบผิด เช่น ถ้าสำรวจตอนที่ PAW10 ลดแค่ ฿7 แล้วเขียนว่า "ส่วนลด ฿7" แผนนี้ก็ไม่มีวันจับบั๊กได้

กฎ 3 ข้อที่ผู้เรียนต้องใช้
1. **[O] ต้องผ่านการตรวจด้วย [D] หรือ [R] ก่อน** ถ้าตรวจไม่ได้ ให้เขียนลง "คำถามถึงทีม" (QUESTIONS) และติดป้าย `[O-ยังไม่ยืนยัน]`
2. **ตัวเลขเงินคำนวณเอง** จาก [D] + [R] ไม่ลอกยอดจากหน้าจอ แล้วค่อยเปิดเว็บดูว่าตรงไหม ถ้าไม่ตรง = **อาจเป็นบั๊ก ไม่ใช่แก้แผนตามเว็บ**
3. **ข้อความ error** มาจากการสังเกตได้ แต่ต้องตรวจว่า "สมเหตุสมผล" (บอกปัญหาถูกช่อง ภาษาถูก)

> หมายเหตุผู้สอน: ผู้เรียนสำรวจตอน `BUG_MODE=0` จึงสังเกตเห็นค่าที่ถูก แต่ LAB 8 จะให้ลองคิดย้อนว่า "ถ้าวันสำรวจเว็บมีบั๊กอยู่แล้ว แผนของเรายังจับได้ไหม" ข้อที่อิง [D]/[R] จะรอด ข้อที่อิง [O] ล้วนจะพลาด

### 1.4 กติกาสำรวจแบบ black-box
ผู้เรียนมีโค้ดใน `petshop/` แต่ **ห้ามให้ Claude อ่านโค้ดเพื่อหากฎ** (ในโค้ดมี `lib/bugmode.ts`, `lib/pricing.ts` ที่เฉลยบั๊กและกฎทั้งหมด) ทุกพรอมต์สำรวจจึงมีประโยค
`ห้ามเปิดอ่านไฟล์ในโฟลเดอร์ petshop ให้เรียนรู้จากหน้าเว็บเท่านั้น`
ข้อยกเว้น: ดู `data-testid` / ป้ายชื่อปุ่มจากหน้าเว็บ (DOM) ผ่าน Playwright MCP ได้ เพราะเป็นสิ่งที่เห็นจากเบราว์เซอร์

### LAB 3 · ล่ากฎและความเสี่ยง แล้วจัดระดับ P1/P2/P3

🎯 เปลี่ยน "เว็บทำอะไรได้" เป็น "กฎที่ต้องถูก" และ "จุดที่ถ้าพังแล้วเจ็บ"

💬
```text
อ่าน EXPLORATION.md และ TEST-DATA.md แล้วใช้ Playwright MCP ลองเว็บต่อเพื่อหากฎ (ห้ามเปิดอ่านโค้ดในโฟลเดอร์ petshop)

2. ราคาและเงิน: ยอดรวม ส่วนลดคูปองทุกตัวใน TEST-DATA.md ค่าส่งธรรมดา/ด่วน ก่อนและหลัง ฿999 การปัดเศษ

4. สถานะ: รีโหลดแล้วตะกร้า/รายการโปรด/ตัวเลขบนหัวเว็บยังถูกไหม ออกจากระบบแล้วเข้าหน้าชำระเงินได้ไหม
เพิ่มลง EXPLORATION.md:
- ส่วน C กฎที่พบ: ตาราง กฎ | ตัวอย่างที่ลอง | ผลที่เห็น | ที่มา [D] TEST-DATA / [R] กฎทั่วไป / [O] เห็นจากเว็บอย่างเดียว

  ใช้เกณฑ์ P1 = ขายของไม่ได้ เงินผิด หรือสิทธิ์/ข้อมูลผิด · P2 = ฟีเจอร์สำคัญผิดแต่ยังซื้อได้ · P3 = การแสดงผลหรือกรณีเกิดไม่บ่อย
- ส่วน E คำถามถึงทีม: สิ่งที่เว็บทำแต่เราไม่แน่ใจว่าถูก หรือ TEST-DATA ไม่ได้บอก
ห้ามตัดสินว่าสิ่งที่เห็นบนหน้าจอถูกเสมอ ถ้าผลที่เห็นขัดกับ TEST-DATA หรือกฎทั่วไป ให้ทำเครื่องหมาย ⚠️
```

📄 ได้: `EXPLORATION.md` ส่วน C กฎ (~20–30 ข้อ) · D ความเสี่ยง · E คำถามถึงทีม (~5–10 ข้อ)

👀
- คำถามดี ๆ ที่ควรเกิด (ผู้สอนใช้ตรวจ): PAW10 กับ ฿799 ได้ ฿79 หรือ ฿80 (ปัดลง?) · ส่งด่วนเกิน ฿999 ฟรีไหม · NEWCAT50 นับของเล่นแมวด้วยไหม · ใช้คูปองซ้อนได้ไหม · ตัวพิมพ์เล็ก `paw10` ใช้ได้ไหม

- P1 ควรตกที่: ยอดเงิน/คูปอง/ค่าส่ง · สั่งซื้อจนจบ · ฟอร์มที่อยู่ · เข้าสู่ระบบ · สั่งซื้อโดยไม่ login

### LAB 8 · โหมดบั๊กปริศนา — แผนของเราจับได้ไหม? 🐞

🎯 ผู้สอน (หรือพรอมต์) เปิด `BUG_MODE=1` ซึ่งฝังบั๊กไว้โดย **ไม่บอกว่าอยู่ตรงไหน** ดูว่าแผนที่เขียนเองจับได้กี่ตัว แล้วเรียนรู้เรื่อง oracle

💬 (ส่วนที่ 1 · จับบั๊ก)
```text
เปิดเว็บใหม่ในโหมดฝึก: ในโฟลเดอร์ petshop ตั้ง BUG_MODE=1 แล้ว docker compose up -d
(ห้ามเปิดอ่านโค้ดใน petshop เพื่อหาว่าบั๊กอยู่ไหน)
ในโฟลเดอร์ e2e รัน npx playwright test แล้วเปิด e2e/index.html
1. test ไหนล้ม ผิดตรงไหน (ดูภาพวงแดงและ GIF) เป็นบั๊กของเว็บหรือ test/แผนผิด
2. เขียนรายงานบั๊กลง BUG-HUNT.md: ขั้นตอนทำซ้ำ ผลที่คาดหวัง ผลจริง หลักฐาน ความรุนแรง
3. เทียบกับหัวข้อ 8 ของแผน: บั๊กที่เจอตรงกับที่เราทายไว้ไหม
```

💬 (ส่วนที่ 2 · บทเรียนเรื่อง oracle)
```text
ใน BUG-HUNT.md เพิ่มการวิเคราะห์นี้ (ยังเปิด BUG_MODE=1 อยู่)
1. ใช้ Playwright MCP เดินสำรวจเว็บตอนนี้ซ้ำแบบ LAB 3 เฉพาะเรื่องคูปอง รายการโปรด และฟอร์มที่อยู่
2. สมมติว่าเราสำรวจวันนี้แทนวันแรก แล้วลอกผลจากหน้าจอเป็นผลที่คาดหวังทั้งหมด (ที่มา [O]) ตารางนี้: test case | ผลที่คาดหวังในแผนเรา (ที่มา) | ค่าที่จะลอกจากหน้าจอวันนี้ | ยังจับบั๊กได้ไหม
3. สรุป: ข้อที่ที่มาเป็น [D] หรือ [R] ช่วยเราอย่างไร และแผนเราพลาดบั๊กตัวไหน เพราะอะไร ควรเพิ่ม test case อะไร
เสร็จแล้วเปิดเว็บกลับเป็นโหมดปกติ BUG_MODE=0
```

📄 ได้: `BUG-HUNT.md` · รายงาน `e2e/index.html` ที่ไม่ผ่านเกณฑ์

👀
- ผลเป็นไปได้หลายแบบ **ทุกแบบเป็นบทเรียน**: จับครบ 3 = แผนดี · จับได้ 1–2 = ดูว่าข้อที่พลาดขาดเทคนิคอะไร (มักขาด Boundary เบอร์ 9 หลัก หรือขาด State ตัวเลขหัวใจ)
- ข้อความหลัก: **ผลที่คาดหวังที่ลอกจากหน้าจอ จะยืนยันบั๊กแทนที่จะจับบั๊ก** ต้องมีแหล่งอิสระ ([D]/[R]) อย่างน้อย 1 แหล่ง
- หลังเฉลย ผู้สอนเปิดตารางบั๊กจริง (ด้านล่าง) และให้ผู้เรียนเพิ่ม test ที่ขาดลงแผน

**เฉลยสำหรับผู้สอน (ไม่ใส่ใน README ช่วงก่อน LAB 8)**

| บั๊ก (BUG_MODE=1) | test ที่ควรจับได้ | oracle ที่ช่วยจับ | ถ้าลอกจากหน้าจอจะเห็น |
|---|---|---|---|
| PAW10 ลดแค่ 1% | คูปอง PAW10 พร้อมยอดเป็นตัวเลข | [D] "PAW10 ลด 10%" + [R] คำนวณ ฿799×10% | "ส่วนลด ฿7" → อบบั๊กลงแผน |
| ลบรายการโปรดแล้วตัวเลขหัวเว็บไม่ลด (จนรีโหลด) | ลบรายการโปรดแล้วเช็กตัวเลข **ทันที** ไม่รีโหลด | [R] ตัวเลขต้องเท่ากับจำนวนในรายการ | "ตัวเลขยังเป็น 2" → ดูแปลกแต่บางคนอาจจดตาม |
| เบอร์โทร 9 หลักผ่านการตรวจ | Boundary เบอร์ 9 / 10 / 11 หลัก ในหน้าชำระเงิน | [R] เบอร์มือถือไทย 10 หลัก | "9 หลักสั่งซื้อได้" → อบบั๊ก + ไม่รู้ข้อความ error |

ประเด็นเสริมให้ชวนคุย: บั๊กเบอร์ 9 หลักทำให้ **ไม่เห็นข้อความ error** เลย ถ้าสำรวจวันนั้น ผู้เรียนจะไม่มีทางรู้ข้อความ error ที่ถูก → ต้องเขียนผลที่คาดหวังว่า "มีข้อความ error ที่ช่องเบอร์โทร และสั่งซื้อไม่ได้" แล้วติดคำถามถึงทีม

## 5. รูบริก: เช็กลิสต์ "แผนการทดสอบที่ดี" (ผู้เรียนให้คะแนนตัวเอง)

ให้ 1 คะแนนต่อข้อที่ทำได้ · **ดีมาก ≥ 18/20 · ใช้ได้ 14–17 · ต้องแก้ < 14**

**A. ฐานจากการสำรวจ**
- ☐ 1. EXPLORATION.md มีแผนผังเว็บครบทุกหน้า (รวมหน้า 404 และหน้าที่ต้อง login)
- ☐ 2. กฎทุกข้อติดป้ายที่มา [D]/[R]/[O]
- ☐ 3. มีคำถามถึงทีม อย่างน้อย 3 ข้อ (สิ่งที่ TEST-DATA ไม่ได้บอก)
- ☐ 4. ไม่ได้อ่านโค้ดใน petshop/ เพื่อหากฎ

**B. กรอบของแผน (หัวข้อ 1–4)**
- ☐ 5. เป้าหมายข้อเดียวชัดเจน และบอกแหล่งของผลที่คาดหวัง
- ☐ 6. ทุกฟีเจอร์ในแผนผังเว็บอยู่ฝั่ง "ทดสอบ" หรือ "ไม่ทดสอบ (มีเหตุผล)"
- ☐ 7. ขอบเขตระบุเบราว์เซอร์ จอมือถือ และ API
- ☐ 8. นิยาม P1/P2/P3 ใช้ผลกระทบเมื่อพัง ไม่ใช่ความยากของ test

**C. Test cases (หัวข้อ 5)**
- ☐ 9. ทุกฟีเจอร์ในขอบเขตมี test อย่างน้อย 1 ข้อ
- ☐ 10. ใช้ครบ 6 เทคนิค และฟีเจอร์ P1 มีทั้ง Happy + Negative/Boundary
- ☐ 11. ผลที่คาดหวังทุกข้อเป็นตัวเลขหรือข้อความที่ตรวจได้ (ไม่มี "แสดงถูกต้อง")
- ☐ 12. ตัวเลขเงินมีวิธีคำนวณจาก TEST-DATA กำกับ ไม่ได้ลอกจากหน้าจอ
- ☐ 13. ค่าขอบใช้คู่ "ต่ำกว่า/ที่ขอบ" เช่น ฿998/฿999, เบอร์ 9/10 หลัก, สต็อก 3/4
- ☐ 14. ใช้ข้อมูลใน TEST-DATA ครบทุกแถว (บัญชี คูปอง 4 ตัว ค่าส่ง สินค้าหมด/ใกล้หมด)
- ☐ 15. ID เป็นระบบ ไม่ซ้ำ และไม่มี test ซ้ำกัน

**D. เกณฑ์และคุณภาพ (หัวข้อ 6–8)**
- ☐ 16. Entry/Exit criteria วัดได้ (healthy + health ok · P1 ผ่าน 100% · อัตราผ่าน X%)
- ☐ 17. หัวข้อ 8 ทาย "ถ้าพังแบบนี้ → test ไหนล้ม" อย่างน้อย 5 แบบ
- ☐ 18. ข้อ [O] ล้วนมีไม่เกิน ~20% และทุกข้ออยู่ในคำถามถึงทีม

**E. พิสูจน์แผน**
- ☐ 19. ทุกข้อแปลงเป็น Playwright ได้ และเว็บปกติผ่านเกณฑ์ตามแผน
- ☐ 20. ในโหมดบั๊ก แผนจับบั๊กได้ ≥ 2 จาก 3 ตัว และ BUG-HUNT.md อธิบายตัวที่พลาดได้ว่าขาดเทคนิค/oracle อะไร
