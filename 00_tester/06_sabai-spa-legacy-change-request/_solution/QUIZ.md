## 2. คำอธิบายรายข้อ + คำตอบผิดที่พบบ่อย

### ข้อ 1 · วงจร CR + คำอ้าง ≠ หลักฐาน (🎓 1 · LAB 1 · LAB 6–12)

- **ประเด็นที่ต้องมี:** (1) รันชุดที่ส่งมอบเองก่อนเชื่อ · จำแนกข้อแดงโดยไม่แก้เทสต์ · commit baseline ให้มีจุดถอย (2) ลำดับสถานะตาม `CHANGE-REQUESTS/REGISTER.md` 7 ขั้น · "ทดสอบผ่าน" = ทีมพิสูจน์แล้ว · "รอตรวจรับ" = รอเจ้าของงานลองตาม UAT · "ปิดงาน" = ลงชื่อรับ
- **ตัวอย่างจริง:** e2e-legacy "41 passed · 1 failed" = ผ่านจริง 38 + expected-fail 3 + ล้ม 1 (TC-SEC-05) → คำอ้าง "ผ่านหมดยกเว้น 3" = ❌ · คำอ้าง "ปิด reset ใน production" ก็ ❌ (ค่าเริ่ม `ALLOW_TEST_RESET=1` · reset ตอบ 200) · หลัง LAB 10 ทั้ง 5 CR อยู่ที่ "ทดสอบผ่าน (รอ UAT)" ยังไม่ปิด
- **ผิดบ่อย:** คัดคำอ้างลงรายงานเป็นผล · ข้ามสถานะ "อนุมัติแผน" (ลงมือก่อนผู้อนุมัติเห็น impact) · ถือว่าเทสต์เขียว = ปิดงาน

### ข้อ 2 · 3 ตา + ตาที่ 4 คือ DB (🎓 2 · LAB 2–3)

- REA (grey-box) เห็นหน้า · endpoint ที่ client เรียก · สัญญา API จาก HAR · **ไม่เห็นกฎฝั่งเซิร์ฟเวอร์และไม่อ่าน Postgres** · อ่าน repo (white-box) เห็นทุกอย่างที่เขียน · DB schema = กฎที่ฐานบังคับเองแม้โค้ดลืม (รอบจริง CHECK 51 · FK 25 · EXCLUDE 2)
- ตัวอย่าง `GROUP_MAX`: โค้ดยอม 8 แต่ CHECK `party_size <= 6` ปฏิเสธตอน INSERT · REA/HAR ไม่มีทางรู้จนกว่าจะลองจองกลุ่ม 7–8 คนจริง
- **ตรงกัน = มั่นใจ · ไม่ตรง = คำถาม:** รอบจริง triangulation 23 แถว ✅ 17 ⚠️ 6 (เช่น BR-17 ระยะรถ: โค้ดปัดทศนิยม · runtime 15.04 กม. รับ · DB CHECK ≤ 15.0 · SPEC "> 15 ไม่รับ" → SPEC-GAPS G4)
- **ผิดบ่อย:** "อ่านโค้ดครบแล้วไม่ต้องดู DB" · "REA เห็นทุก endpoint" · นับ constraint จาก `\d` 2 ตาราง (ได้ CHECK 23 แทน 51)

### ข้อ 3 · หาไม่เจอ ≠ ไม่มี (ขอบเขต browser-only ของ REA) (🎓 2 · LAB 2 · LAB 11)

- ของจริงในบท: `/api/me` `/api/me/bookings` `/api/services` ไม่อยู่ใน HAR เลย ทั้งที่ `/account` แสดง 8 นัด · LAB 3 ยืนยัน: หน้าเป็น Server Component เรียก lib ตรง · handler ที่ไม่มีผู้เรียกในเว็บ 8 ตัว
- อีกแบบของ "หาไม่เจอ": static ของ REA ไม่เห็น `/api/slots` `/cancel` เพราะ URL เป็น template literal (`BookingWizard.tsx:144`) แต่ HAR เห็น · coverage `partial` → ห้ามสรุปว่าไม่มี
- คำตอบที่ถูก: ป้าย inference/unknown + เหตุผลที่เป็นไปได้ + ตาที่สอง (อ่าน repo · grep ผู้เรียก) + คำถามถึงร้าน (มีระบบภายนอกใช้ route นี้ไหม — SYSTEM-MAP U3)
- **ผิดบ่อย:** "route นี้ไม่ได้ใช้ ลบได้" · "REA ไม่เห็น CR-02 ใน bundle = CR-02 ไม่ได้เปลี่ยนอะไร" (LAB 11)

### ข้อ 4 · characterization ≠ ความถูกต้อง (🎓 3 · LAB 5)

- characterization ตอบ "ระบบทำอะไรอยู่" (ป้าย [E]) ไม่ใช่ "ควรทำอะไร" ([D] / [D:CR-0N]) · [E] ขัด [D] = ผู้ต้องสงสัยบั๊ก ไม่ใช่ค่าคาดหวัง
- รอบจริง: KI-01 บัตรปลอม (API 422 แต่หน้าจอไม่เตือน) และ KI-02 เบอร์ `abc` (201) เขียนคู่ ① ล็อก ② `test.fail` · KI-03 owner ยกเลิกแทน (โค้ดตั้งใจให้ทำได้ · SPEC เงียบ) ล็อกอย่างเดียว + "ต้องถามร้าน"
- เมื่อมี CR แก้แล้ว ② จะผ่าน (Playwright รายงาน "ผ่านโดยไม่คาด") → ถอด `test.fail` และปรับ ①
- **ผิดบ่อย:** ล็อก 201 เป็นค่าคาดหวังเดี่ยว ๆ แล้วเรียกว่า "เทสต์ผ่าน" · แอบแก้บั๊กระหว่างสร้างตาข่าย · ใส่ `test.fail` ทุกเรื่องแปลกโดยไม่ถามร้าน

### ข้อ 5 · test seam (🎓 3 · LAB 5 · ใช้ใน LAB 6 9 10)

- seam = จุดที่เปลี่ยนสภาพแวดล้อมเพื่อทดสอบได้ **โดยไม่แก้กฎ** · `POST /api/test/clock` แตะแค่ `app_setting.test_today` · reset = ล้างทุกตาราง + seed ใหม่ (นัดที่เพิ่งจองหาย)
- รอบจริง: จอง B14 → clock 2026-10-12T09:00 → "วันนี้" เปลี่ยน · คิว 12 ต.ค. ยังมี B01 B14 · `ALLOW_TEST_RESET=0` → 404 · ค่าไม่ถูก → 422 · ใช้ต่อ: CR-02 C15–C17 (ข้ามวันมีผล) · CR-05 R10 (ตั้ง 12 ต.ค. 14:00 ให้ถึงเวลานัดก่อน owner กดเสร็จ B01)
- **ผิดบ่อย:** แก้ `clock()` หรือกฎให้คืนวันที่ที่ต้องการ (แก้ของจริงเพื่อเทสต์) · seam ที่ปิดไม่ได้ใน production · ใช้ `new Date()` ในโค้ดใหม่ (seam คุมไม่ได้)

### ข้อ 6 · mutation (🎓 3 · LAB 5)

- แกล้งทำโค้ดผิด 1 จุด → รันตาข่าย → แดง = "ฆ่า" mutant · รอด = รู · ต้องคืนไฟล์ทุกครั้ง (`git checkout -- <ไฟล์>` · `git diff -- web/lib/rules/` = 0)
- รอบจริง: X1 `tier.ts` `>=`→`>` (golden 2/62 · check-rules 88/90) · X2 ที่นั่ง 4→5 (golden 3/62 · 88/90) · X3 กลุ่ม 10→15 (golden 10/62 · 83/90) · **e2e-cr จับ 0/3** เพราะ char-booking ล็อกแค่ลูกค้าไม่ล็อกอินจองเดี่ยว ไม่มีส่วนลด/รถ
- X1 รอดได้ง่าย: golden จับเพราะ seed **บังเอิญ** มี U07 ยอดสะสม ฿10,000 พอดี · ถ้าเลือกเคสราคาแค่ผู้ไม่ล็อกอิน X1 จะรอด
- **ผิดบ่อย:** "ไม่มีตัวรอด = ตาข่ายสมบูรณ์" · "e2e ผ่าน = กฎปลอดภัย" · ลืมคืนไฟล์ mutant แล้ว commit

### ข้อ 7 · regression ที่ตั้งใจ vs ไม่ตั้งใจ (🎓 4 · LAB 6 7 · LAB 11)

- **ตั้งใจ** = CR สั่งให้ค่าเดิมเปลี่ยน → ต้องมีแถวใน `docs/ORACLE-CHANGES.md` (ค่าเดิม → ใหม่ · CR ไหน · ผู้อนุมัติ) ก่อนแก้ค่าคาดหวัง · **ไม่ตั้งใจ** = ค่าเปลี่ยนโดยไม่มีใครขอ → แก้โค้ด ห้ามแก้เทสต์
- TC-BOOK-07 (รอบจริง): U02 จองคู่ทับ B02 **ของตัวเอง** → เข้าทั้ง "ห้องเต็ม" และ "นัดซ้ำคนเดิม" · CR-03 ไม่ได้กำหนดลำดับ → แก้ลำดับในโค้ด (ตรวจนักบำบัด/ห้องก่อน แล้วจึงตรวจนัดซ้ำ) + เพิ่ม C17/C18 → baseline 38/1/3 · ORACLE-CHANGES ยังว่าง
- ด้านกลับ (CR-02): ถ้าเปลี่ยนค่าคงที่ส่วนลดตรง ๆ โดยไม่มีวันมีผล check-rules E26/E28/E79 + golden จะแดง = regression ไม่ตั้งใจ (CR สั่งเฉพาะการจองตั้งแต่ 1 พ.ย.) → ตาข่ายเดิมทำหน้าที่ "กันเปลี่ยนเกินขอบเขต"
- จำแนกเทสต์เดิมที่แดงได้ 3 แบบ: เว็บผิด · เทสต์ล้าสมัย (ต้องมี CR) · เทสต์ใหม่เขียนผิด
- **ผิดบ่อย:** แก้ข้อความคาดหวังของ TC-BOOK-07 "เพราะ CR-03 เปลี่ยนข้อความ" · `golden --update` หลังแก้โค้ด

### ข้อ 8 · migration บนฐานที่มีข้อมูล + ถอยกลับ (🎓 5 · LAB 8 · LAB 12)

- `db/compose.yaml` mount `./init` เป็น `/docker-entrypoint-initdb.d` → รันเฉพาะ volume ว่าง · ระบบจริงมีข้อมูลแล้ว → ต้องเป็นไฟล์ migration แยก รันซ้ำได้ (idempotent) มี `.down.sql` · ยังต้องแก้ `db/init` สำหรับเครื่องติดตั้งใหม่ และรายการตารางที่ reset ล้าง
- รอบจริง: ครั้งที่ 1 `CREATE TABLE` · `INSERT 0 3` · ครั้งที่ 2 NOTICE `already exists, skipping` · `INSERT 0 0` · exit 0 ทั้งคู่ · นัดใหม่ B14 อยู่ · `th_ok = t` · สำรอง 52,535 ไบต์ · tag image `before-cr04` ก่อน rebuild
- ลำดับ: **ขึ้น** สำรอง → migrate → rebuild (เว็บใหม่ขึ้นก่อน migrate = slots/price/bookings/reset 500) · **ถอย** เว็บเดิมก่อน → `down.sql` (เว็บใหม่อ่านตารางนี้อยู่) · `down.sql` ทำวันหยุดที่ร้านเพิ่มเองหาย → เขียนในแผน
- **ผิดบ่อย:** แก้ `db/init` แล้ว `docker compose down -v` เพื่อให้ init รัน (ข้อมูลลูกค้าหาย) · เห็น NOTICE สีแดงใน PowerShell แล้วคิดว่าพัง · ส่ง SQL ภาษาไทยผ่าน pipe PowerShell (กลายเป็น `?`)

### ข้อ 9 · traceability + audit trail (🎓 6 · LAB 6–12)

- ห่วงโซ่: **CR** (หนังสือ) → **BR** (กฎที่เปลี่ยน/เพิ่ม ใน SPEC) → **TC** (เทสต์ที่พิสูจน์) → **ผล** (แดงก่อน · เขียวหลัง · regression) · หลักฐานที่ตรวจย้อนได้: commit แดง → commit แก้ · log ผลรันพร้อมเวลา · `docs/TRACEABILITY.md` · `CHANGE-REPORT.md` · `REGISTER.md` · (LAB 11–12) REGRESSION-REPORT · UAT-CHECKLIST
- ตัวอย่างจริง CR-03: ทำซ้ำเรื่องร้องเรียน 201 B14 B15 B16 ([E] ขัด [D:CR-03]) → BR-21 → C1–C18 + UI-1 → `eb0bf69` แดง 5/16 → `fe187aa` เขียว 18/18 · check-rules 90/90 · golden 62/62 · e2e-legacy 38/1/3 = baseline
- REA ช่วยตรงไหน: เทียบ bundle v1 ↔ v2 ว่าเปลี่ยนตรงหน้าที่ CR แตะ · กฎฝั่งเซิร์ฟเวอร์ (CR-02 CR-03) มองไม่เห็น → ชี้เทสต์ที่พิสูจน์แทน
- **ผิดบ่อย:** ส่ง "แก้แล้ว เทสต์ผ่าน" โดยไม่มีเลข commit/ผลรัน · ไฟล์ที่เปลี่ยนบางไฟล์โยง CR ไม่ได้ · ใช้ "REA ไม่เห็นความต่าง" เป็นหลักฐานว่าไม่มีผลข้างเคียง

### ข้อ 10 · oracle อิสระ (🎓 4 · LAB 10)

- oracle = แหล่งของค่าคาดหวัง · ถ้าเอาจากหน้าที่เพิ่งสร้าง เทสต์จะเขียวเสมอแม้คิดผิด (วนตัวเอง) · CR-05 ใช้ SQL บน seed ที่รัน **ก่อน** เขียนโค้ด (อยู่ใน commit แดง `15fb782`)
- รอบจริง: ก.ย. ยืนยัน/เสร็จ/ยกเลิก 0/3/1 · ยอดขาย 1,900 · ส่วนลดระดับ 100 · แต้ม 19 (ไขว้ `point_txn` 19) · ครั้งคอร์ส 2 · หลังทำ ตรวจไขว้รายงาน = Σ ตารางคิวหลังร้าน 3/3
- ข้อจำกัดที่ควรพูดถึง: seed ไม่มีนัดที่วัน UTC ≠ วันไทย (`q_tz` = 0) → เทสต์บน seed พิสูจน์เรื่องโซนเวลาได้จำกัด
- **ผิดบ่อย:** เปิดหน้ารายงานแล้วคัดตัวเลขลงเทสต์ · ใช้ SQL ที่ตัดวันด้วย UTC (oracle ผิดแบบเดียวกับโค้ด = ไม่อิสระจริง)
