# PawPantry ระบบเดิม: รับช่วง repo ที่ทีมเก่าทิ้งไว้ ด้วย REA + Playwright (Copy & Paste)

บทนี้เริ่มจาก **ระบบที่มีอยู่แล้ว** คือร้าน PawPantry ที่ทีมพัฒนาเดิมลาออกไปหมด เหลือไว้แค่ repo · ชุดเทสต์เก่า · เอกสารส่งมอบ 1 หน้า · ข้อมูลทดสอบของร้าน
Claude Code ช่วยเรา **อ่านและอธิบาย repo · ส่องของที่ build และรันอยู่ด้วย REA · ล็อกพฤติกรรมเดิม · แก้บั๊กที่ลูกค้าแจ้ง · เพิ่มฟีเจอร์ตามที่ร้านขอ** แล้วพิสูจน์ว่าแก้แค่ที่ตั้งใจ
หน้าที่ของเราคือ **คัดลอกพรอมต์ → วางใน Claude Code → อ่านผล → ตัดสินใจ** ไม่ต้องเขียนโค้ดเอง

![ร้าน PawPantry ทีมพัฒนาเดิม 4 คนใส่เสื้อเขียนว่า Build Improve Pass It On แบกกล่องเดินออกประตูพร้อมโบกมือลา บนเคาน์เตอร์มีแล็ปท็อปเปิดเว็บ PawPantry แมวส้มเกาะจอ และกล่องเครื่องมือเก่าขึ้นสนิมมีหยากไย่ เด็กถือแฟ้มบาง ๆ HANDOVER ทำหน้าตกใจ หุ่นยนต์ยืนข้าง ลูกหมาเกาะเคาน์เตอร์ หัวเรื่อง รับช่วงระบบเดิม เด็กพูดว่า เอกสารแค่นี้เหรอ?](img/intro-01-legacy-handover.jpg)

### 1) Reverse engineering คืออะไร (Chikofsky & Cross 1990)

![หัวเรื่อง ย้อนรอยระบบ = จากของจริง กลับไปหาแบบ ป้ายใหญ่แบ่งสองฝั่ง ฝั่งซ้ายลูกศรชี้ขวา Forward engineering กระดาษ แบบ กลายเป็นร้าน PawPantry ฝั่งขวาลูกศรชี้ซ้าย Reverse engineering เด็กกับหุ่นยนต์ส่องแว่นขยายที่ร้าน PawPantry แล้ววาด แบบ ย้อนกลับ มีการ์ดลอยออกมา หน้าเว็บ API โมดูล กฎธุรกิจ ป้ายไม้ด้านล่าง นวัตกรรมเริ่มจากการสังเกตของจริง และ มองให้ลึก คิดให้ไกล เข้าใจระบบได้มากขึ้น เด็ก หุ่นยนต์ แมวส้ม ลูกหมาชูมือดีใจ](img/concept-01-reverse-engineering.jpg)

Chikofsky & Cross แบ่งระบบเป็นชั้น: ความต้องการ → การออกแบบ → โค้ด แล้วตั้งชื่อ "การเดินทางระหว่างชั้น" ไว้ 6 แบบ

| คำ | ทิศ | เปลี่ยนระบบไหม | ตัวอย่าง PawPantry | ใช้ใน |
|---|---|---|---|---|
| **Forward engineering** | บน → ล่าง | ✅ สร้างใหม่ | บท 04: สัมภาษณ์ → Claude สร้างเว็บ | บท 04 |
| **Reverse engineering** | ล่าง → บน | ❌ ดูอย่างเดียว | อ่าน bundle `.next/static` แล้วรู้ว่ามี endpoint `/api/products` | LAB 1–3 |
| **Redocumentation** | ชั้นเดียวกัน | ❌ | เขียนตาราง "หน้าไหนเรียก API ไหน" จากโค้ดจริง | LAB 1 (`CODEBASE-MAP.md`) |
| **Design recovery** | ล่าง → บน (ลึกกว่า) | ❌ | "ตะกร้าเก็บในเบราว์เซอร์ ส่วนคูปองตรวจที่ server" (ต้องรู้โดเมนร้านด้วย) | LAB 1–2 |
| **Restructuring** | ชั้นเดียวกัน | ✅ ข้างใน · พฤติกรรมภายนอกเหมือนเดิม | แยก `lib/pricing.ts` เป็นหลายไฟล์ โดยยอดเงินทุกหน้าเท่าเดิม | LAB 9 (คอลัมน์ "ชนิดงาน") |
| **Re-engineering** | ขึ้น แล้วลง | ✅ | เข้าใจระบบก่อน แล้วแก้บั๊ก/เพิ่มฟีเจอร์ | LAB 5–10 |

![หัวเรื่อง ย้อนรอยระบบ: ระดับของความเข้าใจ ตามนิยามของ Chikofsky & Cross (1990) ตัวอย่างแต่ละขั้นจากร้าน PawPantry บันได 5 ขั้นจากล่างขึ้นบน 1 ไบต์ / ไฟล์ที่ส่งมอบ bundle .js ที่ build แล้ว (ย่อชื่อตัวแปร) .next/static/chunks/*.js · 2 โค้ด / ฟังก์ชัน คำนวณยังไงทีละขั้น lib/pricing.ts evaluateCoupon() · 3 โมดูล + API ส่วนไหนคุยกับส่วนไหน POST /api/coupons/validate · 4 ฟีเจอร์ / เส้นทางผู้ใช้ ผู้ใช้กดอะไร เห็นอะไร ใช้คูปองตอนจ่ายเงิน /checkout · 5 กฎธุรกิจ / ความต้องการ ระบบต้องทำอะไร เพราะอะไร PAW10 ลด 10% · บนสุดเขียน นามธรรมมากขึ้น (ทำไม) ล่างสุดเขียน รูปธรรมมากขึ้น (ของจริงที่รันอยู่) · ลูกศรฟ้าซ้ายชี้ขึ้น Reverse engineering (design recovery) ย้อนขึ้นไปหาแบบ · ลูกศรส้มขวาชี้ลง Forward engineering สร้างลงมา กฎ → โค้ด → bundle · กล่องล่าง Redocumentation = เขียนเอกสารใหม่จากของจริง (ไม่เปลี่ยนระบบ) และ Re-engineering = ย้อนรอย + แก้ + สร้างใหม่ (ขึ้นไปก่อน แล้วค่อยลงมา) · แถบล่าง งานแก้ระบบเดิม = ย้อนขึ้นไปให้ถึงกฎ ก่อนลงมือแก้](img/re-taxonomy.png)

| ขั้นบันได | ตอบคำถาม | ใครพาขึ้นถึง |
|---|---|---|
| 1 ไบต์ → 2 โค้ด | ไฟล์นี้คือไฟล์ไหนแน่ · มีคำสั่งอะไรในนั้น | hash + static analysis (เครื่องมือ) |
| 3 โมดูล → 4 ฟีเจอร์ | ส่วนไหนเรียกส่วนไหน · ผู้ใช้กดแล้วไปแตะ API ไหน | REA graph + trace + ดูตอนรัน |
| 5 กฎธุรกิจ | ระบบ **ควร** ทำอะไร เพราะอะไร | **ร้าน [D] เท่านั้น** เครื่องมือขึ้นมาไม่ถึงเอง |

Michael Feathers นิยามว่า **legacy code = code without tests** · ปัญหาไม่ใช่ "โค้ดเก่า" แต่คือ "แก้แล้วไม่รู้ว่าพังไหม" · RE คือก้าวแรกที่บอกว่าต้องล็อกอะไรไว้ก่อนแก้

> **RE = ดู ไม่ใช่แก้** · การแก้คือ re-engineering ซึ่งต้องมี RE ก่อนเสมอ · ยิ่งขึ้นบันไดสูง ยิ่งต้องอนุมานมาก ความมั่นใจยิ่งลด · ขั้นบนสุดต้องถามร้าน อย่าให้ AI เดาว่า "กฎน่าจะเป็นแบบนี้"

| ช่องทาง | 📗 พิสูจน์ได้ | 📕 พิสูจน์ไม่ได้ | 🧰 ในบทนี้ |
|---|---|---|---|
| **อ่าน source** | เจตนาของคนเขียน (ชื่อ คอมเมนต์ ค่าคงที่) | ว่า source นี้คือของที่ deploy อยู่ · ว่าคอมเมนต์ยังจริง | Claude อ่าน repo (LAB 1) |
| **Static analysis** ของที่ build แล้ว (ไม่รัน) | มีข้อความ/คำสั่งนี้อยู่ใน bytes จริง | ว่าโค้ดนั้นถูกเรียกตอนรัน · ค่าที่ประกอบตอนรัน | `analyze-javascript-application` (LAB 2) |
| **Runtime observation** (dynamic) | สิ่งนี้ **เกิดขึ้นจริง** ในรอบที่ดู | ว่าจะเกิดทุกครั้ง · ทางที่ไม่ได้กด | `capture-browser-scenario` (LAB 3) |
| **Network capture (HAR)** | ข้อมูลที่วิ่งผ่านสายจริง ณ ตอนนั้น | ตรรกะข้างใน server · มาจากโค้ดบรรทัดไหน | `record-har.mjs` + `inspect-web-network-capture` (LAB 3) |

**กฎทอง (Dijkstra):** การทดสอบและการสังเกต **แสดงว่ามี** ได้ แต่ **พิสูจน์ว่าไม่มี** ไม่ได้ · และจากทฤษฎีการคำนวณ (Rice's theorem) static analysis ตัดสินพฤติกรรมทุกแบบของโปรแกรมได้ไม่ครบ → REA จึงรายงาน coverage `partial` เป็นเรื่องปกติ ไม่ใช่ความล้มเหลว

> **static เจอ ≠ เกิดขึ้นจริง** · REA เจอ `fetch("/api/orders")` ใน bundle แปลว่า "มีโค้ดนี้อยู่" ไม่ได้แปลว่า "มีคนกดสั่งซื้อแล้ว" · และตรรกะฝั่ง server (API route) **ไม่อยู่ใน bundle ของเบราว์เซอร์** bundle เหมือนเดิมจึงไม่ได้แปลว่าพฤติกรรมเหมือนเดิม

### 3) 3 ตา: black / white / grey-box

![หัวเรื่อง 3 วิธีรู้จักระบบเดิม กล่อง 3 ใบบนโต๊ะ กล่องดำ เด็กกดปุ่มด้านนอกแล้วดูไฟแดง เหลือง เขียว ป้าย Black-box: เห็นแค่ข้างนอก กล่องแก้วใสเห็นเฟืองข้างใน หุ่นยนต์ใส่แว่นอ่านม้วนโค้ด ป้าย White-box: อ่านโค้ดข้างใน กล่องเทามีหน้าต่าง เด็กกดปุ่มขณะหุ่นยนต์ส่องแว่นขยาย REA เข้าไป ป้าย Grey-box: ส่องของที่ส่งมอบ ป้ายไม้มุมขวา เรียนรู้ ไปด้วยกัน แมวส้มและลูกหมานั่งข้างโต๊ะ](img/concept-03-black-white-grey-box.jpg)

![หัวเรื่อง 3 ตา มองระบบเดิม ระบบ legacy ไม่มีใครเล่าให้ฟังครบ · มองจาก 3 มุม แล้วเอาคำตอบมาเทียบกัน ตาราง 3 คอลัมน์ 1 Black-box เดินเว็บ + Playwright + HAR · 2 Grey-box REA ส่อง bundle / HAR / เบราว์เซอร์ · 3 White-box อ่าน source + CLAUDE.md · แถว ต้องมี source ไหม ไม่ต้อง ใช้แค่เว็บที่รันอยู่ / ไม่ต้อง ใช้ไฟล์ที่ build / ที่รันอยู่ / ต้องมี repo ครบ · แถว เห็นอะไร หน้าจอ ข้อความ ยอดเงิน คำขอ / คำตอบ API ใน HAR / endpoint โมดูล storage ที่ซ่อนใน bundle เส้นทางที่เว็บเรียกจริงตอนรัน / ตรรกะจริงทีละบรรทัด ชื่อฟังก์ชัน ค่าคงที่ คอมเมนต์ · แถว พิสูจน์อะไรไม่ได้ ทำไมถึงคำนวณแบบนั้น ทางที่เราไม่ได้เดิน / ชื่อถูกย่อ (minified) บางข้อเป็นแค่การอนุมาน ต้องยืนยันด้วยการรัน / โค้ดตรงกับกฎธุรกิจไหม เอกสาร / คอมเมนต์อาจเก่าแล้ว · แถว เครื่องมือ Playwright session.har เดินเว็บเอง + จดผล / analyze-javascript-application inspect-web-network-capture / CLAUDE.md grep ให้ Claude อ่าน repo + อธิบาย · แถว ใช้ตอนไหน มีแค่เว็บ ไม่มีโค้ด เก็บผลจริงไว้เทียบ ก่อน–หลังแก้ / ได้แค่ของที่ส่งมอบ เทียบ 2 เวอร์ชันที่ build แล้ว / มี repo ครบ ก่อนแก้ต้องรู้ว่ากระทบตรงไหน · แถบล่าง เอา 3 ตามาเทียบกัน (triangulate) · ตรงกัน = มั่นใจ · ไม่ตรง = เจอเรื่องต้องถาม](img/three-eyes.png)

| ตา | ข้อดี | ข้อเสีย | ในบทนี้ |
|---|---|---|---|
| ⬛ **Black-box** | มองแบบลูกค้า ไม่ลำเอียงตามโค้ด | ไม่รู้ว่ามีทางซ่อนอยู่ตรงไหน | LAB 5 ขั้นแรก: ทำซ้ำอาการจากหน้าเว็บก่อนเปิดโค้ด |
| 🔲 **Grey-box** | รู้โครงพอวางแผน แต่ยังทดสอบจากข้างนอก | ต้องแยก "เห็น" กับ "เดา" ให้ออก | LAB 2–3: REA ส่อง build และเว็บที่รัน |
| ⬜ **White-box** | ไล่ได้ทุกบรรทัด หาต้นเหตุได้ | เชื่อโค้ดจนลืมดูของจริง | LAB 1 อ่าน repo · LAB 5 ขั้นหลัง: หาต้นเหตุ |

**Triangulation** = ให้ 2 ตาขึ้นไปยืนยันเรื่องเดียวกัน เช่น 🔲 REA trace บอกว่า chunk หนึ่งเรียก `/api/orders` (static ไม่รู้ว่า method อะไร) · ⬜ ค้นใน repo เจอ `components/CheckoutForm.tsx` เรียก `fetch("/api/orders", …)` · ⬛ HAR ตอนกดสั่งซื้อเห็น `POST /api/orders` ได้ `201` · ตรงกันครบ → "หน้าชำระเงินส่งคำสั่งซื้อผ่าน API นี้" ยืนยันด้วย 3 ตา

> **อย่าใช้ตาเดียว** · ตาขาวอย่างเดียวเชื่อคอมเมนต์ที่อาจเก่า · ตาดำอย่างเดียวไม่รู้ว่าแก้ที่ไหน · ทุกแถวใน `CODEBASE-MAP.md` และ `SYSTEM-MAP.md` ต้องบอกว่า **ยืนยันด้วยกี่ตา ตาไหน**

### 4) ใช้ REA เมื่อไร เมื่อไรอ่าน repo เฉย ๆ

![หัวเรื่อง ใช้ REA เมื่อไร? ทางแยกสองสายในร้าน PawPantry ป้ายซ้าย อ่าน repo เลย ชี้ไปหนังสือเปิดที่เขียนว่า source ครบ ป้ายขวา ใช้ REA ส่อง ชี้ไปกล่องพัสดุปิดผนึกกับแล็ปท็อปมีหน้าที่กำลังวิ่ง เด็กเอามือแตะคางชี้ไปทางซ้าย หุ่นยนต์ถือแผนที่ แมวส้มและลูกหมานั่งข้าง ๆ](img/concept-04-rea-or-read.jpg)

![หัวเรื่อง ใช้ REA เมื่อไร? ผังตัดสินใจ 4 ขั้น · ถามทีละข้อจากบนลงล่าง ข้อแรกที่ตอบใช่คือเครื่องมือที่ควรเริ่ม · จุดเริ่ม อยากรู้ว่าระบบเดิมทำอะไร · ข้อ 1 มี source ครบ และเชื่อได้ว่าตรงกับที่ deploy? ใช่ → อ่าน repo เลย ข้าม REA (White-box) skill ของ REA เองบอกให้ข้ามเมื่อเป็นการอ่านสถาปัตยกรรมจาก source ปกติ Claude Code อ่าน repo CLAUDE.md grep LAB 1 · ไม่ → ข้อ 2 มีแค่ไฟล์ที่ build แล้ว? เช่น .next/static ที่ส่งมอบมา ใช่ → REA ส่อง build (static) Grey-box กู้ endpoint โมดูล storage แล้วตามรอยว่าใครเรียกฟีเจอร์นั้น analyze-javascript-application trace-application-feature LAB 2 · ไม่ → ข้อ 3 อยากเห็นตอนรันจริง? API ที่เรียกจริง ชื่อ key ใน localStorage ใช่ → HAR / scenario (runtime) Black + Grey-box HAR อ่านประวัติแบบ offline ไม่ยิงซ้ำ scenario REA ขับเบราว์เซอร์ มีผลข้างเคียง inspect-web-network-capture capture-browser-scenario LAB 3 · ไม่ → ข้อ 4 มี source แต่ไม่แน่ใจว่า build ตรงกับ source? ใช่ → เทียบ source กับ bundle Grey-box ไฟล์ไหนตรง ไฟล์ไหนหาคู่ไม่เจอ ใช้คู่กับ SHA-256 ของ source import-reference-source compare-source-to-bundle LAB 9 · ไม่ → ยังไม่แน่ใจ ใช้ 3 ตาเทียบกัน (triangulate) · แถบล่าง REA = ตาสำหรับของที่ส่งมอบ / รันอยู่ มี source ครบ → อ่าน repo ก่อน](img/when-rea.png)

skill ของ REA เขียนเองว่า **"Skip REA for ordinary source-repository architecture analysis."** · มี source ครบและเชื่อได้ → อ่าน repo ตรงกว่า ถูกกว่า · REA คือ **ตาสำหรับของที่ส่งมอบหรือรันอยู่**

| มีอะไรในมือ | มุม | ใช้อะไร | ได้อะไร |
|---|---|---|---|
| มีแค่ URL ของเว็บที่รันอยู่ | black-box | Playwright + HAR → `inspect-web-network-capture` · `capture-browser-scenario` | API ที่เรียกจริง · payload · หน้าจอ |
| มีแค่ไฟล์ build (`.next/`) | grey-box | `analyze-javascript-application` → `trace-application-feature` | แผนที่ module ↔ endpoint ↔ storage |
| มี source แต่ **ไม่แน่ใจว่าตรงกับที่ deploy** | grey + white | `import-reference-source` + `compare-source-to-bundle` | ไฟล์ไหนตรง ไฟล์ไหนต่าง |
| มี source ครบ เชื่อได้ | white-box | Claude อ่าน repo + ค้นโค้ด · **ไม่ต้องใช้ REA** | ไฟล์:บรรทัด ที่ต้องแก้ |

บทนี้มี source ครบ แต่ยังใช้ REA เพราะ: เอกสารส่งมอบอาจเก่า · ต้องรู้ว่า **build ที่รันอยู่** ตรงกับ repo ไหม · และตอนส่งมอบต้องมีหลักฐานว่า build ใหม่เปลี่ยนแค่ที่ตั้งใจ

> **REA ไม่ได้แทนการอ่านโค้ด** · ถ้าคำถามคือ "ฟังก์ชันนี้คิดเงินยังไง" ให้อ่าน repo · ถ้าคำถามคือ "ของที่ลูกค้าใช้อยู่ทำอะไรจริง" หรือ "build นี้ตรงกับ source ไหม" ค่อยใช้ REA

### 5) Evidence ไม่ใช่ความเห็น · authority 4 ถัง · หาไม่เจอ ≠ ไม่มี

![หัวเรื่อง หลักฐาน ไม่ใช่ความเห็น ฉากศาลในสวน หุ่นยนต์ถือแว่นขยาย REA ยื่นการ์ดหลักฐาน 4 ใบให้เด็ก แต่ละใบมีลายนิ้วมือ SHA-256 และแท็ก static runtime inference unknown ผีหุ่นยนต์สีเทาคิดว่า น่าจะ... มีกากบาทแดงทับ ป้ายบนโต๊ะ ไม่เจอ ≠ ไม่มี มีค้อนผู้พิพากษากับกองหนังสือ แมวส้มและลูกหมาดูอยู่](img/concept-05-evidence-not-opinion.jpg)

REA ไม่ตอบเป็นประโยคลอย ๆ แต่ตอบเป็น **Evidence record** ที่ตรวจย้อนได้

| ช่องใน Evidence | ถามว่า | ทำไมสำคัญ |
|---|---|---|
| `subject` + `digest` (SHA-256) | วิเคราะห์ bytes ชุดไหน | build ใหม่ = digest ใหม่ = ต้องเก็บหลักฐานใหม่ |
| `provider` · `authority` · `confidence` | เครื่องมือไหนตอบ · เห็นจริงหรืออนุมาน · มั่นใจแค่ไหน | แยก "เห็น" กับ "เดา" |
| `limitations` · `coverage` | มองไม่เห็นอะไร · ตรวจครบไหม (`complete` / `partial` / `unknown`) | บังคับให้พูดว่า "ไม่รู้" อย่างเป็นระบบ |
| `locations` · `evidence_id` | เจอที่ไฟล์/ตำแหน่งไหน · ID ของหลักฐาน | คนตรวจเปิดดูเองได้ · AI ต้องอ้าง ID ไม่ใช่อ้างความจำ |

![หัวเรื่อง Evidence ไม่ใช่ความเห็น · 4 ถังของหลักฐาน ตัวอย่างจากการรันจริงบน PawPantry · แถวช่องใน Evidence subject + digest, provider, authority (ไฮไลต์), confidence, limitations, coverage, locations, evidence_id · ถังฟ้า static เห็นใน bytes ของไฟล์ที่ build แล้ว ไม่ต้องรัน ตัวอย่าง /api/orders ถูกเรียกด้วย fetch ใน bundle มีโค้ดเรียก ≠ มีคนกดสั่งซื้อแล้ว → ใช้เป็น [E] ได้ว่ามีโค้ดนี้ · ถังเขียว runtime เห็นเกิดขึ้นตอนรันจริง เฉพาะรอบที่สังเกต จาก HAR และ scenario ตัวอย่าง key pp-cart pp-coupon pp-recent ใน localStorage static เห็นแค่ว่ามีการเขียน ไม่รู้ชื่อ key → ใช้เป็น [E] ได้ว่าระบบทำอยู่ · ถังเหลือง inference REA อนุมานจากหลักฐานอื่น ยังไม่ได้เห็นตรง ๆ ตัวอย่าง ป้าย electron-renderer บนหน้า HTML ของ Next.js ไม่ได้แปลว่าแอปนี้เป็น Electron → ติด [E?] แล้วยืนยันด้วยการรัน · ถังเทา unknown ตรวจไม่ครบ ชื่อถูกย่อ ค่าประกอบตอนรัน coverage partial เป็นเรื่องปกติ ตัวอย่าง endpoint a b c ชื่อถูก minify และไม่เจอ /api/recommendations เพราะ URL ประกอบตอนรัน → ห้ามเขียน TC ต้องไม่มี X · แถบล่าง หาไม่เจอ ≠ ไม่มี เห็นใน bytes ≠ เกิดขึ้นจริง อนุมาน ≠ เห็นเอง ไม่เจอ = ยังไม่พบ (coverage partial)](img/evidence-4-buckets.png)

REA ติด `authority` ละเอียดกว่านี้มาก (เช่น `ast-static-analysis` `controlled-replay` `static-relationship-inference`) และแยก `state` (`observed` / `inferred` / `unknown`) ออกจาก `confidence` · บทนี้ **รวบเป็น 4 ถัง** ให้อ่านง่าย:

| ถัง | authority จริงใน REA (ตัวอย่าง) | แปลว่า | ตัวอย่าง | ใช้เป็นผลที่คาดหวังได้ไหม |
|---|---|---|---|---|
| 🔵 **static** | `artifact-bytes` · `ast-static-analysis` | เห็นใน bytes จริง | endpoint `/api/products` (`call:fetch`) ใน chunk | ✅ ว่า "มีโค้ดนี้" · ❌ ว่า "ถูกเรียก" |
| 🟢 **runtime** | `controlled-replay` · `passive-cdp-runtime` | เห็นเกิดขึ้นตอนรันจริง (รอบที่ดู) | คำขอ `POST /api/coupons/validate` ใน HAR | ✅ เฉพาะรอบนั้น |
| 🟡 **inference** | `static-relationship-inference` · `cross-version-comparison` | อนุมานจากหลักฐาน (state `inferred`) | ป้าย `electron-renderer` (REA เดารูปแบบ ไม่ได้แปลว่าเว็บนี้เป็น Electron) | ❌ ใช้ชี้เป้าเท่านั้น |
| ⚪ **unknown** | `unknown` | ไม่รู้ + บอกเหตุผล | storage ที่ `name: null` · endpoint ชื่อ `a` `b` `c` | ❌ ต้องหาหลักฐานเพิ่ม |

**3 คำถามที่ต้องถามทุกหลักฐาน:** ① มาจาก bytes หรือการรันไหน (digest) ② เห็นจริงหรืออนุมาน (authority) ③ ตรวจครบไหม (coverage)

![หัวเรื่อง หาไม่เจอ ไม่ได้แปลว่าไม่มี โกดังมืดของร้าน เด็กส่องไฟฉาย ในวงไฟมีกล่อง /api/products และ /api/orders หุ่นยนต์ชูป้าย หาไม่เจอ ≠ ไม่มี ในเงามืดมีกล่องใหญ่ /api/recommendations และกล่องเล็ก a b c แมวส้มโผล่จากกล่องในเงา ลูกหมายืนข้างเด็ก ประตูหลังมีป้าย PET FOOD](img/concept-06-missing-not-absent.jpg)

| REA (static) เห็น | ความจริง | บทเรียน |
|---|---|---|
| endpoint ชื่อ `a` `b` `c` | เป็นชื่อตัวแปรที่ถูกย่อ (minify) ค่าจริงประกอบตอนรัน | "มีการ fetch" แต่ไม่รู้ URL · **อย่าใส่ในรายงานเป็น endpoint จริง** |
| **ไม่มี** `/api/recommendations` | หน้าแนะนำอาหารเรียกด้วย URL ที่ต่อ string ตอนรัน (template literal) | หาไม่เจอเพราะเป็นค่าที่ประกอบตอนรัน **ไม่ใช่เพราะไม่มี** |
| storage `local-storage` แต่ `name: null` | ชื่อ key ส่งผ่านตัวแปร | รู้ว่า "มีการเขียน localStorage" แต่ไม่รู้ key → ต้องดูตอนรัน (LAB 3) |

> **หาไม่เจอ ≠ ไม่มี** · REA เขียนเองว่า *"unavailable facts remain explicit and must not be read as absence"* · เมื่อ coverage เป็น `partial` ห้ามสรุปว่า "ระบบไม่มี X" และห้ามเขียน test แบบ "ต้องไม่มี X" จากหลักฐานนั้น · เขียนว่า **"ยังไม่พบ (coverage partial)"** แทน

### 6) ลายนิ้วมือของไฟล์ (content digest · SHA-256)

![หัวเรื่อง ลายนิ้วมือของไฟล์ กล่องพัสดุ 2 กล่องหน้าตาเหมือนกันวางบนเครื่องสแกน ป้ายชื่อ page.js เหมือนกันทั้งคู่ แต่สติกเกอร์ลายนิ้วมือต่างกัน กล่องหนึ่งสีฟ้า อีกกล่องสีส้ม หุ่นยนต์ส่องแว่นขยายแล้วชูป้าย คนละกล่อง! เด็กเขียน SHA-256 บนคลิปบอร์ด แมวส้มและลูกหมาเกาะเคาน์เตอร์](img/concept-07-content-digest.jpg)

SHA-256 = ลายนิ้วมือของไฟล์ · bytes ต่างแม้ 1 bit → hash ต่างโดยสิ้นเชิง (ดูจาก hash ไม่ออกว่าต่างกันมากหรือน้อย) · REA ผูกทุกผลกับ hash ของสิ่งที่วิเคราะห์

| hash บอกอะไร | hash ไม่ได้บอกอะไร | ใช้ในบทนี้ |
|---|---|---|
| hash เท่ากัน = **bytes เดียวกัน** ทุกตัว | ไม่ได้บอกว่า **ถูกต้อง** (ไฟล์ที่มีบั๊กก็มี hash) | LAB 2 จด digest ของ build เดิม (v1) |
| hash ต่าง = เนื้อหาเปลี่ยน → ต้องเทสต์ส่วนที่เกี่ยวซ้ำ | ไม่ได้บอกว่าเปลี่ยน **ตรงไหน** หรือ **ทำไม** | LAB 9 เทียบ hash ของ source เดิม ↔ ปัจจุบัน |
| `next build` ใหม่ = digest ใหม่ | ชื่อไฟล์/path เดียวกัน **ไม่ได้แปลว่า** เนื้อหาเดียวกัน | หลักฐานเก่าใช้กับ build ใหม่ไม่ได้ ต้องเก็บใหม่ |

> **path เดียวกัน ≠ ไฟล์เดียวกัน** · REA ยึด digest ก่อนชื่อเสมอ (*"A path never overrides a digest disagreement"*) · รายงานส่งมอบต้องบอกได้ว่าทดสอบ **build ไหน** ด้วย digest ไม่ใช่แค่ "เวอร์ชันล่าสุด"

### 7) เทียบเวอร์ชัน = หลักฐานว่าแก้ตรงไหน

![หัวเรื่อง เทียบเวอร์ชัน = หลักฐานว่าแก้ตรงไหน ชั้นวางกล่อง 2 แถว v1 กับ v2 กล่องคู่ที่ลายนิ้วมือตรงกันติดป้ายเขียว เหมือนเดิม 2 คู่ คู่ที่ลายนิ้วมือต่างกันติดป้ายส้ม เปลี่ยน คู่ที่อยู่ในหมอกมีเครื่องหมายคำถาม ติดป้ายเทา ไม่รู้ หุ่นยนต์ส่องแว่นขยายชี้กล่องที่เปลี่ยน เด็กถือคลิปบอร์ดหัวข้อ ต้องทดสอบซ้ำ แมวส้มกับลูกหมาอยู่ข้างชั้น](img/concept-08-version-compare.jpg)

REA เทียบได้ 2 แบบ · บทนี้ใช้แบบที่ 2 เป็นตัวหลัก

| คำสั่ง | เทียบอะไร | ผลที่ได้ | อ่านยังไง |
|---|---|---|---|
| `compare-application-versions` | build v1 ↔ build v2 | `unchanged` `added` `removed` `changed` `unknown` | ชื่อ chunk เป็น hash เปลี่ยนทั้งชุดทุก build → ผลมี noise เยอะ ส่วนใหญ่เป็น `unknown` · ใช้ดูข้อจำกัดเท่านั้น |
| `compare-source-to-bundle` ⭐ | source ↔ bundle ฝั่ง server (จับคู่ด้วย digest) | 7 คลาส `unchanged` `modified` `removed` `split` `merged` `duplicated` `unknown` | ทำ **4 ทิศ** (source เดิม/ใหม่ × build เดิม/ใหม่) แล้วดูเฉพาะไฟล์ที่ผลต่างกัน |

| เห็นคำว่า | แปลว่า | ทำอะไรต่อ |
|---|---|---|
| `unchanged` | digest ตรงกันทุก byte | ลดลำดับความสำคัญของ regression ได้ |
| `unknown` ที่ไฟล์ที่เราแก้ | REA หา digest ของ source ไฟล์นั้นใน bundle ไม่เจอ = สอดคล้องกับ "ไฟล์ถูกแก้" | เทียบกับ SHA-256 ของ source ประกอบ · ไม่ใช่หลักฐานว่าไฟล์หาย |
| `unknown` ที่ไฟล์ที่เรา **ไม่ได้** แก้ | มีการเปลี่ยนนอกแผน หรือไฟล์ไม่ได้อยู่ใน bundle อยู่แล้ว | ต้องอธิบายได้ทุกแถว |

> **อย่ารอคำว่า `modified`** · ในรอบที่ผู้สร้างบทลองรัน ไฟล์ที่ถูกแก้ออกมาเป็น `unknown` ไม่ใช่ `modified` เพราะ REA จับคู่ด้วย digest ไม่ได้ · และ `added`/`removed` จะขึ้นได้ก็ต่อเมื่ออีกฝั่ง coverage `complete` (หาไม่เจอ ≠ ไม่มี อีกครั้ง)

### 8) แผนที่แอป (application graph) + ตามรอยฟีเจอร์ (feature trace)

![หัวเรื่อง ตามรอยฟีเจอร์บนแผนที่ระบบ กระดานแผนที่แบบรถไฟใต้ดิน สถานีเรียงจากขวาไปซ้าย /api/coupons/validate หน้าตะกร้า localStorage endpoint chunk เด็กปักหมุดแดงที่สถานี /api/coupons/validate หุ่นยนต์ใช้พู่กันระบายเส้นสีฟ้าย้อนกลับไปจนถึงสถานี chunk ป้ายไม้มุมขวาล่าง seed → trace แมวส้มกับลูกหมานั่งยิ้มหน้ากระดาน](img/concept-09-feature-trace.jpg)

| ส่วนของแผนที่ | คือ | ตัวอย่างใน PawPantry |
|---|---|---|
| **node** | สิ่งของในแอป | `javascript-module` · `javascript-asset` · `endpoint` · `storage` |
| **edge** | ความสัมพันธ์มีทิศ | `contains` (ไฟล์มี chunk) · `calls` (chunk เรียก endpoint) · `persists_to` (เขียน storage) |
| **provenance** | หลักฐานของทุก node/edge | authority + location ของแต่ละชิ้น |

`trace-application-feature` เริ่มจาก **seed** แล้วเดินตามเส้น · บทนี้ใช้ seed ชนิด `string` (เช่น `coupons/validate`)

| direction | ตอบคำถาม | ใช้เมื่อ |
|---|---|---|
| `incoming` ⭐ | "ใครเรียกสิ่งนี้" | หาไฟล์/หน้าที่กระทบเมื่อจะแก้ endpoint (ใช้บ่อยสุด) |
| `outgoing` | "สิ่งนี้ไปเรียกอะไรต่อ" | ดูว่าโมดูลหนึ่งแตะ API/storage ไหน |
| `both` | ทั้งสองทาง | แอปเล็กแบบ PawPantry ได้แทบทั้งกราฟ → ไม่ช่วยจำกัดขอบเขต |

> **ทุก node ที่เดินถึง ≠ ส่วนของฟีเจอร์** · trace เดินผ่าน `contains` ด้วยจึงลามไปโมดูลข้างเคียงได้ (skill ของ REA เตือนเอง) · ใช้ trace เป็น "รายชื่อผู้ต้องสงสัย" แล้วยืนยันด้วยการค้นโค้ดหรือการรัน · และเลือก seed ให้ถูกชนิด: seed `api` ของ REA หมายถึง API ของ Electron ไม่ใช่ HTTP ส่วน `route` กับ `api` ที่ลองกับ `/api/coupons/validate` ได้ **no-match** จึงใช้ `string`

### 9) 3 วิธีดูเว็บที่รันอยู่: passive · driven · HAR

![หัวเรื่อง 3 วิธีสังเกตเว็บที่รันอยู่ การ์ตูน 3 ช่อง ช่อง 1 Passive: ดูอย่างเดียว เด็ก แมวส้ม และลูกหมานั่งดูจอเว็บร้านสัตว์เลี้ยงเงียบ ๆ มีกล้องวงจรปิดที่มุม ช่อง 2 Driven: ขับตามสคริปต์ หุ่นยนต์ถือรีโมตบังคับรถเข็นช็อปปิ้งเดินตามเส้นประบนเว็บ เด็กกับสัตว์ดูอย่างตื่นเต้น ช่อง 3 HAR: ดูบันทึกย้อนหลัง เด็กเปิดอัลบั้มที่มีจดหมายวิ่งไปมาระหว่างเบราว์เซอร์กับเซิร์ฟเวอร์ ข้าง ๆ มีหีบล็อกป้าย ความลับ ใส่กุญแจกับคุกกี้](img/concept-10-passive-driven-har.jpg)

| โหมด | ใครคุมเบราว์เซอร์ | ทำอะไรกับเว็บ | ได้หลักฐาน | ในบทนี้ |
|---|---|---|---|---|
| **Passive** (attach ผ่าน CDP) | คน · REA แค่ดู | ไม่คลิก ไม่เปลี่ยนหน้า | DOM · script · network ช่วงที่ดู | ไม่ใช้ (เบราว์เซอร์ของเราต้องเปิดพอร์ต debug) |
| **Driven** (`capture-browser-scenario`) | REA เปิด Playwright เอง ทำตามสคริปต์ JSON | ✅ คลิก/พิมพ์ตาม action ที่ประกาศ → **มีผลข้างเคียงกับระบบ** | หน้าจอ · accessibility tree · storage ทีละขั้น | LAB 3 (`rea/scenario-coupon.json`) |
| **HAR** (`inspect-web-network-capture`) | ไม่มีเบราว์เซอร์ | ❌ อ่านไฟล์ offline **ไม่ยิงคำขอซ้ำ** | คำขอ/คำตอบ ณ เวลาที่บันทึก | LAB 3 (`rea/record-har.mjs`) |

> **HAR = ความลับเต็มไฟล์** · HAR ที่บันทึกแบบ `full` มีรหัสผ่านและ cookie แบบตัวอักษรธรรมดา · ให้ REA ปิดค่าด้วย `--sensitive-value` · ห้ามส่งต่อ ห้าม commit (`.gitignore` กัน `*.har` ไว้แล้ว) · และ driven ทำให้ข้อมูลในร้านเปลี่ยนจริง (เช่นสต็อกลด) ต้อง reset ก่อนเทียบผล

### 10) Obligation: ของใหม่ต้องทำได้เท่าของเดิม

![หัวเรื่อง ของใหม่ต้องทำได้เท่าของเดิม กระดานเช็กลิสต์ 3 แถวที่ปิดครบ แต่ละแถวมีตรา 3 ดวง เจ้าของ (รูปคน) กรณีทดสอบ (หลอดทดลอง) ผลตรวจ (เครื่องหมายถูกสีเขียว) แถวล่างสุดยังเป็นช่องว่างมีเมฆสีเทาปิดพร้อมแม่กุญแจ unknown หุ่นยนต์ถือตรายาง เด็กถือคลิปบอร์ดตรวจ แมวส้มและลูกหมาอยู่ข้างกระดาน](img/concept-11-obligation-ledger.jpg)

REA มีแนวคิด **reconstruction obligation** = รายการพันธะที่ระบบที่แก้แล้ว **ต้องยังทำได้** · เทียบกับงาน tester ได้ตรง ๆ

| ช่องของ obligation | เทียบกับงานทดสอบ | ตัวอย่างสมมติ: คูปอง PAW10 |
|---|---|---|
| ของเดิมที่ต้องรักษา | requirement ที่กู้มา / test condition | "ใส่ PAW10 แล้วได้ส่วนลด" |
| กรณีที่ต้องมี `positive` `negative` `malformed` | เทคนิคออกแบบ TC (ปกติ / ผิด / เพี้ยน) | โค้ดถูก · โค้ดที่ไม่มีจริง · โค้ดว่าง/มีช่องว่าง |
| หลักฐานของเดิม (original authority) | แหล่ง oracle | HAR ของ `/api/coupons/validate` |
| ตัวตรวจ (verifier) + ผล | test ที่รันได้ + ผลผ่าน | Playwright E2E ผ่าน 3 เบราว์เซอร์ |

กฎ **fail-closed**: `fail` `unknown` `skipped` **ไม่มีวันรวมเป็น "ผ่าน"** · ข้อที่ยังไม่รู้ถูกล็อกไว้จนกว่าจะมีหลักฐาน (แถวเมฆในภาพ)

> **ปิดพันธะด้วยหลักฐานผิดชนิดไม่ได้** · static บอกแค่ว่า "มี endpoint นี้" ยังปิด obligation ของพฤติกรรมไม่ได้ ต้องมีผลจากการรันจริง · ใน LAB 9 เราทำ **obligation ledger** ของเดิมที่ต้องยังทำได้หลังแก้

### 12) จริยธรรม: ส่องได้เฉพาะระบบที่ได้รับอนุญาต

![หัวเรื่อง ส่องได้เฉพาะระบบที่ได้รับอนุญาต ประตู 2 บาน บาน ระบบของเรา เปิดอยู่มีกุญแจห้อย เด็กสะพายเป้กับหุ่นยนต์ถือแว่นขยายเดินเข้าไป แมวส้มกับลูกหมาเดินตาม บาน ระบบคนอื่น ปิดอยู่มีป้ายหยุดรูปมือสีแดงและป้ายตาชั่งกฎหมาย หุ่นยนต์อีกตัวยืนข้างประตูถือป้าย ต้องได้รับอนุญาต ข้างตู้เซฟล็อกกุญแจป้าย password / cookie](img/concept-13-ethics-permission.jpg)

| หลัก | ในทางปฏิบัติ |
|---|---|
| **ส่องเฉพาะระบบของเรา หรือได้รับอนุญาตเป็นลายลักษณ์อักษร** | ในคลาส = PawPantry ที่รันบนเครื่องตัวเองเท่านั้น · งานจริงต้องมีขอบเขตในสัญญา/หนังสืออนุญาต · ใบอนุญาต MIT ของ REA **ไม่ได้** อนุญาตให้ส่องของคนอื่น |
| **กฎหมายไทย (ภาพรวม ไม่ใช่คำแนะนำทางกฎหมาย)** | พ.ร.บ.คอมพิวเตอร์ (2550 แก้ไข 2560): เข้าถึงระบบที่มีมาตรการป้องกันโดยไม่ได้รับอนุญาต = ความผิด · ข้อมูลส่วนบุคคลใน HAR/ฐานข้อมูลอยู่ใต้ PDPA · ไม่แน่ใจ → ถามผู้ว่าจ้าง/ฝ่ายกฎหมายก่อน |
| **สัญญาซอฟต์แวร์ (EULA)** | ซอฟต์แวร์เชิงพาณิชย์หลายตัวห้าม reverse engineering ในสัญญา |
| **ไม่ดึงหรือพิมพ์ความลับ** | รหัสผ่าน token cookie ที่เจอ → ไม่คัดลอกลงรายงาน ไม่ส่งให้ AI · เจอ secret ใน bundle = รายงานเป็น **ข้อบกพร่องด้านความปลอดภัย** |
| **ผลถูกส่งออกนอกเครื่อง** | REA วิเคราะห์ในเครื่อง แต่ผลที่ Agent อ่านถูกส่งให้ model ของ Agent · ระบบราชการที่มีข้อมูลลับต้องตรวจนโยบายก่อน |

> **ได้เครื่องมือ ≠ ได้สิทธิ์** · REA ออกแบบให้ปลอดภัยโดยปริยาย (ทำงานในเครื่อง · ตัด credential ออกจาก capture · HAR ไม่ยิงซ้ำ) แต่ **การขออนุญาตเป็นหน้าที่ของเรา** · ในบทนี้ใช้ Playwright แบบ headless ในโปรไฟล์แยก ไม่แตะ Chrome หรือ cookie ของเราเอง

### 15) Characterization test: ล็อกสิ่งที่ระบบทำอยู่

![หัวเรื่อง Characterization test หุ่นยนต์ถ่ายรูปชั้นอาหารแมว CAT FOOD ที่เอียงนิด ๆ แล้วปักรูปไว้บนผนังป้าย พฤติกรรมเดิม มีเต่าทองตัวเล็กซ่อนอยู่บนชั้น เด็กถือไม้บรรทัดป้าย [D] ร้าน ทำหน้าสงสัย พูดว่า ล็อก ≠ ถูก แมวส้มกับลูกหมานั่งข้างเด็ก ในร้าน PawPantry](img/concept-15-characterization-lock.jpg)

Michael Feathers: ก่อนแก้ระบบที่ไม่มีเทสต์ ให้ **เขียนเทสต์ที่บันทึกสิ่งที่ระบบทำอยู่ตอนนี้** (ไม่ใช่สิ่งที่ควรทำ) รวมจุดแปลก ๆ · แก้แล้วเทสต์แดง = รู้ทันทีว่าพฤติกรรมเปลี่ยน · **golden master** = เก็บผลชุดใหญ่ไว้เทียบทั้งก้อน

| ล็อกด้วย | ล็อกอะไรได้ | ระวัง |
|---|---|---|
| `toHaveText` ค่าเงินตรง ๆ | ตัวเลขทุกจุดที่ลูกค้าเห็น | ต้องรู้ค่าที่จะล็อก และเทียบ [D] ก่อน |
| API JSON snapshot (`toMatchSnapshot`) | ข้อมูลและรูปแบบคำตอบ | ตัดฟิลด์ที่เปลี่ยนเอง (เวลา id) ก่อน |
| aria snapshot (`toMatchAriaSnapshot`) | โครงหน้า: heading ปุ่ม ลิงก์ | **ไม่ล็อกตัวเลข** Playwright เขียนเลขเป็น regex `\d+` |
| screenshot (`toHaveScreenshot`) | หน้าตา layout | tolerance กลืนตัวเลขที่ต่างเล็กน้อยได้ · baseline ผูกกับเบราว์เซอร์ × OS |

ถ้าค่าที่ระบบทำอยู่ **[E] ขัดกับ [D]** ให้เขียน **test คู่**: ข้อหนึ่งล็อกค่าปัจจุบัน (annotation `legacy-quirk`) · อีกข้อตาม [D] ใส่ `test.fail()` (annotation `KNOWN-ISSUE`) · วันที่มีคนแก้ ข้อ `test.fail` จะรายงาน *"Expected to fail, but passed."* = สัญญาณว่าพฤติกรรมเปลี่ยนแล้ว

> **ล็อก ≠ ยอมรับว่าถูก** · characterization test ที่ลอกค่าจากระบบที่มีบั๊กจะ "ผ่านตลอดไป" · ห้ามรัน `-u` (update snapshot) ให้ผ่านโดยไม่บอกเหตุผล · ค่าที่ขัด [D] ต้องจดเป็นผู้ต้องสงสัยใน `BASELINE.md` ไม่ใช่อบลงผลที่คาดหวัง

### 17) Impact analysis: แก้ตรงนี้กระทบอะไร

![หัวเรื่อง แก้แค่ที่ตั้งใจ กระดาษม้วน 3 แผ่นวางเรียงบนโต๊ะ หัวข้อ ตั้งใจแก้ · hash ต่าง · bundle ต่าง แต่ละแผ่นมีไอคอนไฟล์ เฟือง และรูปภาพ หุ่นยนต์ใช้ปากกาลากเส้นสีฟ้าเชื่อมรายการที่ตรงกันข้ามทั้ง 3 แผ่น เด็กชูตรายาง ส่งมอบได้ แมวส้มกับลูกหมาเกาะโต๊ะ ในร้าน PawPantry](img/concept-23-change-proof.jpg)

ก่อนอนุมัติให้แก้ ต้องรู้ว่าแตะไฟล์ไหน ใครเรียกไฟล์นั้น และต้องรันเทสต์อะไรซ้ำ · รายการ "ตั้งใจแก้" นี้คือแผ่นแรกในภาพ ที่ LAB 9 จะเอาไปเทียบกับ hash และ bundle จริง

| วิธี | ได้อะไร | ระวัง |
|---|---|---|
| ค้นโค้ด (Grep ของ Claude · `git grep -n`) | ทุกจุดที่อ้างชื่อหรือค่านั้น | ชื่อที่ประกอบตอนรัน (`"api/" + x`) ค้นไม่เจอ · เครื่องอาจไม่มี `rg` อย่าเขียนในพรอมต์ |
| ไล่ caller → callee (ขึ้น 2 ชั้น) | เส้นทางที่กระทบ พร้อมไฟล์:บรรทัด | AI อาจเดาจากชื่อไฟล์ → ทุกแถวต้องแนบผลค้น |
| REA trace `incoming` | chunk/โมดูลใน build ที่เรียก endpoint นั้น | เห็นแค่ฝั่ง client · coverage `partial` |
| `npx playwright test --list -g "<คำ>"` | ชุดเทสต์ที่เกี่ยว | ก่อนส่งมอบยังต้องรันเต็มชุด |

ตาราง impact ที่ให้ Agent ส่ง **ก่อนเขียน diff** ทุกครั้ง: `ไฟล์ที่จะแตะ | เหตุผล (BUG/CR) | ใครเรียกใช้ (ผลค้น) | หน้าจอ/API ที่กระทบ | เทสต์ที่ต้องรันซ้ำ | ความเสี่ยง`

> **impact ต้องครอบทุกจุดที่คำนวณ *และแสดง* ผล** · กฎเดียวกันอาจถูกคิดหรือแสดงซ้ำหลายที่ (หน้าเว็บ · API · หน้าสรุป) · ตรวจด้วยการค้นโค้ด ไม่ใช่เดาจากชื่อไฟล์ · และแยก **ต้นเหตุ** กับ **ปลายเหตุ** ให้ออกก่อนแก้ (LAB 6)
