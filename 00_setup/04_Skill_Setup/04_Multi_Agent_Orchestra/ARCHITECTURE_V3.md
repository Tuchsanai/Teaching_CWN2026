## 2) เส้นทางของ "ถามด้วยเสียง → ตอบด้วยเสียง" + RabbitMQ กระจายโหลด

```
ไมค์ (เบราว์เซอร์) → web /api/voice
  → RabbitMQ stt.request ──► stt-worker ×N ──► GPU-2 Whisper                (prefetch ตามที่ GPU-2 รับไหว)
  → RabbitMQ chat.request ─► chat-worker ×N
        ├ SQL: สินค้า ราคา สต็อก (Postgres)
        ├ Hybrid RAG: vector + keyword → RRF top 20 → GPU-3 /v1/rerank → top 4
        └ GPU-1 Qwen → chat.reply (สตรีมทีละคำ)                              (prefetch 4 = --max-concurrency 4)
  → RabbitMQ tts.request ──► tts-worker ×N ──► GPU-3 VoxCPM2                (prefetch ตามที่ GPU-3 รับไหว)
  → เบราว์เซอร์เล่นเสียง + มาสคอต 3D ขยับปากตามเสียง
```

**RabbitMQ ช่วยกระจายโหลดอย่างไร**
- 1 คิวต่อ 1 ชนิดงาน/1 GPU → GPU แต่ละใบรับงานเท่าที่ไหว (`prefetch` = จำนวนงานพร้อมกันสูงสุดของ GPU นั้น) ที่เกินรอในคิว ไม่ error
- เพิ่ม worker ได้ด้วย `docker compose up --scale chat-worker=2` (หรือชี้ worker อีกชุดไป GPU ใบที่ 2 ของงานเดียวกัน) → RabbitMQ แจกงานแบบ round-robin ให้ทุก consumer
- ตั้งค่าจากผล **load test** (ข้อ 5): prefetch ต่อคิว · จำนวน worker · เวลารอในคิวสูงสุด
- ข้อความไม่หายเมื่อ worker/GPU ล่ม (ack หลังทำเสร็จ) · ล้มเกิน 2 ครั้ง → dead-letter

แชทจำบริบท **หลายรอบ** (เก็บประวัติ 10 ข้อความล่าสุดต่อ session) → ทดสอบบทสนทนา 4–6 รอบ

## 4) ประเมิน RAG (พรอมต์ใหม่)

ชุดคำถามจาก PDF ใน `documents/` + ฐานข้อมูลสินค้า แยกชุด แยก metric:

| ชุด | ตัวอย่าง | metric |
|---|---|---|
| **A · RAG จากเอกสาร** (**150–170 ข้อ**: ข้อความ · ตารางหัว 2 ชั้น · เซลล์รวม · เชิงอรรถ · ข้ามหน้า) | "ปูกระเบื้อง 60×60 ใช้เกรียงฟันกี่มิล" | ① **Hit@4** (หน้าที่ถูกอยู่ใน 4 ย่อหน้าที่ค้นได้) · ② **MRR** · ③ **Faithfulness** (ทุกข้อความอ้างจากย่อหน้าที่ค้นได้ · LLM judge) · ④ **Citation accuracy** (ป้าย 📄 ไฟล์/หน้า ตรงคำตอบที่คาด) · ⑤ **Answer correctness** (ข้อเท็จจริงหลัก/ตัวเลขตรง) |
| **B · คำถามปกติ** (**70–80 ข้อ**: ราคา สต็อกสาขา ราคาส่ง คูปอง ค่าส่ง (SQL) · ข้อมูลร้าน · คำนวณวัสดุ · นอกเรื่อง) | "ปูน CEM-001 50 ถุง ราคาส่งเท่าไร" | ① **Exact numeric match** · ② **Tool/SQL correctness** (เรียกข้อมูลถูกตาราง) · ③ **Answer correctness** |
| **C · บทสนทนาหลายรอบ** (10–12 บท × **4–6 รอบ** ขั้นต่ำ 4 · บางบทเป็นเสียง) | "ปูนไหนเก็บนานสุด" → "แล้วราคาส่ง 100 ถุงล่ะ" → "ใส่ตะกร้าให้หน่อย" | **Context retention** (รอบหลังเข้าใจคำว่า "อันนั้น") + metric ของชุด A/B ต่อรอบ · เสียง: **WER/CER ของ Whisper** |

ผล → `eval/results.json` → หน้า **/admin/eval** (dashboard: คะแนนต่อ metric · ต่อเอกสาร · ต่อประเภทคำถาม · เทียบมี/ไม่มี reranker · ข้อที่ตอบผิดพร้อมเหตุผล)

## 5) Load test — รับผู้ใช้พร้อมกันได้กี่คน

สคริปต์ `loadtest/` ยิงผู้ใช้จำลองพร้อมกัน 1 → 2 → 4 → 8 → 16 → 32 คน (ขั้นละ 2–3 นาที) ผ่าน**ทางเดียวกับผู้ใช้จริง** (web → RabbitMQ → worker → GPU) แยก 3 แบบ:

| แบบ | ยิงอะไร | วัด |
|---|---|---|
| L1 แชทพิมพ์ (Qwen) | คำถามสุ่มจากชุดประเมิน | เวลาถึงคำแรก (TTFT) p50/p95 · เวลาจบ · token/s รวม · ความยาวคิว `chat.request` |
| L2 ฟังเสียง (Whisper) | ไฟล์เสียงคำถาม 3–8 วินาที | เวลาถอดความ p50/p95 · real-time factor · ความยาวคิว `stt.request` |
| L3 พูด (VoxCPM2) | คำตอบ 1–3 ประโยค | เวลาได้เสียง p50/p95 · RTF · ความยาวคิว `tts.request` |
| L4 ครบวง (เสียง→เสียง) | ผสมทั้งหมด | เวลาจากหยุดพูดถึงได้ยินคำตอบ p50/p95 |

ผล: **จำนวนผู้ใช้พร้อมกันสูงสุด** ที่ยังผ่านเกณฑ์ (เช่น p95 คำแรก < 5 วิ · เสียงตอบ < 8 วิ · error 0%) ต่อ GPU · กราฟ latency vs ผู้ใช้ · ค่า prefetch/จำนวน worker ที่แนะนำ → หน้า **/admin/load** (หรือแท็บใน dashboard เดียวกับ eval)
