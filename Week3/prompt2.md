# สร้างบทเรียน AI Workflow Engineering สำหรับ System Analyst

สร้างสื่อการสอนภาษาไทยพร้อม LAB แบบ **ทำตามทีละขั้นและตรวจผลได้ทุกขั้น** ครอบคลุม **Loop Engineering, Graph Engineering และ Dynamic Workflow**
ให้นักศึกษารับบทเป็น System Analyst (SA) ในบริษัท Tech โดยใช้กรณีศึกษา **“ครัวคุณยาย”** เพื่อออกแบบ **FR/NFR, Flow และโครงสร้างระบบ พร้อมสร้าง UI Mock-up ที่เล่นได้จริง**
อธิบายทฤษฎีอย่างละเอียด จัดกิจกรรมจากง่ายไปยาก และแสดงว่าแต่ละ Workflow ช่วยแก้ข้อจำกัดของวิธีก่อนหน้าอย่างไร พร้อมเปรียบเทียบคุณภาพ เวลา และต้นทุนจากหลักฐานจริง

## 1. โครงสร้างไฟล์

สร้างโฟลเดอร์หลัก `AI_Workflow_Engineering_for_SA` ประกอบด้วย:

* `README.md` — ภาพรวม เป้าหมาย ลำดับบทเรียน การเตรียมเครื่อง และวิธีใช้งาน
* `AI_Workflow_Engineering_SA.html` — สไลด์สื่อการสอนภาษาไทย
* `001_LAB_<ชื่อกิจกรรม>/`
* `002_LAB_<ชื่อกิจกรรม>/`
* … จนถึง `00x_LAB_<ชื่อกิจกรรม>/`

วางโฟลเดอร์แต่ละ LAB ในโฟลเดอร์หลักโดยตรง **ไม่สร้าง `LAB/` ครอบ** กำหนดชื่อและจำนวนกิจกรรมตามความเหมาะสม โดยมี **ไม่เกิน 9 LAB**
ทุก LAB ต้องมี `README.md` ภาษาไทย พร้อมไฟล์ตั้งต้น Prompt ตัวอย่างผลลัพธ์ และวิธีเปิดใช้งานชิ้นงาน จัดเก็บแผนภาพ เอกสารอ้างอิง และหลักฐานให้เป็นระเบียบ พร้อม relative links ที่ใช้งานได้จริง

ใช้ **กรณี A: ครัวคุณยาย — ระบบสั่งอาหารผ่าน QR ที่โต๊ะและสั่งกลับบ้าน** ความเสี่ยงระดับกลางตามโจทย์ ครอบคลุม 3 บทบาท:

| บทบาท                | ขอบเขตหลัก                                                  |

| พนักงานครัว/หน้าร้าน | รับและจัดการออเดอร์ อัปเดตสถานะ จัดการวัตถุดิบ โต๊ะ และบิล  |
| ผู้จัดการร้าน        | จัดการเมนู วัตถุดิบ ช่วงเร่งด่วน สิทธิ์พนักงาน และรายงาน    |

อ้างอิงไฟล์แนบ:

* `appendix-a-restaurant.md` — User Story 26 รายการ
* `ai-agent-routing.html` — บริบทและรายละเอียดของกรณีครัวคุณยาย

อ่านข้อมูลก่อนออกแบบบทเรียน รักษารหัส User Story, Acceptance Criteria กฎธุรกิจ เงื่อนไขเชิงตัวเลข และข้อจำกัดตามต้นฉบับ โดยครอบคลุม:

* การสั่งที่โต๊ะและสั่งกลับบ้าน
* เมนู ตัวเลือกเพิ่ม และการแมปวัตถุดิบ
* สถานะออเดอร์และช่วงเร่งด่วน
* วัตถุดิบหมดระหว่างมีออเดอร์
* เงินสด/PromptPay และทางออกเมื่อบริการใช้ไม่ได้
* การเปิด–ปิดโต๊ะ รวมบิล สิทธิ์พนักงาน และรายงาน
* การใช้งานบน Ubuntu เครื่องเดียวและเครือข่ายภายในร้านตามต้นฉบับ

แต่ละ LAB เลือกใช้ User Story บางส่วนได้ โดยระบุรหัสและขอบเขต พร้อมตารางความครอบคลุมตลอดบทเรียน หากพบข้อมูลขัดแย้งหรือเพิ่มสมมติฐานเพื่อการสอน ต้องระบุให้ชัดเจน

## 3. เป้าหมายการเรียนรู้และชิ้นงาน

เมื่อจบบทเรียน นักศึกษาต้องสามารถ:

1. **เลือกและออกแบบ Workflow** ให้เหมาะกับปัญหา ความเสี่ยง เวลา และงบประมาณ
2. **ออกแบบ FR/NFR** พร้อมกฎธุรกิจ เกณฑ์ยอมรับ และวิธีตรวจสอบที่วัดผลได้
3. **ออกแบบ Flow และโครงสร้างระบบ** ครอบคลุมขั้นตอนหลัก ทางเลือก กรณีผิดพลาด การเปลี่ยนสถานะ โมดูล ข้อมูลและความสัมพันธ์ หน้าจอ และสิทธิ์แต่ละบทบาท
4. **สร้าง UI Mock-up ที่เล่นได้จริง** ผ่านเว็บเบราว์เซอร์ โดยใช้ข้อมูลจำลอง
5. **ตรวจทานและปรับปรุงชิ้นงาน** จัดการข้อขัดแย้ง งานที่ล้มเหลว และการเปลี่ยนแปลงข้อกำหนด
6. **ส่งต่อผลงานให้ Developer และ QA** พร้อมหลักฐานตรวจสอบย้อนกลับ:

**User Story → FR/NFR → Flow และโครงสร้าง → UI Mock-up → Test Scenarios**

## 4. ลำดับและขอบเขต LAB

อธิบายพัฒนาการของแนวคิดตามลำดับ:

**Single Prompt → Loop → Static Graph → Conditional Graph → Dynamic Workflow → Re-planning**

ให้ LAB เน้นเฉพาะ 3 กลุ่ม:

| กลุ่ม             | จุดเน้น                                                     |
| ----------------- | ----------------------------------------------------------- |
| Loop Engineering  | สร้าง ตรวจ และปรับปรุงชิ้นงานเป็นรอบ                        |
| Graph Engineering | แบ่งงาน กำหนด Dependency ส่งต่อข้อมูล เลือกเส้นทาง และรวมผล |
| Dynamic Workflow  | ปรับงานและความสัมพันธ์ระหว่างทำงาน รวมถึง Re-planning       |

ใช้ **Single Prompt เป็นผลตั้งต้นสำหรับเปรียบเทียบภายใน LAB** และรวม **Re-planning ไว้ใน Dynamic Workflow**

กิจกรรมต้องต่อยอดชิ้นงานระบบเดียวกัน เก็บผลแต่ละเวอร์ชัน และเพิ่มความซับซ้อนอย่างมีเหตุผล โดยไม่จำเป็นต้องแบ่งหนึ่งแนวคิดต่อหนึ่ง LAB

## 5. ทฤษฎีในสไลด์
สไลด์ต้องมีภาพรวม เป้าหมาย กรณีศึกษา ทฤษฎี แผนภาพ ตัวอย่าง Input/Output กิจกรรม คำถามตรวจความเข้าใจ และลิงก์ไปยัง LAB จัดเนื้อหาให้อ่านง่ายและละเอียดพอสำหรับเรียนด้วยตนเอง

### Loop Engineering

อธิบาย:
* วงรอบสร้าง → ตรวจ → ระบุข้อบกพร่อง → แก้ไข → ตรวจซ้ำ
* บทบาทผู้สร้าง ผู้ตรวจ และเกณฑ์ประเมินร่วมกัน
* ความต่างระหว่าง Retry เมื่อทำงานล้มเหลว กับการแก้เนื้อหาตาม Feedback
* เงื่อนไขหยุด: ผ่านเกณฑ์ ถึงเพดานรอบ หมดเวลา/งบ หรือคุณภาพไม่ดีขึ้น
* การบันทึกผลและป้องกันการวนซ้ำโดยไม่คืบหน้า
* การตรวจว่าการแก้ไขทำให้ส่วนที่เคยถูกต้องเสียหายหรือไม่
* ตัวอย่างแก้ User Story กำกวม FR/NFR ที่วัดไม่ได้ Flow ตกหล่น และ UI ไม่ตรงข้อกำหนด

### Graph Engineering

อธิบาย:

* Node, Edge, Dependency, State และข้อมูลที่ส่งต่อ
* Static Graph และ Conditional Graph: การเลือกเส้นทางที่กำหนดไว้ต่างจากการสร้างแผนใหม่อย่างไร
* Sequential, Fan-out/Fan-in และการตรวจทานหลายมุมมอง
* DAG สำหรับงานไม่มีวงย้อนกลับ และการแสดง Loop ในกราฟที่มีวงรอบอย่างถูกต้อง
* การแบ่งงานตามบทบาทหรือโมดูล แล้วรวมผลโดยแก้ข้อมูลซ้ำและข้อขัดแย้ง
* รูปแบบผลลัพธ์ เกณฑ์รับงาน เกณฑ์รวมผล และการรับมือเมื่องานบางส่วนล้มเหลว
* Self-consistency: เปรียบเทียบคำตอบหลายชุดด้วยเกณฑ์และหลักฐาน โดยไม่ถือว่าเสียงส่วนใหญ่ถูกเสมอ

### Dynamic Workflow

อธิบาย:

* การเพิ่ม แยก ยกเลิก หรือจัดลำดับงานและ Dependency ใหม่จากข้อมูลระหว่างทาง
* บทบาท Planner, Executor และ Evaluator พร้อมขอบเขตการตัดสินใจ
* ความต่างระหว่าง Conditional Routing, การแก้ผลงานใน Loop และ Re-planning
* การวิเคราะห์ผลกระทบและใช้ซ้ำเฉพาะผลงานเดิมที่ยังถูกต้อง
* การบันทึกแผนแต่ละเวอร์ชัน เหตุผลที่เปลี่ยน และข้อจำกัดเวลา/งบประมาณ

ใช้สถานการณ์ เช่น วัตถุดิบหมดระหว่างมีออเดอร์ หรือพบข้อกำหนดการใช้งานเมื่ออินเทอร์เน็ตภายนอกหลุด โดยแสดง:

1. แผนวิเคราะห์ระบบของ AI ก่อนพบข้อมูล
2. ข้อมูลหรือผลตรวจที่ทำให้แผนเดิมไม่เพียงพอ
3. งานและ Dependency ที่เปลี่ยน
4. FR/NFR, Flow โครงสร้าง และ UI ที่ได้รับผลกระทบ
5. ส่วนที่ใช้ซ้ำได้และส่วนที่ต้องตรวจใหม่

**แยกการเปลี่ยนแผนงานของ AI ออกจากการเปลี่ยนสถานะในระบบร้านอาหารอย่างชัดเจน** หากเงื่อนไขมีอยู่แล้วในต้นฉบับ ให้ระบุว่าเป็นการเปิดเผยข้อมูลเพิ่มเติมระหว่าง LAB

## 6. รูปแบบ LAB: ทำตามทีละขั้นและตรวจผลได้ทุกขั้น

ทุก LAB ต้องเป็นคู่มือ **Step-by-step** ที่นักศึกษาทำตามผ่าน Claude Code หรือ Codex ได้จริง

เริ่มแต่ละ LAB ด้วย:

* โจทย์ธุรกิจและเหตุผลที่ใช้ Workflow
* เป้าหมาย ความรู้ก่อนเรียน และเวลาประมาณการ
* ข้อมูลตั้งต้น รหัส User Story และไฟล์ที่ใช้
* แผนภาพ Workflow และสิ่งส่งมอบ

### รายละเอียดที่ต้องมีในทุกขั้นตอน

| หัวข้อ              | สิ่งที่ต้องระบุ                                                                |
| ------------------- | ------------------------------------------------------------------------------ |
| รหัสและเป้าหมาย     | เช่น `STEP-01` ทำอะไร และเกี่ยวข้องกับ Workflow อย่างไร                        |
| ข้อมูลเข้า          | ไฟล์หรือผลลัพธ์จากขั้นก่อนหน้าที่ต้องใช้                                       |
| วิธีทำ              | คำสั่งหรือ Prompt ที่คัดลอกใช้ได้ พร้อมตำแหน่งที่ต้องรัน                       |
| ผลลัพธ์ที่คาดหวัง   | ชื่อไฟล์ โครงสร้างข้อมูล และตัวอย่างเนื้อหาหรือหน้าจอที่ควรได้                 |
| จุดตรวจสอบ          | Checklist หรือวิธีทดสอบ พร้อมเกณฑ์ผ่านก่อนเริ่มขั้นถัดไป                       |
| วิธีแก้เมื่อไม่ผ่าน | อาการที่พบบ่อย แนวทางแก้ Prompt สำหรับแก้ไข และเงื่อนไขหยุดหรือขอความช่วยเหลือ |
| การส่งต่อ           | ผลลัพธ์ที่ต้องเก็บและวิธีนำไปใช้ในขั้นถัดไป                                    |

ตัวอย่างผลลัพธ์ต้องมีเนื้อหาเพียงพอให้เทียบตรวจได้ ไม่แสดงเพียงรายชื่อไฟล์หรือคำว่า “สำเร็จ”

### การติดตามผลแต่ละขั้น

* กำหนดรหัสขั้น หมายเลขรอบ และเวอร์ชันของชิ้นงาน
* เก็บผลแต่ละขั้นโดยไม่เขียนทับหลักฐานรอบก่อน
* มีตารางบันทึก **ขั้นตอน → ไฟล์ผลลัพธ์ → ผลตรวจ → ข้อบกพร่อง → การแก้ไข → ขั้นถัดไป**
* แยกตัวอย่างผลลัพธ์ที่คาดหวังออกจากผลที่นักศึกษารันได้จริง
* ผลจาก AI ไม่จำเป็นต้องตรงตัวอย่างทุกคำ แต่ต้องผ่านรูปแบบและเกณฑ์เดียวกัน
* สำหรับขั้นสร้าง UI ให้ระบุสิ่งที่ต้องคลิก ข้อมูลที่ต้องกรอก ผลที่ควรปรากฏ และหลักฐานที่ต้องเก็บ

จบแต่ละ LAB ด้วยสรุปชิ้นงาน ผลประเมิน คำถามอภิปราย และข้อจำกัดที่จะนำไปแก้ใน LAB ถัดไป

## 7. ข้อกำหนด UI Mock-up

สร้าง UI Mock-up ที่ทดลองใช้งานผ่านเว็บเบราว์เซอร์ได้จริง โดย:

* ครอบคลุมบทบาทและ User Story ตามขอบเขตที่ระบุ
* คลิกปุ่ม เปลี่ยนหน้า กรอกข้อมูล และทำขั้นตอนหลักได้ต่อเนื่อง
* ทดลองเลือกเมนู เพิ่มตัวเลือก ส่งออเดอร์ อัปเดตและติดตามสถานะ รวมถึงจำลองการชำระเงิน
* แสดงผลสำเร็จ ข้อผิดพลาด และกรณียกเว้นตามกฎธุรกิจ
* ใช้ข้อมูลจำลอง พร้อมระบุส่วนที่จำลอง เช่น PromptPay การแจ้งเตือน และการสลับบทบาท
* มีวิธีเปิดใช้งาน ขั้นตอนทดลอง และการรีเซ็ตข้อมูล
* เชื่อมโยงหน้าจอและพฤติกรรมกับ FR/NFR และ Flow ที่ออกแบบไว้

ระบุ NFR ที่ตรวจได้ใน Mock-up และ NFR ที่ต้องตรวจเพิ่มเติมในระบบจริง เช่น ความปลอดภัย การรองรับโหลด และความพร้อมใช้งาน โดยไม่อ้างว่า Mock-up พิสูจน์คุณสมบัติเหล่านี้ครบแล้ว

## 8. การวัดผลและเปรียบเทียบ

แต่ละ LAB ต้องแสดงว่า Workflow ช่วยสร้าง ตรวจ หรือปรับปรุงชิ้นงานอย่างไร พร้อมอธิบายภาระที่เพิ่มขึ้นและสถานการณ์ที่วิธีเรียบง่ายกว่ายังเหมาะสม

เปรียบเทียบ Workflow ด้วยข้อมูลตั้งต้น ขอบเขตชิ้นงาน และเกณฑ์เดียวกัน โดยวัด:

* ความครบถ้วนของบทบาท กฎธุรกิจ และ FR/NFR
* ความชัดเจนและความสามารถในการทดสอบ Acceptance Criteria
* ความสอดคล้องระหว่าง Requirements, Flow โครงสร้าง และ UI
* ความสำเร็จของการใช้งาน UI ตาม Test Scenarios
* จำนวนข้อขัดแย้ง ข้อมูลตกหล่น และสมมติฐานที่ยังไม่ยืนยัน
* การตรวจสอบย้อนกลับและการรับมือกับการเปลี่ยนแปลง
* เวลา จำนวนรอบ จำนวนการเรียก Agent และต้นทุนที่วัดได้

จัดทำ Rubric แบบบันทึกผล และตารางเปรียบเทียบพร้อมหลักฐาน ระบุเครื่องมือ โมเดล และเงื่อนไขทดลองที่มีผลต่อผลลัพธ์

ห้ามสร้างตัวเลขหรือผลทดลองขึ้นเอง หากวัดไม่ได้ให้ระบุว่าไม่มีข้อมูล แยกค่าประมาณออกจากค่าที่วัดจริง และไม่ตั้งข้อสรุปล่วงหน้าว่า Workflow ที่ซับซ้อนกว่าจะดีกว่าเสมอ

## 9. กติกาและการตรวจรับ

* ใช้ **placeholder สำหรับข้อมูลบุคคลและบัญชี** ห้ามใส่ชื่อบุคคล อีเมล Username หรือ Token จริงใน LAB และหลักฐาน
* สร้างแผนภาพด้วย **Excalidraw MCP** พร้อมเก็บไฟล์แก้ไขได้และไฟล์สำหรับแสดงผล
* ทดสอบสไลด์และ UI Mock-up ด้วย **Playwright CLI** พร้อม Capture ภาพหน้าจอและบันทึกผลจริง
* ตรวจลิงก์ ไฟล์ประกอบ วิธีเปิดใช้งาน และขั้นตอน LAB ให้ทำตามได้
* แยกข้อมูลต้นฉบับ สมมติฐาน ตัวอย่างผลลัพธ์ และผลทดลองใหม่อย่างชัดเจน
* ห้ามนำหลักฐานจาก HTML เดิมมาอ้างว่าเป็นผลการรันใหม่
* ระบุส่วนที่ทดสอบแล้ว ส่วนที่ยังไม่ได้ทดสอบ และข้อจำกัดของเครื่องมือตามจริง

เมื่อเสร็จ ให้สรุปไฟล์ที่สร้าง วิธีเปิดสไลด์ วิธีเริ่ม LAB วิธีทดลอง UI Mock-up และผลการตรวจสอบ เพื่อให้นำไปใช้สอนได้ทันที
