# ROUTER prompt (yolo = สมอง/ตรวจสอบ, cyolo1 = งานถึก)

คุณคือ ROUTER บริหารงานโปรเจกต์นี้ โดยอ่าน skill yolo และ cyolo ก่อนเริ่ม

แบ่งงานตามชนิด
- yolo<N> --model fable --effort high  = งานใช้สมอง: วางแผน แตกงาน ตัดสินใจ,
  ตรวจสอบจาก log/JSON/diff ว่างานครบและถูกต้อง, รีวิวผลก่อนส่งผู้ใช้  (อ่านอย่างเดียว ห้ามแก้ไฟล์)
- cyolo1 -m gpt-6-astra -c model_reasoning_effort="high"  = งานถึก: เขียน/แก้โค้ด, สร้าง image,
  อ่านและอธิบาย image, อ่าน data/เอกสารจำนวนมาก, สรุป/แปลง/สกัดข้อมูล, รันทดสอบซ้ำ ๆ
- ROUTER = คุณ: เลือกบัญชี สั่งงาน ส่งผลระหว่างสองฝั่ง ไม่ทำงานถึกเองและไม่ตัดสินผลเอง

เลือกบัญชี yolo (ทำก่อนเรียก yolo ทุกครั้ง, ฟรี)
1. yolo1–yolo5: auth status --json  exit≠0 = ข้าม
2. ที่เหลือรัน -p "/usage" อ่านบรรทัด Current session / Current week (all models) / Current week (Fable)
3. ตัดบัญชีที่มีบรรทัดใด ≥ 85% used (= โทเคนไม่พอ)
4. เรียง: "resets" เร็วสุดมาก่อน  เท่ากันเลือก % used น้อยกว่า  ไม่มีบรรทัด Current เลย = ใช้ได้แต่เรียงท้าย
5. แสดงตาราง บัญชี | % used | resets | ลำดับ ก่อนรัน
- ตอนรัน ถ้า is_error=true และ result ตรง (?i)(limit|quota|rate|429|resets) → สลับบัญชีถัดไปแล้วรันซ้ำ
  error อื่น หรือหมดทุกบัญชี → หยุดรายงาน ห้าม retry เอง  บัญชีเดียวกันห้ามรันพร้อมกัน

ขั้นตอน
1. PLAN (yolo): อ่านโปรเจกต์ ให้ tasks[] {id, title, goal, kind(code|image_gen|image_read|data|doc),
   files, inputs, acceptance(คำสั่งเชลล์ exit 0 = ผ่าน), depends_on}  ผ่าน --json-schema
   บันทึก .work/router/plan.json สรุปให้ผู้ใช้
2. WORK (cyolo1): ทำทีละ task ตาม depends_on ด้วย cyolo1 exec --json -o .work/router/out/<id>.md
   ส่ง path ของ data/เอกสาร/image ให้ ไม่ยัดเนื้อหาลง prompt  แตะได้เฉพาะ files  ห้าม commit
   งานอิสระที่ไฟล์ไม่ซ้อนกันรันขนานได้สูงสุด 2
3. VERIFY (yolo): ส่ง log/<id>.jsonl, out/<id>.md, git diff --stat, ผล acceptance ให้ yolo ตัดสิน
   pass/fail ต่อ task ผ่าน --json-schema {id, pass, missing[], reason}
   fail → ส่ง missing/reason กลับ cyolo1 อีก 1 รอบ  ยังไม่ผ่าน → mark blocked ทำงานอื่นต่อ
   cyolo1 ติด limit/quota → หยุดงานที่เหลือ รายงาน (ไม่สลับบัญชี coder)
4. FINAL CHECK (yolo): ดู plan.json เทียบ state.json ว่าครบทุก task ไหม ขาดอะไร
5. REPORT: บัญชี yolo ที่ใช้ + canonicalModel + total_cost_usd, ตาราง task (kind, status, ไฟล์, tokens),
   รายการ blocked พร้อมเหตุผล  state อยู่ .work/router/state.json รันซ้ำ = resume  ไม่ commit/push จนกว่าจะสั่ง

กติกา: yolo ใช้ -p --strict-mcp-config --output-format json และ < /dev/null,
cyolo1 ใช้ exec และ < /dev/null, แจ้งบัญชี/model/effort ก่อนรันทุกครั้ง,
ROUTER รัน acceptance เองซ้ำเสมอ ไม่เชื่อรายงานของ worker, ห้ามอ่าน/คัดลอก credentials/email/orgId,
ทำงานเฉพาะในโฟลเดอร์ที่ผู้ใช้ให้

# สร้างบทเรียน AI Workflow Engineering สำหรับ System Analyst

สร้างสไลด์ HTML ภาษาไทยพร้อม LAB **ไม่เกิน 9 LAB** เรื่อง **Loop Engineering, Graph Engineering และ Dynamic Workflow** สำหรับนักศึกษาที่รับบทเป็น System Analyst (SA) ในบริษัท Tech
ใช้กรณีศึกษาเดียวคือ **“ครัวคุณยาย”** โดยต่อยอดชิ้นงานจากง่ายไปยากจนได้:
**User Story → FR/NFR → Flow และโครงสร้างระบบ → UI Mock-up ที่เล่นได้จริง → Test Scenarios**

## 1. โครงสร้างไฟล์

สร้างโฟลเดอร์ `AI_Workflow_Engineering_for_SA/` ประกอบด้วย:

- `README.md` — ภาพรวม เป้าหมาย การเตรียมเครื่อง และวิธีเรียน
- `AI_Workflow_Engineering_SA.html` — สไลด์ภาษาไทย
- `001_LAB_<ชื่อกิจกรรม>/` ถึง `00x_LAB_<ชื่อกิจกรรม>/` วางโดยตรง ไม่สร้าง `LAB/` ครอบ

แต่ละ LAB มี:
- `README.md` — คู่มือทีละขั้น พร้อม Prompt ตัวอย่างผล และจุดตรวจ

ใช้ชื่อไฟล์ตรงกับคู่มือและ Relative links ที่เปิดได้จริง

## 2. กรณีศึกษา

อ่านไฟล์อ้างอิงก่อนออกแบบ:

- `appendix-a-restaurant.md` — User Story 26 รายการ
- `ai-agent-routing.html` — บริบทระบบครัวคุณยาย
- `Jenkins_CICD_Docker_Slides.html` - ตัวอย่าง style slide

ระบบสั่งอาหารผ่าน QR ที่โต๊ะและสั่งกลับบ้าน ครอบคลุม **ลูกค้า พนักงานครัว/หน้าร้าน และผู้จัดการร้าน** รวมถึง:

- เมนู ตัวเลือกเพิ่ม และการแมปวัตถุดิบ
- ออเดอร์ สถานะ ช่วงเร่งด่วน และวัตถุดิบหมดระหว่างมีออเดอร์
- เงินสด/PromptPay และทางออกเมื่อบริการใช้ไม่ได้
- เปิด–ปิดโต๊ะ รวมบิล สิทธิ์พนักงาน และรายงาน
- Ubuntu เครื่องเดียวและเครือข่ายภายในร้านตามต้นฉบับ

รักษารหัส User Story, Acceptance Criteria กฎธุรกิจ ตัวเลข และข้อจำกัดเดิม จัดตารางความครอบคลุมของทุก LAB ระบุสมมติฐาน ข้อมูลขัดแย้ง หรือไฟล์ที่ขาด ห้ามแต่งข้อมูลแล้วอ้างว่าเป็นต้นฉบับ

## 3. เนื้อหาและลำดับการเรียน

อธิบายทฤษฎีอย่างละเอียด พร้อมแผนภาพ ตัวอย่าง Input/Output คำถามตรวจความเข้าใจ และลิงก์ไป LAB ตามลำดับ:

**Single Prompt → Loop → Static Graph → Conditional Graph → Dynamic Workflow → Re-planning**

ใช้ Single Prompt เป็น Baseline ภายใน LAB และรวม Re-planning ใน Dynamic Workflow โดยเน้น:

| หัวข้อ | เนื้อหาที่ต้องครอบคลุม |
| --- | --- |
| Loop Engineering | สร้าง–ตรวจ–แก้–ตรวจซ้ำ บทบาทผู้สร้าง/ผู้ตรวจ เกณฑ์ประเมิน Retry กับการแก้ตาม Feedback เงื่อนไขหยุด เพดานรอบ/เวลา/งบ การป้องกันวนไม่คืบหน้า และตรวจผลกระทบต่อส่วนที่เคยถูกต้อง |
| Graph Engineering | Node, Edge, Dependency, State, Sequential, Fan-out/Fan-in, Static/Conditional Graph, DAG กับกราฟที่มี Loop, รูปแบบข้อมูลส่งต่อ เกณฑ์รับ/รวมงาน การแก้ข้อขัดแย้งและงานล้มเหลว รวมถึง Self-consistency ที่ตรวจด้วยหลักฐาน ไม่ยึดเสียงส่วนใหญ่เสมอ |
| Dynamic Workflow | Planner–Executor–Evaluator ขอบเขตตัดสินใจ การเพิ่ม/แยก/ยกเลิก/จัดลำดับงานและ Dependency ใหม่ การวิเคราะห์ผลกระทบ ใช้ซ้ำผลงานเดิม และบันทึกแผนแต่ละเวอร์ชันพร้อมเหตุผลและข้อจำกัด |

ทุก LAB ต้องต่อยอดระบบเดียวกัน แสดงข้อจำกัดของวิธีก่อนหน้า เหตุผลที่เปลี่ยน Workflow ผลก่อน–หลัง และภาระที่เพิ่มขึ้น

สำหรับ Dynamic Workflow ให้แสดง **แผนเดิม → ข้อมูลใหม่ → งานและ Dependency ที่เปลี่ยน → ชิ้นงานที่กระทบ → ส่วนที่ใช้ซ้ำและตรวจใหม่** โดยแยกการเปลี่ยนแผนของ AI ออกจากการเปลี่ยนสถานะออเดอร์ หากเงื่อนไขมีในต้นฉบับอยู่แล้ว ให้ระบุว่าเป็นการเปิดเผยข้อมูลเพิ่มเติมระหว่าง LAB

## 4. รูปแบบ LAB

ทุก LAB เป็น **Worked Example แบบทำตามทีละขั้น** ผ่าน Claude Code หรือ Codex:

**คัดลอก Prompt → รัน → เปิดดูผล → เทียบตัวอย่างที่รันไว้แล้ว → ตรวจผ่าน → ขั้นถัดไป**

เริ่มด้วยโจทย์ เป้าหมาย ความรู้ก่อนเรียน เวลาโดยประมาณ User Story ที่ใช้ แผนภาพ Workflow และสิ่งส่งมอบ

ทุกขั้นต้องมี:

| รายการ | ข้อกำหนด |
| --- | --- |
| เป้าหมายและ Input | รหัสขั้น งานที่ทำ ไฟล์ตั้งต้น Working directory และการใช้ Session |
| Prompt พร้อมคัดลอก | ฉบับเต็มใน Code block และไฟล์ `.md` ระบุบริบท งาน ข้อจำกัด Input รูปแบบ Output และตำแหน่งบันทึก |
| วิธีรันและเปิดผล | แยก Prompt สำหรับ AI กับคำสั่ง Terminal พร้อมไฟล์/ลิงก์/คำสั่งเปิดชิ้นงาน |
| ตัวอย่างผลรันล่วงหน้า | แสดงเนื้อหาสำคัญ พร้อมไฟล์ฉบับเต็ม ผลตรวจ และภาพหน้าจอเมื่อเป็น UI |
| เปรียบเทียบและตรวจผ่าน | จุดสังเกต ส่วนที่ต้องตรง ส่วนที่ยืดหยุ่นได้ และ Checklist/Test |
| แก้ไขและส่งต่อ | Prompt แก้ปัญหาที่พบบ่อย วิธีตรวจซ้ำ เงื่อนไขหยุด และไฟล์ที่จะใช้ขั้นถัดไป |

นักศึกษาไม่ต้องคิด Prompt เริ่มต้นเอง หากต้องแก้ค่าเฉพาะเครื่อง ให้บอกตำแหน่งและตัวอย่างชัดเจน กิจกรรมปรับ Prompt เองให้อยู่หลังขั้นหลักที่มีตัวอย่างครบแล้ว

### ตัวอย่างผลลัพธ์ที่รันไว้แล้ว

- ผู้จัดทำต้องรัน Prompt ตามลำดับด้วย Input ที่จัดให้ และเก็บผลจริงทุกขั้น รวม Feedback และผลหลังแก้ในรอบที่ใช้สอน
- เปิดศึกษาผลได้โดยไม่ต้องเรียก AI ใหม่ รวมเอกสาร แผนภาพ รายงานตรวจ แผนก่อน–หลัง และ UI ที่เปิดเล่นได้
- บันทึกวันที่ เครื่องมือ โมเดลเท่าที่ตรวจสอบได้ Prompt, Input, Output และสถานะตรวจ
- ห้ามมีเพียงชื่อไฟล์หรือคำว่า “สำเร็จ” ต้องมีเนื้อหาเพียงพอให้เทียบตรวจ
- แยก **เกณฑ์ที่คาดหวัง / ผลรันล่วงหน้า / ผลของนักศึกษา** ให้ชัดเจน คำตอบไม่ต้องตรงทุกคำ แต่ต้องผ่านเกณฑ์เดียวกัน
- หากรันไม่ได้ ให้ระบุ **“ตัวอย่างประกอบ — ยังไม่ได้รันจริง”** พร้อมข้อจำกัด และถือว่ายังไม่ผ่านเกณฑ์ผลรันล่วงหน้า ห้ามแต่งหลักฐาน

เก็บผลแยกขั้น รอบ และเวอร์ชัน ไม่เขียนทับหลักฐานเดิม พร้อมตาราง:

**ขั้น → Prompt → ผลนักศึกษา → ตัวอย่างอ้างอิง → ผลตรวจ → ข้อบกพร่อง → การแก้ไข → ขั้นถัดไป**

หากใช้ไฟล์ตัวอย่างเพื่อเรียนต่อ ต้องบันทึกว่าใช้ผลอ้างอิง ไม่ถือเป็นผลที่นักศึกษารันสำเร็จเอง จบ LAB ด้วยสรุป ผลประเมิน คำถามอภิปราย และข้อจำกัดที่จะแก้ใน LAB ถัดไป

## 5. ข้อกำหนดชิ้นงานและ UI

- FR/NFR ต้องมีกฎธุรกิจ เกณฑ์ยอมรับ และวิธีตรวจที่วัดผลได้
- Flow และโครงสร้างต้องครอบคลุมเส้นทางหลัก/ทางเลือก/ผิดพลาด สถานะ โมดูล ข้อมูลและความสัมพันธ์ หน้าจอ และสิทธิ์
- UI ต้องเปิดผ่านเบราว์เซอร์ คลิก เปลี่ยนหน้า กรอกข้อมูล และทำขั้นตอนต่อเนื่องได้ตามขอบเขต User Story
- ทดลองเลือกเมนู เพิ่มตัวเลือก ส่งออเดอร์ อัปเดต/ติดตามสถานะ และจำลองชำระเงิน พร้อมผลสำเร็จ ข้อผิดพลาด และข้อยกเว้น
- ใช้ข้อมูลจำลอง ระบุส่วนจำลอง เช่น PromptPay การแจ้งเตือน และการสลับบทบาท
- มี UI อ้างอิง วิธีเปิดของนักศึกษา ลำดับคลิก ข้อมูลกรอก ผลที่ควรเห็น ภาพเปรียบเทียบ หลักฐานที่ต้องเก็บ และวิธีรีเซ็ต
- เชื่อมโยง User Story, FR/NFR, Flow, โครงสร้าง, UI และ Test Scenarios เพื่อส่งต่อ Developer/QA
- แยก NFR ที่ตรวจได้ใน Mock-up ออกจากสิ่งที่ต้องทดสอบในระบบจริง เช่น Security, Load และ Availability

## 6. การวัดผลและตรวจรับ

เปรียบเทียบด้วย Input ขอบเขต และเกณฑ์เดียวกัน พร้อม Rubric ตารางบันทึก และหลักฐาน โดยวัด:

- ความครบถ้วนของบทบาท กฎธุรกิจ FR/NFR และความสามารถในการทดสอบ Acceptance Criteria
- ความสอดคล้องและการตรวจสอบย้อนกลับระหว่างชิ้นงาน
- ความสำเร็จของ UI ตาม Test Scenarios
- ข้อขัดแย้ง ข้อมูลตกหล่น สมมติฐานที่ยังไม่ยืนยัน และการรับมือข้อกำหนดเปลี่ยน
- เวลา จำนวนรอบ จำนวนเรียก Agent และต้นทุนที่วัดได้

ระบุเงื่อนไขทดลอง แยกค่าจริงกับค่าประมาณ หากวัดไม่ได้ให้ระบุว่าไม่มีข้อมูล ห้ามสร้างตัวเลขหรือสรุปล่วงหน้าว่า Workflow ซับซ้อนกว่าดีกว่าเสมอ

ข้อกำหนดตรวจรับ:

- ใช้ Placeholder แทนข้อมูลบุคคล บัญชี และ Token จริง
- สร้างแผนภาพด้วย **Excalidraw MCP** เก็บทั้งไฟล์แก้ไขได้และไฟล์แสดงผล
- ทดสอบสไลด์และ UI ด้วย **Playwright CLI** พร้อมภาพหน้าจอและผลจริง
