## ขั้นที่ 5 เสร็จแล้ว: 2 GPU หลัง NGINX least_conn รองรับได้ 384 คน (เพิ่มจาก 192 คนบน 1 ใบ = 2.00 เท่า)

ระดับ N = 128 ถึง 384 ผ่าน SLO ส่วน N = 448 และ 512 ไม่ผ่านติดกัน ตัวยิงจึงหยุดเอง สาเหตุที่ไม่ผ่านคือความเร็วต่อผู้ใช้ (p5) ต่ำกว่า 15 token/วินาที ส่วน TTFT ยังต่ำมาก (ไม่เกิน 0.31 วินาที) และไม่มี error เลย

### ผลตรวจ GPU 2 ใบก่อนวัด

ยิงตรงเข้า vLLM แต่ละตัว ผู้ใช้ 1 คน 5 คำถาม

| vLLM | GPU | ตอนว่าง | ตอนตอบผู้ใช้ 1 คน | ความเร็วผู้ใช้ 1 คน | TTFT |
|---|---|---|---|---|---|
| vllm-1 | GPU 0 RTX 3090 | 51°C | สูงสุด 61°C · clock เฉลี่ย 1,872 MHz (เพดาน 2,115) | 84.0 token/วินาที | 0.032 วินาที |
| vllm-2 | GPU 1 RTX 3090 | 58°C | สูงสุด 66°C · clock เฉลี่ย 1,848 MHz (เพดาน 2,100) | 84.4 token/วินาที | 0.032 วินาที |

**2 ใบเร็วต่างกัน 0.5%** ไม่เกิน 10% จึงไม่ต้องแจ้งเตือน ข้อสังเกตคือตอนรับโหลดเต็ม GPU 1 ร้อนกว่า (73–80°C เทียบกับ GPU 0 ที่ 64–67°C) และ clock ต่ำกว่าราว 2% (~1,800 เทียบกับ ~1,840 MHz) แต่ยังไม่ถึงขั้นลด clock เพราะร้อน

### ทุกระดับ N ของ 2 GPU

วัดระดับละ 30 วินาที ไม่นับ 5 วินาทีแรก

| N | TTFT p50 / p95 (วิ) | token/วิ ต่อผู้ใช้ p50 / p5 | token/วิ รวม | คำถามที่ vllm-1 / vllm-2 ได้รับ | °C GPU 0 / 1 | error | ผล |
|---|---|---|---|---|---|---|---|
| 128 | 0.07 / 0.09 | 45.7 / 44.1 | 5,677 | 854 / 836 | 64 / 73 | 0% | ✅ ผ่าน |
| 192 | 0.10 / 0.12 | 32.0 / 31.0 | 5,969 | 898 / 892 | 66 / 76 | 0% | ✅ ผ่าน |
| 256 | 0.14 / 0.16 | 24.4 / 23.4 | 6,050 | 910 / 893 | 66 / 78 | 0% | ✅ ผ่าน |
| 320 | 0.17 / 0.19 | 20.2 / 19.5 | 6,261 | 925 / 892 | 67 / 79 | 0% | ✅ ผ่าน |
| **384** | 0.20 / 0.23 | 16.6 / **16.0** | 6,157 | 927 / 905 | 67 / 80 | 0% | ✅ ผ่าน |
| 448 | 0.24 / 0.28 | 13.9 / **13.4** | 5,996 | 894 / 860 | 67 / 80 | 0% | ❌ ไม่ผ่าน (ความเร็ว) |
| 512 | 0.29 / 0.31 | 11.6 / **11.1** | 5,718 | 850 / 850 | 67 / 80 | 0% | ❌ ไม่ผ่าน (ความเร็ว) → หยุด |

- **ไม่มีระดับไหนต้องวัดซ้ำ** ระดับที่ใกล้เส้นที่สุดคือ N = 384 ซึ่งได้ความเร็ว 16.0 สูงกว่าเส้น 15 อยู่ 6.7% เกินช่วงก้ำกึ่ง 5%
- GPU ทั้ง 2 ใบทำงาน 100% ทุกระดับ และ least_conn แบ่งงานได้เกือบครึ่งต่อครึ่ง (ต่างกันไม่เกิน 3%)
- ตัวยิงโหลดใช้ CPU รวมราว 100% จากทั้งหมด 1,600% (16 core) จึงไม่ได้เป็นคอขวด

### เทียบตามจำนวน GPU

| จำนวน GPU | สถาปัตยกรรม | รองรับผู้ใช้พร้อมกัน (N) | token/วินาทีรวม | TTFT p95 ที่ N นั้น | เท่าของ 1 ใบ | Efficiency |
|---|---|---|---|---|---|---|
| 1 | ตอบทีละคำถาม | 2 | 82 | 1.605 วิ | 1.00 | 100% |
| 1 | Continuous Batching | 192 | 3,097 | 0.228 วิ | 1.00 | 100% |
| 2 | Continuous Batching · vLLM 2 ตัวหลัง NGINX least_conn | **384** | 6,157 | 0.230 วิ | **2.00** | **100%** |

> **1 ใบ 192 คน → 2 ใบ 384 คน (2.00 เท่า, efficiency 100%)**

**GPU 2 ใบได้งานเท่ากันไหม:** เกือบเท่ากัน แต่ละใบรับคำถามราวครึ่งหนึ่ง และ token/วินาทีรวมที่ความจุเพิ่มขึ้น 1.99 เท่า แม้ GPU 1 จะร้อนกว่า ก็ช้ากว่าเพียงราว 2%

ข้อควรระวังในการอ่านตัวเลข 100%: ชุด 1 GPU วัดทีละ 32 คน ส่วนชุด 2 GPU วัดทีละ 64 คน ขีดจำกัดจริงของ 1 ใบอยู่ระหว่าง 192 ถึง 224 คน และของ 2 ใบอยู่ระหว่าง 384 ถึง 448 คน ดังนั้น 2.00 เท่าจึงถูกต้องตามความละเอียดที่วัด แต่ไม่ใช่ค่าที่แม่นยำ

**ประมาณการ 3 ใบ (เป็นการคำนวณ ไม่ใช่ผลวัด):** 192 × 3 × 100% ≈ **576 คน** (ถ้าคิดจากช่วง 192–224 ต่อใบ จะได้ราว 576–672 คน) ตัวเลขนี้สมมติว่า NGINX และ CPU ยังไม่เป็นคอขวด และ GPU ใบที่ 3 เร็วเท่ากับ 2 ใบนี้
