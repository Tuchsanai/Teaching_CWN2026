## ผลทดสอบจากนอกเครื่อง (ยิงไปที่ `http://203.0.113.10:41234`)

| การทดสอบ | ผล |
|---|---|
| 1. ส่งงาน 1 งานพร้อม key (normal) | **HTTP 202** ได้เลขงาน `130ce94765f0` สถานะ `queued` เวลารอโดยประมาณ 0.5 วินาที ตอนนี้มี Worker 0 ตัว ถามสถานะซ้ำแล้วยังเป็น `queued` |
| 2. ส่งแบบไม่มี key | **HTTP 401** `invalid or missing API key` ส่วน `GET /stats` ที่ไม่มี key ก็ได้ 401 เหมือนกัน |

**งานที่รออยู่ในคิว: 1 งาน** (normal 1, express 0) ตัวเลขฝั่ง gateway ตรงกับที่ RabbitMQ นับได้ ยังไม่มีงานเสียใน Dead-letter queue และเพดานคิว normal ตอนนี้คือ 100

- ไฟล์โค้ดอยู่ที่ `/workspace/vastapp_lab/lab9_hybrid/code/gateway.py` และบนเครื่องที่ `/workspace/lab9/code/gateway.py` ผลทดสอบเก็บไว้ที่ `results/gateway_submit.json` กับ `results/gateway_stats.json`

## อธิบายโค้ด
1. ทุกทางเรียกต้องมี key ตัวเดิม (อ่านจากไฟล์เดียวกับ API แบบ Synchronous) `POST /jobs` บันทึกงานลง SQLite แล้วส่งเข้าคิว `jobs` ซึ่งเป็น durable และเป็น Priority queue (express = 9, normal = 1) ข้อความเป็น persistent จากนั้นตอบเลขงานกับเวลารอโดยประมาณทันที
2. งานที่ Worker ปฏิเสธจะไปลงคิว `jobs.dead` (Dead-letter queue)
3. Backpressure: ถ้างาน normal ที่รอมีถึง 100 × จำนวน Worker จะตอบ 429 พร้อม `Retry-After` ส่วนงาน express รับเสมอ
4. Worker ส่งเหตุการณ์ (เริ่มงาน / เสร็จ / ล้มเหลว / heartbeat) กลับมาทาง exchange `jobs.events` gateway ใช้เหตุการณ์เหล่านี้อัปเดตสถานะงานและสถานะ Worker แต่ละตัว ปลุก `GET /jobs/{id}` ที่รออยู่ได้สูงสุด 10 วินาที และเก็บงานที่เสร็จล่าสุด 12 งานไว้ให้ `/stats`

## เรื่องที่ควรรู้
- **ตอนยังไม่มี Worker ระบบคิดเพดานเหมือนมี Worker 1 ตัว (100 งาน)** ถ้าคิดตรงตามสูตร 100 × 0 = 0 งาน normal จะโดน 429 ทุกงาน และทดสอบข้อ 1 จะไม่ผ่าน
- ใน `/stats` ผมตีความ "ถูกปฏิเสธ" ว่าคืองานที่ gateway ตอบ 429 ส่วน "งานเสีย" คืองานที่ไปอยู่ใน Dead-letter queue
- Worker ที่จะเขียนต่อไปต้องประกาศคิว `jobs` ด้วยค่าตั้งเดียวกัน และส่งเหตุการณ์ตามรูปแบบที่เขียนไว้ใน docstring ด้านบนของ `gateway.py`
- คำสั่ง `rabbitmqctl` ใช้บนเครื่องนี้ไม่ได้ เพราะเปิดไฟล์ `.erlang.cookie` ไม่ได้ (สิทธิ์ไม่พอ) ผมจึงเช็กคิวผ่าน Python แทน
