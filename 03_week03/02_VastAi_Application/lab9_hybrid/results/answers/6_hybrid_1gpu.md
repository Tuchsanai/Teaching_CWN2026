## สิ่งที่เพิ่มใน `lab9_hybrid/code/loadtest.py`
- เพิ่มตัวเลือก `--mode hybrid` โดยผู้ใช้จำลองแต่ละคนจะส่งงานด้วย `POST /jobs` แล้วรอด้วย `GET /jobs/{id}?wait=10` จนงานเสร็จ จากนั้นโหลดภาพด้วย `GET /jobs/{id}/image`
- จับเวลาตั้งแต่ส่งงานจนโหลดภาพเสร็จ ถ้าเกิน 30 วินาที ถูกตอบ 429 หรือได้รหัสผิดพลาดอื่น นับเป็นงานล้ม
- นับจำนวนภาพต่อครั้งจากเหตุการณ์ `done` ที่ Worker ส่งเข้า RabbitMQ (exchange `jobs.events`) แล้วบันทึกเป็นช่อง `avg_images_per_batch` ของแต่ละระดับ
- โหมดเดิม (`sync`) ยังเป็นค่าตั้งต้นและทำงานเหมือนเดิม ส่วนผู้ใช้จำลอง ระดับ N เวลาต่อระดับ และ SLO ใช้ชุดเดียวกับ Baseline ทั้งหมด

## เทียบกับ Baseline (เซิร์ฟเวอร์ตอบภาพทันที)
| | Baseline | ระบบผสม | ต่างกัน |
|---|---|---|---|
| ผู้ใช้พร้อมกันที่ผ่าน SLO | 30 คน | **52 คน** | ×1.73 |
| ภาพต่อวินาทีสูงสุด | 2.15 | **3.80** | ×1.77 |
| GPU utilization ตอนเต็ม | ~60% | **~91%** | |
| เวลาวาดต่อภาพ | 0.47 วินาที (ทีละภาพ) | 0.25 วินาที (ครั้งละ 4 ภาพ) | |

**ทำไมถึงต่างกัน**
1. **วาดหลายภาพพร้อมกัน:** Baseline วาดทีละภาพ ใช้ภาพละ 0.47 วินาที จึงได้สูงสุดราว 2.15 ภาพ/วินาที ส่วน Worker ดึงงานที่รออยู่มาวาดพร้อมกันได้สูงสุด 4 ภาพ ใช้ครั้งละราว 1 วินาที เฉลี่ยภาพละ 0.25 วินาที จึงได้ราว 3.8 ภาพ/วินาที
2. **ยิ่งงานมาก ยิ่งรวมได้มาก:** ตารางแสดงว่าภาพต่อครั้งเพิ่มเองตามโหลด จาก 1.0 ที่ 1 คน เป็น 2.0 ที่ 16 คน และเต็ม 4.0 ตั้งแต่ 32 คน หลังจากนั้นอัตราภาพคงที่ 3.8 ภาพ/วินาที แปลว่า GPU ทำได้เต็มที่แล้ว
3. **GPU แทบไม่ว่าง:** Baseline ทำงานเพียงราว 60% ของเวลา เพราะระหว่างภาพมีช่วงรับคำขอ HTTP และแปลงเป็น JPEG ซึ่ง GPU ไม่ได้ทำงาน ส่วน Worker ได้งานจากคิวต่อเนื่องเป็นชุด จึงใช้ GPU ได้ราว 91%
4. **ความจุโตตามอัตราภาพ:** ผู้ใช้เพิ่ม ×1.73 ใกล้กับอัตราภาพที่เพิ่ม ×1.77 เพราะผู้ใช้แต่ละคนกดซ้ำในอัตราใกล้เดิม จำนวนคนที่รับได้จึงขึ้นกับว่าระบบผลิตภาพได้กี่ภาพต่อวินาที
5. **ข้อเสียตอนโหลดน้อย:** ที่ 1 คน ระบบผสมช้ากว่าเล็กน้อย (0.51 เทียบกับ 0.47 วินาที) เพราะต้องผ่านคิว รอผล และโหลดภาพอีกรอบ
6. **ทำไมไม่มี 429:** คิวรับงานรอได้ 100 งานต่อ Worker หนึ่งตัว แต่ผู้ใช้สูงสุดในการวัดคือ 64 คน คิวจึงไม่เคยเต็ม
