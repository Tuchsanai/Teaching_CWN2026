## Speedup ของ 2 Node (แนวทาง B, Effective Batch 32, ปรับน้ำหนัก 6 ครั้ง ไม่นับ 2 ครั้งแรก)
| | Replica | วินาที/การปรับน้ำหนัก (คำนวณ / สื่อสาร) | ใบ/วินาที | Speedup | Efficiency | เงินต่อ Epoch 800 ใบ |
|---|---|---|---|---|---|---|
| 1 Node | 2 | 20.65 (19.87 / 0.75) | 1.55 | 1.00× | 100% | $0.068 |
| 2 Node | 4 | 14.35 (9.95 / 4.35) | 2.23 | **1.44×** | 72% | $0.101 |

- ทั้ง 2 รอบ checksum ของทุก replica ตรงกัน ขนาด Gradient 7.67 MB ต่อ replica ต่อครั้ง และ VRAM สูงสุด 20.4 GiB ต่อใบ
- **ทำไมไม่ถึง 2 เท่า:** เวลาคำนวณลดลงครึ่งหนึ่งพอดี (19.9 → 9.95 วินาที) แต่เวลาสื่อสารเพิ่มจาก 0.75 เป็น 4.35 วินาที ส่วนนี้มาจาก 2 อย่าง
  - ส่ง Gradient ข้ามอินเทอร์เน็ตใช้ 2–3 วินาที
  - ทุกครั้งต้องรอ replica ที่ช้าที่สุดราว 4–5 วินาที เพราะใบเสร็จแต่ละใบยาวไม่เท่ากัน
- ทุกครั้งของการปรับน้ำหนักอยู่ในช่วง 12.7–16.7 วินาที ไม่มีครั้งไหนสะดุด จึงไม่ได้วัดซ้ำ ค่าอ้างอิงของ LAB 5 (Quebec + Utah) ได้ 1.80×
- **ทำไม Effective Batch ใหญ่คุ้มกว่า:** เวลาสื่อสารเกือบคงที่ต่อการปรับน้ำหนัก 1 ครั้ง batch ยิ่งใหญ่ เวลาคำนวณยิ่งมากเมื่อเทียบกับเวลาสื่อสาร รอบนี้วัดแค่ EB 32 ตามที่สั่ง เกณฑ์ "EB 32 ได้ Efficiency สูงกว่า EB 8" จึงยังไม่ได้ตรวจ
- ค่าของ 3 Node ใน `metrics.json` (1.27–1.74×) เป็นการคำนวณจากเวลาที่วัดได้ ไม่ใช่ผลวัดจริง
