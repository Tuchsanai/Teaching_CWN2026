- `cluster.sh up 2 4 32 --lb round_robin|least_conn --slow 1:40` เลือกวิธีแจกงานได้ และสั่งให้ replica ที่เลือกช้าลงรูปละกี่ ms ได้ เลข replica นับจาก 0 ดังนั้น `1:40` คือ replica ตัวที่ 2 (GPU 1)
- `server.py` อ่านค่า `SLOW_MS` แล้วหน่วงหลังเรียกโมเดล batch ละ (จำนวนรูป × SLOW_MS) โดยไม่หน่วงตอนอุ่นโมเดล และ `/health` แสดงค่านี้ให้เห็น
- ใน NGINX เพิ่ม `zone` เพื่อให้ worker ทุกตัวใช้ตัวนับร่วมกัน least_conn จึงเห็นงานค้างรวมของทุก worker รอบ gpu2 เดิมไม่มี `zone` แต่ round-robin ยังแจกได้ 50:50 เท่าเดิม จึงเทียบกันได้

### ทำไมผลต่างกัน
- **round-robin แจกงานวนเท่ากันทุกตัว และไม่ดูว่าใครยังมีงานค้าง** ตัวที่ช้าจึงยังได้งานครึ่งหนึ่ง แล้วงานไปกองรอคิวที่ตัวนั้น ระบบทั้งหมดเลยเร็วได้แค่ราว 2 เท่าของตัวที่ช้า throughput จึงตันที่ประมาณ 165 รูป/วินาที GPU 0 ทำงานแค่ราว 46% ทั้งที่ยังว่าง และ p95 พุ่งขึ้นเพราะคำขอที่บังเอิญไปตกที่ตัวช้า
- **least_conn ส่งงานให้ตัวที่มีงานค้างน้อยที่สุด** ตัวที่ช้าจะมีงานค้างมากกว่า งานใหม่จึงไหลไปตัวที่เร็วเอง (ประมาณ 80:20) GPU 0 ใช้งานได้ราว 80% throughput จึงสูงกว่า 2.4 เท่า
- **ถ้า replica เท่ากัน** ทั้งสองแบบแจกได้ประมาณ 50:50 และ throughput สูงสุดเกือบเท่ากัน least_conn ได้เพิ่มเล็กน้อยตรงที่ไม่ส่งงานซ้อนให้ process ที่กำลังติด batch ใหญ่ ทำให้ p95 ที่ N สูง ๆ ต่ำกว่า ความจุจึงขึ้นจาก 176 เป็น 256 คน
