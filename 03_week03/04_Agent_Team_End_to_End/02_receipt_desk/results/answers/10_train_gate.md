## ขั้นที่ 10 · เทรน LoRA บน 1 GPU และ 2 GPU + Acceptance Gate (เครื่อง e2e-receipt)

### 1. เตรียมข้อมูล (`code_step10/prep_cord.py`)
- แปลง CORD-v2 เป็น JSONL ตามรูปแบบในโค้ดของทีม: Training **400 ใบ** (สุ่มด้วย seed 0) · Validation 98 ใบ · Test **95 ใบ** + ชุด "อ่านไม่ได้" 20 ใบ
- Test Set ของ CORD มี 100 ใบ แต่ 5 ใบ (te0009, 0037, 0039, 0057, 0076) ไม่มียอดรวม `total_price` ในเฉลย จึงไม่มียอดจริงให้เทียบ เลยตัดออก เหลือ 95 ใบ
- CORD ไม่มีชุดใบที่อ่านไม่ได้ จึงสร้างขึ้น 20 ใบจากรูปใน Test Set (เบลอหนัก 10 ใบ และตัดให้เหลือแค่ครึ่งบนก่อนถึงยอดรวม 10 ใบ) ไว้วัด M5
- CORD ไม่มีชื่อร้านและวันที่ จึงใส่ค่าแทนเป็น `merchant="UNKNOWN"` และ `date="1900-01-01"` ให้ครบสัญญา 5 ช่อง ส่วนตัวเลขแบบอินโดนีเซีย (`41,500`, `28.000`, `118.000,00`) แปลงเป็น `41500.00`
- Test Set มีไม่ถึง 200+20 ใบตาม NFR-01 จึงต้องรันด้วย `--allow-small-test-set` ผลนี้ใช้เป็นการตรวจเบื้องต้นเท่านั้น

### 2. เทรน (โค้ด `train_lora.py` ของทีม)
- **โค้ดของทีมรันผ่านทั้ง 2 รอบโดยไม่ต้องแก้แม้แต่บรรทัดเดียว** จึงไม่มีไฟล์ `*.orig` สิ่งที่ทำเพิ่มมีแค่ติดตั้ง `transformers 5.23 · peft 0.21 · accelerate 1.16` บนเครื่องเช่า
- ค่าที่ใช้เหมือนกันทั้ง 2 รอบ: Qwen3-VL-2B-Instruct · LoRA r16 (alpha 32, เฉพาะส่วนภาษา) · 1 Epoch · global batch 16 (= 25 step) · lr 1e-4 · seed 0 · bf16
  - 1 GPU: `python train_lora.py ...` ใช้ grad-accum 16
  - 2 GPU: `torchrun --nproc_per_node 2 train_lora.py ...` ใช้ grad-accum 8
- เวลาต่อ Epoch อ่านจาก `train_runtime` ของ Trainer (ไม่รวมเวลาโหลดโมเดล) ถ้ารวมเวลาโหลดด้วยจะได้ 217.4 s กับ 117.5 s
- loss สุดท้ายเกือบเท่ากัน (0.0956 กับ 0.0953) กราฟ loss ของ 2 รอบจึงทับกันเป็นเส้นเดียว
- งานทั้งหมดรันใน tmux บนเครื่องเช่า (`pipeline.sh`) จึงทำต่อได้แม้การเชื่อมต่อหลุด

### 3. วัดผล (โค้ด `evaluate.py` ของทีม, backend hf)
- **ตัดสินเรื่องเส้นแบ่งบน Validation ก่อนเปิด Test** ใช้โมเดลหลังเทรนรันบน Validation 98 ใบ แล้วไล่เส้นความมั่นใจตั้งแต่ 0.50 ถึง 0.99
  - M4 อยู่ระหว่าง 49–51% ทุกเส้น เพราะธงเกือบทั้งหมดมาจาก BR-05 ไม่ใช่ BR-04
  - ธงจาก BR-05 มี 48 ใบ ธงจาก BR-04 อย่างเดียวมี 2 ใบ
  - จึงตรึงเส้นไว้ที่ **0.90 ตาม BR-04** แล้วค่อยรัน Test
- ความมั่นใจคำนวณตาม Requirement คือ `total_confidence = exp(ผลรวม logprob ของ token ที่เป็นค่ายอดรวม)`
- ใบที่ติดธงถูกต้องแต่ยอดถูกมีจำนวนมาก เพราะใบเสร็จ CORD มีภาษีหรือค่าบริการ ทำให้ ผลรวม `menu.price` ≠ ยอดรวม เกิน 1.00 ตามกฎ BR-05 (บน Validation มี 44 ใบที่ยอดถูกแต่ติดธงนี้)
- ใบที่โมเดลหลังเทรนตอบผิดโดยไม่ติดธงมี 1 ใบ (te0067) ตอบ 9,500,000 ด้วยความมั่นใจ 0.995
- กับชุดอ่านไม่ได้ 20 ใบ โมเดลหลังเทรนตอบ `"total": "0.00"` ด้วยความมั่นใจ 1.0 ทุกใบ
  - สาเหตุคือ Training Set ไม่มีใบ unreadable เลย โมเดลจึงไม่เคยเห็นตัวอย่างที่ควรตอบ `{"unreadable": true}`
  - ผลรวมรายการ 0 เท่ากับยอดรวม 0 จึงไม่ติดธงทั้ง BR-04 และ BR-05 → ละเมิด M5 ครบ 20 ใบ
- ก่อนเทรน โมเดลมักอ่านเลขแบบอินโดนีเซียผิด เช่น `38.000` อ่านเป็น 38.00 ทำให้ยอดผิดครึ่งหนึ่ง หลังเทรนอ่านถูก (ดู `results/model/sample_answers.md`)
- ใช้ 2 GPU รันพร้อมกัน (GPU0 = หลังเทรน, GPU1 = ก่อนเทรน) ครบ 95 + 20 ใบทั้งสองโมเดลในเวลาที่กำหนด ไม่ต้องลดจำนวนใบ

- **Acceptance Gate: ไม่ผ่าน** โมเดลยังขึ้นใช้งานไม่ได้ เพราะไม่ผ่าน M1 (ขาดไป 1 ใบ), M2 (ผิดเงียบ 1 ใบ), M4 และ M5 ถึงอย่างนั้นการเทรนก็ช่วยมาก: M1 ขึ้นจาก 46% เป็น 95% และ M6 ขึ้นเป็น 100%
- สิ่งที่ควรทำต่อ:
  1. ใส่ใบ unreadable ลงใน Training Set เพื่อแก้ M5
  2. ทบทวน BR-05 กับใบที่มีภาษีหรือค่าบริการ เช่น ให้โมเดลอ่าน subtotal/tax ด้วย เพื่อลด M4
  3. หาข้อมูล Test ให้ครบ 200 + 20 ใบตาม NFR-01
- **การเพิ่ม GPU: คุ้มตามเกณฑ์ NFR-08**
