## 1. เปรียบเทียบ 2 วิธีและเหตุผลที่เลือก

| เกณฑ์ | ก. คิวเดียว `x-max-priority` | ข. 2 คิว ให้ Worker เลือก (ที่เลือก) |
|---|---|---|
| ทำ BR-10 (สลับ 4:1) ได้หรือไม่ | **ไม่ได้** RabbitMQ ส่งข้อความ priority สูงสุดก่อนเสมอ ผู้อ่านขอ "ใบปกติ 1 ใบ" จากคิวเดียวกันไม่ได้ ถ้า reject/requeue ใบด่วนเพื่อไปหาใบปกติ ใบนั้นก็กลับมาอยู่หัวคิวและถูกส่งมาให้อีก จึงวนไม่จบ | **ได้** Worker เลือกได้ว่าจะ `basic.get` จากคิวไหน ใบถัดไปจึงเป็นใบปกติได้พอดีเมื่อถึงรอบ |
| TD-BR10-c (`U1 U2 U3 U4 N1 U5 N2`) | ไม่ผ่าน ได้ `U1…U5 N1 N2` | ผ่าน (ข้อ 4.4) |
| เปลี่ยนชุดที่รออยู่เป็นงานด่วน (FR-18) | แก้ priority ของข้อความที่อยู่ในคิวแล้วไม่ได้ ต้องส่งข้อความใหม่ | ต้องส่งข้อความใหม่เหมือนกัน (ข้อ 3.4) ทั้งสองวิธีเท่ากันในข้อนี้ |
| ความยาวคิวแยกด่วน/ปกติ (G6 · เพดาน 400 / 50 ตาม 6.2) | ต้องนับจาก SQLite เพราะ RabbitMQ ให้ความยาวรวมทั้งคิว | ได้ทั้งความยาวของแต่ละคิวและจากการนับใน SQLite |
| สิ่งที่ต้องจ่ายเพิ่ม | — | ตรรกะการเลือก 1 ฟังก์ชันที่ gateway และ 1 round-trip ภายในเครื่องต่อการหยิบ 1 ครั้ง (หลักมิลลิวินาที เทียบกับเวลาอ่าน 15 วินาที) |

**เหตุผลที่เลือก ข.:** BR-10 เป็นกฎ Must ที่วิธี ก. ทำไม่ได้ และกรณีทดสอบ TD-BR10-c ระบุลำดับที่วิธี ก. ให้ไม่ได้ ส่วนต้นทุนของวิธี ข. มีแค่ฟังก์ชันเดียวและ round-trip เดียว

**ทำไมใช้ `basic.get` ไม่ใช้ `basic.consume`:** ถ้า consume 2 คิวด้วย prefetch 1 RabbitMQ จะส่งมาให้ Worker คิวละ 1 ข้อความ Worker จึงถือใบปกติไว้ 1 ใบระหว่างอ่านใบด่วน Worker อีกตัวหยิบใบนั้นไม่ได้ และลำดับ 4:1 จะเสียไป ส่วน `basic.get` ดึงได้ทีละ 1 ใบจากคิวที่เลือกพอดี ความถี่ที่ต้องการคือ 8 ครั้ง/นาที ภาระของ `basic.get` จึงไม่มีผล

**ทำไมตัวนับต้องอยู่ส่วนกลาง (ตอบ D-05):** BR-10 เขียนว่า "**ระบบ**อ่านใบด่วนติดกันได้ไม่เกิน 4 ใบ" ถ้านับแยก Worker และมี 2 ตัว ลำดับการอ่านของทั้งระบบอาจเป็น `U(w0) U(w1) U(w0) U(w1) U(w0) U(w1) U(w0) U(w1)` คือติดกัน 8 ใบขณะมีใบปกติรอ ซึ่งผิดกฎตามตัวอักษร ส่วนตัวนับกลางที่จองโควตาไว้ก่อน (ข้อ 3.2) ทำให้ไม่เกิน 4 ใบเสมอ (ข้อ 4.2) Worker ต้องเรียก gateway เพื่อ `claim` ก่อนอ่านทุกใบอยู่แล้ว (I1) การวางตัวนับที่ gateway จึงไม่เพิ่มจุดที่ล่มได้

## 3. กติกาการหยิบ (ข้อกำหนดสำหรับผู้ทำ gateway และ Worker)

### 3.1 สถานะที่ gateway เก็บ

| ชื่อ | เก็บที่ | ความหมาย |
|---|---|---|
| `streak` | SQLite ตาราง `gw_state` (1 แถว ไม่หายเมื่อเริ่มใหม่) | จำนวนใบด่วนที่ `claim = go` ติดกันทั้งระบบนับจากใบปกติ `go` ครั้งล่าสุด |
| `reserved[worker_id]` | หน่วยความจำ | Worker ตัวนี้ได้คำตอบ "urgent" จาก I4 ไปแล้วแต่ยังไม่ `claim` (ล้างเมื่อตัวเดิมเรียก I4 อีกครั้ง เมื่อ `claim` หรือเมื่อ Worker ถูกตัดสินว่าล่ม) |
| `nq` · `uq` | นับจาก `gw_receipts` ที่ `status = queued` แยก `priority` | ใบปกติ / ใบด่วนที่รออ่านจริง (ไม่นับสำเนาเก่าในคิว ข้อ 3.4) |
| `W` | จาก heartbeat (I3) | จำนวน Worker ที่ยังทำงาน (ใช้ 1 ถ้าเป็น 0) |

ค่าคงที่ (ตั้งผ่าน env ของ gateway)

| ตัวแปร | ค่า | ที่มา |
|---|---|---|
| `URGENT_STREAK_MAX` | 4 | BR-10 |
| `GUARD_MINUTES` | 115 | 120 (BR-13) − 5 นาทีเผื่อเวลาส่งไป-กลับ ใบที่อ่านค้าง และอ่านซ้ำ |
| `SECONDS_PER_RECEIPT` | 15 | 4 ใบ/นาที (NFR-05) ใช้ค่าที่ช้ากว่าระหว่างค่านี้กับค่าที่วัดได้จาก G6 |
| `IDLE_POLL_SECONDS` | 1 | เมื่อทั้ง 2 คิวว่าง |

### 3.2 I4 `POST /internal/workers/{worker_id}/next` → `{"queue": "urgent" | "normal" | "none", "reason": "…"}`

ทำใน lock เดียว (asyncio.Lock + ธุรกรรม SQLite)

```text
reserved[worker_id] = false                       # ยกเลิกการจองเดิมของตัวนี้
R  = จำนวน Worker อื่นที่ reserved = true
ua = uq − R                                        # ใบด่วนที่ยังไม่มีใครจอง
1. ถ้า nq > 0 และ deadline_guard() เป็นจริง        → "normal"  reason=deadline_guard
2. ถ้า ua > 0 และ (nq = 0 หรือ streak + R < 4)     → "urgent"  reserved[worker_id] = true
                                                      reason = (nq = 0 ? no_normal_waiting : urgent_first)
3. ถ้า nq > 0                                      → "normal"  reason = (ua > 0 ? ratio_4_1 : fifo)
4. ไม่มีงาน                                         → "none"
```

ใน I1 `claim` (เพิ่มช่อง `queue` และ `msg_priority` ในคำขอ)

```text
ถ้า msg_priority ≠ gw_receipts.priority          → "skip"  (สำเนาเก่า ข้อ 3.4)
ถ้าผลเป็น go:  priority = urgent → streak += 1    |   priority = normal → streak = 0
ทุกกรณี: reserved[worker_id] = false
```

ข้อ 2 ใช้ `streak + R` จึงนับใบด่วนที่ Worker อื่นจองไว้แต่ยังไม่ `claim` ด้วย ถ้า Worker 2 ตัวขอพร้อมกันตอน `streak = 3` จะได้ urgent แค่ตัวเดียว

### 3.3 `deadline_guard()`

```text
s = max(SECONDS_PER_RECEIPT, วินาทีต่อใบที่วัดได้)
เรียงใบปกติที่ queued ตาม queued_at (ลำดับเดียวกับ FIFO ของคิว) ให้ i = 1, 2, …
E_i = อายุของใบ (now − accepted_at) + i × s / W        # เวลาที่คาดว่าใบ i จะอ่านเสร็จ นับจากรับแล้ว
คืน true ถ้า max(E_i) ≥ GUARD_MINUTES
```

- `accepted_at` ส่งมาเป็นช่องเสริมใน G2 (เป็นเวลา ไม่ใช่ข้อมูลระบุตัวตน จึงไม่ขัด NFR-07) ถ้าไม่มี ให้ใช้ `queued_at` ของ gateway ซึ่งช้ากว่าไม่เกิน 15 วินาที และอยู่ในค่าเผื่อ 5 นาทีแล้ว
- คำนวณกับใบไม่เกิน 400 แถวทุกครั้งที่หยิบ (≤ 8 ครั้ง/นาที) ภาระไม่มีผล

**คุณสมบัติที่ข้อพิสูจน์ใช้:** หยิบใบปกติ 1 ใบ อายุของทุกใบเพิ่ม s/W และลำดับของทุกใบลด 1 ค่า E จึงคงที่ หยิบใบด่วน 1 ใบ ค่า E เพิ่ม s/W ดังนั้น **ค่า E สูงสุดเพิ่มขึ้นได้เฉพาะตอนหยิบใบด่วน** และ guard หยุดการหยิบใบด่วนเมื่อ E ถึง 115 นาที

### 3.4 การเปลี่ยนชุดที่รออยู่เป็นงานด่วน (G5) และสำเนาเก่า

RabbitMQ ลบข้อความกลางคิวไม่ได้ G5 จึงทำดังนี้

1. ในธุรกรรมเดียว: `gw_receipts.priority = urgent` สำหรับใบที่ `queued` ของชุด
2. publish ข้อความใหม่ `{receipt_ref, job_ref, priority: "urgent"}` เข้า `receipts.urgent` และรอ publisher confirm
3. ข้อความเดิมใน `receipts.normal` ยังอยู่ เมื่อถูกหยิบ I1 จะตอบ `skip` เพราะ `msg_priority (normal) ≠ urgent` แล้ว Worker ack ทิ้ง **โดยไม่นับเป็นการอ่าน** และไม่แก้ `streak`
4. ใบที่ `processing` อยู่ไม่ถูกแตะ (ไม่ขัดจังหวะ) ใบที่จบแล้วถูกข้าม

ผลซ้ำจึงเป็น 0 เพราะแต่ละใบมีข้อความที่ "ถูกต้อง" ได้ 1 ข้อความเท่านั้น และ gateway รับผลครั้งแรกครั้งเดียว (DESIGN 7)
ไม่ตั้ง `x-max-length` ที่คิว เพราะสำเนาเก่าทำให้ความยาวใน RabbitMQ ไม่ตรงกับจำนวนใบจริง เพดาน 400 / 50 ให้ gateway นับจาก `gw_receipts`

### 3.5 วงรอบของ Worker

```text
loop:
  d = I4 next
  if d.queue == "none": sleep(IDLE_POLL_SECONDS); continue
  msg = basic.get("receipts." + d.queue, auto_ack=false)
  if msg is None: continue                         # Worker อื่นหยิบไปก่อน → ถามใหม่ (I4 ล้างการจองเดิมให้)
  c = I1 claim(msg.receipt_ref, queue=d.queue, msg_priority=msg.priority)
  skip → ack · wait → nack(requeue=true), sleep(1) · dead → reject(requeue=false) → DLQ
  go   → อ่าน (timeout 60 วินาที) → I2 ส่งผล → ack | ล้มเหลวครั้งที่ 1–2 → nack(requeue=true) | ครั้งที่ 3 → reject → DLQ
```

### 3.6 Worker ล่ม: ปลดสัญญาเช่าทันทีที่ตรวจพบ

เมื่อ heartbeat ของ Worker เงียบเกิน 15 วินาที (I3) gateway ต้อง (ก) ล้าง `reserved[worker_id]` และ (ข) ตั้ง `lease_until = now` ให้ใบที่ Worker นั้นถืออยู่ ถ้าต้องรอสัญญาเช่า 90 วินาทีหมดเอง กรณี C′ ในข้อ 5.1 จะใช้ 345 วินาที เกิน 5 นาที
การปลดสัญญาเช่าไม่ทำให้เกิดผลซ้ำ เพราะผลที่มาช้าจาก Worker ที่ถูกตัดสินว่าล่มถูกทิ้งตามกติกา "ผลครั้งแรกครั้งเดียว"

### 3.7 บันทึกการตัดสิน (ใช้ทดสอบ)

ทุกครั้งที่เรียก I4 และ I1 gateway บันทึก 1 บรรทัด: `ts · worker · queue · result · streak · nq · uq · reason · receipt_ref` (ไม่มีเนื้อหาใบเสร็จ ตาม NFR-07) การทดสอบ BR-10 ตอนมี Worker 2 ตัวใช้บันทึกนี้ (ข้อ 7)

## 4. พิสูจน์ BR-10 (สลับ 4:1)

### 4.1 นิยาม

"ลำดับการอ่าน" = ลำดับที่ gateway ตอบ `claim = go` (ใบที่ถูกอ่านซ้ำตาม BR-07 นับใหม่ทุกครั้ง) "มีงานปกติรออยู่" = `nq > 0` ตอนตัดสินใจ

### 4.2 ข้อพิสูจน์ (ใช้ได้กับ Worker กี่ตัวก็ได้)

1. ตัวเดียวที่ทำให้มีใบด่วนถูก `claim = go` คือคำตอบ "urgent" จาก I4 ซึ่งต้องผ่านข้อ 2
2. ขณะ `nq > 0` ข้อ 2 ตอบ urgent เฉพาะเมื่อ `streak + R < 4` และเพิ่ม R ทันทีใน lock เดียวกัน ดังนั้น `streak + R ≤ 4` เสมอขณะ `nq > 0`
3. ใบด่วนแต่ละใบที่ `go` เพิ่ม `streak` 1 และลด R 1 ผลรวม `streak + R` จึงไม่เพิ่ม ใบปกติที่ `go` ตั้ง `streak = 0`
4. ดังนั้นระหว่างใบปกติ `go` 2 ครั้ง (หรือตั้งแต่ใบปกติ `go` ครั้งล่าสุด) ขณะมีใบปกติรอ จะมีใบด่วน `go` ได้ไม่เกิน 4 ใบ ∎
5. ถ้า `nq = 0` ใบด่วนต่อกันได้ไม่จำกัด ซึ่งตรงกับ BR-10 ("เมื่อมีงานปกติรออยู่") และ TD-BR10-d เมื่อใบปกติเข้ามาตอน `streak ≥ 4` ใบถัดไปต้องเป็นใบปกติทันที

ผลตามมา: ขณะทั้ง 2 คิวมีงาน ใบด่วนได้ ≥ 4/5 ของการหยิบ (ข้อ 2 ตอบ urgent ทุกครั้งที่ไม่ติดเพดาน) ส่วนใบปกติได้ ≥ 1/5 ตาม NFR-04

### 4.3 กรณีแข่งกันของ Worker 2 ตัว

| เหตุการณ์ | `streak` | R | คำตอบ |
|---|---|---|---|

ลำดับ `go` เป็น `…U U U U N` หรือ `…U U U N U` ก็ได้ (ขึ้นกับว่าตัวไหน claim ก่อน) ทั้งสองแบบมีใบด่วนติดกันไม่เกิน 4

## 5. พิสูจน์เวลา: NFR-03 (≤ 5 นาที) และ BR-13 (≤ 120 นาที)

### 5.0 ตัวแปรและข้อสมมติ

| สัญลักษณ์ | ค่า | ที่มา |
|---|---|---|
| s | 15 วินาที/ใบ/Worker | 4 ใบ/นาที (NFR-05 · D-01 ยังต้องวัด) |
| W | 2 หรือ 1 | NFR-03 |
| d_in (ด่วน) | ≤ 25 วินาที | รอบ dispatcher 5 + ส่งรูปปกติที่กำลังส่งอยู่ให้จบ 10 + ส่งรูปด่วนใบแรก 10 (G5 ที่รูปอยู่บน gateway แล้วใช้ ≤ 6 วินาที ตัวเลขนี้จึงเป็นขอบบน) |
| d_in (ปกติ) | ≤ 15 วินาที | รอบ dispatcher 5 + ส่งรูป 10 |
| t_x | ≤ 10 วินาที/รูป | รูป 10 MB (BR-02) ที่ ≥ 8.4 Mbit/s ใบเสร็จทั่วไป 1–3 MB ใช้ 1–3 วินาที |

| d_out | ≤ 5 วินาที | dispatcher ถามสถานะทุก 5 วินาที แล้วตั้ง `review` |

ข้อสมมติของการพิสูจน์: ไม่มีความล้มเหลวพร้อมกัน 2 อย่าง และการส่งรูปไม่เป็นคอขวดของการอ่าน (ข้อ 5.4 บอกว่าเหลือเวลาเผื่อเท่าใดสำหรับการอ่านซ้ำ)

**การนับครั้งที่หยิบ:** งานด่วนรวม k ใบ ในกรณีแย่สุด (`streak = 4` พอดีตอนงานเข้า และคิวปกติเต็ม) ต้องหยิบทั้งหมด **P = k + ⌈k/4⌉** ครั้ง เช่น k = 10: `N UUUU N UUUU N UU` = 13 ครั้ง · k = 20: 25 ครั้ง

**สูตรขอบบน:** T = d_in + w0 + ⌈P/W⌉ × s + d_out (นำทุกช่วงมาบวกกันตรง ๆ แม้บางช่วงเกิดพร้อมกัน จึงเป็นขอบบน) Worker W ตัวหยิบได้ W ใบต่อรอบ 15 วินาที รอบแรกเริ่มเมื่อใบที่อ่านค้างอยู่จบ

**สายการส่งรูป (ตรวจคู่กัน):** T_x = 5 + 10 + k × t_x + 15 (รอ Worker ว่าง) + 15 (อ่าน) + 5

### 5.2 BR-13 / NFR-04 · ใบปกติมีผลภายใน 120 นาทีนับจากรับแล้ว

กรณีแย่สุดของใบปกติ X:

- BR-11 ทำให้ตอนรับ X มีใบปกติที่ `queued + processing` รวม X ไม่เกิน 400 ใบ
- คิวเป็น FIFO ใบที่เข้ามาหลัง X จึงไม่ทำให้ X ช้าลง
- ใบด่วนที่แทรกได้ต่อวันมีไม่เกิน 5 × 10 = **50 ใบ** (BR-08 × BR-09)
- จำนวนครั้งที่หยิบจนถึง X: P = 400 + 50 = 450

| กรณี | ⌈P/W⌉ × s | T = 15 + w0 + ⌈P/W⌉·s + 5 | กรณีหนัก (w0 = 60) | เกณฑ์ |
|---|---|---|---|---|
| W = 2 | 225 × 15 = 3,375 วินาที | 3,410 วินาที = **56.8 นาที** | 57.6 นาที | ≤ 120 ✓ (เหลือ 63 นาที) |
| W = 1 | 450 × 15 = 6,750 วินาที | 6,785 วินาที = **113.1 นาที** | 113.8 นาที | ≤ 120 ✓ (เหลือ 6.2 นาที) |
| Worker ล่มระหว่างทาง (2 → 1) | ขอบบนคือกรณี W = 1 + ตรวจพบ 15 วินาที + หยิบซ้ำ 1 ครั้ง | 6,815 วินาที = 113.6 นาที | — | ≤ 120 ✓ |

"ไม่ค้างข้ามวัน" (NFR-04): ใบที่รับก่อน 22:00 มีผลไม่เกิน 22:00 + 113.8 นาที = **23:54** (W = 1) หรือ 22:58 (W = 2) ✓

### 5.3 Deadline guard ไม่ทำงานในกรณีที่พิสูจน์ แต่ป้องกันกรณีที่เกินข้อสมมติ

- **ภายใต้ข้อสมมติ:** ค่า E สูงสุดเริ่มที่ 400 × s/W และเพิ่มเฉพาะตอนหยิบใบด่วน ใบละ s/W (ข้อ 3.3)
  - W = 1: 100 + 50 × 0.25 = **112.5 นาที < 115** → guard ไม่ทำงาน
  - W = 2: 50 + 50 × 0.125 = **56.3 นาที < 115** → guard ไม่ทำงาน
  - ข้อพิสูจน์ NFR-03 ในข้อ 5.1 จึงไม่ถูกกระทบ
- **กรณีที่เกินข้อสมมติซึ่ง Requirement ไม่ได้ครอบคลุม:** ช่วง 120 นาทีที่คร่อมเที่ยงคืน (เช่น 23:00–01:00) มีโควตาด่วนได้ 2 วันรวม 100 ใบ ถ้า W = 1 และคิวปกติเต็ม
  - ไม่มี guard: P = 500 → 15 + 15 + 7,500 + 5 = 7,535 วินาที = **125.6 นาที ✗**
  - มี guard: ใบด่วนถูกหยิบได้จน E ถึง 115 นาที (60 ใบแรก) หลังจากนั้นหยิบเฉพาะใบปกติและ E ไม่เพิ่มอีก
  - X จึงมีผลไม่เกิน 115 + 0.25 (ค่า E เกินเส้นได้ไม่เกิน 1 ใบ) + 0.25 (ใบที่อ่านค้าง) + 0.33 (d_in + d_out) ≈ **115.8 นาที ✓**
  - แลกกับงานด่วนในช่วงนั้นที่ช้ากว่า 5 นาที
- **ทางที่เลือกเมื่อ 2 ข้อชนกันจริง:** ป้องกัน BR-13 ก่อน ตาม A-04 ("แซงไม่จำกัดทำให้งานปกติค้างได้ไม่มีเพดาน") และข้อกังวลของเจ้าของใน C-04 ทั้งนี้เกิดได้เฉพาะนอกขอบเขตที่พิสูจน์ไว้ และต้องยืนยันกับลูกค้า (Q-03)

### 6.1 BR-08 · ไม่เกิน 10 ใบต่องาน

|---|---|---|
| 9 | ตั้งด่วนได้ | TD-BR08-a |
| 10 | ตั้งด่วนได้ | TD-BR08-b |
| 11 | `422 urgent_too_large` ชุดยังเป็นงานปกติ ไม่ใช้โควตา | TD-BR08-c |

- นับจำนวนใบ**ทั้งชุด** รวมใบที่อ่านเสร็จแล้ว เพื่อให้ตรงกับ TD-BR08
- ตรวจก่อน BR-09 ชุดที่ไม่ผ่าน BR-08 จึงไม่ใช้โควตา

- ผลที่ใช้ในข้อพิสูจน์: งานด่วน 1 งานมี k ≤ 10 ใบ

### 6.2 BR-09 · ไม่เกิน 5 งานต่อวันปฏิทิน (Asia/Bangkok)

| ตั้งไปแล้ววันนี้ | งานถัดไป | ตรงกับ |
|---|---|---|
| 4 | ตั้งได้ → 5 | TD-BR09-a |
| 5 | `409 urgent_quota` → ยังเป็น 5 | TD-BR09-b |
| เมื่อวาน 23:59 มี 5 · วันนี้ 0 | ตั้งได้ → 1 | TD-BR09-c |

- **นับแบบ atomic:** ทำในธุรกรรมเดียว โดยล็อกแถวโควตาของวันนั้น (`SELECT … FOR UPDATE` บนแถว `urgent_quota(day)` หรือ `pg_advisory_xact_lock(วันที่)`) แล้วนับ `batches.urgent_set_at` ของวัน `(urgent_set_at AT TIME ZONE 'Asia/Bangkok')::date` ถ้ากดพร้อมกัน 2 ครั้งตอนตั้งไปแล้ว 4 งาน จะสำเร็จ 1 ครั้งและได้ `409` 1 ครั้ง จำนวนงานต่อวันจึงไม่ถึง 6 (แถว "สูงกว่า" ของ BR-09)
- **เรียกซ้ำไม่นับซ้ำ:** ตั้งด่วนให้ชุดที่เป็นด่วนอยู่แล้ว → `200` และไม่ใช้โควตา (สอดคล้องกับ G5)
- **การตั้งด่วนตอนอัปโหลด (W7 `urgent=true`)** นับเป็น 1 งานเช่นเดียวกัน
- ตั้งด่วนให้ชุดที่ทุกใบอ่านเสร็จแล้วได้ (ใช้โควตา) เพื่อไม่ให้ผลทดสอบขึ้นกับว่า mock อ่านเสร็จก่อนกดหรือไม่ หน้าเว็บเตือนก่อนกดว่า "ทุกใบอ่านเสร็จแล้ว"
- ผลที่ใช้ในข้อพิสูจน์: ใบด่วนต่อวันมีไม่เกิน 5 × 10 = 50 ใบ

### 6.3 งานด่วนพร้อมกันเกินขอบเขตของ NFR-03 (ตอบ D-06 · รอยืนยัน Q-04)

- **ไม่ปฏิเสธ** เพราะคิวด่วนเป็น FIFO งานที่ตั้งก่อนจึงยังได้ผลตามข้อ 5.1 (งานที่ 1 ของกรณี D ใช้ 240 วินาที) การปฏิเสธจะบังคับให้หัวหน้าทีมกดใหม่เองโดยไม่ทำให้อะไรเร็วขึ้น
- **แจ้งเวลาที่คาดไว้** เมื่องานด่วนที่ยังอ่านไม่จบ ≥ W งาน: หน้า `/batches/[id]` แสดง "งานด่วนอีก n ใบกำลังอ่านก่อน คาดว่าได้ผลในราว M นาที" โดย M = ⌈(d_in + w0 + ⌈P/W⌉ × s + d_out) ÷ 60⌉ คิดจาก P ของใบด่วนที่อยู่ก่อนหน้า + ใบของชุดนี้

## 8. สิ่งที่ต้องแก้ใน DESIGN.md ตามเอกสารนี้

1. หัวข้อ 6.1: เปลี่ยน "ตัวนับต่อ Worker" เป็นตัวนับส่วนกลาง `streak` ที่ gateway + ระบบจอง (ข้อ 3.2) และเพิ่ม deadline guard (ข้อ 3.3) ปิด D-05
2. หัวข้อ 5.8: เพิ่ม I4 `POST /internal/workers/{worker_id}/next` · I1 รับช่อง `queue` และ `msg_priority` และตอบ `skip` เมื่อเป็นสำเนาเก่า
3. หัวข้อ 5.3 (G2 `POST /v1/receipts`): เพิ่มช่องเสริม `accepted_at`
4. หัวข้อ 5.5 (G5): ย้ายใบ = อัปเดต `gw_receipts.priority` + publish ข้อความใหม่ ส่วนสำเนาเก่าถูก skip (ข้อ 3.4)
5. หัวข้อ 7: เมื่อ heartbeat เงียบเกิน 15 วินาที ให้ปลดสัญญาเช่าและล้างการจองของ Worker นั้นทันที (ข้อ 3.6)
6. หัวข้อ 3 / dispatcher: ทุกรอบส่ง G5 และรูปของใบด่วนก่อนใบปกติ
7. ตารางตัวเลขในหัวข้อ 6.1: แทนด้วยตารางข้อ 5.1 – 5.2 (นับครั้งที่หยิบแบบปัดขึ้น + d_in/d_out) และระบุเกณฑ์อัตราขั้นต่ำ 3.8 ใบ/นาที/Worker ไว้ใน D-01
