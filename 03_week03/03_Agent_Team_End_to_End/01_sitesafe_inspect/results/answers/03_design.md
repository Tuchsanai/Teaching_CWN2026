**สิ่งที่ออกแบบตามแต่ละข้อ**

1. **แผนภาพ Mermaid 4 ภาพ** อยู่ใน `DESIGN.md` หัวข้อ 1–4: Architecture · ER Diagram · ลำดับการทำงานตั้งแต่อัปโหลดจนเห็นผล · สถานะของงาน ("รอคิว" → "กำลังตรวจ" → "เสร็จแล้ว" หรือ "ตรวจไม่สำเร็จ")
2. **API Contract เว็บ ↔ gateway** มี 4 API
   - ส่งรูป: `POST /v1/jobs` โดย `job_id` คือรหัสรูปของเว็บ ส่งซ้ำได้ `200` ไม่เกิดงานซ้ำ
   - ถามสถานะ: `GET /v1/jobs/{job_id}` และ `GET /v1/jobs?ids=…` คืนค่า H, V และกรอบ
   - คิวเต็ม: ตอบ `429 QUEUE_FULL` พร้อม `Retry-After` เว็บเก็บรูปไว้ที่ "รอคิว" แล้วส่งใหม่ รูปไม่หาย
   - API key: header `X-API-Key` ทุกคำขอ รวม `/v1/health` ไม่มีหรือผิดตอบ `401` ค่า key อยู่ใน `.env` และไม่ถูกส่งไปที่เบราว์เซอร์
3. **คิว** ใช้ RabbitMQ quorum queue แบบ durable 3 คิว
   - Worker ล่ม: Worker รับทีละ 1 งานและ ack หลังส่งผลสำเร็จ งานที่ยังไม่ ack กลับเข้าคิวเอง ผลซ้ำถูกทิ้ง งานที่ลองครบ 3 ครั้งเป็น "ตรวจไม่สำเร็จ"
   - คิวยาวเกินกำหนด: งานค้าง ≥ `MAX_QUEUE_DEPTH` (ค่าเริ่มต้น 200) ปฏิเสธงานใหม่
4. **เว็บ** มี `GET /api/health` · `POST /api/test/reset` (เปิดด้วย `ENABLE_TEST_RESET=1` และตั้งนาฬิกาทดสอบได้) · `data-testid` ของปุ่มและช่องกรอกทุกหน้า 8 กลุ่มหน้า
5. **`BUG_MODE=1`** ทำให้ Business Rule ผิด 3 ข้อ ทั้งหมดอยู่ในไฟล์กติกาไฟล์เดียว รายชื่ออยู่ที่ `docs/BUGS-SECRET.md` เท่านั้น
6. **ข้อมูลทดสอบ** ครบกรณี "ต่ำกว่า · เท่ากับ · สูงกว่า" เส้นแบ่งของทั้ง 7 Business Rule เช่น 269 ÷ 300 = 89.67% (แดง) · 270 ÷ 300 = 90.00% (ไม่แดง) · 15,728,640 ไบต์ (รับ) · 15,728,641 ไบต์ (ปฏิเสธ)

**สิ่งที่เพิ่มจากที่สั่ง**

- โหมด `AI_MODE=mock`: บริการ `mock-gateway` ทำตาม API Contract เดียวกัน และคืนค่า H, V ตามชื่อไฟล์ เช่น `h0_v2.jpg` เพื่อให้ทดสอบ Business Rule ได้ผลแน่นอนโดยไม่ต้องเช่า GPU
- บริการ `dispatcher` แยกจาก `web` ทำหน้าที่ส่งรูปและถามสถานะ เพื่อให้งานเดินต่อเมื่อผู้ใช้ปิดหน้าจอ (FR-05)

**สิ่งที่ยังไม่ได้ตรวจ:** แผนภาพ Mermaid ยังไม่ได้ลองแสดงผลจริง และตัวเลข SLO ยังไม่ได้วัด เพราะขั้นนี้ยังไม่มีโค้ดและยังไม่ได้เช่าเครื่อง
