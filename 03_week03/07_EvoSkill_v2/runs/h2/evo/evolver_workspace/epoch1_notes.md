# Epoch 1 — บันทึกการวิเคราะห์และการตัดสินใจ

- t1-cafe-bill: 0.6 / 0.5 / 0.5
- t2-split-bill: 0.7 / 0.6 / 0.6

- t4-cashback: 0.4 ×3

## วิธีวินิจฉัย
สร้าง solve.py ของแต่ละ rollout ใหม่จาก trace (Write + Edit ตามลำดับ) แล้วรันกับ
`reference/answers/*/test_solve.py` (โฟลเดอร์ `analysis/replay/`, สคริปต์ `analysis/replay.py`).
ผลที่ได้บอกว่าความผิดพลาดที่ตรวจได้ด้วย test ที่มองเห็นคืออะไร (คะแนนจริงเป็น hidden test จึงต่างจากนี้)

## สาเหตุที่พบ (เรียงตามผลกระทบ)
1. **ใช้ TypeError กับ input ผิดชนิด** — t3-s1, t4-s1/s2/s3 → test Reject ที่คาดหวัง ValueError ไม่ผ่าน
   ทั้งที่ `TypeError` ไม่ใช่ subclass ของ `ValueError`
2. **ไม่ตรวจชนิดเข้มงวด / แปลงค่าเอง** — t1-s2 ใช้ `int()` ทำให้ '2' และ 4500.0 ผ่าน;
   t2-s3, t3-s2/s3 ไม่ตรวจ bool/float; t4-s1 ใช้ `.strip().lower()` กับ tier
3. **ปัดเศษผิดลำดับ** — t1-s2 ปัดทุกขั้น → NoDrift ไม่ผ่าน; t4 ทุกรอบปัดลงก่อนแล้วคูณ ×2 → NoDrift ไม่ผ่าน
   (ตัวอย่าง: 10015 platinum เดือนเกิด ควรได้ 801 แต่ได้ 800)
4. **ใช้ floor กับทิป** — t2-s2 (ไม่ผ่าน hidden ที่ทิปมีเศษ ≥ .5; visible ผ่านหมด)
5. **กฎที่โจทย์ไม่ได้ระบุ** — ไม่แก้ได้ด้วยสกิลทั่วไป (ดูหมายเหตุด้านล่าง)
6. งานเสียรอบ: ใช้ `python3 -I -c "from solve import ..."` ทำให้ ModuleNotFoundError หลายครั้ง;
   expected ที่คิดในใจผิดหลายครั้ง (t1-s1, t2-s1, t3-s1/s3, t4-s3)

## สิ่งที่ตั้งใจ *ไม่* ใส่ในสกิล
- reference มีกฎเฉพาะของร้านที่โจทย์ไม่ได้เขียน (เช่น ระยะ 0 กม. ไม่คิดค่าส่ง, ส่งด่วนจำกัดน้ำหนัก,
  silver ไม่ได้สิทธิ์เดือนเกิด). นี่คือ policy ของ train ไม่ใช่หลักทั่วไป โจทย์ held-out จะมี policy ของตัวเอง
  จึงไม่เขียนเป็นกฎในสกิล มีแค่ checklist ทั่วไปให้ไล่ค่าขอบและ flag ทุกผสม (สกิล spec-reading-thai ข้อ 5)
- ค่าเริ่มต้นการปัด (ยอดเข้าร้าน = half-up, เงินที่จ่ายออก = floor) เป็นข้อตกลงที่ตั้งเองให้ Solver ใช้เมื่อโจทย์เงียบ
  และให้ระบุในคำตอบ ไม่ได้อ้างว่าเป็นกฎของ benchmark

## สกิลที่เขียนสำหรับ skills_v1 (อยู่ใน /evo/staging/)
- `money-arithmetic-rounding/` — exact arithmetic, ปัดครั้งเดียว, ลำดับตัวคูณ/เพดาน, ค่าเริ่มต้นการปัด + `money_helpers.py`
- `strict-input-validation/` — ValueError เท่านั้น, `type(x) is int`, ห้าม coercion + `validators.py`
- `spec-reading-thai/` — แปลงคำเปรียบเทียบไทย, ลำดับการคิด, ค่าขอบ
- `solver-selftest-workflow/` — หมวด test, expected ด้วย Fraction, หลีกเลี่ยง `-I -c`, `test_template.py`

ตรวจแล้ว: ค่าที่ได้จากกฎในสกิลตรงกับ reference สำหรับกรณี NoDrift ของ t1, t4 และ t2 half-up tip

## ถ้ามี epoch ถัดไป ควรดู
- ดูว่า Solver ใช้สกิลแล้วคะแนนขึ้นไหม เทียบกับ epoch 0 ราย task

- ความผิดที่ยังเหลือ น่าจะเป็นกฎของ policy ที่โจทย์ไม่ได้เขียน ซึ่งสกิลทั่วไปแก้ไม่ได้

# Epoch 2 — ผลของ epoch 1 และการแก้ใน skills_v2

## คะแนน epoch 1 (สกิล v1)
- t1: 0.8 / 0.7 / 0.8 · t2: 0.8 / 0.8 / 0.8 · t3: 0.7273 / 0.7273 / 0.6364 · t4: 0.7 / 0.7 / 0.6
- ดีขึ้นทุกโจทย์ จาก epoch 0 (ค่าเฉลี่ยต่อ task ประมาณ +0.2)

## การวิเคราะห์ (replay ด้วย analysis/replay2.py ผ่าน reference tests ทั้ง 12 รอบ)
- solve.py ทุกรอบ **ผ่าน reference tests ที่มองเห็นทั้งหมด (12/12)** ทั้งที่คะแนน hidden ยังไม่เต็ม
  → สิ่งที่ยังขาดอยู่คือพฤติกรรมที่ test ที่มองเห็นไม่ครอบคลุม
- ทุกรอบใช้ Fraction ปัดครั้งเดียว, ตรวจชนิดด้วย `type(x) is int`, raise ValueError ครบ
- t4 ทุกรอบยังให้สิทธิ์เดือนเกิดกับ silver ด้วย (เหมือนกันหมด) → ความต่างจาก reference น่าจะเป็นกฎที่โจทย์ไม่ได้เขียน
- t3 ทุกรอบไม่มีกฎค่าส่งกรณีระยะ 0 และจำกัดน้ำหนักส่งด่วน (เป็นกฎที่โจทย์ไม่ได้เขียนเช่นกัน)
- t3 s1 กับ s3 ตรรกะเหมือนกันทุกจุดที่ตรวจได้ แต่คะแนนต่างกัน 0.09 → ไม่สามารถระบุสาเหตุจากโค้ดได้
- t1 s1/s2/s3 ตรรกะเหมือนกัน คะแนน 0.8/0.7/0.8 → ไม่สามารถระบุสาเหตุจากโค้ดได้

## สิ่งที่แก้ใน v2 (แก้ในที่เดิมของ staging ตามกติกา)
1. `strict-input-validation`: เพิ่มกติกา "ตรวจ input ก่อน early return ทุกชนิด" เพราะ `if amount < 10000: return 0`
   จะคืน 0 แทน ValueError เมื่อ amount=-1 (ยังไม่พบใน epoch 1 แต่เป็นช่องโหว่ที่เห็นได้จากโครงสร้าง)
2. `solver-selftest-workflow/test_template.py`: เพิ่ม test "ค่าผิดใต้เกณฑ์ธุรกิจต้อง raise"
3. `spec-reading-thai`: เพิ่มข้อ "เงื่อนไขที่ให้ผล 0 ต้องอยู่หลังการตรวจ input" และย้ายลำดับข้อ

## ไม่ได้ทำ (ตั้งใจ)
- ไม่เพิ่มกฎ policy ของ train (silver ไม่ได้เดือนเกิด, ระยะ 0 ไม่คิดค่าส่ง ฯลฯ) เพราะเป็นกฎเฉพาะของ train
  และโจทย์ held-out จะมีกฎของตัวเอง; ไม่มีหลักทั่วไปที่ช่วยเดาได้จากโจทย์
- ไม่เปลี่ยน money_helpers / validators เพราะทำงานถูกต้องตามการตรวจทั้งหมด

# Epoch 3 — สถานะ plateau และ skills_v3

## คะแนน epoch 2 (สกิล v2)
- t1: 0.8 ×3 · t2: 0.8 ×3 · t3: 0.7273 ×3 · t4: 0.7 ×3 (สม่ำเสมอทุกรอบ)
- เทียบ epoch 1: t1 และ t4 ดีขึ้น (t4 s3 จาก 0.6 เป็น 0.7), t3 s3 ดีขึ้น (0.636 เป็น 0.727), t2 เท่าเดิม

## การวินิจฉัย
- replay (analysis/replay_e2/) ผ่าน reference tests 12/12 ทุกรอบ, ไม่มี ModuleNotFoundError, process สะอาด
- ช่องว่างที่เหลือยังคงเป็นพฤติกรรม hidden ที่โจทย์ไม่ได้เขียน:
  - t4: silver ได้สิทธิ์เดือนเกิดด้วย (ทุกรอบ)
  - t3: ไม่มีกฎระยะ 0 กม. และไม่จำกัดน้ำหนักส่งด่วน (ทุกรอบ)
  - t1/t2: ค่า 0.8 ทั้งหมด ไม่พบจุดที่ต่างจากข้อกำหนดที่มองเห็น

- skills_v3 = skills_v2 (ไม่เปลี่ยนเนื้อหา) เพราะการเพิ่มกฎเฉพาะ train จะไม่ช่วยโจทย์ held-out
