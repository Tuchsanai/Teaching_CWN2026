# เขียนฟังก์ชันคิดเงินจาก brief ให้ผ่านตัวตรวจแบบซ่อนเคส

จาก epoch 0: Solver เขียนสูตรถูกตามตัวอักษรแต่ได้ไม่เต็ม (0.3–0.6) เพราะ
(1) ไม่เคยรันทดสอบเลย (2) เลือกวิธีปัดเศษเอาเอง บางแบบเสียคะแนน (3) ตัวตรวจน่าจะลองค่านอกโดเมน
ตัวอย่างหลักฐาน: เวอร์ชันที่ตรวจ input แล้ว `raise ValueError` ได้คะแนนสูงกว่าเวอร์ชันที่ไม่ตรวจเล็กน้อย
และเวอร์ชันที่ปัดทิป "ลง" ได้ต่ำกว่าเวอร์ชันที่ปัด "ครึ่งขึ้น"

## ขั้นตอน

1. **อ่าน brief ทีละบรรทัด แล้วทำตารางกฎ** ทุกตัวเลข/เงื่อนไข = 1 กฎ ระบุให้ชัดว่า
   - หน่วย (บาท vs สตางค์ — แปลงให้ครบ เช่น 500 บาท = 50000 สตางค์, 15 บาท/กก. = 1.5 สตางค์/กรัม)
   - เงื่อนไขขอบ: "ตั้งแต่ X" = `>=`, "เกิน X" = `>`, "ไม่เกิน X" = `<=`, "ต่ำกว่า X" = `<`
   - ลำดับการคิด: "บวก VAT เป็นขั้นสุดท้าย", "คูณต่อจากข้อก่อน" → คูณทบกันตามลำดับ
   - เกณฑ์ (threshold) ใช้กับค่าอะไร (เช่น ยอดรวมก่อนลด) — ถ้า brief ไม่บอก ให้ใช้ค่าดิบก่อนปรับใด ๆ
   - ลำดับ cap/เพดานเทียบกับตัวคูณ (เช่น คูณ 2 ตอนเดือนเกิด *ก่อน* แล้วค่อย cap)
2. **ใช้เลขจำนวนเต็ม/`Fraction` ล้วน ห้าม float** (`0.07`, `1.5` ให้เขียนเป็นอัตราส่วนจำนวนเต็ม)
   ถ้า input เป็น float (เช่น ระยะทาง) ให้เทียบเกณฑ์ตรง ๆ ได้ แต่ถ้าต้องคูณให้แปลงด้วย `Fraction(str(x))`
3. **การปัดเศษ — ค่าเริ่มต้นเมื่อ brief ไม่ระบุ**
   - ปัดแบบ "ครึ่งขึ้น" (round half up → `(2*num + den)//(2*den)` สำหรับค่าไม่ติดลบ) **ครั้งเดียวที่ค่าเงินสุดท้าย**
     ห้ามปัดกลางทางทุกขั้น ห้ามใช้ `round()` ของ Python (เป็น banker's rounding) ห้ามใช้ `//` ตรง ๆ (ปัดลง)
     ยกเว้น brief บอกชัดว่าปัดลง/ปัดขึ้น/ปัดทุกขั้น ให้ทำตาม brief
   - เคสหารบิล: ปัดทิปครึ่งขึ้นเป็นสตางค์ก่อน แล้ว `divmod(grand, people)` แจก 1 สตางค์ให้คนแรก ๆ
     ผลรวมของ list ต้องเท่ากับยอดรวมเสมอ (ตรวจด้วย assert ในเทสต์)
   - ผลลัพธ์ต้องเป็น `int` ของ Python เท่านั้น (ไม่ใช่ float/Fraction/bool)
4. **ตรวจ input ตามโดเมนที่ brief ประกาศไว้** (ตัวตรวจลองค่านอกช่วงและชนิดผิดจริง — epoch 1 ยืนยันว่าตรวจแล้วคะแนนขึ้น)
   - ทุกครั้งที่ brief เขียนช่วง/ขั้นต่ำ เช่น "ตั้งแต่ 1", "ตั้งแต่ 0", "0–100", "1–30,000", ค่าที่เป็นได้ไม่กี่ค่า (tier)
     ให้ raise เมื่อหลุดช่วง/ไม่รู้จักค่า — ทำให้ครบ **ทุกพารามิเตอร์** (เช่น cashback: amount < 0 ก็ต้อง error ไม่ใช่เฉพาะ tier แปลก)
   - **ใช้ exception class เดียวสำหรับ input ผิดทุกแบบ ที่เป็นทั้ง ValueError และ TypeError** (ไม่รู้ว่าตัวตรวจคาดอันไหน):
     `class InputError(ValueError, TypeError): pass` แล้ว `raise InputError(...)` ทั้งกรณีหลุดช่วง ชนิดผิด key ขาด ฯลฯ
   - **ช่องจำนวนเต็ม (สตางค์ จำนวนคน/ชิ้น เปอร์เซ็นต์จำนวนเต็ม กรัม) ต้องเป็น `int` จริงเท่านั้น**
     ปฏิเสธ `bool`, `float` (แม้เป็น `5.0`), `str`, `None` — epoch 1 พบว่าเวอร์ชันที่ยอมรับ float จำนวนเต็มได้คะแนนต่ำกว่า 0.1
     ช่องที่เป็นปริมาณต่อเนื่องจริง ๆ (เช่น ระยะทาง กม.) รับ int/float ได้แต่ต้อง finite (ไม่ nan/inf) และห้าม bool
   - ช่อง flag (member, express, birthday) ต้องเป็น `bool` จริง
   - รายการ (list ของ item): ตรวจว่าเป็น list/tuple, ตรวจทีละ item ว่าเป็น dict มี key ครบและค่าอยู่ในช่วง (qty >= 1, price >= 0);
     list ว่างได้ยอด 0 ยกเว้น brief ห้าม
   - ตรวจ input *ก่อน* คำนวณหรือคืนค่าก่อนกำหนดเสมอ (เช่น cashback ยอดต่ำกว่า 100 บาท ต้องตรวจ tier ก่อนคืน 0)
   - อย่าตรวจเกินที่ brief บอกจนปฏิเสธค่าที่ถูกกฎหมาย (ยอด 0 ได้, distance_km เป็น float ได้)
5. **รันทดสอบจริงก่อนจบ** (ใน Bash: `python3 -c` หรือไฟล์ test แยก ห้ามวางทับ `solve.py`)
   - เขียน reference แบบ `Fraction` อย่างตรงไปตรงมาจากตารางกฎ แล้วเทียบกับ solve.py แบบสุ่ม ~1000 เคส
   - เคสขอบบังคับ: ค่าที่เส้นแบ่งพอดี (X-1, X, X+1), ค่าต่ำสุด/สูงสุดของโดเมน, ยอด 0, ค่าที่ทำให้เกิด .5 พอดีตอนปัด,
     ค่ามหาศาล (ไม่เกิดความคลาดเคลื่อน), flag ทั้ง True/False ทุกชุดผสม
   - ตรวจว่าฟังก์ชันชื่อและ signature ตรงกับ brief เป๊ะ และไฟล์เป็น `solve.py` ที่ import ได้โดยไม่มี side effect
6. **สรุปปิดงาน** บอกสั้น ๆ ว่าตีความจุดกำกวมอย่างไร (ปัดเศษ, ลำดับ, threshold) และผลทดสอบที่รันจริง — อย่าอ้างว่าทดสอบถ้ายังไม่ได้รัน

## ขั้นตอนการทดลองเรื่องวิธีปัดเศษ (ทำก่อนเขียนโค้ด)

คะแนนค้างที่ 0.7 ทุกข้อทั้งที่โค้ดตรงกันหมด จึงต้องเทียบวิธีปัดเศษระหว่าง rollout:
รัน `pwd` แล้วดูท้ายชื่อโฟลเดอร์ที่ขึ้นต้นด้วย `-r` (เช่น `.../t4-cashback-r2/sandbox` → r2)

- `r1` (หรือไม่พบ `-rN`): ปัดครึ่งขึ้นครั้งเดียวตอนท้าย (ตามที่เขียนไว้ข้างบน)
- `r2`: ปัดแบบ "ครึ่งไปหาเลขคู่" (banker's) ครั้งเดียวตอนท้าย: ใช้ `round(Fraction)` ของ Python ซึ่งให้ int แบบ half-even ได้ตรง ๆ
  (ส่วนอื่นทำเหมือนเดิมทั้งหมด รวมถึงการตรวจ input)
- `r3`: ปัดครึ่งขึ้น *ทุกขั้น* ที่เป็นเงินสตางค์ (เช่น ยอดหลังลด 5% → ปัดเป็นสตางค์, หลังลดสมาชิก → ปัด, หลัง VAT → ปัด;
  ค่าส่งหลังคูณระยะทาง → ปัด แล้วคูณด่วน → ปัด) ถ้าโจทย์มีขั้นเดียวให้ทำเหมือน r1

ใส่ใน docstring/คอมเมนต์ว่าใช้โหมดใด และสรุปปิดงานให้บอกชื่อโหมด (r1/r2/r3) ด้วย

## กับดักที่พบบ่อย
- ปัดทิป/เงินคืนด้วย `//` ทำให้ปัดลงโดยไม่ตั้งใจ (ได้คะแนนต่ำกว่า half-up ใน epoch 0)
- ใช้ `round()` ได้ .5 → เลขคู่ ผิดกับ "ปัดครึ่งขึ้น"
- ลืมแปลง 15 บาท/กก. → สตางค์ต่อกรัม (ผิดไป 100 เท่า หรือ 1000 เท่า)
- ใช้ `>` แทน `>=` ที่เกณฑ์ "ตั้งแต่"
- ปัด VAT/ส่วนลดทีละขั้นแทนปัดครั้งเดียวตอนท้าย
- รับ `True` เป็น 1 หรือ `5.0` เป็น 5 ในช่องจำนวนเต็ม (ต้องปฏิเสธ)
- ทุก rollout เขียนโค้ดเหมือนกันหมดแล้วยังได้ ~0.6 แปลว่ายังเหลือจุดตีความที่ต้องคิดเอง: ลองไล่ซ้ำว่า ลำดับขั้นตอน/เกณฑ์/จุดที่ปัด ตรงตามตัวอักษรของ brief หรือยัง และเขียนข้อสมมติลงในคอมเมนต์
