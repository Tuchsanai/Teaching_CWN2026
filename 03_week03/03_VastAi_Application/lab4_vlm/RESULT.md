## 7) ข้อสังเกต / สิ่งที่ผู้เรียนควรรู้

- **Fine-tune ไม่ได้สอนให้ "อ่านออก" แต่สอน "กติกาของงาน"**: Base อ่านตัวอักษรได้อยู่แล้ว (JSON ถูก 100%, ยอดรวมถูก 89.5%) สิ่งที่ผิดคือการตัดสินใจ เช่น ช่อง price ต้องเป็นยอดของบรรทัดไม่ใช่ราคาต่อหน่วย, total ไม่ใช่ยอด CASH, ชื่อสินค้าต้องคงคำนำหน้าไว้ตามที่พิมพ์ · ตัวอย่าง 800 ใบสอนกติกาเหล่านี้ได้ใน 6 นาที
- **เทรนแค่ 0.41% ของพารามิเตอร์** ได้ adapter 35 MB เทียบกับโมเดลเต็ม 4.3 GB · server เดียวเสิร์ฟได้ทั้ง Base และ Fine-tuned (vLLM `--enable-lora`) โดยใช้ VRAM ของโมเดลชุดเดียว
- **วัดผลบน Test Set ที่ไม่ได้ใช้เทรน** และใช้พรอมต์เดียวกันทั้งสองโมเดล จึงเทียบกันได้ตรงๆ · validation loss ใช้ดูระหว่างเทรนว่ายังดีขึ้นอยู่หรือไม่ (Epoch 2 ดีขึ้นอีกเล็กน้อย ยังไม่ overfit)
- **เกณฑ์ให้คะแนนเข้ม**: ชื่อผิด 1 ตัวอักษรนับว่าผิดทั้งรายการ · เฉลยของ CORD-v2 เองมีจุดไม่สม่ำเสมอ (ช่องว่าง, อักขระเกิน) ตัวเลข F1 จึงไม่ถึง 100 ได้ง่ายๆ

## 8) แนวคิดทฤษฎีที่ต้องอธิบาย (รายการภาพทฤษฎีที่ควรมี)

1. **VLM คืออะไร** — ภาพใบเสร็จถูกตัดเป็น patch → Vision Encoder แปลงเป็น image token → ต่อกับ token ของพรอมต์ → Language Model สร้างข้อความ (JSON) ทีละ token · ภาพควรสื่อ: "ภาพกลายเป็น token แบบเดียวกับคำ" (ใบเสร็จ 1 ใบ ≈ 500–1100 token)
2. **จาก OCR สู่ Structured Output** — เทียบ 2 ทาง: OCR ได้ข้อความทุกบรรทัดแล้วต้องเขียนกฎแยกเอง กับ VLM ที่ตอบ JSON ตาม schema ตรงๆ · ภาพควรสื่อ: ใบเสร็จ → JSON `{items, subtotal, tax, total}` → แถวในฐานข้อมูล
3. **LoRA** — น้ำหนักเดิม W ถูกแช่แข็ง เพิ่มเมทริกซ์เล็ก A (r×d) และ B (d×r) ข้างๆ: W' = W + BA · rank 8 → เทรน 8.72 M จาก 2,136 M (0.41%) · ภาพควรสื่อ: กล่องใหญ่สีเทา (แช่แข็ง) กับแถบเล็กสีส้ม (เทรน) และไฟล์ adapter 35 MB เทียบโมเดล 4.3 GB
4. **Fine-tune ส่วนไหนของ VLM** — LAB นี้ใส่ LoRA เฉพาะส่วนภาษา ส่วนมองภาพคงเดิม · ภาพควรสื่อ: Vision Encoder (แช่แข็ง) → Language Model (+LoRA)
5. **Training / Validation / Test Set** — 800 ใบใช้ปรับน้ำหนัก · 100 ใบดู loss ระหว่างเทรน · 100 ใบวัดผลสุดท้ายครั้งเดียว ทั้ง Base และ Fine-tuned · ภาพควรสื่อ: กอง 3 กองและลูกศรว่าแต่ละกองใช้ตอนไหน
6. **loss เฉพาะส่วนคำตอบ** — ลำดับ token = [ภาพ][พรอมต์][คำตอบ JSON] คิด loss เฉพาะช่วงคำตอบ · ภาพควรสื่อ: แถบ token ที่ไฮไลต์เฉพาะส่วนคำตอบ
7. **ตัวชี้วัด** — Exact Match ของยอดรวม · Precision / Recall / F1 ของรายการ (ถูกเมื่อชื่อและราคาตรงทั้งคู่) · ภาพควรสื่อ: ตัวอย่างใบเดียว เฉลย 4 รายการ โมเดลตอบ 4 รายการ ถูก 3 → P = R = F1 = 75%
8. **เสิร์ฟ Base + LoRA บน server เดียว** — vLLM โหลดโมเดลเดิมครั้งเดียว แล้วสลับ adapter ตามชื่อโมเดลในคำขอ (`receipt-base` / `receipt-ft`) · ภาพควรสื่อ: เว็บ (เครื่องเรา พอร์ต 3404) → อินเทอร์เน็ต + API key → vLLM บน Vast (GPU) → JSON กลับมา → PostgreSQL
9. **ต้นทุนของการเช่า GPU** — ค่า GPU ต่อชั่วโมง + disk + ค่าดาวน์โหลดต่อ GB · ทั้ง LAB ทางการ 22 นาที = $0.154

## 10) ปัญหาที่เจอ (ไม่ลง README)

- **OOM ตอนเทรนบน 24 GB**: ลำดับยาว ~1,100–1,700 token ต่อใบ การเก็บ activation สำหรับ backward ใช้ราว 6–7 GB ต่อใบ (batch 4 และ batch 2 ล้ม) → ใช้ batch 1 + สะสม gradient 4 รอบ (VRAM สูงสุด 11.3 GB) และคิด logits เฉพาะตำแหน่งคำตอบ
- **host แรกโหลดช้า**: PyPI/Hugging Face ~1 MB/s ทั้งที่โฆษณา 3081 Mbps (ติดตั้ง library 12 นาที, โหลด dataset ไม่ขยับ) → ลบแล้วเปลี่ยน host และเพิ่มขั้นทดสอบความเร็วในสูตร
- ssh ค้างเมื่อสั่งงานเบื้องหลังโดยไม่ปิด stdin → ใช้ `setsid nohup … < /dev/null &` · `pkill -f <ชื่อ>` ฆ่า shell ของตัวเองเพราะชื่อตรงกับ command line
- Git Bash แปลง path `/workspace/...` ใน `docker exec` → ตั้ง `MSYS_NO_PATHCONV=1`
- `vastai create instance --raw` พิมพ์ `instance_api_key` (ใช้ได้เฉพาะเครื่องนั้นและหมดอายุเมื่อลบเครื่อง) ออกมาใน log ของคำสั่ง ทั้งรอบพัฒนาและรอบทางการ → เพิ่มคำเตือนในสูตร · ไม่มีค่านี้ในไฟล์ของ repo
- vLLM เปิดพร้อมใช้ช้ากว่าที่คาด (~3 นาที) เพราะเตรียม engine · LoRA ของ Qwen3-VL ใช้กับ vLLM 0.34 ได้ตรงๆ เมื่อใส่ LoRA เฉพาะส่วนภาษา ไม่ต้อง merge
- เว็บ: การตรวจ `/api/status` ครั้งแรกหลัง `docker compose up` อาจล้มเพราะ container เพิ่งเริ่ม ลองซ้ำแล้วผ่าน
- คำตอบของการรันทางการกล่าวถึงเครื่องของ track อื่น (เห็นจาก `vastai show instances`) แต่ไม่ได้แตะ
