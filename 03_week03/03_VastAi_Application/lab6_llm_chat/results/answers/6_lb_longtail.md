**ผลที่ได้** (ผู้ใช้ 448 คน วัด 90 วินาที ไม่นับ 30 วินาทีแรก มีคำถามยาว 20%)

คำตอบยาวได้ 600 token จริงทุกข้อ ส่วนคำตอบสั้นเฉลี่ย 84 token ทั้ง 2 วิธีไม่ผ่าน SLO ข้อความเร็วต่อผู้ใช้ (ต้องได้อย่างน้อย 15 token/วินาที) เพราะคำตอบยาวใช้ GPU นานกว่าคำตอบสั้นราว 7 เท่า 448 คนจึงเกินกำลังเมื่อมีคำถามยาวปน

**ทำไมผลต่างกัน**
- **Round Robin นับแค่จำนวนคำถาม:** ส่งให้ 2 GPU เท่ากันเป๊ะ (1,201 / 1,201 ข้อ และคำถามยาว 228 / 227 ข้อ) แต่ไม่ดูว่าแต่ละใบยังทำค้างอยู่กี่ข้อ
- **Round Robin ทำให้ GPU 1 ค่อยๆ แน่นขึ้น:** ใบที่ทำหลายข้อพร้อมกันจะตอบแต่ละข้อช้าลง คำถามจึงค้างนานขึ้น แล้วก็สะสมมากขึ้นอีก GPU 1 เลยไต่ขึ้นไปชนเพดาน 256 ข้อของ vLLM คำถามใหม่ต้องเข้าคิวรอ TTFT จึงสูงขึ้น ส่วน GPU 0 ทำแค่ราว 180–200 ข้อ เหลือที่ว่างแต่ไม่ได้ใช้
- **least_conn ส่งไปใบที่ค้างน้อยกว่า:** ทั้ง 2 ใบจึงอยู่ที่ราว 220 ข้อตลอดเวลา ไม่มีใบไหนชนเพดาน TTFT p95 ดีขึ้นราว 4 เท่า token/วินาทีรวมก็สูงขึ้น 5%

ช่วงวินาทีที่ 12–17 มีคิวพุ่งขึ้นสั้นๆ ในทั้ง 2 รอบ (สูงสุด 66 และ 55 ข้อ) แต่ละวิธีวัดแค่รอบเดียว ตัวเลขจึงแกว่งได้บ้าง ส่วนเส้นของ Round Robin ที่ค่อยๆ แยกห่างกันตลอด 90 วินาทีเห็นชัดในกราฟ

**สิ่งที่แก้และไฟล์ผล**
- `code/loadtest.py`: เพิ่มตัวเลือก `--long-frac 0.2 --long-max-tokens 600` คำถามยาวใช้คำสั่งให้ตอบละเอียดเป็นข้อๆ ผลเก็บแยกคำถามสั้นกับยาว และเก็บจำนวนคำถามที่ GPU แต่ละใบกำลังทำทุกวินาทีไว้ด้วย
- ผลอยู่ใน `results/`: `loadtest_mix_round_robin.*` และ `loadtest_mix_least_conn.*`
- `code/report.py`: แยกชุดนี้ออกจากตารางความจุเดิม เพิ่มตารางเทียบ 2 วิธี หัวข้อ `lb_compare` ใน `metrics.json` และกราฟ 2 รูป
  - `results/lb_ttft_p95.png`: TTFT p95 รวม / คำถามสั้น / คำถามยาว
  - `results/lb_running_per_gpu.png`: จำนวนคำถามที่ GPU แต่ละใบกำลังทำ ทุกวินาที
- รัน report ใหม่แล้ว ผลชุดเดิมไม่เปลี่ยน
- ค่า API key ไม่ได้แสดงที่ไหน ตรวจแล้วไม่มีอยู่ในไฟล์ผล
